# i0001-27. closed な issue は原則再オープンしないが、同じ不具合の再発だけは承認を得て再オープンできる

## 背景

従来の要件は「closed な issue は再オープンしない」と一律に定めていた（過去の結論を尊重し、閉じた経緯を AI が覆さないため）。敵対的レビューで、参考実装は「再発バグは再オープン、仕様変更は新規」の分岐を持っており、一律禁止が意図的ならその根拠が要ると指摘された。同じ不具合が再発したとき新規 issue を作ると、過去の調査・修正の経緯と切り離され、再発であるという最重要の情報が issue のつながりから読めなくなる。

## 決定

- closed な issue は**原則**再オープンしない
- ただし**同じ不具合の再発への対応**に限り、ユーザーの承認を得て再オープンしてよい（AI が自動で再オープンしない。承認①の選択肢として提示する）
- 仕様変更・新しい要望は、過去の issue が似ていても常に新規に起票する（閉じた合意を新しい要望で上書きしない）

## 理由

- 再発は「同じ問題がまだ直っていない」ことであり、過去の経緯（調査・修正・レビュー）と同じ場所にある方が原因の特定が速い。再オープンはこの場合に限り経緯の連続性を守る
- 仕様変更・新しい要望は過去の結論と別の合意であり、新規 issue の方が「何が新しく決まったか」が明確になる
- 承認を必須にすることで、「再発かどうか」の判断（一見同じでも原因が違うことがある）を人間に残す

## 却下した案

- **一律再オープン禁止（従来）**: 安全だが、再発対応で経緯が分断される。参考実装の分岐が実用上妥当
- **AI の判断で再オープン可**: 「再発」の判定を AI に委ねると、似て非なる問題を古い issue に混ぜる誤りが起きる。承認で担保する

## 影響

- `10-task-overall-plan.md`（例外フロー: closed な類似 issue の扱い）
- `20-common-step-issue.md` は状態変更をスコープ外としているため、再オープンの操作の置き場は仕様で定める（承認後の操作として全体計画タスクが行う）
