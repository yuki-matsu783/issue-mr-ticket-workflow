# block-chmod フック

## 概要

AI が `chmod` を実行しようとしたときに拒否するフックの要件を定義する。禁止するコマンドの一覧を持ち、`chmod` はその最初の項目である。

- **背景**: Windows の git bash では `chmod` による実行権限の変更が意味を持たず、git のファイルモードの差分としてだけ残ってレビューのノイズになる。環境によって効く・効かないが変わる操作を AI の裁量で行わせない。本機構のスクリプトはすべて `bash <パス>` で呼ぶため、実行権限そのものが要らない。
- **目的**: 実行権限の変更が AI の裁量で行われず、必要な場合はユーザーの判断を経る状態を実現する。
- **スコープ**:
  - 含む: `chmod`（パス付き・ラッパー経由・複合コマンド内を含む）の検知と拒否、拒否メッセージ、禁止コマンドの一覧による拡張、記録、緊急停止
  - 含まない: `git` のコミット・push の直接実行の拒否（`block-direct-git`）、チケットの宣言に基づくコマンドの許可・拒否（`workflow-guard`）、git のファイルモードの設定そのもの

## ユーザーストーリー

**[As a]** レビュアーとして、

**[I want]** 実行権限の変更だけの差分が MR に紛れ込まないでほしい。

**[So that]** レビューで見るべき変更に集中できるため。

**[As a]** 機構の保守者として、

**[I want]** 環境によって結果が変わるコマンドを AI が実行しないよう止め、禁止したいコマンドが増えたら一覧に足すだけで済ませたい。

**[So that]** 環境差による不具合を減らし、禁止の追加でフックのコードを触らずに済むため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が Bash または PowerShell ツールで `chmod` をコマンドとして実行しようとしたとき、Shall フックは拒否し、「実行権限の変更は不要でスクリプトは `bash <パス>` で実行すること」「本当に必要ならユーザーに提案すること」を伝えなければならない。
- When `chmod` が複合コマンドの中にあるとき（`;` `|` `&&` `||` の後、`sudo` などのラッパーの後）、または絶対パス付き（`/bin/chmod`、`/usr/bin/chmod`）で実行されるとき、Shall フックは同じように拒否しなければならない。
- When `chmod` の語がクォートされた文字列・コメント・ヒアドキュメント・検索の対象語・日本語の地の文に現れるだけで、コマンドとして実行される位置に無いとき、Shall not フックは拒否してはならない。
- When 文字列をコードとして受け取る実行系（`eval`、`bash -c`、`xargs` など）が絡んで判定できないが `chmod` の語を含むとき、Shall フックは拒否側に倒さなければならない。
- When AI が提供コマンド（機構のスクリプト）を実行するとき、Shall not フックはその呼び出し文字列だけを見て、スクリプトの内部処理を拒否の対象にしてはならない。
- When 禁止するコマンドを追加・変更するとき、Shall それは判定のコードではなく一覧への追加で行え、追加したコマンドにも上記の規則（複合コマンド・パス付き・誤検知の防止）が同じように適用されなければならない。
- When 一覧に無いコマンドが実行されるとき、Shall not このフックは拒否してはならない（コマンドの許可・拒否は `workflow-guard` が担う）。
- When フックが拒否したとき、Shall その記録（拒否したコマンドの先頭部分）が残らなければならない。記録とメッセージに機密情報を含めない。
- When 拒否メッセージを出すとき、Shall メッセージは他のフックの拒否と機械的に区別できる識別子を持ち、対処を含んでいなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは判定を行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If フックの入力が解釈できない場合、Then フックは拒否側に倒し、拒否の理由に機構の不調であることを含めなければならない。
- If AI がこのフックに拒否された場合、Then AI は別のコマンドや実行系で実行権限を変える迂回を行わず、必要ならユーザーに提案しなければならない。

## 前提条件

- Claude Code のフック機構が使え、Bash / PowerShell ツールへ渡されたコマンド文字列を実行前に検査できること
- 機構のスクリプトが `bash <パス>` で呼ばれ、実行権限を要しないこと

---

## 制約条件

- **技術的制約**: 実体は bash で書き、外部プロセスを起動しない純粋な判定でホットパス（すべてのコマンド実行）に耐える。コマンド位置の判定は `block-direct-git` と共有する。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: 緊急停止（機構全体 / このフックだけ）は環境変数で行い、ユーザーが新しいセッションに対して設定する。AI は同じセッションの中で設定できない
- **外部的制約**: 意図的な文字列の分割などによる回避への対抗は目的としない（既定動作を安全側へ倒す仕組みであり、安全境界ではない）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | すべてのコマンド実行の前に働くため、一覧のコマンドと無関係なコマンドは外部プロセスを起動せずに体感できない時間で通す |
| セキュリティ | 記録とメッセージにコマンド文字列に含まれうる機密情報を出力しない |
| 保守性 | 禁止コマンドの追加は一覧への 1 行の追加で済む。拒否メッセージの識別子は機械的に分類できる |
| テスト容易性 | コマンド文字列を与えて拒否 / 許可を単体テストでき、複合コマンド・パス付き・誤検知の代表例がテストに含まれる。テストは合否件数を出力し失敗時に非 0 で終わる |
