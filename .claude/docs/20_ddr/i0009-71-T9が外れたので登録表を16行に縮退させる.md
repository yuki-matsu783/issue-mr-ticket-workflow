# i0009-71. T9 が外れたので登録表を 16 行に縮退させる

## 背景

### 17 行を支えていたもの

- `i0009-06` は WF801（実行者の不一致）を `PreToolUse` の `Agent` で起動**前**に判定すると決め、§1 の登録表を 17 行にした
- `i0009-26` は WF801 を `systemMessage`（ユーザーへ即時）と `additionalContext`（AI へ）の 2 経路で出すと決め、17 行を維持した。7 行目（`PreToolUse` / matcher `Agent` の `subagent-start-check`）を残す**唯一の根拠**は、`systemMessage` がサブエージェントの起動前に人間へ届く経路であること
- `i0009-54` はその根拠が検証の予定表のどこにも載っていないことを見つけ、§12 に **T9**（`systemMessage` が PreToolUse でユーザーに実際に表示されるか）を新設した。あわせて**外れたときの縮退**を「7 行目を外し、実行者の不一致は `subagent-stop-check` の縮退判定だけに寄せる（登録表は 16 行に戻る）」と、実測の**前に**決めた

### 実測（0031・フェーズ 4c）

証跡を 3 つ揃えた。

1. **人間の一次報告**: プローブ (b) を有効にして `PreToolUse:Agent` で無条件に `systemMessage` を 1 件出している状態で、人間がサブエージェントを 1 つ起動して観測した。**通知は来なかった**（面: VSCode 拡張）
2. **機械側の到達**: 同じ呼び出しをヘッドレス（`claude -p … --output-format stream-json --verbose`）で行うと、出力に `{"type":"system","subtype":"informational","content":"PreToolUse:Agent says: …","level":"notice"}` が **1 件あった**
3. **負のコントロール**: 同じ呼び出しで `logs/hooks/probe-4c.jsonl` に 7 行落ちている（フックは起動していて、出力もしている）

つまり `systemMessage` は破棄されているのではなく、**SDK のメッセージには `level: notice` で載るが、対話 UI が人間に見せない**。要件が求めていたのは「サブエージェントが動き出す前に**ユーザーへ**伝える」なので、前提は外れた。なお `additionalContext` のほうはメインエージェントに**届いた**（この非対称は §3 の記述どおり）。

ユーザーの判断は「`systemMessage` が人間に届くという要件は特に無い」。

### 同じ実測で分かったもう 1 つのこと

`PreToolUse:Agent` の `tool_input` に **`model` は呼び出し側が明示したときだけ入る**。モデルを指定しない起動では `tool_input` が `subagent_type` / `prompt` / `description` の 3 つだけになり、比較する値が無い（= 既定モデルで走る）。一方 `PostToolUse:Agent` には **`tool_response.resolvedModel`** が来る。

## 決定

- **§1 の登録表を 16 行にする**。`PreToolUse` / matcher `Agent` の `subagent-start-check` の行を削除する
- **フック本体 `subagent-start-check.sh` は消さない**。`SubagentStart` の登録（WF802 の要点注入）は残るし、`PreToolUse` の経路も設定を戻せば生き返る。**登録から外すだけ**にする
- `subagent-start-check` の仕様から `PreToolUse` `Agent` の経路（WF801 / WF803 の起動**前**通知）を落とす
- 失うものと受け皿を対で確定させる

| 失うもの | 受け皿 |
|---|---|
| **WF801**（実行者の不一致を起動**前**に伝える） | `subagent-stop-check` の**縮退判定**。「このセッションに `subagent-start-check` の記録が 1 件でもあるか」で引くので、7 行目が外れた状態では印が常に無く、**縮退の側が必ず動く**（`i0009-52` の設計どおり）。比較の材料は `PostToolUse:Agent` の **`tool_response.resolvedModel`**（実測で実在を確認）で、実際に使われたモデルと突き合わせる |
| **WF803**（background 起動を起動**前**に警告） | `subagent-stop-check` の **WF814** が起動直後に同じことを伝える（この実測で実際に発火した。対話で `run_in_background` を省略すると `tool_response.status` は `async_launched`）。WF803 は識別子を**予約**として残し、発行しない |

- `subagent-stop-check` の縮退判定は、仕様の「同じ `tool_response.agentId` についての記録」ではなく**セッション単位**で引く（`PreToolUse` の時点では agentId がまだ発行されておらず、記録に載せられない）
- §2 に「`PreToolUse:Agent` の `tool_input.model` は呼び出し側が明示したときだけ来る（**値が無いことを「一致」と読まない**）」と「実際に使われたモデルは `tool_response.resolvedModel` で比較できる」を書く
- §12 の T9 の行を「実測で外れた」に書き換えて縮退の発動を確定させ、**その後で** §12 を節ごと削除する

## 理由

- **7 行目を残す根拠が 1 本しか無く、それが外れた**。`i0009-54` が縮退条件を実測の前に決めていたので、実測の結果から結論までが機械的に決まった。実測の後に条件を考えていたら「`additionalContext` は届いたのだから」と 17 行を守る議論になっていた。**縮退条件を先に書くことの価値がそのまま出た事例**である
- **`additionalContext` が届いたことは 7 行目を残す根拠にならない**。§12 が先に書いていたとおり、不一致を起こしている当事者（メインエージェント）に「あなたは不一致を起こしています」と伝えても、判断が変わる保証が無い。人間に伝える経路としての価値が前提だった
- **起動前 → 起動直後の遅れは、この 2 つでは実害が小さい**
  - WF803 は「background で起動した」という事実の通知で、起動直後でも取れる手（待つ / 止める）は同じ。しかも WF814 は実測で実際に発火している
  - WF801 は起動前に止められればサブエージェントの実行そのものを避けられるが、後述のとおり**そもそも起動前には比較できないことが多い**
- **`tool_input.model` の実測が、7 行目の価値をさらに下げた**。§2 は「実行者の比較は `tool_input.model` を読める PreToolUse で行う」と書いていたが、モデルを指定しない起動では値が来ない。値が無いことを「一致」と読むと、不一致の検知が静かに効かなくなる。`resolvedModel` は必ず来るので、材料としては起動後のほうが**確実**である。つまり縮退は機能の後退だけでなく、判定材料の改善でもある
- **ホットパスが 1 本軽くなる**。`PreToolUse` の matcher が 1 つ減れば、`Agent` 呼び出しのたびに走るフックが 1 本減る
- **本体を消さないのは、判断が実測 1 件に依存しているため**。面（VSCode 拡張 / ターミナル / SDK）によって `systemMessage` の扱いは変わりうるし、公式の実装が変われば 7 行目は `settings.json` の 1 行を戻すだけで生き返る。実体を消すとその復路が失われ、テスト（SA-T01〜T09）も一緒に失う
- **順序を守る必要がある**。§12 を先に消すと「実装は 16 行・仕様は 17 行・TBD は空」という、もっとも読み違えやすい状態になる。次に仕様を読んだ人が 17 行で作り直す

## 却下した案

- **17 行のまま残し、`systemMessage` が届かないことを承知で登録し続ける**: 誰にも届かない出力のためにホットパスで 1 本走らせることになる。`additionalContext` の側だけを根拠に残す案も、上記の理由（当事者に伝えても意味がない）で価値が無い
- **`systemMessage` の代わりに別の経路で人間に届ける**
  - `decisions.jsonl` を人間が見る: 即時性が無い。起動前に伝える要件を満たさない
  - 拒否に倒して `permissionDecisionReason` で伝える: 「実行者が既定と違う」だけでサブエージェントの起動を止めることになり、重すぎる。ユーザーの判断（「人間に届くという要件は特に無い」）とも合わない
- **`subagent-start-check.sh` の `PreToolUse` の分岐ごと実装から削除する**: 復路が失われる。登録の 1 行を外すのが最小の変更で、テストもそのまま残せる
- **ヘッドレスでは届くのだから、ヘッドレスのときだけ登録する**: 登録は `settings.json` の静的な表で、実行時のモードで切り替えられない。§10（ヘッドレスの判定）はフックの内側の話で、登録の有無には及ばない
- **実測をやり直す（別の面で観測する）**: 観測者は人間で、負のコントロールも揃っている。仮に面を変えて 1 回届いたとしても「対話 UI で確実に届く」とは言えず、要件（起動前にユーザーへ確実に伝える）は満たせない
- **WF803 の識別子を欠番にする**: 起動前の通知が復活したときに同じ事柄を指す識別子が要る。予約として残し、`i0009-45`（テスト ID の通番）と同じく番号の意味を動かさない
