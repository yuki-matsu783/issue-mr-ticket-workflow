# workflow-state-guard フック

## 概要

チケットの着手・完了、レビュー依頼・完了、マージ前作業（片付け・衝突確認・issue への通知・draft 解除）は、すべて機構の提供コマンド経由でのみ行い、AI の自己申告では状態が進まない。このフックは、その経路以外で進行状態を作る操作（進行状態のファイルの直接編集、チケットの置き場への直接の移動や作成、draft 解除の直接実行）を、作業中のチケットの有無を問わず拒否する。本書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

- **背景**: 提供コマンドは遷移の前提条件（未コミット無し・push 済み・ワークの切れ目にいる・変更要求が残っていない など）を 1 か所で検証し、MR への実操作の証跡を記録する。AI がファイルを直接動かしたり状態ファイルを書き換えたりできると、その検証と証跡が意味を失う。`workflow-guard` は作業中のチケットが無いと働かないため、チケットが無い状態（ワークの切れ目・レビュー待ち・全体まとめの片付け後）でも常に働く保護が別に要る。
- **目的**: 進行状態が提供コマンド経由でしか変わらない状態を実現し、AI が状態を作って先へ進むことを防ぐ。
- **スコープ**:
  - 含む: 進行状態のファイルの保護（編集・削除・復元・上書きの拒否）、作業中・完了のチケットの置き場への直接の移動・作成の拒否、draft 解除の直接実行の拒否、提供コマンド経由の操作の許可、記録
  - 含まない: チケットの宣言した範囲の強制（`workflow-guard`）、`git` のコミット・push の直接実行の拒否（`block-direct-git`）、ワークの切れ目の判定とレビュー状態の遷移そのもの（提供コマンド）、次のワークのチケットを作業中へ移してよいかの判定（提供コマンドが前提条件として検証する）

---

## ユーザーストーリー

**[As a]** レビュアーとして、

**[I want]** 「レビューを依頼した」「レビューが完了した」「マージ前作業を終えた」という状態が、AI の申告ではなく MR への実操作の証跡に基づいて進んでいてほしい。

**[So that]** MR の差分で「いつ何が依頼され何が確認されたか」を追え、レビューを飛ばして先へ進まれないため。

**[As a]** 機構の保守者として、

**[I want]** 作業中のチケットが無い状態でも、進行状態を作る直接操作は止めてほしい。

**[So that]** ワークの切れ目やレビュー待ちの間に AI が状態を書き換えて次のワークへ進むことを防げるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が進行状態を記録するファイル（レビュー依頼・完了の証跡、マージ前作業の記録）を編集・削除・復元・上書きしようとしたとき（書き込み用のツール・コマンドのどちらでも）、Shall フックは作業中のチケットの有無を問わず拒否し、「状態は提供コマンドでのみ遷移すること」「状態を進めたいなら該当の提供コマンドを実行すること」「前提条件が満たせないならユーザーに報告し、ファイルを編集・削除・復元して状態を作らないこと」を伝えなければならない。
- When AI が進行状態のファイルを読むだけの操作（表示・検索・差分の確認）を行うとき、Shall not フックは拒否してはならない。
- When 提供コマンドが進行状態のファイルを書き換えるとき、Shall not フックは拒否してはならない（提供コマンドが唯一の書き換え経路）。
- When コマンドの文字列に進行状態のファイルの名前が現れるだけで、そのファイルへの書き込みを伴わないとき（説明の地の文・引用など）、Shall not フックは拒否してはならない。
- When AI がチケットを作業中の置き場へ移動・作成しようとしたとき（着手に相当。提供コマンド以外の手段）、Shall フックは拒否し、着手は提供コマンドで行うよう伝えなければならない。
- When AI がチケットを完了の置き場へ移動・作成しようとしたとき（完了に相当。提供コマンド以外の手段）、Shall フックは拒否し、完了は提供コマンドで行うよう伝えなければならない。
- When AI が作業中のチケットの本文（作業ログ・DoD のチェックなど）を編集するとき、Shall not このフックは拒否してはならない（ワークの種類・宣言の改変の拒否は `workflow-guard` が担う）。
- When AI が未着手の置き場にチケットを作成・編集するとき（計画ワークがチケットを起こす操作）、Shall not このフックは拒否してはならない。
- When AI が MR の draft 解除（`glab mr update --ready`、GitHub では `gh pr ready`）を直接実行しようとしたとき、Shall フックは作業中のチケット・ワークの切れ目・レビュー状態を問わず常に拒否し、全体まとめの提供コマンド経由で行うよう伝えなければならない。
- When 全体まとめの提供コマンドが draft を解除するとき、Shall not フックは拒否してはならない。
- When フックが拒否したとき、Shall その記録（操作の種類・対象・拒否の種類）が残り、フィードバック計画の振り返りで AI とユーザーが参照できなければならない。記録に機密情報を含めない。
- When 拒否メッセージを出すとき、Shall メッセージは拒否の種類ごとに機械的に区別できる識別子を持ち、使うべき提供コマンドと、前提条件が満たせないときの対処（ユーザーへの報告）を含んでいなければならない。
- When フックが対処を求めるとき、Shall ユーザーへの確認ではなく拒否と案内で対処し、ユーザーが応答できない実行形態でも AI が提供コマンドで復旧できなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは判定を行わず、停止していることが記録から分かるようにしなければならない。
- If `glab` / `gh` が使えない環境で提供コマンドが外部委任モード（MCP ツールでリモート操作を代行）で動いている場合、Then フックは提供コマンド経由の操作を同じように許可し、MCP ツールによる draft 解除の直接実行は提供コマンドの検証を経ていないため拒否の対象としなければならない。

### 例外フロー

- If フックの依存（入力の解釈・補助ファイル）が壊れて判定できない場合、Then フックは進行状態のファイル・チケットの置き場・draft 解除に関わる可能性のある操作を拒否側に倒し、拒否の理由に機構の不調であることを含めなければならない。それらと無関係と確定できる操作は止めない。
- If AI がこのフックに拒否された場合、Then AI は進行状態の直接編集・別の手段での迂回・機構の緊急停止を行わず、提供コマンドを実行するか、前提条件が満たせないことをユーザーに報告しなければならない。

---

## 前提条件

- チケットの着手・完了、レビュー依頼・完了、マージ前作業を行う提供コマンドが導入され、それぞれが進行状態のファイルの唯一の書き換え経路であること
- 進行状態のファイルの置き場と、チケットの置き場（未着手 / 作業中 / 完了）が作業領域の中で決まっていること
- 作業は default ブランチ以外の feature ブランチ上で行われること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。`workflow-guard` とは独立に働き、作業中のチケットが無くても判定する。コマンドの判定は「コマンドとして実際に実行される位置にあるか」で行い、地の文や引用の語で誤って拒否しない（判定の共通部分は `block-direct-git` と共有する）
- **ビジネス的制約**: 進行状態の遷移とその前提条件の検証は提供コマンドが持ち、このフックは経路を塞ぐだけで判定の規則を複製しない
- **外部的制約**: 悪意ある迂回への対抗は目的としない（既定動作を安全側へ倒す仕組みであり、安全境界ではない）

---

## 依存関係

- チケットの着手・完了・レビュー依頼と完了・マージ前作業の提供コマンド（許可対象であり、進行状態のファイルの書き換え元。未作成）
- `workflow-guard`（作業中のチケットの宣言の強制と自己改変の拒否。未作成）
- `block-direct-git`（コマンド位置の判定を共有。未作成）
- `workflow-entry`（レビュー待ち・マージ前作業中の継続条件に進行状態を使う。未作成）
- `.claude/rules/`（bash 規約、ユーザーが応答できない実行形態の考慮）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | すべての書き込みと実行の前に働くため、無関係な操作の判定は体感できない時間（数十 ms）で終わる |
| セキュリティ | 記録とメッセージに機密情報を含めない。進行状態の証跡が AI の申告で書き換えられない |
| 可用性 | 判定できないときは関係しうる操作だけを拒否側に倒し、無関係な操作を止めない |
| ヘッドレス耐性 | 確認を使わず拒否と案内だけで対処し、AI が提供コマンドで復旧できる |
| 保守性 | 保護対象（進行状態のファイル・チケットの置き場・draft 解除）の追加が限られた箇所で済み、拒否メッセージの識別子は機械的に分類できる |
| テスト容易性 | 操作と作業領域の状態を与えて、許可 / 拒否とメッセージを単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
