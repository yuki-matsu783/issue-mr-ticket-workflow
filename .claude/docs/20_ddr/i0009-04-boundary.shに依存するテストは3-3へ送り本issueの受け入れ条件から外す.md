# i0009-04. boundary.sh に依存するテストは 3/3 へ送り、本 issue の受け入れ条件から外す

## 背景

`workflow-entry` の WE-T10 は「継続条件の判定が、同じ作業領域・`logs/` に対する `boundary.sh status --offline` の `position` と食い違わない」を固定する観点。`boundary.sh` は issue #9 のスコープ外（3/3 で実装）で、この issue の時点では存在しない。同種のテストは `session-start` にも 7 本ある（SS-H01〜04・06〜08。0013 の担当）。

`boundary.sh` が無い環境では、`workflow-entry` の判定結果と「無出力」を比べることになり、**空同士の比較で無意味に通る**（0005 f5 が SS-H09 について指摘したのと同じ形）。

## 決定

- **WE-T10 は 3/3 に送る**。この issue では実装せず、仕様のテスト観点の行に「3/3 に送る」と理由付きで書く
- issue #9 の受け入れ条件 1 の「テストが通る」は、**この issue で実装するフックのテスト**を指すと解釈する。依存先が未実装のテストは対象に含めない
- 同じ判断を `session-start` の 7 本にも適用するかは 0013 が決める（同じ理由が当てはまる見込み）

## 理由

- WE-T10 は「2 つの実装の結果が一致すること」を確かめる観点で、片方が無ければ観点そのものが成立しない
- 偽実装（テスト用のスタブ）で代えると、「本物と一致するか」という観点が「スタブと一致するか」に変わり、テストの意味が失われる
- 最小スタブを作る案は、スタブの忠実度をどこまで上げるかという新しい判断を生み、3/3 で本物を書くときに捨てる作業になる

## 却下した案

- **最小スタブを `wip/tmp/` に置いてテストだけ通す**: 忠実度の判断が必要になり、通っても「本物と一致する」証拠にならない
- **`boundary.sh` をこの issue で実装する**: issue #9 のスコープ外と明記されており、11 本のフックの実装と同時に提供コマンドを 1 本増やすとレビューの単位が壊れる
- **テスト観点そのものを削る**: 3/3 で必要になる観点を消すと、次の issue で書き直しになる

## 影響

- `10_spec/hooks/10-UserPromptSubmit/workflow-entry.md` テスト観点 WE-T10
- `10_spec/hooks/00-SessionStart/session-start.md` のテスト観点（0013 が同じ判断を適用するか決める）
- issue #9 の受け入れ条件 1 の解釈（結果報告に明記する）
