この計画で何をするか

設計に入る前に、答えが出ていないと設計を書けない問いだけを潰す。答えが後続の計画に効かない問いは含めない。

決めたこと

  • 7 つの問いを 4 つのまとまりに束ね、1 まとまり = 1 チケット
  • 0004 は実際にコマンドを動かして確かめる。0007 は外部技術調査チケットとして VS Code の公式ドキュメントを参照する。0003 と 0005 はリポジトリ内の読み取りに限る
  • どのチケットもソースコード・設計文書・.claude/ 配下には書き込まない。直したい箇所は結果レポートに書いて後続フェーズへ回す

対象と範囲

issue #13 の詳細欄は置き場を tools/vscode-ticket-board/ と書いているが、scope-limits.json の implementation は src/** と tests/** を許可し、design は docs/** を許可する。この食い違いを Q5 で確定する。

対象内容根拠・仕様の節
Q1チケットの frontmatter と本文はどのキー・値域・見出し構造を取り、カードに出す 6 項目（番号・タイトル・ticket_type・executor・人間レビュー要否・敵対的レビュー要否）はどこから取れるかissue #13 受け入れ条件 2
Q2現実に起こりうる frontmatter / 本文の壊れ方は何かissue #13 受け入れ条件 7
Q3この実行環境で npm から拡張の開発依存（typescript / @types/vscode / テストランナー）を取得できるか受け入れ条件 9・10、全体計画の保留事項「テストランナーの選択」
Q4取得できない場合、依存ゼロで受け入れ条件 9・10 を満たせるかQ3 が否のときの退避路
Q5拡張のソースと設計文書の置き場として、機構の上限設定と設計文書ルールが想定するパスはどこか全体計画の保留事項「設計文書の置き場」、scope-limits.json
Q6ソース追加が push.sh の push 前チェック 4 項目・.gitignore・commit.sh の自動除外に触れないか実装フェーズで push が止まらないこと
Q7VS Code 拡張の最小構成（package.json の engines.vscode / activationEvents / contributes.commands）、Webview の生成と postMessage、FileSystemWatcher がファイルの移動をどう見せるかの API 事実は何か受け入れ条件 1・4・5。web を持つ type は investigation だけで、設計・実装フェーズからは公式ドキュメントを引けない

方法とステップ

  1. 1

    チケット Markdown の実形と壊れ方（Q1・Q2 / チケット 0003）

    読む場所は ticket.template.md、ticket.sh の frontmatter 書き込み箇所、frontmatter.sh の読み取り実装、task-types.tsv、実在するチケット 6 枚。壊れ方は yaml_escape と set_field が通す形を読み、手で壊した例を wip/tmp/ に置いて読み取りの挙動を見る。

  2. 2

    ビルド・テスト環境の成立性（Q3・Q4 / チケット 0004）

    node --version / npm --version とレジストリへの到達確認を行い、wip/tmp/ に捨てるプロジェクトを作って npm install --no-save を実際に走らせる。取得できない場合に備え、Node 標準の node:test が同じ環境で動くかを併せて確かめる。vscode を import したモジュールが VS Code ホスト外で解決できるかという事実だけを記録し、層の分け方の決定は設計へ回す。VS Code 本体・code CLI の有無と、無い場合の受け入れ確認の代替手段も見る。

  3. 3

    既存機構との境界と置き場（Q5・Q6 / チケット 0005）

    scope-limits.json の types、rules/design-docs.md、要件書と仕様書のディレクトリ規約、push.sh の検査 4 項目、exclude-patterns.txt、.gitignore を読む。上限設定を変えずに置ける選択肢を列挙し、変更が要る場合はどのフェーズの誰がどの承認で行うかまで答える。

  4. 4

    VS Code API の外部技術調査（Q7 / チケット 0007）

    敵対的レビューの指摘で追加。VS Code の公式ドキュメント（Extension Anatomy / Webview API / workspace.createFileSystemWatcher）を参照し、拡張の最小構成・Webview の生成と postMessage・watcher がファイルの移動をどう通知するかの API 事実を確定する。allow.ops に web を持つ type は investigation だけで、設計・実装フェーズからは公式ドキュメントを引けないため、ここで拾う。

allow.ops の分類についての補足

フック共通仕様の build-test は「上限設定 commands.build-test に列挙されたコマンド、または tests/ / test/ 直下の *.sh」で、本リポジトリの scope-limits.json は "commands": {"build-test": []} と空である。npm は読み取り専用コマンド一覧にも無いため、フックが有効なら npm の実行は分類されず止まる。現状 .claude/settings.json に hooks キーが無くフックは登録されていないので実際には止まらないが、この前提は保留した点に明記した。

検証

成果物は調査結果レポート wip/30_reports/0003-investigation.md / 0004-investigation.md / 0005-investigation.md / 0007-investigation.md と同名の HTML。仕様は「1 タスク 1 レポート、以降は節を追記」と定めているが、本 issue ではチケットごとに 1 本ずつ計 4 本に分けた（仕様からの逸脱として作業ログに記録）。設計計画が判断できる状態を次の 3 点で確かめる。

リスクと復旧

リスク影響対処・巻き戻し
0004 で npm レジストリに到達できないテストランナーの選択肢が狭まり、受け入れ条件 9・10 の満たし方が変わるQ4 の退避路（Node 標準の node:test、依存ゼロ）を同じチケットで確かめる。両方だめなら残課題にして設計計画で扱いを決める
