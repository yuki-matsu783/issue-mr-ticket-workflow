# i0004-03. 片付けから draft 解除までを 1 つの提供コマンドに統合し、チケット無し状態の個別操作を廃する

## 背景

従来は片付け（cleanup）→ push（push.sh）→ draft 解除（ready）を AI が個別に実行する設計で、片付けの後はチケットが存在しないため、機構側に「チケットが無い状態でも push と draft 解除を拒否しない」「振り分けの再宣言を求めない」という例外規定（entry フックの継続判定・push 前チェックの通し方・J 節の規定）を広く持つ必要があった。ユーザーから「1 つのシェルにまとめれば機構チェックの変な考慮が不要になるのでは」と提案された。

## 決定

- `finalize.sh release` の 1 コマンドに統合する: 前提検査（FN001）→ 完了検査（FN002）→ 片付け（`pre_cleanup_sha` 記録・全削除・1 コミット）→ push（内部で push.sh）→ 最終ゲート（base の遅れ・衝突。FN003）→ draft 解除、を段階実行する
- 各段階の完了を `logs/merge-state.json` の `state`（`started` → `cleaned` → `pushed` → `ready`）に記録し、途中で失敗したら**同じコマンドの再実行**で済んだ段階を飛ばして続きから進む（冪等）
- チケットが無い状態で AI に許される操作を「release の再実行」だけに絞る。entry フックの継続判定・機構要件の該当規定をこの狭い形に書き換えた
- 最終ゲート（FN003）で止まった場合、片付けは巻き戻さない。取り込み（merge）をして release を再実行する

## 理由

- チケット無し状態の個別操作が消えると、宣言体系の例外は「1 コマンドの再実行」という点に縮み、entry / guard / push 前チェックの相互作用を考える必要がなくなる（第 2 回敵対的レビューの指摘 1 と同系の穴を構造的に塞ぐ）
- 段階記録により、失敗時のリカバリが「同じコマンドをもう一度」に統一され、AI の判断余地（どこからやり直すか）が消える
- push を内部化しても push 前チェックはそのまま通る（片付け後は wip が空・未コミット無しのため）

## 却下した案

- **cleanup / push / ready の 3 段を AI が順に実行（従来）**: チケット無し状態の操作許可を機構の 3 か所に書く必要があり、規定が広い
- **失敗時に片付けを巻き戻して最初から**: 削除の巻き戻しは破壊的で、push 済みの状態と食い違う危険がある。前進のみの再実行が安全

## 影響

- `00_requirement/skills/10-task-overall-summary.md`・`10_spec/skills/10-task-overall-summary.md`（release への統合・FN の再定義・テスト観点）
- 自己改善ワークフロー機構.md J 節・`hooks/10-UserPromptSubmit/workflow-entry.md`（例外規定の縮小）
- `logs/merge-state.json` のスキーマ（`state` の段階値）
