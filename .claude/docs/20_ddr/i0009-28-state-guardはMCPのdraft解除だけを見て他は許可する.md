# i0009-28. `workflow-state-guard` は MCP の draft 解除だけを見て、他の MCP は許可する

## 背景

`workflow-state-guard` は matcher に `mcp__.*` を含む（MCP 経由の draft 解除を捕まえるため）。しかし制御方式は「書き込みツール（対象パス）」「実行ツール（`cmdpos.sh` でコマンド列）」「入力不正 → deny WF309」の 3 分岐しか無く、**MCP ツールを受け止める分岐が無かった**。

境界レビュー（付録 A の R5）の指摘: `mcp__github__get_issue` は書き込みツールでも実行ツールでもなく、`file_path` も `command` も持たない。制御方式 2・3 のどちらにも当たらず「入力不正」に落ちる。そこの許可カーブアウトは「`tool_input` から**対象パスが読め**、保護対象と無関係と確定できる操作」を条件にしているので満たせず、**すべての MCP 呼び出しが WF309 で拒否**される。

state-guard は拒否側なのでラッパー付きで登録されており、外部委任モード（`gh` 不在時のフォールバック）が機能不全になる。要件が求めているのは draft 解除の拒否だけなので、要件を超える過剰仕様でもある。

## 決定

制御方式に **MCP ツールの分岐**を明示する（入力不正の 1 つ前）。

- `mcp__*pull_request*` / `mcp__*merge_request*` で **`draft` を false にする入力** → **deny WF304**
- **それ以外の MCP ツールは許可**

理由を「このフックが守るのは進行状態ファイル・置き場・draft 解除の 3 つで、MCP ツールがそのうち触り得るのは draft 解除だけ」と書く。テスト `SG-T09` に**負のコントロール**（draft 解除以外の MCP が通ること）を置く。

## 理由

- **拒否側は判定できなければ拒否に倒す**という原則（§3）は、「保護対象に関わり得るのに判断できない」場合のためのもの。MCP ツールは**関わり得る範囲が draft 解除に限られる**と静的に分かるので、原則の適用対象ではない
- 過剰拒否は「守っている」ように見えて、実際には外部委任モードという正当な経路を潰すだけ。守る対象が増えていない
- 負のコントロールを置くのは、「拒否されない」だけの assert が抽出の故障でも通ってしまうため（`20-common-step-shell-script` の「テストの書き方」の規約）

## 却下した案

- **matcher から `mcp__.*` を外す**: draft 解除の直接実行を塞げなくなる。要件（`workflow-state-guard`「draft 解除の直接実行を常に拒否する」）を満たせない
- **MCP ツールを一律 deny のまま、必要なものだけ許可リストに載せる**: 許可リストの保守が必要で、MCP サーバが増えるたびに機構を触ることになる。守る対象（draft 解除）が固定なのだから、そちらを名指しする方が短い
- **入力不正の許可カーブアウトを「対象パスが読める」から「保護対象と無関係と確定できる」に緩める**: 条件が曖昧になり、本当に判断できない入力まで通り得る。MCP という具体的な分岐にする方が安全

## 影響

- `10_spec/hooks/20-PreToolUse/workflow-state-guard.md` 制御方式（4 を新設、旧 4 を 5 に）・外部委任モードの説明・`SG-T09`（新規）
