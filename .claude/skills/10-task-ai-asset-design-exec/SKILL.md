# 10-task-ai-asset-design-exec — AI アセットの正史を書く

共通手順の禁止事項（並列実施しない、サブエージェントを入れ子起動しない、完了済みチケットを戻さない）に加えて、アセット本体（`.claude/skills/`・`hooks/`・`rules/`・`agents/`・`settings.json`）に書き込まない（書きたい内容は仕様書へ。実装は AI アセット実装フェーズ）。要件定義書に内部構造（スクリプト名・判定順・スキーマ）を書かない（仕様書へ）。1:1:1 を崩す文書を作らない。正史に経緯を書かない（経緯は DDR）。テスト観点を機械テストか eval か区別せずに書かない。設計計画書・調査結果レポートを書き換えない。

## 目的

機構自身の要件と仕様を、実装が読める粒度の正史にする。テスト観点まで書き切ることで、実装フェーズが DoD を機械で判定できるようにする。

- 要件: `.claude/docs/00_requirement/skills/10-task-ai-asset-design-exec.md`
- 仕様（正。固有手順・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-ai-asset-design-exec.md`
- 処理の共通手順（正）: `10-task-investigation-exec` の「実施タスクの共通手順（正）」

## 手順

共通手順（入力の確認 → 1 枚ずつ着手 → 実施 → レポートに追記 → コミットと完了 → 次へ）は `10-task-investigation-exec` に従う。実施（共通手順 3）の固有部分は次のとおり。

- 書き方の正は `20-common-step-requirement`（要件: 外部視点・EARS・メイン → 代替 → 例外 → 細部）、`20-common-step-spec`（仕様: アセット種別ごとの節構成・テスト観点）、`20-common-step-ai-asset-creator`（置き場・命名・1:1:1）
- **要件定義書**: 受け入れ条件を EARS の受け入れ基準に落とし、**ヘッドレス実行での帰結**を代替フローに書く
- **仕様書**: 内部の挙動（判定順・入出力・エラー識別子・回復手順）と**テスト観点**を書き、テスト ID を振る。各観点に**機械テスト**（決定論的に検査できる）か **eval**（モデルの振る舞いをログ等で評価する）かを明記する。エラー識別子は既存の採番規則に従う
- 決定は根拠付きで正史に書き、採らなかった案と理由を DDR（`i<issue>-NN`）に残す。既存文書の更新は本文をその時点の正史に書き換える
- **実装を正として仕様に写すときは、実装の該当行（ファイル:行）を作業ログの「判断と根拠」に残す**。仕様に書くのは振る舞いだけなので、何を読んで写したかが正史からは辿れない。後から確かめる人が同じ行に戻れるようにする
- **1 つの決定が同じ文書の何か所に効くかを、書き換える前に列挙する**。処理フローの 1 項目を変えると、概要の要約・IN / OUT・禁止事項・OUT ひな形・要件との対応の表・frontmatter の `description` と `keywords` にも同じ前提が書かれていることが多い。`grep` で先に洗い出し、まとめて直す
- **既存文書を改訂したら frontmatter の `description` と `keywords` を見直す**。本文だけ直して frontmatter が古いままだと、索引と検索が誤った説明を返す
- 計画書の横断整合に挙がった横断文書・用語辞書を更新する（用語の追加は別名も含めて辞書へ）
- 書き終えたらプレースホルダ 0 件・frontmatter（`type: requirement` / `spec`）・要件と仕様の相互参照・用語の整合を確認する
- **設計チケットを分割したときは、各チケットの DoD に「参照先の再読」を入れる**。後のチケットは前のチケットが書き換えた文書を前提に書くため、着手時に古い記憶で書き始めないようにする
- **見てほしい点の固定項目**: 外部視点と内部構造の分離 / テスト ID と機械・eval の区別 / ヘッドレス挙動の記載 / 横断文書・用語辞書との整合

## OUT ひな形

このスキルは固有のテンプレートを持たない。`20-common-step-report-view` の `assets/report.template.md`（と `report.template.html`）をそのまま使い、次を含める。作成・更新した要件定義書・仕様書・DDR・横断文書の一覧（アセットとの 1:1:1 対応）/ 決定と根拠の要約 / 受け入れ条件 × テスト ID（機械 / eval）の対応表 / ヘッドレス挙動の一覧 / 想定と異なった点 / 残課題を含める。

## エラー時の対処

| 状況 | 対処 |
|------|------|
| アセット本体を直したくなった | 直さない。仕様書に書き、実装フェーズへ回す |
| 要件に内部構造を書きたくなった | 書かない。スクリプト名・判定順・スキーマは仕様書へ |
| テスト観点が機械か eval か決まらない | 曖昧なまま書かない。判定方法まで書けるほうに寄せ、書けなければ残課題にする |
| 1 つの決定が文書の複数か所に効く | 1 か所だけ直さない。`grep` で洗い出してまとめて直し、frontmatter も見直す |
| 骨子どおりに書けない | 骨子を書き換えず、書ける範囲を書いて未解決事項として残す |
| 共通手順で止まった（TK005 / RV00x / 書き込み拒否） | `10-task-investigation-exec` の「エラー時の対処」に従う |
