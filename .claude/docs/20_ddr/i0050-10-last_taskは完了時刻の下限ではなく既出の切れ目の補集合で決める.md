# i0050-10. `last_task` は完了時刻の下限ではなく、既出の切れ目の補集合で決める

## 背景

`i0050-01` の並列実施では完了の順序と番号の順序が一致しないため、タスクの範囲（`last_task`）を「番号の連続」ではなく「`ticket_type` のまとまり」で切る形に改めた。その手順は次のようになっていた。

1. 完了チケットのうち、**直前の切れ目より後に完了したもの**（記録の `boundary.last_done` のチケットの `completed_at` より後）を集める
2. 1 種類なら、それが `last_task`
3. 2 種類以上なら、最も早く完了した種類のまとまりを `last_task` とし、**残りは次の切れ目へ持ち越す**

1 と 3 は両立しない。`0011`-investigation → `0012`-design → `0013`-investigation の順に完了した場合、1 回目の切れ目は `{0011, 0013}` で `last_done` = `0013` になる。次の切れ目では「`0013` の `completed_at` より後」だけを集めるので、それより前に完了した `0012` は**二度と集合に入らない**。持ち越したはずのチケットが、どの切れ目にも属さないままレビューを受けずに通過する。番号で切ったときの取りこぼしを塞ぐために入れた仕組みが、時刻で切ることで別の取りこぼしを作っていた。

## 決定

- **`last_task` の絞り込みに完了時刻の下限を使わない。** 代わりに**既出集合の補集合**で決める: `covered` = `logs/review-history.jsonl` の各行の `boundary.tickets` ∪ 現在の `logs/review-state.json` の `boundary.tickets`。完了チケットのうち `covered` に入っていないものを集める
- **`completed_at` を使うのは並べ替えだけ**にする（2 種類以上あるとき、どの `ticket_type` が最も早く完了したかを決める）
- **記録の規則を 1 つに定める**: `request` と `skip` は、`review-state.json` を新しい切れ目の内容で上書きする**前に**、直前の内容を `review-history.jsonl` に 1 行追記する。`complete` は同じ切れ目の更新なので追記しない。これで「1 つの切れ目 = `review-history.jsonl` の 1 行（進行中の切れ目だけが `review-state.json` 側）」が保たれる
- **レビューを省略した切れ目（`skip`）も `boundary.tickets` を残す。** 残さないと、そのタスクのチケットが `covered` に入らず次の切れ目に混ざる
- `review.state` の有効性判定（`boundary.last_done` が現在の `last_task` の最大連番と一致するときだけ有効）は変えない。持ち越しの後は最大連番が一致しなくなるので `none` から始まり、レビュー依頼をやり直せる

## 理由

- 「レビューを一度も受けずに通過するチケットを作らない」が守るべき不変条件で、時刻の下限も番号の連続も**その時点より前を切り捨てる**形なので、持ち越しと構造的に両立しない。切り捨てではなく「まだ扱っていないもの」を直接表す形にすれば、持ち越しは自然に次の回に入る
- 補集合は状態から導けるので、持ち越しのために新しい状態（持ち越し中の番号）を増やさずに済む。増やした状態は、更新を忘れた経路（`skip` だけを通った切れ目・記録の再導出）で必ずずれる
- 記録の追記点を「上書きする側」に一本化すると、「切れ目の数 = 履歴の行数 + 1（進行中）」という数え方が成り立ち、`covered` を作る側が何を読めばよいか迷わない。従来の `complete` での追記のままだと、`skip` で閉じた切れ目が上書きで消え、補集合の材料が欠ける
- 記録が壊れた・消えた場合は `covered` が空になり、完了チケット全件が候補になる（従来と同じ縮退）。レビュー済みのタスクが再び切れ目に出ることはあっても、レビューを受けないチケットは出ない。**倒す向きを「余分に出す」側に揃える**（`i0010-09` と同じ倒し方）

## 却下した案

- **持ち越し中のチケット番号を `review-state.json` に明示的に記録する（`carried_over`）**: 状態が 1 つ増え、`request` / `skip` / `complete` と `status` の再導出のすべてで更新の責任が発生する。更新を落とした経路で持ち越しが消え、いまと同じ症状に戻る。補集合なら状態を増やさずに済む
- **時刻の下限を「直前の切れ目の `completed_at`」から「持ち越したチケットのうち最も古い `completed_at`」に変える**: 持ち越しが 2 世代（`A` を持ち越した次の回でさらに `B` を持ち越す）になると同じ問題が再発する。下限という形そのものが原因である
- **1 つの切れ目で複数の `ticket_type` をまとめてレビューに出す（持ち越しをやめる）**: 「1 つの切れ目で 2 つのタスクをまとめてレビューに出さない」は、レビュー依頼の粒度をタスクに揃えるための決まりで、これを崩すと MR 本文の「変更点」の行とレビュー依頼の対象がタスクと 1:1 でなくなる
- **番号順に戻す**: `i0050-01` の並列実施では完了の順序と番号の順序が一致せず、そもそもの取りこぼしが戻る
- **`review-history.jsonl` を読まず `review-state.json` だけで判定する**: 現在の切れ目の分しか分からないので、2 回前の切れ目に属したチケットが `covered` から漏れ、毎回すべての完了チケットが候補になる

## 影響

- `10_spec/skills/00-workflow-issue-mr-driven.md`「切れ目の判定（正）」の `last_task` の手順を 4 段（`covered` の作成 → 補集合 → 1 種類 → 2 種類以上）に書き換え、`completed_at` の用途を並べ替えに限る旨と、記録の規則を明記する
- 同 `request` 3・`skip` 2・`complete` 5 に追記点の一本化を書き、「進行状態と記録」の `review-state.json` の説明を合わせる
- `BD-T20` の期待値を 2 回の切れ目にわたるものに拡張する（1 回目 `{0011, 0013}`・2 回目 `{0012}`、2 回目の `review.state` が `none`、履歴が 1 切れ目 1 行、どのチケットもどこかの `last_task` に 1 回だけ入る）
- 実装フェーズは、既存の `BD-T01`（`at_boundary` の基本形）と `BD-T07`（追加チケットで `last_done` が変わる）が新しい判定でも通ることを確かめる。`completed_at` を持たない記録の扱いは既存の残課題 R59 のまま
