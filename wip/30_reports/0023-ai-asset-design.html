境界レビュー 2 巡目の A1・A2・B11・B12 を反映した。中心は 0021 が「解消した」と報告した宿題が実は解消しておらず、しかもロックアウト経路を 1 つ開けていたという発見で、実測とパスの構造の両方から確かめた。更新は仕様 4 本・DDR 3 本の訂正（うち 1 本はファイル名も）、新規の DDR は 4 件（i0009-46〜49）。確定したのは 4 つ: (1) ホットパスの jq は最大 2 回（stdin と固定パスで 1 回 + session_id 依存で 1 回。2 回目は構造が強いている）、(2) 副入力は --rawfile + fromjson? // null（--slurpfile は破損・不在で呼び出しごと失敗し stdout を空にする — 実測）、(3) scope.sh の読み込み関数は JSON のファイルを開かない、(4) parse_errors は実行ログ 1 か所とヘルパ 6 つの契約。

  • f2（✕問題）上限を 1 回から 2 回に上げたこと。0021 は「上限が要求に押されて動くなら制約として機能しない」として緩めなかった。今回は緩めているので、「構造が強いているから 2 回」という理由が、次に別の要求が来たときに歯止めとして機能するかを見てほしい

実施した内容と結果

  1. 1

    --slurpfile は副入力の破損で判定ごと落ちる ✕問題 根拠: 境界レビュー A1、実測

    i0009-37 は hook_read_input が jq --slurpfile lim <scope-limits.json> で設定を副入力に渡す形を決めた。実際に走らせると、副入力が壊れているか無いときに呼び出し全体が失敗して stdout が空になる。つまり設定 1 ファイルが壊れた瞬間、フックは tool_name も tool_input.file_path も session_id も取れない。ところが workflow-guard 制御方式 3（WF210 + 復旧経路）と workflow-state-guard 制御方式 0（既定値で続行。i0009-29）はどちらも「tool_name と対象パスが分かっていること」が前提で、相乗りさせると前提ごと失われる。i0009-29 が塞いだロックアウト経路を i0009-37 が別の形で開け直していた。決定: --slurpfile を使わない。存在するファイルだけを --rawfile で文字列として渡し fromjson? // null に通す。存在しないファイルは --argjson <名前> null に差し替える（存在確認は [ -f ] = bash 組み込みで fork しない）。読めなかったことは HC_<名前>_STATE（ok / missing / broken）で伝え、扱いは各フックの制御方式が決める。

    実測への依存: 実測済み（この環境の jq で確認）

    根拠を見る（実行したコマンドと出力） 
    $ printf '{"bad"' > bad.json
$ echo '{"a":1}' | jq --slurpfile lim bad.json '.a'
jq: Bad JSON in --slurpfile lim bad.json: Unfinished JSON term at EOF at line 1, column 6
exit=2      # stdout は空

$ echo '{"a":1}' | jq --slurpfile lim missing.json '.a'
jq: Bad JSON in --slurpfile lim missing.json: Could not open missing.json: …
exit=2      # stdout は空

# 対照（採用する形）
$ echo '{"a":1}' | jq -r --rawfile lim bad.json \
    '{a:.a, lim:(($lim|fromjson?) // null)} | @json'
{"a":1,"lim":null}
exit=0

# --rawfile も「不在」では失敗する → [ -f ] で分岐し --argjson lim null に差し替える
DDR: i0009-47 / テスト: HK-T18

    結論

    実測で塞げるロックアウト経路（0019 の相対パス登録、0020 の設定破損時の拒否に続く 3 つ目）を塞いだ。ただし同じ型の失敗が 3 回続いていることが問題として残る。

  2. 2

    session_id 依存のパスは 1 回目に混ぜられない ✕問題 根拠: 境界レビュー A2、grep -c CLAUDE_SESSION = 0

    i0009-37 は「チケットの frontmatter は純 bash で読むので、残るのは上限設定だけ」と書いていた。これが偽だった。workflow-guard は logs/sessions/<session_id>/approvals.json を判定順 (6) で、workflow-entry は同じ配下の entry.json を手順 3 で読む。session_id は stdin を解析して初めて分かるので、これらを 1 回目の jq に渡すことは原理的にできない（公式に session_id を渡す環境変数は無い）。決定: 上限を「jq だけを起動してよく、呼び出しは最大 2 回」に改め、内訳を固定する — 1 回目 hook_read_input（stdin + 固定パス）、2 回目 hook_read_state（session_id 依存。要るフックだけ）。実際の回数は block-chmod / block-direct-git / workflow-state-guard が 1 回、workflow-guard / workflow-entry が 2 回。

    実測への依存: 一部あり（HK-T19 の期待値は実装で確かめる）

    根拠を見る（読んだ箇所と出力） 
    workflow-guard.md:32   参照: … logs/sessions/<session_id>/approvals.json
workflow-entry.md:34   参照: … logs/sessions/<session_id>/entry.json
grep -c CLAUDE_SESSION wip/tmp/hooks.md → 0
  （session_id は共通入力フィールドとしてのみ与えられる。hooks.md:728）

内訳の固定（これ以上は増えない理由）:
  固定パスの副入力はいくつ増えても 1 回目に相乗りできる
  → 2 回目が要るのは「パスが stdin に依存する」ものだけ

却下: 純 bash の JSON パーサ（入れ子とエスケープで壊れやすい）
      書式を key=value に変える（書き手が独自形式・原子的置換の対象外に）
      session_id で分離するのをやめる（並行セッションの承認が互いに見える）
      承認の記憶を捨てる（要件違反）
DDR: i0009-46 / テスト: HK-T19

    結論

    0019 の f2（✕問題）はここで決着した。0021 の「解消」は固定パスの副入力についてだけ正しかった。上限を緩めた形になるので、歯止めが機能するかを見てほしい。

  3. 3

    scope.sh の読み込み関数はファイルを開かない ◎良 根拠: 境界レビュー B11、i0009-33 の出力の形

    i0009-33 の「出力の形」では scope_load <scope-limits.json> / scope_load_approvals <approvals.json> がパスを取る形だった。jq の回数を hook-common.sh に閉じる決定と並べると、実装者が「どちらが読むのか」を推測することになる。決定: 2 関数からパス引数を外し、hook-common.sh が取り出した HC_* を SC_* に詰め替えるだけにする。読めなかったことは HC_<名前>_STATE から SC_ERROR と戻り値 2 に写す。例外は scope_load_ticket <ticket.md> で、frontmatter.sh（純 bash・fork なし）が読むので上限に関わらない。境界は「ファイルを開くかどうか」ではなく「jq を使うかどうか」。

    実測への依存: 無し（インターフェースの定義）

    根拠を見る（読んだ箇所と出力） 
    変更前: scope_load <scope-limits.json> [type]
        scope_load_approvals <approvals.json>
変更後: scope_load [type]
        scope_load_approvals            （引数なし）
        scope_load_ticket <ticket.md>  （例外。frontmatter.sh は純 bash）

理由: 「jq を呼ぶのは hook-common.sh だけ」と決めれば HK-T19 が意味を持つ
      scope.sh を source する 4 本が「自分が何回呼ぶか」を目で追える
      i0009-17（ライブラリは分類まで / 照合は呼び手）と同じ線引き
却下: 生の JSON 文字列を渡す（解釈にまた jq が要る）
      パスを取り内部でキャッシュ（jq が走るかが呼び手から見えない）
      hook-common.sh が SC_* まで詰める（依存が逆向きになる）
DDR: i0009-48

    結論

    回数の検査（HK-T19）が意味を持つ形になった。i0009-17 の線引きがここでも使えた。

  4. 4

    parse_errors の循環とヘルパの契約 ◎良 根拠: 境界レビュー B12、§5・post-push-usage-report.md

    §5 は「ロックを取得できなければ 2 秒待って諦め、加算せずに parse_errors を +1」と書いていたが、parse_errors が usage/<branch>.json の中にあるならその +1 自体が同じ read-modify-write でロックを要る。しかも post-push-usage-report 仕様のスキーマ列挙に parse_errors は無く、回復手順は実行ログ側を指しており、置き場が仕様内で 2 通りあった。決定: parse_errors の置き場は実行ログ 1 か所。JSON には書かない（理由も §5 に添えた）。あわせて §1 にヘルパの契約の表を置き、切り詰めは hc_append_jsonl が行う・2 秒のタイムアウトは hc_lock が持つ・hc_unlock は冪等を決めた。

    実測への依存: 無し（契約の定義）

    根拠を見る（読んだ箇所と出力） 
    §5（変更前）取得できなければ最大 2 秒待って諦め、加算せずに parse_errors を +1
  → parse_errors が usage/<branch>.json の中にあるなら、その +1 に同じロックが要る（循環）
post-push-usage-report.md:26  usage/<branch>.json のスキーマ列挙に parse_errors は無い
post-push-usage-report.md:77  回復手順は logs/sh/hook-…​.log の parse_errors を指す
  → 置き場が 2 通り

契約の表（§1 に新設）:
  hook_read_input [固定パス...] / hook_read_state <パス>...  引数・戻り値・読む範囲
  hc_append_jsonl   redact → 4KB 未満に切り詰め → >>   （切り詰めはこの関数）
  hc_json_write     .tmp. へ書いて mv        （一時ファイル名は関数）
  hc_lock           mkdir・2 秒で諦める・trap 登録      （タイムアウトは関数）
  hc_unlock         rmdir・冪等
DDR: i0009-49

    結論

    「方針だけ書いても実装で消える」（0021 の fm_* と同じ型）を、関数の契約に落として防いだ。

設計への反映

  1. 0016 へ: ホットパス 5 本のテストに make_counting_path による jq の回数検査（1 回 / 2 回）を入れる。scope.sh に jq の呼び出しが 1 つも無いことも同時に確かめる
  2. 0016 へ: hook_read_input / hook_read_state の実装が先。scope.sh の読み込み関数はそれに依存する
  3. 実装フェーズへ: [ -f ] で存在を確かめてから --rawfile、無ければ --argjson <名前> null。この分岐を hook-common.sh の 1 か所に閉じる
  4. 実装フェーズへ: hc_append_jsonl は redact → 切り詰め → >> の順。hc_lock は取得時に trap へ解放を登録する
  5. 0024 以降へ: 「この決定で塞がらなくなるものは何か」を DDR に書く枠を設けるかを検討する（f1 の申し送り）

想定と異なった点

計画時の見込み実際どう扱ったか
A1 は「--slurpfile を --rawfile に変える」1 行の直し--rawfile も不在では失敗する（破損だけが救われる）。[ -f ] の分岐が要った実験で切り分け、--argjson null へのフォールバックまで決めた
A2 は上限を 2 回に上げれば済む「なぜ 2 回で止まるのか」を書かないと、0021 が退けた「要求に押されて緩む」そのものになる内訳（固定パス / セッション依存）を固定することで歯止めにした
B11 は表の 2 行の書き換え「jq を使うかどうか」が境界だと気づくまで、scope_load_ticket だけ引数を残す理由が説明できなかったi0009-48 の理由に書いた
B12 は parse_errors の置き場を選ぶだけヘルパ 4 つの契約が丸ごと未定義だった（切り詰めの責任・タイムアウトの持ち主・冪等性）表にして §1 に置いた

残課題

  • 穴を塞ぐ決定が別の穴を開ける型が 3 回続いている（f1）。DDR に「この決定で塞がらなくなるものは何か」を書く枠が要るかもしれない。0026 までの間に決める
  • hook_read_state が 1 回で足りるのは今の状態の数による。セッション依存の状態が増えれば同じ問題が繰り返す
  • --rawfile に渡すファイルが巨大になったときの挙動（approvals.json が貯まり続ける経路）
  • [ -f ] と読み取りの間の競合（TOCTOU）。拒否側は安全側に落ちるが案内側は無出力で通る
  • hc_lock の 2 秒が実運用で妥当か（0021 から持ち越し）
  • .claude/rules/markdown-docs.md が存在しないのに ai-asset-design-docs.md が frontmatter の正としてそれを参照している（スコープ外で見つけた。0026 か別 issue で扱う）
