# i0001-05. HTML ビューはレポート必須・計画任意とし、テンプレートのコピーと編集で作る

## 背景

依頼では「レポートは HTML のビューを提供し、テンプレートをコピーしたうえで Edit コマンドで修正して使う」ことが求められた。参考実装 MR-driven-workflow は計画・レポートの両方に HTML ビューを必須とし（8 箇所で md と html を同期）、テンプレートは共通 DOM + 4 スタイルで提供している。同期の二重管理コストが弱点として挙がっている。

## 決定

- HTML ビューは `wip/30_reports/` の各実施ワークの結果レポートと全体まとめの統括レポートに**必須**、`wip/00_overall_plan/` と `wip/20_plans/` の計画書のうち、全体計画書には**作らない**（1 画面程度の短い文書で、合意はチャットと全体計画書本文で取るため）、各フェーズの計画書には**任意**
- Markdown が正文、HTML はその視覚化。両者は同じベース名で併存させ、内容を同期させる（片方だけ更新しない）
- HTML はスキルの `assets/` にある `*.template.html` を同じベース名でコピーし、Edit で節を埋める。生成スクリプトで HTML を組み立てない
- テンプレートは自己完結（外部リソース無し）、ライト / ダーク両対応。複数デザインを提供する場合は `<style>` 以外の DOM を同一にし、同一性をテストで固定する
- 節構成と視覚語彙（結論の性質は 3 色 + 記号 + 文字、レビューの重みは色相を使わず ◆ / ◇ / ・）は MR-driven-workflow のレポートテンプレートを踏襲する
- 出力後に機械的検査（プレースホルダ 0 件・リンク破断 0 件・重複 ID 無し・外部依存 0 件・`<style>` が 1 つ）を行い、結果を作業ログに残す

## 理由

- レビュアーが繰り返し目を通すのはレポートであり、型を固定する価値があるのはそこに集中する。計画書はレビュー往復で頻繁に書き換わり、HTML の同期コストが相対的に高い
- コピーして編集する方式は、AI が節の意味を理解しながら埋めるため、生成スクリプトより内容の質が安定し、テンプレートの改訂も HTML を直すだけで済む
- Markdown を正文にすることで、frontmatter 索引・grep・DDR への反映が Markdown だけを対象にできる

## 却下した案

- **計画書にも HTML を必須にする（MR-driven-workflow 方式）**: レビュー体験は揃うが、同期箇所が倍になる。計画は本文が短く Markdown で十分読める
- **Markdown から HTML を生成するスクリプトを作る**: 同期漏れが無くなるが、節構成・視覚語彙を Markdown 側の記法で表現する規約が別途要り、依頼の「コピーして Edit で修正」から外れる
- **HTML だけを正文にする**: ファイルが 1 つで済むが、frontmatter を持てず索引・検索の対象にできない

## 影響

- 要件定義書 F 節
- push 前チェックに「レポートの md と html の同期」を含める
- テンプレートの初版は MR-driven-workflow の `reports-clean.template.html` を土台に、参考実装固有の記述（flow-id 等）を除いて作る
