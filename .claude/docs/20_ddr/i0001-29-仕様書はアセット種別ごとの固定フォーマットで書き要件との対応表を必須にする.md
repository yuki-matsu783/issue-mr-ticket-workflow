# i0001-29. 仕様書はアセット種別ごとの固定フォーマットで書き、要件との対応表を必須にする

## 背景

`10_spec/` 配下に `00_requirement/` と同じディレクトリ構成で仕様書（内部的な挙動の設計書）を書き始めるにあたり、節構成を決める必要があった。要件定義書は全種別で同じ章立て（EARS・フロー順）だが、仕様書はアセットの性質 — スキルは AI が読む手順書、エージェントは定義ファイル、フックは stdin/stdout の契約 — が違うため、同じ節構成では書きにくい。

## 決定

仕様書は frontmatter（type: spec）を要件書と揃え、種別ごとに次の節構成で書く。

- **スキル**: 概要・禁止事項 / 呼出条件 / IN・OUT / IN・OUT サンプル / 処理フロー（AI の手順・承認ポイント。手順が薄い common-step では省略可）/ OUT ひな形（assets のテンプレート構成）/ 参照ナレッジ / Script 処理（scripts のインターフェース・判定順・エラー。テスト観点を含む）/ 要件との対応
- **エージェント**: 概要・禁止事項 / 呼出条件 / IN・OUT / IN・OUT サンプル / ツール権限 / 定義ひな形（定義ファイルの frontmatter・モデル指定・システムプロンプトの節構成）/ 参照ナレッジ / 要件との対応
- **フック**: 概要・禁止事項 / 呼出条件（発火イベント・matcher・登録）/ 入出力（stdin の JSON・返し方・終了コード）/ 制御方式（判定の順序・許可/確認/拒否・誤検知防止と縮退方向）/ エラー識別子とメッセージ / 回復手順（識別子ごとの対処）/ 記録（logs/ への判定記録）/ テスト観点 / 要件との対応
- **ルール**: 初回作成時に同じ要領で提案して決める
- **要件との対応**は全種別で必須: 対応する要件定義書の受け入れ基準を全件列挙し、実現する節・要素を指す表。実現されない要件と要件のない過剰仕様をレビューで機械的に見つける
- エラー識別子はフックが `WF0xx`、スキルのスクリプトは種別ごとの接頭辞（チケット操作は `TK0xx` など）で採番し、識別子と回復手順を 1:1 で対応させる
- 「関連するドキュメント」「レビュー記録」の節は置かない（要件書と同じ方針）

## 理由

- スキルを「呼出条件 → IN/OUT → 変換処理」の関数として仕様化すると、実装（SKILL.md・assets・scripts）が仕様から一意に導ける。エージェント・フックも同じ発想で、それぞれの契約（ツール権限・stdin/stdout）を独立の節にした
- 対応表を必須にすることで、`20-common-step-spec` の要件「どの受け入れ基準をどの節が実現するかが読み取れる」を型として担保する
- 拒否された AI が迂回を試みないためには、エラー識別子ごとに「次に取るべき対処」が書かれている必要がある（回復手順の節をフックで必須にする理由）

## 却下した案

- **全種別で同一の節構成**: フックの「制御方式・回復手順」やエージェントの「ツール権限」がスキルには不要で、無理に共通化すると空の節か意味のずれた節が生まれる
- **要件との対応を frontmatter や概要の一文で済ませる**: 全件列挙でないと「実現されない要件」の検査に使えない

## 影響

- `10_spec/` 配下のすべての仕様書
- この節構成自体は将来 `rules/`（設計文書ルール）に収め、機械検査（節見出しの検査）の対象にする
- エラー識別子の採番台帳（横断の一覧）は仕様書が増えて重複の危険が出た時点で `10_spec/hooks/` 直下に置く
