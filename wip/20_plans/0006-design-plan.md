# チケットボード拡張の設計計画

## 対象

- 対象 issue: #13 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/issues/13
- PR: #14 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/pull/14
- ブランチ: `claude/vscode-ticket-visualization-ci8etr`
- チケット: 0006-design-plan
- 入力: 調査結果レポート 0003（実形と壊れ方）/ 0004（ビルド・テスト環境）/ 0005（境界と置き場）/ 0007（VS Code API）

## この計画で何をするか

調査で出た事実から採る案を確定し、要件定義書 1 本と仕様書 1 本の骨子を決めて、設計実施チケット 1 枚に落とす。設計書の中身そのものは書かない。

決めたこと。

- 設計書は要件 1 本 + 仕様 1 本。拡張は 1 つの機能のまとまりなので分割しない
- 設計チケットは 1 枚（要件と仕様を同じチケットで書く）
- アプリ向けの仕様書の節構成は機構が定めていないので、この計画で決めて DDR に残す

## 判断点の結論方針

調査結果の候補から採る案を、比較軸ごとの根拠付きで示す。

### 1. 成果物の置き場

| 比較軸 | `tools/vscode-ticket-board/`（issue #13 の記述） | `src/vscode-ticket-board/`（採用） |
|---|---|---|
| 上限設定との整合 | `implementation.allow` にも `common.allow` にも入らない | `implementation.allow` の `src/**` に収まる |
| 設計文書の置き場 | 規定なし | `design.allow` の `docs/**` と対になる |
| issue の記述との一致 | 一致する | 詳細欄と食い違う（受け入れ条件は場所を規定していない） |

**採る案**: `src/vscode-ticket-board/`。テストは同ディレクトリ内の `test/`。設計文書は `docs/00_requirement/vscode-ticket-board.md` と `docs/10_spec/vscode-ticket-board.md`（0005 章 1・2）。

`src/vscode-ticket-board/.gitignore` に `node_modules/` と `out/` を書く。root の `.gitignore` は変更できないため（0005 章 4・5）。

### 2. frontmatter の読み方

| 比較軸 | 汎用 YAML ライブラリ | サブセット専用の自前パーサ（採用） |
|---|---|---|
| 扱う形の数 | YAML 全体 | 5 種類（フラットスカラー / クォート付きスカラー / フロー配列 / インラインマップ / 入れ子マッピング 2 段） |
| 壊れた入力 | 例外を投げうる。受け入れ条件 7 のために握り潰しが要る | 取れないキーを「取れない」と返す設計にできる |
| 依存 | 1 つ増える | 増えない |

**採る案**: サブセット専用の自前パーサ。値の妥当性検査はパーサの外に置く（0003 章 4・5）。

### 3. ビルドとテスト

**採る案**: TypeScript + `tsc -p .` + `node --test out/test/*.test.js`。開発依存は `typescript` / `@types/node` / `@types/vscode` の 3 つ。`@vscode/test-electron` は使わない（0004 章 1・2・5）。

`package-lock.json` をコミットして再現性を確保する。

### 4. 層の分け方

`vscode` は VS Code ホストの外では解決できないため、単体テストの対象にできるのは `vscode` を import しないコードだけである（0004 章 3）。これは好みではなく制約なので、層を分ける。

| 層 | `vscode` への依存 | テスト |
|---|---|---|
| 走査・パース・ボード組み立て・HTML 生成 | 無し。ファイル読み取りは `node:fs` | `node --test` で単体テスト |
| コマンド登録・Webview の生成・watcher の購読 | 有り | 単体テストの対象外。実機確認は人間 |

### 5. 更新の戦略

`FileSystemWatcher` はファイル移動を表すイベントを持たず、状態変更（`git mv`）は `onDidDelete` + `onDidCreate` に割れ、順序も保証されない（0007 章 3）。

**採る案**: 差分更新をせず、3 イベントのいずれを受けても 4 ディレクトリを全部読み直してボードを作り直す。短時間に連続するイベントは短い遅延でまとめて 1 回にする（0007 章 3・4）。

### 6. Webview の作り

**採る案**: 外部リソースを一切読まない自己完結 HTML を文字列で生成し `webview.html` に代入する。`localResourceRoots` は空、`asWebviewUri` は使わない。CSP は `default-src 'none'` から組み、スタイルは `webview.cspSource`、スクリプトは nonce 付きインラインのみ。`retainContextWhenHidden` は使わず、`onDidChangeViewState` で可視になったら読み直す（0007 章 2）。

### 決めきれない点（設計チケットで結論を書く）

| 項目 | 設計で決めること |
|---|---|
| 連続イベントをまとめる遅延の値 | 具体値と、その値にした根拠 |
| DoD のチェック進捗をカードに出すか | 受け入れ条件には無い。出すなら要件の受け入れ基準に足す |
| 不備の表示の粒度 | 「取得できなかったキー名」「不正な値」をどこまでカードに出すか |
| アプリ向け仕様書の節構成 | 機構の `20-common-step-spec` はスキル / エージェント / フックの 3 種しか定めていない。アプリ用の節構成を決めて DDR に残す |

## 設計書の一覧

| 文書 | 新規 / 更新 | 置き場 | 骨子 |
|---|---|---|---|
| 要件定義書 | 新規 | `docs/00_requirement/vscode-ticket-board.md` | 概要（背景・目的・スコープ）/ ユーザーストーリー / 受け入れ基準（EARS。メイン → 代替 → 例外 → 整合）/ 前提条件 / 制約条件 / 依存関係 / 非機能要件 |
| 仕様書 | 新規 | `docs/10_spec/vscode-ticket-board.md` | 概要・禁止事項 / 起動と入口（コマンド・`package.json` の contributes）/ モジュール構成（層の分け方と依存の向き）/ データの形（チケットの内部表現・不備の表し方）/ 処理フロー（走査 → パース → 検査 → 組み立て → HTML 生成 → 表示・更新）/ HTML の構造と CSP / エラー識別子とメッセージ / テスト観点（テスト ID）/ 要件との対応 |
| DDR | 新規 | `docs/20_ddr/i0013-01-成果物の置き場をsrc配下にする.md` | 背景 / 決定 / 理由 / 却下した案 / 影響 |
| DDR | 新規 | `docs/20_ddr/i0013-02-アプリ向け仕様書の節構成.md` | 同上 |

`docs/90_glossary/` は作らない。プロジェクト固有語が「チケット」「ボード」程度で、辞書に載せる基準（複数文書で使われ、指し先や表記が揺れうる固有語）に達しないため。

仕様書の節構成は上表のとおりこの計画で決める。機構の `20-common-step-spec` はスキル / エージェント / フックの 3 種しか定めておらず、アプリ向けの節構成が無いため（DDR i0013-02 に残す）。

## 受け入れ条件との対応

| # | issue #13 の受け入れ条件 | 要件の受け入れ基準 | 仕様の実現箇所 | テスト |
|---|---|---|---|---|
| 1 | コマンドパレットから「チケットボードを開く」で Webview が開き 4 状態が列として並ぶ | メイン: コマンドが実行されたとき、4 状態の列を持つボードを表示する | 起動と入口 / HTML の構造 | HTML 生成関数が 4 列を出すこと |
| 2 | 番号・タイトル・ticket_type・executor・人間レビュー要否・敵対的レビュー要否が分かるカード | メイン: 各チケットについて 6 項目を表示する | データの形 / HTML の構造 | 実チケットを入力にカードの 6 項目が出ること |
| 3 | 列ごとの件数と残チケット（todo + doing）合計の表示 | メイン: 列ごとの件数と残件数を表示する | HTML の構造 | 件数の計算が正しいこと |
| 4 | カードのクリックで該当 .md をエディタで開く | メイン: カードが選択されたとき、対応するファイルを開く | 処理フロー（メッセージ） | 対象外（`vscode` 依存層）。実機確認 |
| 5 | 追加・削除・移動・編集がボードに自動反映される | メイン: チケットのファイルが変化したとき、ボードを更新する | 処理フロー（更新） | 走査関数が状態変化後の入力で正しい結果を返すこと |
| 6 | チケット 0 件でもエラーにならず空だと分かる | 代替: チケットが 0 件のとき、空であることを示す | HTML の構造 | 0 件入力で空表示の HTML が出ること |
| 7 | frontmatter が壊れていても落ちず、不備が分かる表示が出る | 例外: 解析できないチケットがあっても処理を続け、不備を示す | データの形 / エラー識別子 | 0003 章 4 の 9 パターンを入力に落ちないこと |
| 8 | wip/10_tickets が無いときは静かに終わる | 例外: 対象ディレクトリが無いとき、その旨を示して終了する | 起動と入口 | 対象外（`vscode` 依存層）。走査関数側は空を返すこと |
| 9 | 単体テストがあり、ビルドとテストの実行方法が README に書かれている | 整合: テストと README を備える | テスト観点 | README の存在と手順の一致 |
| 10 | ビルドとテストがローカルで通る | 整合: `tsc` と `node --test` が成功する | テスト観点 | 実行して確認 |

受け入れ条件 4 と 8 は `vscode` に依存する層に属し単体テストの対象にできない（0004 章 3）。要件には落とすが、確認は実機で人間が行う前提を要件の「制約条件」に明記する。
