# 10-work-design-feedback-plan スキル

## 概要

設計反映フェーズの計画ワークの要件を定義する。フィードバック計画で「この MR で対応する」と決まった設計への反映について、実装の差分と作業ログの「仕様からの逸脱」を設計書（要件定義書・仕様書）と突き合わせ、差分を分類した一覧とどの設計書のどの節をどう書き戻すかの方針を設計反映計画書にまとめ、設計反映チケット群と次の計画チケットを起こして設計反映計画チケットを完了する。設計書は直さない（`10-work-design-feedback-exec`）。

- **背景**: 実装を経た設計書は「実装が正しく設計書が古い」「設計書が正しく実装が漏れている」「設計に無い決定が実装で生まれた」が混ざった状態になる。分類せずに書き戻すと、実装漏れを設計書の側で消してしまい、受け入れ条件が骨抜きになる。差分を分類して人間が見てから書き戻したい。
- **目的**: 設計書の節ごとに実装（ファイル・シンボル・テスト）と照合した差分一覧（分類つき）と書き戻し方針を、実装漏れの扱いとともにレビュー可能な計画書として残す。
- **スコープ**:
  - 含む: 設計反映計画書（差分一覧と書き戻し方針）の作成、差分の分類、実装漏れの扱いの提案、設計反映チケット群と次の計画チケットの作成、設計反映計画チケットの着手から完了まで、「対象なし（差分なし）」の扱い、再開時の扱い、呼び出し元への結果報告
  - 含まない: 設計書の書き戻し（`10-work-design-feedback-exec`）、実装の修正（実装フェーズの追加チケット）、設計反映フェーズ自体の要否の決定（`10-work-feedback-plan`）、AI アセットの設計文書（AI アセット設計フェーズ）、ワークの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 設計書と実装の差分がどこにあり、どれを設計書の側に書き戻し、どれが実装の漏れなのかを分類した一覧で確認したい。

**[So that]** 実装漏れが設計書の書き換えで隠れるのを防ぎ、マージ時点で設計書と実装が一致している状態を作れるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このワークに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、実装の差分・実装チケットの作業ログ（仕様からの逸脱。テスト側を直した記録を含む）・設計書・フィードバック計画で決めた対応の一覧を入力に、読み取りだけで進めなければならない。
- When 設計反映計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 突き合わせるとき、Shall スキルは設計書の節（受け入れ基準・インターフェース・処理フロー・エラー・テストシナリオ）ごとに実装（ファイル・シンボル・テスト）と照合し、差分を「一致」「実装が正しく設計書が古い（書き戻す）」「設計書が正しく実装が漏れている（書き戻さない。実装の追加チケットを提案）」「設計に無い決定事項（設計書に追記し、経緯を DDR に残す）」のいずれかに分類しなければならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 設計反映計画書の案ができたとき、Shall スキルは関連する設計書のまとまりを単位に設計反映チケット群（1 枚以上）を未着手に作らなければならない。互いに依存しないチケットは並列に進めてよいことを記す。
- When 設計反映チケットを作るとき、Shall その DoD は「<設計書> の <節> が実装（<ファイル・シンボル>）と一致するよう更新されている」「設計に無かった決定事項 <X> が追記され、経緯が DDR に残っている」「差分一覧の該当行が『一致』になっている」の型で書かなければならない。
- When 設計反映チケット群を作り終えたとき、Shall スキルはフィードバック計画で決めたフェーズ列で設計反映の次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない（次のフェーズが無ければ全体まとめのチケット）。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: ワークの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When 設計反映計画チケットを完了するとき、Shall 設計反映計画書（md + HTML）・設計反映チケット群・次の計画チケットが存在し、DoD（差分一覧が分類つきで全節を照合している / 実装漏れが一覧化されている / チケットが差分一覧と対応している / 次の計画チケットがある）がすべて満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 設計反映計画チケットを完了したとき、Shall スキルは結果報告（計画書の場所、差分の件数と分類、実装漏れの一覧と提案、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「差分一覧が設計書の全節を照合しているか」「『設計書が古い』と『実装が漏れている』の分類が正しいか（実装を正としてよい差分か）」「設計に無い決定事項が作業ログの逸脱一覧と一致するか」「実装漏れの扱い（実装の追加チケット / 今回はスコープ外）」を挙げなければならない。

### 代替フロー

- If 突き合わせの結果、差分が 1 件も無い場合、Then スキルは設計反映計画書に「差分なし」とその照合の範囲を書き、設計反映チケットを起こさず次の計画チケットだけを作って設計反映計画チケットを即座に完了しなければならない（照合したことが計画書に証跡として残る）。
- If 設計フェーズが「対象なし」で終わっていて対象の設計書が無い場合、Then スキルはその旨を計画書に書き、差分なしと同じ扱いで完了しなければならない。
- If 再開時に設計反映計画チケットが作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、計画書・チケットを二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのワークに戻った場合、Then スキルは計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残さなければならない。

### 例外フロー

- If 実装が漏れている差分が多く、設計反映よりも実装の続きが必要な状態だった場合、Then スキルは設計反映チケットを最小限に留め、実装の追加チケットの提案を結果報告に含めて人間レビューに委ねなければならない（設計書を実装に合わせて弱めない）。
- If 設計書と実装の両方が曖昧でどちらに合わせるべきか決められない場合、Then スキルは両案を差分一覧に書き、判断を人間レビューに委ねなければならない（勝手に決めない）。
- If 設計書への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、その内容を設計反映チケットに回さなければならない（計画ワークでは設計書を直さない）。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

### 設計反映計画書の内容

- When 設計反映計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、差分一覧（設計書の節 × 実装の対応表。分類と根拠つき）、書き戻し方針（設計書ごとに直す節・追記する内容・DDR に残す経緯）、実装漏れの一覧と扱いの提案、受け入れ条件の確認（テストと設計書の両方で裏付けられているか）、設計反映チケットの一覧、判断を保留した点。
- When 設計反映計画書を書くとき、Shall 「これから何をするか」だけを書き、設計書の書き戻しを始めてはならない。
- When 設計反映計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### 設計反映計画チケットの扱い

- When 設計反映計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、設計文書・ソースコード・`.claude/` 配下を書けてはならない。
- When 設計反映計画チケット・設計反映チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければどちらも「要」を既定としなければならない（設計書の書き換えは受け入れ条件の解釈に触れる）。

### 他のスキル・機構との整合

- When 実装の差分・作業ログ・設計書を参照するとき、Shall スキルはそれらを書き換えず、読み取りだけで突き合わせなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When フィードバック計画で「別 issue」とされた反映候補に出会ったとき、Shall not スキルはそれをこのワークのチケットにしてはならない（別 issue の扱いはフィードバック計画の決定が正）。

## 前提条件

- フィードバック計画がこのフェーズを含めると決め、そのワークの切れ目の処理が済み、設計反映計画チケットが未着手にあること
- 設計反映計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う差分は分類を保留して両案を書き、人間レビューで確定する。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 「実装を正としてよいか」の判断は人間レビューが行う。スキルは分類と根拠を揃えるまで
- **外部的制約**: 対象はアプリ本体の設計文書に限る。`.claude/` 配下は AI アセット設計フェーズで扱う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 差分一覧の各行に分類の根拠（ファイル・シンボル・作業ログの記録）が残り、書き戻しの前後を辿れる |
| 一貫性 | チケットの記載事項・DoD の型・作業ログは他の work スキルと同じ。フェーズの名前は `00-workflow-issue-mr-driven.md`「ワークの構成」と一致する |
| 簡潔性 | 差分一覧は表で読める形にし、一致した節の記述は 1 行に留める |
| 冪等性 | 再開時に計画書とチケットを二重に作らない |
