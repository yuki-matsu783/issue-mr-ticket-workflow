# チケットボード拡張の成果物の置き場を src/ 配下にする

## 背景

issue #13 の詳細欄は、拡張のソースを `tools/vscode-ticket-board/` に置くと書いていた。一方、機構の上限設定 `.claude/hooks/config/scope-limits.json` は、実装タスクが書き込めるパスを `src/**` と `tests/**`、設計タスクが書き込めるパスを `docs/**` に限っている。`tools/**` はどの許可範囲にも入らない。

また、拡張のビルドで生じる `node_modules/` と `out/` が未追跡のまま残ると、`push.sh` の push 前チェック項目 1 と `ticket.sh complete` の未コミット検査が止まる。リポジトリ直下の `.gitignore` は上限設定の `common.protected` にあり、どのタスク種別の許可範囲にも入っていないため変更できない。

## 決定

- 拡張のソースを `src/vscode-ticket-board/` に置く。テストは同ディレクトリ内の `test/`
- 設計文書を `docs/00_requirement/vscode-ticket-board.md` と `docs/10_spec/vscode-ticket-board.md` に置く
- ビルド成果物の除外は `src/vscode-ticket-board/.gitignore`（入れ子の `.gitignore`）で行う
- issue #13 の受け入れ条件は変更しない

## 理由

- 上限設定が許可するパスに収まり、機構の判定と衝突しない
- 設計文書の置き場を定める `design-docs` ルールの適用範囲が `docs/**` であり、要件と仕様を同じ規約の下に置ける
- 入れ子の `.gitignore` はリポジトリルート相対の `.gitignore` とは別のパスなので `common.protected` に当たらず、実装タスクの許可範囲 `src/**` に収まる。実測で `node_modules/` と `out/` が `git status` から消えることを確認した
- issue #13 の受け入れ条件 10 件はいずれも成果物の場所を規定していないため、置き場を変えても条件は変わらない

## 却下した案

- **`tools/vscode-ticket-board/` のまま進める**: 上限設定の許可範囲外で、フックが有効化された時点で書き込みが止まる。現在フックが登録されていないことに依存する設計になる
- **リポジトリ直下の `.gitignore` に `node_modules/` と `out/` を足す**: `common.protected` にあり、AI アセット実装タスクの許可範囲にも入っていないため、どのタスクからも変更できない。人間に依頼すれば可能だが、入れ子の `.gitignore` で済むなら依頼する理由がない
- **上限設定 `scope-limits.json` の `implementation.allow` に `tools/**` を足す**: 1 つの拡張のために機構の上限を広げることになる。上限設定の変更は `.claude/hooks/config/**` への書き込みで、AI アセット実装タスクと人間の確認が要る

- **issue #13 の詳細欄を更新して `src/` 配下に揃える**: 記述の食い違いは消えるが、issue の編集は外部への副作用で、設計タスクの `allow.ops` は `read` と `remote-read` だけである。フィードバック計画または全体まとめで、人間の承認を得たうえで issue コメントとして残すほうが手順に合う

## 影響

- issue #13 の詳細欄と実際の置き場が食い違う。受け入れ条件は変わらないが、issue を読んだ人が混乱しうるので、フィードバック計画で issue への追記の要否を判断する
- このリポジトリにトップレベルの `docs/` と `src/` が新設される。いずれも上限設定が想定している置き場である
