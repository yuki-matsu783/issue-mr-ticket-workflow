# 10-task-investigation-exec — 読み取りだけで観点に答える

ファイルを書き換えない。リポジトリ外へ問い合わせない（`allow.ops` に `web` が宣言された外部技術調査のチケットだけが例外）。ビルド・テストを実行しない（`allow.ops` に `build-test` が宣言されたチケットだけが例外で、書き込みは一時ディレクトリに限る）。`.claude/**` を一時的にも変更しない。設計・実装を決めない（候補と比較軸を並べるまで）。計画書・全体計画書を書き換えない。推測を事実のように書かない。チケットを並列に実施せず、サブエージェントを入れ子で起動しない。完了済みチケットを作業中に戻さない。

## 目的

調査計画が立てた観点に、根拠付きの答えを返す。次の計画（設計・実装）が判断できる材料を揃えるところまでを担う。

- 要件: `.claude/docs/00_requirement/skills/10-task-investigation-exec.md`
- 仕様（正。実施タスク共通の処理フロー・調査の固有手順）: `.claude/docs/10_spec/skills/10-task-investigation-exec.md`

## 手順

### 実施タスクの共通手順（正。他の `10-task-*-exec` はここを参照する）

1. **入力の確認**: 計画書と実施チケット群を読む。計画書が無い・チケットが計画と対応しないときは始めず、状態の不整合として結果報告に書いて呼び出し元に戻す
2. **着手**: `bash .claude/skills/20-common-step-ticket/scripts/ticket.sh next` が示すチケットを `ticket.sh start` で **1 枚ずつ**作業中にする。そのチケットの担当範囲だけを実施する。作業ログはその都度追記する
3. **実施**: 各スキルの固有手順
4. **レポート**: **1 タスク（同じ種類のチケット群）につきレポートは 1 つ**。最初のチケットで `wip/30_reports/<最初のチケット連番>-<種類>.md` をレポートテンプレートから作り、`20-common-step-report-view` の手順で同名 HTML を作る。以降のチケットは同じレポートに節を追記し、md と HTML を同期させて `check-html.sh` に通す
   - チケットごとにレポートを分けない。分けるとレビュアーが 1 つのタスクの結論を読むのに複数のファイルを開くことになり、必須節がファイルの数だけ重複する
   - 追記する節は**どのチケットで書いたかが分かる形**にする（サマリの冒頭に「0011 まで」「0012 まで」と積み上げ、結論の見出しは連番で通す）。件数タイル（◎良 / △注意 / ✕問題）はタスク全体の合計になる
   - 差し戻しの追加チケットも同じレポートに追記する（新しいレポートを作らない）
5. **成果物のコミットと完了**: そのチケットの成果物を `20-common-step-commit-push` の `commit.sh` でコミットし、`ticket.sh complete <番号>`
6. **次へ**: 同じ種類のチケットが未着手に残っていれば 2 へ（タスクの切れ目ではない）。すべて完了したらレポートを仕上げ、結果報告（完了したチケットの一覧・レポートの場所とサマリ・見てほしい点・確かめられなかったこと・残課題）を呼び出し元に返す

- **再開**: 作業ログ「現在地」から続け、レポートの節を二重に作らない
- **差し戻し**（同種の追加チケット）: 既存のレポートに追記・修正し、対応を作業ログ「判断と根拠」に残す
- **書き込みを拒否されたら**: 範囲を広げる確認を求めず、直したい内容を修正案としてレポートに書いて後続のフェーズへ回す
- HTML の検査で問題があれば解消してから完了する
- 敵対的レビューが計画されているタスクでは、レポートと成果物がその対象になる。指摘は人間の指摘と同じ扱いで対応する

### 調査の固有手順

- 3 の実施は**読み取りだけ**（閲覧・検索・履歴・既存のテスト結果や記録）。`allow.ops` に `web` が明示された外部技術調査だけは Web 検索・公式ドキュメントの閲覧を許し、候補・選定基準・出典の比較にまとめる。`allow.ops` に `build-test` が明示されたチケットだけは既存のテスト・ビルドの実行を許す（計画書が「確かめ方」に書いた範囲に限り、書き込みは一時ディレクトリだけ。コマンドと要約を根拠に残す）
- 宣言の無いチケットで実行が要ると思っても実行しない。既存の記録で代え、必要なことを「確かめられなかったこと」に理由付きで書く（次の調査計画で宣言付きのチケットを起こす提案にしてよい）
- 選択肢が複数ある問いは**候補と比較軸**（変更量・リスク・既存パターンとの整合など）を並べるまでで、決めない
- 観点自体が的外れだと分かったら観点は書き換えず、「答えが出なかった理由」として経緯を書き、代わりの問いを「残課題」に提案する
- 想定外の事実（不具合・負債・文書と実装の食い違い）は直さず「想定と異なった点」または「残課題」に書き、作業ログ「スコープ外で見つけたこと」にも残す
- **見てほしい点の固定項目**: すべての観点に答えまたは理由があるか / 根拠が具体的か / 候補と比較軸が次の計画の判断に足りるか / 調査の範囲を超えた決定をしていないか

## OUT ひな形

このスキルは固有のテンプレートを持たない。`20-common-step-report-view` の `assets/report.template.md`（と `report.template.html`）をそのまま使う。「実施した内容と結果」に観点ごとの小節（答え / 根拠 / 結論の性質 ◎良・△注意・✕問題 / レビューの重み ◆・◇・・）を置き、対象 issue と MR を冒頭に明記する。

## 参照

- チケット操作・作業ログ・完了検査: `20-common-step-ticket`
- レポートの HTML と検査: `20-common-step-report-view`
- コミット: `20-common-step-commit-push`（`git commit` の直接実行はフックが拒否する）
- 観点と「やってよいこと」の出どころ: `10-task-investigation-plan` が作った調査計画書

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 計画書が無い / チケットが計画と対応しない | 始めず、状態の不整合として結果報告に書いて呼び出し元に戻す |
| `curl` / `wget` がフックに拒否された | `allow.ops` に `web` が無いチケット。迂回せず、確かめられなかったこととして残す |
| ビルド・テストがフックに拒否された | `allow.ops` に `build-test` が無いチケット。既存の記録で代え、理由を残す |
| 書き込みがフックに拒否された | 迂回せず、修正案としてレポートに書いて後続フェーズへ回す |
| 観点に答えが出ない | 答えが出た体で書かない。理由を書き、代わりの問いを残課題に提案する |
| `check-html.sh` が `RV00x` | 指摘された項目を直してから完了する |
| `ticket.sh complete` が TK005 | DoD・作業ログ・未コミットのどれかが未充足。列挙された項目を埋めてから再実行する |
