# 10-task-overall-summary スキル

## 概要

フェーズ列の末尾に置かれる全体まとめタスクの要件を定義する。フィードバック計画より後のタスクで新たに見つかった反映すべき内容の別 issue 起票 → default ブランチとの衝突解消 → 統括レポートの作成 → MR 本文の最終化 → push（統括レポートを含む成果物を履歴に載せる）→ 完了検査とその統括レポートへの記録 → 成果物のリンク一覧を本文に記載 → 作業領域の片付け → push → draft 解除 の順に進め、マージは行わず停止する。HTML レポートの添付は任意で、成果物の所在は本文のリンク一覧が担う。作業中の issue にはコメントを含め書き込まない。承認（衝突解消の方針・投稿する本文）が続けて挟まるため、メインエージェントが行う。振り返りは行わない（フィードバック計画で済んでいる）。

- **背景**: 作業領域（計画・チケット・レポート）はブランチ限りの記録で、マージには載せない。一方で「何が満たされ、何が残ったか」は MR に残す必要がある。片付けと記録の書き写しの順序を誤ると、消してはいけない要約が消え、あるいは作業ファイルが MR の差分に残る。締めの手順を 1 本のタスクに固定したい。
- **目的**: 受け入れ条件の充足と残課題が MR 上で追える状態にし、作業領域を空にし、レビュー可能な状態（draft 解除）で人間のマージ判断に引き渡す。
- **スコープ**:
  - 含む: 残った反映すべき内容の別 issue 起票、default ブランチとの衝突解消、統括レポート（md + HTML）の作成、MR 本文の最終化、完了検査とその記録、成果物のリンク一覧、HTML レポートの添付、作業領域の片付け、push、draft 解除、全体まとめチケットの着手から完了まで、再開時の扱い
  - 含まない: 振り返りと改善候補の決定（`10-task-feedback-plan`）、MR のマージ（人間が行う）、レビュー指摘への対応（各タスクの追加チケット）、影響を受ける他の既存 issue の検索・通知（参考実装にあった機能。採らない — 反映すべき内容の別 issue 起票で代替する）、片付け・draft 解除を安全にする仕組み（仕様書）

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 作業の締めで、受け入れ条件の充足・残課題・別 issue 化された内容が MR に書き写され、作業領域が片付いた draft 解除済みの MR を受け取りたい。

**[So that]** マージの判断に必要な情報が GitLab / GitHub 上に揃い、作業ファイルの混入や消し忘れを気にせずマージできるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルはメインエージェント自身で実施し、サブエージェントに委ねてはならない（承認が続けて挟まるため）。
- When 全体まとめチケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、以降の手順を 別 issue 起票 → 衝突解消 → 統括レポート → MR 本文の最終化 → push → 完了検査とその記録 → 成果物のリンク一覧 → 片付け → push → draft 解除 の順で行わなければならない（順序を入れ替えない）。
- When フィードバック計画より後のタスクの作業ログ・レポートに反映すべき内容（改善候補・スコープ外の気づき）が残っているとき、Shall スキルはそれらを集めて別 issue の本文案を提示し、承認を得てから起票しなければならない（この MR での追加対応はしない。振り返りもやり直さない）。
- When default ブランチとの衝突を確かめるとき、Shall スキルは最新の default ブランチと突き合わせ、衝突が無ければ承認なしで次へ進み、衝突があれば衝突ファイルと解消方針を提示して承認を得てから取り込み（merge）で解消しなければならない。rebase と、片側を丸ごと採用する解消を使ってはならない。
- When 統括レポートを書くとき、Shall 作業領域のレポートの置き場に md + HTML で 1 つ作り、issue の受け入れ条件との対応（何がどのタスク・テストで満たされたか）、各タスクのレビュー結果（人間レビューを省略したタスクはその旨）、フィードバック計画で決めた対応（この MR で対応したもの・別 issue に起票したもの・対応しないとしたもの）、残課題を 1 つにまとめなければならない。
- When MR 本文を最終化するとき、Shall スキルは統括レポートの要約（受け入れ条件との対応・残課題・別 issue の一覧）を MR 本文に書き写さなければならない（作業領域の記録は片付けで消えるため、残したい内容はここまでに書き写す）。
- When 成果物の所在を残すとき、Shall スキルは片付けで消える前の時点に固定したリンクの一覧を **MR 本文**（description）に表として記載しなければならない。コメントとしては投稿しない（コメントは流れて見つけにくく、本文だけで辿れることを保証できない）。
- When ホストが公式の添付 API を提供していないとき、Shall HTML レポートの添付は**人間が MR 本文に対して行い**、スキルはこの手順で何もしてはならない（待たない・催促しない）。非公式の経路でアップロードを試みてはならない。
- Where ホストが公式の添付 API を提供しているとき、Shall スキルは HTML レポートを添付し、返ったリンクを MR 本文に記録してよい。
- When 添付が行われたとき、Shall スキルはその後に本文を書き換える際、人間または自分が置いた添付のリンクを消してはならない（書き換えてよいのは成果物のリンク一覧の中身だけ）。
- When 添付の有無を扱うとき、Shall 添付は任意であり、行われなくても成果物の所在は本文のリンク一覧で辿れなければならない（添付の有無で手順を分岐させない）。
- When 書き写しの済みを確かめるとき、Shall このタスクが行う書き写しは MR 本文と統括レポートに限り、`.claude/docs/` に残すべき内容が未反映で見つかった場合は別 issue の起票に回さなければならない（`.claude/docs/` への書き写しは、それを書けるフェーズのタスクが自フェーズ内で済ませている前提。このタスクは `.claude/docs/` を書けない）。
- When 作業中の issue（この MR が紐づく issue）に関わるとき、Shall not スキルはその issue にコメントの投稿を含む書き込みを行ってはならない。マージ判断に必要な情報は MR 本文（要約と成果物のリンク一覧）で揃え、issue の本文・タイトル・状態も変更しない（close はマージ後に人間が行う）。
- When 統括レポートを書き終えたとき、Shall スキルは push しなければならない（統括レポートを含む成果物を、片付けで消える前にブランチの履歴に載せるため。本文のリンク一覧が指す先を実在させる。人間レビューの要否によらず毎回行う）。
- When 全体まとめチケットの完了を確かめるとき、Shall 完了検査は片付けの提供コマンドが行い、**その結果（DoD 1 件ごとの合否と根拠）を統括レポートに書き出してから片付けに進まなければならない**。チケットの状態遷移としての完了は起こらないため、検査の通過は片付けで消えない場所に残す必要がある。
- When 作業領域を片付けるとき、Shall スキルは片付けの提供コマンドで行い、そのコマンドは全体まとめチケットの完了（DoD・作業ログの検査と完了時刻の記録）を確かめてから、完了済みの全体まとめチケットを含む作業領域（全体計画書・チケット・計画書・レポート・チケットのレビュー状態などブランチ内の進行状態・一時ファイル）を空にしなければならない（完了だけを別に実行しない）。機構がリポジトリ直下の `logs/`（コミットの対象外）に記録する進行状態 — MR の記録・マージ前作業の証跡・前回 push 時点 — は片付けの対象にせず、片付け後の push・draft 解除・継続判定はそれで行われる。片付けの前提（未着手・作業中のチケットが全体まとめチケット以外に無い・書き写しが済んでいる）は機構が確かめる。
- When 片付け・push・draft の解除を行うとき、Shall これらは 1 つの提供コマンドで連続して行われ、AI が push・draft 解除を個別の操作として行ってはならない。コマンドが途中で失敗した場合は、再実行で済んだ段階を飛ばして続きから進められること。チケットが無い状態で許される操作はこの再実行だけであり、振り分けの再宣言は求められない。
- When draft を解除する直前に、Shall スキルは最新の default ブランチとの衝突・遅れを再確認し、default が進んでいれば衝突解消の手順に戻らなければならない（レビュー待ちや片付けの間に default が進んでいても、古いベースのまま解除しない）。
- When draft を解除したとき、Shall スキルは結果（issue・MR の番号、別 issue の一覧、衝突解消の有無と内容、片付けの件数）に、片付け前の push のコミットに固定した作業領域（HTML レポートの置き場）へのリンクを添えて報告し、マージを行わずに停止しなければならない（コミット固定のリンクのため片付け後も辿れ、HTML をダウンロードできる）。

### 代替フロー

- If フィードバック計画より後に反映すべき内容が何も残っていない場合、Then スキルは別 issue を起票せず、統括レポートに「追加の反映なし」とその確認範囲を書いて次へ進まなければならない。
- If 再開時に全体まとめが途中まで進んでいる場合、Then スキルは機構が示す進行状態（どの手順まで済んだか）から続きを行い、済んだ手順（起票・完了検査の記録・リンク一覧・片付け）をやり直してはならない（二重に起票・記録しない）。
- If 添付が行われなかった場合、Then スキルは何も補わなくてよい（成果物の所在は本文のリンク一覧が担うため、添付の有無で代替の記述を書き分けない）。
- If ユーザーが「draft のまま置く」ことを選んだ場合、Then スキルは draft 解除を行わず、そこまでの結果を報告して停止しなければならない。
- If 全体計画でこのチケットの人間レビューが「要」とされている場合、Then スキルは統括レポートの push を終えた時点でレビューを依頼し、レビュー完了（未解決スレッドの確認を含む）を受けてから完了検査以降に進まなければならない。
- If ホストの CLI が使えない実行環境の場合、Then 本文の更新と draft の解除は呼び出し元が代行し、片付けの提供コマンドはその代行を前提に残りの手順を進めなければならない（代行であることを進行状態と統括レポートに残す）。

### 例外フロー

- If 片付けの前提が満たせない（完了していないチケットが残っている・最後のタスクのレビューが未完了・未コミットの変更がある）場合、Then スキルは機構が返す未充足を報告し、該当する手順（タスクの継続・レビュー・コミット）へ戻らなければならない。進行状態を直して通そうとしない。
- If 衝突の解消方針が一意に決まらない場合、Then スキルは両側の意図を要約して判断を仰ぎ、勝手にどちらかを選んではならない。承認が得られなければ停止する。
- If 別 issue の起票に失敗した場合、Then スキルはエラー内容と実施済み・未実施の別を報告して停止し、再試行で二重に起票してはならない。
- If ユーザーが応答できない実行形態で**別 issue の起票**が必要になった場合、Then スキルは起票せず、候補の一覧と本文案を統括レポートに書いて次の手順へ進まなければならない（起票は取り消せない外部への副作用なので既定で行わないが、それだけのために全体まとめ全体を止めない）。
- If ユーザーが応答できない実行形態で**衝突の解消**または **draft 解除の可否**の判断が必要になった場合、Then スキルは衝突内容またはそこまでの結果を報告してセッションを終え、次回セッションで進行状態から再開しなければならない（衝突の解消は履歴を変え、draft 解除は外部から見える状態を変えるため、既定で進めない）。
- If HTML ビューの機械的検査で問題が見つかった場合、Then スキルは解消してから先へ進まなければならない。
- If 片付けと draft 解除の呼び方そのものが成立していない場合（知らない指示・足りない引数・依存するコマンドの不在）、Then 機構は前提の未充足とは別の識別子と別の終了の仕方で拒否しなければならない。スキルは前提を直して繰り返すのではなく、呼び方か環境を直さなければならない。
- If 進行状態が読めない、または進行状態が知らない段階を指している場合、Then 機構は止まらず実態から進行状態を導き直して続けなければならない（進行状態は直接編集できないので、止めると人間にも直す手段が残らない）。
- If 導き直しの途中でどちらとも判定できない項目がある場合、Then 機構は「済んでいない」側に倒し、その段階をもう一度実行しなければならない。実行していない段階を済んだこととして扱ってはならない。

### 規約: 全体まとめチケット

- When 全体まとめチケットが作業中のとき、Shall そのチケットの「やってよいこと」はレポートの置き場・チケットの置き場・`wip/tmp/` への書き込み・作業領域の片付けと、リモート書き込み（別 issue の起票・MR 本文の編集・公式 API での添付・衝突解消の取り込み・push・draft 解除）を含み、ソースコード・設計文書・`.claude/` 配下を書けてはならない（衝突解消で生じる取り込みの変更を除く）。
- When 全体まとめチケットの完了条件を書くとき、Shall 決まった型（別 issue の確認 / 衝突解消 / 統括レポートの内容 / 本文への書き写し / 受け入れ条件の根拠 / `.claude/docs/` への未反映が無いこと）に沿って書き、根拠にはチケット番号・レポートの節・テストの識別子を挙げ、片付けで消える場所のパスを恒久の参照として書いてはならない。
- When 全体まとめチケットの人間レビュー要否を決めるとき、Shall 全体計画の方針に従い、方針が無ければ「不要」を既定としなければならない（承認が要る操作はタスクの中で個別に承認を取り、最終確認はマージの判断そのものが担うため）。人間レビュー要の場合は統括レポートの push の後・完了検査の前にレビューを受ける。

### 他のスキル・機構との整合

- When コミット・push・チケットの状態変更・片付け・draft 解除を行うとき、Shall スキルは提供コマンド経由でのみ行い、進行状態の直接編集や draft 解除の直接実行を行ってはならない。
- When draft を解除するとき、Shall 作業領域が空であることが機構に確かめられていなければならない。draft 解除後にこの MR で追加の作業が発生した場合も、push の前に作業領域を片付け、作業領域にファイルが残った状態で push してはならない。
- When 統括レポートの節順・視覚語彙を決めるとき、Shall 他の実施タスクのレポートと同じ機構のテンプレートに従わなければならない。
- When 作業ログを書くとき、Shall 他の task スキルと同じ固定見出しでその都度追記しなければならない（このタスクの気づきは別 issue の本文か MR 本文に書き写す。作業ログ自体も片付けで消えるため）。

## 前提条件

- フェーズ列のすべてのタスクが完了し、最後のタスクの切れ目の処理（レビュー要ならレビュー完了）が済み、全体まとめチケットが未着手にあること
- メインエージェントで実行されること（サブエージェントからは呼ばれない）
- 片付け・draft 解除・レポートのテンプレート・チケットの提供コマンドが用意されていること

## 制約条件

- **技術的制約**: 承認（別 issue 本文・衝突解消）が続けて挟まるためメインエージェントが行う。手順の順序は固定（書き写しが済む前に片付けない）
- **ビジネス的制約**: マージは人間が行う。AI は draft 解除で止まる。振り返りはこのタスクでは行わない
- **外部的制約**: 別 issue の起票は取り消せない外部への副作用のため、本文そのものの承認なしに行わない。作業中の issue にはコメントを含め書き込まない。ヘッドレスでは承認が取れないので、別 issue の起票は行わず候補を残して進み、衝突解消と draft 解除は報告して停止する

## 非機能要件
