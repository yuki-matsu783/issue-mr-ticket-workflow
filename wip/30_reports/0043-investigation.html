解析そのものは shlex が圧勝し、プロセス起動で逆転する。起動を除いた解析時間は shlex 版 0.048 ms に対し現行 cmdpos_parse が 2.40 ms で 50 倍速い。ところが Python のプロセス起動が 27.3 ms かかり、解析の 570 倍にあたる。ホットパスのフックは毎ツール呼び出しで起動し直す使い捨てプロセスなので、この 27.3 ms が丸ごと乗る。1 本あたり +20.7 ms、5 本で +103 ms。

◆特に見てほしい

判断に困っている

  • 「解析は 50 倍速い」を捨てる判断でよいか。常駐プロセスにすれば活かせるが、フックの実行モデルを変える話になる
  • 直列の合計（+103 ms）を増分として扱ってよいか。5 本は並列に起動するので壁時計はこれより短い

◇承認が欲しい

方針は決めた

  • DDR i0009-22 は上書きせず維持する。Python の追加は認められている外部プロセスの予算（jq 1 回 = 3.85 ms）の 7.1 倍
  • Python 不在の環境で検査が丸ごと落ちる形は、fail-open を塞げないという DDR i0009-11 の前提と噛み合わない

・細かいレビューは不要

ほぼ確実

  • 測定の揺れより差がはるかに大きい。bash 版の最大値 9,656 µs と Python 版の最小値 25,936 µs は範囲が重ならない

確かめられなかったこと（この結果が言っていないこと）

  • Windows / Git Bash での実測。この実行環境（Linux コンテナ）から測れない。仕様書は Git Bash での git 起動を約 95 ms としており差はさらに開く見込みだが、裏付けは無い
  • ホットパス 5 本を実際に同時起動させたときの壁時計時間。本調査は 1 本ずつ直列に測った
  • uv を使った場合の起動時間。uv はこの環境に無い。#15 本文の実測（uv run --no-project 29 ms）を引き継ぐに留めた

実施条件（測った対象・環境）

  • Linux コンテナ。bash 5.x、Python 3.11.15、jq
  • 各 50 回の中央値。時刻は bash の EPOCHREALTIME（マイクロ秒）と Python の time.perf_counter
  • 解析に使った入力は git commit -m "fix: あ" && echo $(ls -1) | tee out.txt（複合コマンド・日本語・コマンド置換・パイプ・書き込み先を含む）
  • 計測スクリプトは wip/tmp/bench.sh と wip/tmp/probe.py（追跡外）

実施した内容と結果

  1. 1

    B-1 起動コストの実測 ✕問題 根拠: bench.sh stats（各 50 回）

    対象中央値 (µs)最小最大
    python 内 shlex 解析（起動なし）4846177
    bash -c ':' 起動2,3962,1203,732
    bash 内 cmdpos_parse（起動なし）2,3952,0834,412
    jq -n 起動3,8503,4656,346
    bash 起動 + cmdpos.sh 読込 + 解析6,6165,4279,656
    python3 -S -c pass10,8929,80413,308
    python3 -S -c 'import shlex'21,45019,67439,631
    python3 起動 + 解析27,33225,93630,884

    増分の見積り: ホットパス 1 本が現行 6,616 µs、Python 版が 27,332 µs で +20.7 ms。5 本が毎ツール呼び出しで走るので直列に足すと +103.6 ms／ツール呼び出し。

    import shlex だけで 10.6 ms 増える（10,892 → 21,450）。shlex が re を引き込むためで、最小限の起動でも避けられない。何もしない Python（-S -c pass）でも bash の空起動の 4.5 倍。

    結論

    DDR i0009-22 は「ホットパスが起動してよい外部プロセスは jq の 1 回だけ」と定めている。その jq が 3,850 µs。Python の追加は 27,332 µs で、認められている予算の 7.1 倍を 1 本ごとに使う。「1 秒以内」という目安には収まるが、同 DDR が「1 秒以内は検査できない形なので fork 回数で縛る」と決めた経緯からすると、目安を持ち出して通す筋ではない。

  2. 2

    B-2 Python 実装の前提 ✕問題 根拠: DDR i0001-14 / i0009-11、hook-common.sh の読み込み行

    #必要になるもの難しさ
    1インタプリタの解決フックはリポジトリルートを fork なしで解決している。Python の場所は同じようには決められない。Windows では python3 が PATH に無く py や python になる
    2起動オプション-S で 27.3 → 21.5 ms 程度。-I で環境変数の影響を排除。それでも bash の 2.4 ms には届かない
    3import の最小化shlex は re を引き込み 10.6 ms。json を足せばさらに増え、stdin を jq で読んでいる現状と重複する
    4DDR i0001-14 の基準を満たすこと判定材料は「想定する全実行環境で確実にアクセスできるもの」に限られる。Python は Git Bash に同梱されない。同 DDR は逃げ道（全環境で保証されるようになれば使ってよい）を用意しているが、uv 自体の配布が要る
    5ブートストラップの入口SessionStart フック自身は Python 不在でも動く必要があり bash で書くことになる。入れ子の依存が生じる
    6失敗時の振る舞いDDR i0009-11 が「打ち切りは fail-open で塞げない」と決めている。Python 不在の環境ではコマンド検査が丸ごと落ちる。bash 版のフォールバックを残すなら同じ判定を 2 言語で二重実装することになり、食い違いが新しいバグの種になる

    結論

    6 項目のうち 1・4・5・6 が設計上の判断を要する。とくに 6 が重い。フックは自動で走り、失敗したときの復旧手段が AI に無い。Python 不在の環境で検査が落ちる形は、この機構の前提と噛み合わない。

設計への反映

  1. 本番置換は採らない。0046 の「判定誤りが 7 件入る」に加え、本調査の「+103 ms／ツール呼び出し」「DDR i0009-22 の予算の 7.1 倍」「Python 不在時に検査が落ちる」が重なる。どれか 1 つでも十分な却下理由になる
  2. DDR i0009-22 は維持する。上書きの必要が無い。ただし「なぜ Python を入れなかったか」を新しい DDR に残し、次に同じ問いが出たときに実測から辿れるようにする
  3. 照合役案の起動コストは問題にならない。テストは毎ツール呼び出しではなく明示的に走らせるもので、27 ms の起動が 1 回増えても影響しない
  4. 解析が 2.4 ms かかっている事実は別の話として残る。cmdpos_parse は fork ゼロだが、bash の空起動と同じだけの時間を解析に使っている。速くする余地はあるが本 issue の範囲外

想定と異なった点

計画時の見込み実際どう扱ったか
Python 版は「起動のぶんだけ遅い」解析そのものは 50 倍速く、起動で逆転する構図だった「解析 vs 起動」を分けて測り直し、両方を表に載せた
#15 の実測（python3 18.5 ms）を再現するこの環境では 27.3 ms。-S で 21.5 ms まで下がる環境差として両方を記録し、増分の見積りには自分の実測を使った
B-2 は「何が必要か」の列挙で終わる失敗時の振る舞い（項目 6）が単なる列挙ではなく却下理由の 1 つになった設計への反映に格上げした

  • ホットパス 5 本の並列起動の壁時計時間。直列の合計（+103 ms）は上限側の見積り
