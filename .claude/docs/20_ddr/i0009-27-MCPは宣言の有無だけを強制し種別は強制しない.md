# i0009-27. MCP 経由の操作は宣言の有無だけを強制し、リモート書き込みの種別は強制しない

## 背景

`mcp__.*` を matcher に持つのは `workflow-state-guard` の 1 行だけだった（draft 解除の検知用）。`workflow-entry`（未宣言の拒否）と `workflow-guard`（宣言範囲の強制）はどちらも `Edit|Write|MultiEdit|NotebookEdit|Bash|PowerShell|EnterPlanMode|Agent|Workflow` で、MCP を含まない。§2 の `tool_class` も MCP を「読み取り」（上記以外）に落とす。

境界レビュー（付録 A の R4）が指摘したのは、`gh` / `glab` が使えない環境で MCP に切り替えた瞬間（`00-workflow-issue-mr-driven` の外部委任モードは実際にこれを想定している）、`mcp__github__create_issue` / `add_issue_comment` / `update_pull_request` が **WF101（未宣言の拒否）も WF206（宣言に無いリモート書き込み）も通らずに素通り**すること。要件 `workflow-guard`「リモートへの書き込みが試みられたとき…宣言にその操作があるときだけ許可し、無ければ拒否」を満たしていない。

## 決定

- **`workflow-entry` の matcher に `mcp__.*` を足す**（§1 の登録表 2 行目）。未宣言のセッションでは MCP ツールも WF101 で拒否される
- **`workflow-guard` の matcher には足さない**。MCP 経由のリモート書き込みの**種別**（issue 作成 / コメント / MR 編集）は宣言と突き合わせない
- §13「意図的な緩和」に理由付きで書く。要件（`workflow-guard`）にも「外部の連携ツールを経由するリモート書き込みは種別を強制しない。この統制は計画タスクの自制に依存する」を追記する
- draft 解除だけは従来どおり `workflow-state-guard` が塞ぐ（`mcp__*pull_request*` / `*merge_request*` の `draft:false`）

## 理由

- **宣言の有無の判定にはツールの種類が要らない**。「振り分けを宣言したか」はセッション状態を見るだけなので、何をする MCP ツールかを分類できなくても判定できる。安く確実に効くので足す
- **種別の突き合わせには分類が要る**が、**MCP のツール名はサーバが定義する**もので `remote-write:<種別>` に機械的に対応づけられない。`mcp__github__*` は名前から推測できても、別の MCP サーバが同じ操作を別名で提供する。パターンを書けば書くほど、当たらない名前に対して「守っている」という誤った安心が生まれる（`redact` と同じ構造の問題）
- **誤分類の害が大きい**。外部委任モードは `gh` が使えないときの唯一のフォールバックで、ここで正当な操作を止めるとワークフローが進まない。`00-workflow-issue-mr-driven` の手順は `--external` フラグで人間の目を通す形になっており、そちらが統制を担う
- 「強制するもの / 自制に依存するもの」の線引きは要件の制約条件に既にある枠組みで、そこに載せれば済む

## 却下した案

- **`workflow-guard` にも `mcp__.*` を足し、名前のパターンで種別を分類する**: 上記のとおり当たらない名前が残り、誤った安心を与える。誤分類で止まる害も大きい
- **MCP ツールをすべて `remote-write` 扱いにして宣言を要求する**: `mcp__github__get_issue` のような読み取りまで止まる。読み取りは `read` / `remote-read` として宣言なしで通すのが既定（§8）で、それに反する
- **`workflow-entry` にも足さない（完全に素通りさせる）**: 宣言の強制は分類が要らないのに諦めることになる。振り分けの入口ガードは機構の骨格なので、抜け道を残さない
- **MCP を使うときは提供コマンドを経由させる**: 提供コマンドは `gh` / `glab` に依存しており、`gh` 不在時のフォールバックとして成立しない
