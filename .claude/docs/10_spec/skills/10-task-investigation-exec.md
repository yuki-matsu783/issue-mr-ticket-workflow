# 10-task-investigation-exec スキル 仕様

## 概要・禁止事項

調査実施タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-investigation-exec.md](../../00_requirement/skills/10-task-investigation-exec.md)。

**実施タスク（`10-task-*-exec`）に共通する処理フローの正はこの仕様書**で、他の実施タスクの仕様は差分だけを書く。

禁止事項:

- ファイルの書き換え・リポジトリ外への問い合わせ（承認された外部技術調査のチケットを除く。コマンドによる取得はチケットの `allow.ops` の `web` を機構が強制し、Web 検索・Web 取得のツールは自制による — `フック共通仕様` §8）・ビルドやテストの実行（チケットの `allow.ops` に `build-test` が宣言されている調査チケットを除く。宣言があっても書き込みは一時ディレクトリに限る）
- `.claude/**` への一時的な変更（`settings.json` へのフックの一時登録など。機構の上限が拒否する経路であり、調査計画も計画しない — DDR i0006-05）
- 設計・実装の決定（候補と比較軸を並べるまで）、調査計画書・全体計画書の書き換え
- 推測を事実のように書くこと、答えが出ていない問いを出たことにすること
- チケット群の並列実施、サブエージェントの入れ子起動（DDR i0001-23）
- 完了済みチケットを作業中に戻すこと（差し戻しは追加チケット）

## 呼出条件

- `00-workflow-issue-mr-driven` の `next` が調査チケットを示したとき、全体計画で合意した実行者（サブエージェントのモデル）で読み込まれる
- チケットの実行者がタスクのモデルと異なる場合、チケット単位のサブエージェント起動を呼び出し元に要求する（自分では起動しない）

## IN / OUT

| IN | OUT |
|----|----|
| 調査計画書（観点・対象と方法・成果物の形）、調査チケット群 | 調査結果レポート（`wip/30_reports/`、md + HTML）、完了済みの調査チケット群、結果報告 |

## IN / OUT サンプル

- レポート: `wip/30_reports/0003-investigation.md` / `.html`（最初のチケットで作成、2 枚目以降は節を追記）
- 観点ごとの節: 「答え: 空パスワードは `auth/validate.ts:42` で弾かれていない（根拠: 該当行・テスト `auth.spec.ts` に該当ケース無し）。性質: 問題 / 重み: ◆」
- 結果報告: 「チケット 0003・0004 完了。レポート 0003-investigation。見てほしい点: 全観点に答えか理由があるか / 根拠の具体性 / 候補と比較軸が設計計画に足りるか / 決定していないか。確かめられなかったこと: CI の実行結果（ログ無し）」

## 処理フロー

### 実施タスクの共通手順（正）

1. **入力の確認**: 計画書と実施チケット群を読む。計画書が無い・チケットが計画と対応しない場合は始めず、状態の不整合として結果報告に書いて呼び出し元に戻す
2. **着手**: `ticket.sh next` が示すチケットを `ticket.sh start` で 1 枚ずつ作業中にする。そのチケットの担当範囲だけを実施する。作業ログはその都度追記する
3. **実施**: 各仕様の固有手順
4. **レポート**: 最初のチケットで `wip/30_reports/<最初のチケット連番>-<種類>.md` をレポートテンプレートから作り、`20-common-step-report-view` の手順で同名 HTML を作る。以降のチケットは同じレポートに節を追記し、md と HTML を同期させて検査する
5. **成果物のコミットと完了**: そのチケットの成果物を `20-common-step-commit-push` でコミットし、`ticket.sh complete`（DoD・作業ログ・未コミット無しが検査される）
6. **次へ**: 同じ種類のチケットが未着手に残っていれば 2 へ（タスクの切れ目ではない）。すべて完了したらレポートを仕上げ、結果報告（完了したチケットの一覧・レポートの場所とサマリ・見てほしい点・確かめられなかったこと・残課題）を呼び出し元に返す

- 再開: 作業ログ「現在地」から続け、レポートの節を二重に作らない
- 差し戻し（同種の追加チケット）: 既存のレポートに Edit で追記・修正し、対応を「判断と根拠」に残す
- 書き込みの拒否: 範囲を広げる確認を求めず、直したい内容を修正案としてレポートに書いて後続のフェーズへ回す
- HTML の検査で問題があれば解消してから完了する
- 敵対的レビューが計画されている場合、レポート（と成果物）はその対象になり、指摘は人間の指摘と同じ扱いで対応する

### 調査の固有手順

- 3 の実施は**読み取りだけ**（閲覧・検索・履歴・既存のテスト結果や記録）。チケットの「やってよいこと」に外部への問い合わせが明示された外部技術調査だけは Web 検索・公式ドキュメントの閲覧を許し、結果を候補・選定基準・出典の比較にまとめる。同様に、`allow.ops` に `build-test` が明示された調査チケットだけは既存のテスト・ビルドの実行を許す（計画書が「確かめ方」に書いた範囲に限り、書き込みは一時ディレクトリだけ。結果はコマンドと要約を根拠として残す）
- 宣言の無いチケットでビルド・テストの実行が要ると思っても実行せず、既存の記録で代え、必要なことを「確かめられなかったこと」に理由付きで書く（次の調査計画で宣言付きのチケットを起こす提案にしてよい）
- 選択肢が複数ある問いは候補と比較軸（変更量・リスク・既存パターンとの整合など）を並べるまでで、決めない
- 観点自体が的外れだと分かったら観点は書き換えず「答えが出なかった理由」として経緯を書き、代わりの問いを「残課題」に提案する
- 想定外の事実（不具合・負債・文書と実装の食い違い）は直さず「想定と異なった点」または「残課題」に書き、作業ログ「スコープ外で見つけたこと」にも残す
- 見てほしい点の固定項目: すべての観点に答えまたは理由があるか / 根拠が具体的か / 候補と比較軸が次の計画の判断に足りるか / 調査の範囲を超えた決定をしていないか

## OUT ひな形

調査結果レポートは report-view のレポートテンプレート（サマリ → 確かめられなかったこと → 実施した内容と結果 → 設計への反映 → 想定と異なった点 → 残課題）を使い、「実施した内容と結果」に観点ごとの小節（答え / 根拠 / 結論の性質 良・注意・問題 / レビューの重み ◆・◇・・）を置く。対象 issue と MR を冒頭に明記する。
