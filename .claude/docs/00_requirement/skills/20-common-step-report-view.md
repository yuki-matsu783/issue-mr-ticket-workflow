# 20-common-step-report-view スキル

## 概要

HTML ビュー作成の共通ステップの要件を定義する。レポート（各実施タスクの結果レポート・全体まとめの統括レポート）と各フェーズの計画書に付ける HTML ビューを、テンプレートのコピーと編集で作り、Markdown と同期させ、機械的検査に通す手順を標準化する。計画・実施・全体まとめのタスクから使われる。

- **背景**: レポート・計画書は人間レビューの主要な入力であり、HTML ビューがあると読みやすさが大きく変わる。一方で md と HTML の二重管理は不同期を生みやすく、HTML を生成やフリーハンドで書くとテンプレートから逸れて壊れた（プレースホルダ残り・外部依存あり）ビューが届く。
- **目的**: どのレポート・計画書にも同じ見た目・同じ視覚語彙の HTML ビューが付き、正文（Markdown）と常に同期し、壊れたビューが機械的検査で止まる状態を作る。
- **スコープ**:
  - 含む: 対象の判定（HTML ビューが必須の文書）、テンプレートのコピーと編集による作成、md との同期の保ち方、出力後の機械的検査、検査結果の記録
  - 含まない: レポート・計画書の中身（各タスクの手順）、テンプレート自体の設計・改訂（AI アセットの設計・実装）、MR へ添付する操作（`10-task-overall-summary`）

---

## ユーザーストーリー

**[As a]** 計画とレポートをレビューする開発者として、

**[I want]** どの文書も同じ見た目の HTML ビューで読め、内容が Markdown と一致し、壊れたビューが届かないでほしい。

**[So that]** フェーズをまたいでも同じ読み方でレビューでき、ビューの崩れや古い内容に気を取られないため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 対象の文書を作るとき、Shall スキルは HTML ビューが必須の文書（`wip/30_reports/` の結果レポートと統括レポート、`wip/20_plans/` の各フェーズの計画書）に、正文の Markdown と同じベース名の HTML を併存させなければならない。全体計画書には作らない。
- When HTML を作るとき、Shall 用途に対応するテンプレートを同じベース名でコピーし、節を編集で埋めなければならない（スクリプトで HTML を組み立てない・白紙から書かない）。
- When 内容を書くとき、Shall Markdown を正文とし、HTML は同じ内容の視覚化にしなければならない（HTML にだけある情報を作らない）。
- When 正文を更新したとき、Shall 同じ変更を HTML にも反映してから作業を終えなければならない（片方だけの更新で終えない）。
- When HTML を書き終えたとき、Shall 機械的検査（プレースホルダ 0 件・リンク破断 0 件・重複 ID 無し・外部依存 0 件・`<style>` が 1 つ）に通し、結果を作業ログに残さなければならない。

### 代替フロー

- If 文書の内容にテンプレートの節が対応しない場合、Then スキルは節の意味に沿って最も近い節に収めるか空の節を規定の書き方で明示し、テンプレートの DOM 構造を改変してはならない（構造の変更はテンプレート自体の改訂として提案する）。

### 例外フロー

- If 機械的検査が失敗した場合、Then スキルは検査を飛ばして提出せず、原因を直して再検査しなければならない。
- If 対応するテンプレートが無い場合、Then スキルはフリーハンドで HTML を書かず、テンプレートの不在を呼び出し元に返さなければならない。

### 見た目と構成の規約

- When 視覚語彙を使うとき、Shall テンプレートの定義（結論の性質は 3 色 + 記号 + 文字、レビューの重みは色相を使わず ◆ / ◇ / ・）に従い、独自の色・記号を持ち込んではならない。
- When HTML を作るとき、Shall 自己完結（外部リソースの参照なし）で、ライト / ダークの両方で読める形にしなければならない（テンプレートに従えば満たされる）。

### 他のスキル・機構との整合

- When push するとき、Shall md と HTML の同期が push 前チェックの対象であることを前提とし、不同期のままの push は止まる。
- When 各タスクのスキルが HTML ビューの作り方を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。

---

## 前提条件

- 正文となる Markdown（レポート・計画書）が呼び出し元のタスクで書かれていること
- 用途別のテンプレートと機械的検査の手段が導入されていること

---

## 制約条件

- **技術的制約**: HTML は自己完結・1 ファイル。テンプレートの DOM は改変しない
- **ビジネス的制約**: 正文は Markdown。合意・索引・検索は Markdown を対象にする
- **外部的制約**: テンプレートの構成・視覚語彙・検査項目の正は仕様書とテンプレート自体。このスキルは使い方を標準化する

---

## 依存関係

- 各計画・実施タスクと `10-task-overall-summary`（呼び出し元）
- レポート用・計画書用のテンプレートと機械的検査の手段（未作成）
- `20-common-step-ticket`（検査結果の記録先である作業ログ）

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | すべてのレポート・計画書が同じテンプレート・同じ視覚語彙で表示される |
| 完全性 | 提出される HTML はプレースホルダ・破断リンク・外部依存を含まない |
| 同期性 | md と HTML の内容が常に一致し、不同期は push 前に検出される |
| 可搬性 | HTML 単体で（オフラインでも）開いて読める |
