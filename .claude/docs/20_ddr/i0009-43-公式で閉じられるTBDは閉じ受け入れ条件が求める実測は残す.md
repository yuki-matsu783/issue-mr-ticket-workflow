# i0009-43. 公式で閉じられる TBD は閉じ、受け入れ条件が求める実測は残す

## 背景

共通仕様 §12 の TBD 表に、公式の記述と食い違う扱いが 3 つ残っていた。

- **T1**（`SubagentStop` の出力がメインエージェントに届くか）: 取得済みの原本が既に答えている（`hooks.md:2346`「To inject context into the parent session after a subagent returns, use a `PostToolUse` hook on the `Agent` tool instead.」）のに、実測待ちのままだった
- **T6**（PreToolUse の deny が `permissionDecision` + 終了 0 で効くか）: 引用していた「Claude Code ignores the exit code and the JSON alone decides the outcome」は `hooks.md:824`、すなわち **`#### Other exit codes`（0 と 2 以外）の節**からの転用で、**終了 0 の経路を支えていない**
- **T7**（`tool_response` の終了コードのフィールド名）: 文書の確認だけで「解決（TBD ではない）」と打ち消し線を引いた。しかし issue #9 の受け入れ条件 5 は「`tool_response` / `agent_type` / `web` の強制 / `defer` の扱いが**実物の確認に基づいて**仕様に書かれている」を求めており、全体計画のフェーズ 4c の表にも T7 の実測行がある。文書で閉じたことで 4c で実物を見る動機が消え、全体計画と食い違っていた

## 決定

- **T1 を閉じる**（打ち消し線 + 「解決（TBD ではない）」）。根拠は `hooks.md:2346`。現行の登録（PostToolUse `Agent` で通知）が公式の推奨形そのもの。全体計画 4c 表の T1 も実測不要にする
- **T6 の引用を差し替える**。`hooks.md:774`（「The exit code doesn't act alone. Claude Code reads JSON output fields from stdout on every exit code, not just 0, and for events that use the standard decision model, a parsed object that passes schema validation takes effect alongside the code.」）と `:778`（「Exit 0 means success, and is the intended exit code when you print JSON for structured control.」）に、PreToolUse の decision control の「`"deny"` prevents the tool call.」を添える。従前の引用がどの節のものだったかも書き残す。位置づけは**文書上は解決 + 段階登録 ②-1 のスモークテスト**のまま
- **T7 の打ち消し線を外す**。「**文書上は解決**（実物の確認はフェーズ 4c）」に戻し、4c で `post-push-*` が受け取る `tool_response` を `logs/` に落として文書どおりであることを確かめる。縮退の欄も復活させる
- **一般則**: 公式の記述だけで閉じられる TBD は閉じる。ただし**受け入れ条件が「実物の確認」を明示しているものは、文書での解決を実測の免除にしない**

## 理由

- **取得済みの原本が答えているのに実測待ちにするのは、条件の充足度を理由なく下げる**。T1 は 0007 の調査で落とした原本にそのまま書かれており、読めば閉じる
- **引用は文脈ごと正しくないと根拠にならない**。「その他の終了コード」の節の一文で終了 0 の経路を説明すると、読み手は「終了 0 でも JSON が単独で決めるのか」を確かめられない。`:774` は終了コード全体を通した規則を述べており、`:778` が終了 0 が意図された経路であることを言う。この 2 つで足りる
- **受け入れ条件は「文書に書いてある」ではなく「実物の確認に基づいて」と書かれている**。文書での解決は実測の**予測**を強くするが、条件そのものを満たさない。4c の実測はコストが小さい（`logs/` に落として見るだけ）ので、条件どおりに残すのが安い
- **T7 と T1 の扱いが違うのは条件の文言による**。T1 は受け入れ条件 5 の列挙（`tool_response` / `agent_type` / `web` / `defer`）に含まれないため、文書で閉じてよい

## 却下した案

- **T7 も打ち消し線のままにして 4c から外す**: 受け入れ条件 5 を満たさない。全体計画の 4c 表とも食い違ったままになる
- **受け入れ条件 5 の解釈を「公式ドキュメントという実物」に広げる**: 条件は「公式リファレンス（フェーズ 2）→ 実測（4c）」という段取りとセットで全体計画に書かれており、実物 = 動いている機構が受け取る値である。解釈で条件を緩めない
- **T1 も 4c の実測に残す**: 実測の項目が増えるほど 4c が重くなる。原本で閉じられるものを残す理由が無い
- **T6 の引用をそのままにして注記だけ足す**: 誤った引用は消す。注記で「実は別の節のもの」と書くくらいなら差し替える

## 影響

- `10_spec/フック共通仕様.md` §12（T1 を解決に・T6 の引用を差し替え・T7 の打ち消し線を外す）
- `wip/00_overall_plan/overall-plan.md` フェーズ 4c の表（T1 を実測不要に・T7 に実測を残す理由を明記）
- **フェーズ 4c へ**: T7 の実測（`post-push-*` が受け取る `tool_response` を `logs/` に落とす）
- 関連: `i0009-07`（PostToolUse に届いた = 成功）・`i0009-06`（`model` は来ない）
