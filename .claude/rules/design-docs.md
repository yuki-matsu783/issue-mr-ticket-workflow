# design-docs — アプリ本体の設計文書（docs/）の正典規約

アプリ本体の設計文書は「その時点で有効な正史」だけを書き、決定の経緯は DDR に、用語の定義は用語辞書に置く。requirement は利用者から見た振る舞い、spec は内部構造。適用範囲は `docs/**` だけで、AI アセットの設計文書（`.claude/docs/**`）は `ai-asset-design-docs` ルールが独立に持つ（共通する規定は両方に書き、内容を食い違わせない）。frontmatter のキーと `type` の値一覧は `markdown-docs` ルールが正で、ここでは再掲しない。

## 適用範囲

- `docs/**` の文書を作成・変更するとき（要件定義書 `00_requirement/`、仕様書 `10_spec/`、DDR `20_ddr/`、用語辞書 `90_glossary/`）
- 文書の内容の妥当性は MR 上の人間レビューが判断する。このルールは形（置き場・書き分け・書いてはいけないもの）を定める

## 構造・配置

- 置き場は `docs/00_requirement/`（要件定義書）/ `docs/10_spec/`（仕様書）/ `docs/20_ddr/`（DDR）/ `docs/90_glossary/`（用語辞書）の 4 つ。他のディレクトリに設計文書を置かない
- requirement と spec の書き分け: requirement は利用者から見た振る舞い（何ができ、何が拒否され、何が出力されるか）、spec は内部構造（コマンドの構成・状態の持ち方・判定の手順・データの形式）。requirement に内部構造が混ざったら spec へ移す
- DDR は設計上の決定（複数案から選んだ・方針を変えた）ごとに 1 ファイル。命名は issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md`。issue を持たない DDR を作らない
- DDR の一覧は各 DDR の frontmatter から生成する。手書きの一覧を保守しない（生成手段は仕様書が定める）
- 用語辞書は「用語の定義（意味・目的・他の用語との関係）」の正。振る舞いの正（When / Shall）は requirement / spec が持ち、辞書と要件書で役割を重複させない

## 書式・可読性

- requirement / spec は正史のみ。検討の経緯・却下した案・過去の版の内容・変更履歴の表・「以前は〜」を本文に残さない（履歴は git のコミット履歴と DDR で追う）
- DDR は 背景 / 決定 / 理由 / 却下した案 / 影響 を持つ
- 辞書のエントリは 用語名 + 定義（2〜4 行）+ 別名・禁止表記（旧称・使わない言い方。あれば）。定義は辞書の中だけで読めて完結させ、設計書へのリンクに頼らない
- 辞書に振る舞いの要件（When / Shall、判定基準・数値・手順）を書かない
- 収録済みの用語を文書で使うときは辞書の表記に従い、初出箇所で辞書へリンクし、文書内で定義を再掲しない。禁止表記を使わない
- 辞書に載せる語は、複数の文書で使われ、かつ指し先や表記が揺れうるプロジェクト固有語（アプリが導入した概念・コンポーネント名・用語の読み替え規則）に限る。一般的な技術用語は載せない
- frontmatter（`type` / `title` / `description` / `tags` / `keywords`）の規約は `markdown-docs` ルールに従う（再掲しない）

## セキュリティ

- 該当なし — 設計文書は共有前提の記述で秘密情報を含めない一般則は文書全般の規約（`markdown-docs`）が担い、設計文書に固有の規定は無い

## 堅牢性

- マージ済みの DDR は本文を変更しない。後続の決定で無効になったときは frontmatter の状態（置き換え済み / 廃止）と置き換え先だけを更新する
- マージ済み DDR の内容を訂正する必要が出たら、新しい DDR で置き換え、旧 DDR は frontmatter の状態の更新だけで扱う（本文の書き換えで直さない）
- 新しい固有語は、まず辞書に定義してから設計書で使う（辞書が先、設計書が参照する）。収録語をリネームしたときは同じチケットの中で辞書を更新し、旧称は別名・禁止表記に残す
- 他の文書と矛盾する記述を見つけたら、片方だけ直さず、矛盾する文書を特定して同じ変更の中で揃える

## パフォーマンス

- 該当なし — 設計文書は読み物で実行時の性能観点が無い。探索は frontmatter 索引で足りる長さと粒度（1 対象 1 文書）を保つことは「構造・配置」が担う

## テスト・機械的検査

- 章立て・禁止節（変更履歴・レビュー記録）の不在・DDR の命名・一覧の生成状態の機械的検査は、設計文書検査（仕様書が定める）に統合する。整備されるまでは、要件書・仕様書の作成手順（`20-common-step-requirement` 処理フロー 7、`20-common-step-spec` 処理フロー 5）のセルフレビューと MR 上のレビューで見る
- レビューで見る観点は本ルールの各章。別のチェックリスト文書を作らない
