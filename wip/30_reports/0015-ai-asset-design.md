# 0015 AI アセット設計結果 — 共通ライブラリと提供コマンドの仕様

## サマリ

0008 の設計計画が割り付けた**決定 3・4・7・13・15・16 の残り**を 3 スキル（`20-common-step-shell-script` / `20-common-step-ticket` / `20-common-step-commit-push`）の仕様に落とした。更新した文書は仕様 4 本・要件 1 本、新規の DDR は 4 件（`i0009-16`〜`19`）。

確定したことは 6 つ。

1. **`frontmatter.sh` のスタブは戻り値 2**。`0` = 読めた / `1` = キーが無い（→ **WF211** チケットの記載不正）/ `2` = ライブラリ不在（→ **WFx09** 機構の破損）。0014 が送ってきた最重要の申し送りが閉じた
2. **共有ライブラリは分類まで、規約の照合は呼び手**。`tool_class` は `Skill` を `tool_input.skill` の値を見ずに常に「宣言」に分類し、振り分けスキル名の照合は `workflow-entry` が `entry-skills.txt` で行う
3. **`run-tests.sh` の ID 抽出の制約**（`^(PASS|FAIL) ([A-Z]{2,6}-[TE][0-9]{2}[a-z]?)`）を仕様に明記し、**仕様に書かれた全 ID がこの形に適合すること**を確認した（フック側 109 件・スキル側 81 件、非適合 0 件）
4. **G8: 提供コマンドは作業中チケット 1 枚を前提に動く**。件数を見るのは `ticket.sh start` だけ。実体の修正は**不要**なので #10（3/3）への申し送りは出さない
5. **D5: `ops` 上限を広げない**。設計・実装が外部の情報を要したら調査タスクを起こす、を要件に 1 行足した
6. **D6: `shellcheck` を CI に載せない**。`run-tests.sh` にも組み込まず、ローカル検査の**記録を省略できないもの**にした

- ◎良 5 件 / △注意 2 件 / ✕問題 0 件

## レビューしてほしい観点

### ◆特に見てほしい（判断に困っている）

- **f5（△注意）D5 で `ops` 上限を広げない**と決めたこと。0014 で `web` を強制しないと決めた以上、上限に足しても機構の振る舞いは変わらない。それでも足さないのは「設計中に外部を見たくなったら調査タスクを起こす」という圧力を残すためで、**運用の窮屈さと引き換え**になっている。この issue の 0012〜0014 は 0007 の調査結果を引用して回避できたが、いつもそうとは限らない
- **f6（△注意）D6 で `shellcheck` を CI に載せない**と決めたこと。「記録を省略できない」だけで実効性を担保しているので、レビューで省略の連続を見つけられなければ静的検査が形骸化し得る

### ◇承認が欲しい（方針は決めた）

- **f1** `frontmatter.sh` のスタブを戻り値 2 にし、`scope.sh` が 1 と 2 を潰さずに呼び手へ返すこと（`HK-T16` で固定）

- **f4** 提供コマンドの実体を直さず「1 枚前提」を仕様に明記すること（#10 への申し送りを出さない）

### ・細かいレビューは不要（ほぼ確実）

- **f3** `run-tests.sh` の ID 抽出の正規表現の制約と `TR-T06` の追加（機械的に確認済み）
- **f7** フック共通仕様 §2・§8 に残っていた未決の言い回しの解消と、3 スキルの要件が「対象なし」であることの確認

## 実施した内容と結果

### f1. `frontmatter.sh` のスタブは戻り値 2 で「読めない」と「無い」を区別する ◎良

0014（`i0009-14`）が `scope.sh` の読み込みポリシーを `nop` にしたとき、**`WF209`（機構の破損）と `WF211`（チケットの記載不正）を区別する方法**を 0015 に送っていた。どちらも `fm_get` が空を返すので、空だけを見ると取り違える。

- **決定**: `nop` で読めなかったとき `fm_*` を**出力なし・戻り値 2** のスタブとして定義し、`FM_AVAILABLE=0` を設定する。戻り値で 3 状態（0 読めた / 1 キーが無い / 2 ライブラリ不在）を区別する
- `scope.sh` は `fm_*` の戻り値 2 を自分の戻り値 2 としてそのまま呼び手へ返す（1 と 2 を潰さない）
- 案内側フックは 1 と 2 のどちらでも通すが、`decisions.jsonl` の `note` に原因を書き分けられるよう区別自体は保つ
- 決め手は「提供コマンドの終了コード（0 成功 / 1 前提未充足 / 2 環境の誤り）と揃う」こと。読み手が新しい約束を覚えなくてよい
- テストは `SS-T04`（スタブと `FM_AVAILABLE=0`）と新規 **`HK-T16`**（`scope.sh` の戻り値 0 / 1 / 2 の区別と無出力）で固定した

結論: 0014 の最重要の申し送りが閉じた。DDR `i0009-16`。

### f2. 共有ライブラリは分類まで、規約の照合は呼び手が行う ◎良

`hook-common.sh` の `tool_class` が `00-workflow-*` の接頭辞で「振り分けの宣言か」を判定しており、正である `entry-skills.txt` との**二重定義**になっていた（0005 f2 / DDR `i0009-03`）。`i0009-03` はこれを 1 件の是正として決めたが、同じ形の問題は他のライブラリにも起こり得る。

- **決定**: `source` 専用ライブラリと `.claude/hooks/lib/` の共有ライブラリは**入力の機械的な分類まで**を担い、規約との照合は呼び手が行う。`20-common-step-shell-script` 仕様に 4 関数（`tool_class` / `cmdpos.sh` / `scope_classify` / `frontmatter.sh`）の線引きを表として置いた
- `tool_class` は `Skill` を `tool_input.skill` の値を**見ずに**常に「宣言」に分類する。フック共通仕様 §2 の分類表からも条件を外した
- 理由は 3 つ: (1) 二重定義は必ず片方だけ更新される（`00-workflow-hotfix` を足したときの更新漏れ）、(2) 分類（Claude Code の都合で変わる）と照合（プロジェクトの都合で変わる）は変更の理由が違う、(3) ライブラリは呼び手の識別子を知らない（`scope.sh` は WF2xx と WF3xx の両方から使われる）

結論: `i0009-03` の 1 件の是正を、ライブラリ設計の規則に一般化した。DDR `i0009-17`。

### f3. `run-tests.sh` の ID 抽出の制約を明記し、全 ID の適合を機械的に確認した ◎良

0005 f3 が挙げた「`SS-H*` が `run-tests.sh` の抽出正規表現に一致しない」問題は 0013 が `SE-T` への変更で解いたが、**制約そのものが仕様に書かれていなかった**（コードにしか無い）。

- **決定**: `run-tests.sh` の手順 3 に「抽出は `^(PASS|FAIL) ([A-Z]{2,6}-[TE][0-9]{2}[a-z]?)` に一致する行だけ」を明記し、**新しい接頭辞は必ずこの形に合わせる**ことを書いた（接頭辞は大文字 2〜6 文字、続くセグメントは `T`（機械テスト）か `E`（eval）で始まり 2 桁 + 任意の小文字 1 文字）
- 一致しない ID を仕様に書くと、テストが通っていても `--ids` に現れず突合できない = **受け入れ条件 2 を満たせない**ことを理由として書いた
- 境界テスト **`TR-T06`** を追加（`PASS ss-h01` / `PASS SS-X01` / 本文中の `PASS` を数えない。`SE-T01` は拾う）
- **機械的に確認した**: 仕様に書かれた ID のうち非適合は 0 件（フック側 109 件 / スキル側 81 件 / 実装済みテストから抽出した 65 件）

結論: 受け入れ条件 2 の前提（全件が `--ids` に現れる形）が仕様として固定された。実際に走らせた確認はフェーズ 4c。

### f4. 提供コマンドは作業中チケット 1 枚を前提に動く（実体の修正は不要）◎良

G8 の提供コマンド側。現状は非対称で、`run-tests.sh` / `push.sh` / `ticket.sh next` は **1 枚目だけ**を読み、件数を見るのは `ticket.sh start` だけ、`complete` / `cancel` は番号引数なので枚数に依存しない。

- **決定**: **実体は直さない**。「作業中は 1 枚」を前提に動くことを 3 スキルの仕様に明記し、`ticket.sh start` の件数検査を「2 枚目を作らせないための入口の防御」と位置づけた。2 枚以上の**検知と復旧の案内は `workflow-guard` の WF207**（`i0009-02` の延長）
- 「1 枚目」の決め方（名前順 = チケット番号順）も仕様に書き、万一 2 枚あっても挙動が決定的になるようにした
- 残るリスクは「WF207 が提供コマンドを通す」ため `run-tests.sh` が誤ったチケットの `allow.ops` で判定し得ることだが、**影響はテストを走らせるかどうかに閉じており**、作業領域外への書き込みやリモート操作には及ばない
- 実体の修正が不要なので、**#10（3/3）への申し送りは出さない**（DoD が「実体修正が要る結論なら申し送り」としていた条件に当たらない）

結論: G8 は 0012（フック側 WF207）と 0015（コマンド側 1 枚前提）で閉じた。DDR `i0009-18`。

### f5. D5: `ops` 上限を広げず、外部が必要なら調査タスクを起こす △注意

`investigation` 以外の実施タスク（`design` / `ai-asset-design` / `design-feedback` / `implementation`）は `ops` に `web` を持たない。

- **決定**: **広げない**。`scope-limits.json` の実体も変えない
- 0014（`i0009-12`）で `web` は機構が強制しないと決めたので、上限に足しても機構の振る舞いは変わらない。変わるのは「計画が宣言できるかどうか」だけ
- 上限に無いことが「**まず調査を起こせ**」という設計の圧力になる。要件（メインフロー D）に「設計や実装のタスクが外部の情報を必要としたときは、外部への問い合わせを宣言できる範囲を広げるのではなく、調査のタスクを起こして結論を持ち帰る」を 1 行足した
- 実績として、この issue の 0012〜0014 は 0007 の調査結果（`curl` で落とした原本の行番号付き引用）を参照することで済んでおり、**しかも根拠が調査結果として残った**
- あわせて、`investigation` の上限にある「上限に含めるだけで既定では使えない」という注記が**特例ではなく共通の規則の再掲**であることを §8 に明記した（読み手が特例だと誤解する書き方だった）

結論: 現状維持だが、**なぜ広げないか**を要件と DDR に残した。運用の窮屈さと引き換えである点はレビューで見てほしい。DDR `i0009-19`。

### f6. D6: `shellcheck` を CI に載せず、ローカル検査の記録を必須にする △注意

- **決定**: **CI で回さない**。`run-tests.sh` にも組み込まない。処理フロー 5 のローカル検査を続け、**実施の有無の記録を省略できないもの**にした（「実行した」か「不在で省略した」のどちらかを必ず作業ログに書く）
- 理由: (1) CI 設定の変更はリポジトリの設定変更に当たりスコープ外（`CLAUDE.md` の制約条件）、(2) 機構が守るのは「AI が作業している最中に止める」ことで CI は別レイヤ、(3) `run-tests.sh` に混ぜるとテストランナー（振る舞い）と静的検査（形）の責務が混ざり、`shellcheck` 不在の環境で TR005（環境不備・終了 2）になってテストを回せない環境が増える
- 要件の非機能（テスト容易性）に「静的検査は作成・変更のたびにローカルで行い、実施の有無を作業ログに残す（自動実行の仕組みを外部のサービスに置かない）」と書いた

結論: 実効性は「記録を省略できない」ことだけで担保している。省略の連続をレビューで拾えるかが弱点。DDR `i0009-19`（D5 と同じ DDR に統合。0008 の計画どおり）。

### f7. 横断文書の整合と、3 スキルの要件は対象なしだった ◎良

- **フック共通仕様の残骸を直した**: §8 の `ops` の説明にあった「`web` を強制するなら matcher に加える — **2/3 で判断**」を、0014 の決定（強制しない）に合わせて確定文に書き換えた。§2 の分類表の「宣言」の行も f2 に合わせた
- **3 スキルの要件定義書は対象なし**。`20-common-step-shell-script` は既に「静的検査ツールが無ければ省略を作業ログに残す」（D6 と整合）、`20-common-step-ticket` は「スクリプトは作業中のチケットが既にあれば着手を拒否」（f4 の `start` の件数検査と整合）、`20-common-step-commit-push` は「push 前チェックの項目は仕様で定める」（f4 は仕様側の話）。いずれも外部的な書き方で、今回の決定と矛盾しない
- **`自己改善ワークフロー機構.md` は 2 か所**（メインフロー D に f5 の 1 行、非機能のテスト容易性に f6 の方針）。0014 に続いて 2 チケット連続で要件に手が入った
- `.claude/rules/ルール体系.md` は対象なし（ルールの増減なし）。`90_glossary/ワークフロー用語.md` も対象なし（概念 20 語のみ）

結論: 未決の言い回しが仕様に残らなくなった。3 スキルの要件は外部的に書かれていたため、内部の決定が波及しなかった。

## 残課題

- **`run-tests.sh --ids` を実際に走らせた確認ができていない**。適合の確認は文字列と正規表現の突合に留まる。全件の実行はフェーズ 4c（約 5 分かかる）
- D5・D6 はどちらも「現状維持 + 記録」で実効性を担保しており、**レビューが記録を読まなければ形骸化する**。振り返りフェーズで見直しの材料を決める
- 作業中チケットが 2 枚ある状態を作って提供コマンドの挙動を確かめていない。「名前順の 1 枚目」が決定的であることは仕様で決めたが、実装が実際にそうなっているかはフェーズ 4 で確認する
- `tool_class` から接頭辞判定を外すと、参考実装（`hook-common.sh:156-165`）との差分が生まれる。参考実装を後から取り込み直すときに戻ってしまわないよう、実装フェーズで理由をコメントに残す必要がある
- フック側の仕様 ID が 109 件に増えたことで、実装フェーズの本数が 0008 の見積もりより約 15% 多い。0016 の実装計画で工数の見積もりを取り直す必要がある
