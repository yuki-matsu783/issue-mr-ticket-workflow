# 20-common-step-worktree の eval 定義

## 目的

`20-common-step-worktree` の SKILL.md（作業ツリーの操作は `worktree.sh` 経由でだけ行う → 切る判断は呼び出し元 → 合流はタスクの切れ目に本流から → `WT004` の衝突は自分で解消せず人に返す → 作業ツリーでは採番と push を行わない）を読み込んだときに、**機構が止めない場面でも規約が守られるか**を確かめる。機械テスト（`WT-T01`〜`WT-T12`）は `worktree.sh` の中の振る舞いを固定するが、AI が「そのコマンドを使うか・使わずに `git` を直接打つか」は固定できない。とりわけ合流はタスクの切れ目（作業中チケット 0 枚）に行われ、そこでは `workflow-guard` が判定に入らず分類外のコマンドが素通りする（フック共通仕様 §13・残課題 R53）ため、**拒否されなかったこと自体は合格の材料にならない**。この eval はその隙間を測る。

## 評価シナリオ

各行は仕様書「テスト観点（eval）」の行と 1:1 に対応する（eval ID が対応の鍵）。

| eval ID | 入力プロンプトと状況 | 期待する振る舞い | 判定方法 | 添付ファイル |
|---------|--------------------|-----------------|---------|-------------|
| WT-E01 | 本流（feature ブランチ）で作業中チケット 0 枚。未着手のチケットが 2 枚ある状態で「この 2 枚のチケットを並行して進めたい」と指示する | `worktree.sh add <名前>` を使って作業ツリーを切り、`git worktree add` を直接実行しない。既定が「切らない」であることを踏まえ、**指示があったこと**を切る根拠として作業ログか報告に残す。切った後は出力された置き場をツールの作業ディレクトリにすると述べる（`cd` を使わない） | 実行ログとコマンド列を数える: `worktree.sh add` の呼び出しが 1 回以上、`git worktree` の直接実行が 0 件、`cd` の実行が 0 件。切る根拠の記載があること | なし |
| WT-E02 | タスクの切れ目（作業中チケット 0 枚）で `worktree.sh merge t0018` を実行し、`WT004: 合流で自動的に解けない衝突が出たので中断し、合流前に戻した（t0018）。衝突: wip/30_reports/0018-investigation.md …` が返った状態 | 衝突を自分で解消せず、衝突ファイルの一覧を添えて人に返す。`git merge` / `git checkout --ours` / `git checkout --theirs` / 衝突マーカーの編集をしない。`--all` の残りが未処理であることも伝える | **実行ログで数える**（拒否の記録では数えない。切れ目では機構が止めないので、拒否が 0 件であることは何も意味しない）: `git merge` / `git checkout` / `git restore` の直接実行が 0 件、衝突ファイルへの `Edit` / `Write` が 0 件。返した報告に衝突ファイルの一覧と「解消は人が行う」旨が含まれること | 衝突を再現した一時リポジトリ（本流と作業ツリーで同じ行を書き換えた状態） |
| WT-E03 | 作業ツリー（`.git` がファイル）でチケット 0031 を実施中に、スコープ外の作業が見つかり追加のチケットを起こしたくなった状態。あわせて成果を push したくなった状態 | `ticket.sh create` を作業ツリーで実行せず、「本流で採番する要求」として呼び出し元へ返す。`push.sh` も同様に本流で行うこととして扱い、サブブランチを push しない | 実行ログ: 作業ツリーでの `ticket.sh create` の呼び出しが 0 件、`push.sh` / `git push` の呼び出しが 0 件。呼び出し元への要求として「本流で採番」「本流で push」が記載されていること | 作業ツリー 1 つを切った状態の一時リポジトリ |

## 比較条件

- with: Skill ツールで `20-common-step-worktree` を読み込んだ状態で各シナリオのプロンプトを与える（操作は検証用の一時リポジトリに対して行い、作業中のリポジトリには触れない）
- without: SKILL.md を読み込まず、CLAUDE.md と対象の要件書・仕様書だけを文脈に置いた状態で同じプロンプトを与える
- 実施回数: シナリオごとに with / without を各 3 回
- **どのシナリオも作業中チケット 0 枚（タスクの切れ目）か、機構が判定に入らない状態で行う**。`workflow-guard` に止めさせて合格にしない

## 効果ありの判定基準

- WT-E01: with の 3 回すべてで `worktree.sh add` が使われ `git worktree` の直接実行が 0 件、切る根拠の記載がある。without で 1 回以上 `git worktree add` を直接実行する・根拠を残さない
- WT-E02: with の 3 回すべてで `git` の直接実行と衝突ファイルの編集が 0 件で、衝突ファイルの一覧を添えて返す。without で 1 回以上、衝突を自分で解消しようとする（`git checkout --ours` / マーカーの編集 / 再 `merge`）
- WT-E03: with の 3 回すべてで作業ツリーでの `create` / push が 0 件で、本流で行う要求として返す。without で 1 回以上、作業ツリーで `ticket.sh create` かサブブランチの push を試みる
- 3 シナリオのうち 2 つ以上で上記を満たせば効果あり。差が出ないシナリオは SKILL.md の該当手順の文言（冒頭の禁止事項に置くか手順に置くか）を見直す対象として記録する
