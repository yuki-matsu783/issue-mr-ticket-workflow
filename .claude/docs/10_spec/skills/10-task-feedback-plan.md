# 10-task-feedback-plan スキル 仕様

## 概要・禁止事項

フィードバック計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-feedback-plan.md](../../00_requirement/skills/10-task-feedback-plan.md)。

主作業の後に 1 issue につき 1 回だけ実施し、記録からの洗い出し → 分類 → 対話での対応先の合意 → 後続チケットの確定までを行う。

禁止事項:

- サブエージェントへの委譲（対応先の決定に対話が要る。メインエージェント専任）
- 記憶に頼った洗い出し（入力は記録のみ。全チケットの作業ログの固定見出しを機械的になぞる）
- 合意前の後続チケット作成・別 issue の起票
- 独自の分類（観点・類型は機構の定義と一致させる）
- 改善の実施（`.claude/` 配下・ソースコード・設計文書への書き込み。後続フェーズが行う）
- 振り返りのやり直し（フィードバック計画より後の候補は全体まとめの別 issue 起票へ）

## 呼出条件

- `00-workflow-issue-mr-driven` の `next` がフィードバック計画チケットを示したとき、メインエージェントが読み込む（主作業フェーズの切れ目の処理が済んだ後）

## IN / OUT

| IN | OUT |
|----|----|
| この issue の全チケットの作業ログ（`wip/10_tickets/20_done/`・`30_cancelled/`）、MR のレビュー指摘、各レポートの「想定と異なった点」「残課題」、使った AI アセットの一覧 | フィードバック計画書（md + HTML）、起票された別 issue（あれば）、後続フェーズの最初の計画チケットまたは全体まとめチケット（未着手）、見直された未着手チケット、完了済みフィードバック計画チケット |

## IN / OUT サンプル

候補一覧の 1 行（フィードバック計画書の表）:

| # | 候補 | 出どころ | 観点 | 類型 | いつ効くか | 守らせ方 | 対応先 |
|---|------|---------|------|------|-----------|---------|--------|
| 3 | 除外リストに `.tfvars` が無い | チケット 0007 作業ログ「スコープ外で見つけたこと」 | 足りなかった | (c) 罠が書かれていない | 操作のたび | 機械的に拒否 | この MR |

## 処理フロー

1. **着手**: `ticket.sh start` でフィードバック計画チケットに着手する
2. **洗い出し**: 完了・取り消し済みの全チケットの作業ログを、固定見出し（一覧の正は `00_requirement/skills/20-common-step-ticket.md`。全項目を対象にする）の順に**チケット番号順で機械的になぞり**、MR のレビュー指摘（`gh api --paginate` / `glab api --paginate` で全件取得）と各レポートの「想定と異なった点」「残課題」を加えて候補を列挙する。確認した記録の範囲（チケット番号・レポート名）を計画書に書く
3. **分類**: 候補ごとに観点（足りなかった / 邪魔だった / 無かった / 問題なし）と類型（(a) 無かった / (b) 誤っていた / (c) 罠が書かれていなかった / (d) 辿り着けなかった）を付け、反映先を「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）× 守らせ方（読ませる / 手順化する / 機械的に拒否する）」の 2 軸で選ぶ。常時読込を増やす提案にはコストの注記を付ける
4. **合意**: 候補の一覧・分類・提案（既定「この MR で対応」。大きすぎるものだけ「別 issue」）を提示し、候補ごとの対応先（この MR / 別 issue / 対応しない + 理由）を対話で合意する。ヘッドレスでは一覧と提案をコミットせずに報告してセッションを終える（チケットは作業中のまま。作業ログの「現在地」に洗い出し済みである旨を残す）
5. **別 issue の起票**: 合意された候補は本文案の承認を得て `20-common-step-issue` で起票し、番号を計画書に記録する。承認されなかった候補は「この MR に戻す / 対応しない（理由）」を確認する
6. **後続の確定**: 後続フェーズ（設計反映 / AI アセット設計 / AI アセット実装・テスト）の要否を確定し、含める最初の計画チケット（無ければ全体まとめチケット）を `ticket.sh create` で 1 枚未着手に作る。記載事項は全体計画の方針と work-defaults に従う
7. **未着手チケットの見直し**: 振り返りの結果に応じて未着手チケットの範囲・実行者・レビュー要否・DoD を見直し、変更をユーザーに伝える
8. **計画書**: `wip/20_plans/` にテンプレートから md を書き、`20-common-step-report-view` の手順で HTML を作って検査する
9. **完了**: 作業ログを整えて `ticket.sh complete` で完了し、呼び出し元に制御を戻す

- 候補 0 件: 0 件の根拠（確認した記録の範囲）を計画書に書き、6 へ進む
- 再開: 作業ログ「現在地」から続け、済んだ合意をやり直さない。起票済み issue を二重に作らない
- 差し戻し: レビューの差し戻しで同じ種類の追加チケットとして戻った場合は、候補の一覧と後続チケットを見直し、変更を対話で合意し直す（完了済みチケットは戻さない）

## OUT ひな形

`assets/feedback-plan.template.md`（+ 計画書用 HTML テンプレートは report-view のものを使う）:

| 節 | 内容 |
|----|------|
| 対象 | issue・MR |
| 確認した記録の範囲 | チケット番号の一覧・レポート名・レビュー指摘の取得範囲 |
| 改善候補の一覧 | サンプルの表形式（候補 / 出どころ / 観点 / 類型 / 2 軸 / 対応先） |
| 合意 | 候補ごとの決定と合意の記録（0 件ならその根拠） |
| 起票した issue | 番号と URL |
| 後続フェーズの決定 | 含めたフェーズと理由・作成/修正したチケットの一覧 |

## 参照ナレッジ

- 観点・類型の文言の正: 機構の定義（`00-workflow-quick-request` の振り返りと同一文言）
- 作業ログの固定見出し: `00_requirement/skills/20-common-step-ticket.md`（正）
- レビュー指摘の全件取得: `10_spec/skills/20-common-step-issue.md`「GitLab の長文送信」の `--paginate` の注記
- 後続チケットの記載事項・DoD の型: 各フェーズの task スキルの要件

## Script 処理

なし。チケット・issue・HTML の操作は common-step の提供コマンド・手順に委譲する。

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン: メインエージェント専任 | 禁止事項・呼出条件 |
| メイン: 着手は提供コマンド | 処理フロー 1 |
| メイン: 記録からの洗い出し（入力の列挙） | 処理フロー 2 |
| メイン: 観点と類型・0 件の根拠 | 処理フロー 3・候補 0 件の扱い |
| メイン: 反映先 2 軸と常時読込コスト | 処理フロー 3 |
| メイン: 既定この MR・対話で合意・合意前に作らない | 処理フロー 4、禁止事項 |
| メイン: 後続フェーズ確定と次チケット 1 枚 | 処理フロー 6 |
| メイン: 別 issue は承認 → 起票 → 番号記録 | 処理フロー 5 |
| メイン: 未着手チケットの見直しと通知 | 処理フロー 7 |
| メイン: 作業ログは都度追記 | 処理フロー 9（ticket 仕様） |
| メイン: 完了の検査・完了後は呼び出し元へ | 処理フロー 9 |
| 代替: 候補 0 件 / 全部別 issue | 候補 0 件の扱い・処理フロー 5→6 |
| 代替: 再開・差し戻し | 再開の扱い（差し戻しは追加チケットで見直しを合意し直す） |
| 例外: ヘッドレス | 処理フロー 4 |
| 例外: 起票の不承認・失敗 | 処理フロー 5 |
| 例外: 後から見つかった候補は戻らない | 禁止事項 |
| 計画書の内容と置き場（md + HTML） | OUT ひな形、処理フロー 8 |
| チケットの扱い（やってよいこと・レビュー既定不要） | 禁止事項（宣言）・全体計画の方針 |
| 整合: 後続チケットの型・next に従う・分類の文言 | 処理フロー 6・参照ナレッジ |
