# 10-task-implementation-exec スキル

## 概要

実装・テストフェーズの実施タスクの要件を定義する。実装計画書のステップに従って実装チケットを順に実施し、テストを先に書いて失敗を確認してからコードを変更し、テストとビルドで確かめる。仕様どおりにできなかった点・仕様の誤り・追加で決めた点（仕様からの逸脱）は必ず作業ログに残し、設計反映フェーズの入力にする。タスクの最後に実装結果レポートをまとめる。

- **背景**: 実装は振る舞いを変える最もリスクの高いタスクであり、差分が計画から逸れても・テストが形だけでも、動くように見えてしまう。差分を計画と許可範囲に閉じ、テストをテスト ID で仕様に結び、逸脱を隠さず記録する形にしたい。
- **目的**: 計画のステップどおりにテスト → 実装 → 確認を回し、すべてのテスト ID が失敗ケースを含めて通り、差分が計画の変更対象に収まり、逸脱の一覧が揃った状態でレビューに出す。
- **スコープ**:
  - 含む: 実装チケットの実施（着手から完了まで）、テスト先行の実装、テスト・ビルドによる確認、仕様からの逸脱の記録、実装結果レポート（md + HTML）の作成、再開・差し戻しの扱い、呼び出し元への結果報告
  - 含まない: 変更対象・テスト方針の決定（`10-task-implementation-plan`）、設計書の修正（設計反映フェーズ）、コード品質基準の定義（プロジェクトの規約）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）、許可範囲を強制する仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 計画に収まった差分と、仕様に結びついたテストの結果、仕様からの逸脱の一覧をセットでレビューしたい。

**[So that]** 差分の妥当性を計画と照らして判断でき、実装と設計書のずれを見落とさずに後で書き戻せるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、実装計画書（変更対象・テスト方針・ステップ・検証方法）・実装チケット群・設計書を入力に進めなければならない。
- When 実装チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットのステップだけを実施しなければならない。
- When 実装するとき、Shall スキルは DoD のテスト ID に対応するテストを先に書き、失敗することを確認してからコードを変更し、テストが通ることと既存のテストが壊れていないことを確認しなければならない。テストにはテスト ID を名前またはコメントで残す。
- When コードを書くとき、Shall スキルはプロジェクトの規約（`CLAUDE.md` の基本原則・コード規約のルール）と設計書のインターフェースに従い、チケットの「やってよいこと」の範囲の外を変更してはならない。
- When 仕様どおりに実装できない・仕様が誤っている・仕様に無い判断をした、のいずれかが起きたとき、Shall スキルはその場で作業ログの「仕様からの逸脱」に内容と理由を書き、設計書を直してはならない（書き戻しは設計反映フェーズ）。
- When テストが失敗した原因が実装ではなくテストの側（テストコードの誤り・テストシナリオの誤り）にあったとき、Shall スキルはそのことと修正の内容・理由を作業ログの「仕様からの逸脱」に記録してからテストを直さなければならない（実装を通すために黙ってテストを書き換えない）。テストシナリオの誤りは設計反映の入力になる。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 実装チケットを完了するとき、Shall DoD（変更対象が仕様書のとおり実装されている / テスト ID のテストが失敗ケースを含めて通る / 既存テストが通る / 逸脱が作業ログにある）が実行結果を根拠に満たされ、差分がチケットの「やってよいこと」に収まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 1 枚の実装チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の実装チケットに着手しなければならない（タスクの切れ目ではない）。
- When すべての実装チケットが完了したとき、Shall スキルは実装結果レポートを仕上げ、結果報告（完了したチケットの一覧、テスト結果、逸脱の一覧、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「すべてのテスト ID がテストとして存在し失敗ケースを含めて通っているか」「差分が計画の変更対象に収まっているか。計画外の変更の理由」「仕様からの逸脱の一覧（設計反映で書き戻す対象。テスト側を直した場合はその理由を含む）」「コード品質」を挙げなければならない。

### 代替フロー

- If 再開時に実装チケットが作業中でコードが書きかけの場合、Then スキルは作業ログの「現在地」とテストの状態から続きを進め、同じ変更をやり直してはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは指摘をテストで再現できるものはテストから直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残し、レポートを追記・修正しなければならない。
- If 計画に無いファイルを変更する必要が分かった場合、Then スキルは理由を作業ログの「判断と根拠」に書いてから最小限で変更し、結果報告の「見てほしい点」に明示しなければならない。範囲が大きく変わるなら変更せず、実装計画の追加チケットを結果報告で提案する。

### 例外フロー

- If テストが通らず DoD を満たせない場合、Then スキルはチケットを完了にせず、原因と試したことを作業ログに書き、判断が要ることを結果報告で呼び出し元に返さなければならない（通ったことにしない）。
- If 設計書（`docs/` 配下）や `.claude/` 配下への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、設計書に書きたい内容は「仕様からの逸脱」に、AI アセットに書きたい内容は「AI アセットに反映すべき内容」に記録して先へ進まなければならない。
- If 許可範囲の外への差分が機構に指摘された場合、Then スキルはその差分を基準の状態に戻し、必要なら理由を付けて計画の見直しを提案しなければならない（黙って持ち込まない）。
- If 実装計画書が無い、または実装チケットが計画のステップと対応しない場合、Then スキルは実装を始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。

### 実装結果レポートの内容

- When すべての実装チケットが完了するとき、Shall 実装結果レポートが作業領域のレポートの置き場に 1 つあり、同じ名前の HTML ビューが併存しなければならない（Markdown が正文。テンプレートのコピーと Edit で作り、機械的検査の結果を作業ログに残す）。
- When 実装結果レポートを書くとき、Shall 機構のレポートの節順に沿って次を含めなければならない: 変更したファイルと内容の要約（計画との対応）、テスト結果（テスト ID ごとの結果と実行方法。失敗ケースを含む）、仕様からの逸脱の一覧（設計反映の入力）、想定と異なった点、残課題（テストで確かめられなかったこと・計画外の変更とその理由）。

### 実装チケットの扱い

- When 実装チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画の変更対象（コード・テスト）・レポートの置き場・チケットの置き場・`wip/tmp/` への書き込みと、ビルド・テスト系の操作に限り、設計文書・`.claude/` 配下を書けてはならない。
- When 実装計画書で並列に進めてよいとされたチケット群を並列で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。並列にしたチケットが同じファイルを変更しないよう、担当の範囲を分ける。
- When 実装チケットの人間レビュー要否を参照するとき、Shall チケットの記載に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 実装計画書・設計書を参照するとき、Shall スキルはそれらを書き換えてはならない。計画やインターフェースの見直しが必要だと分かったときは、作業ログとレポートに残して提案する。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルはコード差分と実装結果レポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

---

## 前提条件

- `10-task-implementation-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、実装チケットが未着手にあること
- 実装チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- ビルド・テストがローカルで実行できること（実行方法は実装計画書に書かれている）
- レポートのテンプレート（md + HTML）と、チケットの着手・完了の提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は作業ログとレポートに残し、人間レビューで確定する
- **ビジネス的制約**: 差分の妥当性とコード品質の判断は MR 上の人間レビューが行う。スキルはテストと逸脱の記録を揃えるまで
- **外部的制約**: 設計書は直さない（設計反映フェーズの仕事）。リモートへの操作（push・MR 更新）はタスクの切れ目で呼び出し元が行う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | テスト ID で仕様書のテストシナリオとテストコードが結ばれ、差分は計画の変更対象と、逸脱は設計反映のチケットと対応づく |
| 一貫性 | レポートの節順・視覚語彙・HTML の検査は他の実施タスクと同じ。作業ログと DoD の型は他の task スキルと同じ |
| 簡潔性 | レポートは計画との差分と逸脱に集中し、コードの説明を仕様書と重複して書かない |
| 冪等性 | 再開時に同じ変更・同じテストを二重に作らない |
