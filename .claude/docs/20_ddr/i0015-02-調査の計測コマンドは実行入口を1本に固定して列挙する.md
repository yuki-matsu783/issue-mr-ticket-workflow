# i0015-02. 調査の計測コマンドは実行入口を 1 本に固定して `commands.build-test` に列挙する

## 背景

issue #15 の調査フェーズで `python3` を使って `shlex` の挙動を確かめようとしたところ、フックが **WF204（分類外のコマンドは既定拒否）**で拒否した。

`scope.sh` の `scope_classify` は、読み取り系の語彙表にも `scope-limits.json` の `commands.build-test` にも無いコマンドを `unknown` として既定拒否に落とす。`commands.build-test` には npm の 6 コマンドしか列挙されていなかったため、チケットの `allow.ops` に `build-test` を宣言しても `python3` は分類外のままだった。

迂回せず作業を止め、許可範囲を広げる実装チケットを差し込むことをユーザーと合意した（2026-09-03）。

## 決定

- `commands.build-test` に 2 行だけ追加する。

  ```
  "python3 wip/tmp/probe.py"
  "bash wip/tmp/bench.sh"
  ```

- **実行入口をスクリプト 1 本ずつに固定し、何をするかは第 1 引数のモードで選ぶ**。調査ごとにスクリプトを増やして列挙を伸ばさない
- 計測スクリプトは `wip/tmp/` 配下に置く。同ディレクトリは追跡外で、リポジトリの成果物には残らない
- 既定拒否の仕組み自体は変えない。変えたのは列挙 2 行だけ

## 理由

- **`scope_classify` の突き合わせは半角空白区切りの前方一致**である。判定は「列挙した文字列と完全一致」または「列挙 + 半角空白で始まる」の 2 通りしかない。そのため `"python3 wip/tmp/"` のようなディレクトリ単位の指定は効かない（`python3 wip/tmp/x.py` は `python3 wip/tmp/` にも `python3 wip/tmp/ ` にも一致しない）。ディレクトリを開ける手段が無い以上、入口をファイル 1 本に固定するのが最小の広げ方になる
- **拒否側が拒否のまま**であることを確認した。列挙に一致しない形はすべて `unknown`（既定拒否）に落ちる。

  | 入力 | 分類 |
  |---|---|
  | `python3 wip/tmp/probe.py a2` | build-test |
  | `python3 wip/tmp/probe.py` | build-test |
  | `bash wip/tmp/bench.sh classify` | build-test |
  | `python3 wip/tmp/other.py` | unknown |
  | `python3 /etc/evil.py` | unknown |
  | `python3 wip/tmp/probe.pyx` | unknown |
  | `bash wip/tmp/evil.sh` | unknown |

- **`python3 -c` は列挙しても通らない**。`cmdpos.sh` が「コード文字列を渡すオプション」を伴う実行系を `opaque` と判定し、その判定が前方一致より先に立つ。通す設計にすべきでもないので、スクリプトファイル経由に限る

## 却下した案

- **`commands.build-test` に `python3` だけを列挙する**: 任意のパスの Python 実行が通ってしまう。既定拒否の設計が骨抜きになる
- **調査のたびに具体的なコマンドを列挙し、終わったら削る**: 列挙の出入りが頻繁になり、削り忘れが残る。入口を固定すれば列挙は 2 行のまま増えない
- **`scope_classify` の判定を glob 対応にする**: 判定の仕組みを変える話で、調査を進めるための前提整備の範囲を超える。必要になれば issue #30（計画タスクが `commands.build-test` を列挙できない）と合流させて別途扱う

## 残る弱点

`wip/tmp/probe.py` と `wip/tmp/bench.sh` は追跡外のファイルで、中身は自由に書き換えられる。入口を固定しても、そのファイルの中身が任意である以上、**実質は任意の Python / bash 実行に等しい**。

この弱点を承知のうえで受け入れている。理由は、`build-test` はもともと「テストとビルドを走らせる」ための分類で、`npm test` も同様に任意のコードを実行できるためである（`package.json` の `scripts.test` は自由に書ける）。列挙による制限は「うっかり別のものを走らせない」ための歯止めであって、悪意ある書き換えを防ぐ機構ではない。

## 影響

- `.claude/hooks/config/scope-limits.json` の `commands.build-test`（6 → 8 件）
- `10_spec/フック共通仕様.md` §8 は変更しない。判定の仕組みは変わらず、列挙が増えただけのため
- **issue #30 へ**: `commands.build-test` がディレクトリ単位・glob での指定をできないという制約。本 DDR は入口の固定で回避したが、計画タスクが列挙を組み立てる場面では同じ制約が別の形で効く
