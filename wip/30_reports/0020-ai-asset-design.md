# 0020 AI アセット設計結果 — 制御方式の穴と WF801 の到達

## サマリ

設計ワークの境界レビュー 1 巡目の指摘のうち、**制御方式の穴に関わる 7 件（S1・R4・R5・R13・R20・R21・R23）**を仕様に反映した。更新した文書は仕様 5 本・要件 2 本、新規の DDR は 7 件（`i0009-26`〜`32`）。

最大の争点は **S1**。`i0009-06` は「起動前に伝えられるから」を根拠に WF801 を PreToolUse `Agent` に移し、§1 の登録表を 17 行にした。ところが公式は `additionalContext` の入る位置を「PreToolUse … **next to the tool result**」と定めており、**メインエージェントが読むのはサブエージェントが走り終わった後**。採用した案 (c) は、却下した案 (a)（事後通知）と到達時点が同じだった。

結論は **17 行を維持**する。ただし根拠を差し替えた — トップレベルの **`systemMessage`**（公式「Warning message shown to the user」）を併用し、**ユーザーには起動前に**、**AI には結果と同時に**伝える 2 経路にする。`systemMessage` はサブエージェントが動き出す前に人間が気づける唯一の経路で、事後通知では代替できない。要件も「AI に起動前に伝えることは実行基盤の仕組み上できないため、これを求めない」と精密化した。

残る 6 件は制御方式の抜け。**MCP**（宣言だけ強制 / 種別は強制しない・draft 解除以外は許可）、**設定破損時の state-guard**（拒否に倒さず既定値で続ける）、**チケットの削除**（`rm` の元を見る）、**WF801 の再掲**（縮退時だけ）、**`subagent_type`**（`task-executor` に絞る）。

- ◎良 5 件 / △注意 1 件 / ✕問題 1 件

## レビューしてほしい観点

- **f1（✕問題）17 行を維持したこと**。根拠は「`systemMessage` によるユーザーへの起動前の警告は事後通知では代替できない」で、これが 1 行の登録に見合うかを見てほしい。**`permissionDecision: "ask"` で起動を止める案は却下した**が、誤警告のリスク（モデル名の正規化に依存する推定・ヘッドレスで `deny` に化ける）と、止められることの価値のどちらを取るかは判断が割れ得る

## 実施した内容と結果

### f1. WF801 は `systemMessage` + `additionalContext` の 2 経路。17 行は維持する ✕問題

`i0009-06` の根拠「**起動前に伝えれば、メインエージェントは止めて正しいモデルで起動し直せる**」が、公式の記述で否定された。

> `additionalContext` … Where the reminder appears depends on the event:
> * **PreToolUse**, PostToolUse, PostToolUseFailure, and PostToolBatch: **next to the tool result**

> Claude reads the reminder on **the next model request**

PreToolUse に登録しても、メインエージェントが読むのは **`Agent` ツールの結果の隣** = サブエージェントが走り終わった後。`i0009-06` が案 (a)（事後通知に一本化）に付けた欠点が、採用した案 (c) にもそのまま当てはまっていた。

- **決定**: **17 行を維持**し、WF801 を **2 経路**で出す
  - **`systemMessage`**（公式「Warning message shown to the user」）: **ユーザーに即時表示**。サブエージェントが動き出す前に人間が気づける**唯一の経路**で、中断して起動し直せる
  - **`additionalContext`**: メインエージェントへ。届くのは `Agent` の結果と同時（事後）
- 仕様に**限界 2**「メインエージェントに起動前に伝えることは Claude Code の仕様上できない」を明記した
- 要件を精密化: 「サブエージェントが動き出す前に**ユーザーへ**伝え、**AI へは遅くとも結果と同時に**伝える。AI に起動前に伝えることは実行基盤の仕組み上できないため、これを求めない」
- **`ask` は採らない**: 判定はモデル名の正規化に依存する推定で誤警告の余地があり、ヘッドレスでは `ask` が `deny` に化けて（§10）サブエージェントの起動不能になる。WF801 は要件が「起動を妨げてはならない」と定める通知である

**なぜ ✕ か**: 4 チケット（0012〜0015）が「起動前に伝えられる」という**誤った前提**の上に 17 行目を積んでいた。今回は代わりの根拠（`systemMessage`）が見つかったので結論は変わらなかったが、**`systemMessage` が実際にユーザーへ表示されることを実測していない**。表示されなければ 17 行目の根拠がもう一度崩れる。4c の実測項目にした。

結論: 結論（17 行）は維持したが、根拠は差し替わった。要件も「実現できないこと」を求めない形に直した。DDR `i0009-26`。

### f2. MCP は宣言の有無だけを強制し、種別は強制しない △注意

`mcp__.*` を matcher に持つのは `workflow-state-guard` の 1 行だけで、`workflow-entry`（未宣言の拒否）と `workflow-guard`（宣言範囲の強制）は MCP を含まない。`gh` / `glab` が使えない環境で MCP に切り替えた瞬間（外部委任モードは実際にこれを想定している）、`mcp__github__create_issue` などが **WF101 も WF206 も通らずに素通り**する。

- **決定（強制する側）**: **`workflow-entry` の matcher に `mcp__.*` を足す**。宣言の有無の判定には**ツールの種類が要らない**（セッション状態を見るだけ）ので、分類できなくても安く確実に効く。`WE-T11` を新設
- **決定（強制しない側）**: **`workflow-guard` には足さない**。MCP のツール名は**サーバが定義する**もので `remote-write:<種別>` に機械的に対応づけられない。パターンを書けば書くほど、当たらない名前に対して「守っている」という誤った安心が生まれる（`redact` と同じ構造の問題）
- 誤分類の害も大きい。外部委任モードは `gh` 不在時の唯一のフォールバックで、ここで正当な操作を止めるとワークフローが進まない。`00-workflow-issue-mr-driven` の手順は `--external` フラグで人間の目を通す形になっており、そちらが統制を担う
- §13「意図的な緩和」に理由付きで書き、要件（`workflow-guard`）にも「外部の連携ツールを経由するリモート書き込みは種別を強制しない。この統制は計画タスクの自制に依存する」を足した

**△ の理由**: 要件が求める統制の一部を**明示的に諦めた**。「強制するもの / 自制に依存するもの」の枠組みには載せたが、諦めた範囲が妥当かは判断が要る。

結論: 素通りしていた穴のうち、分類が要らない側（宣言）だけを塞いだ。DDR `i0009-27`。

### f3. `workflow-state-guard` は MCP の draft 解除だけを見て、他は許可する ◎良

state-guard の制御方式は「書き込みツール（対象パス）」「実行ツール（コマンド列）」「入力不正 → deny WF309」の 3 分岐しか無く、**MCP ツールを受け止める分岐が無かった**。`mcp__github__get_issue` は `file_path` も `command` も持たないので入力不正に落ち、許可カーブアウトの条件（「対象パスが読める」）も満たせず、**すべての MCP 呼び出しが WF309 で拒否**される。

- **決定**: 制御方式に MCP の分岐を新設（入力不正の 1 つ前）。`mcp__*pull_request*` / `*merge_request*` の `draft:false` → **WF304**、**それ以外の MCP は許可**
- 理由は「このフックが守るのは進行状態ファイル・置き場・draft 解除の 3 つで、MCP ツールがそのうち触り得るのは draft 解除だけ」。拒否側に倒す原則は「**保護対象に関わり得るのに**判断できない」場合のもので、関わり得る範囲が静的に分かるなら適用対象ではない
- `SG-T09` に**負のコントロール**（draft 解除以外の MCP が通ること）を置いた

結論: 要件を超える過剰拒否が解消し、外部委任モードが機能する。DDR `i0009-28`。

### f4. 設定が読めなくても state-guard は既定値で判定を続ける ◎良

`workflow-guard` は `scope-limits.json` が壊れたとき **WF210** とし、復旧経路（提供コマンド・`wip/10_tickets/**`・**`scope-limits.json` 自身への ask 付きの書き込み**）を用意している。ところが state-guard は同じ状況で拒否側の原則どおり **WF309** に倒れる。

**フックは並列に走る**（`i0009-21`）ので deny はどれか 1 つでも出れば成立する。つまり **state-guard の deny が workflow-guard の復旧経路を潰し**、設定 1 ファイルの破損が完全なロックアウトになる。

- **決定**: state-guard は**拒否に倒さず**、`common.state_files` の**既定値**（`logs/mr.json` / `review-state.json` / `review-history.jsonl` / `merge-state.json`）にフォールバックして判定を続ける。フォールバックした旨は `notify` で記録する
- 保護対象 3 つのうち置き場と draft 解除は設定に依存しないので、そのまま働く
- 禁止事項「保護対象の一覧をコードに埋めること」に但し書きを足した（禁止の趣旨は「設定を無視する」ことで、**設定が読めないときのフォールバックは別**）
- `SG-T10` に「設定が壊れていても `scope-limits.json` 自身への Write がこのフックを通る」を置いた

**気づきの一般化**: **復旧経路は 1 本でも塞がれば意味が無い**。並列実行なので、復旧経路を用意する側と塞ぐ側が別のフックでも結果は同じ。復旧経路の設計は**全フックの合意**で成立する。

結論: ロックアウトの経路がもう 1 つ塞がった（0019 の f3 に続いて 2 つ目）。DDR `i0009-29`。

### f5. 作業中・完了チケットの削除を塞ぐ ◎良

state-guard の実行ツールの判定は「`mv` / `cp` / `git mv` / `touch` / リダイレクトの**宛先**」だけで、**`rm` が一覧に無い**。作業中チケットが 0 枚の切れ目では `workflow-guard` も判定しない（判定順 1）ので、`rm wip/10_tickets/20_done/*.md` が**誰にも止められない**。

完了チケットは `workflow-entry` の継続条件・`workflow-diff-check` の先行判定（WF602）・`ticket.sh next` の `predecessors` の解決の材料なので、消えるとこれらが**静かに違う答えを返す**。

- **決定**: 制御方式 3 に**元（消える側）の判定**を足す。`rm` / `git rm` / `mv` / `git mv` の元が `10_doing/**` → **WF302**、`20_done/**` → **WF303**
- §13 の「継続条件の窓」の緩和は「切れ目の処理に必要な書き込みを妨げない」ためのもので、そこで機構が守ると明言しているのは進行状態・コミット / push・`chmod`。チケットの置き場は state-guard 自身が「進行状態」と定義しているので、緩和の対象ではない
- `SG-T02` に `rm` のケース（`wip/tmp/` の `rm` は通る負のコントロール付き）を足した

結論: 切れ目に空いていた穴が塞がった。state-guard は作業中チケットの有無を問わず働くので、追加の登録も要らない。DDR `i0009-30`。

### f6. WF801 の再掲は縮退のときだけにする ◎良

`subagent-stop-check` の概要は「WF801 の再掲は**事後の保険**であり、**PreToolUse の経路が使えない縮退のときだけ**唯一の通知経路になる」と書いていたが、**制御方式にもテストにも条件が無く**、`SP-T05` は「記録があれば再掲される」と**無条件**を固定していた。通常経路では同じ不一致が 2 回通知され、しかも 2 回目は回復手順（「止めて起動し直す」）が既に無意味。

- **決定**: 同じ `agent_id` について `decisions.jsonl` に `subagent-start-check` の WF801 の `notify` 記録が**無い**とき（= 縮退）だけ再掲する
- 概要の「事後の保険」を「**縮退時の唯一の通知経路**であり、通常経路では出さない」に改め、`SP-T05` を条件付きに書き直した
- `i0009-26` で PreToolUse の `additionalContext` も結果と同時に届くことが確定したので、無条件の再掲は**ほぼ同時に 2 つ**入ることになり、いっそう紛らわしい

結論: 説明と実装（テスト）の食い違いが解消した。DDR `i0009-31`。

### f7. WF801 は `task-executor` 以外には出さない ◎良

`subagent-start-check` は `tool_input.subagent_type` を読む（`HOOK_SUBAGENT_TYPE` に入れる）と入出力に書きながら、**制御方式で使っていなかった**。敵対的レビュー（`adversarial-reviewer`）や探索（`Explore`）を別のモデルで起動すると、チケットの `executor` と一致しないので **WF801 が誤発報**する。

- **決定**: 制御方式 4 の条件に `subagent_type` が **`task-executor`**（タスク実施者）であることを加える
- 理由: チケットの `executor` は**タスクの実施者**に対する指定で、レビュアーには当てはまらない（むしろ敵対的レビューは実施者と別のモデルで回す方が価値がある）。禁止事項は既に「誤警告を出さない」を掲げている
- **要点の注入（WF802）は絞らない**。レビュアーにも「レビュー対象の範囲を知る材料」として有用（呼出条件に既にその旨がある）
- `SA-T07` に負のケース（`adversarial-reviewer` / `Explore` では通知しない）と正のコントロール（`task-executor` では出る）を置いた

結論: この issue 自身が opus のレビュアーを明示的に起動しているので、運用が変われば当たる穴だった。DDR `i0009-32`。

## 残課題

- **`systemMessage` の実測**（4c）。表示されなければ f1 の結論が崩れ、17 行を 16 行に戻す判断が要る
- MCP のリモート書き込みの種別を強制しないことで、外部委任モードでは**宣言と実際の操作がずれても機構は止めない**。`--external` フラグの手順（人間の目）が唯一の統制
- `scope-limits.json` を壊した状態で 2 つのフックを同時に走らせ、復旧経路が通ることを確かめていない（`SG-T10` は state-guard 単体）
- `cmdpos.sh` が `rm` の対象を取り出せるかは 0021 と実装フェーズ
- **同じ形の穴が他にもある可能性**: 今回見つけた 3 つ（MCP が分岐に落ちない・設定破損で復旧経路が潰れる・削除が宛先判定に掛からない）は、いずれも「**判定の入口の形が想定と違う入力**」だった。他のフックにも同種の入力があり得る。`workflow-guard` は `EnterPlanMode`（制御方式 7）と `Agent` / `Workflow`（制御方式 8「起動 → 許可」）を明示的に扱っているので**この 2 つは穴ではない**ことを確認したが、同じ観点で `workflow-diff-check` と `subagent-stop-check`（どちらも案内側なので害は小さい）は未点検
