# 20-common-step-ticket スキル

## 概要

チケット操作の common-step スキルの要件を定義する。チケットの作成・着手・完了・取り消しの標準手順と、チケットのテンプレート・状態遷移のスクリプトをこのスキルが持つ。すべての task スキルはチケット操作をこのスキルの手順で行い、各 task スキルの要件書はチケットの中身（種類ごとの DoD の型・やってよいことの方針）だけを定める。

- **背景**: チケットの状態（未着手 / 作業中 / 完了）は宣言範囲の強制・タスクの切れ目の判定・振り分けの継続判定の入力であり、手作業で動かすと機構の判定と実態がずれる。また記載事項・作業ログの検査を人（AI）の注意力に頼ると漏れる。操作を 1 か所のテンプレートとスクリプトに集め、検査を機械に持たせたい。
- **目的**: どの task スキルから使っても同じ形のチケットが作られ、状態遷移が必ずスクリプトを通り、完了時に DoD と作業ログの必須項目が機械的に検査される状態を作る。
- **スコープ**:
  - 含む: チケットの作成（テンプレート・記載事項・連番）、着手（同時 1 枚の保証・開始時刻の記録）、完了（DoD・作業ログの検査・完了時刻の記録）、取り消し、次のチケットの提示、スキルが持つテンプレートとスクリプト
  - 含まない: チケットの中身の決め方（各 task スキル）、宣言範囲の強制・タスク境界の判定の仕組み（フックの要件・仕様）、作業領域の片付け（`10-task-overall-summary` と提供コマンド）

---

## ユーザーストーリー

**[As a]** チケット駆動で AI に作業させる開発者として、

**[I want]** チケットの形と状態遷移がどのタスクでも同じで、完了の条件が機械的に検査されてほしい。

**[So that]** チケットを見れば状態と根拠が分かり、「完了したことにする」逸脱が仕組みで防がれるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When チケットを作るとき、Shall スキルはこのスキルが持つテンプレートをコピーして記載事項（タスクの種類、状態、先行チケット、実行者、人間レビューの要否と理由、やってよいこと、目的、DoD、作業ログの固定見出し）を埋め、実施順に単調増加する連番を付けて未着手の置き場に置かなければならない。雛形の痕跡を残さない。
- When チケットに着手するとき、Shall スキルは提供スクリプトで未着手 → 作業中に進めなければならない。スクリプトは作業中のチケットが既にあれば着手を拒否し、開始時刻を機械的に記録する。
- When チケットを完了するとき、Shall スキルは提供スクリプトで作業中 → 完了に進めなければならない。スクリプトは DoD のチェックが全て埋まっていること・作業ログの必須項目（未完了時の現在地の消込・AI アセットに反映すべき内容）があることを検査し、欠けていれば理由を伝えて完了を拒否し、通れば完了時刻を機械的に記録する。
- When 次に着手するチケットを知りたいとき、Shall スキルは提供スクリプトが示す「次のチケット」と「対応するタスクの種類」に従い、目視で選んではならない。
- When チケットを取り消すとき（全体計画が「対応なし」で終わった場合など）、Shall スキルは提供スクリプトで取り消し、理由を記録しなければならない（完了と区別する）。

### 代替フロー

- If 作業中のチケットがある状態でセッションが再開された場合、Then スキルはそのチケットの作業ログの「現在地」を読み、続きから進めなければならない（状態を動かし直さない）。
- If 完了済みのチケットに誤りが見つかった場合、Then スキルはそれを作業中に戻さず、同じ種類の追加チケットを作って対応しなければならない。
- If 全体まとめチケットを完了する場合、Then 完了は作業領域の片付けの提供コマンドが検査（DoD・作業ログ）と完了時刻の記録とともに行い、完了のスクリプトを単独で実行してはならない（完了済みチケットを含めて作業領域が空になる。手順は `10-task-overall-summary.md` が正）。

### 例外フロー

- If チケットのファイルを手で移動・改名して状態を変えようとした場合、Then 機構はそれを拒否し、スキルは提供スクリプトでやり直さなければならない。
- If 完了の検査で拒否された場合、Then スキルは伝えられた未充足（DoD の未チェック・作業ログの欠け）を解消して再実行しなければならない。検査を通すための形だけの記入をしない。
- If 提供スクリプトが壊れていて操作できない場合、Then スキルは手作業で代替せず、エラー内容を報告して停止しなければならない。
- If テンプレートに無い記載事項を追加したくなった場合、Then スキルは独自の項目を足さず、必要性を作業ログの「AI アセットに反映すべき内容」に書いて改善候補にしなければならない。

### テンプレートとスクリプト

- When このスキルを導入するとき、Shall チケットのテンプレート（記載事項・目的・DoD・作業内容・作業ログの固定見出し・備考）と、作成・着手・完了・取り消し・次のチケットの提示を行うスクリプトがこのスキルの配下に置かれ、task スキルはそれらを重複して持ってはならない。
- When 作業ログの固定見出しを定めるとき、Shall テンプレートは次の項目を持たなければならない（この一覧はこの要件書が正）: **現在地**（未完了のチケットで必須。どこまで終わり、次に何をするか）、うまくいったこと、うまくいかなかったこと（想定と異なった点を含む）、仕様からの逸脱、**判断と根拠**（決めたこと・選ばなかった案・理由）、**拒否・確認・迂回の記録**（機構に拒否された操作と対処、ユーザーに確認した内容と回答、手順どおりに進まず回り道した箇所）、**使った AI アセットと効き目**（読んだスキル・ルールと「足りた / 足りなかった / 邪魔だった / 辿り着けなかった」）、**スコープ外で見つけたこと**（直さなかった不具合・負債・別 issue 候補）、**AI アセットに反映すべき内容**（必須。0 件なら 0 件である根拠）、**備考**（自由記述）。必須以外は該当があるときだけ書いて空欄でよく、定型文で埋めない。
- When テンプレートやスクリプトを変更するとき、Shall not このスキルの利用中に行わず、AI アセットのフェーズ（設計 → 実装・テスト）で行わなければならない。

### 他のスキル・機構との整合

- When task スキルがチケット運用を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。
- When チケットの記載事項の意味（実行者・レビュー要否・やってよいことの上限）を定めるとき、Shall 機構の定義（type ごとの上限・タスク別の既定判断基準）に従い、このスキルは書き方と検査だけを担わなければならない。

## 前提条件

- 作業領域（チケットの置き場）が用意され、振り分けスキル（`00-workflow-issue-mr-driven`）の下で使われること
- スクリプトの実行環境（bash）が使えること

---

## 制約条件

- **技術的制約**: 状態遷移はスクリプト経由のみ。AI の自己申告・手作業のファイル移動では状態が進まない
- **ビジネス的制約**: 完了の実質的な判断（DoD の中身が正しいか）は人間レビューが担い、スクリプトは形式の検査と記録に徹する
- **外部的制約**: 検査の項目・拒否の理由の返し方はフックと仕様書が正。このスキルは使い方を標準化する

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | どの task スキルから使っても同じテンプレート・同じ検査・同じ記録形式になる |
| 追跡性 | 着手・完了の時刻と実行者の宣言がチケットに残り、後から所要と担当を集計できる |
| 冪等性 | 同じ操作を二度実行しても状態と記録が壊れない |
| 可読性 | チケットは 1 画面程度で読め、テンプレートの項目以外を増やさない |
