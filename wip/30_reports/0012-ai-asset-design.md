## 実施した内容と結果

### f1. `git 'commit'` は bash 経路でも WF403 で拒否する ◎良

根拠: 共通仕様 §7-9、issue #9 の申し送り D2、0007 f9

- `block-direct-git` の制御方式 3 に「実行体が `git` 系（`CP_GITLIKE` を含む）で第 1 サブコマンドが特定できない（`CP_SUBCMD[i]` が `_`）→ **deny WF403**」を追加した。bash 経路も PowerShell 経路も同じ扱い
- WF403 の条件を「opaque / **第 1 サブコマンドが特定できない `git`** / 縮退での拒否」に広げ、メッセージに「サブコマンドをクォートで割らずに書く」という対処を足した
- 要件に受け入れ基準を 1 つ足した（「`git` がコマンドとして実行される位置にあるが第 1 サブコマンドを特定できないとき、Bash / PowerShell のどちらの経路でも拒否側に倒す」）
- テスト観点 BG-T01 に `git 'commit'` と `git "push"` を足し、**期待する識別子が WF403**（他は WF401 / WF402）であることを明記した。種別は機械テスト
- 経緯: DDR `i0009-01`

結論: §7-9 と D2 の意図どおりになった。現状でも作業中チケットがあれば `workflow-guard` の WF204 で止まるが、この変更で「チケットが 0 枚の窓」でも止まり、メッセージが提供コマンドへの導線になる。

### f2. `workflow-state-guard` の呼出条件に `mcp__.*` を明記した ◎良

根拠: フック共通仕様 §1 の登録表、0005 f6

- 呼出条件を「PreToolUse、matcher: 書き込み / 実行 / **`mcp__.*`**（共通仕様 §1 の登録表の 3 行）」に直し、`mcp__.*` が要る理由（MCP 経由の draft 解除 `draft:false` と置き場宛の書き込みを捕まえる）を添えた
- 判定順は変えていない

結論: §1 の登録表 16 行と各仕様の呼出条件の唯一の食い違い（0005 f6）が解消した。

### f3. 作業中チケット 2 枚以上の検知は `workflow-guard` に集約する ◎良

根拠: issue #9 G8、`run-tests.sh:86`・`push.sh:98`・`ticket.sh:208`・`:334` の現物

- `workflow-guard` の制御方式 2（WF207）に、提供コマンド側の非対称の実態を注記として書いた: **1 枚目しか見ない** = `run-tests.sh:86` / `push.sh:98` / `ticket.sh next`（`:334`）、**件数で見る** = `ticket.sh start`（`:208`）、**非対称ではない** = 完了検査（番号引数）
- 「2 枚以上を機構の異常として止めるのはこのフックの役割であり、提供コマンドの側は 1 枚である前提で動く」と明記した
- WF207 は `ask` にせず `deny`（ヘッドレス実行でも同じ結果。共通仕様 §10）
- 要件に 2 つ足した: 「これは確認ではなく拒否とし、ヘッドレス実行でも同じ結果にならなければならない」「提供コマンドはその状態を検知する責任を負わない」
- **提供コマンドの実体は変更していない**（この issue の実装フェーズの許可範囲外でもある）
- 経緯: DDR `i0009-02`

結論: G8 は「フックが止める・提供コマンドは 1 枚前提」で閉じた。3/3 への申し送りは発生しない。

### f4. `boundary.sh` に依存する WE-T10 は 3/3 に送る △注意

根拠: 0005 f5、`workflow-entry` 仕様のテスト観点、issue #9 のスコープ外の記述

- WE-T10 の行に「**`boundary.sh` は 3/3 で実装するため、この観点は 3/3 に送る**」と理由付きで書いた。理由は 2 つ: (a) 両方が無出力になる空同士の比較では意味が無い、(b) 偽実装で代えると「本物と一致するか」という観点そのものが失われる
- あわせて **issue #9 の受け入れ条件 1 の「テストが通る」は、この issue で実装するフックのテストを指す**と解釈することを明記した
- 経緯: DDR `i0009-04`

結論: 同じ理由が `session-start` の 7 本（SS-H01〜04・06〜08）にも当てはまる見込みだが、**適用は 0013 が決める**。0013 が別の判断（最小スタブなど）を採るなら、WE-T10 の扱いも合わせ直す必要がある。

### f5. 横断文書と用語辞書は更新不要だった ◎良

根拠: `00_requirement/自己改善ワークフロー機構.md`・`00_requirement/rules/ルール体系.md`・`90_glossary/ワークフロー用語.md` の確認

- `自己改善ワークフロー機構.md`: このチケットの決定はフック 1 本ずつの判定の話で、機構全体の方針（`web` の強制・`ops` 上限・CI）に触れない。0014・0015 が更新する
- `ルール体系.md`: ルールの追加・削除・変更が無い
- `90_glossary/ワークフロー用語.md`: 収録されているのはワークフローの概念（振り分け・タスク・チケット・実行者 ほか 20 語）で、エラー識別子（WF403 / WF207）や実装の用語は入っていない。今回追加すべき概念は無い（「fail-open」「defer」は 0014 の担当）
- 実測への依存: 無し

結論: 更新不要。0014・0015 が横断文書を触るときに、この 3 件が「対象なし」だったことを前提にしてよい。
