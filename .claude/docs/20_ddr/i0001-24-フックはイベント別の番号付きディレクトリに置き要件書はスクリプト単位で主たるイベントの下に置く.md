# i0001-24. フックはイベント別の番号付きディレクトリに置き、要件書はスクリプト単位で主たるイベントの下に置く

## 背景

フックの要件書 11 本を書いた時点で、置き場は `.claude/docs/00_requirements/hooks/` 直下、実装予定の `.claude/hooks/` はフラットだった。どのフックがどのイベントで動くのかが一覧から読めず、また敵対的レビューで「ディレクトリの番号体系がどこにも定義されていない」「複数イベントで働くフック（workflow-entry 等）と 1:1:1（要件書 : 仕様書 : アセット）の数え方が曖昧」と指摘された。

## 決定

- `.claude/hooks/` と `.claude/docs/00_requirements/hooks/`（仕様書 `10_spec/hooks/` も同様）は、Claude Code のフックイベント別のディレクトリ `<NN-イベント名>` で構成する
- 番号は**十の位 = スコープ**（0x = セッション、1x = ターン・実行単位、2x = ツール）、**下一桁 = 公式ドキュメント（https://code.claude.com/docs/ja/hooks ）の掲載順**とする。現行の 9 つ: `00-SessionStart` / `01-PreCompact` / `10-UserPromptSubmit` / `11-Stop` / `12-SubagentStart` / `13-SubagentStop` / `20-PreToolUse` / `21-PermissionRequest` / `22-PostToolUse`
- イベントは全種（公式に 33 種）を作らず、フックを置く・置く予定のものだけをディレクトリにする。増えたら同じ規則で追加する
- **アセットの単位はスクリプト 1 本**とし、要件書・仕様書はスクリプトと 1:1 で対応させる。複数イベントで働くスクリプト（`workflow-entry` の宣言記録と拒否、`post-push-usage-report` の蓄積と報告など）は、その正体を表す**主たるイベント**のディレクトリに置き、どのイベントに登録するかは仕様（`settings.json` への登録）が定める

## 理由

- 一覧（`ls`）からフックの発火タイミングと構成が読める。スコープの十の位により、セッション系 → ターン系 → ツール系の順に並ぶ
- スクリプト単位の 1:1:1 を保てば、イベント横断のフックでも要件書が 1 つの振る舞いとして読める。イベントごとに文書を割ると 1 つの仕組み（宣言の記録と拒否）が分断される

## 却下した案

- **公式の全イベント分のディレクトリを作る**: 将来の枠は揃うが、空ディレクトリだらけになり構成が読みにくい
- **イベントごとに要件書を分割する**: 配置は単純だが、1 スクリプトの振る舞いが複数文書に分かれ、1:1:1 が崩れる
- **ディレクトリを切らずフラットに置く**: 従来どおりだが、発火タイミングが名前から読めない

## 影響

- 既存のフック要件書 11 本の配置と `.claude/hooks/` の骨組み（実施済み）
- 仕様書フェーズの `10_spec/hooks/` は同じ体系で作る
- 複数イベントへの登録の対応表は仕様書が持つ
