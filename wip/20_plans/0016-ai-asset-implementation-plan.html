この計画で何をするか

設計フェーズ（0012〜0015・0017）が .claude/docs/ の正史に落とした仕様を、.claude/ 配下のアセットと機械テストとして実装する順序・範囲・検証手段を決める。効くのは受け入れ条件 A1（worktree 上で機構が健全に動くこと）・A3（並行作業の手段への 1 ホップ）・A5（宣言範囲・差分の基準点・実行者照合が作業ツリーごとに一意であることを機械テストで確認）・A6（合流手順の実体 = worktree.sh merge）である。

決めたこと

  • 発効に依存しない部分（S1〜S9）と、発効の可否を判定する実効性の確認（S10）を分ける。 設計は「並列実施は採用するが発効は保留」（DDR i0050-08）で終わっているので、保留のままでも価値が出る部分を先に確実に作る
  • テスト ID は機械的に抜き出して割り付ける。 仕様全体 368 件 / 本 issue で新設 41 件 / 変更行に現れる既存 9 件 = 割付表 50 行（機械 37・eval 13）
  • 固定順は 設定・定義 → 中核 → 中核の機械テスト → スキル・ルール・エージェント → 参照更新。 中核の機械テストは中核の変更と同じチケットに置き、離さない
  • A1-6 を閉じる機械テスト（WG-T19 / WG-T20 / DC-T08 / DC-T09 / SA-T10 / SP-T09）は、負のコントロールの前提をテスト自身が作る形を崩さない。 調査の実測が空振りした原因は「どの作業ツリーにも作業中チケットが 0 枚で、両フックが入口で exit 0 した」ことだった
  • 実装と仕様が食い違ったら、実装計画でも実装でも仕様を直さず「逸脱」として記録する。 反映はフィードバック計画 → 設計反映フェーズが行う
  • 0027（発効の判定）だけ実行者をメインエージェントに外す。 解禁の条件 1 の確認にサブエージェントの起動が要り、サブエージェントは入れ子にできない

方法とステップ

  1. 1

    S1 設定・定義（0018）

    scope-limits.json の ai-asset-implementation.allow に .gitignore を足し、続けて .gitignore に .claude/worktrees/ を足す。この順を守る（前者が済むまで後者は WF205 で止まる）。実装結果レポート（md + HTML）もここで起こす。中核相当なので jq -e . で構文を確かめる。

  2. 2

    S2 中核 a: hook-common.sh（0019）

    HOOK_SHARED_ROOT（値は HOOK_ROOT に固定・上書きの口を作らない）／hook_worktrees（.git/worktrees/*/gitdir から集合を作り git を呼ばない）／hook_rel_path の 4 段化と「判定できない」戻り値／decisions.jsonl の cwd・agent_id。値の往復（書く側 hook_rel_path と読む側 3 本の WF209 / WF309 / WF605）を同じチケットに置く。

  3. 3

    S3 中核 b: cmdpos.sh と scope.sh（0020）

    算術展開は段を割らない／コマンド置換・プロセス置換の閉じ括弧の後ろの語を実行体にしない／git の限定適用 6 件（worktree list の read 化だけが通す向き、他 5 件は閉じる向き）／cd は分類に足さない（負のコントロールで固定）／R52 の軽微 2 件。全フックが読むので、フック本体より先に固める。

  4. 4

    S4 中核 c: 拒否側フック 2 本と A1-6 の機械テスト（0021）

    宣言範囲の強制が「その作業ツリーの作業中チケット 1 枚」で一意に決まること・WF207 が「1 作業ツリーあたり 2 枚」を指すこと・提供コマンドの置き場を指す引数の例外・作業ツリーをまたぐ絶対パスの保護（無条件）。WG-T19 / WG-T20 / WG-T21 / WG-T14 / SG-T12 / SG-T13 を同じチケットで通す。

  5. 5

    S5 中核 d: 案内側フック 4 本・post-push-* と A5 の機械テスト（0022）

    差分の基準点の一意性（DC-T08 / DC-T09）・対象チケットを採る作業ツリー（SA-T10 / SA-T11）・実行者照合を呼び出し元の作業ツリーで行う（SP-T09）・現在地を断定しない（SE-T11）・logs/push-state.json と logs/usage/ を共有ルートへ。

  6. 6

    S6 提供コマンド a: worktree.sh の新設（0023）

    20-common-step-worktree/SKILL.md・scripts/worktree.sh・scripts/tests/test_worktree.sh（WT-T01〜WT-T12）・eval 定義 WT-E01〜WT-E03。「本流かどうかの判定」はこのスキルの仕様が正で、S7 の 3 コマンドはこれを作り直さず共有する。

  7. 7

  8. 8

    S8 スキル・ルール・エージェントと eval 定義（0025）

  9. 9

    S9 参照更新と全体検査（0026）

    参照更新一覧の 7 行を検索して消し込む／プレースホルダ 0 件／frontmatter の必須項目／run-tests.sh --ids の全件実行で FAIL 0・ID 重複 0／本 issue の残りが回せることの確認（commit.sh・push.sh・boundary.sh・ticket.sh・run-tests.sh の 5 経路）。

  10. 10

リスクと復旧

ロックアウト対策（中核ステップごと）

対策として数えるのは、変更した判定を実際に踏むものだけである。テスト ID と判定の対応が付かないものは対策にならない。強制無効化（WORKFLOW_ENTRY_ENFORCE=0 / WORKFLOW_ENFORCE=0）は既定の手段にしない。<base_sha> は ticket.sh start が機械的に記録した各チケットの基準点。

ステップ確かめる操作（踏む判定）復旧手順
S1HK-T02 が scope-limits.json を実際に読んで scope_classify を走らせる／.gitignore 変更後に wip/ へ Write を 1 回（判定順 (2) を踏む）git checkout <base_sha> -- .claude/hooks/config/scope-limits.json .gitignore。scope-limits.json が壊れると WF210 で全書き込みが止まるので、編集は 1 回にまとめ、直後に jq -e . で構文を確かめる
