# 10-task-feedback-plan — 記録から改善候補を洗い出して後続を確定する

サブエージェントに委譲しない（対応先の決定に対話が要るのでメインエージェント専任）。記憶に頼って洗い出さない（入力は記録だけ。全チケットの作業ログの固定見出しを機械的になぞる）。対応先が確定する前に後続チケットを作らない。承認を得ずに別 issue を起票しない（ヘッドレスでは起票そのものを行わない）。独自の分類を作らない（観点・類型は機構の定義と一致させる）。改善を自分で実施しない（`.claude/` 配下・ソースコード・設計文書への書き込みは後続フェーズの担当）。振り返りをやり直さない。

## 目的

主作業で積み上がった記録を 1 回だけ棚卸しし、「次に何をするか」を確定させる。後続フェーズが 1 つも起票されないまま issue が宙に浮くのを防ぐ。

- 要件: `.claude/docs/00_requirement/skills/10-task-feedback-plan.md`
- 仕様（正。処理フロー 1〜9・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-feedback-plan.md`

## 手順

1. **着手**: `bash .claude/skills/20-common-step-ticket/scripts/ticket.sh start <番号>`
2. **洗い出し**: 完了・取り消し済みの全チケットの作業ログを、固定見出しの順に**チケット番号順で機械的になぞる**（全項目が対象）。MR のレビュー指摘（`gh api --paginate` / `glab api --paginate` で全件取得）と、各レポートの「想定と異なった点」「残課題」を加えて候補を列挙する。確認した記録の範囲（チケット番号・レポート名）を計画書に書く
3. **分類**: 候補ごとに**観点**（足りなかった / 邪魔だった / 無かった / 問題なし）と**類型**（(a) アセットが無かった / (b) あったが誤っていた / (c) あったが罠が書かれていなかった / (d) あったのに辿り着けなかった）を付ける。反映先は「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）× 守らせ方（読ませる / 手順化する / 機械的に拒否する）」の 2 軸で選ぶ。常時読込を増やす提案にはコストの注記を付ける
4. **合意**: 候補の一覧・分類・提案（既定は「この MR で対応」。大きすぎるものだけ「別 issue」）を提示し、候補ごとの対応先（この MR / 別 issue / 対応しない + 理由）を対話で合意する
   - **ヘッドレス実行では止まらない**。既定の提案どおりに対応先を決めて後続の起票（手順 6）まで進め、決めた内容を `boundary.sh note` で MR に記録する（チケットは完了させる）。人間は MR のコメントを読んで後から差し戻せる
   - ただし**別 issue の起票（手順 5）だけはヘッドレスでも行わない**。取り消せない外部への副作用だからである。「別 issue」と判断した候補は起票せず、内容と理由を計画書と `note` に残す
5. **別 issue の起票**: 合意された候補は本文案の承認を得て `20-common-step-issue` で起票し、番号を計画書に記録する。承認されなかった候補は「この MR に戻す / 対応しない（理由）」を確認する
6. **後続の確定**: 後続フェーズ（設計反映 / AI アセット設計 / AI アセット実装・テスト）の要否を確定し、含める最初の計画チケット（無ければ全体まとめチケット）を `ticket.sh create` で 1 枚だけ未着手に作る。記載事項は全体計画の方針と `.claude/rules/work-defaults.md` に従う
7. **未着手チケットの見直し**: 振り返りの結果に応じて未着手チケットの範囲・実行者・レビュー要否・DoD を見直し、変更をユーザーに伝える
8. **計画書**: `wip/20_plans/` にテンプレートから md を書き、`20-common-step-report-view` の手順で HTML を作って `check-html.sh` に通す
9. **完了**: 作業ログを整えて `ticket.sh complete <番号>` で完了し、呼び出し元に制御を戻す

- **候補 0 件**: 0 件の根拠（確認した記録の範囲）を計画書に書き、6 へ進む
- **再開**: 作業ログ「現在地」から続け、済んだ合意をやり直さない。起票済みの issue を二重に作らない
- **差し戻し**: 同じ種類の追加チケットとして戻ったときは、候補の一覧と後続チケットを見直し、変更を対話で合意し直す（完了済みチケットは戻さない）

## OUT ひな形

`assets/feedback-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR |
| 確認した記録の範囲 | チケット番号の一覧・レポート名・レビュー指摘の取得範囲 |
| 改善候補の一覧 | 候補 / 出どころ / 観点 / 類型 / 2 軸 / 対応先の表 |
| 合意 | 候補ごとの決定と合意の記録（0 件ならその根拠） |
| 起票した issue | 番号と URL |
| 後続フェーズの決定 | 含めたフェーズと理由・作成 / 修正したチケットの一覧 |

## 参照

- 観点・類型の文言の正: 機構の定義（`00-workflow-quick-request` の振り返りと同一文言）
- 作業ログの固定見出し: `20-common-step-ticket`（正）
- レビュー指摘の全件取得と issue の起票: `20-common-step-issue`
- 計画書の HTML と検査: `20-common-step-report-view`
- MR への記録: `00-workflow-issue-mr-driven` の `boundary.sh note`
- 後続チケットの記載事項・DoD の型: 各フェーズのタスクスキル

## エラー時の対処

| 状況 | 対処 |
|------|------|
| ヘッドレスで合意が取れない | 止まらない。既定の提案どおりに決めて手順 6 まで進み、`boundary.sh note` で MR に記録する |
| ヘッドレスで「別 issue」と判断した候補がある | 起票しない。候補の内容と理由を計画書と `note` に残す |
| 候補が 0 件 | 0 件の根拠（確認した記録の範囲）を書いて手順 6 へ進む。省略しない |
| 改善を自分で直したくなった | 直さない。後続フェーズのチケットに落とす |
| 後続フェーズが 1 つも要らないと判断した | 全体まとめチケットを 1 枚作る。何も作らずに完了しない |
| `ticket.sh complete` が TK005 | 列挙された未充足を埋めてから再実行する |
