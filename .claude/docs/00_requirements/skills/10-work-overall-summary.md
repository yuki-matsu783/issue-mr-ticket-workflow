# 10-work-overall-summary スキル

## 概要

フェーズ列の末尾に置かれる全体まとめワークの要件を定義する。フィードバック計画より後のワークで新たに見つかった反映すべき内容の別 issue 起票 → default ブランチとの衝突解消 → 統括レポートの作成 → MR 本文の最終化 → 関連 issue へのコメント → 作業領域の片付け → push → draft 解除 の順に進め、マージは行わず停止する。承認（衝突解消の方針・投稿する本文）が続けて挟まるため、メインエージェントが行う。振り返りは行わない（フィードバック計画で済んでいる）。

- **背景**: 作業領域（計画・チケット・レポート）はブランチ限りの記録で、マージには載せない。一方で「何が満たされ、何が残ったか」は issue と MR に残す必要がある。片付けと記録の書き写しの順序を誤ると、消してはいけない要約が消え、あるいは作業ファイルが MR の差分に残る。締めの手順を 1 本のワークに固定したい。
- **目的**: 受け入れ条件の充足と残課題が issue・MR 上で追える状態にし、作業領域を空にし、レビュー可能な状態（draft 解除）で人間のマージ判断に引き渡す。
- **スコープ**:
  - 含む: 残った反映すべき内容の別 issue 起票、default ブランチとの衝突解消、統括レポート（md + HTML）の作成、MR 本文の最終化、関連 issue へのコメント、作業領域の片付け、push、draft 解除、全体まとめチケットの着手から完了まで、再開時の扱い
  - 含まない: 振り返りと改善候補の決定（`10-work-feedback-plan`）、MR のマージ（人間が行う）、レビュー指摘への対応（各ワークの追加チケット）、片付け・draft 解除を安全にする仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 作業の締めで、受け入れ条件の充足・残課題・別 issue 化された内容が issue と MR に書き写され、作業領域が片付いた draft 解除済みの MR を受け取りたい。

**[So that]** マージの判断に必要な情報が GitLab / GitHub 上に揃い、作業ファイルの混入や消し忘れを気にせずマージできるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このワークに入ったとき、Shall スキルはメインエージェント自身で実施し、サブエージェントに委ねてはならない（承認が続けて挟まるため）。
- When 全体まとめチケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、以降の手順を 別 issue 起票 → 衝突解消 → 統括レポート → MR 本文の最終化 → 関連 issue へのコメント → 片付け → push → draft 解除 の順で行わなければならない（順序を入れ替えない）。
- When フィードバック計画より後のワークの作業ログ・レポートに反映すべき内容（改善候補・スコープ外の気づき）が残っているとき、Shall スキルはそれらを集めて別 issue の本文案を提示し、承認を得てから起票しなければならない（この MR での追加対応はしない。振り返りもやり直さない）。
- When default ブランチとの衝突を確かめるとき、Shall スキルは最新の default ブランチと突き合わせ、衝突が無ければ承認なしで次へ進み、衝突があれば衝突ファイルと解消方針を提示して承認を得てから取り込み（merge）で解消しなければならない。rebase と、片側を丸ごと採用する解消を使ってはならない。
- When 統括レポートを書くとき、Shall 作業領域のレポートの置き場に md + HTML で 1 つ作り、issue の受け入れ条件との対応（何がどのワーク・テストで満たされたか）、各ワークのレビュー結果（人間レビューを省略したワークはその旨）、フィードバック計画で決めた対応（この MR で対応したもの・別 issue に起票したもの・対応しないとしたもの）、残課題を 1 つにまとめなければならない。
- When MR 本文を最終化するとき、Shall スキルは統括レポートの要約（受け入れ条件との対応・残課題・別 issue の一覧）を MR 本文に書き写さなければならない（作業領域の記録は片付けで消えるため、残したい内容はここまでに書き写す）。
- When 関連 issue にコメントするとき、Shall スキルは投稿先の issue 番号と本文そのもの（受け入れ条件との対応・成果物・マージ後の扱い）を提示して承認を得てから投稿しなければならない（「投稿してよいか」だけを聞かない）。追加の通知先はユーザーが指定する。
- When 作業領域を片付けるとき、Shall スキルは提供コマンドで作業領域（全体計画書・チケット・計画書・レポート・進行状態・一時ファイル）を空にしなければならない。片付けの前提（未着手・作業中のチケットが全体まとめチケット以外に無い・書き写しが済んでいる）は機構が確かめる。
- When 片付けが終わったとき、Shall スキルは全体まとめチケットを提供コマンドで完了し、push し、draft を提供コマンド経由で解除しなければならない。チケットが無くなった状態でもこれらが機構に拒否されず、振り分けの再宣言も求められない。
- When draft を解除したとき、Shall スキルは結果（issue・MR の番号、別 issue の一覧、衝突解消の有無と内容、片付けの件数）を報告してマージを行わずに停止しなければならない。

### 代替フロー

- If フィードバック計画より後に反映すべき内容が何も残っていない場合、Then スキルは別 issue を起票せず、統括レポートに「追加の反映なし」とその確認範囲を書いて次へ進まなければならない。
- If 再開時に全体まとめが途中まで進んでいる場合、Then スキルは機構が示す進行状態（どの手順まで済んだか）から続きを行い、済んだ手順（起票・投稿・片付け）をやり直してはならない（二重投稿しない）。
- If ユーザーが「draft のまま置く」ことを選んだ場合、Then スキルは draft 解除を行わず、そこまでの結果を報告して停止しなければならない。

### 例外フロー

- If 片付けの前提が満たせない（完了していないチケットが残っている・最後のワークのレビューが未完了・未コミットの変更がある）場合、Then スキルは機構が返す未充足を報告し、該当する手順（ワークの継続・レビュー・コミット）へ戻らなければならない。進行状態を直して通そうとしない。
- If 衝突の解消方針が一意に決まらない場合、Then スキルは両側の意図を要約して判断を仰ぎ、勝手にどちらかを選んではならない。承認が得られなければ停止する。
- If issue コメントや別 issue の起票に失敗した場合、Then スキルはエラー内容と投稿済み・未投稿の別を報告して停止し、再試行で二重投稿してはならない。
- If ユーザーが応答できない実行形態で承認（別 issue 本文・衝突解消・コメント本文）が必要になった場合、Then スキルは本文案・衝突内容を報告してセッションを終え、次回セッションで進行状態から再開しなければならない。
- If HTML ビューの機械的検査で問題が見つかった場合、Then スキルは解消してから先へ進まなければならない。

### 全体まとめチケットの扱い

- When 全体まとめチケットが作業中のとき、Shall そのチケットの「やってよいこと」はレポートの置き場・チケットの置き場・`wip/tmp/` への書き込み・作業領域の片付けと、リモート書き込み（別 issue の起票・関連 issue へのコメント・衝突解消の取り込み・push・draft 解除）を含み、ソースコード・設計文書・`.claude/` 配下を書けてはならない（衝突解消で生じる取り込みの変更を除く）。
- When 全体まとめチケットの人間レビュー要否を決めるとき、Shall 全体計画の方針に従い、方針が無ければ「不要」を既定としなければならない（承認が要る操作はワークの中で個別に承認を取り、最終確認はマージの判断そのものが担うため）。人間レビュー要の場合は統括レポートの作成後・片付けの前にレビューを受ける。

### 他のスキル・機構との整合

- When コミット・push・チケットの状態変更・片付け・draft 解除を行うとき、Shall スキルは提供コマンド経由でのみ行い、進行状態の直接編集や draft 解除の直接実行を行ってはならない。
- When 統括レポートの節順・視覚語彙を決めるとき、Shall 他の実施ワークのレポートと同じ機構のテンプレートに従わなければならない。
- When 作業ログを書くとき、Shall 他の work スキルと同じ固定見出しでその都度追記しなければならない（このワークの気づきは別 issue の本文か MR 本文に書き写す。作業ログ自体も片付けで消えるため）。

## 前提条件

- フェーズ列のすべてのワークが完了し、最後のワークの切れ目の処理（レビュー要ならレビュー完了）が済み、全体まとめチケットが未着手にあること
- メインエージェントで実行されること（サブエージェントからは呼ばれない）
- 片付け・draft 解除・レポートのテンプレート・チケットの提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: 承認（別 issue 本文・衝突解消・コメント本文）が続けて挟まるためメインエージェントが行う。手順の順序は固定（書き写しが済む前に片付けない）
- **ビジネス的制約**: マージは人間が行う。AI は draft 解除で止まる。振り返りはこのワークでは行わない
- **外部的制約**: issue コメント・別 issue の起票は取り消せない外部への副作用のため、本文そのものの承認なしに行わない。ヘッドレスでは承認が取れないため報告して停止する

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 受け入れ条件との対応・残課題・別 issue の一覧が MR 本文と issue コメントに残り、片付け後も GitLab / GitHub 上で追える |
| 冪等性 | 再開時に進行状態から続き、起票・投稿・片付けを二重に行わない |
| 一貫性 | 統括レポートの節順・視覚語彙・検査は他の実施ワークと同じ。チケットの記載事項・作業ログは他の work スキルと同じ |
| 安全性 | 書き写しが済むまで片付けない。片付け後の push・draft 解除で機構が誤作動しない |
