# 10-task-overall-plan スキル 仕様

## 概要・禁止事項

全体計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-overall-plan.md](../../00_requirement/skills/10-task-overall-plan.md)。

issue・ブランチ・MR・チケットの個々の操作はすべて common-step スキルに委譲し、このスキルは判断（種別・フェーズ列・方針）と承認の取得、全体計画書の作成を担う。

禁止事項:

- サブエージェントへの委譲（人間との合意が本体のため、メインエージェント専任）
- 承認①②③を得る前の先の段階への前進（承認なしの起票・ブランチ作成・計画チケット作成）
- `git commit` / `git push` の直接実行（common-step の提供コマンドのみ）
- 全体計画書への実施結果・経過の記載（「これから何をするか」だけ）、HTML ビューの作成
- closed な issue の再オープン（同じ不具合の再発で承認を得た場合を除く）
- フィードバック計画より後のフェーズの要否の決定（フィードバック計画で決める）
- ソースコード・設計文書・`.claude/` 配下への書き込み（宣言外。フックが拒否する）

## 呼出条件

- `00-workflow-issue-mr-driven` が全体計画チケットを作業中に置いた直後に、メインエージェントが読み込む（タスクループの先頭・毎 issue 1 回）
- 前提: 作業領域のチケットが全体計画チケット 1 枚だけであること。他のチケットが既にある場合は状態の不整合として報告し、指示を待つ
- 再開時（draft MR と全体計画書が既にある）も同じスキルで続きから進める

## IN / OUT

| IN | OUT |
|----|----|
| 依頼の整理結果（要約・種別の見立て・検索語・受け入れ条件・やらないこと）、または quick-request 振り返りからの引き継ぎ（起票済み issue・種別 AI アセット・フェーズ列） | 確定した issue（番号・URL）、feature ブランチ、draft MR（番号・URL）、合意済みの全体計画書（`wip/00_overall_plan/`）、最初の計画チケット（未着手）、完了済みの全体計画チケット |

## IN / OUT サンプル

- IN: 「ログインで空パスワードが通る」→ 検索語 `ログイン login パスワード password`
- OUT: issue #12（既存に追記）、`fix-12-login-empty-password`、PR #13（draft）、`wip/00_overall_plan/overall-plan.md`（種別: アプリ、フェーズ列: 調査 → 設計 → 実装・テスト → フィードバック計画）、チケット `0002-investigation-plan.md`

## 処理フロー

1. **issue の確定**: `20-common-step-issue` の手順で類似の open issue を検索（0 件なら closed も）して提示し、**承認①**（既存 #N で進める / 新規に起票する）を取る。番号・URL 指定があれば検索を省く。closed のみ見つかったときは「新規に起票 / 対応なし（過去の結論を採る）」を確認し、同じ不具合の再発なら再オープンの承認を選択肢に加える
2. **issue の内容の確定**: 既存 issue の記述が計画に十分ならそのまま進む。不足があれば追記案、新規なら本文案（テンプレート）を作り、**ブランチ名・MR タイトルの案と同時に承認②**を取ってから `20-common-step-issue` で追記・起票する。主目的がアプリと AI アセットにまたがる・1 MR に大きすぎるときは分割案を提示し、このセッションで扱う 1 つを決める（残りは起票のみ）
3. **マージ方式の確認**: `gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed` / `glab api "projects/:id" | jq .squash_option` で squash merge の可否・既定を確認し（`jq` は機構の実行環境の前提に含まれる）、squash が使えない・既定でないときは影響（作業領域の全履歴が main に残る）を警告して設定変更を人間に委ねる（AI は変更しない）
4. **ブランチと draft MR**: 未コミットの変更があれば扱い（コミット / stash / 破棄 / 中断）を確認してから、`20-common-step-feature-mr` の手順で作成し、issue 番号・ブランチ名・MR 番号と URL を報告する
   - **前の issue の作業領域が default ブランチに残っていないかをここで確かめる**（`wip/` 配下に `.gitkeep` 以外の追跡されたファイルがあるか）。片付けを飛ばしてマージされた MR があると、前の issue のチケット・計画書・レポートが default に残ったままこの issue が始まり、以降どのチケットからも消せなくなる（`wip/` の削除は全体まとめの片付けだけが行い、それは**この issue の**作業領域を消す操作なので、他の issue の残骸は対象外）。**ブランチを切る前がこれを片付けられる唯一の機会である**
   - 残骸を見つけたら、対象の一覧と出どころ（どの MR の残りか）を提示し、**この全体計画チケットの中で削除してブランチの最初のコミットに含めてよいか**を承認として確認する。承認されたときに限り、全体計画チケットの `allow.write` に `wip/**` を含めて削除する（既定の宣言は `wip/00_overall_plan/**` / `wip/10_tickets/**` / `wip/tmp/**` なので、`wip/20_plans/` `wip/30_reports/` の残骸はそのままでは消せない）。承認されなければ削除せず、残骸の一覧と「この issue では消せない」ことを全体計画書の「保留した点」に書いて進む（別 issue に回す）
5. **種別の判定**: 受け入れ条件と変更対象から「アプリ / AI アセット」を判定し、根拠とともに提示する（「両方」は置かない — 手順 2 で分割済みのはず）
6. **フェーズ列**: 種別のテンプレート（`10_spec/skills/00-workflow-issue-mr-driven.md` の対応表とフェーズ列のテンプレートが正）を土台に、調査とフィードバック計画を必ず含め、主作業フェーズは迷ったら含める側に倒す（不要なら計画タスクの「対象なし」で即完了）。フィードバック計画より後は含めない
7. **方針**: `rules/work-defaults.md` があればそれを基準に、タスクの種類ごとの実行者・人間レビュー要否（理由付き）・やってよいことの方針を、基準との差分として理由付きで組む。基準が無ければスキルの既定を使いその旨を計画書に書く
8. **全体計画書と承認③**: テンプレートから全体計画書を作って提示し、フェーズ列・実行者・レビュー要否・やってよいことの方針の合意を取る（`AskUserQuestion`。却下されたら修正して再提示）。合意の内容（誰が・いつ・何に）を計画書に記録する
9. **最初の計画チケット**: `20-common-step-ticket` の `create` で調査計画チケットを 1 枚だけ未着手に作る（記載事項は全体計画の方針から埋め、DoD は issue の受け入れ条件から導く）
10. **完了**: 作業ログを整えて `ticket.sh complete` で全体計画チケットを完了し、`00-workflow-issue-mr-driven` に制御を戻す（切れ目の処理はそちら）

- ヘッドレス実行（承認が取れない）: 案（issue 案・計画案）をコミットせずに報告してセッションを終える
- 再開: draft MR と全体計画書が既にあれば 1〜4 をやり直さず、既存の計画を提示して続きから進める（二重作成しない）

## OUT ひな形

`assets/overall-plan.template.md`（HTML ビューなし・1 画面程度）:

| 節 | 内容 |
|----|------|
| 対象 | issue 番号と URL・MR 番号と URL・ブランチ |
| 種別 | アプリ / AI アセットと判定根拠 |
| フェーズ列 | 採用した列・テンプレートとの差分と理由 |
| 受け入れ条件との対応 | 条件 × 満たすフェーズの表 |
| 方針 | タスクの種類ごとの実行者・人間レビュー要否（理由）・やってよいこと（work-defaults との差分表示） |
| 保留した点 | 判断を保留した項目と決める時期 |
| 合意の記録 | 承認①②③の内容・日時 |

## 参照ナレッジ

- issue 操作・ブランチと MR・チケット操作・コミット: 各 common-step の仕様
- タスクの構成（15 種・順序・種別テンプレート）: `10_spec/skills/00-workflow-issue-mr-driven.md`（正）
- 既定判断基準: `rules/work-defaults.md`（任意）
- 承認の記録の寿命: 切れ目ごとの MR コメントへの書き写し（呼び出し元の切れ目処理。DDR `i0001-26`）

## Script 処理

なし。操作はすべて common-step の提供コマンドに委譲する（このスキル固有のスクリプトを持たない）。

## テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| OP-E01 | AI アセットの変更が主目的の issue | フェーズ列テンプレート（AI アセット）を選び、省略なしで全体計画書に書く。省略するなら理由を書く | 選んだテンプレートと、フェーズ列の並び |
| OP-E02 | 実行者・レビュー要否を決める場面 | `rules/work-defaults.md` の既定を基準に提案し、基準から外す行は「何を・どちらへ・なぜ」を書く。基準どおりの行は「基準どおり」と書く | 差分の書き方と、基準との突き合わせ |
| OP-E03 | issue の受け入れ条件が 9 件ある | 9 件すべてをフェーズに割り付け、「受け入れ条件との対応」に漏れなく載せる | 対応表の行数と条件の件数の一致 |
| OP-E04 | 全体計画の承認をユーザーに求める場面 | フェーズ列・実行者・やってよいことをまとめて 1 回で確認する。承認を得るまで最初の計画チケットを起こさない | 確認の回数と、起票のタイミング |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| issue確定: メインエージェント専任 | 禁止事項・呼出条件 |
| issue確定: 類似検索（open→closed）と提示 | 処理フロー 1 |
| issue確定: 承認①、内容提示 | 処理フロー 1 |
| issue確定: 十分なら追記なしで前進 | 処理フロー 2 |
| issue確定: 不足の追記案 + 承認②・追記のみ | 処理フロー 2 |
| issue確定: 新規案 + 承認② | 処理フロー 2 |
| issue確定: 本文はファイル経由・DoD に落ちる粒度 | `20-common-step-issue` 仕様へ委譲 |
| issue確定: またがる・大きすぎる場合の分割 | 処理フロー 2 |
| ブランチMR: マージ方式の確認と警告 | 処理フロー 3 |
| ブランチMR: default 最新から命名規約で作成 | `20-common-step-feature-mr` 仕様へ委譲（処理フロー 4） |
| ブランチMR: draft MR と報告 | 処理フロー 4 |
| ブランチMR: 差分なしは空コミット | feature-mr 仕様へ委譲 |
| ブランチMR: common-step 経由・直接 git 禁止 | 禁止事項 |
| 計画: 種別判定（両方なし） | 処理フロー 5 |
| 計画: フェーズ列（テンプレ土台・調査と FB 計画必須・後は決めない） | 処理フロー 6 |
| 計画: 迷ったら含める側 | 処理フロー 6 |
| 計画: 実行者とレビュー要否の提案・リスク高は要 | 処理フロー 7 |
| 計画: work-defaults を基準に差分提示 | 処理フロー 7 |
| 計画: やってよいことの方針（上限内） | 処理フロー 7 |
| 計画: 承認③・合意前にチケットを作らない | 処理フロー 8、禁止事項 |
| 計画: 最初の計画チケット 1 枚のみ | 処理フロー 9 |
| 計画: チケットの記載事項と DoD | 処理フロー 9（ticket 仕様の記載事項） |
| 計画: 完了の検査と提供コマンド | 処理フロー 10（ticket 仕様の complete） |
| 計画: 完了後は呼び出し元へ | 処理フロー 10 |
| 代替: 番号指定・closed のみ・対応なし・起票のみ | 処理フロー 1・2（対応なし / 起票のみは報告して停止） |
| 代替: 再開・quick-request からの切り替え | 処理フロー末尾の再開、IN（引き継ぎ） |
| 代替: 受け入れ条件が曖昧なら追記から | 処理フロー 2 |
| 例外: CLI 未導入・origin 対象外・失敗時停止 | common-step 仕様へ委譲 |
| 例外: 未コミットの変更の確認 | 処理フロー 4 |
| 例外: 合意保留・ヘッドレス | 処理フロー 8・ヘッドレスの扱い |
| 例外: 他のチケットが既にある | 呼出条件（前提）に規定 |
| 例外: default に残った前の issue の作業領域 | 処理フロー 4 の但し書き（一覧と出どころの提示・承認・保留した点への記録） |
| 計画書の内容・結果を書かない・1 つ・HTML なし | OUT ひな形、禁止事項 |
| 承認ポイント: 却下時は留まる | 処理フロー 1・2・8 |
| チケットの扱い: やってよいこと・レビュー既定不要 | 禁止事項（宣言）・処理フロー 7 の既定 |
