# i0001-09. 全体計画チケットを最初に置き、マージ前作業は全体まとめに含める

## 背景

参考実装 agent-workflow では、振り分けの継続判定を「作業領域にチケットがあるか」で行うため、(1) issue の確定からブランチ作成までのチケットが無い区間と、(2) マージ前の片付けでチケットが消えた後の区間で、別プロンプトから再開すると振り分けの再宣言が要る（既知の制約として SKILL.md に記載されていた）。また、マージ前作業（wip の片付け・衝突確認・issue 通知・draft 解除）は全タスク完了後の「完了処理」としてオーケストレータが別途行う構造で、振り返り（retrospective）とは別の段階だった。

## 決定

- `00-workflow-issue-mr-driven` で進めると決まったら、**最初に全体計画チケットを作成して作業中に置く**。issue の確定・ブランチと MR の作成・全体計画の合意はこのチケットの中で行い、合意後に完了する。issue・ブランチ・MR の作成と push は全体計画チケットの「やってよいこと」として宣言する（リモート書き込みの統制は i0001-18 の宣言体系による）。issue の確定・ブランチと MR の作成の手順と承認は `10-task-overall-plan` の要件とし、`00-workflow-issue-mr-driven` は全体計画チケットの配置・タスクの起動・切れ目の処理に徹する
- マージ前作業（衝突解消・作業領域の片付け・push・draft 解除）は、**全体まとめのタスクに含める**。全体まとめは「フィードバック計画より後のタスクで残った反映すべき内容の別 issue 起票 → default ブランチとの衝突解消 → 統括レポートの作成 → MR 本文の最終化 → HTML レポートの MR 先頭コメントへの添付（できる環境の場合）→（人間レビュー要ならここでレビュー）→ 作業領域の片付け → push → draft 解除 → 停止」の順で進む。作業中の issue にはコメントを含め書き込まない（マージ判断に必要な情報は MR 本文と添付に揃える。close はマージ後に人間が行う）。振り返りと改善候補の起票はフィードバック計画（i0001-11）で済んでいるため全体まとめでは行わない。「マージ前作業に進むか」だけを問う独立した承認は置かない（全体計画で全体まとめの内容に合意済みのため）。衝突解消と別 issue の起票は引き続き承認を取る
- 片付けでチケットが無くなった後の push と draft 解除は、機構に拒否されず、振り分けの再宣言も求められない状態でなければならない（実現方法は仕様で定める）
- 類似候補が closed な issue だけのときは、再オープンを選択肢にせず、過去の類似事例を示したうえで「新規に作る」か「対応なし」かを確認する

## 理由

- 開始直後にチケットを置くことで、issue 検索や承認の往復が複数プロンプトにまたがっても、機構から見て「作業中」の状態が途切れない
- マージ前作業を全体まとめに含めると、全体まとめの計画・チケットの中で片付けと draft 解除まで見通せ、オーケストレータ側の「完了処理」という別の段階を持たなくて済む
- 片付け後の区間を機構の例外として明示することで、参考実装で既知の制約とされていた再宣言の穴を、運用注意ではなく要件として塞ぐ
- closed な issue は当時「やらない」または「終わった」と判断されたものであり、再オープンより「新たに issue を起こす」か「今回も対応しない」のほうが判断として素直。過去の結論を見せることで同じ議論の繰り返しを避ける

## 却下した案

- **全体計画チケットを作らず、ブランチ作成後に最初のチケットを起こす（agent-workflow 方式）**: 構造は単純だが、issue の確定までの区間でチケットが無く、再宣言の穴が残る
- **マージ前作業をオーケストレータの完了処理として全体まとめの外に置く（agent-workflow 方式）**: 全体まとめとマージ前作業の責務が分かれて読みやすいが、承認③（マージ前作業に進むか）という追加の往復と、片付け後の再宣言の穴が残る
- **closed な issue の再オープンを選択肢に含める（agent-workflow 方式）**: 経緯が 1 つの issue にまとまる利点はあるが、閉じた判断を覆すことになり、当時の結論を読み直す手間がかかる
- **issue の確定・ブランチと MR の作成を `00-workflow-issue-mr-driven` の手順として持つ**: 作業の起点が 1 つのスキルに見える利点はあるが、全体計画チケットの中で行う作業が 2 つのスキルに分かれ、承認の番号付けや issue 周りの代替・例外フローで 00 側が膨らみ、オーケストレータとしての読みやすさを損なう

## 影響

- 要件定義書 B・C・J 節、`00-workflow-issue-mr-driven.md` のメインフロー・承認ポイント・代替フロー、`10-task-overall-plan.md` の issue の確定・ブランチと draft MR の作成・承認①②
- 全体計画チケットは他のチケットと異なりリモート操作（issue・ブランチ・MR・push）を許可する必要がある。type 定義の上限で扱う
- 全体まとめの task スキルはメインエージェントが実施する（i0001-08）
- タスクの切れ目の判定・振り分けの継続判定は、片付け後の状態を「継続中」として扱えるようにする（仕様で定める）
