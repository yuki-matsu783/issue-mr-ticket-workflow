# 10-work-design-exec スキル

## 概要

設計フェーズの実施ワークの要件を定義する。設計計画書の骨子と結論方針に従って設計チケットを順に実施し、アプリ本体の設計文書の置き場（`docs/` 配下）に要件定義書・仕様書を作成・更新する。文書には現在の正史だけを書き、決定の経緯（採らなかった案と理由）は DDR に分離する。ワークの最後に設計結果レポートをまとめる。

- **背景**: 設計書は実装のよりどころであり、受け入れ条件がどの受け入れ基準・テストシナリオに落ちたかが追えないと、実装とテストの完了判定が曖昧になる。また設計中の決定を文書の本文に経緯ごと書くと、正史と歴史が混ざって読めなくなる。
- **目的**: 受け入れ条件を漏れなく受け入れ基準（EARS 形式）とテスト ID 付きのテストシナリオに落とし、判断点の結論を根拠付きで正史に、経緯を DDR に残し、実装フェーズが判断に使える設計書と、レビュアーが読む設計結果レポートを揃える。
- **スコープ**:
  - 含む: 設計チケットの実施（着手から完了まで）、要件定義書・仕様書の作成・更新、決定の経緯の DDR 化、設計結果レポート（md + HTML）の作成、再開・差し戻しの扱い、呼び出し元への結果報告
  - 含まない: 設計書の一覧と骨子の決定（`10-work-design-plan`）、設計書の書式そのもの（設計書作成の task スキルとテンプレートが正）、コードの作成（実装・テストフェーズ）、AI アセットの設計（AI アセット設計フェーズ）、ワークの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 受け入れ条件がどの受け入れ基準・テストシナリオに落ちたかが追える設計書と、その要約のレポートをレビューしたい。

**[So that]** 実装に入る前に設計の抜けと判断の誤りを正せ、実装・テストの完了を設計書に照らして判定できるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このワークに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、設計計画書（結論方針・一覧・骨子）・調査結果レポート・issue の受け入れ条件・既存の設計文書を入力に進めなければならない。
- When 設計チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットが担う設計書だけを書かなければならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 設計チケットを完了するとき、Shall そのチケットの DoD（設計書がテンプレートに沿っている / 骨子の各節が埋まりプレースホルダが無い / 受け入れ条件が受け入れ基準・テストシナリオに落ちている / 経緯が DDR に残っている）が根拠付きで満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 1 枚の設計チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の設計チケットに着手しなければならない（ワークの切れ目ではない）。
- When すべての設計チケットが完了したとき、Shall スキルは設計結果レポートを仕上げ、結果報告（完了したチケットの一覧、設計書と DDR の一覧、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「受け入れ条件が受け入れ基準・テストシナリオに漏れなく落ちているか」「判断点の結論が根拠付きで調査結果と矛盾しないか」「仕様が実装可能な粒度か。逆にコードに踏み込みすぎていないか」「既存の設計書との整合」を挙げなければならない。

### 代替フロー

- If 再開時に設計チケットが作業中で設計書が書きかけの場合、Then スキルは作業ログの「現在地」から続きを進め、設計書・DDR・レポートの節を二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのワークに戻った場合、Then スキルは設計書と DDR を直し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残し、レポートを追記・修正しなければならない。
- If 設計計画書の骨子どおりに書けない（調査に無かった事実が見つかり前提が崩れた）場合、Then スキルは推測で骨子を変えず、書ける範囲を書いたうえで「未解決事項」と代わりの案をレポートに残し、判断を人間レビューに委ねなければならない。

### 例外フロー

- If ソースコードや `.claude/` 配下への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、コードに書きたい内容は仕様書のインターフェース定義に、AI アセットに書きたい内容はフィードバック計画に回さなければならない。
- If 設計計画書が無い、または設計チケットが計画書の一覧と対応しない場合、Then スキルは設計を始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。
- If HTML ビューの機械的検査、またはプレースホルダの検査で問題が見つかった場合、Then スキルは解消してから完了しなければならない。

### 設計書と DDR の内容

- When 設計書を書くとき、Shall アプリ本体の設計文書の置き場（`docs/` 配下。既存の構成があればそれに従う）に、機構の設計書テンプレート（要件定義書・仕様書）に沿って書かなければならない。書き方の正は設計書作成の task スキルとする。
- When 要件定義書を書くとき、Shall issue の受け入れ条件を EARS 形式（When / Shall、If / Then、Shall not）の受け入れ基準に落とし、前提・制約・依存関係を書かなければならない。
- When 仕様書を書くとき、Shall 入出力・処理フロー・インターフェース・エラーハンドリング・テストシナリオを実装可能な粒度で書き、テストシナリオにはテスト ID を振らなければならない（実装フェーズの DoD とテストの対応に使う）。実装の詳細（コード）に踏み込んではならない。
- When 設計計画書で「設計チケットで結論を書く」とされた判断点に結論を書くとき、Shall 根拠付きで正史に書き、採らなかった案と理由は DDR に残さなければならない。
- When 既存の設計書を更新するとき、Shall 本文はその時点の正史だけになるよう書き換え、過去の記述・変更履歴・経緯を本文に残してはならない（経緯は DDR へ。履歴は Git が持つ）。
- When 設計書を書き終えたとき、Shall テンプレートのプレースホルダが 1 つも残っておらず、用語・インターフェースが既存の設計書と整合していなければならない。

### 設計結果レポートの内容

- When すべての設計チケットが完了するとき、Shall 設計結果レポートが作業領域のレポートの置き場に 1 つあり、同じ名前の HTML ビューが併存しなければならない（Markdown が正文。テンプレートのコピーと Edit で作り、機械的検査の結果を作業ログに残す）。
- When 設計結果レポートを書くとき、Shall 機構のレポートの節順に沿って次を含めなければならない: 作成・更新した設計書と DDR の一覧、判断点の結論とその根拠の要約、受け入れ条件と受け入れ基準・テストシナリオの対応表、設計中に分かった想定と異なった点、残課題（骨子どおりに書けなかった点・未解決事項）。

### 設計チケットの扱い

- When 設計チケットが作業中のとき、Shall そのチケットの「やってよいこと」はアプリ本体の設計文書の置き場（DDR を含む）・レポートの置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、ソースコード・`.claude/` 配下を書けてはならない。
- When 設計計画書で並列に進めてよいとされたチケット群を並列で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。並列にしたチケットが同じ設計書を書き換えないよう、担当の文書を分ける。
- When 設計チケットの人間レビュー要否を参照するとき、Shall チケットの記載に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 設計計画書・調査結果レポートを参照するとき、Shall スキルはそれらを書き換えてはならない。骨子どおりに書けないと分かったときは、設計書とレポートに「未解決事項」として残し、必要なら設計計画の追加チケットを結果報告で提案する。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルは設計書と設計結果レポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

---

## 前提条件

- `10-work-design-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、設計チケットが未着手にあること
- 設計チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 設計書作成の task スキル（要件定義書・仕様書のテンプレートと手順）、レポートのテンプレート（md + HTML）、チケットの提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない（ヒアリングの代わりに調査結果・設計計画書・受け入れ条件を使う）。判断に迷う点は「未解決事項」に残す
- **ビジネス的制約**: 設計の採否は MR 上の人間レビューで確定する。スキルは根拠付きの正史と DDR を揃えるまで
- **外部的制約**: 書くのは設計であり、コードは書かない。設計文書は正史のみ・経緯は DDR という機構のドキュメント体系に従う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 受け入れ条件 → 受け入れ基準 → テストシナリオ（テスト ID）→ 実装フェーズの DoD と辿れる。決定の経緯は DDR から辿れる |
| 一貫性 | 設計書はテンプレートと既存文書の用語・構成に合わせる。レポートの節順・視覚語彙・検査は他の実施ワークと同じ |
| 簡潔性 | 設計書は実装が判断に使う粒度までとし、コードの先取りや網羅的な背景説明を書かない |
| 冪等性 | 再開時に設計書・DDR・レポートを二重に作らない |
