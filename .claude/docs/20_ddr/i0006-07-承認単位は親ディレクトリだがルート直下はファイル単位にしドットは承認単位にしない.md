# i0006-07. 承認単位は親ディレクトリだが、ルート直下のファイルはファイル単位にし、"." は承認単位にしない

## 背景

`workflow-guard` は許可範囲の外への書き込みを ask（WF202）で人間に確認し、承認された範囲を `wip/10_tickets/approvals.json` に記録して以降は allow にする。承認単位は「書こうとしたファイルの親ディレクトリ」（`file_granular` に載るファイルだけファイル単位）と仕様 §8 に書いていた。実装（issue #6 チケット 0014〜0021）で、リポジトリルート直下のファイル（`README.md` 等）の親は `.` になり、これを承認単位として記録すると次からリポジトリ内のあらゆるパスが「`.` 配下」として allow になることが分かった（実装結果レポート 0013 の逸脱 D-25、テスト HK-T11 で固定）。

## 決定

- 承認単位は親ディレクトリのまま。ただし**リポジトリルート直下のファイルは親ではなくファイルそのものを承認単位にする**（`file_granular` と同じ扱い）
- `approvals.json` に `"."`（または空）が記録されていても、承認済み範囲としては**無視する**。記録の有無にかかわらず `"."` は何も許可しない
- 承認範囲の一致は「`scope` に完全一致、または `scope/` 配下」で判定する（前方一致ではない。`logs` の承認で `logs2/x` は通らない）

## 理由

- ルート直下のファイルは種類がばらばら（README・設定・ライセンス）で、1 つ承認したら隣も書いてよいという推定が成り立たない。ディレクトリ単位の承認が意味を持つのは「同じ性質のファイルが集まる場所」に限る
- `"."` を無視するのは、記録ファイルの壊れ方（手で書かれた・古い版の記録）に対しても全許可にならないため。読み手側で守る方が、書き手側の検査 1 か所に頼るより堅い
- 例外を `file_granular` の仕組みに寄せたので、判定順や記録の形（`scope` のリスト）は変わらない

## 却下した案

- **ルート直下も親ディレクトリ（= `.`）で承認する**: 1 回の承認で全許可になる。ask の意味が無くなる
- **ルート直下のファイルは常に ask（承認を記録しない）**: 同じファイルを何度も書く作業（README の推敲）で毎回止まる。ヘッドレスでは 1 回目の ask で止まるのはどちらも同じだが、対話中の往復が増える
- **`"."` を記録時に弾くだけ（読み手は信用する）**: 記録経路が 1 つ（フック自身）でも、壊れた記録を読んで全許可になる経路が残る

## 影響

- `10_spec/フック共通仕様.md` §8「判定順」(6)(7) と §11 HK-T11
- `10_spec/hooks/20-PreToolUse/workflow-guard.md`（WF202 の承認単位）と `22-PostToolUse/workflow-diff-check.md`（承認の記憶。`"."` は記録しない）
- ヘッドレス実行: ルート直下のファイルへの書き込みは 1 ファイルごとに ask で止まる（既定で進まない）。計画がルート直下の変更を含むなら `types[t].allow` に個別に載せる
