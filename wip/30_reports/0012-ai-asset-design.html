0012 まで。 AI アセット設計計画書（wip/20_plans/0010-ai-asset-design-plan.md）の結論方針 P1・P1a・P3・P8・P9 を .claude/docs/ の正史へ落とした。フック共通仕様に作業ツリーの三分（HOOK_ROOT / HOOK_WORKTREE / HOOK_SHARED_ROOT）と進行状態・ロック・集計の共有ルートへの一本化を定め、workflow-state-guard に作業ツリーをまたぐ絶対パスの保護（A1-2。無条件）、workflow-diff-check に作業ツリーごとに一意な差分の基準点（A5）と仕様 §13 の書き戻し（P9）を書いた。DDR は 3 本（i0050-01 / i0050-02 / i0050-07）作り、置き換えられた 3 本には frontmatter の status と置き換え先だけを足した。更新した文書は要件 3・仕様 3・DDR 新規 3・DDR frontmatter 3 の計 12 ファイル。

◆特に見てほしい

判断に困っている

  • 計画書が指定したテスト ID の接頭辞 WD-T を使わず、DC-T08 / DC-T09 を採った（e8-1）。workflow-diff-check の仕様が現に使っている接頭辞は DC-T（DC-T01〜DC-T07、テストの実体も DC-T）で、WD-T を新設すると 1 つのアセットが 2 つのテスト ID 接頭辞を持つ。計画書の骨子から外れる判断なので、WD-T でなければならない理由があれば差し戻してほしい
  • 計画書のヘッドレス実行の帰結が「4 本のフックは拒否側に倒す」と書いているが、そのうち 2 本は拒否できない（e8-2）。workflow-diff-check（PostToolUse）と subagent-start-check（SubagentStart）は deny を出す経路を持たない。「拒否側に倒す」の中身を、拒否できるフックは deny、案内側は『判定していない』ことを伝える側に倒すと読み替えて §2 に書いた。読み替えの当否を見てほしい

◇判断が欲しい

決めた方針の承認 / 決められない点の判断

  • 共有ルートを HOOK_SHARED_ROOT という別の変数として持ち、値は HOOK_ROOT と同一に固定した（計画書の保留 P2 の決着。e1）。環境変数からの上書きを受け付けないのは、進行状態の置き場を外から動かせることが workflow-state-guard の保護対象を外から外せることを意味するため
  • workflow-state-guard が「畳めないパス」を拒否する範囲を、リポジトリの外と確定できるものは許可 / 位置を確定できないものだけ拒否 に分けた（e3）。一律拒否にすると OS の一時ディレクトリへの正当な書き込みまで止まるので、i0010-09 の適用対象を「判定できない」に限った
  • workflow-diff-check に新しい識別子 WF605（作業ツリーを確定できない）を採った（e4）。既存の WF604（基準点なし）に相乗りさせると 1 番号に 2 原因が乗るため分けた
  • 置き換えられた DDR 3 本の frontmatter に status / superseded_by / superseded_scope を足した（e6）。チケットの作業内容は「既存の DDR は書き換えない」だが、ai-asset-design-docs ルールは置き換えの関係を対で持たせることを求めているので、本文は 1 文字も変えず frontmatter だけを足した

実施した内容と結果

  1. 1

    e1. 作業ツリーの三分を §2 に定義し、共有ルートは別の変数として持って値を HOOK_ROOT に固定した ◎良 根拠: 10_spec/フック共通仕様.md §2（計画書 P3・保留 P2）

    10_spec/フック共通仕様.md §2 に、フックが区別する 3 つの根を表で置いた。

    名前変数指すものそこに置かれるもの
    置き場HOOK_ROOT読み込み行が解決したリポジトリルート（本流）フック・共通ライブラリ・hooks/config/・settings.json
    判定対象の作業ツリーHOOK_WORKTREEその操作が行われた作業ツリーwip/、logs/hooks/decisions.jsonl、logs/sh/
    共有ルートHOOK_SHARED_ROOTissue・ブランチ・MR に属する進行状態を集める根logs/ の進行状態・ロック・集計・セッション状態

    計画書の保留 P2（変数を分けるか決め打つか）は分けるで決着させた。ただし値の解決は HOOK_ROOT と同一に固定し、環境変数・設定からの上書きを受け付けない。理由は 2 つで、①名前を分けておけば、別 clone を使う運用（要件の前提条件が認めている）を扱うときに値の解決だけを変えればよく、進行状態を読む全フック・全提供コマンドを触らずに済む ②上書きの口を開けると、進行状態の置き場を動かすことで workflow-state-guard の保護対象そのものを外から外せる（拒否側の保護が環境変数 1 つで無効になる）。

  2. 2

    e2. 進行状態・ロック・集計を共有ルートへ、判定記録と実行ログを作業ツリー側へ分けた ◎良 根拠: 10_spec/フック共通仕様.md §1・§5（計画書 P3 / 束 1 の 6・7）

    §5 の表に「根」の列を足し、記録ごとの置き場を 1 か所で読めるようにした。共有ルート側は mr.json / review-state.json / review-history.jsonl / merge-state.json / locks/ / usage/<branch>.json / sessions/<session_id>/ / push-state.json、作業ツリー側は hooks/decisions.jsonl と sh/<name>.log の 2 つだけである。logs/locks/<name>.lock は表に無かったので行を足した（実装は使っており、束 1 の 7 が名指ししている対象なので、置き場を決める以上は表に載っている必要がある）。

    decisions.jsonl のスキーマに cwd（判定時の作業ツリー）と agent_id（サブエージェントの識別）を足し、HK-T06（記録のスキーマ）にその検査と負のコントロール（メインの呼び出しでは agent_id が空）を書き足した。

    この決定が §1 の別の記述に効いていた。 §1 は「jq は最大 2 回」の内訳として「logs/ は作業ツリー側に置き、作業ツリーは stdin の cwd を読んで初めて決まるので、この 4 つを 1 回目に混ぜることは原理的にできない」と書いていた。進行状態を共有ルートへ寄せると review-state.json / merge-state.json の置き場はフックの起動時に決まるので、この理由付けは成り立たなくなる。2 回目が要る理由を session_id 依存（approvals.json / entry.json）に置き換え、review-state / merge-state を 1 回目に混ぜない理由を「読むのが 2 本のフックだけだから」に書き直した。

    「issue に属する情報は共有ルート / 作業ツリーで起きたことの記録は作業ツリー側」という分け方で一本化した。1 つの決定が §5 だけでなく §1・§11 にも効いていたので、まとめて直した。

    e3. 作業ツリーをまたぐ絶対パスの保護漏れ（A1-2）を、無条件の記述で閉じた ◎良 根拠: 調査 e5 / e51（03-state-guard.txt）・計画書 P8 / 束 2 の 2

    調査 e5 / e51 の A1-2（cwd が worktree のとき、本流の logs/mr.json と wip/10_tickets/20_done/*.md を絶対パスで書き換えても止まらない）を、要件と仕様の両方に無条件で書いた（並列を採らなくても作業ツリーが 2 つあれば踏むため）。

    • 要件: 「別の作業ツリーにある進行状態のファイル・チケットの置き場を絶対パスで指して…操作しようとしたとき、Shall フックは自分がいる作業ツリーの中の同じ対象と同じ理由・同じ識別子で拒否しなければならない（保護は作業ツリーの数に依らない）」をメインフローに追加。裏側として「同じリポジトリの外への書き込みは拒否してはならない」も置いた
    • 仕様: 「対象パスの畳み込み」の節を制御方式の前に置き、hook_rel_path の結果を 3 通り（同一リポジトリのいずれかの根の配下 → 畳んだ相対パスで照合 / どの根の配下でもない → 許可 / 判定できない → WF309）に分けた。このフックは「畳めた根がどれか」を見ないことを明示した

    「畳めないパスを拒否側に倒す」は、「リポジトリの外と確定できるもの」と「位置を確定できないもの」を分けて書いた。前者まで拒否すると OS の一時ディレクトリへの正当な書き込みが止まるので、i0010-09 の適用対象は後者に限る。この線引きは §13 の「意図的な緩和」にも 1 項目として書いた。畳み込みの規則そのものは workflow-state-guard に閉じず、共通仕様 §2 に hook_rel_path の振る舞いとして置いた（workflow-guard の __wg_rel も同じ規則を要るため。判定順は 0013 が書く）。

    e5. A1-6 を閉じる機械テスト観点を DC-T08 / DC-T09 として置き、負のコントロールの前提をテスト自身が作る形にした ◎良 根拠: 調査 e48 / R31 / R41・計画書「A1 の実測をどう閉じるか」

    受け入れ条件 A1-6（workflow-guard / workflow-diff-check が worktree 側のチケットで判定するか）は、実測時にどの作業ツリーにも作業中チケットが 0 枚で負のコントロールまで無音になり、判定不能のまま残っていた。計画書の指示どおり、人間の再実測に戻さず機械テストで閉じる。0012 が担うのは差分の基準点の 2 件で、宣言範囲の強制（WG-T）と実行者照合（SA-T）は 0013 が担う。

    テスト ID種別前提の作り方期待する結果
    DC-T08（機械テスト）正常系一時リポジトリに本流と worktree を作り、それぞれ別の base_sha を持つ作業中チケットを 1 枚ずつ置く。枚数はテスト自身が 10_doing/ を数えて assert するcwd を worktree にすると、worktree 側チケットの base_sha 以降の範囲外の差分だけが WF601 に並び、本流側の差分は並ばない
    DC-T09（機械テスト。DC-T08 の負のコントロール）正常系同じ構成で本流に作業中 1 枚・worktree に 0 枚を置く（枚数を assert する）cwd を worktree にすると何も出ない。この前提を作らずに DC-T08 だけを見ると、無出力を「判定した結果、差分が無かった」と読み違える

    負のコントロールの前提（作業中チケットの枚数）をテスト自身が assert で作ることを、テスト観点の本文に書いた。実測が失敗したのは「実行時のリポジトリの状態に前提を依存させた」ためなので、同じ失敗を再発させない条件がテストの中に無ければ、機械テストに移す意味が無い。

    あわせて共通仕様 §11 に HK-T21（作業ツリーの三分の解決）と HK-T22（作業ツリーをまたぐパスの畳み込み）を新設し、workflow-state-guard 側は SG-T12（他ツリーの保護対象を絶対パスで書く）と SG-T13（集合を読めないときに WF309）を新設した。採った ID はすべて、入力・期待する振る舞い・判定方法を持つ行として同じチケットの中で定義した（接頭辞の予約だけで終わらせていない）。
