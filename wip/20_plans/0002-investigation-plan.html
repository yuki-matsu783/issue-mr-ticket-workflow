この計画で何をするか

issue #10 の主作業（タスクスキル 15 本・ワークフロースキル 2 本・エージェント 2 本・提供コマンド 2 本の実装と参照更新）に入る前に、読み取りだけで答えられる問いを 4 枚の調査チケットに割り付ける。実測が要る問いは実施せず、確かめ方だけを「実装フェーズの検証項目」として整理する。

決めたこと

  • 調査チケットは 4 枚（0003 / 0004 / 0005 / 0006）。1 観点のまとまり = 1 チケット
  • 外部技術調査は計画しない。対象がすべてリポジトリ内の仕様書とアセットで、外部情報に依存する問いが無いため web を宣言するチケットは無い
  • 既存テストの実行は 0006 だけに計画する（fm_get と TICKET-T05 の現在の形を確かめるため build-test を宣言）
  • .claude/** への一時的な変更は計画しない（investigation は .claude/** を deny）
  • 次の計画チケットは 0007-ai-asset-design-plan。predecessors に 0003・0004・0005・0006 を入れる
  • 実装フェーズの検証項目 V1〜V7 はこの計画書が表として持つ。調査チケットは作らない

方法とステップ

  1. 1

    観点 A: 作成物を 1 行 1 件で書き出す

    読む場所は 10_spec/skills/10-task-*.md（15 本）・10_spec/skills/00-workflow-*.md（2 本）・10_spec/agents/*.md（2 本）と対応する要件、既存の .claude/skills/20-common-step-*/（作法の実例）、.claude/evals/（既存 9 本）、20-common-step-ai-asset-creator の仕様とテンプレート。各仕様の「処理フロー」「OUT ひな形」「参照ナレッジ」「Script 処理」から作成物を書き出し、同じ名前が複数の仕様に出るものに重複の印を付ける。

  2. 2

    観点 B: 仕様と実装済みフックを突き合わせる

    仕様側は 00-workflow-issue-mr-driven（boundary.sh）と 10-task-overall-summary（finalize.sh）とフック共通仕様。実装側は workflow-state-guard.sh・session-start.sh・workflow-entry.sh・hooks/lib/*.sh と既存の提供コマンド。食い違いは「項目 / 仕様の言い分 / 実装の言い分 / 実測に依存するか」の表にする。logs/ の 4 ファイルは書く側と読む側の両方からスキーマを書き出して一致を見る。

  3. 3

    観点 C: 旧名を全件出して置換後を決める

    grep -rn で 5 種を全件出し、参考ディレクトリ/・logs/・.git/・.claude/docs/20_ddr/ を除外した一覧を作る。期待値は「置換後に残るもの」の形で書き、行末に依存する検索語にしない。期待値が変更対象に依存するテストファイルも洗い出す。

  4. 4

    観点 D: 申し送りを反映先に割り付ける

    issue #10 本文の申し送りを 1 行 1 件に分解し、反映先の仕様書と節を割り当てる。反映済みのものは根拠（ファイル:行）を添える。fm_get は run-tests.sh --ids TICKET-T05 を実行して現在の期待値の形を確かめる。

検証

調査は成果物がレポートなので、機械的なテスト ID は割り付けない。次の内容が書かれていることをもって検証とする。

何をどう確かめるかテスト ID / 成果物
観点 A の答え作成物の全件一覧（種類 / パス / 出典の仕様の節 / 既存の有無）があり、重複候補・共通化候補・欠落が別表で示されているwip/30_reports/0003-investigation.md と HTML
観点 B の答えサブコマンドごとの判定順と入出力、logs/ の 4 ファイルのスキーマ（書く側 / 読む側）、食い違いの一覧があるwip/30_reports/0004-investigation.md と HTML
観点 C の答え残存箇所の全件（ファイル:行 / 旧名 / 置換後の候補）と、置換後の期待値の書き方、期待値が変更対象に依存するテストの一覧があるwip/30_reports/0005-investigation.md と HTML
観点 D の答え申し送り × 反映先の対応表があり、fm_get と TICKET-T05 の現在の形が実行結果つきで書かれているwip/30_reports/0006-investigation.md と HTML、TICKET-T05 の実行出力
共通答えが出なかった問いが理由付きで残課題にあり、設計で決めるべきものは「設計へ回す」と明示されている各レポートの残課題節

実装フェーズの検証項目

読み取りでは答えが出ず、フェーズ 4 以降で動かして確かめるもの。調査チケットは作らない。

#確かめることどの段で / どう確かめるか
V1boundary.sh status が実際の作業領域と logs/ から正しい現在地を返すか4a の直後。作業中チケットがある状態・無い状態の両方で実行し at_boundary と position を照合
V2session-start が boundary.sh status --offline の出力から注入テキストを組み立てられるか（2/3 で保留した部分）4a の直後。新しいセッションを開いて注入の有無を確認。組み立ての実装が要るなら実装チケットを追加
V3boundary.sh request / complete が実際の MR に対して通るか4a の後の最初の切れ目で 1 回使い、logs/review-state.json が書かれることを確認。失敗したら直接投稿に戻す
V4finalize.sh release の前提検査（FN001）が途中の状態で正しく拒否するか4a の直後。チケットが残っている状態で実行し、FN001 と未充足の列挙が出て片付けが起こらないことを確認
V5finalize.sh release がフェーズ 7 で実際に通るか7。通らなければ手作業で代替し、原因をフィードバック計画へ

リスクと復旧

リスク影響対処・巻き戻し
観点 A の一覧が抜けるフェーズ 4 で作り漏れが出て、受け入れ条件 A1（仕様と 1:1）を満たさない出典の仕様の節を全件に添えることを DoD にする。設計計画（0007）で仕様 19 本の側から突き合わせて漏れを検出する
観点 B の食い違いを調査が独断で解消する調査が実装方針を決めてしまい、設計の判断が形骸化する調査は列挙と「実測に依存するか」の注記まで。解消の判断は 0007 以降に回すことを DoD に書く
0006 のテスト実行が長引く調査が止まる--ids で対象を絞る。全件テスト（10 分前後）は回さない。2 本同時に走らせない
観点 C の grep の除外条件が漏れる参考ディレクトリ/ や logs/ の一致を数えてしまい、0 件の判定が永久に成立しない除外条件込みの検索コマンドをレポートにそのまま書き、V6 で同じものを使う

スコープ外

  • 実測が要る問い（V1〜V7）。この調査では確かめ方の整理までで、実施はフェーズ 4 以降
  • eval の実行。issue のスコープ外で、定義を作るところまで
  • 参考実装（参考ディレクトリ/agent-workflow）の旧スキルの調査。フェーズ 4 で書き方の参考として読むだけ
  • .claude/settings.json の変更。フックの登録 16 行は #9 で完了しており、この issue では触らない
