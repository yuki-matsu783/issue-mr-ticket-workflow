# 0014 AI アセット設計結果 — フック共通仕様の横断決定

## サマリ

0008 の設計計画が割り付けた**決定 9〜15**（および 0012・0013 からの波及）をフック共通仕様に落とした。更新した文書は仕様 5 本・要件 1 本、新規の DDR は 6 件（`i0009-10`〜`15`）。

確定したことは 6 つ。

1. **フックが読む外部データは `.claude/hooks/config/` に集約**する（`assets/` はフック側に作らない）。暫定だった `entry-skills.txt` と `model-aliases.txt` のパスが確定した
2. **§1 の登録表は 17 行**に確定（PreToolUse 7 行目 = `subagent-start-check`）。内訳は SessionStart 1 / UserPromptSubmit 1 / PreToolUse 7 / PostToolUse 4 / SubagentStart 1 / SubagentStop 2 / Stop 1、うち拒否側 5 行
3. **打ち切り（timeout）は fail-open** で、登録ラッパーも `trap ERR` も効かない。フェイルクローズドの原則の**唯一の穴**であることを認め、`timeout` は登録に明示せず「ホットパス 1 秒以内」の目安で守る
4. **`web` は機構が強制しない**（`WebFetch` / `WebSearch` を登録しない）。チケットの `allow.ops` の `web` は意図の記録に留める
5. **`defer` は採用しない**（対話セッションでは無視される）。§12 T3 のうち `defer` の側を閉じ、「`claude -p` を入力から判別できるか」はフェーズ 4c に残す
6. **`scope.sh` の読み込みポリシーを `nop`** にし、失敗の扱いは呼び手のフックが決める。§12 の **T7・T8 を閉じた**（TBD は 8 件 → 実質 5 件）

- ◎良 4 件 / △注意 2 件 / ✕問題 1 件

## レビューしてほしい観点

### ◆特に見てほしい（判断に困っている）

- **f2（✕問題）打ち切りが fail-open であることを「塞がない」と決めた**こと。拒否側フックが打ち切られると素通りする経路が残り、機構の原則（拒否側は判定できなければ拒否へ）が破れる。`timeout` を短くするのは逆効果（素通りを早めるだけ）と判断したが、「速さで守る」以外の手がないという結論に見落としがないか
- **f5（△注意）`scope.sh` を `nop` にした結果、`WF209`（機構の破損）と `WF211`（チケットの記載不正）を戻り値で区別する方法が 0015 に渡る**こと。この区別の設計が失敗すると、拒否側フックが「破損」と「記載不正」を取り違えて誤った回復案内を出す

### ◇承認が欲しい（方針は決めた）

- **f1** 外部データの置き場を `.claude/hooks/config/` に一本化し、フック側に `assets/` を作らないこと（`config/` は `common.confirm` なので新規作成のたびに WF203 の確認が入る）
- **f3** `web` を強制せず意図の記録に留めること（§13「意図的な緩和」に 1 行として載せた）
- **f4** `defer` を採用しないこと

### ・細かいレビューは不要（ほぼ確実）

- **f6** §1 の 17 行への確定・§2（`model` は SessionStart のみ）・§6 台帳の WF801 の持ち主・§12 T4 / T7 の書き換え（0013 の決定をそのまま写しただけ）
- **f7** `WF009` を台帳の先頭行に載せたこと

## 確かめられなかったこと（この結果が言っていないこと）

- **ホットパス 1 秒の目安が実際に守れるか**を測っていない。Windows の git bash で `bash` プロセスの起動がどれだけかかるかは実装フェーズ・4c の実測待ち
- **`.claude/hooks/config/` の新規作成で WF203 が実際に出るか**を確かめていない（`workflow-guard` が未実装のため）。仕様上そうなるという読みに留まる
- **`defer` が対話セッションで警告を出す**ことを実測していない。公式の原文（`hooks.md` L1783 付近）の記載に依拠している
- `scope.sh` を `nop` にしたときに `fm_*` が空を返す**スタブの具体的な形**は決めていない（0015 の担当）
- 打ち切りの fail-open を**実測していない**（600 秒待つ実験はしていない）。公式の Timeouts 節の記載に依拠している

## 実施した内容と結果

### f1. フックが読む外部データを `.claude/hooks/config/` に集約する ◎良

0005 f4 が挙げた未作成 3 本のうち、`entry-skills.txt` と `model-aliases.txt` の基準ディレクトリが未定だった（仕様は `assets/entry-skills.txt` と相対で書いていた）。`assets/` はスキルの規約から借りた書き方で、フックには `assets/` の慣行が無い。

- **決定**: フックが読む外部データはすべて `.claude/hooks/config/`（1 ファイル 1 用途）。現時点で 5 本（`scope-limits.json` / `task-types.tsv` / `blocked-commands.txt` / `entry-skills.txt` / `model-aliases.txt`）。フック側に `assets/` は作らない
- 決め手は `scope-limits.json` の `common.confirm` が既に `.claude/hooks/config/**` を持っていること。置き場が 1 か所なら保護パターン 1 行で全部が守られる
- 副作用を仕様に明記した: `config/` 配下は `common.confirm` に当たるため、**新規作成時に毎回 WF203 の確認が入る**（実装フェーズで驚かないため）
- 反映先: 共通仕様 §1、`workflow-entry` 仕様（呼出条件・WE-T07）、`subagent-start-check` 仕様（制御方式 4 の「暫定」の注記を外した）、`i0009-03` の影響欄

結論: 0013 が「暫定」として残した最重要の申し送りが閉じた。DDR `i0009-10`。

### f2. 打ち切り（timeout）は fail-open で、塞ぐ手段が無い ✕問題

機構はフェイルクローズドを二重に守っている（§1 の登録ラッパー `|| deny` と §3 の `trap ERR`）。0007 f7 で公式の Timeouts 節を読み直した結果、**どちらも打ち切りには効かない**ことが確定した。

- `command` 型の既定タイムアウトは 600 秒。`UserPromptSubmit` に登録されたものは既定 30 秒
- 打ち切られたフックは**出力が破棄され、判定なしとして扱われる**。`PreToolUse` では「A timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call.」
- プロセスごと終了させられるので、`||` も `trap` も走らない

これは**機構の原則が破れる唯一の経路**で、仕様のどこにも書かれていなかった。

- **決定**: §3 に fail-open を原文の引用付きで明記し、「フェイルクローズドの原則の唯一の穴」であると認める。塞ぐ手段は「フックを速く保つ」ことだけ
- §1 に**ホットパス 5 本**（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）の実行時間の目安を **1 秒以内**として置いた
- **`timeout` は登録に明示しない**。短く明示するのは安全側に見えて逆で、「拒否側が判定を諦めて通す確率」を上げるだけ
- 要件（`自己改善ワークフロー機構.md` 例外フロー）にも外部から見える性質として 1 行足した: 打ち切られたときは通る／判定は打ち切りに達しない速さで保つ

結論: **穴があることを仕様に書いた**。塞げないので、実装フェーズと 4c で「速さ」を測ることが唯一の対策になる。DDR `i0009-11`。

### f3. `web`（外部への問い合わせ）は機構が強制しない ◎良

チケットの `allow.ops` の `web` に対応する強制の経路が仕様に無く、「宣言だけあって効いていない項目」だった（決定 14 = D3）。

- **決定**: `WebFetch` / `WebSearch` を `PreToolUse` に登録しない。`web` の宣言は意図の記録に留める
- 理由 3 つ: (1) `scope_classify` はコマンド列を前提にしており `tool_name` だけの入力に同じ分類を当てられない、(2) 外部への問い合わせは副作用が読み取りに閉じ、機構が守る対象（作業領域外への書き込み・コミット / push・進行状態）に当たらない、(3) 宣言と実際の使用がずれてもレビューで気づける
- 止めた場合の害も考慮した。調査タスクは公式ドキュメントの取得が本体で、しかも `Bash` の `curl` という抜け道が残る（`curl` まで止めるのは過剰）
- 反映先: 共通仕様 §8（理由）・§13「意図的な緩和」（1 行）、要件の制約条件（自制に依存する統制の例に追加）

結論: 「強制しない」ことを**明示的な決定として仕様に書いた**（黙って強制しないのとは違う）。DDR `i0009-12`。

### f4. `permissionDecision` の `defer` は採用しない ◎良

0007 f3 で `deny` / `ask` / `allow` に加えて第 4 の値 `defer` があることが分かり、§12 T3 に採否が保留されていた。2 巡目に原本（`hooks.md` L1783 付近）を読み直した結果:

> Claude Code honors this value only in non-interactive mode with the `-p` flag. In interactive sessions it logs a warning and ignores the hook result.

- **決定**: 採用しない。制御方式は `deny` / `ask` / `allow` の 3 値のまま。ヘッドレスでの `ask` は現行どおり `deny` に置き換える
- この機構は対話セッションで動くことを前提にしている（承認ポイント・レビュー依頼・`AskUserQuestion` が骨格）。対話セッションで無視され、しかも警告が出る値を選択肢に加える理由が無い
- §12 T3 は**半分だけ閉じた**。`defer` の採否は閉じ、「`claude -p` を入力から判別できるか」はフェーズ 4c に残す

結論: 受け入れ条件 5 の `defer` の分が閉じた。DDR `i0009-13`。

### f5. `scope.sh` の読み込みポリシーを `nop` にする（T8 を閉じる）△注意

§12 T8 は「案内側フックが `scope.sh` を `source` したとき、`frontmatter.sh` が読めないと deny が出て案内側の原則に反する」を実測待ちにしていた。実測を待つまでもなく矛盾と分かる（`PostToolUse` では `permissionDecision` 自体が無視されるので、誤解を招く記録だけが残る）。

- **決定**: `scope.sh` の読み込みポリシーを **`nop`** に変える。読めなければ `fm_*` が空を返すスタブになり、`scope.sh` 自身は何も出力しない
- **失敗の扱いは呼び手が決める**: 拒否側（`workflow-guard` / `workflow-state-guard`）は自分で deny に倒す（`WF209` / `WF309`）、案内側（`workflow-diff-check` / `subagent-stop-check`）は何も出さずに通す
- 根拠は「失敗ポリシーは呼び手の性格で決まる」。同じライブラリを拒否側と案内側の両方が使う以上、ライブラリ側が一律のポリシーを持つ設計そのものが誤り
- **0015 へ送った部分**: `frontmatter.sh` 不在（機構の破損 → `WF209`）とチケットの記載不正（→ `WF211`）を**戻り値で区別する方法**は `20-common-step-shell-script` 仕様が定める。空の `fm_*` だけでは区別できない

結論: T8 を閉じたが、**回復案内の正しさは 0015 の設計に依存する**。DDR `i0009-14`。

### f6. §1 が 17 行に確定し、§2・§3・§6・§12 T4 / T7 を 0013 の決定に揃えた ◎良

0013 の申し送り（最重要）をそのまま反映した。

- **§1**: `subagent-start-check` の PreToolUse `Agent` を **7 行目**として追加し、**全 17 行**（フック 11 本 + 複数登録 6 行）と内訳・拒否側 5 行を本文に明記した。`subagent-start-check` 仕様の「16 行 → 17 行になる（確定は 0014）」も確定形に直した
- **§2**: `SubagentStart` の入力から `model` を削り、「公式は『Only `SessionStart` hooks can receive a `model` field』と明記」を根拠として書いた
- **§3**: 「メインへの通知（サブエージェント**起動前**）」の行を足し、PreToolUse の `additionalContext` の形と「`permissionDecision` は出さない」を明記した
- **§6**: WF801–809 の持ち主欄を「PreToolUse `Agent` = WF801 / SubagentStart = WF802、`subagent-stop-check` の再掲は事後の保険」に書き換えた
- **§12 T4**: 「`model` は来ない」を確定として書き、残る検証を「実物に `model` が無いこと」「PreToolUse の `additionalContext` が届くこと」に絞った。縮退（届かなければ 16 行に戻る）も書いた
- **§12 T7**: 「終了コードのフィールドは存在しない」で閉じた（打ち消し線 + 解決の明記）。`PostToolUseFailure` は登録しない

結論: 0012・0013 と共通仕様の食い違いが解消した。HK-T01 はこの 17 行との行単位の照合として書ける。

### f7. `WF009` を採番台帳に載せ、横断文書は要件 1 本のみ更新した △注意

- **`WF009`**: 0005 f2 が挙げた「23 ファイルで使われているのに台帳に無い」問題。**共通ライブラリ（`hook-common.sh` / `scope.sh` の読み込み行）**の既定として台帳の先頭行に登録し、「フックはこの番号を自分で出さない（読み込み行より前に `HOOK_DENY_ID=WFx09` を代入する）」を明記した。番号を `WF099` に変える案は 23 ファイルの書き換えに見合わないので却下。運用上、**`WF009` が出たら代入忘れ**というシグナルになる（DDR `i0009-15`）
- **横断文書**: 0012・0013 はいずれも「対象なし」だったが、今回は `00_requirement/自己改善ワークフロー機構.md` に **2 か所**足した。例外フローに「打ち切られたら通る／速さで保つ」（f2）、制約条件の自制に依存する統制の例に「チケットが宣言した外部への問い合わせの範囲」（f3）。いずれも**外部から見える性質**として書き、内部構造（`timeout` の秒数・matcher・フック名）は書いていない
- `.claude/rules/ルール体系.md` は対象なし（ルールの増減なし）。`90_glossary/ワークフロー用語.md` も対象なし（概念 20 語のみで、`timeout` や `defer` のような実装用語を収録していない）

結論: 要件書に手を入れたのは、書かないと要件が**偽のこと**（可用性「拒否側は依存が壊れたとき拒否へ」）を主張したままになるため。

## 想定と異なった点

| 計画時の見込み | 実際 | どう扱ったか |
|---|---|---|
| 決定 10（`timeout` の既定）は「登録に何秒と書くか」を決めるだけ | 打ち切りが **fail-open で二重の守りがどちらも効かない**ことが分かり、`timeout` を書くこと自体が有害だと判明した | f2 として「明示しない + 速さで守る」に方針を変え、穴があることを仕様と要件の両方に書いた |

| 横断文書は 0012・0013 と同じく「対象なし」で済む | 要件の可用性・制約条件が f2・f3 の決定と食い違っており、**放置すると要件が偽のことを主張する**状態だった | f7 として要件に 2 か所だけ、外部から見える性質として足した |

## 残課題

- **打ち切りの fail-open は塞げない**。ホットパス 5 本の実行時間をフェーズ 4c で測り、1 秒を超えるものがあれば判定を軽くする以外の対策が無い
- `WF209` と `WF211` を戻り値で区別する方法が決まらないと、`scope.sh` を `nop` にした利益（案内側の原則との整合）と引き換えに回復案内の精度が落ちる（0015）
- `.claude/hooks/config/` の新規作成で WF203 が出ることは仕様上の読みであり、`workflow-guard` の実装後に確かめる必要がある
- §12 の TBD は T7・T8 が閉じても **6 件が実測待ち**で残る。4c で全部を確かめられるかは 0016 の実装計画の見積もり次第
- 共通仕様が 269 行から増え続けている。§1 だけで登録表 17 行 + 説明 6 行になり、「差分だけを書く」ための前提文書としては読む負荷が上がっている。分割の要否は振り返りフェーズで扱う
