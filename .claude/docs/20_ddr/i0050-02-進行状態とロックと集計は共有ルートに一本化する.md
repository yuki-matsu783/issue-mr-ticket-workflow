# i0050-02. 進行状態とロックと集計は共有ルートに一本化し、判定記録と実行ログは作業ツリー側に残す

## 背景

`i0009-55` は「worktree では `cwd` 側の作業ツリーを採る」と決め、あわせて「`logs/` と `wip/` は作業ツリー側に置く（worktree ごとに進行状態が分かれる）」と書いた。作業ツリーの解決そのものはこの決定のとおりでよい（実測で確定している）が、`logs/` を丸ごと作業ツリー側に置いたことが、worktree を使った瞬間に次を起こすことが実測で分かった。

- 新しい作業ツリーには `logs/` が無いので、振り分けの宣言の記録が読めず、宣言済みのセッションでも未宣言として拒否される
- 未記載パスの承認の記憶も無いので、同じセッションでも承認を取り直すことになる
- MR・レビュー・マージの進行状態が読めず、切れ目の処理が「MR が無い」状態として動く
- ロック（`logs/locks/`）と使用量の集計（`logs/usage/<branch>.json`）が作業ツリーごとに分かれ、同じブランチに対する排他も集計も成立しない

一方で、判定の記録（`logs/hooks/decisions.jsonl`）と実行ログ（`logs/sh/`）は「どの作業ツリーで何が起きたか」の記録であり、共有ルートへ寄せると、どちらの作業ツリーの判定だったかが分からなくなる。

## 決定

- **`logs/` の中身を、置き場の性質で 2 つに分ける。**
  - **共有ルート**（本リポジトリでは本流のチェックアウト）に置く: `mr.json` / `review-state.json` / `review-history.jsonl` / `merge-state.json` / `locks/` / `usage/<branch>.json` / `sessions/<session_id>/`（宣言・承認の記憶）/ `push-state.json`
  - **作業ツリー側**に残す: `hooks/decisions.jsonl` / `sh/<name>.log`
- **フックは根を 3 つに分ける**（`HOOK_ROOT` = スクリプトと設定の置き場 / `HOOK_WORKTREE` = 判定対象の作業ツリー / `HOOK_SHARED_ROOT` = 共有ルート）。共有ルートの値は `HOOK_ROOT` と同一に固定し、環境変数や設定からの上書きは受け付けない
- **判定の記録に `cwd`（判定時の作業ツリー）と `agent_id`（サブエージェントの識別。メインなら空）を足す。** 合流後に 1 本の履歴として読むときに、どの作業ツリーの、メインかサブエージェントかを区別できるようにする

## 理由

- 進行状態は「issue と MR に属する」情報で、issue も MR もブランチも 1 つしか無い。作業ツリーごとに分ける意味が無く、分けると上の 4 つの不具合がそのまま出る
- ロックと集計は「ブランチ単位の資源」に対する排他と加算なので、資源が 1 つなのに置き場を分けると、排他も集計も定義できなくなる
- セッションの記憶（宣言・承認）は `session_id` で分離されており、作業ツリーで分ける必要が無い。むしろ共有ルートに置けば、同じセッションが作業ツリーを移っても宣言と承認がそのまま効く
- 判定記録と実行ログだけは作業ツリーごとの事実なので、寄せずに残し、`cwd` / `agent_id` を足して合流後も切り分けられるようにするほうが情報が増える
- **共有ルートを外から差し替えられる口を開けない**のは、進行状態の置き場を動かせることが、進行状態ファイルの保護（`workflow-state-guard`）の対象そのものを外から外せることを意味するため。名前だけを別に持てば、別 clone を扱う判断が要るときに値の解決だけを変えられる

## 却下した案

- **`.worktreeinclude` で `logs/` を丸ごと作業ツリーへ複製する**: 進行状態が作業ツリーの数だけ増える。どれが正かの規則が新たに要り、記録が issue をまたいで使い回される既存の問題（`mr.json` に issue・ブランチのキーが無い）が作業ツリーの数だけ再生産される
- **作業ツリーごとに `logs/` を空から初期化する**: 宣言と承認を作業ツリーのたびに取り直すことになる。ユーザーが応答できない実行形態では承認を取れないので、そこで詰む
- **`logs/` を丸ごと共有ルートへ寄せる**: 判定記録と実行ログが 1 本に混ざり、どの作業ツリーの判定だったかを後から切り分けられない。並列で走った 2 つの作業ツリーの記録が交互に並ぶだけになる
- **共有ルートを環境変数で指定できるようにする**: 別 clone を使う運用に開けるが、進行状態の保護対象を環境変数 1 つで外側へ逃がせることになり、拒否側の保護が無効化できる形になる

## 影響

- `10_spec/フック共通仕様.md` の §2（作業ツリーの三分・作業ツリーをまたぐパスの畳み込み）と §5（記録と状態の置き場の表・`decisions.jsonl` のスキーマ）を書き換える。テストは HK-T06（記録のスキーマ）と HK-T21（三分の解決）で固定する
- `i0009-55` の「作業ツリーの解決順」と「スクリプトの置き場は常に `HOOK_ROOT`」は有効なまま。無効になるのは「`logs/` と `wip/` は作業ツリー側に置く」のうち `logs/` の部分だけで、`wip/` は作業ツリー側のままである
- 進行状態を共有ルートに置くことで、`workflow-state-guard` の保護対象のパスは共有ルート基準になる（作業ツリーをまたぐ絶対パスの扱いは `i0050-07` と同じ改修で閉じる）
