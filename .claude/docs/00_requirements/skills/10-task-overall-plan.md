# 10-task-overall-plan スキル

## 概要

`00-workflow-issue-mr-driven` のタスクループの先頭で、依頼を issue に結び付け、ブランチと draft MR を用意し、issue の受け入れ条件からその issue をどう進めるかを決める全体計画タスクの要件を定義する。`00-workflow-issue-mr-driven` は全体計画チケットを作業中に置いてこのタスクを呼ぶだけであり、issue の確定・ブランチと MR の作成・全体計画書の作成と合意・最初の計画チケットの作成・全体計画チケットの完了までをこのタスクがメインエージェントで行う。本書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

- **背景**: 作業の起点を issue に固定するには「どの issue に対する作業か」を最初に確定し、以降の成果が載る MR を用意する必要がある。またタスクの種類は 15 種あり、issue ごとにどのフェーズを使うか・誰（どのモデル）が実施するか・どこで人間が見るかが変わる。これらを実施しながら決めると、issue との対応や レビューの省略・モデルの選択が AI の裁量になり、後から追えない。着手前に 1 か所で決めてユーザーと合意し、以降のタスクはその方針に従って動く。
- **目的**: 依頼を 1 issue = 1 ブランチ = 1 MR に結び付け、issue の種別に応じたテンプレートからフェーズ列を組み、各タスクの実行者・人間レビュー要否・やってよいことの方針を全体計画書として残し、合意のうえで次のタスク（調査計画）へつなぐ。
- **スコープ**:
  - 含む: 対象 issue の確定（既存 issue の検索・追記・新規起票）、feature ブランチと draft MR の作成、全体計画書の作成、issue の種別の判定とテンプレートの適用、受け入れ条件と各フェーズの対応付け、実行者とレビュー要否の方針、最初の計画チケットの作成、全体計画チケットの完了、再開時の扱い
  - 含まない: 全体計画チケットの作成と完了後の切れ目の処理（`00-workflow-issue-mr-driven`）、issue・ブランチ・MR を操作する個々の手順（common-step スキル）、各フェーズの計画書とチケット群の作成（各計画タスク）、フィードバック計画より後のフェーズの要否の決定（`10-task-feedback-plan`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 依頼がどの issue に対応するのかを最初に確定し、着手前に、どのフェーズをどのモデルで進め、どこで自分がレビューするかを 1 枚の計画で確認して合意したい。

**[So that]** 作業が必ず issue と MR に紐づき、進め方を最初に握って、途中でレビューが抜けたり想定外のモデルで作業されたりしないため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー: issue の確定

- When このタスクに入ったとき、Shall スキルは全体計画チケットが作業中であることを前提に、メインエージェント自身で進めなければならない（サブエージェントに委ねない）。
- When 依頼を受けたとき、Shall スキルは `glab`（GitHub では `gh`）で open な issue から類似のものを検索して提示し、なければ closed な issue も検索して過去の類似事例として提示しなければならない。
- When 類似の open な issue が見つかったとき、Shall スキルはその issue の内容（目的・受け入れ条件・やらないこと）を提示し、その issue で進めるか新規に起票するかの承認を得なければならない（承認①）。
- When 既存の issue で進めることになり、その issue の記述が計画を立てるのに十分なとき、Shall スキルは追記の案を出さず、確認も求めずにブランチの作成へ進まなければならない。
- When 既存の issue で進めることになり、受け入れ条件やスコープが不足しているとき、Shall スキルは不足を補う追記案を提示し、ブランチ名・MR タイトルと合わせて承認を得てから追記しなければならない（承認②）。既存の記述を書き換えず、追記として残す。
- When 類似の open な issue が無いとき、Shall スキルは新規 issue の案（タイトル、目的・背景、受け入れ条件、やらないこと）をブランチ名・MR タイトルと合わせて提示し、承認を得てから起票しなければならない（承認②）。
- When issue を新規に起票するか追記するとき、Shall 本文はコマンドライン引数に直接埋め込まず `wip/tmp/` に置いたファイルから渡し、受け入れ条件は後のフェーズで DoD に落とせる粒度で書かなければならない。
- When 依頼または issue の主目的がアプリと AI アセットの両方にまたがるとき、または複数の独立した成果を含み 1 つの MR に載せると大きすぎるとき、Shall スキルは issue の分割案（既存 issue なら残りを別 issue として起票する案）を提示して承認を得、このセッションで扱う 1 つを決めなければならない（残りは起票だけして着手しない）。

### メインフロー: ブランチと draft MR の作成

- When 対象 issue が確定したとき、Shall スキルは default ブランチの最新から `feature-<issue番号>-<slug>`（不具合修正は `fix-<issue番号>-<slug>`）のブランチを作り、切り替えなければならない。
- When ブランチを作ったとき、Shall スキルは issue へのリンクを含む本文で draft MR を作成し、issue 番号・ブランチ名・MR 番号と URL をユーザーに報告しなければならない。
- When draft MR を作るのに default ブランチとの差分が無いとき、Shall スキルは空コミットを作って push してから再試行しなければならない。
- When issue・ブランチ・MR の操作を行うとき、Shall スキルは対応する common-step スキルの手順（提供コマンド）に従い、`git commit` / `git push` を直接実行してはならない。

### メインフロー: 全体計画の作成と合意

- When issue の種別を判定するとき、Shall スキルは受け入れ条件と変更対象から「アプリ（`docs/`・ソースコードが主目的）」「AI アセット（`.claude/` 配下が主目的）」のどちらかを判定し、根拠とともに提示しなければならない（「両方」という種別は置かない。両方にまたがる issue は確定の段階で分割する）。
- When フェーズ列を組むとき、Shall スキルは種別ごとのテンプレート（`00-workflow-issue-mr-driven.md`「タスクの構成」）を土台に、調査とフィードバック計画を必ず含め、主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット実装・テスト）は依頼の性質に応じて含め、フィードバック計画より後のフェーズは含めないまま（フィードバック計画で決める）にしなければならない。
- When 主作業のフェーズを含めるか迷うとき、Shall スキルは含める側に倒し、やることが無ければ計画タスクで「対象なし」として即座に完了する前提にしなければならない（全体計画の段階で「やらない」と決めない）。
- When 実行者とレビュー要否の方針を決めるとき、Shall スキルはタスクの種類ごとに既定の実行者（モデル）と人間レビュー要否（理由付き）を提案し、リスクの高いタスク（実装・テスト実施、AI アセット実装・テスト実施など）は人間レビュー要を既定としなければならない。
- When 既定の実行者とレビュー要否を提案するとき、Shall スキルはプロジェクトにタスクの種類ごとの既定の判断基準（`.claude/rules/` のルールとして定義。既定の実行者・人間レビュー要否とその理由・調整してよい条件）が置かれていればそれを基準にし、issue の性質に応じた調整を基準との差分として理由付きで示さなければならない。基準が無ければスキルの既定を使い、その旨を全体計画書に書く。
- When やってよいことの方針を決めるとき、Shall スキルはタスクの種類ごとに書き込んでよい範囲と実行してよい操作の分類を、機構が定める上限の中で提案しなければならない。
- When 全体計画書の案ができたとき、Shall スキルはそれをユーザーに提示し、フェーズ列・実行者・レビュー要否・やってよいことの方針について合意を得なければならない（承認③）。合意前に次の計画チケットを作ってはならない。
- When 合意が得られたとき、Shall スキルは最初の計画チケット（調査計画）を 1 枚だけ未着手に作らなければならない。以降のチケットは各計画タスクが連鎖的に起こす。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: タスクの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと（書き込んでよい範囲・実行してよい操作の分類）、目的、完了条件（DoD）。DoD は issue の受け入れ条件から導く。
- When 全体計画チケットを完了するとき、Shall 全体計画書と最初の計画チケットが存在し、合意の内容が全体計画書に記録され、作業ログが機構のチケットテンプレートの項目に沿って書かれ、必須項目（AI アセットに反映すべき内容。0 件なら根拠）が埋まっていなければならない。完了は提供コマンドで行い、必須項目が欠けていれば完了は拒否される。
- When 全体計画チケットを完了したとき、Shall スキルは `00-workflow-issue-mr-driven` に制御を戻し、タスクの切れ目の処理（push・MR 本文への全体計画の要約の追記・レビュー要否に応じたレビュー依頼）はそちらが行う。

### 代替フロー

- If ユーザーが issue 番号または URL を指定した場合、Then スキルは類似 issue の検索を省いてその issue を取得し、内容を提示して確定しなければならない（記述が十分なら追記の確認は求めない）。
- If 類似の issue が closed のものしか無い場合、Then スキルはそれを過去の事例として提示し、新規に起票するか対応なし（過去の結論を採る）かを確認しなければならない。closed な issue は再オープンしない。
- If ユーザーが「対応なし」を選んだ場合、Then スキルはブランチと MR を作らず、`00-workflow-issue-mr-driven` に「対応なし」で終わったことを返さなければならない（全体計画チケットの取り消しはそちらが行う）。
- If ユーザーが issue の起票だけを指示し着手の指示が無い場合、Then スキルは起票と報告で止まり、ブランチと MR を作らず指示を待たなければならない。
- If 再開時に同じブランチに draft MR と全体計画書が既にある場合、Then スキルは issue の確定とブランチ・MR の作成をやり直さず、既存の計画を提示して続きから進めなければならない。
- If 依頼が `00-workflow-quick-request` の振り返りから切り替えて来たものである場合、Then スキルは引き継がれた issue（起票済み）・issue 種別（AI アセット）・フェーズ列をそのまま土台にし、issue の検索は省き、合意は改めて取らなければならない。
- If 受け入れ条件が曖昧で対応付けができない場合、Then スキルは不足を指摘し、承認②の手順で issue に追記してから計画を続けなければならない。

### 例外フロー

- If `glab` / `gh` が未導入または未認証の場合、Then スキルは導入・認証の手順を案内して停止し、WebFetch / curl で代替してはならない。
- If `origin` が GitLab / GitHub のリポジトリでない場合、Then スキルは対象外として報告し停止しなければならない。
- If 未コミットの変更がある状態でブランチを作ろうとした場合、Then スキルは変更内容を提示し、コミット / stash / 破棄 / 中断のいずれにするかを確認してから進めなければならない（黙って持ち越さない）。
- If issue・MR の作成や追記に失敗した場合、Then スキルはエラー内容を報告して停止し、再試行や別手段での代替を自動で行ってはならない。
- If ユーザーが合意を保留・却下した場合、Then スキルは計画を修正して再提示し、合意が得られるまで計画チケットを作ってはならない。
- If ユーザーが応答できない実行形態で承認①②③のいずれかが取れない場合、Then スキルは案（issue 案・全体計画書の案）をコミットせずに報告し、セッションを終えなければならない（承認なしに起票・ブランチ作成・計画チケット作成をしない）。
- If 全体計画チケット以外のチケットが既に存在する場合、Then スキルは状態の不整合として報告し、ユーザーの指示を待たなければならない。

### 全体計画書の内容

- When 全体計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、issue の種別（アプリ / AI アセット）とその根拠、採用したフェーズ列（テンプレートとの差分と理由）、受け入れ条件と各フェーズの対応（どの条件をどのフェーズが満たすか）、タスクの種類ごとの実行者（LLM モデル）と人間レビュー要否の方針、タスクの種類ごとの「やってよいこと」の方針、判断を保留した点。
- When 全体計画書を書くとき、Shall 「これから何をするか」だけを書き、実施結果や経過を書いてはならない。
- When 全体計画書を置くとき、Shall 作業領域の全体計画の置き場に 1 issue につき 1 つだけ置き、HTML ビューは作らない。

### 承認ポイント

- 承認①: 類似の open な issue で進めるか、新規に起票するか
- 承認②: issue への追記案または新規 issue 案（ブランチ名・MR タイトルと同時）
- 承認③: 全体計画書（フェーズ列・実行者・レビュー要否・やってよいことの方針）
- When 承認①②③のいずれかで却下されたとき、Shall スキルはその段階に留まって案を修正し、先の段階（ブランチ作成・計画チケット作成）へ進んではならない。

### 全体計画チケットの扱い

- When 全体計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は全体計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みと、issue・ブランチ・MR の作成と push を含み、それ以外のファイル（ソースコード・設計文書・`.claude/` 配下）を書けてはならない。
- When 全体計画チケットの人間レビュー要否を決めるとき、Shall 既定は「不要」（合意はチャットで取り全体計画書に記録するため）とし、ユーザーが MR 上でも計画を確認したい場合は「要」にできなければならない。

## 前提条件

- 対象プロジェクトが GitLab または GitHub 上の Git リポジトリで、`origin` がそこを指していること
- `00-workflow-issue-mr-driven` が全体計画チケットを作業中に置いてからこのタスクを呼ぶこと
- タスクの種類ごとの上限（書き込んでよい範囲・操作の分類）が機構の設定として定義されていること
- 実行者として指定できるモデルは、サブエージェントで選択できるモデルに限ること
- タスクの種類ごとの既定の判断基準（実行者・レビュー要否）のルールは任意。置かれていればそれを基準にし、無ければスキルの既定を使う

---

## 制約条件

- **技術的制約**: GitLab（`glab` CLI）を基準に記述し、GitHub では MR → PR、`glab` → `gh` に読み替える。全体計画はメインエージェントが行う（人間との合意が要り、サブエージェントはユーザーと対話できないため）。全体計画書は 1 issue に 1 つ。1 セッションで確定する issue と MR は 1 つ
- **ビジネス的制約**: issue の内容・フェーズ列・実行者・レビュー要否の方針は人間が決める。スキルは案を出し、承認なしに確定しない
- **外部的制約**: フィードバック計画より後のフェーズの要否は全体計画では決めない。closed な issue は再オープンしない

## 非機能要件

| 項目 | 説明 |
|------|------|
| セキュリティ | issue・MR の本文に環境変数の値・トークン・個人情報を書かない。投稿本文の一時ファイルは `wip/tmp/`（コミット対象外）に置き、ワークスペース外のパスを使わない |
| 追跡性 | ブランチ名・MR 本文・全体計画書に issue 番号が残り、全体計画書に MR 番号・合意の内容（誰が・いつ・何に合意したか）が残る |
| 一貫性 | フェーズの名前・順序・テンプレートは `00-workflow-issue-mr-driven.md`「タスクの構成」と一致する。チケットの記載事項は他の task スキルと同じ |
| 性能 | 類似 issue の検索は open / closed それぞれ 10 件程度の提示に留め、全件を読み込まない |
| 可用性 | リモートに到達できないときはローカルで案（issue 案・計画案）を作るところまで進め、起票・ブランチ・MR の作成は到達できてから行う |
| 簡潔性 | 全体計画書は 1 画面程度で読める分量にし、詳細は各フェーズの計画書に委ねる |
| 冪等性 | 再開時に issue・ブランチ・MR・全体計画書・チケットを二重に作らない |
