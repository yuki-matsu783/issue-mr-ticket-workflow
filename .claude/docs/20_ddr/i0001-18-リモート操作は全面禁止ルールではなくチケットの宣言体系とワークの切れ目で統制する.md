# i0001-18. リモート操作は全面禁止ルールではなく、チケットの宣言体系とワークの切れ目で統制する

## 背景

参考実装 agent-workflow はチケット作業中の `gh` と push をフックで一律にブロックし（リモート操作はチケットの外で行う）、本機構も当初「全体計画チケット以外のチケットが作業中のときは `glab` / `gh` と push を禁止」と書いていた。しかし要件を書き進めると、フィードバック計画（承認済み別 issue の起票）と全体まとめ（別 issue 起票・issue コメント・衝突解消・push・draft 解除）はチケットの作業中にリモート書き込みが必要で、例外のつぎはぎになった。再開時の現在地導出など読み取り系の操作も、一律禁止では実態と合わない。

## 決定

- **読み取り系**（issue / MR の参照・レビューの取得・状態の確認）は、チケットの状態によらずいつでも行える
- **書き込み系**（push・issue の起票・追記・コメント・MR の作成・編集・draft 解除）は、次の 2 つの経路でのみ行える
  1. ワークの切れ目の処理（push・MR 本文更新・レビュー依頼と完了。作業中のチケットが無い状態で行われる）
  2. 作業中のチケットの「やってよいこと（実行してよい操作の分類）」に宣言された操作。宣言は機構がワークの種類ごとに定める上限（i0001-02）を超えられない
- 既定でリモート書き込みを宣言するのは 3 つのチケットだけ: **全体計画**（issue の確定・ブランチと MR の作成・push）、**フィードバック計画**（承認を得た別 issue の起票のみ）、**全体まとめ**（別 issue の起票・MR への添付・衝突解消の取り込み・push・draft 解除）
- 「全体計画チケット以外は禁止」という特定チケット基準の全面ルールは置かない。push 前チェックの「作業中のチケットが無い」も、push を宣言したチケットの作業中は例外とする

## 理由

- 統制したいのは「統制外の外部への副作用」であり、「特定チケット以外の glab/gh」ではない。禁止の軸をチケット名にすると、リモートが要るワークを追加するたびに例外が増える
- チケットには既に「やってよいこと（書き込んでよい範囲・実行してよい操作の分類）」と type ごとの上限があり、ファイル書き込みと同じ枠組みでリモート書き込みを扱えば、要件・フック・レビューの見え方が一本化される
- 読み取りは副作用が無く、再開時の現在地導出・レビュー状況の確認に常時必要。禁止する理由が無い

## 却下した案

- **特定チケット以外は禁止 + 例外を列挙（当初案 / 参考実装方式）**: 実装は単純だが、フィードバック計画・全体まとめで既に破綻し、例外の列挙が宣言体系と二重管理になる
- **リモート書き込みを常にワークの切れ目まで遅延させる**: 統制は強いが、フィードバック計画で合意した別 issue の起票が切れ目までずれ、合意と操作の間に距離ができて忘れやすい。全体まとめの手順（起票 → 衝突解消 → … → draft 解除）も切れ目に押し出せない
- **リモート書き込みを自由にし、レビューで見る**: 統制が事後になり、取り消せない外部への副作用（issue コメント等）に合わない

## 影響

- `00-workflow-issue-mr-driven.md` の整合節（読み取り / 書き込みの 2 項目に書き換え）、`10-work-feedback-plan.md`・`10-work-overall-plan.md` の「やってよいこと」
- 要件定義書 E 節の push 前チェック（「作業中のチケットが無い」に宣言例外を追記）
- i0001-09 の「全体計画チケットの作業中に限り行える」は、宣言体系による表現に置き換えた
- フックの仕様: リモート書き込みの検知は「切れ目の処理か、作業中チケットの宣言にあるか」で判定する（仕様で定める）
