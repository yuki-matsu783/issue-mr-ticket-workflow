# 10-task-feedback-plan スキル

## 概要

フィードバック計画タスクの要件を定義する。主作業（実装・テスト、または AI アセット実装・テスト）が終わった位置で、ここまでの全チケットの作業ログ・レビュー指摘・拒否と確認の記録を振り返って改善候補を洗い出し、候補ごとに「この MR で対応する」（既定）か「別 issue として起票する」かをユーザーと対話しながら決め、後続フェーズ（設計反映・AI アセット設計・AI アセット実装・テスト）の要否を確定してチケットを作成・修正する。振り返りの機会は 1 issue につきこの 1 回だけ。メインエージェントが行う（承認・対話が多いため）。

- **背景**: 作業の中で見つかった「うまくいかなかったこと」「AI アセットに反映すべき内容」は、チケットの作業ログに散らばったまま放置されると次の issue でも同じ失敗を繰り返す。一方で振り返りを何度も挟むと MR が終わらない。振り返りを 1 か所に固定し、洗い出しから後続チケットの確定までを人間と一緒に一度で行いたい。
- **目的**: 全チケットの記録だけから改善候補を漏れなく洗い出し（候補 0 件ならその根拠を残し）、対応先と後続フェーズをユーザーと合意し、以降のタスクが迷わず進める状態（後続チケットが揃った状態）を作る。
- **スコープ**:
  - 含む: 改善候補の洗い出しと分類、候補ごとの対応先（この MR / 別 issue）の合意、後続フェーズの要否の決定とチケットの作成・修正、別 issue の起票、未着手チケットの見直し、フィードバック計画書の作成、フィードバック計画チケットの着手から完了まで、再開時の扱い
  - 含まない: 改善の実施（設計反映・AI アセット設計・AI アセット実装・テストの各タスク）、フィードバック計画より前のフェーズ列の決定（`10-task-overall-plan`）、フィードバック計画より後に見つかった候補の扱い（全体まとめで別 issue）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** ここまでの作業で溜まった気づき・指摘・失敗を一度にまとめて振り返り、どれをこの MR で直し、どれを別 issue に回すかを対話で決めたい。

**[So that]** 同じ失敗を次の issue で繰り返さず、AI アセットと設計書が作業のたびに育ち、かつ MR が振り返りの繰り返しで肥大しないため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルはメインエージェント自身で実施し、サブエージェントに委ねてはならない（対応先の決定に人間との対話が要るため）。
- When フィードバック計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 改善候補を洗い出すとき、Shall スキルはこの issue の全チケットの作業ログ（うまくいかなかったこと・仕様からの逸脱・判断と根拠・拒否・確認・迂回の記録・使った AI アセットと効き目・スコープ外で見つけたこと・AI アセットに反映すべき内容）、MR のレビュー指摘、各レポートの「想定と異なった点」「残課題」、この issue で使った AI アセット（スキル・フック・ルール・エージェント・`CLAUDE.md`）を入力にし、記憶ではなく記録から洗い出さなければならない。
- When 改善候補を分類するとき、Shall 「足りなかった / 邪魔だった / 無かった / 問題なし」の観点と、「(a) アセットが無かった / (b) あったが誤っていた / (c) あったが罠が書かれていなかった / (d) あったのに辿り着けなかった」の類型で整理し、候補が 0 件のときも 0 件である根拠をフィードバック計画書に残さなければならない。
- When 改善候補の反映先（どのアセット・どの文書に効かせるか）を考えるとき、Shall 「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）」と「守らせ方（読ませる / 手順化する / 機械的に拒否する）」の 2 軸で選び、常時読み込まれるアセットを増やすコストを考慮しなければならない。
- When 候補ごとの対応先を決めるとき、Shall スキルは「この MR で対応する」を既定とし、変更が大きくなりすぎる場合に限り「別 issue として起票する」を提案し、候補の一覧・分類・提案をユーザーに提示して対話で合意しなければならない。合意前に後続チケットを作ってはならない。
- When 対応先が合意されたとき、Shall スキルは後続フェーズ（設計反映 / AI アセット設計 / AI アセット実装・テスト。issue の種別に応じたテンプレートの範囲）を含めるかを確定し、含めるフェーズの最初の計画チケットを 1 枚未着手に作らなければならない（後続フェーズが無ければ全体まとめのチケット）。
- When 別 issue として起票すると合意された候補があるとき、Shall スキルは issue の本文案を提示して承認を得てから起票し、起票した issue の番号をフィードバック計画書に記録しなければならない。
- When 未着手のチケットが残っているとき、Shall スキルは振り返りの結果に合わせてそれらを見直してよく（範囲・実行者・レビュー要否・DoD）、変更した内容をユーザーに伝えなければならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し、完了時にまとめて書いてはならない。
- When フィードバック計画チケットを完了するとき、Shall フィードバック計画書（候補の一覧・分類・対応先の合意・起票した issue・後続フェーズの決定）と次のチケットが存在し、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When フィードバック計画チケットを完了したとき、Shall スキルは `00-workflow-issue-mr-driven` に制御を戻し、タスクの切れ目の処理はそちらが行う。

### 代替フロー

- If 改善候補が 0 件だった場合、Then スキルは 0 件である根拠（確認した記録の範囲）をフィードバック計画書に書き、後続フェーズを含めずに次のチケット（全体まとめ、またはテンプレートで残るフェーズの計画チケット）を作って完了しなければならない。
- If 候補がすべて「別 issue」になった場合、Then スキルはこの MR の後続フェーズを含めず、起票を済ませて次のチケットを作って完了しなければならない。
- If 再開時にフィードバック計画チケットが作業中で候補の一覧が途中まである場合、Then スキルは作業ログの「現在地」から続きを進め、済んだ合意をやり直してはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは候補の一覧と後続チケットを見直し、変更を対話で合意し直さなければならない（完了済みチケットは戻さない）。

### 例外フロー

- If ユーザーが応答できない実行形態で対応先の合意が取れない場合、Then スキルは候補の一覧と提案を報告してセッションを終えなければならない（合意なしに後続チケットの作成・別 issue の起票をしない）。
- If 別 issue の起票が承認されなかった場合、Then スキルはその候補を「この MR で対応」に戻すか「対応しない（理由を記録）」にするかを確認し、フィードバック計画書に残さなければならない。
- If issue の起票に失敗した場合、Then スキルはエラー内容を報告して停止し、別の手段で代替してはならない。
- If フィードバック計画より後のタスクで新たな改善候補が見つかった場合、Then not このタスクには戻らず、全体まとめの別 issue 起票で扱う（振り返りは 1 回だけ）。

### フィードバック計画書の内容

- When フィードバック計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、改善候補の一覧（出どころの記録・観点・類型・反映先の 2 軸）、候補ごとの対応先（この MR / 別 issue / 対応しない）とその合意、起票した issue の番号、後続フェーズの決定と作成・修正したチケットの一覧、候補 0 件の場合はその根拠。
- When フィードバック計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### フィードバック計画チケットの扱い

- When フィードバック計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みと、承認を得た別 issue の起票に限り、ソースコード・設計文書・`.claude/` 配下を書けてはならない。
- When フィードバック計画チケットの人間レビュー要否を決めるとき、Shall 既定は「不要」（合意は対話で取り、フィードバック計画書に記録するため）とし、ユーザーが MR 上でも確認したい場合は「要」にできなければならない。

### 他のスキル・機構との整合

- When 後続フェーズのチケットを作るとき、Shall チケットの記載事項・DoD の型は各フェーズの task スキルの要件に従い、実行者・レビュー要否は全体計画の方針（とタスク別の既定判断基準）に従わなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When 分類の観点・類型の文言を使うとき、Shall 機構の定義（振り返りの観点と類型）と一致させ、独自の分類を増やしてはならない。

## 前提条件

- 全体計画のフェーズ列でフィードバック計画の位置（主作業の後）が決まっており、直前のタスクの切れ目の処理が済み、フィードバック計画チケットが未着手にあること
- メインエージェントで実行されること（サブエージェントからは呼ばれない）
- 計画書・チケットのテンプレートと提供コマンド、issue を起票する common-step スキルが用意されていること

---

## 制約条件

- **技術的制約**: 対話が必要なためメインエージェントが行う。振り返りは 1 issue に 1 回。計画書は 1 つ
- **ビジネス的制約**: 候補の対応先（この MR / 別 issue / 対応しない）は人間が決める。スキルは記録から候補と提案を揃えるまで
- **外部的制約**: リモート操作は承認を得た別 issue の起票に限る（push・MR 更新はタスクの切れ目で呼び出し元が行う）。`.claude/` 配下の変更はここでは行わず、後続の AI アセットのフェーズで行う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 改善候補ごとに出どころの記録（チケット・指摘・レポート）と対応先の合意が辿れ、別 issue は番号で結ばれる |
| 一貫性 | 分類の観点・類型・作業ログの見出しは機構の定義と一致する。チケットの記載事項は他の task スキルと同じ |
| 網羅性 | 洗い出しは全チケットの作業ログの固定見出しを機械的になぞり、記憶に頼らない |
| 冪等性 | 再開時に候補の洗い出しと合意をやり直さず、起票済みの issue を二重に作らない |
