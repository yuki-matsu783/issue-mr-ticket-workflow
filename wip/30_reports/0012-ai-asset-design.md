### ◆特に見てほしい（判断に困っている）

- **計画書が指定したテスト ID の接頭辞 `WD-T` を使わず、`DC-T08` / `DC-T09` を採った**（e8-1）。`workflow-diff-check` の仕様が現に使っている接頭辞は `DC-T`（`DC-T01`〜`DC-T07`、テストの実体も `DC-T` で書かれている）で、`WD-T` を新設すると 1 つのアセットが 2 つのテスト ID 接頭辞を持つ。計画書の骨子から外れる判断なので、`WD-T` でなければならない理由があれば差し戻してほしい
- **計画書のヘッドレス実行の帰結が「4 本のフックは拒否側に倒す」と書いているが、そのうち 2 本は拒否できない**（e8-2）。`workflow-diff-check`（PostToolUse）と `subagent-start-check`（SubagentStart）は deny を出す経路を持たない。「拒否側に倒す」の中身を、**拒否できるフックは deny、案内側は『判定していない』ことを伝える側に倒す**と読み替えて §2 に書いた。読み替えの当否を見てほしい

### ◇判断が欲しい（決めた方針の承認 / 決められない点の判断）

- **共有ルートを `HOOK_SHARED_ROOT` という別の変数として持ち、値は `HOOK_ROOT` と同一に固定した**（計画書の保留 P2 の決着。e1）。環境変数からの上書きを受け付けないのは、進行状態の置き場を外から動かせることが `workflow-state-guard` の保護対象を外から外せることを意味するため。別 clone を使う運用は、値の解決だけを変えれば参照側を触らずに済む形にしてある
- **`workflow-state-guard` が「畳めないパス」を拒否する範囲を、`リポジトリの外と確定できるものは許可 / 位置を確定できないものだけ拒否` に分けた**（e3）。「畳めなければ一律拒否」にすると OS の一時ディレクトリへの正当な書き込みまで止まるので、`i0010-09`（判定できないときは拒否側）の適用対象を「判定できない」に限った
- **`workflow-diff-check` に新しい識別子 `WF605`（作業ツリーを確定できない）を採った**（e4）。既存の `WF604`（基準点なし）に相乗りさせると 1 番号に 2 原因が乗るため分けた
- **置き換えられた DDR 3 本の frontmatter に `status` / `superseded_by` / `superseded_scope` を足した**（e6）。チケットの作業内容は「既存の DDR は書き換えない」だが、`ai-asset-design-docs` ルールは置き換えの関係を対で持たせることを求めているので、**本文は 1 文字も変えず frontmatter だけ**を足した

## 実施した内容と結果

### e1. 作業ツリーの三分を §2 に定義し、共有ルートは別の変数として持って値を `HOOK_ROOT` に固定した ◎良

`10_spec/フック共通仕様.md` §2 に、フックが区別する 3 つの根を表で置いた。

| 名前 | 変数 | 指すもの | そこに置かれるもの |
|---|---|---|---|
| 置き場 | `HOOK_ROOT` | 読み込み行が解決したリポジトリルート（本流） | フック・共通ライブラリ・`hooks/config/`・`settings.json` |
| 判定対象の作業ツリー | `HOOK_WORKTREE` | その操作が行われた作業ツリー | `wip/`、`logs/hooks/decisions.jsonl`、`logs/sh/` |
| 共有ルート | `HOOK_SHARED_ROOT` | issue・ブランチ・MR に属する進行状態を集める根 | `logs/` の進行状態・ロック・集計・セッション状態 |

計画書の保留 P2（変数を分けるか決め打つか）は**分ける**で決着させた。ただし値の解決は `HOOK_ROOT` と同一に固定し、環境変数・設定からの上書きを受け付けない。理由は 2 つで、①名前を分けておけば、別 clone を使う運用（要件の前提条件が認めている）を扱うときに値の解決だけを変えればよく、進行状態を読む全フック・全提供コマンドを触らずに済む ②上書きの口を開けると、進行状態の置き場を動かすことで `workflow-state-guard` の保護対象そのものを外から外せる（拒否側の保護が環境変数 1 つで無効になる）。

あわせて、**同一リポジトリの作業ツリーの集合**（`HOOK_ROOT` と `.git/worktrees/*/gitdir` に登録されたすべて）を §2 に定義した。この集合は「保護してよい範囲」を広げるためだけに使い、`HOOK_WORKTREE` の決定には使わないので、stale な登録が混ざっても判定は緩まない（緩むのは `HOOK_WORKTREE` の決定側だけで、そちらは従来どおり相互参照の双方向を要求する）。

### e2. 進行状態・ロック・集計を共有ルートへ、判定記録と実行ログを作業ツリー側へ分けた ◎良

§5 の表に「根」の列を足し、記録ごとの置き場を 1 か所で読めるようにした。共有ルート側は `mr.json` / `review-state.json` / `review-history.jsonl` / `merge-state.json` / `locks/` / `usage/<branch>.json` / `sessions/<session_id>/` / `push-state.json`、作業ツリー側は `hooks/decisions.jsonl` と `sh/<name>.log` の 2 つだけである。`logs/locks/<name>.lock` は表に無かったので行を足した（実装は `logs/locks/<name>.lock` を使っており、束 1 の 7 が名指ししている対象なので、置き場を決める以上は表に載っている必要がある）。

`decisions.jsonl` のスキーマに `cwd`（判定時の作業ツリー）と `agent_id`（サブエージェントの識別）を足し、`HK-T06`（記録のスキーマ）にその検査と負のコントロール（メインの呼び出しでは `agent_id` が空）を書き足した。

**この決定が §1 の別の記述に効いていた。** §1 は「`jq` は最大 2 回」の内訳として「`logs/` は作業ツリー側に置き、作業ツリーは stdin の `cwd` を読んで初めて決まるので、この 4 つを 1 回目に混ぜることは原理的にできない」と書いていた。進行状態を共有ルートへ寄せると `review-state.json` / `merge-state.json` の置き場はフックの起動時に決まるので、この理由付けは成り立たなくなる。**2 回目が要る理由を `session_id` 依存（`approvals.json` / `entry.json`）に置き換え**、`review-state` / `merge-state` を 1 回目に混ぜない理由を「読むのが 2 本のフックだけだから」に書き直した。

### e3. 作業ツリーをまたぐ絶対パスの保護漏れ（A1-2）を、無条件の記述で閉じた ◎良

調査 e5 / e51 の A1-2（`cwd` が worktree のとき、本流の `logs/mr.json` と `wip/10_tickets/20_done/*.md` を絶対パスで書き換えても止まらない。`03-state-guard.txt` で実測確定）を、要件と仕様の両方に**無条件で**書いた（束 2 の 2。並列を採らなくても作業ツリーが 2 つあれば踏むため）。

- **要件**（`00_requirement/hooks/20-PreToolUse/workflow-state-guard.md`）: 「別の作業ツリーにある進行状態のファイル・チケットの置き場を絶対パスで指して…操作しようとしたとき、Shall フックは自分がいる作業ツリーの中の同じ対象と同じ理由・同じ識別子で拒否しなければならない（保護は作業ツリーの数に依らない）」をメインフローに追加。裏側として「同じリポジトリの外への書き込みは拒否してはならない」も置いた（保護対象はリポジトリの中にしか無く、作業ツリーの外への書き込みの可否は `workflow-guard` の責務）
- **仕様**（`10_spec/hooks/20-PreToolUse/workflow-state-guard.md`）: 「対象パスの畳み込み」の節を制御方式の前に置き、`hook_rel_path` の結果を 3 通り（同一リポジトリのいずれかの根の配下 → 畳んだ相対パスで照合 / どの根の配下でもない → 許可 / 判定できない → `WF309`）に分けた。**このフックは「畳めた根がどれか」を見ない**（自分の作業ツリーか他の作業ツリーかで扱いを変えない）ことを明示した

「畳めないパスを拒否側に倒す」は、**「リポジトリの外と確定できるもの」と「位置を確定できないもの」を分けて**書いた。前者まで拒否すると OS の一時ディレクトリへの正当な書き込みが止まるので、`i0010-09` の適用対象は後者に限る。この線引きは §13 の「意図的な緩和」にも 1 項目として書いた（リポジトリの外への書き込みは、作業中チケットが無い切れ目では誰も止めない）。

畳み込みの規則そのものは `workflow-state-guard` に閉じず、共通仕様 §2 に `hook_rel_path` の振る舞いとして置いた（`workflow-guard` の `__wg_rel` も同じ規則を要るため。判定順は 0013 が書く）。

### e4. 差分の基準点の一意性を明記し、仕様 §13 の食い違いを実装に合わせて書き戻した ◎良

調査 e6 の D1（仕様 §13 が「差分の事後検査は `HOOK_ROOT` の作業ツリーだけを見る」と書くが、実装は初版から `git -C "$HOOK_WORKTREE"`）を、**実装を正として**次のように決着させた（計画書 P9 / 束 2 の 9。無条件の記述）。

- 共通仕様 §13 から「worktree の中の差分の事後検査」の項目を外した（実在しない穴を緩和として書いていた）
- `workflow-diff-check` の仕様の概要に「判定の対象は `HOOK_WORKTREE` に閉じる。作業中チケットも `base_sha` も差分の取得もすべて同じ作業ツリーから取る」を書き、入出力の参照先を `git -C "$HOOK_WORKTREE"` の形に揃えた
- 要件（外部視点）にはメインフローとして「差分を調べる対象は操作が行われた作業ツリーであり、他の作業ツリーの差分を混ぜてはならない」「差分の基準点はその作業ツリーの作業中のチケットが着手時に記録した基準点で一意に決まる」を追加した（受け入れ条件 A5 の条文そのもの）
- 制御方式に段階 0（作業ツリーの確定）を足し、確定できないときは `WF605` を伝えて抜ける形にした。**`cwd` が worktree でないと確かめられて `HOOK_ROOT` に倒れた場合は「決められない」ではない**（決まった値が `HOOK_ROOT` なだけ）ことを但し書きにした

`WF605` は共通仕様 §6 の採番台帳（`WF601–609` の行）に登録した。

### e5. A1-6 を閉じる機械テスト観点を DC-T08 / DC-T09 として置き、負のコントロールの前提をテスト自身が作る形にした ◎良

受け入れ条件 A1-6（`workflow-guard` / `workflow-diff-check` が worktree 側のチケットで判定するか。観点 A の中心の問い）は、実測時にどの作業ツリーにも作業中チケットが 0 枚で負のコントロールまで無音になり、判定不能のまま残っていた（調査 e48 / R31 / R41）。計画書の指示どおり、**人間の再実測に戻さず機械テストで閉じる**。0012 が担うのは差分の基準点の 2 件で、宣言範囲の強制（`WG-T`）と実行者照合（`SA-T`）は 0013 が担う。

| テスト ID | 種別 | 前提の作り方 | 期待する結果 |
|---|---|---|---|
| `DC-T08`（機械テスト） | 正常系 | 一時リポジトリに本流と worktree を作り、**それぞれ別の `base_sha` を持つ作業中チケットを 1 枚ずつ**置く。枚数は**テスト自身が `10_doing/` を数えて assert する** | `cwd` を worktree にすると、worktree 側チケットの `base_sha` 以降の範囲外の差分だけが `WF601` に並び、本流側の差分は並ばない |
| `DC-T09`（機械テスト。`DC-T08` の負のコントロール） | 正常系 | 同じ構成で**本流に作業中 1 枚・worktree に 0 枚**を置く（枚数を assert する） | `cwd` を worktree にすると何も出ない。この前提を作らずに `DC-T08` だけを見ると、無出力を「判定した結果、差分が無かった」と読み違える |

**負のコントロールの前提（作業中チケットの枚数）をテスト自身が assert で作る**ことを、テスト観点の本文に書いた。実測が失敗したのは「実行時のリポジトリの状態に前提を依存させた」ためなので、同じ失敗を再発させない条件がテストの中に無ければ、機械テストに移す意味が無い。

あわせて共通仕様 §11 に `HK-T21`（作業ツリーの三分の解決。作業ツリーが 1 つの環境では 3 つとも同じ値になることを負のコントロールに置く）と `HK-T22`（作業ツリーをまたぐパスの畳み込み。リポジトリ外の絶対パスは「無関係」、`.git/worktrees/` を読めない環境は「判定できない」）を新設した。`workflow-state-guard` 側は `SG-T12`（他ツリーの保護対象を絶対パスで書く。負のコントロールはリポジトリ外の同名ファイル）と `SG-T13`（集合を読めないときに `WF309`。worktree が 1 つも無いだけの状態では従来どおり）を新設した。**採った ID はすべて、入力・期待する振る舞い・判定方法を持つ行として同じチケットの中で定義した**（接頭辞の予約だけで終わらせていない）。

### e6. DDR を 3 本作り、置き換えられた 3 本には frontmatter だけを足した △注意

| ID | 題目 | 却下した案 |
|---|---|---|
| `i0050-01` | 1 issue 内の同一フェーズのチケットの並列実施を採用する | 見送る（直列維持）/ 利得を測ってから決める / 並列は採らず worktree の健全性だけ直す / 帰属モデルを要件化して 1 つの作業ツリーの中で並列にする |
| `i0050-02` | 進行状態とロックと集計は共有ルートに一本化し、判定記録と実行ログは作業ツリー側に残す | `.worktreeinclude` で複製 / 作業ツリーごとに空から初期化 / `logs/` を丸ごと共有ルートへ寄せる / 共有ルートを環境変数で指定できるようにする |
| `i0050-07` | 作業ツリー解決は相互参照の双方向を要求し、差分の事後検査は判定対象の作業ツリーを見る | 片方向でよいとする元の決定を維持して実装を緩める / §13 の緩和を残したまま実装側に注記だけ足す / `i0009-64` の本文を直接書き換える |

`i0050-01` には計画書 P1a のとおり「**採用の根拠は依頼と原則の読み直しであって、コストと利得の比較ではない**」「所要時間の短縮幅を測らずに採った」を決定の一項として書いた。利得を推定値で埋めると DDR の記述が実測を装った推測になるためで、非対称を明示したまま残すほうが後から見直せる。

**△注意**: チケットの作業内容は「既存の `i0001-23` / `i0009-55` / `i0009-64` は書き換えない」だが、`ai-asset-design-docs` ルールは「置き換えられた側に `superseded_by`、置き換えた側に `supersedes` を**対で**持たせる」ことを求めている。**本文は 1 文字も変えず、frontmatter に `status: 一部置き換え済み` / `superseded_by` / `superseded_scope` の 3 行だけ**を足して両立させた。3 本とも全体が無効になったわけではないので `一部置き換え済み` を採り、何が無効になったかを `superseded_scope` に 1 行で書いた（例: `i0001-23` は並列廃止の決定だけが無効で、WIP リミットは「1 作業ツリーあたり 1 枚」として有効）。

### e7. 束 1 / 束 2 の書き分けと、1 つの決定が効く箇所の洗い出し ◎良

計画書の決まり（束 1 = 並列を採る場合にだけ効く / 束 2 = 採らなくても直すべき）を、記述の側で読み分けられる形にした。
