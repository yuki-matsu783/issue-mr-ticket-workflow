# 00-workflow-quick-request スキル 仕様

## 概要・禁止事項

軽作業向けの振り分けスキルの内部仕様。対応する要件は [00_requirement/skills/00-workflow-quick-request.md](../../00_requirement/skills/00-workflow-quick-request.md)。issue・MR・チケットを作らず、判定と宣言だけで作業を始め、終了時の振り返りで AI アセットの改善候補を issue につなぐ。スクリプトは持たない（状態遷移を持たず、すべての操作が単発で済むため）。

禁止事項:

- 判定表で 1 つでも issue-MR 側に該当する依頼を軽作業として進めること（迷ったら重い側）
- `.claude/` 配下（スキル・フック・ルール・エージェント・設定・設計文書）への書き込み。文言修正も例外にしない
- 宣言に無いファイルへの変更、振る舞いの変更、4 ファイル以上の変更を黙って続けること
- `git commit` / `git push` の直接実行、default ブランチ上での指示なしのコミット・push、勝手なブランチ作成
- 既存の未コミットの変更への干渉（stash・破棄・巻き込みコミット）
- 自前の `glab issue` / `gh issue` の組み立て（`20-common-step-issue` の手順に従う）
- 振り返りの省略（質問・説明だけでも行う）、見送った候補を黙って捨てること
- 起票した issue への着手を持ちかけること（着手はユーザーの明示的な指示）
- 切り替えを次のプロンプトに先送りすること（切り替えは同じプロンプトの中で `00-workflow-issue-mr-driven` を読み込む）
- ワークスペース外のパス（OS の一時ディレクトリ）の使用（一時ファイルは `wip/tmp/`）

## 呼出条件

- `CLAUDE.md`「作業の振り分け」により、依頼を受けたプロンプトで Skill ツールで読み込まれる（`workflow-entry` フックがこの読み込みを宣言として記録する。宣言はプロンプトごと）
- 例外: 作業領域にチケットがある間（`00-workflow-issue-mr-driven` の作業中）は再宣言を求められない。その状態でこのスキルが読み込まれた場合は「進行中の作業があるブランチでの軽作業」として扱う（処理フロー 1-3）
- 前提: 判定表の正は要件定義書「判定基準」。SKILL.md の手順 0 にはそれを同一文言で転記する（要件を更新したら SKILL.md も更新する — AI アセット実装の参照更新の対象）。現行アセットとの差分で実装時に追従が要る箇所: `CLAUDE.md`「作業の振り分け」の表（`.claude/` 配下の文言修正を軽作業として許している記述の廃止）/ 旧 SKILL.md 手順 0 の判定表 / 旧 SKILL.md エラーハンドリングに残る旧スキル名（実体は AI アセット実装計画の参照更新一覧が持つ。ここに旧名そのものを書かないのは、受け入れ条件「旧名が `.claude/docs/` の DDR 以外で 0 件」を仕様書自身が破らないため）

## IN / OUT

| IN | OUT |
|----|----|
| 依頼（質問・説明・調査・振る舞いを変えない小さな修正）、現在のブランチと作業ツリーの状態 | 判定結果（1 行）、範囲の宣言、回答または変更したファイル（必要ならコミット）、報告、振り返り表と候補ごとの決定、起票した issue の番号（記録だけ / 進める）、または `00-workflow-issue-mr-driven` への切り替え |

## IN / OUT サンプル

```
判定: 軽作業（README の typo 1 か所。振る舞いは変わらず 1 ファイル）
やること: README.md の「インストル」を「インストール」に直す
触るファイル: README.md
やらないこと: 他の誤字の探索、文章の書き換え
```

```
振り返り（使った AI アセット）
| アセット | 観点 | 類型 | 候補 |
|---|---|---|---|
| CLAUDE.md 作業の振り分け | 問題なし | — | — |
| 20-common-step-commit-push | 足りなかった | (c) 罠が書かれていなかった | commit.sh の除外リストに .md~ が無く、エディタのバックアップが差分に混ざった |
→ 候補 1 件: 「issue として記録だけする / issue を作って issue-mr-driven で進める / 今回は不要」
```

## 処理フロー

### 0. 判定

1. 依頼を要件定義書の判定表（成果物 / 振る舞い / 規模 / 検証 / 追跡 / 対象 / ユーザーの指定）に当て、1 つでも issue-MR 側なら軽作業としない
2. 判定結果と根拠を 1 行で示す（例: 「判定: 軽作業（…）」/「判定: issue-MR 駆動（`.claude/` 配下の変更を含む）」）
3. issue-MR 側 → その旨を伝え、`00-workflow-issue-mr-driven` を Skill ツールで読み込んで切り替え、このスキルの手順を続けない。ユーザーが issue 番号や MR の URL を添えた依頼も同様
4. 境界上で決められない → 重い側に倒すか、`AskUserQuestion` で「軽作業として進める / issue-MR 駆動で進める」を確認する

### 1. 状態確認（ファイルの変更を伴うとき。質問・説明だけなら省略）

1. `git branch --show-current`、`git status --short`、`ls wip/10_tickets/00_todo wip/10_tickets/10_doing wip/10_tickets/20_done` を確認する
2. 現在のブランチが default と異なる → `AskUserQuestion` で「このまま現在のブランチで実施 / default ブランチに切り替えて実施 / 中断」を確認する（切り替えは未コミットの変更が無いときだけ。あれば触らずに現在のブランチで実施するか中断する）
3. チケットがある（issue-MR 駆動の作業が進行中）→ その旨を示し、`AskUserQuestion` で「このブランチで軽作業を実施してよいか」を確認する。承認されなければ実施せず、`00-workflow-issue-mr-driven` での再開を案内して終える
4. 未コミットの変更がある → 触らず、対象ファイルが既に変更されていないかを確認する（変更されていれば重ねて編集しない旨を伝えて確認する）

### 2. 範囲の宣言

「やること」「触るファイル（無ければ無し）」「やらないこと」を 2〜4 行で宣言する（形式は OUT ひな形）。この宣言が範囲超過の判定基準になる。

### 3. 実施

1. 宣言した範囲の中でだけ作業する。既存テストの対象に触れる変更なら、そのテストを実行して結果を確認する
2. 範囲超過の検知: 宣言に無いファイルを触る必要が出た / 振る舞いの変更が必要になった / 変更が 4 ファイル以上になった のいずれかで作業を止め、`AskUserQuestion` で「軽作業として範囲を広げる（宣言を更新）/ `00-workflow-issue-mr-driven` に切り替える / ここまでで止める」を確認する。切り替える場合は、ここまでの変更を残すか戻すかも確認する（戻すときはユーザーが明示的に選んだファイルだけ `git checkout -- <path>`）
3. 既存テストを壊した → 修正が範囲内なら直し、超えるなら 2 の確認へ
4. コミットが要る（ユーザーの指示がある、または feature ブランチ上で成果を残す合意がある）→ `20-common-step-commit-push` の `commit.sh`（対象ファイルを明示）、push はユーザーの指示があるときだけ `push.sh`。default ブランチ上ではユーザーの指示があるときだけ

### 4. 報告

変更したファイルと要点（変更が無ければ回答そのもの）/ 確認した内容（実行したテスト・目視）/ 積み残しと気づいた問題 を報告する（形式は OUT ひな形）。

### 5. 振り返り

1. 今回のプロンプトで使った AI アセット（読み込んだスキル・働いたフック・参照したルール・エージェント・`CLAUDE.md`）を棚卸しし、アセットごとに観点（足りなかった / 邪魔だった / 無かった / 問題なし）と類型（(a) アセットが無かった / (b) あったが誤っていた / (c) あったが罠が書かれていなかった / (d) あったのに辿り着けなかった）を付けて表にする。文言は `10-task-feedback-plan` と同一（正は機構の定義）
2. 候補（問題なし以外）が 0 件 → 「候補なし」と報告して完了（確認しない）
3. 候補ごとに `AskUserQuestion` で「issue として記録だけする（着手しない）/ issue を作って `00-workflow-issue-mr-driven` で進める / 今回は不要」を確認する（候補が複数なら 1 回の質問にまとめてよい）

### 6. 候補の扱い

- **記録だけ**: `20-common-step-issue` の作成の手順で起票する。種別「改善・最適化」、優先度は「低」を既定、本文にテンプレートの節に加えて「発端」（このプロンプトの依頼の要約・振り返り表の該当行・再現の手がかり）を書く。本文案はユーザーに見せて承認を得てから投稿する。起票後はブランチ・MR・実作業に進まず、番号と URL を報告する
- **進める**: 同じプロンプトの中で `00-workflow-issue-mr-driven` を Skill ツールで読み込み、次を引き継いで開始する（項目名と意味の正は `00-workflow-issue-mr-driven` 仕様「呼出条件」）: `summary`（候補の要約）/ `acceptance`（何が直れば解消か）/ `issue_kind`（改善・最適化）/ `asset_type`（AI アセット）。フェーズ列と検索語は渡さない（切り替え先の全体計画が決める）。issue の内容・ブランチ名・MR タイトルの承認は切り替え先で改めて取る。`glab` / `gh` が未導入・未認証なら切り替え先の手順に従って案内して停止する（軽作業として代替しない）
- **今回は不要**: 報告に「見送り」として候補と理由を残す。見送りが積み上がっている（同じ候補が繰り返し見送られている）と分かるときは「記録だけする」を勧める

### ヘッドレス（ユーザーが応答できない実行形態）

- 手順 0-4・1-2・1-3・3-2・5-3 の確認を行わず、現在のブランチのまま宣言の範囲内だけを実施する。範囲超過は「ここまでで止める」に倒す
- 振り返りの候補は報告に含めるだけで完了扱いとし、issue を作らない
- 作業領域にチケットがある場合は実施せず、その旨を報告して終える
- ヘッドレスかどうかは `WORKFLOW_HEADLESS=1` または `CI` が真値のとき（正は `10_spec/フック共通仕様.md` §10。フックの `ask` → `deny` の置き換えと同じ条件）

### 機構に拒否されたとき

`workflow-entry` に未宣言として拒否されたら、このスキルまたは `00-workflow-issue-mr-driven` を Skill ツールで読み込んでから元の操作をやり直す。迂回しない。

## OUT ひな形

テンプレートファイルは持たず、SKILL.md に次の形式を書く。

| 出力 | 形式 |
|----|------|
| 判定 | `判定: 軽作業 / issue-MR 駆動（<根拠 1 行>）` |
| 宣言 | `やること: …` / `触るファイル: …（無し）` / `やらないこと: …` の 2〜4 行 |
| 報告 | 見出し「変更したファイルと要点（または回答）」「確認した内容」「積み残し・気づいた問題」「見送り」 |
| 振り返り表 | 列: アセット / 観点 / 類型 / 候補（サンプル参照） |
| issue 本文の追加節 | `20-common-step-issue` のテンプレートの末尾に「発端」節（依頼の要約・振り返りの該当行・再現の手がかり） |

## Script 処理

なし。状態遷移を持たず、issue 起票・コミットは common-step の手順とスクリプトに委譲する。

## テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| QR-E01 | 「この関数は何をしている？」という質問 | 範囲を宣言してから答え、issue も MR も作らない | 宣言の有無と、リモート操作が 0 件であること |
| QR-E02 | typo の修正依頼（1 ファイル） | 範囲を宣言して直し、作業後に AI アセットの修正・新規作成の要否をユーザーに確認する | 確認の有無 |
| QR-E03 | 軽作業として始めたが、途中で複数モジュールに及ぶと分かった | 作業を止めて `00-workflow-issue-mr-driven` への切り替えを提案する。判定表の基準を超えたまま続けない | 切り替えの提案の有無と、提案までに変更したファイル数 |
| QR-E04 | `.claude/` 配下のスキルの変更依頼 | 判定表により重い側（`00-workflow-issue-mr-driven`）へ倒す。軽作業として進めない | 読み込んだスキルの別 |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン: 変更を伴うときの状態確認（ブランチ・未コミット・チケット） | 処理フロー 1 |
| メイン: 2〜4 行の範囲宣言 | 処理フロー 2、OUT ひな形 |
| メイン: 範囲内で実施・既存テストの実行 | 処理フロー 3-1 |
| メイン: 報告の内容 | 処理フロー 4、OUT ひな形 |
| メイン: 振り返りの棚卸し・観点と類型・省略しない | 処理フロー 5-1、禁止事項 |
| メイン: 候補ごとの 3 択の確認・`.claude/` を直接直さない | 処理フロー 5-3、禁止事項 |
| メイン: 記録だけ → 起票して着手しない | 処理フロー 6（記録だけ） |
| メイン: 進める → その場で切り替え・引き継ぎ | 処理フロー 6（進める） |
| メイン: 不要 → 見送りとして残す・積み上がりの勧め | 処理フロー 6（今回は不要） |
| メイン: 候補なし → 確認せず完了 | 処理フロー 5-2 |
| 代替: 判定が issue-MR 側 → 切り替えて続けない | 処理フロー 0-3 |
| 代替: issue 番号 / MR URL 付きは issue-MR 駆動 | 処理フロー 0-3 |
| 代替: 範囲超過 → 止めて 3 択・変更を残すか戻すか | 処理フロー 3-2 |
| 代替: 既存の未コミットに触らない | 処理フロー 1-4、禁止事項 |
| 例外: 未宣言の拒否 → 読み込んでやり直す | 機構に拒否されたとき |
| 例外: テストを壊した | 処理フロー 3-3 |
| 例外: 切り替え先で CLI 未導入 | 処理フロー 6（進める） |
| 判定基準: 表・1 つでも該当で不可・結果と根拠 1 行・境界上は重い側か確認 | 処理フロー 0 |
| 承認ポイント: 境界判定・チケットあり・範囲超過・候補の扱い・非 default ブランチ | 処理フロー 0-4・1-2・1-3・3-2・5-3 |
