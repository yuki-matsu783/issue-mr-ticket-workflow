# i0001-11. 実装後にフィードバック計画ワークを置き、振り返りと後続フェーズの決定をメインエージェントが人間と行う

## 背景

初版の要件では、振り返りと AI アセット改善候補の起票を最後の「全体まとめ」で行い、設計フィードバック・AI アセット設計・AI アセット化を含めるかは全体計画の時点で決める（調査と AI アセット系は必須）としていた。しかし全体計画の時点では、実装で何が起き、何を設計文書や AI アセットへ戻すべきかはまだ分からない。また、振り返りを最後に置くと、そこで見つかった改善をこの MR で対応する余地が無く、全件が別 issue になる。ワークがサブエージェントで実施される（i0001-08）ため、振り返りの材料はサブエージェントが記録として残しておく必要もある。

## 決定

- 実装・テストの後（設計フィードバックの前）に **フィードバック計画** ワークを新設する。ワークの種類が 1 つ増える
- フィードバック計画は**メインエージェント**が担当し、ユーザーと対話しながら、ここまでのワークで得た反映すべき内容（チケットの作業ログ・レビュー指摘・拒否と確認の記録・レポートの「想定と異なった点」）を振り返る
- 改善候補ごとに「**この MR で対応する**」か「**別 issue として起票する**」かを決める。既定はこの MR で対応し、変更が大きくなりすぎる場合に別 issue とする。決定に従って設計フィードバック・AI アセット設計・AI アセット化のチケットを作成・修正し、別 issue は承認を得て起票する
- **サブエージェントは、担当したチケットの作業ログに「うまくいかなかったこと」「AI アセットに反映すべき内容」を残す。** フィードバック計画はこの記録だけで振り返れることを前提にする
- 全体計画で必ず含めるフェーズは**調査とフィードバック計画**だけにする。フィードバック計画より後のフェーズを含めるかは全体計画では決めず、フィードバック計画で決める。ただし issue の主目的が AI アセットのときは AI アセット設計・AI アセット化は主作業として全体計画で含める（i0001-12 のテンプレート）
- **振り返りと候補の取捨の機会はフィードバック計画の 1 回だけ**とし、以後のワークで見つかった反映すべき内容は全体まとめで別 issue として起票する（この MR では対応しない）
- 全体まとめからは振り返りと改善候補の起票を外し、衝突解消・統括レポート・MR 本文の最終化・issue へのコメント・片付け・push・draft 解除だけを行う（i0001-09）

## 理由

- 実装まで終えた時点なら、何を設計文書へ戻し、どのアセットを直すべきかが実際の情報に基づいて決められる。全体計画の時点で「必須」と決め打ちする必要が無くなる
- 振り返りを最後ではなく後続フェーズの前に置くことで、見つかった改善をこの MR の中で対応でき、「別 issue に積むだけで直らない」状態を避けられる
- 改善候補の取捨と「この MR か別 issue か」は規模と優先度の判断であり、人間との対話が要る。サブエージェントはユーザーと対話できないため、メインエージェントが担当する
- サブエージェントの記録をチケットに残すことで、メインエージェントがサブエージェントのコンテキストを持たなくても振り返りができる

## 却下した案

- **振り返りと改善候補の起票を全体まとめで行う（初版・参考実装の retrospective 方式）**: 1 箇所にまとまるが、この MR で対応する余地が無く、すべて別 issue になる。全体まとめが重くなり、片付け・draft 解除と混ざる
- **設計フィードバック・AI アセット設計・AI アセット化を全体計画で必須にする（初版）**: 省略の判断が裁量にならない利点はあるが、根拠の無い時点で必須にしており、多くの場合「対象なし」で即完了するだけの空回りになる
- **フィードバック計画をサブエージェントに任せる**: 他のワークと扱いが揃うが、「この MR か別 issue か」の判断に人間との対話が要るため成立しない
- **反映すべき内容の収集をフィードバック計画の時点でメインエージェントが差分から推測する**: 記録の義務を課さずに済むが、サブエージェントの試行錯誤はコンテキストの外に消えており、差分からは「うまくいかなかったこと」が読み取れない

## 影響

- 要件定義書 B・C・I 節、`00-workflow-issue-mr-driven.md` のメインフロー・承認ポイント
- work スキルに `10-work-feedback-plan` を追加する。type 定義にエントリを 1 つ足す
- チケットテンプレートの作業ログに「AI アセットに反映すべき内容」の欄を設ける
- 軽作業（`00-workflow-quick-request`）の終了時の振り返りは、フィードバック計画と同じ観点・類型を使う
