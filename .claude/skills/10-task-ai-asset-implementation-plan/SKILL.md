# 10-task-ai-asset-implementation-plan — 固定順のステップと許可範囲を決める

共通手順の禁止事項（計画書・チケット・`wip/tmp/` 以外に書き込まない、全体計画書と受け入れ条件を書き換えない、次の計画チケットを推測で作らない）に加えて、アセット本体・テストを書き始めない。要件・仕様を書き換えない（不備は AI アセット設計への差し戻し提案）。テスト ID の無いアセット変更をステップに入れない。中核（フック・`settings.json`）の変更を、そのテストより後ろのステップやスキル変更と同じチケットに置かない。参照更新一覧を検索せずに書かない（検索語と検索結果を添える）。

## 目的

機構自身を安全に書き換えるための順序と範囲を決める。中核とそのテストを隣接させ、変更後に自分が止まったときの戻し方まで先に書いておく。

- 要件: `.claude/docs/00_requirement/skills/10-task-ai-asset-implementation-plan.md`
- 仕様（正。固有手順・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-ai-asset-implementation-plan.md`
- 処理の共通手順（正）: `10-task-investigation-plan` の「計画タスクの共通手順（正）」

## 手順

共通手順（着手 → 入力の確認 → 計画書 → 実施チケット群 → 次の計画チケット → 完了 → 結果報告）は `10-task-investigation-plan` に従う。ここでは固有部分だけを示す。

- 仕様書にテスト ID が無い（または受け入れ条件に対応するテスト観点が無い）ときは実装チケットを起こさない。不足を結果報告に書き、AI アセット設計（`ai-asset-design`）の追加チケットを起こす提案を返す
- ステップは**固定順**で並べる: 設定・定義（`settings.json`・frontmatter・テンプレート）→ 中核（フック・提供コマンド）→ 中核の機械テスト → スキル・ルール・エージェント → 参照更新。中核の変更と機械テストは同じチケットか隣接するチケットにする
- **計画書の記述順とチケットの実行順を一致させる**。ステップに割り付けたチケットの連番は `ticket.sh next` が返す順（先行の解決を挟んだ最小連番）と同じ並びにする。順序が入れ替わる依存があれば `predecessors` で表し、ステップの順番を実行順に合わせて書き直す
- **提供コマンド自身を変えるステップ**（`ticket.sh` / `commit.sh` / `push.sh` / `boundary.sh` / `finalize.sh` など）には、**変更後の自分のコマンドで自分をコミット・完了させる最初の操作**を手順として明示する。書き換えた直後の 1 回目が壊れていると、そのチケットを完了させる手段が無くなる。「変更 → `commit.sh` で自分をコミット（この 1 回目が検証を兼ねる）→ `ticket.sh complete`」の並びを書き、失敗時に戻す基準点（`base_sha`）を添える
- テスト方針: 仕様のテスト観点をステップに割り付け、**機械テスト**は実行コマンドを、**eval** は定義（入力・期待する振る舞い・判定方法）を書く。eval は実装フェーズでは定義までで、実行は人間の判断
- **テスト ID の割付表は機械的に作る**。`grep -rhoE "[A-Z]{2,6}-[TE][0-9]{2}[a-z]?" .claude/docs/10_spec/ | sort -u` の出力を計画書に載せ、それを左列にして割付表を組む。抜き出しの結果と割付表の行数が一致することを書く。この正規表現は `run-tests.sh` が `PASS` / `FAIL` 行から ID を抽出する形と同じにする
- **テストを実行するチケットは `build-test` と `hook-test` を両方宣言する**。`.claude/hooks/**/tests/*.sh` と `.claude/skills/*/scripts/tests/*.sh` は `hook-test`、`commands.build-test` の列挙とリポジトリ直下の `tests/*.sh` は `build-test` になる。片方だけだと WF204 で止まる
- **AI アセット実装チケットの DoD の型**: 「{{アセット}} が仕様書 {{節}} のとおりになっている」「機械テスト {{ID}} が通る（実行方法）」「eval {{ID}} が定義されている（実行しない）」「プレースホルダ・frontmatter の検査が 0 件」「参照更新の検索で旧名が 0 件（DDR・用語辞書の別名を除く）」
- **実装結果レポートの作成は最初の実装チケットの DoD に入れる**（「実装結果レポート（md + HTML）があり `check-html.sh` が通っている」）。書かないと最後のチケットでまとめて書くことになる
- **参照更新一覧**は変更する名称・パスごとに検索語とヒット箇所を書き、DDR と用語辞書の別名は除外として明示する。**検索語は行末に依存しない形で書く**（`foo\.sh$` は行の途中のヒットを取りこぼす）。**期待値は「残るもの」で書く**（「旧名が 0 件」ではなく「結果が DDR の N 件と用語辞書の M 件だけ」）。0 件を期待値にすると、検索語が間違っていて何もヒットしない場合と区別が付かない
- **期待値が変更対象に依存するテストを洗い出して同じチケットの許可範囲に入れる**。変更対象ごとに `grep -rn "<旧名>" --include="test_*.sh"` を実行し、ヒットしたテストファイルをそのステップの `allow.write` に加える
- **値の往復（書く側と読む側）が要る修正は、両側の許可範囲を同じチケットに置く**。エスケープ・シリアライズ・状態ファイルのスキーマのように往復するものは、**書く側・読む側・その両方を検証するテスト**の 3 点をひとまとまりのステップにする
- **ロックアウト対策**: 中核（入口ガード・フック・`settings.json`）を変えるステップには、変更後の最初の操作で自分が止まる可能性と復旧手順（どのファイルを基準点に戻すか）を書く。強制無効化 `WORKFLOW_ENTRY_ENFORCE=0` はユーザーの明示があるときだけ
- 許可範囲案はステップごとに最小（`.claude/` 配下の対象アセット・テスト・`logs/`）。ただし上の 3 つ（テストの `ops` 両方・依存するテストファイル・値の往復の両側）は「最小」より優先する。狭すぎる宣言は WF204 / WF205 で止まり、チケットの途中で範囲を広げる相談になるためである
- 人間レビュー要否の既定（方針が無い場合）: AI アセット実装計画チケット「要」、中核を含む実装チケットも「要」
- **見てほしい点の固定項目**: ステップ順と中核・テストの隣接 / テスト ID の割付の漏れ / 参照更新一覧の検索根拠 / ロックアウト対策の妥当性

## OUT ひな形

`assets/ai-asset-implementation-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR・根拠とする要件・仕様 |
| 変更対象 | アセット一覧（新規 / 更新 / 削除）と仕様書の節 |
| 許可範囲案 | ステップごとの書き込み先・実行コマンド |
| テスト方針 | テスト ID × ステップ × 機械 / eval、実行方法または eval 定義 |
| ステップ | 固定順に並べたステップ・依存・チケット |
| 参照更新一覧 | 名称・パス × 検索語（行末に依存しない形）× ヒット箇所 × 除外 × 期待値（残るものの件数と場所） |
| 依存するテスト | 変更対象 × それを入力・期待値に持つテストファイル × 入れるステップ |
| ロックアウト対策 | 中核ステップごとの復旧手順 |
| リスク | 影響範囲・巻き戻し方 |
| 保留した点 / 対象なし / 設計差し戻し | 該当時 |

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 仕様書にテスト ID が無い | 実装チケットを起こさない。AI アセット設計の追加チケットを提案する |
| 中核とテストを同じチケットに入れられない | 隣接するチケットにして `predecessors` で順序を固定する。離さない |
| 参照更新の検索が 0 件だった | 検索語を疑う。期待値は「残るもの」で書き直し、0 件を成功条件にしない |
| 許可範囲を最小にすると WF204 / WF205 が出そう | 最小より優先して、テストの `ops` 両方・依存するテストファイル・値の往復の両側を入れておく |
| 中核変更で自分が止まりそう | ロックアウト対策に復旧手順を書く。強制無効化を既定の手段にしない |
| 共通手順で止まった（TK002 / TK005 / RV00x） | `10-task-investigation-plan` の「エラー時の対処」に従う |
