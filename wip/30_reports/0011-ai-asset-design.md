## 実施した内容と結果

### e1. 提供コマンドの置き場を仕様側に確定した ◎良

`boundary.sh` は `.claude/skills/00-workflow-issue-mr-driven/scripts/`、`finalize.sh` は `.claude/skills/10-task-overall-summary/scripts/` に置く。**2 本だけの措置ではなく機構全体の原則**として、要件書（自己改善ワークフロー機構）と用語辞書（提供コマンド）にも書いた。

| 論点 | 仕様側に寄せる | 実装側に寄せる |
|---|---|---|
| 変更行数 | 実装 7 行 | 仕様 8 行 |
| 既存 5 本との一貫性 | 揃う | 崩れる |
| 所有関係 | 置き場で分かる | 分からない |
| 中核（`session-start.sh`）を触るか | **触る** | 触らない |

決め手は一貫性と所有関係。中核を触るリスクは、実装計画にロックアウト対策を付けることで引き受ける。却下案 4 件（`.claude/hooks/` に寄せる / 専用ディレクトリの新設 / 両方に置く / 決めずに送る）は DDR `i0010-01` に残した。

実装フェーズで直す 7 行は `00-workflow-issue-mr-driven` 仕様の新設節「現行アセットとの差分」に表で置いた。うち 1 行目（`session-start.sh:64`）は中核、4〜7 行目は**期待値が置き場に依存するテスト**なので同じチケットの許可範囲に入れる（申し送り 0038）。

### e2. release に段階を 1 つ増やして B3 の順序を成立させた ◎良

issue 追記 3 は「片付け直前の SHA が確定してから本文を更新する」を求める。現行の仕様は処理フロー 5（本文の最終化）→ 9（release で片付け）の順で、本文更新の時点で `pre_cleanup_sha` が未定義だった。

解決は**リンク一覧だけを release の中へ移す**こと。処理フロー 5 は要約（受け入れ条件との対応・残課題・別 issue 一覧）を書くだけにし、SHA に依存するリンク一覧は release の段階 3 で書く。

| 段階 | 内容 | `state` |
|---|---|---|
| 1 | 前提検査 | `started` |
| 2 | 完了検査（結果を統括レポートへ） | `started` |
| **3（新設）** | **片付け直前の SHA の確定と本文のリンク一覧の更新** | **`linked`** |
| 4 | 片付け | `cleaned` |
| 5 | push | `pushed` |
| 6 | 最終ゲートと draft 解除 | `ready` |
| 7 | 出力 | — |

段階が増えたので、記録が壊れたときの再導出も 1 段増えた。`wip/` に成果物があるときの分岐を「本文にリンク一覧の表が無い → 未実施」「ある → `linked`」に分けている。**表の有無を機械的に見分ける方法は実装フェーズの課題**として残る。

> この判定は誤りで、0021（e28）で固定マーカーに置き換えた。段階番号も 0021（e25）で 1 つずつ繰り下がり、リンク一覧の更新は**段階 4** になっている。以下の表は 0011 時点の記録。

### e3. TK005 は例外ではなく設計だと明示し、完了検査を共有関数にした ◎良

`ticket.sh complete` が全体まとめを必ず拒否するのは、完了が `finalize.sh release` に内包されているためで、抜け道を作る話ではない。ただし拒否だけでは検査の結果がどこにも残らないので、**検査そのものは release の段階 2 が同じ関数で行い、結果を統括レポートの「完了検査」節に書き出す**と定めた（B4）。

- `20-common-step-ticket` 仕様: 検査を `ticket_check_completion <チケットのパス>` として定義し、`finalize.sh` が source して使う（二重実装しない）
- 全体まとめチケットも「`complete` を通らないだけで同じ検査は受ける」ことを明記した
- 統括レポートは片付けで消えないコミットに載るので、チケットが消えた後も検査の通過を辿れる

### e4. テスト観点を 2 件追加した △注意

段階順（B3）と完了検査の出力先（B4）は、仕様の文言を読んだだけでは実装が守ったか確かめられない性質のもの（順序と副作用）なので、テスト ID を足した。

| テスト ID | 種別 | 固定する振る舞い |
|---|---|---|
| FN-T06 | 正常系 | 本文のリンク一覧が `pre_cleanup_sha` に固定され、片付けコミットの後も辿れる |
| FN-T07 | 正常系 | 完了検査の結果が統括レポートの「完了検査」節に書き出されてから片付けが走る |

0008 が数えたテスト ID の総数（完成時 **191**）は **193** になる。実装計画の割付表はこの数を使う。

### e5. CLI 不在時の release を仕様に追加した ◎良

食い違い #7（旧 SKILL.md が `merge-prep.sh --external` を書いていたが、新仕様に記述が無い）を、`10-task-overall-summary` 仕様の新設節「CLI が使えない環境での release」で埋めた。リモートに書く段階は 3（本文のリンク一覧）と 6（draft 解除）の 2 つだけなので、その 2 つだけを呼び出し元に代行させる。

- 段階 3: `release --external --pr <M> --body-file <path>` がリンク一覧をファイルに書き出して戻り、呼び出し元が MCP ツールで本文を更新してから `--linked` で再開
- 段階 6: 呼び出し元が draft を解除してから `release --external --pr <M>` で最終ゲートだけを通す
- `via: "external"` を記録し、`gh` 自身が確認する強度より劣ることを統括レポートに書く。`curl` / `WebFetch` へは落とさない

> 段階番号は 0021（e25）の振り直しで **4（リンク一覧）と 7（draft 解除）** になった。代行させる 2 段階という設計は変わらない。

### e6. 成果物の所在をコメントから MR 本文へ移した（B1） ◎良

処理フロー 6 を「成果物のリンク一覧と HTML 添付」に書き換え、**リンクを列挙した通常コメントの投稿をやめた**。所在は本文の見出し `## 統括` 配下の表（レポート名 / 1 行説明 / リンク）で辿る。リンクは片付け直前の SHA に固定した blob URL なので、片付け後も永続的に開ける。

コメントの投稿は禁止事項にも入れた。「投稿してもよいが本文にも書く」だと、二重管理になって片方が古くなる。

### e7. GitHub への HTML 添付を AI の手順から外した（B2） ◎良

`uploads.github.com` への `curl` を仕様から削除し、禁止事項に移した。**添付は人間がブラウザで本文に行い、AI は返った URL を記録するだけ**にする。

| 送り方 | content_type | 結果 |
|---|---|---|
| 生バイナリ + ヘッダ | `text/html` | 422 `content_type is not included in the list of allowed content types` |
| 同上 | `text/markdown` / `text/plain` / `application/zip` / `application/pdf` | 422 同じ |
| 同上 | `image/png` | **201 Created** |

`image/png` が同じトークン・同じエンドポイントで通るので、リクエストの組み立てではなく**種別で拒否されている**。ブラウザ側の 3 段階の経路（CSRF トークン → S3 署名 → 確定）も、1 段目が PAT では 302 → `/login` になりアセット id が採番されないため再現できない。実測は DDR `i0010-02` に写した。

**添付は任意**の位置づけに下げた。リンク一覧が本文にある以上、添付が無くても成果物は辿れる。これで「添付できない環境」という代替フローの分岐が 1 本消えた。GitLab は `glab api uploads` が公式に使えるので、AI が添付してよい（ホストで扱いが違うことを明記した）。

### e13. 敵対的レビューの出力に 2 つの一覧を足した（申し送り #19） ◎良

`checked_ok` は**既存の禁止事項と紛らわしい**ので、線引きを仕様に書いた。禁止されているのは「該当の無い観点を『問題なし』として並べる」水増しで、足したのは「指摘になりうると思って**実際に中身を見に行き、見た結果として否定できた**もの」である。呼び出し元はこれを読んで「見ていない範囲」と「見たうえで問題が無かった範囲」を区別できる。

`sampled` は、レビュー対象が「N 件を反映した」「すべて通る」のような**まとめの主張**を含むときに、何件かを抜き取って実体と突き合わせた記録である。この issue の調査フェーズで、まとめの件数が 5 回続けて実体と食い違った（42 vs 55、16 vs 15、110 vs 111、11 vs 12、96 vs 95）。**まとめの主張を数えずに信じない**ことを、レビュアー側の義務として固定した。

- `pre_cleanup_sha` は「段階 3 のコミットを含む HEAD」と定義し直した。本文のリンク一覧が指す先に「完了検査」節が実在する
- FN-T07 を「書き出した」ではなく「`pre_cleanup_sha` が指すコミットの統括レポートに含まれている」に強めた

### e26. HTML 添付の可否をホストで分け、要件と仕様の矛盾を解いた（指摘 2・10） ◎良

要件は「スキルが自らアップロードの API を呼んではならない」と無条件に禁じ、仕様は GitLab では AI が添付してよいとしていた。DDR `i0010-02` の決定は後者である。

- 要件の受け入れ基準を 4 本に分けた。公式 API が無いホスト（GitHub）は人間が行いスキルは何もしない（待たない・催促しない）、公式 API があるホスト（GitLab）はスキルが添付してよい、添付の後に本文を書き換えるときリンクを消さない、添付は任意で分岐させない
- 段階 4 の本文書き換えを「`## 統括` 配下のリンク一覧の**表の中身だけ**を置き換える」に限定した。人間が本文のどこに添付を貼っても消えない。受け渡しの経路を「人間が本文に直接貼る」1 つに決めたので、残課題 R5 は閉じる
- FN-T09（本文書き換えが添付と要約を残す）を足した

### e27. ヘッドレス実行の帰結を項目ごとに分けた（指摘 3） ◎良

要件の例外フローは「ヘッドレスでは報告して停止」と一括りだったが、0007 の計画書は「別 issue 起票だけは進む」としていた。

- 別 issue の起票 → 起票せず、候補と本文案を統括レポートに書いて**次の手順へ進む**（起票は取り消せないが、それだけのために全体まとめを止めない）
- 衝突の解消・draft 解除の可否 → **停止**して次回セッションで進行状態から再開する（履歴と外部から見える状態を変えるため）
- 制約条件の「外部的制約」も同じ書き分けに揃えた

### e28. 再導出の判定材料を固定マーカーにした（指摘 9） ◎良

`logs/merge-state.json` を失ったときの再導出が「本文にリンク一覧の表があるか」で `linked` を判定していた。表の骨格は処理フロー 5 の時点でテンプレートが置くので、中身が空でも表は存在し、必ず `linked` と誤判定する。

- FN-T08（空の表が `linked` にならない）を足した

### e29. 要件書の規約違反と段階番号の振り直し漏れを直した（指摘 5・6・14・15） ◎良

### e30. feedback-plan の内部矛盾を「確定」の定義で解いた（指摘 4） ◎良

0013 でヘッドレスの方針を反転させたとき、例外フローだけを書き換えてメインフローを見直していなかった。メインフローは「合意前に後続チケットを作ってはならない」、例外フローは「ヘッドレスでは既定どおりに決めて起票まで行う」。ヘッドレスでは合意が発生しないので、文面どおりに読むと後続チケットを作れない。
