# workflow-diff-check フック

## 概要

`workflow-guard` は操作の前に判定するが、コマンドの実行やツールの副作用で生じた差分までは事前に判定できない。このフックは操作のあとに作業ツリーを調べ、作業中のチケットの許可範囲の外に差分があれば AI に伝えて復旧させる。あわせて、未記載のパスへの書き込みがユーザーの確認を経て実行された事実をセッション内の記憶として記録し、`workflow-guard` が同じセッションで再確認しないようにする。

- **背景**: 事前の判定だけでは、スクリプトやビルドが生成したファイル・想定外の場所への出力・移動やリネームによる差分を捕まえられない。また未記載パスの確認で承認された範囲を記録しなければ、同じセッションで同じ確認が繰り返される。事後の検知と承認の記憶を担う仕組みが要る。
- **目的**: 作業中のチケットの着手時点を基準に、許可範囲の外の差分が残らない状態と、承認済みの範囲を同じセッションで再確認しない状態を実現する。
- **スコープ**:
  - 含む: 許可範囲の外の差分（未追跡ファイルを含む）の検知と復旧指示、未記載パスの承認のセッション内の記憶への記録、先行チケットの未完了の警告、作業中チケットの種類の改変の警告、記録
  - 含まない: 操作の前の許可 / 確認 / 拒否（`workflow-guard`）、差分の自動的な巻き戻し（行わない）、チケットの着手・完了そのもの（提供コマンド）、サブエージェント起動時の実行者の不一致の検知（`subagent-start-check`）

## ユーザーストーリー

**[As a]** Claude Code に作業を任せる開発者として、

**[I want]** コマンドやビルドの副作用でチケットの範囲外に差分が生じたら、その場で AI に気づかせて片付けさせたい。

**[So that]** 完了時のコミットに範囲外の変更が紛れ込まず、チケットの宣言どおりの差分だけがレビューに載るため。

**[As a]** 同じセッションで作業を続ける開発者として、

**[I want]** 一度承認した未記載パスへの書き込みを、同じセッションの中で何度も確認されたくない。

**[So that]** 確認の往復を必要な箇所に絞れるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 作業中のチケットが無いとき、Shall not フックは何もせず、AI に何も伝えてはならない。
- When 作業中のチケットがある状態で AI の操作（ファイルの書き込み・コマンドの実行）が完了したとき、Shall フックはチケットの着手時点の基準点以降の差分と未追跡ファイルを調べ、禁止範囲または承認されていない未記載パスに差分があれば、対象パスの一覧と復旧の指示（許可範囲内へ戻す、または必要ならユーザーに提案する。迂回しない）を AI に伝えなければならない。
- When 差分が許可範囲・宣言の範囲・承認済みの範囲の中だけにあるとき、Shall not フックは AI に何も伝えてはならない。
- When 差分の対象が移動やリネームであるとき、Shall フックは移動先のパスを判定の対象としなければならない。
- When 機構自身の記録（判定の記録・セッション内の記憶）や、機構が生成する全体計画の置き場に差分があるとき、Shall not フックはそれを違反として扱ってはならない。
- When 差分を検知したとき、Shall not フックは作業ツリーへの自動的な巻き戻し（破壊的操作）を行ってはならず、復旧は伝えられた指示に従って AI が行う。
- When 未記載のパスへの書き込みが `workflow-guard` の確認を経て実行されたとき、Shall フックは承認された範囲（既定は親ディレクトリ単位。設定で指定した特別なファイルはファイル単位）をセッション内の記憶として記録し、以後同じセッションでは `workflow-guard` が再確認しない状態にしなければならない。
- When 毎回確認する範囲への書き込みが実行されたとき、Shall not フックはそれを記憶に記録してはならない（次回も確認する）。
- When セッションが変わったとき、Shall 記憶は引き継がれず、未記載のパスは改めて確認の対象になる。
- When 作業中のチケットの先行チケットが未完了のまま作業が進んでいるとき、Shall フックは依存違反として未完了の先行チケットを AI に伝え、先に完了させるか計画を見直すよう促さなければならない。
- When 作業中のチケットのタスクの種類が、着手時点でコミットされた値から書き換えられているとき、Shall フックはチケットの改変として元の値と現在の値を AI に伝え、元に戻すよう促さなければならない。
- When フックが違反・警告を伝えたとき、Shall その記録（対象パスまたはチケット・違反の種類）が残り、フィードバック計画の振り返りで AI とユーザーが参照できなければならない。記録に機密情報を含めない。
- When AI に伝えるとき、Shall メッセージは違反の種類ごとに機械的に区別できる識別子を持ち、対象と対処を含んでいなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは検知を行わず、停止していることが記録から分かるようにしなければならない。
- If 作業中のチケットの着手時点の基準点の記録が見つからない場合、Then フックは基準点が無いことを AI に伝え、差分の判定は行わずに通さなければならない（着手は提供コマンドで行われるため、通常は起きない）。

### 例外フロー

- If 作業中のチケットが 2 枚以上ある、設定が読めない、チケットの種類が不正である場合、Then フックは判定不能として何も伝えずに抜けなければならない（これらの拒否は `workflow-guard` が操作の前に行う）。
- If 差分の取得に失敗した場合（git が使えない等）、Then フックは何も伝えずに抜け、AI の操作を止めてはならない（事後の検知は案内側の仕組みであり、拒否側の `workflow-guard` が前段で働いている）。

## 前提条件

- チケットの着手が提供コマンドで行われ、着手の時点の差分の基準点（そのときの HEAD）が機構に記録されること
- `workflow-guard` が導入され、未記載のパスへの書き込みで確認を求めること
- タスクの種類ごとの上限を定める設定が、セッション内の記憶をファイル単位で持つ特別なファイルの一覧を含むこと

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。判定の材料は `workflow-guard` と同じ設定・チケット・記憶であり、独自の許可範囲を持たない。差分の取得は git の状態から行う。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: 差分の復旧は AI が行い、機構は巻き戻さない
- **外部的制約**: フックは AI に伝えるだけで操作を遡って拒否できないため、事前の拒否は `workflow-guard` に委ねる

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | 作業中のチケットが無いときは即座に抜ける。あるときも差分の取得を 1 回で済ませ、操作ごとの遅延を体感できない範囲に収める |
| セキュリティ | 記録とメッセージに機密情報を含めない。差分の内容そのものは伝えず、パスだけを伝える |
| 可用性 | 判定できないときは何も伝えずに通し、AI の操作を止めない |
| 保守性 | 判定の規則は `workflow-guard` と 1 か所で共有し、複製しない。メッセージの識別子は機械的に分類できる |
| テスト容易性 | 作業領域の状態と差分を与えて、伝える内容と記憶の記録を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
