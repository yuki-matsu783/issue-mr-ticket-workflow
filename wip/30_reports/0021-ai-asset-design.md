## 実施した内容と結果

### f1. `scope.sh` の出力の形を `cmdpos.sh` と同じ形式で定めた ◎良

`scope.sh` は 4 本のフックが共有するのに、仕様に書かれていたのは「戻り値 0/1/2」と HK-T15 の「段階番号が返る」だけだった。**両立しない**（bash の戻り値は 1 つしか返せない）うえ、関数名は `scope_classify` 1 つしか出てこない。対照的に `cmdpos.sh` は §7-9「出力の形」で完全に定義されている。

- **決定**: §8 に §7-9 と同じ形式の表を置いた（7 関数 × 種類 / 出力変数 / 戻り値）

| 関数 | 種類 | 出力変数 | 戻り値 |
|---|---|---|---|
| `scope_load` / `scope_load_ticket` / `scope_load_approvals` | 読み込み | `SC_COMMON_*` / `SC_TYPE_*` / `SC_TICKET_TYPE` / `SC_DECL_*` / `SC_APPROVED[]` / `SC_ERROR` | 0 / 1 / 2 |
| `scope_resolve <path>` | 判定 | `SC_DECISION` / `SC_ID` / `SC_STAGE` / `SC_ASK_SCOPE` | 常に 0 |
| `scope_classify <セグメント番号>` | 判定 | `SC_CLASS` / `SC_TARGETS[]` | 常に 0 |
| `scope_match` / `scope_op_declared` | 述語 | なし | 真偽 |

- **判定結果は戻り値ではなく変数で返す**。読み込みの成否だけを戻り値にするのは、`set -e` の意味（失敗したら止まる）と合う
- HK-T15・HK-T16 の期待値をこの形に合わせた

結論: 「仕様書は実装・テストが推測なしに作れる粒度まで決める」という自分たちのルールを、`scope.sh` について満たした。参考実装が正になってしまう状態を避けられた。DDR `i0009-33`。

### f2. 戻り値 0/1/2 の規約は読み込み系の 3 関数だけに適用する ◎良

`i0009-16` は「`scope.sh` の関数の戻り値は 0/1/2」と**関数を限定せずに**書いていた。ところが `scope.sh` には真偽を返す述語関数がある（`scope_match` の「一致 0 / 不一致 1」、`scope_op_declared` の「宣言なしが 1」）。このままだと「一致しない（1）」が呼び手で「記載不正 → WF211」と誤読される。

- **決定**: 規約を**読み込みの 3 関数だけ**に限定し、述語関数は真偽を返すと明記した。判定関数の戻り値は常に 0
- 理由は bash の慣習（`if scope_match "$p" "$pat"; then` と書けるのが読みやすさの本体）と、`scope_match` に「ライブラリ不在」を返す場面が無いこと（パターン照合は純 bash で `frontmatter.sh` に依存しない）
- HK-T16 を「読み込み系は 3 状態、述語は真偽」に書き直した

結論: 規約は「どの関数に効くか」まで書かないと規約にならない。DDR `i0009-34`。

### f3. `fm_*` の呼び出し規約を書き方まで降ろした ✕問題

`i0009-16`（スタブは戻り値 2）と `i0009-14`（`scope.sh` は 1 と 2 を潰さない）が成立して初めて `WF209` / `WF211` を区別できる。ところが**どう書けば潰さないかが仕様に無かった**。bash には戻り値を静かに失う書き方が 2 つある。

- **`local v=$(fm_get "$f" k)`**: bash の仕様上 `local` 自身の終了ステータス（常に 0）が `$?` になり、**戻り値が黙って消える**
- **`|| true`**: `set -e` で落ちないようにするためだけに書かれ、戻り値を捨てる

**参考実装 `.claude/hooks/lib/scope.sh:101-104` は現に後者を選んでいる**。さらに `scope_load_ticket` は「ファイル不在」「`ticket_type` 空」「スタブ」の 3 つをすべて `return 1` に潰している。

- **決定**: 呼び出し規約を仕様に書いた
  - `local` と代入を**同じ行に書かない**（`local v; v="$(...)" || rc=$?`）
  - **`|| true` を使わない**（`|| rc=$?` で受けて分岐する）
  - 戻り値を使わない呼び出しでも `|| rc=$?` で受け、**無視すると決めたことがコードから読める**ようにする
  - **パイプやコマンド置換の中で `fm_*` を呼ばない**（`$(...)` の中の非 0 は `set -e` の対象外）
  - **`FM_AVAILABLE` を設定するのは読み込み行**（読めたら 1、`nop` なら 0）。`frontmatter.sh` 自身は設定しない — 読み込めていないときに実行されるのはスタブの側なので、ライブラリに任せられない

**なぜ ✕ か**: 設計で 2 チケット（0014・0015）かけて決めた区別が、**実装では既に消えている**（参考実装が `|| true`）。規約を書いたが、他に戻り値を失う書き方が無いことを網羅的に確かめていない。「方針を書けば守られる」という前提が 1 度崩れた場所なので、実装フェーズで実際に守られるかを見る必要がある。

結論: 規約は書き方まで降りて初めて効く。DDR `i0009-35`。

### f4. 読み込み行のバイト一致を `SS-T05` で固定する △注意

「読み込み行はコピーして引数だけを変え、中身を自作・改変しない（実体は雛形が正）」という規約があるのに、**一致を検査する手段が無かった**。`__ss_load` を持つファイルはリポジトリ内に **20 本以上**あり、現行の全コピーは `FM_AVAILABLE` をどこにも設定していない（`i0009-35` で決めた項目が全コピーに無い）。唯一の関連テスト `test_templates.sh` は雛形だけを読む。

- **決定**: `SS-T05` を新設。すべての `.sh` の `^__ss_load() {` の行が雛形のそれと**バイト一致**する。違えば失敗し、**違うファイルを列挙する**
- 0016（実装計画）に「読み込み行の一斉置換（20 本以上）」を作業項目として立てる

**△ の理由**: 検査は安いが、**一斉置換の作業が実装フェーズの工数に乗る**。しかも `scope.sh` は `nop` ポリシーの主役なので、直し忘れると `HK-T16` が通らないか、通っても本番経路が旧仕様のまま残る。

結論: 「コピーせよ」という規約は、一致を検査しない限り必ずドリフトする。DDR `i0009-36`。

### f5. `jq` 1 回の制約は `--slurpfile` で解ける（0019 の宿題）◎良

0019 は「ホットパスで起動してよい外部プロセスは `jq` 1 回だけ」と決め、**`workflow-guard` がそれで書けるかを未確認のまま ✕問題として残した**。このフックは stdin のフック入力と `scope-limits.json` の 2 つの JSON を要る（チケットの frontmatter は純 bash の `frontmatter.sh` で読むので問題にならない）。

- **決定**: `hook_read_input` が **`jq` の `--slurpfile`** で `scope-limits.json` を副入力として渡し、**stdin と設定を 1 回の `jq` 呼び出しで読む**
- 上限を「`jq` 2 回」に緩める案は却下した。**上限が要求に押されて動くなら制約として機能しない**し、5 本が並列に走るので 1 回の増加が 5 プロセスの増加になる
- `scope-limits.json` を平文形式に変える案も却下（ユーザーが管理する設定なので可読性を落とさない）
- 読み取りが 1 か所に集まる利点もある（各フックが設定の読み方を自作しない）

結論: **0019 の ✕問題が解消した**。上限を守ったまま要求を満たせる。DDR `i0009-37`。

### f6. 書き込みヘルパを `hook-common.sh` に置き、`cmdpos_operands` を足した ◎良

- **書き込みヘルパ**（`i0009-23` の実装面）: `hc_append_jsonl <file> <line>`（4 KB 未満に切り詰めて `>>`）/ `hc_json_write <file> <content>`（一時ファイル + `mv`）/ `hc_lock` `hc_unlock`（`mkdir` ロック・2 秒でタイムアウト・`trap` で解放）を `hook-common.sh` に置き、**各フックは自作しない**。`decisions.jsonl` は 11 本すべてが書くので、切り詰めロジックの重複を避ける意味が大きい。ロックの解放漏れを `trap` の登録ごと関数に閉じるのも要点（DDR `i0009-38`）
- **`cmdpos_operands <i>`**（`i0009-30` の実装面）: `CP_ARGS[i]` から `-` 始まりと `--` 以降を除いた**位置引数**を `REPLY_OPERANDS` に展開する。**削除対象か宛先かの解釈は呼び手**（`workflow-state-guard` は `rm` / `git rm` なら全部を元、`mv` なら最後を宛先）。`i0009-17`（ライブラリは分類まで / 照合は呼び手）の線引きがそのまま適用できた（DDR `i0009-39`）

結論: 0019・0020 が決めた規則の実装面が、ライブラリの関数として定まった。

### f7. `agent_transcript_path`・PP-T02・スタブの表記を是正した ◎良

- **R14**: `post-push-usage-report` の入出力が `transcript_path` だけを挙げており、SubagentStop でも同じものを読む記述だった。公式は「The `transcript_path` is **the main session's transcript**, while `agent_transcript_path` is the subagent's own transcript」と定める。読み違えると**メイン分が `subagents[agent_id]` に二重計上**され `last_offset` も競合する。入出力と `--accumulate` 2 を「Stop / PostToolUse は `transcript_path`、**SubagentStop は `agent_transcript_path`**」に直し、`UR-T03` に負のケースを足した
- **R3 の残り**: `HK-T13` の終了コード読みは 0019 で既に除去済みだった（確認）。`PP-T02` の「push 失敗」は**このフックに届かない**（失敗は `PostToolUseFailure` に流れる）ので、失敗ケースは lib 単体でも本体でも検査しないと明記した
- **R15**: §1 と §12 T8 に残っていた「`fm_*` が**空を返す**スタブ」を「**出力なし・戻り値 2** のスタブになり `FM_AVAILABLE=0` が立つ」に更新した（0015 の決定が横断仕様＝前提文書に反映されていなかった）

結論: 0014・0015 の掃き残しのうち、ライブラリに関わる 3 件が片付いた。
