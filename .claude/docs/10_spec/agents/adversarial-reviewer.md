# adversarial-reviewer エージェント 仕様

## 概要・禁止事項

対応する要件は [00_requirement/agents/adversarial-reviewer.md](../../00_requirement/agents/adversarial-reviewer.md)。定義ファイルは `.claude/agents/adversarial-reviewer.md`。

経緯を知らされない読み取り専用のレビュアー。呼び出し元（メインエージェント。`00-workflow-issue-mr-driven` が実施タスクの結果報告を受けた後、`rules/work-defaults.md` の敵対的レビュー要否に従って起動）から対象と観点を受け取り、指摘を JSON で返す。

禁止事項:

- ファイルの作成・変更、git 操作、リモートへの投稿（MR コメントを含む）
- 実装の経緯（`git log`、チケットの作業ログ、計画書の「判断と根拠」、過去のレビュー）を読むこと
- 観点を自分で集めに行くこと（渡されたものだけ）
- 該当の無い観点の「問題なし」の列挙、水増しの軽微な指摘（**実際に中身を見て否定できたものを `checked_ok` に書くのはこれに当たらない**）
- 実装の意図の推測による指摘の取り下げ
- 講評・要約の散文

## 呼出条件

- 呼び出し元がタスクの切れ目の前（結果報告の受領後、push の前）に Agent ツールで起動する。実施タスクのサブエージェントからは起動の要求だけが返る（入れ子不可）
- 実施回数の上限はフェーズごとに呼び出し元が持つ（`rules/work-defaults.md` の敵対的レビュー要否欄。既定 1 回）。エージェント側に緩める手段は無い
- 毎回新しいコンテキスト（前回の指摘を渡さない）

## IN / OUT

| IN | OUT |
|----|----|
| レビュー対象（差分の基準 SHA..HEAD、または対象ファイルの一覧）、レビュー観点（成果物ルールの観点章から呼び出し元が集めた箇条書き。無ければ無し）、対象の種類（コード / 文書） | 指摘の JSON 配列（0 件なら `[]`）と、レビューできなかった対象の一覧 |

## IN / OUT サンプル

起動プロンプト（`assets/adversarial-review-prompt.template.md`）:

```
対象: 差分 wip/tmp/adversarial-1.patch（5c19f25..a1b2c3d。ファイル: src/auth/validate.ts, tests/auth.spec.ts）
種類: コード
観点:
- [bash-script/堅牢性] ...
- [design-docs/テスト・機械的検査] ...
出力: 下記スキーマの JSON だけを返す
```

出力:

```json
[
  {"path": "src/auth/validate.ts", "line": 42, "severity": "high", "confidence": 0.8,
   "problem": "空文字のパスワードが通る", "when": "password が \"\" のとき trim 後の長さ判定が無い",
   "fix": "length === 0 を先に弾く", "perspective": "堅牢性", "verified": true}
]
```

- `severity`: `high` / `medium` / `low`。`confidence`: 0〜1（裏取り済み `verified: true` でなければ 0.7 以上を付けない）。`perspective`: 渡された観点名、観点外なら `"観点外"`
- レビューできなかった対象: `{"unreviewed": [{"path": ..., "reason": ...}]}` を配列の後に添える（無ければ省略）
- **確かめて問題なしと判断した点**: `{"checked_ok": [{"perspective": ..., "what": ..., "how": ...}]}` を添える（申し送り 0022 E3）。`what` は確かめた具体的な事柄、`how` は確かめ方（読んだファイルと行、突き合わせた対象）。**該当の無い観点を「問題なし」として並べることとは違う**（それは引き続き禁止）。ここに書けるのは、指摘になりうると思って**実際に中身を見に行き、見た結果として否定できた**ものだけである。呼び出し元はこれを読んで「見ていない範囲」と「見たうえで問題が無かった範囲」を区別する
- **抜き取り検証の一覧**: `{"sampled": [{"claim": ..., "source": ..., "result": "一致" | "不一致" | "確かめられない"}]}` を添える（申し送り 0022 E3）。レビュー対象が「N 件を反映した」「すべて通る」のような**まとめの主張**を含むとき、そのうち何件かを抜き取って実体と突き合わせた記録を残す。`claim` は主張の引用、`source` は突き合わせた実体（ファイル:行、コマンドの出力）、`result` は突き合わせの結果。`不一致` は指摘として配列にも載せる。**まとめの主張を数えずに信じない**ことをこの一覧で担保する

## ツール権限

| 許可 | 不許可 |
|------|--------|
| `Read` `Glob` `Grep` のみ | `Bash`（`git log` / `git blame` / `gh` を止める手段が無いため与えない。敵対的レビューは切れ目の前 = 作業中チケット 0 枚で起動され `workflow-guard` が判定しない）、`Edit` `Write` `MultiEdit` `NotebookEdit`、`Agent`、`WebFetch` / `WebSearch` |

差分は Bash を使わずに読めるよう、呼び出し元が起動前に `git diff <base_sha>..HEAD > wip/tmp/adversarial-<n>.patch` を書き出し、起動プロンプトでそのパスと対象ファイルの一覧を渡す。エージェントは patch とファイル本体（`Read`）と周辺（`Grep`）だけで裏取りする。読み取り専用はツール権限で機械的に担保し、定義本文の禁止事項は多重防御に徹する。

## 定義ひな形

```markdown
---
name: adversarial-reviewer
description: 経緯を知らされない読み取り専用のレビュアー。渡された対象と観点で欠陥を探し、位置・重大度・確度付きの指摘を JSON で返す
tools: Read, Glob, Grep
model: claude-fable-5-1
---
（本文: 役割 / 入力（patch のパス・対象ファイル・観点）/ 進め方 5 段階 — 観点の突き合わせ → 観点外の探索（境界値・エラー経路・波及先・説明と実体の食い違い）→ **まとめの主張の抜き取り検証** → 各指摘への反証 1 回 → 確度の申告 / 禁止事項 / 出力スキーマ / 0 件・unreviewed・checked_ok・sampled の扱い / 文書対象でも同じ姿勢）
```

### モデルの選び方

`model` には**実行者と別のモデル**を指定する（既定は `claude-fable-5-1`）。`inherit` にすると呼び出し元と同じモデルになり、同じ癖で同じ見落としをする。敵対的レビューの値は「別の目で見る」ことにあるので、モデルを分けることをここで固定する。

- 呼び出し元（メインエージェントまたは `task-executor`）と同じモデルを指定しない
- **定義の固定値だけでは「別のモデル」を保証できない**。チケットの `executor` がたまたま同じモデル（この既定なら fable）のとき、レビュアーと実行者が一致する。保証するのは**起動する側**で、`00-workflow-issue-mr-driven` 手順 2a が、レビュー対象を作った実行者と定義の `model` を突き合わせ、一致していれば Agent ツールの `model` で別のモデルに差し替えて起動する（差し替えたことを切れ目のコメントに残す）。エージェント側にこの判定を持たせないのは、自分を起動したモデルを知る手段が無いためである
- プロジェクトが別のモデルを使いたい場合は `rules/work-defaults.md` に書き、定義ファイルの `model` をそれに合わせる（`work-defaults.md` はタスクの実行者のモデルを定める表なので、敵対的レビュアーの行を持つときは「レビュアー」と明記する）
- モデル名の妥当性は機構が検査しない（存在しないモデル名を書くと起動時に失敗する）

## 参照ナレッジ

- 観点章の正: `rules/ルール体系.md` の章スキーマ（観点の収集は呼び出し元が行う）
- 指摘の投稿と返信: `00-workflow-issue-mr-driven` 手順 3（`boundary.sh note` でインラインではなく通常コメント、またはレビュー API — 投稿手段は呼び出し元の判断。指摘の選別は `confidence >= 0.5` を既定）
- 敵対的レビュー要否の既定: `rules/work-defaults.md`

## テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| ADV-E01 | 観点を数個渡してレビューを依頼する | 渡された観点で突き合わせたうえで、観点外の欠陥（境界値・エラー経路・波及先・説明と実体の食い違い）も探す | 指摘の `perspective` に「観点外」が現れうること |
| ADV-E02 | 欠陥が見つからない対象 | 空の配列を返す。該当の無い観点の「問題なし」や軽微な指摘で水増ししない | 返した配列の中身と `checked_ok` の書き分け |
| ADV-E03 | 「N 件すべて反映した」のようなまとめの主張を含む対象 | 何件かを抜き取って実体と突き合わせ、`sampled` に主張・突き合わせ先・結果を残す。数えずに信じない | `sampled` の有無と `source` の具体性 |
| ADV-E04 | 指摘の裏取りが patch だけでは足りない | ファイル本体と周辺を読んで確かめる。確かめられなければ `confidence` を 0.7 未満にする | `verified` と `confidence` の組み合わせ |
| ADV-E05 | 読めない対象（バイナリ・巨大ファイル）が混ざっている | 読めた分だけでレビューを装わず、`unreviewed` に理由付きで返す | `unreviewed` の記載 |
| ADV-E06 | 実装の意図を推測すれば説明のつく欠陥 | 意図の推測で指摘を取り下げない。確度を下げて出す | 指摘の残存と `confidence` |
| ADV-E07 | 実際に中身を見たうえで問題なしと判断した点がある | `checked_ok` に何をどう確かめたかを書く。見ていない範囲と区別できるようにする | `checked_ok` の `what` と `how` |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン 1: 対象と観点を渡されて起動・観点を集めに行かない | 呼出条件、IN / OUT、禁止事項 |
| メイン 2: 観点の突き合わせ + 観点外の探索・「問題なし」を並べない | 定義ひな形（進め方）、禁止事項 |
| メイン 3: 裏取りは読み取り専用・経緯は読まない | ツール権限（Read / Glob / Grep のみ。Bash 無しで `git log` を物理的に読めない）、禁止事項 |
| メイン 4: 反証 1 回・裏取りなしの高確度禁止 | 定義ひな形、`confidence` の規則 |
| メイン 5: 指摘の内容（位置・重大度・確度・3 点）と機械可読な形 | 出力スキーマ（`findings`） |
| メイン 6: 確かめて問題なしと判断した点を返す | 出力スキーマ（`checked_ok`）、定義ひな形の進め方 5 段階（申し送り 0022 E3） |
| メイン 7: 件数・網羅の主張は抜き取って実体と突き合わせる | 出力スキーマ（`sampled`）、定義ひな形の進め方 5 段階（申し送り 0022 E3） |
| メイン 8: 0 件は `[]`・水増し禁止 | IN / OUT、禁止事項 |
| メイン 9: 書き込み・git 操作・リモートへの投稿をしない | ツール権限、禁止事項 |
| メイン 10: 意図の推測で指摘を取り下げない | 禁止事項 |
| 代替 1: 観点が渡されなければ一般観点 + 注記 | IN / OUT（無ければ無し）→ 定義ひな形 |
| 代替 2: 文書も同じ姿勢・指摘の形も変えない | 定義ひな形 |
| 例外 1: 読めない対象は `unreviewed` に理由付きで返す | 出力スキーマ（`unreviewed`）、禁止事項（読めた分で装わない） |
| 整合 1: レビュー対象を作った実行者と別のモデルで動く | 「モデルの選び方」 |
| 整合 2: 実施ごとに新しいコンテキスト・上限は機構側が持つ | 呼出条件、禁止事項（上限を緩める手段を持たない） |
