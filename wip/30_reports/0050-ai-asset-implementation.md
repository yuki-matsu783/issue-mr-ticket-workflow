## 実施した内容と結果

### e1. レビューの重みの ◇ の見出しを「判断が欲しい」に変えた ◎良

`report.template.html` の 2 か所（冒頭のガイドコメントと `#focus-want` のラベル）と `report.template.md` の 1 か所を変えた。副題は「決めた方針の承認 / 決められない点の判断」とし、本文のガイドも「自分で決めた判断と根拠、または決めずに候補と比較軸を並べた点」に直した。

`.claude/skills/*/assets/` に「承認が欲しい」は 0 件。`.claude/skills/` 全体では `20-common-step-report-view/SKILL.md` に 1 件残っていて、これは S4（0053）の担当。

根拠: `20-common-step-report-view` 仕様 OUT ひな形の視覚語彙（「◇ の欄の見出しは『判断が欲しい』とし、書き手が方針を決めていることを前提にした文言にしない」）。

### e2. フィードバック計画のひな形に消し込み表の節を足した ◎良

「確認した記録の範囲」と「改善候補の一覧」の間に「消し込み表」の節を置いた。列は 走査した記録 / 抽出した項目 / 行き先（候補 #n / 既に反映済み / 候補にしない + 理由）。ガイドに「行数が『確認した記録の範囲』の件数と一致することを確かめてから候補の一覧へ進む」と「この表が無いと拾ったのに載せ損ねた項目が誰にも気づかれない」を書いた。

あわせて、同じひな形の類型のガイドが省略形（`(a) 無かった` など）だったので、機構の定義と同じ文言（`(a) アセットが無かった` など）に直した。

根拠: `10-task-feedback-plan` 仕様 OUT ひな形の「消し込み表」の行と、処理フロー 2 の但し書き。

### e3. 引数・環境の誤りを BD006 / FN004 に分けた ◎良

`boundary.sh` と `finalize.sh` の `arg_ng` が、呼び方が成立していない誤り（未知のサブコマンド・値の無いオプション・依存コマンドの不在）を、前提未充足と同じ `001` の番号で返していた。終了コードだけが 2 で違うという状態で、番号を見た呼び手が前提を直そうとしてしまう。番号を末尾に足した `BD006` / `FN004` に変え、コメントも「仕様に専用番号が無いため」という逸脱の記録から、番号の意味の説明に書き換えた。

変更は 1 行ずつの 2 か所で、既存の `BD001`〜`BD005` / `FN001`〜`FN003` は振り直していない。振り直すとテストの期待値・実装・レポートの記述が連動して壊れる。

ロックアウト対策として、書き換えた直後に `commit.sh` で自分をコミットし（`96c2b1d`）、続けて `boundary.sh status` が JSON を返すことを確かめた。切れ目の判定が動く経路を実際に踏んでから次に進んでいる。

根拠: `00-workflow-issue-mr-driven` 仕様 エラー識別子（`BD006`）、`10-task-overall-summary` 仕様 エラー識別子（`FN004`）、DDR `i0010-07`（番号は末尾に足す）。

### e4. テスト BD-T19 / FN-T18 を足した ◎良

仕様のテスト観点どおり、1 つの ID に 3 つの原因（未知のサブコマンド / 値を取るオプションに値が無い / 必要な外部コマンドが無い）を並べた。依存コマンドの不在は `test-lib.sh` の `make_restricted_path bash git` で `jq` の無い PATH を作って踏ませている。

同じ ID の中で、`-h` と `--help` が終了 0 で使い方を出すことと、前提未充足が `BD001` / `FN001` と終了 1 のまま変わらないことも確かめている。番号を分けた変更が、分けるべきでない側まで動かしていないことを 1 つのケースで見られる。

根拠: `run-tests.sh --filter '*test_boundary*'` が `OK: 1 本 / 19 件`（`passed=112 failures=0`）、`--filter '*test_finalize*'` が `OK: 1 本 / 18 件`（`passed=69 failures=0`）。
