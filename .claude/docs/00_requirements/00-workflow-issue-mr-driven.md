# 00-workflow-issue-mr-driven スキル

## 概要

開発作業向けの振り分けスキルの要件を定義する。依頼を受けたら全体計画チケットを置き、全体計画ワーク（issue の確定・ブランチと draft MR の作成・フェーズ列の合意まで）を経て、以降のワークを順に起動し、人間レビューが必要なワークの切れ目で MR 上のレビューを挟み、全体まとめで draft 解除まで進める。このスキルはワークの起動順序と切れ目の処理を司るオーケストレータであり、各ワークの中身は work スキルに、issue・ブランチ・MR の操作は task スキルに委ねる。本書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

- **背景**: チケット駆動の実作業だけでは「その作業がどの issue に対するもので、どの MR に載るのか」「どこで人間が確認するのか」が決まらない。作業の起点を issue に固定し、ワークの切れ目で人間の判断を挟む順序を 1 か所で司りたい。
- **目的**: 「全体計画チケットの着手 → 全体計画ワーク → ワークの繰り返し（レビュー要のチケットを含むワークの後は人間レビュー）→ フィードバック計画 → 全体まとめ（draft 解除）→ 停止」の順序を固定し、すべての作業が 1 issue = 1 ブランチ = 1 MR に紐づき、レビューが必要な箇所を飛ばして進めない状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md と参照資料）、ワークの構成（種類・順序・担当・切れ目の規則）、全体計画チケットの配置、ワークの起動（メインエージェントで行うかサブエージェントに委ねるかの振り分け・次のワークの選択）、切れ目の処理（push・MR 本文更新・レビュー依頼と完了・指摘への追加チケット・未着手チケットの見直し）、再開
  - 含まない: issue の確定・ブランチと draft MR の作成・フェーズ列の合意（`10-work-overall-plan`）、各ワークの内容と承認（`10-work-*`）、issue / ブランチ / MR の操作手順（task スキル）、宣言範囲の強制やワーク境界の判定の仕組み（仕様書）、MR のマージ（人間が行う）

---

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼した作業を issue と MR に紐づけて、レビューが必要なワークの切れ目で MR 上のレビューを挟みながら進めたい。

**[So that]** AI の作業を必要な箇所で確認でき、依頼・合意・作業・成果の経緯を GitLab / GitHub 上で追えるため。

## 受け入れ基準（Acceptance Criteria）

### ワークの構成

このスキルが組み合わせるワークは次の 15 種で、issue ごとにこの中からフェーズ列を組む。各ワークの中身（成果物の書き方・チケットの起こし方・そのワークの中の承認）は対応する work スキルの要件定義書が正とし、ここでは種類・順序・担当・切れ目の規則だけを定める。

担当の整理は 1 つだけ: **全体計画・フィードバック計画・全体まとめ**は承認や対話が多く挟まるためメインエージェントが work スキルを読み込んで行い、**それ以外のワーク**はサブエージェントが work スキルを読み込んで行う。どちらも同じ work スキルを使い、違いは誰が実行するかだけ。

| # | ワーク名 | 種別 | 担当 | 主な成果物 |
|---|---|---|---|---|
| 1 | 全体計画 | 計画 | メインエージェント | 確定した issue、feature ブランチと draft MR、全体計画書（issue の種別・フェーズ列・受け入れ条件との対応・各チケットの実行者とレビュー要否の方針）、最初の計画チケット |
| 2 | 調査計画 | 計画 | サブエージェント | 調査計画書、調査チケット群、次の計画チケット |
| 3 | 調査実施 | 実施 | サブエージェント | 調査結果レポート（md + HTML） |
| 4 | 設計計画 | 計画 | サブエージェント | 設計計画書（書く設計文書の一覧と骨子）、設計チケット群 |
| 5 | 設計実施 | 実施 | サブエージェント | 要件定義書・仕様書（アプリ本体向け `docs/`）、設計結果レポート |
| 6 | 実装・テスト計画 | 計画 | サブエージェント | 実装計画書（変更対象・許可範囲案・テスト方針）、実装チケット群 |
| 7 | 実装・テスト実施 | 実施 | サブエージェント | コードとテスト、実装結果レポート |
| 8 | フィードバック計画 | 計画 | メインエージェント | ここまでの振り返り（チケットの作業ログ・レビュー指摘・拒否の記録から洗い出した反映すべき内容）と、候補ごとの「この MR で対応 / 別 issue」の決定、後続フェーズ（設計反映・AI アセット設計・AI アセット化）のチケットの作成・修正、別 issue の起票 |
| 9 | 設計反映計画 | 計画 | サブエージェント | 実装と設計文書の差分一覧と書き戻し計画 |
| 10 | 設計反映実施 | 実施 | サブエージェント | 実装に合わせて更新した設計文書、DDR |
| 11 | AI アセット設計計画 | 計画 | サブエージェント | `.claude/docs/` に書く要件・仕様の一覧と骨子 |
| 12 | AI アセット設計実施 | 実施 | サブエージェント | `.claude/docs/` の要件定義書・仕様書・用語辞書・DDR |
| 13 | AI アセット化計画 | 計画 | サブエージェント | 変更するフック・スキル・ルール・エージェント・設定の一覧とテスト方針 |
| 14 | AI アセット化実施 | 実施 | サブエージェント | フック・スキル・ルール・エージェント・設定とそのテスト |
| 15 | 全体まとめ | まとめ | メインエージェント | 残った反映すべき内容の別 issue 起票、default ブランチとの衝突解消、統括レポート（md + HTML）、MR 本文の最終化、関連 issue へのコメント、作業領域の片付け、push、draft 解除 |

- When フェーズ列を決めるとき、Shall 全体計画ワークは issue の種別（アプリ / AI アセット。両方を含む issue は両方）を判定してユーザーと合意し、種別ごとの次のテンプレートを土台にしなければならない。先頭は全体計画、末尾は全体まとめとし、調査とフィードバック計画は必ず含める。

| issue の種別 | フェーズ列のテンプレート |
|---|---|
| アプリ（`docs/`・ソースコードの変更が主目的。AI アセットへは副産物として反映） | 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計反映 / AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |
| AI アセット（`.claude/` 配下の変更が主目的） | 調査 → AI アセット設計 → AI アセット化 → フィードバック計画 → 追加の AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |

- When テンプレートを当てるとき、Shall 主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット化）は依頼の性質に応じて全体計画で含め、フィードバック計画より後のフェーズは全体計画では決めずフィードバック計画で決めなければならない。フィードバック計画以外のフェーズは「計画 → 実施」の対で並べる（片方だけの採用は不可）。
- When フェーズを並べるとき、Shall 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計反映 → AI アセット設計 → AI アセット化 → 全体まとめ の順とし、含めないフェーズだけを飛ばさなければならない。
- When 含めたフェーズでやることが無いと計画ワークで分かったとき、Shall そのフェーズを省くのではなく、計画チケットを「対象なし」として即座に完了し、次のフェーズの計画チケットを起こさなければならない（まだ行っていない全体計画の段階で「やらない」と判断しない）。
- When 計画ワークが完了するとき、Shall その計画ワークは同じフェーズの実施チケット群と、次のフェーズの計画チケット 1 枚を作成済みでなければならない（チケットを最初に全件作らない）。
- When ワークの中のチケットを実施するとき、Shall チケットは既定ではそのワークの実行者（メインエージェントまたはワークのサブエージェント）の中で順に実施され、互いに依存しないチケット群を並列に進めたいとき、または新しいコンテキストで実施したいとき（チケットの実行者がワークのモデルと異なるときを含む）に限り、チケット単位でさらにサブエージェントに分割しなければならない。分割したチケットにも宣言した範囲の強制が同じように働く。
- When 1 つのワーク（同じ種類のチケット群）が完了したとき、Shall そこをワークの切れ目とし、そのワークのチケットに 1 枚でも「人間レビュー要」のものがあれば、MR 上の人間レビューが完了するまで次のワークに進めてはならない。

### メインフロー

- When このスキルで進めると決まったとき、Shall スキルは最初に全体計画チケットを作成して作業中に置き、以降のプロンプトで振り分けの再宣言を求められない状態にしてから、全体計画ワーク（`10-work-overall-plan`）に入らなければならない。全体計画チケットの作業中に限り、issue・ブランチ・MR の作成と push を行える。
- When 全体計画ワークに入ったとき、Shall スキルはメインエージェント自身で `10-work-overall-plan` を読み込んで実施しなければならない（issue の確定・ブランチと draft MR の作成・全体計画の合意・最初の計画チケットの作成。手順と承認はそちらが正）。
- When 全体計画チケットが完了したとき、Shall スキルはワークの切れ目の処理（push・MR 本文への全体計画の要約の追記・レビュー要否に応じたレビュー依頼）を行い、以降は機構が示す次のワークに順に入らなければならない。
- When 次のワークに入るとき、Shall スキルはそのワークが全体計画・フィードバック計画・全体まとめのいずれかならメインエージェント自身で対応する work スキルを読み込んで実施し、それ以外ならサブエージェント（全体計画で合意したモデル）に対応する work スキルを読み込ませて委ね、自身はワークの起動・結果報告の受け取り・ワークの切れ目の処理に徹しなければならない。
- When 1 つのワークが完了し、そのワークに人間レビュー要のチケットが 1 枚でも含まれるとき、Shall スキルは push し、MR 本文にそのワークの要約を追記し、レビュー観点（差分範囲・見てほしい点・次のワーク）を添えて MR 上でレビューを依頼し、応答を終えなければならない。
- When 1 つのワークが完了し、そのワークのチケットがすべて人間レビュー不要のとき、Shall スキルは push し、MR 本文に要約を追記し、人間レビューを省略して次のワークに進むことをユーザーに報告した上で続けてよい。
- When レビュー完了の連絡を受けたとき、Shall スキルは MR 上のレビュー結果と指摘を取得して提示し、対応要否をユーザーに確認せず、指摘のすべてを同じ種類の追加チケットとして起こしてから再度ワークに入らなければならない（完了済みチケットを未完了に戻さない）。
- When ワークが承認され次のワークに進むとき、Shall スキルは未着手のチケット（範囲・実行者・レビュー要否・DoD）をレビュー結果や新しい知見に合わせて見直してよく、変更した場合はその内容をユーザーに伝えなければならない。
- When 指摘が 0 件、または追加チケットのワークも承認されたとき、Shall スキルは機構が示す次のワークに入り、全体まとめまで繰り返さなければならない。
- When フィードバック計画のワークに入ったとき、Shall スキルはメインエージェント自身で `10-work-feedback-plan` を読み込み、ユーザーと対話しながら、ここまでのワークのチケットに残された「うまくいかなかったこと」「AI アセットに反映すべき内容」・レビュー指摘・拒否と確認の記録を振り返り、候補ごとに「この MR で対応する」（既定）か「別 issue として起票する」（変更が大きくなりすぎる場合）かを決め、設計反映・AI アセット設計・AI アセット化のチケットを作成・修正し、別 issue は承認を得て起票しなければならない。振り返りの機会はこの 1 回だけとし、以後のワークで見つかったものは全体まとめで別 issue にする。
- When 全体まとめのワークに入ったとき、Shall スキルはメインエージェント自身で `10-work-overall-summary` を読み込み、フィードバック計画より後のワークで新たに見つかった反映すべき内容の別 issue 起票 → default ブランチとの衝突解消 → 統括レポートの作成 → MR 本文の最終化 → 関連 issue へのコメント → 作業領域の片付け → push → draft 解除 の順に行い、マージは行わず停止しなければならない。
- When 全体まとめの中で作業領域を片付けて push し draft を解除するとき、Shall チケットが無くなった状態でもこれらの操作が機構に拒否されず、振り分けの再宣言も求められてはならない。

### 承認ポイント

各ワークの中の承認（issue の確定、全体計画の合意、フィードバック計画の対応先の合意、衝突解消の方針、issue コメントの本文など）は、そのワークの work スキルが定める。このスキルが持つのはワークの切れ目に関するものだけ。

- When 人間レビュー要のチケットを含むワークの完了後にレビューを依頼したとき、Shall スキルは応答を終えて人間のレビューを待ち、チャット上の質問でセッションを塞いではならない。
- When 人間レビュー不要のワークを省略して次に進むとき、Shall スキルは承認を求めず、省略したことを報告するだけでよい。
- When ユーザーが応答できない実行形態でワークの中の承認が必要になったとき、Shall スキルは承認が必要な内容を報告してセッションを終え、次回セッションの再開から続けなければならない。

### 他のスキル・機構との整合

- When コミット・push・チケットの状態変更・レビュー依頼と完了・マージ前作業を行うとき、Shall スキルは機構の提供コマンド（とそれを使う task スキル）経由でのみ行い、`git` のコミット・push の直接実行、進行状態の直接編集、draft 解除の直接実行を行ってはならない。
- When 全体計画チケット以外のチケットが作業中のとき、Shall not スキルは `glab` / `gh` コマンドや push を実行してはならない（リモートへの操作はワークの切れ目と全体まとめで行う）。
- When 次に入るワークを選ぶとき、Shall スキルは目視で判断せず機構の示す結果に従い、対応する work スキルが無ければ不整合として報告して停止しなければならない。
- When ワークから並列に進めたいチケット群や新しいコンテキストで実施したいチケット（実行者がワークのモデルと異なるものを含む）の要求を受けたとき、Shall スキルがチケット単位のサブエージェントを起動しなければならない。
- When ワークの実施中であるとき、Shall not スキルはチケット運用の手順（着手・完了・作業ログ・DoD）を再掲せず、各ワークの手順を参照しなければならない。

### アルタナティブフロー（代替経路）

- If 現在のブランチに open な MR があり、作業領域にチケット（未着手 / 作業中 / 完了）がある場合、Then スキルは全体計画ワークをやり直さず、現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み）を機構から得て再開しなければならない。レビュー待ちのときはレビュー完了の連絡がない限り応答を終える。
- If 全体計画ワークが「対応なし」で終わった場合（既存の closed な issue の結論を採る等）、Then スキルは全体計画チケットを取り消して停止しなければならない。
- If 全体計画ワークが issue の起票だけで終わった場合（着手の指示が無い）、Then スキルは全体計画チケットを取り消し、着手の指示を待たなければならない。
- If 小さな依頼でレビューの往復が過剰な場合、Then スキルはチケットの人間レビュー要否を「不要」に倒し、やることの無いフェーズは計画ワークで即座に完了することで対処し、必須フェーズの省略やワークの種類の統合で対処してはならない。
- If `glab` / `gh` CLI が使えない環境の場合、Then スキルは機構の外部委任モード（MCP ツールでリモート操作を代行）を使い、WebFetch / curl へ落としてはならない。
- If レビュアーがチャットでレビュー判断を伝えた場合、Then スキルはその判断を MR の通常コメントとして記録してからレビュー完了の手続きに進まなければならない。

### 例外フロー（エラーケース）

- If レビュー依頼が前提未充足（未コミット / 未 push / MR なし / ワークの切れ目でない / 既に依頼済み）で拒否された場合、Then スキルは未充足を解消して再実行し、切れ目でなければ次のチケットに着手しなければならない。
- If レビュー完了の手続きが「変更要求あり」または「未返信のスレッドあり」で止まった場合、Then スキルは同じ種類の追加チケットで対応し、スレッドに返信してから再実行しなければならない。進行状態を直して通そうとしない。
- If サブエージェントに委ねたワークが失敗・中断して結果報告が返らない場合、Then スキルはチケットの状態を機構から確認し、作業中のまま残ったチケットを報告してユーザーの指示を待たなければならない（勝手に完了にしない）。
- If ワークの中の承認で却下された場合、Then スキルはその段階に留まり、先のワークへ進んではならない。

## 前提条件

- 対象プロジェクトが GitLab または GitHub 上の Git リポジトリで、`glab`（GitHub では `gh`）CLI が使えること（導入・認証の確認は全体計画ワークが行う）
- チケット駆動の仕組み（`10-work-*` スキル、提供コマンド、宣言範囲の強制、テンプレート）が導入済みであること
- `00-workflow-quick-request` と対になる振り分けとして、`CLAUDE.md`「作業の振り分け」から呼ばれること

## 制約条件

- **技術的制約**: GitLab（`glab` CLI）を基準に記述し、GitHub では MR → PR、`glab` → `gh` に読み替える。1 セッションは 1 つの MR だけを扱う。サブエージェントはユーザーと対話できず、入れ子にもできないため、承認・対話の多いワーク（全体計画・フィードバック計画・全体まとめ）はメインエージェントが行い、チケット単位のサブエージェントはメインエージェントが起動する
- **ビジネス的制約**: MR のマージ・レビュー完了の判断・チケットのレビュー要否の方針は人間が決める。AI は draft 解除で止まる
- **外部的制約**: 機構の統制に従い、スキル側に迂回経路を書かない。機構側にリモート操作の許可を追加しない

## 非機能要件

| 項目 | 説明 |
|------|------|
| セキュリティ | MR の本文・コメントに環境変数の値・トークン・個人情報を書かない。投稿本文などの一時ファイルは `wip/tmp/`（コミット対象外）に置き、ワークスペース外のパスを使わない |
| 追跡性 | ブランチ名・MR 本文・全体計画・統括レポート・issue コメントのすべてに issue や MR 番号を残す。人間レビューを省略したワークは MR 本文とチャットの両方でそれと分かる |
| 冪等性 | 再開時に全体計画ワークをやり直さず、現在地から続けられる |
| 可読性 | SKILL.md はワークの起動順序と切れ目の処理に集中し、委譲先の手順を再掲しない。読むタイミングごとの詳細は参照資料に分割する |
