  1. 1

    置き場の削除はディレクトリ自身と祖先も拒否する △注意 根拠: 境界レビュー A8（確信度 0.6）、§8 の glob 規則

    i0009-30 は「作業中が 0 枚の切れ目では workflow-guard も判定しないので rm wip/10_tickets/20_done/*.md が誰にも止められない」という穴を塞いだ。ところが追加した判定は wip/10_tickets/20_done/** の glob で、** はパターンの位置より下を指す。rm -rf wip/10_tickets/20_done（ディレクトリ自身）も rm -rf wip/10_tickets も rm -rf wip も一致しない。作業中 0 枚の窓では workflow-guard も判定しないので、塞いだはずの穴が 1 段上のパスにそのまま残っていた。rm -rf wip は進行状態・チケット・計画書・結果報告をまとめて消す。決定: 元が置き場のディレクトリ自身またはその祖先（wip/10_tickets・wip）のときも WF302 / WF303 とする。祖先はどちらの置き場も消すので WF302（作業中の置き場が消える方。回復しにくい）に倒す。

    実測への依存: 一部あり（書き方の網羅は実装で確かめる）

    根拠を見る（読んだ箇所と出力） 
    §8 の glob 規則: `**` は 0 個以上のディレクトリに一致する
  → パターンの位置より下を指す。パターン自身の親には一致しない

rm wip/10_tickets/20_done/0003.md   → 一致する → WF303
rm -rf wip/10_tickets/20_done       → 一致しない
rm -rf wip/10_tickets               → 一致しない
rm -rf wip                          → 一致しない
  かつ workflow-guard は制御方式 1「作業中 0 枚 → 許可」で判定しない

却下: glob の規則を変える（.claude/** がリポジトリルートに一致するなど全部壊れる）
      wip/** を丸ごと保護（wip/tmp/** への書き込みが止まる）
      -rf の有無で拾う（書き方を数える。rm wip/.../20_done を取りこぼす）
      workflow-guard 側で拾う（作業中 0 枚では判定しない＝穴が開いた窓そのもの）
DDR: i0009-59 / テスト: SG-T11（rm -rf wip/tmp と rm -rf logs は通る負のコントロール付き）

    結論

    glob の意味を変えずに、この 1 か所で明示した。ただし書き方の網羅（./wip・wip/・cd wip && rm -rf .）は残課題。

  2. 2

    hc_lock は陳腐化したロックを強制解放する ◎良 根拠: 境界レビュー A7（確信度 0.65）、§3 の fail-open

    i0009-23 は「ロックの解放漏れが一番怖い」と書き、対策を trap にした。ところが同じ共通仕様の §3 が自ら「§1 のラッパーの || も §3 の trap ERR も、打ち切られた場合には効かない」と書いている。post-push-usage-report は transcript を解析する重い処理で、ロックを保持したまま打ち切られる可能性がいちばん高い。そうなるとロックが残り続け、以後の Stop / SubagentStop は毎回 2 秒待って諦め、使用量の集計が恒久的に止まる。決定: hc_lock は取得を試みる前に、ロックの作成時刻が 60 秒より古ければ陳腐化とみなして rmdir してから取り直す。強制解放は実行ログに 1 行残す。60 秒以内は従来どおり 2 秒で諦める。

    実測への依存: あり（60 秒の妥当性は 4c の実行時間の実測で確かめる）

    根拠を見る（読んだ箇所と出力） 
    §3（fail-open）
  §1 のラッパーの || も §3 の trap ERR も、打ち切られた場合には効かない
  （プロセスごと終了させられ、出力が捨てられるため）

60 秒の根拠:
  hc_lock が守るのは JSON を 1 つ読んで加算して書く処理 → 正常なら数十 ms
  command 型フックの既定タイムアウトは 600 秒、UserPromptSubmit は 30 秒（i0009-11）
  → 60 秒は「打ち切られたフックのロック」を確実に拾い、
    「生きているフックのロック」を誤って奪わない範囲

却下: PID で生死を判定（Windows の Git Bash で移植性が無い。PID は再利用される）
      flock（Git Bash に無いことがある。mkdir を選んだ理由がそれ）
      諦めたら記録だけ（人間が手で消すまで直らない）
      タイムアウトを伸ばす（残置ロックには効かない）
      session-start が掃除する（セッションを開き直すまで直らない）
DDR: i0009-60 / テスト: HK-T20

    結論

    「解放漏れが一番怖い」と書いておきながら、いちばん起きやすい経路（打ち切り）に対策が無かった状態を塞いだ。

  3. 3

    usage の加算に hc_lock を使うと個別仕様に書く ◎良 根拠: 境界レビュー B6、grep 'ロック\|lock' = 0 件

    i0009-23 は影響に「post-push-usage-report.md（usage/<branch>.json の加算をロックで直列化）」と挙げていたが、当該仕様に「ロック」の語が 1 つも無かった。実際に競合する --accumulate の加算が無防備で、一時ファイル + mv は「既定」側にだけ入っていた。R22 は §5 と HK-T17 では閉じたが、実装される側の仕様では閉じていなかった（i0009-58 が規約にした型そのもの）。決定: --accumulate と既定の加算に「hc_lock usage-<branch> を取ってから加算し、取れなければ 2 秒で諦めて実行ログに 1 行残して終了 0」を書いた。陳腐化（60 秒）は hc_lock が持つので個別仕様には書かない（数値を 2 か所に置かない）。

    実測への依存: 無し

    根拠を見る（読んだ箇所と出力）

    「logs/usage/.json の該当セッション … に加算し last_offset を更新する」
  一時ファイル + mv は「既定 4」にだけ入っていた

i0009-50（サブエージェントは既定で background）により、
  複数のサブエージェントが同時に走っている状態が既定になった
  → 競合の確率は i0009-23 の想定より高い

却下: §5 への参照だけ（どの段階を当てるかが読み手の判断になる）
