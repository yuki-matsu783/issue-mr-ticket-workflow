# 20-common-step-issue の eval 定義

## 目的

`20-common-step-issue` の SKILL.md（ホスト判定 → 検索は open → 0 件なら closed、1 ページ目のみ → 作成・追記はファイル経由 → 追記は末尾のみで送信直前に再取得）を読み込んだときに、検索の 2 段階・本文のファイル渡し・既存本文の不変が安定するかを確かめる。

## 評価シナリオ

各行は仕様書「テスト観点（eval）」の行と 1:1 に対応する（eval ID が対応の鍵）。

| eval ID | 入力プロンプトと状況 | 期待する振る舞い | 判定方法 | 添付ファイル |
|---------|--------------------|-----------------|---------|-------------|
| IS-E01 | 検索モード。検索語「ログイン login バリデーション validation」。origin は GitHub、open に該当が 0 件で closed に 2 件ある | open を `--limit 21` で検索して 0 件を確認し、`--state all` で再検索して closed の 2 件を得る。番号・タイトル・状態・URL の表と、使った検索語・件数を返す（分類は呼び出し元の基準に委ねる） | 検索が 2 段階（open → all）で行われたこと、表と検索語・件数が返答にあること、2 ページ目以降を取りに行っていないこと | なし |
| IS-E02 | 作成モード。承認済みのタイトル「ログイン検証の不備」と本文案（種別・概要・詳細・受け入れ条件 2 件・スコープ外・優先度）がある | `assets/issue.template.md` を `wip/tmp/issue-body-*.md` に埋め、`gh issue create --title ... --body-file <ファイル>` で作成し、番号と URL を返して一時ファイルを削除する。本文をコマンドライン引数に埋め込まない | 作成された issue の本文が承認済みの本文と一致すること、`--body-file`（GitLab なら `--raw-field description=@`）経由であること、番号と URL の報告、一時ファイルが残っていないこと | `assets/issue.template.md` |
| IS-E03 | 編集モード。既存 issue #34（本文 40 行）に「今回の依頼」の追記が承認済み | 現在の本文を取得し、末尾に `assets/issue-addendum.template.md` を埋めた追記セクションを連結したファイルを作り、送信直前に本文を再取得して一致を確認してから `gh issue edit 34 --body-file <ファイル>` で置き換える。既存の記述を消さない・書き換えない | 追記後の本文が「旧本文 + 空行 + 追記セクション」で、旧本文部分のバイト列が同一であること、送信前の再取得が行われたこと、コメント投稿・状態変更が無いこと | `assets/issue-addendum.template.md`、既存 issue 本文のフィクスチャ（40 行） |

## 比較条件

- with: Skill ツールで `20-common-step-issue` を読み込んだ状態で各シナリオのプロンプトを与える（GitHub 操作は検証用リポジトリの issue に対して行う）
- without: SKILL.md を読み込まず、CLAUDE.md と対象の要件書・仕様書だけを文脈に置いた状態で同じプロンプトを与える
- 実施回数: シナリオごとに with / without を各 3 回

## 効果ありの判定基準

- IS-E01: with の 3 回すべてで検索が 2 段階かつ 1 ページ目のみで、表と検索語・件数が返り、without で 1 回以上 closed を検索しない・表を返さない
- IS-E02: with の 3 回すべてで本文がファイル経由で一致し一時ファイルが残らず、without で 1 回以上コマンドライン引数に本文を埋め込む・テンプレートを使わない
- IS-E03: with の 3 回すべてで旧本文が不変で再取得が行われ、without で 1 回以上既存本文を書き換える・コメントで代替する
- 3 シナリオのうち 2 つ以上で上記を満たせば効果あり。差が出ないシナリオは SKILL.md の該当手順の文言を見直す対象として記録する
