# post-push-usage-report フック

## 概要

push のたびに、前回の push からその push までにかかった AI の対応工数を集計し、MR 上のコメントとして残すための仕組みの要件を定義する。このフックは push の成功を検知して集計とレポート本文の組み立てまでを担い、MR への投稿はタスクの切れ目の処理で AI が実行する提供コマンドが行う。本書は GitLab の用語で書き、GitHub では MR → PR と読み替える。

- **背景**: AI に作業を任せると、その push 分にどれだけのトークン・ツール実行・時間がかかったかが見えない。push 単位で MR に工数が残れば、レビュアーとユーザーは作業のコストを差分と並べて追え、フィードバック計画で「コストに見合わなかったタスク」を振り返れる。
- **目的**: push ごとの対応工数が、AI の自己申告ではなくセッションの記録から集計され、MR のコメントとして push の履歴と対応づけて残る状態を実現する。
- **スコープ**:
  - 含む: push の成功の検知、セッションの終わり・応答の区切りでの使用量のローカルへの蓄積（push が別のセッションで行われても全期間を集計できるようにする）、前回 push からの集計（メインエージェントとサブエージェント）、レポート本文の組み立てとローカルへの記録、投稿の成否に応じたリセットと繰り越し、記録
  - 含まない: MR への投稿そのもの（提供コマンド）、push 前チェック（push の提供コマンド）、参照リンクと `/compact` の促し（`post-push-compact-prompt`）、Claude Code 以外のエージェントの集計

---

## ユーザーストーリー

**[As a]** レビュアー・ユーザーとして、

**[I want]** push ごとに「この分にどれだけの工数がかかったか」を MR 上で差分と並べて読みたい。

**[So that]** AI の作業のコストを把握し、フィードバック計画で進め方を見直す材料にできるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が push の提供コマンドを実行し、それが成功したとき、Shall フックは働かなければならない。検知の規則（成功の確認・コマンド位置の判定・直接実行された push の扱い）は `post-push-compact-prompt` と同じとする。
- When push が失敗したとき、または push 以外のコマンドが実行されたとき、Shall not フックは何もしてはならない。
- When push が成功したとき、Shall フックは前回の push（このブランチで初回なら作業の開始）から今回の push までの対応工数を集計しなければならない: トークン使用量（入力・出力・キャッシュの内訳）、ツールの実行回数、AI の応答回数、実作業時間（応答の間隔から推定した、ユーザーの待ち時間を除く時間）。
- When 集計の元を得るとき、Shall フックはセッションごとに蓄積されたローカルの状態と現在のセッションの記録（transcript）から集計し、AI やユーザーの申告を使ってはならない。期間の一部が集計できなかったときはその旨をレポートに添える。
- When その issue の作業でサブエージェントが起動されていたとき、Shall フックはサブエージェント分も集計に含め、含められなかった場合はその旨をレポートに添えなければならない。
- When push が作業と同じターンの途中で行われたとき、Shall フックはその時点までに記録された分を漏れなく反映しなければならない。
- When 集計したとき、Shall フックは前回 push 以降の累計をローカルの状態として保持し、投稿が完了するまでリセットしてはならない。状態はコミットの対象にしない。
- When セッションの応答が完了したとき、またはセッションが終了するとき、Shall 機構はそのセッションでそれまでに記録された使用量をローカルの状態へ蓄積しなければならない（レビュー待ちなどで push が別のセッションで行われても、前回 push からの全期間が集計できるようにする。蓄積はこのフックと同じスクリプトが別の契機で行い、登録は仕様で定める）。
- When 集計が終わったとき、Shall フックはレポート本文（集計期間としての前回 push と今回 push の時点、ブランチ、このブランチでの push の回数、各指標、AI の投稿であることを示す署名）を組み立ててローカルに記録し、AI に伝えなければならない。
- When AI がタスクの切れ目の処理（MR 本文の更新・レビュー依頼）を行うとき、Shall そのレポートは提供コマンドによって MR の通常コメント（レビューではなく、レビュー判定に影響しないコメント）として投稿されなければならない。
- When 投稿が成功したとき、Shall 集計はリセットされ、次の push からの分だけが次回のレポートに載らなければならない。
- When 投稿が失敗したとき、Shall 集計はリセットされず、次回の push のレポートに繰り越されなければならない。push や AI の操作を止めない。
- When レポートを読むとき、Shall 数値は桁区切り、時間は「H 時間 M 分」の形で、人間が読める日本語で書かれていなければならない。
- When フックが集計・組み立てを行ったとき、Shall その記録（push の時点・集計の要約）が残らなければならない。記録とレポートに環境変数の値・トークン文字列・個人情報を含めない（トークン数は含める）。

### 代替フロー

- If issue と MR を作らずにチケット駆動だけを試す単独実行モードで動いている場合、Then フックは集計とレポートの組み立てを行ってローカルに記録し AI に伝えるだけで、投稿先が無いことを添えなければならない。
- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは集計を行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If セッションの記録が読めない、または形式が想定と異なる場合、Then フックは何もせずに通し、push や AI の操作を止めてはならない。読めた分があればそれだけを集計し、読めなかったことをレポートに添える。
- If ローカルの状態が壊れている場合、Then フックは今回の push を起点として集計を始め、その旨をレポートに添えなければならない。

## 前提条件

- push が提供コマンド経由で行われること
- フックがセッションの記録（transcript）の場所を入力として受け取れ、その形式が仕様で定められていること。応答の完了・セッションの終了の時点でもフックを動かせること
- MR 本文の更新・レビュー依頼の提供コマンドが、記録されたレポートを MR の通常コメントとして投稿し、成否を状態に反映すること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。集計に使う情報はリポジトリ内のファイル・フックへの入力・セッションの記録に限る。集計はセッションの記録の形式に依存するため、形式の変更に追随する箇所を 1 か所にまとめる。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: レポートは事実（集計値）だけを書き、評価や推測を書かない
- **外部的制約**: 集計の対象は Claude Code のセッションに限る（Gemini CLI 等の他エージェントは本機構のスコープ外）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | push 以外のコマンドでは外部プロセスを起動せずに体感できない時間で通す。集計は前回 push 以降の差分だけを読み、記録全体を毎回読み直さない |
| セキュリティ | 記録とレポートに環境変数の値・トークン文字列・個人情報を含めない |
| 可用性 | 記録が読めない・投稿に失敗した場合も push と AI の操作を止めず、集計は繰り越す |
| 正確性 | 集計は記録から機械的に行い、同じ記録に対して同じ結果になる。二重計上しない |
| テスト容易性 | セッションの記録とローカルの状態を与えて、集計値とレポート本文を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
