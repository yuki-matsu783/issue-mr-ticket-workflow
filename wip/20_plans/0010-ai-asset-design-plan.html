この計画で何をするか

調査フェーズ（0004〜0009・0011）が集めた材料をもとに、全体計画書の保留 P1（1 issue 内の並列実施の採否）を採用するで決め、その決定を .claude/docs/ の正史（要件定義書・仕様書・DDR・横断文書・用語辞書）へどう落とすかを骨子まで固める。効く受け入れ条件は A1〜A6 の 6 件すべてで、A5・A6 は「並列を採用する場合」の条件文だが採用する前提に立つので発効する。

決めたこと（詳細は 結論方針）

  • 中核変更 要。hook-common.sh・scope.sh／cmdpos.sh・4 本のフック・settings.json／.gitignore／scope-limits.json が対象になる
  • 保留 P1: 1 issue 内の同一フェーズのチケット並列実施を採用する。DDR i0001-23 を新しい DDR で上書きする（利得側の数値は持たないまま採ったことを DDR に明記する）
  • 並列の実行単位は「作業ツリー」。作業ツリーを誰が作るか（サブエージェント隔離 / 人間の別セッション）は実装フェーズの検証で選ぶ — 設計を実装の検証結果に依存させない
  • 進行状態・ロック・集計は本流に一本化し、判定記録と実行ログは作業ツリー側に残して cwd と agent_id を足す
  • 合流はタスクの切れ目に固定し、提供コマンド worktree.sh merge 経由でのみ行う（新設スキル 20-common-step-worktree）
  • チケットの新規作成は本流でのみ行う（採番の重複が構造的に起きない）
  • scope.sh の穴は提供コマンド（案 D）＋ オプション判定の限定適用（案 C）で塞ぎ、cd は通さない。逆向きの穴 5 件も同じ改修で閉じる
  • A1-6（観点 A の中心の問い）は人間の再実測に戻さず、実装フェーズの機械テストで閉じる。テスト観点 4 件を設計側で用意する
  • 設計チケット 4 枚（0012〜0015）＋ 次の計画チケット 1 枚（0016 = AI アセット実装・テスト計画）

前提として確定させたこと（本計画の入口）

方法とステップ

中核の判定の土台（作業ツリーの三分と進行状態の置き場）を先に固めないと、宣言範囲・提供コマンド・運用のどれも書けない。したがって下から順に積む。結論方針の中身は「結論方針」節が正で、ここでは順序だけを決める。

    S1 — 方式の DDR と、作業ツリーの三分・進行状態の一本化・保護漏れの閉塞（チケット 0012 / 先行 —）

    並列採用の DDR を置き、HOOK_ROOT（スクリプトと設定の置き場）・HOOK_WORKTREE（判定対象の作業ツリー）・共有ルート（進行状態・ロック・集計の置き場）の三分を仕様に定める。作業ツリーをまたぐ絶対パスの保護漏れ（A1-2）を閉じる。

  2. 2

    S2 — 宣言範囲の強制・実行者照合・現在地の導出と、コマンド分類の穴（チケット 0013 / 先行 0012）

    宣言範囲・実行者照合が worktree ごとに一意に決まることを仕様に明記し、A1-6 を閉じる機械テスト観点を用意する。scope.sh の L1〜L4 と cmdpos.sh の P-1・P-2 を決める。session-start の現在地の誤導出（A1-1）を直す。

  3. 3

結論方針

中核変更の要否

中核変更: 要 判断の根拠は次の 4 点で、いずれも読み取りだけで確定している。

#変える中核なぜ避けられないか根拠
1hooks/lib/hook-common.sh（hook_rel_path / hook_record / ロックと集計の置き場）作業ツリーをまたぐ絶対パスの書き込みが進行状態ファイル保護をすり抜ける（A1-2）。hook_rel_path が 1 つの作業ツリーしか基準に持たないことの帰結で、フックの外側では塞げないe5・A1-2（03-state-guard.txt で実測確定）
2hooks/lib/scope.sh と cmdpos.shgit worktree / checkout / switch が unknown に落ち、worktree 運用を機構が支えられない（A1-5）。逆に git -c diff.external=<任意のコマンド> diff が read のまま通るe36〜e41・A1-5（e2-result.txt で実測確定）
3workflow-guard.sh / workflow-diff-check.sh / session-start.sh / subagent-start-check.sh宣言範囲の強制・差分の基準点・実行者照合が「worktree ごとに一意」であることが受け入れ条件 A5 の本文そのもの。session-start は worktree で現在地を誤導出する（A1-1）A5 の条文・e51 の A1-1（06-session-start.txt で実測確定）
4.claude/settings.json（worktree.baseRef）と .gitignore（.claude/worktrees/）と hooks/config/scope-limits.jsonサブエージェント worktree が既定ブランチから切られると機構が丸ごと無音になる（A1-7）。.claude/worktrees/ が未 gitignore だと push.sh 項目 1 が落ちるe20・e21（公式ドキュメントの逐語引用）

ロックアウトの可能性（実装計画への申し送り）

1 と 2 は「フックが自分自身の判定に使う関数」なので、途中の版で誤るとその時点から機構が全操作を拒否する / 全操作を素通しするのどちらかに倒れる。実装フェーズは中核を 1 つ変えるごとに機械テストと「自分が止まらないこと」を確認する固定手順を持っているので、本計画はそれに乗せる前提で骨子を作る。

判断点と採る案

判断点採る案根拠却下した案
P1. 1 issue 内の同一フェーズのチケット並列実施を採るか採る。DDR i0001-23 を新しい DDR で上書きする呼び出し元の確定。加えて e32 が原則との衝突を「成り立たない」と判定し、e27 の案 2（サブブランチ + 合流）が成立することを実測（d1.txt）で確かめている見送る。利得側の数値が無いことを理由に見送ると issue #50 の依頼そのものを否定することになるうえ、見送っても束 2 の 1〜3 は残るので作業量はほとんど減らない
P1a. 利得（所要時間の短縮幅）を測ってから決めるか測らない。非対称を明示したうえで決める直列の実績しか無いので短縮幅は推定にしかならず、推定値を根拠に据えると DDR の記述が実測を装った推測になる。採用の根拠は依頼と原則の再解釈であってコスト・利得の比較ではないと DDR に明記するほうが後から見直せる利得を測る調査チケットを追加する（フェーズ列の逆行になり、推定値しか出ない）

受け入れ条件 A1 の「実測で確かめられ」をどう閉じるか

A1-6（workflow-guard / workflow-diff-check が worktree 側のチケットで判定するか。観点 A の中心の問い）は、実測時にどの作業ツリーにも作業中チケットが 0 枚で負のコントロールまで無音になったため判定不能のまま残っている。

決めたこと

これを人間の再実測に戻さず、実装フェーズの機械テストで閉じる。理由は 3 つ。①再実測は実行時のリポジトリの状態に依存するので同じ失敗が再発しうるが、テストなら前提を自分で作れる ②テストの中の git worktree add はフックの外側なので scope.sh の分類に阻まれず、既存のテストヘルパは既に一時リポジトリを作る形になっている ③機械テストは再現できる実測であり、1 回きりの手作業の実測より強い根拠になる（回帰も守れる）。

観点前提の作り方期待する結果割り付け先
宣言範囲の強制が worktree 側のチケットで判定される一時リポジトリの本流に作業中 0 枚、worktree に作業中 1 枚を作り、cwd を worktree にした入力を workflow-guard に流すworktree 側チケットの allow.write の外への書き込みが拒否される0013（WG-T 新設）
（負のコントロール）本流側のチケットでは判定されない本流に作業中 1 枚、worktree に 0 枚を作り、cwd を worktree にする無音（作業中 0 枚として素通り）。前提が崩れていないことを、テスト自身が枚数を assert して確かめる0013（WG-T 新設）
差分の基準点が worktree 側のチケットの base_sha になる本流と worktree で別の base_sha を持つチケットを置き、cwd を worktree にして workflow-diff-check を走らせるworktree 側の base_sha を基準に差分が判定される0012（WD-T 新設）
実行者照合が worktree 側のチケットで行われる本流と worktree で executor の違うチケットを置き、cwd を worktree にして subagent-start-check / subagent-stop-check を走らせるworktree 側の executor と突き合わせて WF801 / WF802 が出る0013（SA-T 新設）

この 4 観点がそのまま受け入れ条件 A5（「機械テストで確認されている」）の中身になる。

定義を二重に持たせない。「作業ツリー」「本流」「共有ルート」の定義は用語辞書が正で、フック共通仕様と要件定義書は用語辞書の表記を使うだけにする。並列してよいタスクの種類は work-defaults.md が正で、00-workflow-issue-mr-driven は参照する。

ヘッドレス実行の帰結

アセット止まる / 進む既定
20-common-step-worktree（worktree.sh add / list / remove）進む承認を要さない。add は既定の置き場（リポジトリの外）に作る。remove は未コミットの差分があれば失敗終了（消さない）
20-common-step-worktree（worktree.sh merge）止まる自動で解けない衝突があれば合流を中断し、衝突箇所の一覧を出して失敗終了する。衝突を勝手に片方に寄せて進めない（レポートの内容の判断を機械にさせない）
workflow-guard / workflow-state-guard / workflow-diff-check / subagent-start-check止まる既存どおり拒否側に倒す。作業ツリーの解決に失敗したときも拒否側（DDR i0010-09）。ヘッドレスで確認が取れない範囲は WF213 のまま
session-start進む現在地を断定できないときは「不明」を出して進む（案内フックなので止める手段を持たない）
20-common-step-ticket（ticket.sh create の作業ツリーでの拒否）止まる拒否して本流で実行するよう案内する
20-common-step-commit-push（push.sh の本流限定）止まる作業ツリーからの push を拒否する
00-workflow-issue-mr-driven（worktree を切るか / 並列にするか）進む既定は「切らない・並列にしない」。並列にするのはユーザーの明示の指示があるときだけ（DDR i0050-06）。合流は切れ目で自動的に行い、衝突で止まったら人に返す
agents/task-executor進むworktree.baseRef が設定されていない環境では隔離を使わない（静かな無効化を避ける）
10-task-investigation-exec（レポート追記規約）進む並列区間では自分の節だけを追記する
