    7. __hc_redact_to_reply の性能バグ △注意 根拠: 規則ごとの実測: 58442ms → 101ms

    4000 文字の入力で 58 秒かかっていた。規則ごとに計測すると正規表現の 4 規則は各 70ms 程度で、真犯人は規則 5 の pre="${s%%"$m"*}" だった（$m が 4000 文字のリテラルパターンのとき、bash のパターン照合が壊滅的に遅くなる）。位置ベースの O(n) ループに書き直して 101ms になった。__hc_cap_json_field の文字単位ループも O(n^2) で、パラメータ展開だけの O(n) に書き直した。

    根拠を見る（実行コマンドと出力） 
    # 規則ごとの計測（4000 文字の入力）

# 書き直し後

    結論

    フックはツール呼び出しごとに走るので、この形のまま登録していたら機構ごと使い物にならなかった。「bash のパターン照合はパターンが長いと壊滅的に遅い」は DDR 候補として 0032 へ送る。

想定と異なった点

計画時の見込み実際どう扱ったか
Git Bash では作成時刻（birth）が取れないと思っていたstat -c %W が 1788323071 を返し、%Y（mtime）と一致したそれでも移植性（Linux の古い coreutils では 0 を返す）を取り find -mmin を選んだ。ロックディレクトリは中身を書かないので mtime = 作成時刻として扱える
make_counting_path を呼べば PATH が差し替わるCOUNTING_PATH を設定するだけで PATH は変わらない。HK-T19 が 0 回を返した呼び手側で ( PATH="$COUNTING_PATH:$PATH"; hash -r; ... ) の部分シェルに包んだ。雛形のコメント改善候補として作業ログへ
io.open(p, "wb") は書き込みが成功してから内容を差し替える例外の発生前にファイルを truncate する。scope.sh が 0 バイトになったgit checkout -- で復旧し、以後の一括編集はすべて一時ファイル + rename で書いている。find . -size 0 -name '*.sh' で他に 0 バイトが無いことも確認
redact は正規表現が重いだろう正規表現 4 規則は各 70ms、真犯人は規則 5 の ${s%%"$m"*}（58442ms）位置ベースの O(n) に書き直して 101ms（）
テスト ID は一意に振られているCP-T08 が test_commit.sh と test_push.sh の両方にあるgit show HEAD: の版でも両方に存在する既存の重複。ID の付け替えは 0032 の棚卸しへ
