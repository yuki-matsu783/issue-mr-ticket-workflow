# 提供コマンドの引数・環境の誤りは番号を末尾に足す

## 背景

提供コマンドは終了コードを「成功 0 / 前提・状態の未充足 1 / 引数・環境の誤り 2」の 3 段で返すと定めている。`ticket.sh`（`TK008`）・`commit.sh` / `push.sh`（`CP007`）・`check-html.sh`（`RV008`）・`run-tests.sh`（`TR004` / `TR005`）は終了コード 2 に対応する番号を持っていたが、この issue で新設した `boundary.sh` と `finalize.sh` は持っていなかった。終了 2 を返す経路はあるのに、返す識別子が無い。

規約としてもどこにも書かれておらず、次に提供コマンドを作る人が同じ抜けを繰り返す形になっていた。

## 決定

- **提供コマンドの識別子表には「引数・環境の誤り」（終了コード 2）の番号を必ず 1 つ置く**ことを `20-common-step-spec` 仕様の規約にする
- `boundary.sh` に `BD006`、`finalize.sh` に `FN004` を新設する
- **番号は既存の最大の次を末尾に足し、既存の番号を振り直さない**

## 理由

- **呼び手の対処が違う**。終了 1 は前提を直して再実行すれば進むが、終了 2 は呼び方か実行環境を直すまで何度実行しても同じ結果になる。番号で分けておかないと、呼び手（AI）は前提を直そうとして同じ失敗を繰り返す
- **既存の 4 本が持っているのに新設の 2 本が持たないのは、規約が書かれていなかったからである**。仕様の側に規約を置けば、次のコマンドは最初から持つ
- **振り直しの波及が大きい**。番号はテストの期待値（`assert_eq` で最終行を exact に固定している）・実装の分岐・レポートの記述・回復手順の案内に散らばっている。意味の並びを整えるために振り直すと、この 4 種類を同時に直す必要があり、どれか 1 つが漏れると「テストは緑だが案内が古い」状態になる
- **番号の並びに意味を持たせない**という選択でもある。番号は引くための鍵で、並び順は情報を持たない

## 却下した案

- **終了コード 2 の番号を全コマンドで揃える（例: どれも `xxx009`）**: 既存の `TK008` / `CP007` / `RV008` を振り直すことになり、上の波及がそのまま起きる。揃っていることの利得は「覚えやすい」だけで、識別子は覚えるものではなく引くものである
- **終了コード 2 では識別子を出さない（終了コードだけで区別する）**: 出力の最終行が `OK:` か `<接頭辞><番号>:` であることは提供コマンドの契約で、例外を作ると呼び手が最終行の形で分岐できなくなる
- **1 つの番号で「前提未充足」と「引数の誤り」の両方を表し、本文で区別する**: `i0010-05` で `check-html.sh` について同じ形を否定したばかりで、1 番号 1 原因の原則に反する

## 影響

- `10_spec/skills/20-common-step-spec.md` のエラー識別子の規約に 2 項目（終了 2 の番号を 1 つ置く・末尾に足す）を追加する
- `10_spec/skills/00-workflow-issue-mr-driven.md` の識別子表に `BD006`、`10_spec/skills/10-task-overall-summary.md` の識別子表に `FN004` を追加し、それぞれの要件に対応する受け入れ基準を先に追加する
- `フック共通仕様` §6 の `BD` / `FN` の範囲を新しい最大値まで広げる
- 実装フェーズで `boundary.sh` / `finalize.sh` の終了 2 の経路をこの識別子で返すように直す
