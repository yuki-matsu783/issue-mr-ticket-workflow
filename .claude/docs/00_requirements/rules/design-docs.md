# design-docs ルール

## 概要

アプリ本体の設計文書（要件定義書・仕様書・DDR・用語辞書）の正典規約を定める成果物ルールの要件を定義する。適用範囲は `docs/**` のみで、AI アセットの設計文書（`.claude/docs/**`）には効かない。AI アセット側は `ai-asset-design-docs` ルールが同種の規定を独立に持つ（重なる規定は両方のルールに書き、内容を食い違わせない）。

- **背景**: 設計文書は「その時点で有効な正史」と「決定の経緯」が混ざると、読み手がどれを信じてよいか分からなくなる。置き場・書き分け・DDR の運用を 1 つのルールにまとめ、書くときも観点別レビューでも同じ文書を参照できるようにする。
- **目的**: アプリ本体の設計文書を書く AI が、配置・記述の範囲・DDR の扱いで迷わず、レビューエージェントが同じ基準で横並びに検査できる状態を作る。
- **スコープ**:
  - 含む: このルールが定めるべき内容（配置、正史のみの記述、requirements / spec の書き分け、DDR の運用、用語辞書の位置づけ）
  - 含まない: frontmatter のキー定義と `type` の値一覧（`markdown-docs` ルール）、AI アセット設計文書の規定（`ai-asset-design-docs` ルールが独立に持つ）、文書の寿命と置き場所の一般則（`document-lifecycle` ルール）

---

## ユーザーストーリー

**[As a]** アプリ本体の設計文書を書く AI として、

**[I want]** どこに何を書き、何を書いてはいけないかを 1 つのルールで確認したい。

**[So that]** 経緯と正史が混ざった文書を作ってレビューで差し戻されないため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が `docs/` 配下の文書を作成・変更するとき、Shall このルールが収集され、以降の各規定が適用されなければならない。
- When このルールを書くとき、Shall 成果物ルールとして章スキーマ（`ルール体系.md`）に従わなければならない。

### 配置

- When 設計文書を置くとき、Shall `docs/` 配下に、要件定義書を `00_requirements/`、仕様書を `10_spec/`、DDR を `20_ddr/`、用語辞書を `90_glossary/` の構成で置かなければならない。

### 正史のみの記述

- When requirements / spec を更新するとき、Shall それらは「その時点で有効な正史」だけを記述し、検討の経緯・却下した案・過去の版の内容・変更履歴の表を本文に残してはならない（履歴は git のコミット履歴と DDR で追う）。

### requirements と spec の書き分け

- When requirements を書くとき、Shall 利用者から見た振る舞い（何ができ、何が拒否され、何が出力されるか）で記述し、内部構造（コマンドの構成・状態の持ち方・判定の手順）は spec に書かなければならない。

### DDR の運用

- When 設計上の決定（複数案から選んだ・方針を変えた）が行われたとき、Shall その背景・決定・理由・却下案・影響が DDR に記録されなければならない。
- When DDR を命名するとき、Shall issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md` で命名し、issue を持たない DDR を作ってはならない。
- When DDR がマージされたあと、Shall 本文を変更してはならず、後続の決定で無効になった場合は frontmatter の状態（置き換え済み / 廃止）と置き換え先だけを更新しなければならない。
- When DDR の一覧を参照するとき、Shall 一覧は各 DDR の frontmatter から生成されたものであり、手書きで保守されていてはならない。

### 用語辞書

- When 用語を調べるとき、Shall 用語辞書は正典（requirements / spec）への案内役に徹し、辞書自身が用語を再定義していてはならない。
- When 用語辞書に載せる語を決めるとき、Shall 複数の文書で使われ、かつ指し先や表記が揺れうるプロジェクト固有語（アプリが導入した概念・コンポーネント名・用語の読み替え規則）に限らなければならない（一般的な開発用語は載せない）。
- When 辞書のエントリを書くとき、Shall 用語名・一言説明・定義元（正典へのリンク）を持ち、別名・禁止表記（旧称・使わない言い方）があればあわせて持たなければならない。
- When 収録済みの用語を文書で使うとき、Shall 辞書の表記に従い、初出箇所で辞書へリンクしなければならない。禁止表記を使ってはならない。
- When 新しい固有語を導入した・収録語をリネームしたとき、Shall 同じチケットの中で辞書を追記・更新し、旧称は別名・禁止表記へ移さなければならない（あとでまとめて更新しない）。

### 例外フロー

- If マージ済み DDR の内容を訂正する必要が出た場合、Then 新しい DDR で置き換え、旧 DDR は frontmatter の状態の更新だけで扱わなければならない（本文の書き換えで直さない）。

---

## 前提条件

- `markdown-docs` ルールが frontmatter のキー定義・`type` の値一覧・テンプレート命名を持つこと（本ルールは再掲しない）
- DDR 一覧の生成手段は仕様書が定める

---

## 制約条件

- **技術的制約**: 適用範囲は `docs/**` の paths で宣言し、`.claude/docs/**` には適用しない
- **ビジネス的制約**: 文書の内容の妥当性は MR 上の人間レビューが判断する

---

## 依存関係

- `rules/ルール体系.md`（分類・章スキーマ・収集の要件）
- `rules/ai-asset-design-docs.md`（AI アセット側の対応ルール。重なる規定は内容を揃える）
- `markdown-docs` ルール（frontmatter 規約）

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | `ai-asset-design-docs` と重なる規定は内容を食い違わせない（規定はそれぞれのルールに書く） |
| 簡潔性 | 同じファイルにマッチする他ルールの規定（frontmatter・寿命と置き場所）を再掲しない |
