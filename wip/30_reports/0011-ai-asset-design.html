    issue 追記 3 は「片付け直前の SHA が確定してから本文を更新する」を求める。現行の仕様は処理フロー 5（本文の最終化）→ 9（release で片付け）の順で、本文更新の時点で pre_cleanup_sha が未定義だった。解決はリンク一覧だけを release の中へ移すこと。処理フロー 5 は要約だけを書き、SHA に依存するリンク一覧は release の段階 3 で書く。

  3. 3

    TK005 は例外ではなく設計だと明示し、完了検査を共有関数にした ◎良 根拠: 20-common-step-ticket 仕様 complete 2 と issue 追記 4

    ticket.sh complete が全体まとめを必ず拒否するのは、完了が finalize.sh release に内包されているためで、抜け道を作る話ではない。ただし拒否だけでは検査の結果がどこにも残らないので、検査そのものは release の段階 2 が同じ関数で行い、結果を統括レポートの「完了検査」節に書き出すと定めた（B4）。

    結論

    検査を ticket_check_completion <チケットのパス> として定義し、finalize.sh が source して使う（二重実装しない）。全体まとめチケットも「complete を通らないだけで同じ検査は受ける」。統括レポートは片付けで消えないコミットに載るので、チケットが消えた後も検査の通過を辿れる。

  5. 5

    CLI 不在時の release を仕様に追加した ◎良 根拠: 旧 SKILL.md 261 行の merge-prep.sh --external

    食い違い #7（旧 SKILL.md が外部委任の経路を書いていたが、新仕様に記述が無い）を、10-task-overall-summary 仕様の新設節「CLI が使えない環境での release」で埋めた。リモートに書く段階は 3（本文のリンク一覧）と 6（draft 解除）の 2 つだけなので、その 2 つだけを呼び出し元に代行させる。

    結論

    段階 3 は release --external --pr <M> --body-file <path> がリンク一覧をファイルに書き出して戻り、呼び出し元が MCP ツールで本文を更新してから --linked で再開する。段階 6 は呼び出し元が draft を解除してから最終ゲートだけを通す。via: "external" を記録し、gh 自身が確認する強度より劣ることを統括レポートに書く。curl / WebFetch へは落とさない。

  6. 6

    成果物の所在をコメントから MR 本文へ移した（B1） ◎良 根拠: issue #10 追記 1

    処理フロー 6 を「成果物のリンク一覧と HTML 添付」に書き換え、リンクを列挙した通常コメントの投稿をやめた。所在は本文の見出し ## 統括 配下の表（レポート名 / 1 行説明 / リンク）で辿る。リンクは片付け直前の SHA に固定した blob URL なので、片付け後も永続的に開ける。

    結論

    コメントの投稿は禁止事項にも入れた。「投稿してもよいが本文にも書く」だと二重管理になり、片方が古くなる。

  7. 7

    GitHub への HTML 添付を AI の手順から外した（B2） ◎良 根拠: issue #10 追記 2 の実測

    uploads.github.com への curl を仕様から削除し、禁止事項に移した。添付は人間がブラウザで本文に行い、AI は返った URL を記録するだけにする。

    送り方content_type結果
    生バイナリ + ヘッダtext/html422 content_type is not included in the list of allowed content types
    同上text/markdown / text/plain / application/zip / application/pdf422 同じ

    image/png が同じトークン・同じエンドポイントで通るので、リクエストの組み立てではなく種別で拒否されている。ブラウザ側の 3 段階の経路（CSRF トークン → S3 署名 → 確定）も、1 段目が PAT では 302 → /login になりアセット id が採番されないため再現できない。

    結論

    実測は DDR i0010-02 に写した。添付は任意の位置づけに下げたので、「添付できない環境」という代替フローの分岐が 1 本消えた。GitLab は glab api uploads が公式に使えるので AI が添付してよい（ホストで扱いが違うことを明記した）。

  8. 8

    結論

    根拠欄にはチケット番号・レポートの節・テスト IDを書き、wip/ 配下のパスは恒久参照として書かない（片付けで消えるため）。要件書にも受け入れ基準を 1 件足した（完了検査の結果を統括レポートに書き出してから片付けに進む）。

  9. 9
