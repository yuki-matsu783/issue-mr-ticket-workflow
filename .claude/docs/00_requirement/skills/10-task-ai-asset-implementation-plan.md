# 10-task-ai-asset-implementation-plan スキル

## 概要

AI アセット実装・テストフェーズの計画タスクの要件を定義する。機構の設計文書（仕様書のテスト ID を含む）をアセット（スキル・フック・ルール・エージェント・設定）に落とすための変更対象・許可範囲案・テスト方針・実装ステップ・参照更新の一覧を AI アセット実装・テスト計画書にまとめ、実装チケット群と次のフェーズの計画チケットを起こして計画チケットを完了する。アセット本体は書かない（`10-task-ai-asset-implementation-exec`）。

- **背景**: AI アセットの変更は機構自身の振る舞いを変え、フックの不具合は AI のセッション自体を止め得る。また新しい名前・手順を参照すべき既存アセットの更新が漏れると、機構の中で古い参照が生き残る。変更の順序・テスト・参照更新・復旧の備えを先に決め、人間が実装前に見られるようにしたい。
- **目的**: 変更対象を仕様書と対応付け、テストシナリオ（テスト ID）をフックのテスト等に割り付け、参照更新の一覧とロックアウト対策を含む、検証可能なステップに区切った実装チケット群をレビュー可能な計画書として残す。
- **スコープ**:
  - 含む: AI アセット実装・テスト計画書の作成、変更対象と許可範囲案、テスト方針（テスト ID との対応・既存テストの回帰確認）、実装ステップの順序、参照更新の一覧、ロックアウト対策、実装チケット群と次の計画チケットの作成、計画チケットの着手から完了まで、「対象なし」の扱い、再開時の扱い
  - 含まない: アセットとテストの作成（`10-task-ai-asset-implementation-exec`）、機構の設計文書の内容の決定（AI アセット設計フェーズ）、アプリ本体のコード（実装・テストフェーズ）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）

### issue の受け入れ条件との対応

起点は issue #10。この書の受け入れ基準を追加・変更した更新（2026-09-03）で該当する条件を挙げる。

| issue #10 の受け入れ条件 | 満たす受け入れ基準 |
|---|---|
| A4: #6 / #9 の申し送り事項が該当するアセットの設計に反映されている（申し送り #2〜#9 の 8 項目） | メインフロー「提供コマンド自身を変えるとき…最初の操作をステップに書き、戻す基準点を添える」「テストを実行するチケットの『やってよいこと』…テストの置き場に対応する分類をすべて」「書く側・読む側・両者の往復を確かめるテストを同じチケットの範囲に置く」「計画書に書いたステップの順番と、機構が示す次のチケットの順番は一致」、規約節「テスト方針を書くとき…抜き出した件数と割り付けた件数が一致」「参照更新の一覧…期待値は『残るもの』」「名前やパスを変える更新…テストを同じチケットの書き込み範囲に含める」「最初の実装チケットの DoD…実装結果の報告が存在する」 |

A1・A2・A3・A5 と B1〜B4 はこの書の対象外（A1 は eval 定義、A2 は提供コマンドの動作、A3 は参照更新の実施、A5 は実装後の書き戻し、B1〜B4 は `10-task-overall-summary` の条件で、いずれも別のアセットの要件が担う）。

## ユーザーストーリー

**[As a]** 自己改善する機構を運用する開発者として、

**[I want]** 機構が変更される前に、どのアセットがどの順で変わり、どのテストで確かめ、既存のどの参照が更新され、壊れたときにどう戻すのかを 1 枚の計画で確認したい。

**[So that]** 機構自身の変更で AI が動けなくなる事故や、古い参照の残留を実装前に防げるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、機構の設計文書（要件の制約・仕様書のテスト ID）・既存アセットの構造とテストの書き方（読むだけ）を入力に進めなければならない。
- When 計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し、完了時にまとめて書いてはならない。
- When 実装ステップを組むとき、Shall テストが通る単位で区切り、順序は「設定・定義 → 機構の中核（フック等）→ そのテスト → スキル・ルール → 参照更新」を基本とし、機構の中核を変えるステップには小さく変えて都度テストする方針を書かなければならない。**計画書に書いたステップの順番と、機構が示す次のチケットの順番は一致していなければならない**（読み手が「計画では 3 番目だが実際は 1 番目に走る」状態に出会わないようにする）。
- When 実装ステップが機構の提供コマンド自身を変えるとき、Shall スキルは**変更後のそのコマンドで自分のチケットをコミット・完了させる最初の操作**をステップに書き、失敗したときに戻す基準点を添えなければならない（変更した直後の 1 回目が壊れていると、そのチケットを終わらせる手段が無くなるため）。
- When 計画書の案ができたとき、Shall スキルは関連するアセットのまとまりを単位に実装チケット群（1 枚以上）を未着手に作らなければならない。チケットの依存関係（先行チケット）が分かるようにする。
- When 実装チケットを作るとき、Shall その DoD は「<アセット> が仕様書 <節> のとおり作成（変更）されている」「機械的に実行できるテスト <テスト ID> が追加され、既存のテストとあわせて通る（実行方法つき）」「機械的に検証できないアセット（スキル・ルール・エージェント）は eval（評価シナリオ）の定義が作成・更新されている（実行はしない）」「テンプレートのプレースホルダと frontmatter が検査されている」「参照更新（<対象の一覧>）が済み、旧い名前・手順の残存が検索で 0 件（検索の対象から DDR 本文と用語辞書の別名・禁止表記の欄を除く。経緯と禁止表記には旧名が正当に残る）」の型で書かなければならない。
- When 最初の実装チケットの DoD を書くとき、Shall 実装結果の報告（正文と HTML ビューの対）が存在することを含めなければならない（後続のチケットはそこへ節を足す。DoD に無いと報告が最後のチケットまで先送りされるため）。
- When テストを実行するチケットの「やってよいこと」を書くとき、Shall 実行してよい操作の分類に**テストの置き場に対応する分類をすべて**含めなければならない（機構はテストの置き場ごとに分類を分けており、片方だけの宣言では実行が拒否され、チケットの途中で範囲を広げる相談が発生する）。
- When 値を書き出す側と読み取る側の両方に手が入る修正を計画するとき、Shall スキルは**書く側・読む側・両者の往復を確かめるテスト**を同じチケットの範囲に置かなければならない（片側だけを直すともう片方が古い形を期待して壊れるため）。
- When 実装チケット群を作り終えたとき、Shall スキルはフェーズ列で AI アセット実装・テストの次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない（次が無ければ全体まとめのチケット）。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: タスクの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと（書き込んでよい範囲・実行してよい操作の分類。許可範囲案を反映する）、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When 計画チケットを完了するとき、Shall 計画書（md + HTML）・実装チケット群・次の計画チケットが存在し、DoD（計画書に変更対象・許可範囲案・テスト方針・ステップ・参照更新の一覧・ロックアウト対策がある / 実装チケットの DoD にテストと参照更新がある / 次の計画チケットがある）がすべて満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 完了したとき、Shall スキルは結果報告（計画書の場所、実装チケットの枚数、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「変更対象が仕様書と対応し、機構の中核の変更の要否が要件の制約と一致しているか」「テスト方針がテスト ID を網羅し、機械テストと eval の割り付けが妥当で、既存テストの回帰確認を含むか」「ステップの順序と 1 チケットの大きさ」「参照更新の一覧に漏れがないか（検索の結果を添える）」「ロックアウト対策」を挙げなければならない。

### 代替フロー

- If 受け入れ条件（または設計文書）がアセットの変更を必要としないと分かった場合、Then スキルは計画書に「対象なし」とその根拠を書き、実装チケットを起こさず次の計画チケットだけを作って即座に完了しなければならない（フェーズを省かない）。
- If 再開時に計画チケットが作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残さなければならない。

### 例外フロー

- If 仕様書にテスト ID が無い、または実装を計画できる粒度に達していない場合、Then スキルは推測で補わず、不足を結果報告に書いて AI アセット設計フェーズへの差し戻し（設計の追加チケット）を提案しなければならない。
- If アセット本体への書き込みやテストの実行が機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、書き込みは実装チケットに回し、既存テストは読んで把握しなければならない（実行は実装チケットで行う）。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

### 規約: AI アセット実装・テスト計画書

- When 計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、変更対象（アセットごとに新規 / 変更・種類・仕様書との対応・作成に使うテンプレートや型にする既存アセット）、許可範囲案（最小にする。機構の設計文書は含めない）、テスト方針（テスト ID ごとに、機械的に実行できるテスト（フック・スクリプトのテスト）で確かめるか eval（評価シナリオ）で確かめるかの割り付け・既存テストの回帰確認・実行方法。eval は定義の作成・更新までとし、評価の実行は計画に含めない）、実装ステップ（順序と、機構の中核を変えるときの小さく変えて都度テストする方針）、参照更新の一覧（新しい名前・手順を参照すべき既存アセットと文書。検索で洗い出した根拠を添える）、ロックアウト対策（機構の不具合で AI が止まったときの復旧手順。強制の無効化はユーザーの明示的な指示があるときだけ）、リスクと未解決事項、判断を保留した点。
- When テスト方針を書くとき、Shall テスト ID の一覧は設計文書から機械的に抜き出した結果を元にし、抜き出した件数と割り付けた件数が一致していることを示さなければならない（目視で拾うと、設計にあるのに割り付いていない ID が残るため）。
- When 参照更新の一覧を書くとき、Shall 検索の指定は行の末尾に依存しない形にし、期待値は「残るもの（どこに何件残るか）」で書かなければならない（0 件を期待値にすると、検索の指定が誤っていて何も見つからない場合と区別が付かない）。
- When 名前やパスを変える更新を計画するとき、Shall スキルはそれを入力または期待値に持つテストを検索で洗い出し、同じチケットの書き込み範囲に含めなければならない（実装だけ直してテストが古いまま残る状態を作らない）。
- When 計画書を書くとき、Shall 「これから何をするか」だけを書き、アセットの本文を書き始めてはならない。
- When 計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### 規約: AI アセット実装・テスト計画チケット

- When 計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、アセット本体・機構の設計文書・アプリのコードと文書を書けてはならない。
- When 計画チケット・実装チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければどちらも「要」を既定としなければならない（機構自身の振る舞いを変えるリスクが高い）。

### 他のスキル・機構との整合

- When 機構の設計文書を参照するとき、Shall スキルはそれらを書き換えず、疑義があれば結果報告の「見てほしい点」に書かなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When アセットの作り方（テンプレート・書式）に言及するとき、Shall not スキルは手順を再掲せず、アセット作成の common-step スキルを参照しなければならない。

## 前提条件

- AI アセット設計フェーズのタスクの切れ目の処理（レビュー要ならレビュー完了）が済み、計画チケットが未着手にあること
- 計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと提供コマンド、アセット作成の common-step スキルが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずに「判断を保留した点」と「見てほしい点」に書く。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 変更範囲・テストの網羅・許可範囲・ロックアウト対策は人間レビューで確定する。スキルは案を出し、レビュー前にアセットを書き始めない
- **外部的制約**: 許可範囲案は機構が定める上限の中で提案する。機構の統制の無効化を前提にした計画を書かない
