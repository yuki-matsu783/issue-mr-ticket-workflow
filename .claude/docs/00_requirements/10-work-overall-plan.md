# 10-work-overall-plan スキル

## 概要

`00-workflow-issue-mr-driven` のワークループの先頭で、issue の受け入れ条件からその issue をどう進めるかを決める全体計画ワークの要件を定義する。issue の確定・ブランチと MR の作成は `00-workflow-issue-mr-driven` が済ませており、このワークはそれを引き継いで全体計画書を書き、ユーザーと合意し、最初の計画チケットを起こして全体計画チケットを完了する。

- **背景**: ワークの種類は 15 種あり、issue ごとにどのフェーズを使うか・誰（どのモデル）が実施するか・どこで人間が見るかが変わる。これを実施しながら決めると、レビューの省略やモデルの選択が AI の裁量になり、後から追えない。着手前に 1 か所で決めてユーザーと合意し、以降のワークはその方針に従って動く。
- **目的**: issue の種別に応じたテンプレートからフェーズ列を組み、各ワークの実行者・人間レビュー要否・やってよいことの方針を全体計画書として残し、合意のうえで次のワーク（調査計画）へつなぐ。
- **スコープ**:
  - 含む: 全体計画書の作成、issue の種別の判定とテンプレートの適用、受け入れ条件と各フェーズの対応付け、実行者とレビュー要否の方針、最初の計画チケットの作成、全体計画チケットの完了、再開時の扱い
  - 含まない: issue・ブランチ・MR の作成（`00-workflow-issue-mr-driven`）、各フェーズの計画書とチケット群の作成（各計画ワーク）、フィードバック計画より後のフェーズの要否の決定（`10-work-feedback-plan`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 着手前に、どのフェーズをどのモデルで進め、どこで自分がレビューするかを 1 枚の計画で確認して合意したい。

**[So that]** 進め方を最初に握り、途中でレビューが抜けたり想定外のモデルで作業されたりしないため。

---

## 受け入れ基準（Acceptance Criteria）

### 全体計画書の内容

- When 全体計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、issue の種別（アプリ / AI アセット / 両方）とその根拠、採用したフェーズ列（テンプレートとの差分と理由）、受け入れ条件と各フェーズの対応（どの条件をどのフェーズが満たすか）、ワークの種類ごとの実行者（LLM モデル）と人間レビュー要否の方針、ワークの種類ごとの「やってよいこと」の方針、判断を保留した点。
- When 全体計画書を書くとき、Shall 「これから何をするか」だけを書き、実施結果や経過を書いてはならない。
- When 全体計画書を置くとき、Shall 作業領域の全体計画の置き場に 1 issue につき 1 つだけ置き、HTML ビューは任意とする。

### メインフロー

- When このワークに入ったとき、Shall スキルは `00-workflow-issue-mr-driven` から issue 番号・MR・受け入れ条件・やらないことを引き継ぎ、全体計画チケットが作業中であることを前提に、メインエージェント自身で進めなければならない（サブエージェントに委ねない）。
- When issue の種別を判定するとき、Shall スキルは受け入れ条件と変更対象から「アプリ（`docs/`・ソースコードが主目的）」「AI アセット（`.claude/` 配下が主目的）」「両方」を判定し、根拠とともに提示しなければならない。
- When フェーズ列を組むとき、Shall スキルは種別ごとのテンプレート（`00-workflow-issue-mr-driven.md`「ワークの構成」）を土台に、調査とフィードバック計画を必ず含め、主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット化）は依頼の性質に応じて含め、フィードバック計画より後のフェーズは含めないまま（フィードバック計画で決める）にしなければならない。
- When 主作業のフェーズを含めるか迷うとき、Shall スキルは含める側に倒し、やることが無ければ計画ワークで「対象なし」として即座に完了する前提にしなければならない（全体計画の段階で「やらない」と決めない）。
- When 実行者とレビュー要否の方針を決めるとき、Shall スキルはワークの種類ごとに既定の実行者（モデル）と人間レビュー要否（理由付き）を提案し、リスクの高いワーク（実装・テスト実施、AI アセット化実施など）は人間レビュー要を既定としなければならない。
- When やってよいことの方針を決めるとき、Shall スキルはワークの種類ごとに書き込んでよい範囲と実行してよい操作の分類を、機構が定める上限の中で提案しなければならない。
- When 全体計画書の案ができたとき、Shall スキルはそれをユーザーに提示し、フェーズ列・実行者・レビュー要否・やってよいことの方針について合意を得なければならない。合意前に次の計画チケットを作ってはならない。
- When 合意が得られたとき、Shall スキルは最初の計画チケット（調査計画）を 1 枚だけ未着手に作らなければならない。以降のチケットは各計画ワークが連鎖的に起こす。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: ワークの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと（書き込んでよい範囲・実行してよい操作の分類）、目的、完了条件（DoD）。DoD は issue の受け入れ条件から導く。
- When 全体計画チケットを完了するとき、Shall 全体計画書と最初の計画チケットが存在し、合意の内容が全体計画書に記録され、作業ログ（うまくいったこと・うまくいかなかったこと・AI アセットに反映すべき内容）が書かれていなければならない。完了は提供コマンドで行う。
- When 全体計画チケットを完了したとき、Shall スキルは `00-workflow-issue-mr-driven` に制御を戻し、ワークの切れ目の処理（push・MR 本文への全体計画の要約の追記・レビュー要否に応じたレビュー依頼）はそちらが行う。

### 全体計画チケットの扱い

- When 全体計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は全体計画書の置き場・チケットの置き場への書き込みと、issue・ブランチ・MR の作成と push を含み、それ以外のファイル（ソースコード・設計文書・`.claude/` 配下）を書けてはならない。
- When 全体計画チケットの人間レビュー要否を決めるとき、Shall 既定は「不要」（合意はチャットで取り全体計画書に記録するため）とし、ユーザーが MR 上でも計画を確認したい場合は「要」にできなければならない。

### アルタナティブフロー（代替経路）

- If 再開時に同じブランチに全体計画書が既にある場合、Then スキルは新しく作らず、既存の計画を提示して続きから進めなければならない。
- If issue の種別が「両方」の場合、Then スキルはアプリのテンプレートを土台に AI アセット設計・AI アセット化を主作業として全体計画で含め、フェーズ列を 1 本に並べなければならない。
- If 依頼が `00-workflow-quick-request` の振り返りから切り替えて来たものである場合、Then スキルは引き継がれた issue 種別（AI アセット）とフェーズ列をそのまま土台にし、合意は改めて取らなければならない。
- If 受け入れ条件が曖昧で対応付けができない場合、Then スキルは不足を指摘し、issue への追記を `00-workflow-issue-mr-driven` の手順で行ってから計画を続けなければならない。

### 例外フロー（エラーケース）

- If ユーザーが合意を保留・却下した場合、Then スキルは計画を修正して再提示し、合意が得られるまで計画チケットを作ってはならない。
- If ユーザーが応答できない実行形態で合意が取れない場合、Then スキルは全体計画書の案をコミットせずに報告し、セッションを終えなければならない（合意なしに計画チケットを作らない）。
- If 全体計画チケット以外のチケットが既に存在する場合、Then スキルは状態の不整合として報告し、ユーザーの指示を待たなければならない。

---

## 前提条件

- `00-workflow-issue-mr-driven` が issue・ブランチ・draft MR を確定し、全体計画チケットを作業中に置いてからこのワークを呼ぶこと
- ワークの種類ごとの上限（書き込んでよい範囲・操作の分類）が機構の設定として定義されていること
- 実行者として指定できるモデルは、サブエージェントで選択できるモデルに限ること

---

## 制約条件

- **技術的制約**: 全体計画はメインエージェントが行う（人間との合意が要り、サブエージェントはユーザーと対話できないため）。全体計画書は 1 issue に 1 つ
- **ビジネス的制約**: フェーズ列・実行者・レビュー要否の方針は人間が決める。スキルは案を出し、合意なしに確定しない
- **外部的制約**: フィードバック計画より後のフェーズの要否は全体計画では決めない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 全体計画書に issue 番号・MR 番号・合意の内容（誰が・いつ・何に合意したか）が残る |
| 一貫性 | フェーズの名前・順序・テンプレートは `00-workflow-issue-mr-driven.md`「ワークの構成」と一致する。チケットの記載事項は他の work スキルと同じ |
| 簡潔性 | 全体計画書は 1 画面程度で読める分量にし、詳細は各フェーズの計画書に委ねる |
| 冪等性 | 再開時に全体計画書とチケットを二重に作らない |
