# 20-common-step-feature-mr スキル

## 概要

feature ブランチと draft MR 作成の共通ステップの要件を定義する。確定した issue の番号から命名規約に沿ったブランチを default ブランチの最新から作り、issue に紐づく draft MR を作成して番号と URL を返す。全体計画タスク（issue の確定後）から使われる。

- **背景**: ブランチ名・ベースの取り方・MR の初期本文が毎回ぶれると、issue との対応が名前から読めず、MR の作成が「差分なし」で失敗するケースの扱いも揺れる。1 issue = 1 ブランチ = 1 MR の対応を名前と本文で機械的に保ちたい。
- **目的**: ブランチ名と MR から issue 番号が一意に辿れ、MR が必ず draft で作られ、以降のタスクの成果が積める土台（本文テンプレート・リンク）が揃った状態を作る。
- **スコープ**:
  - 含む: ホストの判定、default ブランチの特定と最新化、ブランチの命名と作成、差分なし時の空コミット、draft MR の作成（issue へのリンクを含む本文テンプレート）、結果の報告
  - 含まない: issue の確定とブランチ名・MR タイトルの承認（`10-task-overall-plan`）、未コミットの変更の扱いの確認（呼び出し元）、MR 本文のその後の更新（タスクの切れ目の処理）、マージ

---

## ユーザーストーリー

**[As a]** issue 駆動で作業を追う開発者として、

**[I want]** ブランチ名と MR を見ればどの issue の作業か分かり、MR が最初から draft で issue に紐づいていてほしい。

**[So that]** 作業の単位が GitLab / GitHub 上で迷わず辿れ、未完成の MR が誤ってマージされないため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When ブランチと MR を作るとき、Shall スキルはリポジトリのリモートからホスト（GitLab / GitHub）を判定して対応する CLI を選び、判定できない場合は推測せずユーザーに確認しなければならない。
- When ブランチを作るとき、Shall スキルは default ブランチを特定して最新を取り込み、その先端から `feature-<issue番号>-<slug>`（不具合修正は `fix-<issue番号>-<slug>`。slug は英小文字・数字・ハイフンで 2〜4 語）のブランチを作って切り替えなければならない。ブランチ名は呼び出し元で承認済みのものを使う。
- When MR を作るために差分が必要なとき、Shall スキルはコミット・push の提供コマンドで開始コミット（持ち越された作業領域のファイルがあればそれを載せ、無ければ空コミット）を作って push しなければならない（空コミットが許される場面はここ）。
- When draft MR を作るとき、Shall スキルはこのスキルが持つ MR 本文のテンプレート（概要・変更点・動作確認・関連 issue）を使い、関連 issue の欄に issue へのリンク（マージで issue が閉じる形式）を書き、必ず draft として作成しなければならない。
- When 作成が終わったとき、Shall スキルはブランチ名・MR の番号と URL を呼び出し元に返し、呼び出し元が報告と記録に使えるようにしなければならない。

### 代替フロー

- If 同名のブランチが既に存在する場合、Then スキルは上書きせず、別の slug を提案して呼び出し元に確認を返さなければならない。
- If 現在のブランチに紐づく open な MR が既にある場合、Then スキルは新しく作らず、既存の MR の番号と URL を返さなければならない（1 ブランチ = 1 MR）。

### 例外フロー

- If CLI が未導入・未認証の場合、Then スキルは導入・認証の手順を呼び出し元に返して停止しなければならない。
- If 未コミットの変更がある状態で呼ばれた場合、Then スキルはブランチを作らず、扱いの確認（呼び出し元の手順）が先であることを返さなければならない（黙って持ち越さない・stash しない）。
- If default ブランチの最新化やマージコンフリクトの解消が必要な状態だった場合、Then スキルは自動で解消せず、状態を呼び出し元に返さなければならない。
- If MR の作成に失敗した場合、Then スキルはコマンドと出力を呼び出し元に返して停止し、別の手段で再試行してはならない。
- If リポジトリが手順を安全に進められない状態にある場合（マージ・リベースの途中、リモート追跡の切れたブランチ、複数リモートで push 先が曖昧、ブランチ保護による push 拒否など）、Then スキルは自動で解消せず、状態と対処の選択肢を呼び出し元に返して停止しなければならない。

### 他のスキル・機構との整合

- When ブランチの push と空コミットを行うとき、Shall `20-common-step-commit-push` の手順と提供コマンドに従い、`git` を直接実行してはならない。
- When この操作を行うとき、Shall その書き込みが作業中のチケット（全体計画チケット）の「やってよいこと」に宣言されていることを前提とし、宣言外での実行は機構に拒否される。
- When 呼び出し元がブランチ・MR の作成を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。

---

## 前提条件

- 対象 issue が確定し、ブランチ名・MR タイトルが呼び出し元で承認済みであること
- 未コミットの変更の扱いが呼び出し元で解消済みであること
- `glab`（GitHub では `gh`）CLI が導入・認証済みで、コミット・push の提供コマンドが使えること

---

## 制約条件

- **技術的制約**: ブランチの区切りはすべてハイフン（スラッシュは使わない）。MR は必ず draft で作る
- **ビジネス的制約**: ブランチ名・MR タイトルは人間が承認したものを使う。draft の解除は全体まとめの手順でのみ行う
- **外部的制約**: 1 issue = 1 ブランチ = 1 MR。既存ブランチ・既存 MR を上書きしない

## 依存関係

- `10-task-overall-plan`（呼び出し元。issue の確定と承認を済ませる）
- `20-common-step-commit-push`（空コミットと push）

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | ブランチ名と MR 本文から issue 番号が一意に辿れ、マージで issue が閉じる |
| 一貫性 | GitLab / GitHub のどちらでも同じ命名規約・同じ本文テンプレートで作られる |
| 冪等性 | 再実行しても既存のブランチ・MR を壊さない（既存があればそれを返す） |
| 安全性 | MR は draft で作られ、未コミットの変更を巻き込まない |
