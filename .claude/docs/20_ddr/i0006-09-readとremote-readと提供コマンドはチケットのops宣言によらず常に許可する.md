# i0006-09. read・remote-read・提供コマンドはチケットの ops 宣言によらず常に許可する

## 背景

チケットの権限宣言は type 定義を上限とし、宣言で広げられない（i0001-02）。仕様 §8 は `d.ops` に無い分類は使えない、と書いていた。実装（issue #6 チケット 0014〜0021）の `scope.sh` は `read` / `remote-read` と提供コマンド（`provided`）を宣言の有無にかかわらず allow にしており、フィードバック計画 0022 の候補 G1 で「仕様と実装が食い違う。どちらを正にするか」が挙がった（実装結果レポート 0013 の逸脱 D-26）。`ticket.sh create` の `--allow-ops` を省略したチケット（計画タスクの多く）で、ファイルを読む・`git log` を見る・`ticket.sh complete` を打つ、という最低限の操作が宣言漏れで拒否される問題が実装中に起きていた。

## 決定

- `read` / `remote-read` と提供コマンド（`provided`）は、チケットの `allow.ops` に無くても**常に許可**する。type 定義の `ops` にも依らない
- それ以外の分類（`write-local` / `remote-write` / `build-test` / `hook-test` / `web` 等）は従来どおり「宣言と上限の両方にあるときだけ」
- 仕様 §8 の宣言の説明にこの例外を書き、`10-task-*` の計画タスクは `--allow-ops read` を書かなくてもよい（書いても害はない）

## 理由

- 読むだけの操作は、許可範囲の目的（作業領域外への書き込みと外部への副作用を止める）に触れない。宣言漏れで止まる害の方が大きく、ヘッドレス実行では宣言漏れ 1 つでセッションが終わる
- 提供コマンドは機構自身の状態遷移（着手・完了・コミット）で、これが宣言に依存すると「宣言し忘れたチケットは完了できない」という行き止まりになる。提供コマンドの中の検査（allow.write の範囲・DoD の根拠）は別に効いている
- 実装側を仕様に合わせる（宣言必須に戻す）と、既存チケットの宣言を全件直す上に、0022 で同じ判断（G1 は仕様側を変える）を既に確認している

## 却下した案

- **仕様どおり宣言必須にする**: 計画タスクの `--allow-ops` 省略が全部拒否になる。`ticket.sh create` の既定値に `read` を足す案も、既に作られたチケットには効かない
- **`ticket.sh create` が既定で `read,remote-read` を補う**: 記録上は宣言があるように見えるが、実態は「常に許可」と同じ。仕様に例外として書く方が読み手に正直
- **提供コマンドだけ常に許可し、read は宣言必須**: 読めないのに提供コマンドは打てる、という組み合わせに意味が無い

## 影響

- `10_spec/フック共通仕様.md` §8（宣言 `d` の説明）と §11 HK-T15
- `10_spec/hooks/20-PreToolUse/workflow-guard.md` 制御方式 6（提供コマンド・読み取り系・`remote-read` を無条件に許可する分岐がこの決定の実現箇所。ops 未宣言の拒否は WF204 / WF206 で、これらの分類はその対象にならない）
- `10_spec/skills/20-common-step-ticket.md`（`--allow-ops` の説明。0029 で反映）
