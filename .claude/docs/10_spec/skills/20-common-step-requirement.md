# 20-common-step-requirement スキル 仕様

## 概要・禁止事項

要件定義書の作成・更新の共通ステップの内部仕様。対応する要件は [00_requirement/skills/20-common-step-requirement.md](../../00_requirement/skills/20-common-step-requirement.md)。

スクリプトは持たず、テンプレートと手順で書き方を固定する。書く内容の合意は呼び出し元（設計タスクと人間レビュー）が担う。

禁止事項:

- 内部構造（スクリプト名・コマンド・判定順・スキーマ・実パス）を書くこと — 仕様書へ回す
- 経緯（検討・却下案・変遷）を本文に書くこと — DDR へ分離する
- 本文への変更履歴・追記の印の記録（正史は直接書き換える）
- 「関連するドキュメント」「レビュー記録」の節
- 合意されていない決定の記載
- 同じ内容の複数の書への重複記載（1 か所に書き、他は参照）

## 呼出条件

- `10-task-design-exec`・`10-task-ai-asset-design-exec` が要件定義書を作成・更新するとき
- `00-workflow-quick-request` 等から要件の軽微な文言修正を頼まれた場合も、書き方はこの仕様に従う

## IN / OUT

| IN | OUT |
|----|----|
| 対象（スキル / フック / エージェント）と名前、書くべき要件の内容（呼び出し元で合意済み） | `.claude/docs/00_requirement/<種別ディレクトリ>/<対象名>.md`（新規はテンプレート由来、更新は正史書き換え）。経緯があれば DDR の新規ファイル |

## IN / OUT サンプル

- 新規: スキル `20-common-step-ticket` → `.claude/docs/00_requirement/skills/20-common-step-ticket.md`（対象と同名）
- フック: `workflow-guard`（PreToolUse）→ `.claude/docs/00_requirement/hooks/20-PreToolUse/workflow-guard.md`
- 更新: 「片付けの対象から logs/ を除く」→ 該当の Shall 文を直接書き換え、決定の経緯は `20_ddr/i0004-NN-....md` に起こす

## 処理フロー

1. **配置と命名**: 対象の種別からディレクトリ（`skills/` / `hooks/<イベント番号ディレクトリ>/` / `agents/`）を決め、対象と同名のファイルにする（1 対象 1 書）。横断的な内容はどれか 1 つの書に寄せ、他からは参照する
2. **新規作成**: テンプレートをコピーし、frontmatter（`type: requirement` / title / description / tags / keywords）と章を順に埋める。章の見出しはテンプレートの文言をそのまま使い順序も変えない: 概要（背景・目的・スコープ）→ ユーザーストーリー → 受け入れ基準（Acceptance Criteria）→ 前提条件 → 制約条件 → 依存関係 → 非機能要件
3. **受け入れ基準**: EARS（When 〜 Shall / If 〜 Then / Shall not）で書き、節を メインフロー → 代替フロー → 例外フロー → その他（規約・整合。テンプレートの「他のスキル・機構との整合」など内容に合わせた見出し）の順に置く。先頭 3 節の見出しは「メインフロー」「代替フロー」「例外フロー」の文言で始める（「メインフロー: issue の確定」のように補足を後置してよい。メインフローが長い要件書は「メインフロー」の下に小節（`####`）を切ってよい）
4. **線引きの判定**: 書こうとする記述ごとに「外部の観察者（利用者・レビュアー）に見えるか」を問い、見えないもの（実現手段）は仕様書へ回す。スコープの「含まない」には担い先を添える
5. **経緯の分離**: 決定に検討・却下案があれば DDR（`20_ddr/i<issue番号4桁>-<連番>-<タイトル>.md`。背景 / 決定 / 理由 / 却下した案 / 影響）を起こし、本文には現在の正だけを書く
6. **更新**: 既存の書は該当箇所を直接書き換える。他の書と矛盾したら、矛盾する書を特定して呼び出し元に返す（片方だけ直さない）
7. **セルフレビュー**: 章順・フロー順・禁止節の不在・EARS の形式・プレースホルダの残存が無いことを確認して呼び出し元に返す

## OUT ひな形

`assets/requirements.template.md`: frontmatter と全章の骨格（各章に書き方の 1 行ガイドをコメントで持ち、記入時に消す）。プレースホルダは `{{名前}}` 形式。

## 参照ナレッジ

- 章立て・書き方の詳細な規約: `rules/`（設計文書ルール。`design-docs`・`ai-asset-design-docs`）
- 対になる仕様書の書き方: `20-common-step-spec`
- DDR の形式: 既存の `20_ddr/` の書（形式の手本）

## Script 処理

なし。章立て・フロー順・禁止節の機械検査は将来の設計文書検査（ルールの機械検査）に統合する想定で、それまでは処理フロー 7 のセルフレビューが担う。

### テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| RQ-E01 | 新しいアセットの要件定義書の作成依頼 | 決定済みフォーマット（章立て・受け入れ基準のフロー順）に従い、外部的な振る舞いだけを書き、内部構造（スクリプト名・判定順）を書かない | 章立ての一致、内部構造の語が無いこと |
| RQ-E02 | 既存の要件定義書の更新依頼（振る舞いの変更） | 現在の正史として書き換え、履歴・経緯は書かず DDR に回す | 変更履歴の節が無いこと、DDR の有無 |
| RQ-E03 | 1:1:1 を崩す依頼（2 アセットを 1 文書に） | 崩さず 1 アセット 1 文書にするか、理由を返す | 文書の分割 |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン: 対象と同名で種別ディレクトリに置く（1:1） | 処理フロー 1 |
| メイン: frontmatter と章順 | 処理フロー 2、OUT ひな形 |
| メイン: EARS とフロー節の順序 | 処理フロー 3 |
| メイン: 外部視点・内部構造は仕様へ | 処理フロー 4、禁止事項 |
| メイン: 正史のみ・経緯は DDR へ | 処理フロー 5、禁止事項 |
| メイン: 更新は正史の書き換え・履歴を残さない | 処理フロー 6、禁止事項 |
| 代替: 横断的な要件は 1 つに寄せて参照 | 処理フロー 1、禁止事項（重複） |
| 代替: 線引きに迷ったら観察者基準 | 処理フロー 4 |
| 例外: 矛盾は特定して返す | 処理フロー 6 |
| 例外: 未合意の決定は書かない | 禁止事項 |
| 章の書き方: 背景・目的・スコープの分離、「含まない」の担い先 | 処理フロー 2・4 |
| 章の書き方: 関連ドキュメント・レビュー記録の節を置かない | 禁止事項、処理フロー 7 |
