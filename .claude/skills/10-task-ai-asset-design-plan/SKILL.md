# 10-task-ai-asset-design-plan — .claude/docs/ に何を書くかを決める

共通手順の禁止事項（`10-task-investigation-plan` の冒頭が正）に加えて、`.claude/docs/` の要件・仕様・DDR・用語辞書・横断文書の**本文を書き始めない**（骨子まで）。アセット本体（`.claude/skills/`・`hooks/`・`rules/`・`agents/`・`settings.json`）に書き込まない。1:1:1（アセット 1 : 要件定義書 1 : 仕様書 1。rules は要件のみ）を崩す一覧を作らない。中核の変更要否を判断せずに計画を書かない。

## 目的

AI アセットの正史（`.claude/docs/`）に何をどう書くかを骨子まで固める。中核に触るかどうかを先に決め、後段のロックアウト対策の入力にする。

- 要件: `.claude/docs/00_requirement/skills/10-task-ai-asset-design-plan.md`
- 仕様（正。固有手順・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-ai-asset-design-plan.md`
- 処理の共通手順（正）: `10-task-investigation-plan` の「計画タスクの共通手順（正）」

## 手順

共通手順（着手 → 入力の確認 → 計画書 → 実施チケット群 → 次の計画チケット → 完了 → 結果報告）は `10-task-investigation-plan` に従う。ここでは固有部分だけを示す。

- 入力がフィードバック計画書の改善候補なら、候補ごとに「この issue で扱う / 別 issue / 扱わない」を対応表に書く（扱わないは理由付き）。**扱う候補に実装を伴うものが 1 件でもあれば、次の計画チケットは `ai-asset-implementation-plan` にする**。設計だけで閉じる候補しか無いときだけ、次はフィードバック計画または全体まとめになる。判断の材料は「その候補が `.claude/docs/` の改訂だけで満たされるか」で、アセット本体・フック・`settings.json` に触る必要があるなら実装を伴う
- **実装と仕様が食い違う候補は、どちらを正にするかまで計画の段階で決める**。「設計チケットで決める」と送ると、実装計画が許可範囲を書く時点で対象が確定せず、依存するテストの洗い出しが漏れる。決め方は変更行数だけで選ばず、**既存の同種アセットとの一貫性・所有関係・その決定が波及する範囲**を並べて比べ、採らなかった案と理由を DDR に残す前提で「結論方針」に書く
- **台帳を確定するチケットには「識別子の定義が 1 番号 1 原因か」の確認を DoD に入れる**。エラー識別子・テスト ID・eval ID のように番号で引く一覧は、1 つの番号が 2 つの原因を指すと呼び出し側が分岐できない
- **次の計画チケットの目的文に件数を固定で書かない**。先行チケットで枚数が変わると目的文と実体がずれる。目的は「何を決めるか」で書き、枚数は計画書の表に載せる
- 計画書の**結論方針**でまず**中核（フック・settings.json）の変更要否**を判断し、要なら影響するフックとロックアウトの可能性を書く
- **文書一覧**はアセットごとに 1:1:1 で要件定義書・仕様書（新規 / 更新）を挙げ、骨子を付ける。あわせて更新が要る**横断文書**（`自己改善ワークフロー機構.md`・`rules/ルール体系.md`・`90_glossary/`）と用語の追加・変更を挙げる
- 骨子には**ヘッドレス実行での帰結**（承認が取れないとき止まるのか・既定で進むのか）を各アセットに含める
- **AI アセット設計チケットの DoD の型**: 「要件定義書・仕様書がテンプレートに沿って作成（更新）されている」「受け入れ条件 {{X}} が仕様のテスト観点（テスト ID）に落ちている」「横断文書・用語辞書と整合している」「決定の経緯が DDR に残っている」「ヘッドレス実行の帰結が書かれている」
- 1 チケット = 関連するアセットのまとまり（例: フックとそれを呼ぶスキル）
- 人間レビュー要否の既定（方針が無い場合）: AI アセット設計計画チケット・設計チケットとも「要」
- **見てほしい点の固定項目**: 中核変更の要否判断の根拠 / 文書一覧の網羅（1:1:1・横断）/ ヘッドレスの帰結 / チケットの粒度と次の計画チケット

## OUT ひな形

`assets/ai-asset-design-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR・起点（調査結果 / フィードバック計画の候補） |
| 結論方針 | 中核変更の要否と根拠、採る案 |
| 文書一覧と骨子 | アセット × 要件定義書 × 仕様書（新規 / 更新）× 骨子 |
| 横断整合 | 更新する横断文書・用語辞書の項目 |
| ヘッドレス実行の帰結 | アセットごとの止まる / 進むの方針 |
| 受け入れ条件（候補）との対応 | 条件 × 文書 × テスト ID の予定 |
| AI アセット設計チケット | まとまりごとのチケットと依存 |
| 保留した点 / 対象なし | 該当時 |

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 中核に触るかどうか判断できない | 判断せずに計画を書かない。調査の追加を提案するか、触る前提（重い側）に倒して理由を書く |
| 実装と仕様が食い違う候補がある | 設計チケットに送らず、計画の段階でどちらを正にするか決める |
| 1:1:1 に収まらないアセットがある | 一覧を崩さない。分けられない理由を「保留した点」に書き、見てほしい点に載せる |
| 改善候補が大きすぎる | この issue で扱わず「別 issue」に分類し、理由を対応表に書く |
| 共通手順で止まった（TK002 / TK005 / RV00x） | `10-task-investigation-plan` の「エラー時の対処」に従う |
