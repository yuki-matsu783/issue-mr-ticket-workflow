# i0001-06. ワークは 14 種を計画と実施の対で並べ、type から次のスキルを機械的に決める

## 背景

依頼でワークの種類が 14 種（全体計画、調査計画、調査実施、設計計画、設計実施、実装・テスト計画、実装・テスト実施、設計フィードバック計画、設計フィードバック実施、AI アセット設計計画、AI アセット設計実施、AI アセット化計画、AI アセット化実施、全体まとめ）として指定された。参考実装 MR-driven-workflow は 5 フェーズ 43 ステップの位置番号（flow-id）で進行を管理し、ステップの挿入で以降の番号がすべて繰り下がる負債を抱えている。agent-workflow はチケットの type から次のスキルを一意に決める。

## 決定

- ワークは 14 種に固定し、各ワークに一意の type 識別子を与える（`overall-plan` / `investigation-plan` / `investigation` / `design-plan` / `design` / `implementation-plan` / `implementation` / `design-feedback-plan` / `design-feedback` / `ai-asset-design-plan` / `ai-asset-design` / `ai-asset-implementation-plan` / `ai-asset-implementation` / `wrap-up`）
- フェーズ列は全体計画が決める。先頭は全体計画、末尾は全体まとめ、その間は「計画 → 実施」の対で並べ、片方だけの採用は認めない
- 調査・AI アセット設計・AI アセット化は必ず含める。設計と実装・テストは依頼の性質で含めるかを決め、実装・テストを含めるときは設計フィードバックを必ず含める。含めたフェーズでやることが無いと計画ワークで分かったら、フェーズを省くのではなく計画チケットを「対象なし」として即座に完了する（まだ行っていない全体計画の段階で「やらない」とは判断できないため）
- 次に読み込む work スキルは、境界判定スクリプトが返す `todo_head_type` から機械的に決める（`<phase>-plan` → `10-work-<phase>-plan`、`<phase>` → `10-work-<phase>-exec`、`wrap-up` → `10-work-wrap-up`）。進行を位置番号で表さない
- 「全体まとめ」は参考実装の retrospective（振り返り）に、統括レポートの作成・MR 本文の最終化・AI アセット改善候補の issue 起票を加えたワークとする
- `.claude/` 配下（スキル・フック・ルール・エージェント・settings）の変更は、文言修正であっても `00-workflow-issue-mr-driven` の AI アセット設計 → AI アセット化のフェーズで行う。全体まとめや軽作業の中で直接修正しない

## 理由

- type ベースなら、ワークの追加・並べ替えが既存の識別子に影響しない。位置番号は挿入のたびに全参照の追従が要る
- 計画と実施を別 type にすることで、フェーズごとに「計画の切れ目」と「成果の切れ目」が分かれ（そこで人間レビューを入れるかはチケットのレビュー要否で決まる。i0001-07）、`todo_head_type` からスキルを一意に決められる
- `.claude/` 配下を例外なく issue-MR 駆動にすることで、機構自身の変更が常にレビューと DDR を経る。文言修正の例外を認めると「振る舞いが変わるかどうか」の判定が AI の裁量になる

## 却下した案

- **flow-id（位置番号）で進行を管理する（MR-driven-workflow 方式）**: 人間が「今 3-6」と読めるが、挿入・並べ替えで番号が動き、DDR に「当時の番号」の注記が積み上がる
- **計画と実施を 1 つの type にまとめてレビュー回数を減らす**: 往復は減るが、計画の合意前に実施が始まりうる。往復の重さはチケットの人間レビュー要否を「不要」に倒すこと（i0001-07）で対処する
- **全体計画でフェーズを理由付きで省略できるようにする（初版案）**: 小さな依頼の固定費を下げられるが、調査や設計フィードバックを「やらない」と決める根拠は、まだ行っていない全体計画の時点では持てない。計画ワークで「対象なし」と分かった時点で即完了するほうが、省略の判断が実際の情報に基づく
- **設計フィードバックを設計フェーズに吸収する**: フェーズ数は減るが、実装で判明した差分を設計文書へ書き戻す作業が実装チケットの中に埋もれ、DDR への反映が漏れる
- **`.claude/` 配下の文言修正は軽作業で許す（agent-workflow 方式）**: 手軽だが、上記のとおり判定が裁量になる。ユーザーの指示により例外を置かない

## 影響

- 要件定義書 B・I 節、`CLAUDE.md`「作業の振り分け」
- work スキルは 14 種に対応して `10-work-overall-plan` / `10-work-<phase>-plan` / `10-work-<phase>-exec` / `10-work-wrap-up` を用意する
- type 定義（`workflow-types.json` 相当）は 14 エントリを持つ
