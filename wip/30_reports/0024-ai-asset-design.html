境界レビュー 2 巡目の B1・B15・B2・B3・B4・B5 を反映した。中心は 公式が「subagents run in the background by default」と定めており、PostToolUse Agent が「走り終わった後」ではなく「起動した直後」に発火するという前提の食い違いで、.claude/docs/ に background への言及は 1 件も無かった。更新は要件 1 本・仕様 3 本・DDR 3 本の訂正、新規の DDR は 5 件（i0009-50〜54）。確定したのは 5 つ: (1) background 既定を §2 に据えた（WF801 には有利・WF811〜813 には致命的）、(2) tool_response.status で分岐し async_launched では検査せず WF814 を出す、(3) 通知しない場合も skip を記録し縮退時は自分で判定する、(4) tool_response は camelCase（agentId）、(5) systemMessage の実測を §12 T9 と 4c に登録した。

◆特に見てほしい

判断に困っている

  • f1（✕問題）background 既定という前提が案内側フックの設計全体に効く。今回は subagent-stop-check の検査が「起動直後に作業前の作業領域を見る」ことになる 1 点を直したが、「サブエージェントが終わったことをメインエージェントが知る経路」が機構に無いという構造は残る。SubagentStop の出力は親に届かず（§12 T1）、PostToolUse は起動時に返る。foreground を促す（WF803）以外の手が無いのが正しいか

実施した内容と結果

  1. 1

    サブエージェントは既定で background ✕問題 根拠: 境界レビュー B1、hooks.md:1699・:1701・:1711

    公式は「As of v2.1.198, subagents run in the background by default」「a background launch returns immediately」と定め、tool_response の説明は「When a foreground Agent call completes …」と foreground に限定されている。つまり既定では PostToolUse Agent は起動した直後に発火する。.claude/docs/ に background への言及は 1 件も無かった。この違いは 2 つの用途で逆に効く — WF801（実行者の不一致）には有利（i0009-26 の想定より早く届く）、WF811〜813（作業後の検査）には成立しない（作業前の作業領域を見て「該当なし」を返し、問題が無かったと誤って伝わる）。決定: 前提を §2 に据え、tool_input.run_in_background が明示的に false でなければ background として扱う。タスクの実施者を background で起動しようとしたら WF803 で通知する（起動は止めない）。要件にも「完了を待たない形で起動されるとき、その旨と検査が届かないことを伝える」を足した。

    実測への依存: あり（status が実際に async_launched になるかはフェーズ 4c）

    根拠を見る（読んだ箇所と出力） 
    hooks.md:1699  When a foreground Agent call completes, your PostToolUse hook receives
               the subagent's final text and run telemetry in tool_response
hooks.md:1701  status | "completed" for foreground subagents, "async_launched" for
               background subagents. As of v2.1.198, subagents run in the background
               by default, so an omitted run_in_background also produces "async_launched"
hooks.md:1711  For background subagents, the tool returns when the task moves to the
               background … a background launch returns immediately
hooks.md:1680-1697  Agent の tool_input は prompt / description / subagent_type / model
               （run_in_background は表に無い → 省略 = background として扱う）

grep -rn "async_launched|run_in_background" .claude/docs/  → 0 件（0024 以前）
DDR: i0009-50 / 識別子: WF803

    結論

    前提の食い違いを塞いだ。ただし「サブエージェントが終わったことをメインエージェントが知る経路」が機構に無い構造は残る。

  2. 2

    status で分岐し、async では作業後の検査をしない ◎良 根拠: 境界レビュー B1、tool_response.status

    決定: subagent-stop-check の PostToolUse Agent を tool_response.status で分岐する。completed は従来どおり（記録を読む／その場で検査して WF811〜813）。async_launched は検査しないで、代わりに WF814「background 起動なので完了後の検査は届かない。run_in_background: false で起動し直すか、完了を確かめてから自分で確認すること」を伝える。WF801 の縮退判定は起動の事実に関するものなので status を問わず行う。想定外の status は検査しない側（安全側）に倒す。

    実測への依存: 一部あり（status の実際の値）

    根拠を見る（読んだ箇所と出力） 
    要点: 「検査できない状況で『問題なし』と伝える」のは、何も伝えないより悪い
      WF814 は「検査していない」という事実を伝える

却下: status を見ずに常に検査する（作業前を見て「該当なし」＝誤った安心）
      async のときは何も出さない（検査していないことが誰にも伝わらない）
      次のツール呼び出しまで遅らせる（フックは状態を持たない）
      WF811〜813 を再利用して「検査していない」を表す（識別子は 1 意味に対応）

なお SubagentStop 側の記録は background でも残る
  logs/sessions//subagent-.json
  届かないのは「その場でメインエージェントに」だけ
DDR: i0009-51 / 識別子: WF814 / テスト: SP-T07

    結論

    「検査できない状況で『問題なし』と伝える」を避けた。

  3. 3

    「記録が無いときに再掲する」は論理的に成立しない ◎良 根拠: 境界レビュー B2、i0009-31

    i0009-31 は「decisions.jsonl に WF801 の notify 記録が無いときだけ再掲する」と書いていたが、記録が無ければ再掲する元が無い。さらに「記録が無い」は 2 つの状態を区別できない — (a) PreToolUse が使えず判定していない（縮退）、(b) PreToolUse が判定したが通知不要と決めた（一致していた等）。(b) で通知すると、不一致でないものを通知する。決定: subagent-start-check は通知しなかった場合も skip（理由 5 通り）を記録する。記録が 1 件も無いときだけが縮退。縮退時、subagent-stop-check は再掲ではなく自分で判定する。制御方式にこの手順を置き、入出力に tool_input・decisions.jsonl・model-aliases.txt を加えた。

    実測への依存: 無し（判定条件の定義）

    根拠を見る（読んだ箇所と出力） 
    skip の理由 5 通り:
  一致 / 対象チケット無し / executor の記載無し / model が特定できない
  / subagent_type が対象外

縮退の判定: 同じ tool_response.agentId について subagent-start-check の記録が
            notify も skip も 1 件も無いときだけ

縮退時の自己判定の手順（制御方式 2 として新設。以降を繰り下げ）:
  tool_input.subagent_type == task-executor
  対象チケットの executor が main 以外
  tool_input.model が特定でき、model-aliases.txt で正規化して不一致 → WF801

却下: 環境変数で縮退を判定（登録漏れ・起動失敗・matcher 不一致を拾えない）
      常に判定し記録があれば黙る（「誰が正か」が曖昧になる）
      skip を記録せず notify の有無だけで判定（(b) と区別できない）
DDR: i0009-52 / テスト: SA-T08・SP-T08

    結論

    縮退が機械的に判定できるようになった。skip の記録は「なぜ通知されなかったか」の振り返りにも効く。

  4. 4

    tool_response のフィールド名は camelCase ◎良 根拠: 境界レビュー B15、hooks.md:1702・:2325

    subagent-stop-check は tool_response の agent_id で記録を引くと書いていたが、公式では agentId。イベントの共通入力側は snake_case（agent_id / agent_transcript_path）で、同じものを指す名前が経路によって違う。i0009-52 で縮退判定が agentId による記録の引き当てに依存するようになったので、取り違えると jq が null を返して常に「縮退」と判定し、WF801 を重複して出す。エラーにならないので、テストを書かない限り気づけない。決定: §2 に命名の違いを書き、PostToolUse 経路の記述を tool_response.agentId に直した（SubagentStop 経路の agent_id はそのまま）。

    実測への依存: 無し（公式の記述）

    根拠を見る（読んだ箇所と出力） 
    hooks.md:1702（Agent の tool_response の表）
  agentId | string | Identifier for the subagent run
  同じ表に status / content / resolvedModel / modelsUsed / totalTokens /
  totalDurationMs / totalToolUseCount / usage（すべて camelCase）

hooks.md:2325（SubagentStop の入力）
  stop_hook_active, agent_id, agent_type, agent_transcript_path,
  last_assistant_message（snake_case）

却下: hook-common.sh で snake_case に正規化する（原本と突き合わせるとき変換が要る）
      agent_id で引く（PostToolUse Agent のイベント入力に agent_id は無い）
      両方試す（agentId // agent_id）（どちらが正かを仕様が決めない状態が残る）
DDR: i0009-53 / テスト: SP-T08 に「agent_id では引けない」を明記

    結論

    静かに失敗する（常に縮退と判定する）経路を塞いだ。
