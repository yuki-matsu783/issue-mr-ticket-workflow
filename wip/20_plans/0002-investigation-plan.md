# 0002 調査計画 — フック 11 本の仕様の洗い出しと実装フェーズの検証項目の整理

## 対象

- 対象 issue: #9 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/issues/9
- MR: #12 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/pull/12（draft）
- ブランチ: `feature-9-hook-bodies-settings`
- このチケット: `0002-investigation-plan`（フェーズ 2 の計画）

## この計画で何をするか

issue #9 の主作業（フック本体 11 本の実装）に入る前に、**読み取りだけで答えられる問い**を 3 枚の調査チケットに割り付ける。実測が要る問い（フック共通仕様 §12 の TBD）は、この調査では実施せず「実装フェーズの検証項目」として確かめ方だけを整理する。

決めたこと:

- 調査チケットは 3 枚（0005 / 0006 / 0007）。1 観点のまとまり = 1 チケット
- 外部技術調査（公式 hooks リファレンスの閲覧）は 0007 に閉じ、そのチケットだけ `allow.ops` に `web` を宣言する
- `.claude/**` への一時的な変更（`settings.json` へのフックの一時登録を含む）は計画しない（`10-task-investigation-plan` 仕様「調査計画の固有手順」）
- 既存のテスト・ビルドの実行は計画しない（`build-test` はどのチケットにも宣言しない）。`#6` のテストが通ることは PR #7 のマージ時点で確認済み
- 次の計画チケットは `0008-ai-asset-design-plan`。`predecessors` に 0005・0006・0007 を入れる
- 実装フェーズの検証項目（8 件）は**この計画書が表として持つ**。調査チケットは作らない（全体計画の表に「どの段で確かめるか」を添えたもの）
- 仕様の矛盾の「設計で直す / 実装で扱う」の振り分けは `0008` が行う。0005 は列挙と「実測に依存するか」の注記まで

## 方法とステップ

1. **Q1 の洗い出し（0005）**: `.claude/docs/10_spec/hooks/**/*.md` 11 本と `フック共通仕様.md` を読み、フックごとに「判定順の要約 / エラー識別子 / 終了方式（deny・ask・notify・inject）/ テスト ID の一覧 / 依存する lib・設定」の表を作る。識別子は §6 の台帳と突き合わせ、台帳に無い番号・重複を列挙する。テスト ID は `run-tests.sh --ids` の既存 ID とも突き合わせて重複を見る（実行はせず、既存テストファイルの grep で足りる）
2. **Q2 の結線（0006）**: `.claude/hooks/lib/*.sh` の関数定義（`grep -n '^[a-z_]*()'`）と、各フック仕様が呼ぶと書いている関数名を突き合わせる。引数・戻り値・出力先（stdout / 変数）の食い違い、仕様にあって lib に無い関数、lib にあって誰も呼ばない関数を列挙する
3. **Q3 の参考実装（0006 に同居）**: `参考ディレクトリ/agent-workflow/.claude/hooks/` を読み、構造（入力の読み取り・判定・出力の分け方）・終了方式・テストの書き方の差分をファイル単位で列挙する。流用するかどうかの決定は実装計画（フェーズ 4）に送る
4. **Q4 の外部技術調査（0007）**: 公式の hooks リファレンスを閲覧し、イベント名・入力フィールド・出力スキーマを確認する。仕様の前提（§2・§12 の T3・T4・T7）と一致するか、公式に記載が無いかを 1 行ずつ判定する
5. **Q5 の T5 と `git 'commit'`（0007 に同居）**: `.claude/docs/20_ddr/` と #6 の作業ログ（`git log` / `git show`）で T5 の結論を探し、`hook-common.sh` の実装が PowerShell を吸収しているかを読む。`cmdpos.sh` の `CP_GITLIKE` 周りと `block-direct-git` 仕様の「特定できない」の扱いを突き合わせる
6. **実装フェーズの検証項目**: 下の表（この計画書が持つ）が実装計画（フェーズ 4）の入力になる。**この調査では実施も再整理もしない**（全体計画「判断が必要になりそうな点」の実測側の表に、段階登録のどの段で確かめるかを添えたもの）
