# i0050-08. 並列実施の発効は、委ねた先を作業ツリーで動かす手段が確かめられるまで保留する

## 背景

`i0050-01` で 1 issue 内の同一フェーズのチケットの並列実施を採用し、`00-workflow-issue-mr-driven` 手順 2b（割り付け → `worktree.sh add` → 作業ツリーの置き場を添えた起動）を書いた。この手順は「起動されたサブエージェントの作業ディレクトリが、割り付けた作業ツリーのルートである」ことに全面的に依存している。

設計フェーズの敵対的レビューで、その依存が満たされないことが分かった。

- **起動プロンプトに置き場を書いても、起動された側の作業ディレクトリは変わらない。** `subagent-start-check` はフックの入力（stdin の `cwd`）だけを見て起動プロンプトを読まず、隔離を使わない起動の `cwd` は呼び出し元と同じ値になる（同仕様「対象チケットを採る作業ツリー」の表が自らそう書いている）
- **`cd` では移れない**（分類外 → WF204。フック共通仕様 §8。これは意図した設計判断で、判定の起点を 1 つに保つためのもの）
- 帰結は 2 つ。(1) 提供コマンドはルート相対表記でしか識別されない（同 §7-8・`HK-T12`）ので、作業ツリー側で `ticket.sh start` / `commit.sh` を呼ぶ手段が無い。(2) 作業ツリーへの Edit / Write は他のツリーのルート相対パスに畳まれるが、判定の材料になる作業中チケットは呼び出し元の作業ツリー（作業中 0 枚）から採られるため、`workflow-guard` が判定に入らないまま全部が通る
- つまり、`task-executor` 仕様が「隔離を使う形では避ける」と書いていた**静かな無効化**（隔離はされているが統制は効いていない状態）が、**隔離を使わない側の経路**で起きる

実行基盤について確かめられている事実は 3 つある。(a) Agent ツールには起動ごとの `isolation` があり、`isolation: "worktree"` で基盤が作業ツリーを作る（変更が無ければ自動で片付けられる）。(b) セッション自身を作業ツリーへ移す `EnterWorktree` / `ExitWorktree` がある。(c) **呼び出し元が用意した既存の作業ツリーをサブエージェントに割り当てる指定は無い。**

## 決定

- **並列実施（手順 2b）の発効を保留する。** ユーザーの明示の指示があっても、解禁の条件が満たされるまでは並列にせず、本流で 1 枚ずつ進める
- **`i0050-01` の「並列実施を採用する」という設計上の採否は取り消さない。** 手順・要件・仕様はそのまま残し、**使用可否だけ**を条件付きにする。上書きするのは `i0050-01` の「（採用したのだから）いま使える」という含みだけである
- **解禁の条件**は 2 つで、確認は AI アセット実装フェーズで行う。(1) 呼び出し元が用意した作業ツリーで委ねた先が動くことが確かめられた、**または**基盤の隔離の 3 点（分岐元が呼び出し元の `HEAD` である / ブランチ名の規約 / 成果を載せたまま作業ツリーが消えないこと）がすべて確かめられ、`worktree.sh` の管理対象の定義と `merge` の前提検査を合わせて改めた。(2) その経路で割り付けた作業ツリーの中の書き込みに `workflow-guard` の判定が効くことを機械テストで固定した
- **「作業ツリーを 1 つ使う運用」は保留の対象にしない。** セッション自身が作業ツリーへ移る手段（`EnterWorktree` / `ExitWorktree`）は確認済みで、そこで進めた成果を切れ目で本流へ合流する経路（`worktree.sh add` / `merge` / `remove`）はそのまま使える。受け入れ条件 A2（開始時に切るかどうかの既定と手順）はこの運用で満たす
- **`isolation: worktree` は、`worktree.baseRef` が設定されていても、成果を残す作業には使わない**（下の理由を参照）

## 理由

- 手段が無いまま手順だけを残すと、次に読む人（実装フェーズ）は「書いてあるとおりに起動すればよい」と読む。そのときに起きるのは拒否ではなく**素通り**なので、間違いに誰も気づかない。設計が避けたはずの状態を、設計自身が作ることになる
- 隔離（案 a）に寄せる形は、未確認の前提が 3 つ重なる。とくに**後片付け**が致命的である。本機構はチケットごとに `commit.sh` でコミットし、`ticket.sh complete` が未コミット無しを検査するので、サブエージェントが終わる時点の作業ツリーは**必ず** clean になる。これは「変更が無ければ自動で片付ける」という基盤の挙動の発火条件そのもので、成果を載せたブランチが消える経路と正面から重なる。実測せずにこの上へ仕様を積まない
- 隔離が作るブランチ（`worktree-<名前>`）は `worktree.sh` の管理対象の条件（`<本流の現在ブランチ>--wt-` で始まる）を満たさず、`merge` / `remove` の対象にできない（`WT005`）。管理対象の定義を広げれば通せるが、それは `merge` の前提検査 6「対象が同じ issue に属するブランチである」の根拠を消すことでもある。**統制を緩める向きの変更を、未確認の前提のために先に行わない**
- 保留のコストは小さい。並列実施の既定は元から「しない」（`i0050-06`）で、これまでの運用も本流 1 本である。失うのは「指示があれば並列にできる」という未検証の選択肢だけで、その選択肢は現に成立していない
- 受け入れ条件 A5・A6 は「並列を採用する場合」の条件文であり、手順・要件・仕様を残すことで文書の上では満たされる。実効性の確認は元から実装フェーズの仕事である

## 却下した案

- **基盤の隔離に寄せて発効させる（案 a。`isolation: "worktree"` + `worktree.baseRef` + 管理対象の定義の拡張）**: 未確認の前提が 3 つ（分岐元・ブランチ名・後片付け）あり、そのうち後片付けは本機構の「常に clean で終わる」性質と正面から衝突する。管理対象の定義を広げる変更は `merge` の前提検査の根拠を弱める。実測の後なら採れるので、解禁の条件 1 の選択肢として残した
- **起動プロンプトに置き場を書く形のまま発効させる**: 実際には作業ディレクトリが移らず、統制が効かないまま書き込みが通る。拒否されないので発覚もしない。これが指摘の出発点であり、採れない
- **サブエージェントに「絶対パスで書け」と指示して並列させる**: 書き込み先は他の作業ツリーのルート相対パスに畳まれるが、判定の材料は呼び出し元のチケット（0 枚）のままなので `workflow-guard` は入らない。提供コマンド（`ticket.sh` / `commit.sh`）も呼べないので、チケットの状態遷移とコミットが行えない。運用として成立しない
- **`cd` を分類に足して作業ディレクトリを移せるようにする**: `i0050-04` が「判定の起点を 1 つに保つための設計判断」として明示的に閉じた経路である。`cd <他の場所> && echo x > a.txt` の書き込み先が自分の作業ツリーの相対パスとして判定されるため、作業ツリーの外への書き込みが通る。並列実施のためにここを開けるのは、統制の根を壊す
- **並列実施の採用そのものを取り消す（`i0050-01` を廃止に戻す）**: 採否の判断材料（依頼と原則の読み直し）は変わっておらず、変わったのは手段の有無だけである。設計を捨てると、手段が確かめられたときに同じ設計をやり直すことになる。採否は維持し、発効だけを条件付きにする

## 影響

- `00_requirement/skills/00-workflow-issue-mr-driven.md`: 例外フロー **[E9]**（手段が未確認なら並列にせず本流で 1 枚ずつ）を追加し、メインフローの図に離脱点を置く。並列で委ねるときの受け入れ基準に「委ねた先をその作業ツリーで動かす手段を持っていること」を足す
- `10_spec/skills/00-workflow-issue-mr-driven.md`: 手順 2b を「発効は保留」とし、なぜ保留なのか・作業ディレクトリを向ける手段の表（セッション自身の移動 / 隔離 / 割り当ての指定）・解禁の条件 2 件を置く。eval `WFD-E10`（指示されても手順 2b を始めない）を足す
- `00_requirement/agents/task-executor.md` / `10_spec/agents/task-executor.md`: 「作業している場所が渡された作業ツリーでなければ始めずに返す」を代替フローに置き、`TXE-E09` で固定する。`isolation` は成果を残す作業に使わないことを明記する
- `10_spec/hooks/12-SubagentStart/subagent-start-check.md`: `WF804` が「起動プロンプトに置き場が無いこと」の通知ではないことを明記する
- `10_spec/フック共通仕様.md` §8: 作業ディレクトリを切り替えられるのはそのツールを動かしている主体だけであること、サブエージェントに割り当てる指定が無いことを書く
- AI アセット実装フェーズは、解禁の条件 1・2 を確かめる作業を持つ（既存の残課題 R34・R35 と同じ対象）。確かめられなかった場合も設計は成立し、並列実施が保留のまま残るだけである
