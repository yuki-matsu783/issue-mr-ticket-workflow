# i0004-05. 提供コマンドの内部からの git 実行はフックの拒否対象外とする

## 背景

敵対的レビューで、`finalize.sh` の片付け（wip/ 配下の全削除を 1 コミット）と `ticket.sh` の状態変更コミットの手段が未定義で、`commit.sh` の制約（`-A` / `.` / glob を CP001 で拒否、対象をパスで明示）と衝突すると指摘された。数十ファイルの削除をパス列挙で `commit.sh` に渡すのか、スクリプト内で `git` を直接叩くのか、後者なら `block-direct-git` の例外なのかが決まっていなかった。

## 決定

- `block-direct-git` フックが拒否するのは **AI による `git commit` / `git push` の直接実行**である。**提供コマンド（機構のスクリプト）の内部からの git 実行は拒否の対象外**とする。識別の方法（呼び出し元の判定）はフックの仕様で定める
- `ticket.sh`（create / start / complete / cancel）と `finalize.sh`（片付けの削除コミット）は、内部で `git` を直接実行してコミットする。コミットメッセージの規約（`<prefix>: <日本語>`・AI フッター禁止）には従う
- `commit.sh` の入口制約（対象のパス明示・一括ステージ禁止・除外リスト）は **AI が自分の成果物をコミットするときの制約**であり、提供コマンド内部の機械的なコミットには適用しない

## 理由

- 提供コマンドは機構の一部で、何をコミットするかがスクリプトに固定されている。AI の裁量による巻き込み事故（他作業のファイル・クレデンシャル）を防ぐための入口制約を、そこに課す意味が無い
- 片付けの削除コミットをパス列挙で `commit.sh` に流すのは冗長で、パス数の上限や除外リストとの相互作用で壊れやすい
- 「拒否するのは AI の直接実行」と境界を 1 文で言い切れる方が、フックの識別ロジックも実装者の判断も単純になる

## 却下した案

- **すべてのコミットを commit.sh 経由にし、削除はパス列挙で渡す**: 冗長で、除外リスト・引数長の問題を持ち込む
- **提供コマンドも一律に拒否し、フック側で個別に許可リストを持つ**: 許可リストの保守が要り、スクリプトを追加するたびにフックを直す必要が出る
