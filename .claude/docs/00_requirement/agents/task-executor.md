# task-executor エージェント

## 概要

全体計画・フィードバック計画・全体まとめ以外のタスクを、メインエージェント（`00-workflow-issue-mr-driven`）に代わって実施するタスク実行サブエージェントの要件を定義する。どのタスクもメインエージェントと同じ task スキルを読み込んで実施し、違いは誰が実行するかだけである。

- **背景**: タスクをすべてメインセッションで直列に実施すると、長い issue でコンテキストが compact され、現在地や手順の理解が失われる。タスクごとに独立したコンテキストのサブエージェントへ委ねればメインセッションには結果報告だけが積まれ、チケットに書かれた実行者（LLM モデル）の使い分けもできる。ただしサブエージェントはユーザーと対話できないため、委ねた作業の中で判断を確定できず、終わり方（結果報告）が揃っていないと呼び出し元がタスクの切れ目の処理に進めない。
- **目的**: どのタスクを委ねても、起動時に渡された文脈だけで作業が始まり、機構の統制の下で進み、呼び出し元が作業領域を読み直さなくても次の処理（タスクの切れ目・後始末）を選べる結果報告で終わる状態を実現する。
- **スコープ**:
  - 含む: エージェント定義、起動時に受け取る文脈、タスク単位・チケット単位の実施、**並列で起動されたときの作業ツリーの扱い**、実施中の統制との関わり、結果報告、失敗・中断時の終わり方
  - 含まない: 各タスクの中身と成果物（各 task スキルの要件定義書が正）、起動の判断・実行者の決定・**作業ツリーの割り付けと合流**・タスクの切れ目の処理（`00-workflow-issue-mr-driven` と全体計画）、作業ツリーを切る / 合流する / 片付ける操作（`20-common-step-worktree`）、宣言した範囲の強制（`workflow-guard`）、起動・終了時の検査（`subagent-start-check` / `subagent-stop-check`）、敵対的レビュー（`adversarial-reviewer`）

### issue の受け入れ条件との対応

起点: issue #50（worktree 上での機構の健全性と、1 issue 内の同一フェーズのチケット並列実施）

| issue #50 の受け入れ条件 | 満たす受け入れ基準 |
|---|---|
| A1: worktree 上で機構（フック・提供コマンド・`boundary.sh`）が健全に動くことが実測で確かめられ、動かない箇所があれば直っている | この書の対象外（フックと提供コマンドの要件・仕様が担う）。この書は代替フロー「作業ツリーの隔離を使うのは、隔離した作業ツリーの分岐元が現在の作業の先端になる設定が置かれているときだけ」で、機構が静かに無効になる起動を避ける側に立つ |
| A2: issue-MR 駆動を開始するときに worktree を切るかどうかの既定と手順が要件・仕様に定まっている | この書の対象外（`00-workflow-issue-mr-driven` と `20-common-step-worktree` が担う） |
| A3: 並行作業の手段（worktree / 別 clone）が CLAUDE.md か振り分けスキルから 1 ホップで辿れる | この書の対象外（`00-workflow-issue-mr-driven` が担う） |
| A4: 1 issue の中で同じフェーズの依存しないチケットを並列に実施する方式について、採否と理由が新しい DDR に残っている | この書の対象外（DDR `i0050-01`・`i0050-06`） |
| A5: 並列を採用する場合、宣言範囲の強制・差分の基準点・実行者照合が worktree ごとに一意に決まることが仕様に明記され、機械テストで確認されている | 代替フロー「並列で起動された場合…割り付けられた作業ツリーの中だけで作業し、他の作業ツリーの作業領域・成果物に書き込んではならない」（1 作業ツリー = 作業中チケット 1 枚を保ち、判定の材料を一意にする側に立つ）。判定そのものはフックの要件・仕様が担う |
| A6: 並列を採用する場合、並列作業の成果を feature ブランチへ合流させる手順（チケットファイルの衝突の扱いを含む）が定まっている | 代替フロー「…チケットを新規に作らず、push せず、合流しない」（合流は呼び出し元が切れ目で行う）。手順そのものは `20-common-step-worktree` と `00-workflow-issue-mr-driven` が担う |

## ユーザーストーリー

**[As a]** タスクを委ねるオーケストレータ（メインエージェント）として、

**[I want]** 起動時に渡した文脈だけでタスクを実施し、決まった形の結果報告で返してほしい。

**[So that]** 自分のコンテキストを実施の詳細で埋めずに済み、報告だけでタスクの切れ目の処理に進めるため。

**[As a]** 開発者として、

**[I want]** サブエージェントに委ねた作業も、チケットと作業ログにメインエージェントの実施と同じ粒度で残ってほしい。

**[So that]** どのモデルが実施したかによらず、フィードバック計画と MR レビューで同じように振り返れるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When メインエージェントがタスクを委ねるとき、Shall エージェントは起動時に、実施の対象（タスクまたはチケット）・読み込む task スキル・作業に要る文脈のありか（issue の受け入れ条件・計画書・チケット）・**作業中のブランチ名**（並列で起動されるときは、あわせて**割り付けられた作業ツリーのありか**）を受け取り、それ以上を呼び出し元に問い合わせずに作業を始められなければならない（サブエージェントに与えられる環境の情報はセッション開始時点のもので、その後のブランチの切り替えが反映されないため）。
- When 作業を始めるとき、Shall エージェントは指定された task スキルを読み込み、その手順に従って実施しなければならない（手順の再解釈・省略をしない）。
- When チケットに着手・完了するとき、Shall エージェントは提供コマンドで状態を進め、作業ログをその都度追記しなければならない（メインエージェントが実施する場合と同じ扱い。完了の検査も同じに受ける）。
- When 作業中に判断に迷ったとき、Shall エージェントはユーザーに質問せず、task スキルが定める置き場（作業ログの判断と根拠・レポートの保留した点・見てほしい点）に残して進めなければならない。
- When タスクの実施が終わったとき、Shall エージェントは結果報告を返して終えなければならない。結果報告は少なくとも、実施したチケットとその状態・成果物のありか・DoD の充足（根拠付き）・保留した判断と見てほしい点・呼び出し元への要求（後述）を含み、呼び出し元が作業領域を読み直さなくてもタスクの切れ目の処理に進める粒度でなければならない。
- When 新しいコンテキスト・別モデル（チケットの実行者がタスクのモデルと異なる場合を含む）で実施したいチケットがあるとき、Shall エージェントは自分でサブエージェントを起動せず、その要求を呼び出し元に返さなければならない（サブエージェントは入れ子で起動できないため。並列に実施するかどうかを決めるのも呼び出し元である）。

### 代替フロー

- If チケット単位で起動された場合（新しいコンテキスト・別モデルでの実施）、Then エージェントは渡された 1 枚のチケットだけを実施し、同じタスクの他のチケットに着手してはならない。
- If **並列実施のために作業ツリーを割り付けられて起動された場合**、Then エージェントは割り付けられた作業ツリーの中だけで作業し、他の作業ツリー（本流を含む）の作業領域・成果物に書き込んではならない。そのうえで、**チケットを新規に作らない**（採番は本流だけ）・**push しない**・**成果を本流へ合流しない**（合流は呼び出し元がタスクの切れ目で行う）。作業ツリーのありかが起動時に渡されなかった場合は、自分で切らず、足りないものとして結果報告に返す。
- If 作業ツリーの隔離（起動されたエージェントが自動で自分の作業ツリーを持つ形態）を使う場合、Then その隔離が**現在の作業の先端から分岐する**設定が置かれているときだけ使わなければならない。設定が無い環境では隔離を使わない（分岐元が既定ブランチになると、作業ツリーにチケットが 1 枚も無い状態で起動され、宣言した範囲の強制が働かないまま作業が進むため）。
- If 計画タスクでそのフェーズにやることが無いと分かった場合、Then エージェントは task スキルの定めに従いチケットを「対象なし」として即座に完了し、その旨を結果報告に含めなければならない。

### 例外フロー

- If 機構が操作を拒否した場合、Then エージェントは迂回・進行状態の直接編集・機構の無効化を行わず、伝えられた対処に従い、対処できなければ拒否の内容と現在地を結果報告に含めて終えなければならない。
- If 渡された文脈が不足していて作業を始められない場合、Then エージェントは推測で補わず、何が足りないかを結果報告に返して終えなければならない。
- If 作業を続けられなくなった場合、Then エージェントは現在地（どこまで終わり、次に何をするか）を作業ログに残して終え、チケットを勝手に完了にしてはならない（作業中のまま残ったチケットの後始末は呼び出し元とユーザーが `subagent-stop-check` の通知を受けて判断する）。

### 他のスキル・機構との整合

- When 実施中にリモートに関わるとき、Shall not エージェントはリモートへの書き込み（push・issue / MR の作成・編集・コメント）を行ってはならない（切れ目の push とレビュー依頼は呼び出し元が行う）。リモートの読み取りは行ってよい。
- When 実行者・人間レビュー要否に関わるとき、Shall エージェントはチケットの記載に従い、自分から変えてはならない（決定と変更は全体計画と未着手チケットの見直しで行う）。

## 前提条件

- 各 task スキルが入力（チケット・計画・issue の受け入れ条件）と出力（結果報告）を明確に持ち、メインエージェント・サブエージェントのどちらから読み込まれても成り立つ形で書かれていること
- Claude Code のサブエージェントとして LLM モデルを指定して起動でき、入れ子で起動できないこと
- 宣言した範囲の強制（`workflow-guard`）と起動・終了時の検査（`subagent-start-check` / `subagent-stop-check`）が、サブエージェントの中でもメインエージェントと同じように働くこと
- 並列で起動されるときは、呼び出し元が作業ツリーを用意して割り付け済みであること（作業ツリーの作成・合流・片付けはこのエージェントの仕事ではない）

---

## 制約条件

- **技術的制約**: サブエージェントはユーザーと対話できない。実施中に承認が要る判断はその場で確定せず、記録して人間レビューで確定する形にする
- **ビジネス的制約**: 実行者・人間レビュー要否の決定と変更は全体計画・未着手チケットの見直しで行い、エージェントはチケットの記載に従うだけで自分から変えない
- **外部的制約**: リモートへの書き込み（push・issue / MR の作成・編集・コメント）を行わない（委ねられるタスクのチケットにリモート書き込みは宣言されない。切れ目の push とレビュー依頼は呼び出し元が行う）。リモートの読み取りは行ってよい

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 実施の記録はチケットの作業ログと結果報告に残り、どのモデルが実施したかによらず同じ粒度で振り返れる |
| 一貫性 | どのタスクを委ねても、起動時に渡すものと結果報告の形が同じ |
| 簡潔性 | 結果報告はタスクの切れ目の処理に要る情報に絞り、実施の詳細は作業ログとレポートに残す |
| 可用性 | 失敗・中断しても作業領域は現在地が分かる状態で残り、呼び出し元が再開・後始末を判断できる |
