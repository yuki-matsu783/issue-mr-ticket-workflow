# 20-common-step-requirement スキル 仕様

## 概要・禁止事項

要件定義書の作成・更新の共通ステップの内部仕様。対応する要件は [00_requirement/skills/20-common-step-requirement.md](../../00_requirement/skills/20-common-step-requirement.md)。

スクリプトは持たず、テンプレートと手順で書き方を固定する。書く内容の合意は呼び出し元（設計タスクと人間レビュー）が担う。

禁止事項:

- 内部構造（スクリプト名・コマンド・判定順・スキーマ・実パス）を書くこと — 仕様書へ回す
- 経緯（検討・却下案・変遷）を本文に書くこと — DDR へ分離する
- 本文への変更履歴・追記の印の記録（正史は直接書き換える）
- 「関連するドキュメント」「レビュー記録」「変更履歴」の節
- 合意されていない決定の記載
- 同じ内容の複数の書への重複記載（1 か所に書き、他は参照）
- 図にだけある情報（EARS の箇条書きに無い条件・分岐・禁止）を作ること
- 図を外部ファイル・画像・外部サービスで持つこと
- 規約節にフロー（順序・分岐）を置くこと

## 呼出条件

- `10-task-design-exec`・`10-task-ai-asset-design-exec` が要件定義書を作成・更新するとき
- `00-workflow-quick-request` 等から要件の軽微な文言修正を頼まれた場合も、書き方はこの仕様に従う

## 処理フロー

1. **配置と命名**: 対象の種別からディレクトリ（`skills/` / `hooks/<イベント番号ディレクトリ>/` / `agents/` / `rules/`）を決め、対象と同名のファイルにする（1 対象 1 書）。横断的な内容はどれか 1 つの書に寄せ、他からは参照する
2. **新規作成**: テンプレートをコピーし、frontmatter（`type: requirement` / title / description / tags / keywords）と章を順に埋める。章の見出しはテンプレートの文言をそのまま使い順序も変えない: 概要（背景・目的・スコープ）→ ユーザーストーリー → 受け入れ基準（Acceptance Criteria）→ 前提条件 → 制約条件 → 依存関係 → 非機能要件
3. **受け入れ基準の節構成**: EARS（When 〜 Shall / If 〜 Then / Shall not）で書き、節を メインフロー → 代替フロー → 例外フロー → 規約節（0〜3）→ 他のスキル・機構との整合（0〜1）の順に置く。先頭 3 節の見出しは「メインフロー」「代替フロー」「例外フロー」の文言で始める（補足の後置は可）
4. **フロー節の判定**: 下の「フロー節の判定順」を上から当て、最初に当たった節に置く
5. **メインフローの図**: 下の「メインフローの図の記法」に従い、メインフロー節の先頭（EARS 箇条書きの前）に図を置く。ノード数を数え、上限を超えていれば分割する
6. **離脱点の対応付け**: 図の離脱先の識別子と、代替フロー・例外フローの項目の識別子を一致させる
7. **規約節**: 下の「規約節の命名と上限」に従う
8. **自由記述の分量**: 下の「自由記述と定型の切り分け」の目安に収める
9. **線引きの判定**: 書こうとする記述ごとに「外部の観察者（利用者・レビュアー）に見えるか」を問い、見えないもの（実現手段）は仕様書へ回す。スコープの「含まない」には担い先を添える
10. **経緯の分離**: 決定に検討・却下案があれば DDR（`20_ddr/i<issue番号4桁>-<連番>-<タイトル>.md`。背景 / 決定 / 理由 / 却下した案 / 影響）を起こし、本文には現在の正だけを書く
11. **更新**: 既存の書は該当箇所を直接書き換える。他の書と矛盾したら、矛盾する書を特定して呼び出し元に返す（片方だけ直さない）
12. **セルフレビュー**: 下の「セルフレビュー項目」を全件確認して呼び出し元に返す

### フロー節の判定順

記述ごとに次を上から問い、**最初に当たった**節に置く。当たらない、または複数に当たると判断したら、記述と理由を呼び出し元に返す（自分で決めない）。

| 順 | 問い | 当たったときの置き場 |
|---|---|---|
| 1 | その道は、目的を達成するすべての実行が通るか（分岐の本流を含む） | メインフロー |
| 2 | その道に入る起点は正常か（呼び出し元の入力・選択の違い / 対象が既に目的の状態にある / 複数の正しい入力形式） | 代替フロー |
| 3 | その道に入る起点は異常か（前提の不充足 / 外部の操作の失敗 / 機構の拒否 / 利用者の誤用 / 壊れた状態） | 例外フロー |
| 4 | その記述はフローではなく、成果物・データの中身の規定か | 規約節 |
| 5 | その記述は他のアセットとの関係の規定か | 他のスキル・機構との整合 |

判定は**起点**で決める。終わり方は検算に使う。

- 検算: 代替フローの項目はすべて目的を達成して終わる。目的を達成せずに返す項目が代替フローにあれば、起点の判定を誤っている（多くは前提の不充足で、例外フローが正しい）
- 例外フローの項目は、目的を達成せずに返すことも、回復してメインフローに戻ることもある。終わり方で例外かどうかを決めない

判定の適用例（既存の書から）:

| 記述 | 起点 | 判定 |
|---|---|---|
| 同名のブランチが既に存在する → 上書きせず別案を返す | 前提の不充足（作ろうとする名前が空いていない） | 例外フロー |
| 未コミットの変更がある状態で呼ばれた → ブランチを作らず返す | 前提の不充足 | 例外フロー |
| open な MR が既にある → 既存の番号と URL を返して完了 | 対象が既に目的の状態にある | 代替フロー |
| push 前チェックを意図的に飛ばす → 理由を差分に残してから飛ばす | 呼び出し元の選択 | 代替フロー |
| 直前のコミットに誤りが見つかった → 訂正の新規コミットで直す | 利用者の誤用 | 例外フロー |

### メインフローの図の記法

- 記法は mermaid の `flowchart TD`。Markdown の ```` ```mermaid ```` コードブロックに直接書く（外部ファイル・画像・外部サービスを参照しない）
- ソースは 1 行に 2 つ以上の辺を連ねない（`A --> B --> C` と書かない）。辺の行が行き先ノードのラベルを兼ねるのは可（`M1 -->|無い| M2[すべての操作を通す]`）
- ノード ID はメインフローの通し番号 `M1`, `M2`, … 。メインフローを分割しても番号は文書全体で継続する
- ノードのラベルは利用者から見た動作または判定を表す日本語。識別子だけのノードを置かない
- 判定のノードは `{...}`（ひし形）、通常のノードは `[...]`（四角）で書く。判定から出る辺には `|条件|` のラベルを付ける
- 代替・例外への離脱は破線 `-.->` で書き、辺に離脱の条件をラベルで付ける
- 離脱先は参照ノードとして図の末尾にまとめて宣言する。ID は `A<連番>`（代替フロー）/ `E<連番>`（例外フロー）、形はスタジアム型 `([代替 A1: <項目の要約>])` / `([例外 E1: <項目の要約>])`
- 図は EARS 箇条書きの要約。条件の詳細・禁止（`Shall not`）・数値は EARS が正で、図にだけある情報を作らない

### ノード数の数え方と分割

- 数えるのは 1 つの図に現れる `M<n>` のノードだけ。離脱先の参照ノード（`A<n>` / `E<n>`）は数えない
- 上限は 1 図あたり 15
- 超えたら、メインフローを利用者から見た一区切り（承認・引き渡し・状態の確定が起きる点）で分割する。見出しは `### メインフロー: <一区切りの名前>` とし、節ごとに 1 つの図を置く
- 上限は分割を義務づける閾値であって、上限以下の分割を禁じるものではない。一区切りが明確なら 15 以下でも分割してよい（読み手が節の見出しから流れの単位を掴めるため）
- 分割した節の間の受け渡しは、前の節の図の末尾に参照ノード `N<連番>([次: メインフロー: <次の節名>])` を置き、実線で繋ぐ。この参照ノードもノード数に数えない。最後の節には置かない
- 分割してもなお 1 節が 15 を超えるなら、対象そのものが 1 書に収まっていない。分割の提案を呼び出し元に返す

### 規約節の命名と上限

- 見出しは `### 規約: <対象>` で始める（例: `### 規約: メインフローの図`、`### 規約: 自由記述の分量`）
- 1 書あたり 3 節まで。超えるなら、対象の分割か仕様書への移動を呼び出し元に提案する
- 置けるのは、その書が定める成果物・データの中身の規定。順序・分岐（フロー）は置かない
- 他のアセットとの関係は規約節ではなく `### 他のスキル・機構との整合`（規定文言。1 書に 1 節まで）に置き、受け入れ基準の最後に置く

### 自由記述と定型の切り分け

| 章・節 | 書き方 | 分量の目安 |
|---|---|---|
| 概要（導入・背景・目的） | 自由記述 | 3 か所の合計で 600 字以内 |
| 概要（スコープ） | 定型（箇条書き。「含まない」に担い先を添える） | 「含む」「含まない」各 5 項目以内 |
| ユーザーストーリー | 定型（As a / I want / So that の 3 文） | 3 文 |
| 受け入れ基準（メインフロー） | 定型（図 1 つ + EARS 箇条書き） | 図は 15 ノード以内 |
| 受け入れ基準（代替 / 例外） | 定型（識別子付きの EARS 箇条書き） | 上限なし |
| 受け入れ基準（規約節 / 整合） | 定型（EARS 箇条書き） | 規約節は 3 節以内、整合は 1 節以内 |
| 前提条件 | 定型（箇条書き） | 5 項目以内 |
| 制約条件 | 定型（技術的 / ビジネス的 / 外部的のラベル付き箇条書き） | 各ラベル 1 項目 |
| 依存関係 | 定型（箇条書き） | 5 項目以内 |
| 非機能要件 | 定型（表） | 3〜6 行 |

目安を超える必要が生じたら、目安を無視せず、対象の分割か仕様書への移動を呼び出し元に提案する。

### 代替・例外フローの識別子

- 各項目の先頭に `**[A1]**` / `**[E1]**` を置く。番号は節の中の出現順で 1 から振る
- 図の離脱先の参照ノードの ID と一致させる。図に離脱点が無い項目にも識別子は付ける（節の中の位置が変わっても参照が壊れないため）
- 識別子は書の中でだけ一意であればよい（書をまたいで一意にしない）

### セルフレビュー項目

全件を確認して、未充足があれば直してから返す。

| # | 見るところ |
|---|---|
| 1 | 章順がテンプレートどおりで、章の見出しの文言が変わっていない |
| 2 | 受け入れ基準の節順が メイン → 代替 → 例外 → 規約節 → 整合 になっている |
| 3 | 禁止節（関連するドキュメント / レビュー記録 / 変更履歴）が無い |
| 4 | EARS の形式（When 〜 Shall / If 〜 Then / Shall not）から外れた項目が無い |
| 5 | プレースホルダ（`{{ }}`）とテンプレートのガイドコメントが残っていない |
| 6 | メインフロー節の先頭に図があり、1 図のノード数が 15 以下 |
| 7 | 図のソースが 1 行 1 辺で、ノードのラベルが日本語の動作・判定になっている |
| 8 | 図の離脱先の識別子が、代替・例外フローの項目の識別子と過不足なく一致している |
| 9 | 図にあって EARS 箇条書きに無い条件・分岐が無い |
| 10 | 分割した場合、各節の図が次の節へ渡る参照ノードで繋がっている（最後の節を除く） |
| 11 | 規約節の見出しが `規約: ` で始まり、3 節以内 |
| 12 | 自由記述が 概要の導入・背景・目的 の 3 か所だけで、その合計が 600 字以内 |
| 13 | 判定基準を当てて節が一意に決まらない記述を残していない |

## OUT ひな形

`assets/requirements.template.md`: frontmatter と全章の骨格（各章に書き方の 1 行ガイドをコメントで持ち、記入時に消す）。プレースホルダは `{{名前}}` 形式。メインフロー節には mermaid の記入例を骨格として持ち、書き手はノードのラベルと辺を差し替えるだけで型に沿う。

## 参照ナレッジ

- 章立て・書き方の詳細な規約: `rules/`（設計文書ルール。`design-docs`・`ai-asset-design-docs`）
- 対になる仕様書の書き方: `20-common-step-spec`
- DDR の形式: 既存の `20_ddr/` の書（形式の手本）

## Script 処理

なし。章立て・節順・禁止節・ノード数・識別子の対応の機械検査は将来の設計文書検査（ルールの機械検査）に統合する想定で、それまでは処理フロー 12 のセルフレビューが担う。

### テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| RQ-E01 | 新しいアセットの要件定義書の作成依頼 | 決定済みフォーマット（章立て・節順）に従い、外部的な振る舞いだけを書き、内部構造（スクリプト名・判定順）を書かない | 章立ての一致、内部構造の語が無いこと |
| RQ-E02 | 既存の要件定義書の更新依頼（振る舞いの変更） | 現在の正史として書き換え、履歴・経緯は書かず DDR に回す | 変更履歴の節が無いこと、DDR の有無 |
| RQ-E03 | 1:1:1 を崩す依頼（2 アセットを 1 文書に） | 崩さず 1 アセット 1 文書にするか、理由を返す | 文書の分割 |
| RQ-E04 | メインフローが 25 項目になる対象の要件定義書の作成依頼 | 1 図に詰め込まず、一区切りで分割して節ごとに図を置き、節どうしを参照ノードで繋ぐ | 1 図のノード数が 15 以下、`メインフロー: ` の節が 2 つ以上、参照ノードの存在 |
| RQ-E05 | 「未コミットの変更があると拒否する」振る舞いを代替フローに書くよう指示 | 判定順を当てて起点が前提の不充足であることを示し、例外フローに置く。指示のまま代替に置かない | 該当項目が例外フロー節にあること |
| RQ-E06 | 成果物の中身の規定を独自の見出しで節にするよう指示 | `規約: <対象>` の命名規則に直し、3 節を超えるなら分割を提案する | 見出しが `規約: ` で始まること、節数が 3 以内 |
| RQ-E07 | 背景の説明を 2,000 字で書くよう指示 | 目安（導入・背景・目的の合計 600 字以内）を示し、超える分を仕様書か DDR へ回す提案を返す | 自由記述部の字数、提案の有無 |

| メイン: 規約節の命名規則と 3 節の上限、フローを置かない | 処理フロー 7、規約節の命名と上限、禁止事項 |
| メイン: 自由記述は 3 か所だけ、分量の目安がある | 処理フロー 8、自由記述と定型の切り分け |
| メイン: 外部視点・内部構造は仕様へ | 処理フロー 9、禁止事項 |
| メイン: 正史のみ・経緯は DDR へ | 処理フロー 10、禁止事項 |
| メイン: 更新は正史の書き換え・履歴を残さない | 処理フロー 11、禁止事項 |
| 代替 A1: 横断的な要件は 1 つに寄せて参照 | 処理フロー 1、禁止事項（重複） |
