# issue の受け入れ条件との対応を要件定義書の概要章の小節に置く

## 背景

`20-common-step-spec` は「仕様書の『要件との対応』表の行数が、要件の受け入れ基準の数と一致すること」を検査する。これは要件 → 仕様の段だけを見る検査で、issue → 要件の段の欠落は検出できない。

issue #13 で実際にこれが起きた。設計計画が「issue の受け入れ条件 9 と 10 は整合フローで扱う」と約束していたのに、書かれた要件定義書は別の 3 項目に置き換わっており、受け入れ基準が 19 件（本来 26 件）だった。仕様書の対応表は 19 行で「一致」したため検査を通り、敵対的レビューで初めて見つかった。

要件定義書に「issue の受け入れ条件との対応」表を持たせれば、同じ形の検査で issue → 要件の段も見られる。問題は、その表をどこに置くか。

## 決定

- 対応表は、要件定義書の**概要章の中の小節**「issue の受け入れ条件との対応」に置く
- 表は起点の issue の受け入れ条件を全件、左列に原文（または要約と番号）、右列に満たす受け入れ基準の識別子または節名を書く
- 起点の issue が無い場合は「起点の issue なし」と 1 行書く
- `20-common-step-requirement` のセルフレビューに 14 項目目「対応表の行数が起点の issue の受け入れ条件の数と一致する」を足す
- 既存の要件定義書への遡及適用は求めない。新規作成と更新のときに追加する

## 理由

- **章順の規定に触らずに済む**: `ai-asset-design-docs`（および今回 `design-docs` にも足した）「要件書の形」は章順を 概要 → ユーザーストーリー → 受け入れ基準 → 前提条件 → 制約条件 → 依存関係 → 非機能要件 の 7 章に固定している。8 章目を足すと、この規定を両ルールで変えることになる
- **自由記述の分量制限に抵触しない**: 制限がかかるのは「自由記述（散文）」で、表は定型側。概要章に表を置いても 600 字の目安には数えない
- **起点の issue は概要の情報である**: 「なぜこの要件が要るか」は概要章の背景が担っており、その根拠となる issue の条件を同じ章に置くのは読み手の動線に合う

## 却下した案

- **8 章目「issue の受け入れ条件との対応」として追加する**: 表としては目立つが、両ルールの章順の規定を変える必要がある。章順の規定は #17 で入ったばかりで、既存の要件定義書 46 件（`.claude/docs/00_requirement/` 45 + アプリ 1）が一斉に「章が足りない」状態になる。なお既存文書が新しい記載を持たない点は概要章の小節でも同じで、両案の差は「規定の変更要否」にある
- **設計計画書（`wip/20_plans/`）に置く**: 計画書はブランチ限りの文書で、マージ後に残らない。issue #20 の受け入れ条件「要件定義書のテンプレートに書く場所があり」を満たさない
- **仕様書の「要件との対応」表を 3 列にして issue の条件も入れる**: 要件書を経由せず issue と仕様を直結させることになり、要件書が薄いまま通ってしまう問題を解けない

## 影響

- `20-common-step-requirement` の要件書・仕様書・テンプレート `assets/requirements.template.md` が変わる（テンプレートの変更は AI アセット実装フェーズ）
- セルフレビュー項目が 13 → 14 になる
- `20-common-step-requirement` の処理フローに 2 手順（設計文書ルートの決定・issue の受け入れ条件との対応）が入り、セルフレビューの手順番号が **12 → 14** になる。これを名指ししている `.claude/rules/design-docs.md`（「テスト・機械的検査」）、`.claude/rules/ai-asset-design-docs.md`（同）、`.claude/skills/20-common-step-requirement/SKILL.md`（処理フロー 12 と「13 項目」）を AI アセット実装フェーズで合わせる
- 既存 46 件の要件定義書は小節を持たないまま残る。一括で入れるかは issue #8（要件定義書の標準化）に委ねる
