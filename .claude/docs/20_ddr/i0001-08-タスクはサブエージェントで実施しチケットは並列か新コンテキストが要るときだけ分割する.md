# i0001-08. タスクはサブエージェントで実施し、チケットは並列か新コンテキストが要るときだけ分割する

## 背景

参考実装はどちらもメインセッションが全タスクを直列に実施する。1 issue の作業が長くなるとコンテキストが compact され、現在地や手順の理解が失われる問題に対し、両実装とも SessionStart フックでの再注入で対処していた。一方、Claude Code のサブエージェントは独立したコンテキストで動き、モデルを指定でき、並列に起動できる。

## 決定

- **全体計画・フィードバック計画・全体まとめ以外のタスクはサブエージェントで実施する。** メインセッション（`00-workflow-issue-mr-driven`）はタスクの起動・結果報告の受け取り・タスクの切れ目の処理（push・MR 本文更新・レビュー依頼・完了確認）に徹する。タスクを担当するサブエージェントのモデルは全体計画で合意する
- **全体計画（issue の確定・ブランチと MR の作成を含む）・フィードバック計画・全体まとめの 3 つはメインエージェントが行う。** 承認・対話が多く挟まり、サブエージェントはユーザーと対話できないため。整理はこの 1 つだけで、どのタスクも同じ task スキルを読み込んで実施し、違いは誰が実行するかだけ
- **チケットは既定ではタスクのサブエージェントの中で順に実施する。** チケット単位でさらにサブエージェントに分割するのは、(1) 互いに依存しないチケット群を並列に進めたいとき、(2) 新しいコンテキストで実施したいとき（チケットの実行者がタスクのモデルと異なるときを含む）に限る
- サブエージェントは入れ子で起動できない前提とし、チケット単位のサブエージェントはタスクからの要求に応じてメインセッションが起動する
- 宣言した範囲の強制（フック）はサブエージェントの中でも同じように働く

## 理由

- タスクごとにコンテキストが切れるため、1 つのタスクの中で compact が起きにくく、タスクの手順とチケットの内容だけを持った状態で作業できる
- メインセッションのコンテキストにはタスクの結果報告だけが積まれるので、長い issue でもオーケストレータの現在地が失われにくい
- チケットを常にサブエージェントにすると、1 枚ごとに文脈の受け渡しコストがかかり、直前のチケットの学びが次に引き継がれない。既定はタスク内で順に実施し、分割は利点がある場合に限る
- 実行モデルの指定（i0001-07）は、サブエージェントのモデル指定で自然に実現できる

## 却下した案

- **メインセッションがすべて直列に実施する（参考実装方式）**: 実装が単純で文脈の受け渡しが不要だが、長い issue で compact に依存し、モデルの使い分けができない
- **チケットを常にサブエージェントで実施する**: 並列性と隔離が最大になるが、チケット間の文脈が毎回失われ、小さなチケットほどオーバーヘッドが支配的になる
- **タスクのサブエージェントがチケットのサブエージェントを入れ子で起動する**: 構造が素直だが、Claude Code のサブエージェントは入れ子起動できない前提のため採れない
- **全体まとめはサブエージェントで行い、承認が要る操作（衝突解消・issue へのコメント）だけメインエージェントに戻す**: 全体まとめは衝突解消・issue コメント・draft 解除と承認が続けて挟まり、戻すたびに文脈を受け渡すことになる。丸ごとメインエージェントで行うほうが単純で、担当の整理も「3 つはメイン、他はサブ」の 1 つで済む

## 影響

- 要件定義書 B 節・前提条件、`00-workflow-issue-mr-driven.md` の整合節
- task スキルはメインエージェント・サブエージェントのどちらからも読み込まれる前提で、入力（チケット・計画・issue の受け入れ条件）と出力（結果報告）を明確に持つ必要がある。サブエージェントが担当する task スキルはユーザーへの質問を含めない
- タスクからメインセッションへ「このチケット群は並列で」「このチケットは別モデルで」と要求する形式を仕様で定める

## 未決定事項

- タスクのサブエージェントの中で提供コマンド（チケットの着手・完了）を実行するのか、メインセッションが代行するのかは仕様で決める
