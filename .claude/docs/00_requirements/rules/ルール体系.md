# ルール体系（`.claude/rules/`）

## 概要

`.claude/rules/` 配下のルール全体の構成の要件を定義する。ルールは 2 つの目的に仕える。

1. **実装・テスト時**: あるファイルを書くとき、そのファイル種別に効くルールを機械的に集めれば、守るべきルールが全部揃う（ルールを探して回らない）
2. **レビュー時**: 観点別のレビューエージェント（例: セキュリティ）が、対象ファイル群に効く各ルールの該当観点の章だけを抜き出し、ファイルを横並びでチェックできる

- **背景**: 参考実装は「rules = 知識の正」と「REVIEW-POINTS = ディレクトリごとのチェックリスト」の二本立てで、二重管理を避ける注記を手で保守していた。本機構は観点表の層を設けず、レビュー観点を成果物ルールの章に一本化する。
- **目的**: 実装とレビューが同じ文書を見る状態を作り、規約の正を 1 箇所に保つ。
- **スコープ**:
  - 含む: ルールの 2 分類、成果物ルールの章スキーマ、適用範囲の宣言と収集・抽出の可能性、ルールの一覧と各ルールへ取り込む内容、参考実装からの取り込み時の要件
  - 含まない: 収集・抽出の実現方法（仕様書が定める）、各ルール本文の作成（AI アセット実装フェーズ）、観点別レビューエージェントの定義（エージェントの要件書）
- **文書の構成**: ルール全体の一覧と取り込み内容は本書が正とする。中身の設計判断が要る新設ルール（`work-defaults`・`design-docs`・`ai-asset-design-docs`）だけ個別の要件書を持ち、参考実装からの移植が主のルールは本書の一覧表を要件とする。

---

## ユーザーストーリー

**[As a]** ファイルを実装する AI として、

**[I want]** これから書くファイルに効くルールを機械的に全部集めてから書き始めたい。

**[So that]** 規約を知らずに書いて手戻りしたり、散らばったルールを探して回ったりしないため。

**[As a]** 観点別のレビューエージェントとして、

**[I want]** 担当観点の章だけを、対象ファイルに効く全ルールから抽出して受け取りたい。

**[So that]** 他観点のノイズなしに、同じ観点で複数ファイルを横並びに照合できるため。

**[As a]** 機構の保守者として、

**[I want]** 規約とレビューチェックリストを別々に保守したくない。

**[So that]** 片方だけ直して食い違う事故と、重複回避の注記の保守をなくすため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI がファイルを作成・変更するとき、Shall そのファイルのパスに適用範囲がマッチするルールを機械的に収集でき、その種別のファイルを書くために守るべきルールがその結果で全部揃わなければならない。
- When 観点別のレビューエージェントがレビューするとき、Shall 対象ファイル群にマッチする成果物ルールから指定した観点の章だけを機械的に抽出して入力にでき、抽出結果に他の観点の内容が混ざってはならない。
- When ルールが適用範囲を宣言するとき、Shall frontmatter の `paths`（グロブ）で宣言し、収集・抽出の対象は `paths` のマッチで決まらなければならない（本文の散文だけに依存しない）。行動ルールで `paths` に馴染まないもの（操作の種類で効くもの）は、効くタイミングを frontmatter で宣言する。
- When 同じファイルに複数のルールがマッチするとき、Shall すべてのルールが適用され、規定が重なる場合の正は 1 つのルールに決まっていて、他のルールはそれを再掲してはならない。適用範囲が交わらないルール同士（例: `design-docs` と `ai-asset-design-docs`）が同種の規定をそれぞれ持つことは重複としないが、内容を食い違わせてはならない。

### 代替フロー

- If プロジェクト固有のルールを追加したい場合、Then 本書の 2 分類・章スキーマ・frontmatter に従って 1 ファイル追加すれば、収集・抽出に自動で乗らなければならない。

### 例外フロー

- If 章スキーマ・frontmatter に従わない成果物ルールが持ち込まれた場合、Then 機械的検査でそれを検出できなければならない（検査の実現は仕様書が定める）。
- If あるファイルにどのルールもマッチしない場合、Then 収集は空の結果を返し、エラーにしてはならない。

### ルールの分類

- When ルールを置くとき、Shall 各ルールは次のどちらかに分類されなければならない。
  - **成果物ルール**: リポジトリに残りレビュー対象になる成果物の書き方。章スキーマに従い、観点別抽出の対象になる
  - **行動ルール**: 作業の進め方・その場限りの操作の規約。章スキーマの対象外で、観点別抽出の対象にならない
- When レビュー観点を追加・変更したいとき、Shall 該当する成果物ルールの観点章を編集すれば足り、別のチェックリスト文書（ディレクトリごとの観点表など）を保守してはならない。

### 成果物ルールの章スキーマ

- When 成果物ルールを書くとき、Shall 次の 7 章を固定の見出し文言・固定の順で持たなければならない: **適用範囲 / 構造・配置 / 書式・可読性 / セキュリティ / 堅牢性 / パフォーマンス / テスト・機械的検査**。
- When ある章に定めるルールが無いとき、Shall 見出しを残して「該当なし」と根拠を 1 行書き、章を削除してはならない（「ルールが無い」と「書き忘れ」を観点別レビューエージェントが区別できるようにする）。
- When 実際に踏んだ罠を記録するとき、Shall 該当する観点の章の中に出所（issue 番号）付きで書き、罠専用の章に隔離してはならない（観点章の純度が横並びレビューの成立条件）。
- When ルールの書き手が章スキーマを参照するとき、Shall 書き手向けの正典は `ai-asset-authoring` ルールが持ち、本書の定義と一致していなければならない。

### 参考実装からの取り込み時の要件

- When 参考実装のルールを取り込むとき、Shall 参考実装固有の記述（flow-id、HANDOFF、`.gemini/`、配布層、参考実装の issue 番号への言及）が削除または本機構の用語へ置き換えられていなければならない。
- When 参考実装の PowerShell 文字コードルールを検討するとき、Shall 取り込んではならない（本機構のスクリプトは bash に統一する。`.ps1` を導入するときに改めてルールを起こす）。
- When 参考実装の REVIEW-POINTS（ディレクトリごとのレビュー観点表）を検討するとき、Shall その層を設けず、観点は成果物ルールの観点章として取り込まなければならない。

## 前提条件

- `.claude/rules/` は Claude Code がルールとして読み込む置き場であること
- ルールの収集・抽出の実現方法（スクリプト・索引）は仕様書が定め、本書は「機械的にできること」までを要求する
- ルール本文の作成は AI アセット実装フェーズで行う（本書と個別要件書のレビュー後）
- 観点別のレビューエージェントは別途エージェントの要件書で定義される

---

## 制約条件

- **技術的制約**: 常時読み込まれるルールはコンテキストを消費するため、常時適用は行動ルールの一部（`agent-common`・`directory-structure`）に限る。他は効くタイミングでの参照・収集を前提とする
- **ビジネス的制約**: ルールの中身の妥当性は MR 上の人間レビューが判断する
- **外部的制約**: 参考ディレクトリは git 管理外の参照用であり、取り込み後は本機構のルールが正になる

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | 7 章の見出し文言は全成果物ルールで同一で、機械的に照合できる |
| 簡潔性 | 同じファイルにマッチするルール間では規定を重複させない（適用範囲が交わらないルールが同種の規定を持つのは可）。罠は出所付きの実例で書き、一般論で水増ししない |
| 保守性 | ルールの追加・変更が 1 ファイルの編集で閉じ、収集・抽出側の変更を要しない |
| 可読性 | ルールは日本語で書く |
