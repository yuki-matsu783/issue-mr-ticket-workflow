# i0009-09. session-start の boundary.sh 依存テストを 3/3 へ送り、この issue では 2 本の半分だけを実施する

## 背景

`session-start` は現在地の判定を丸ごと `boundary.sh status --offline` に委ね、スクリプトが無ければ「何も出さずに終了 0」する（仕様 制御方式 3）。`boundary.sh` は issue #9 のスコープ外（3/3 で実装）。

調査 0005 f5 の内訳: 影響するのは SE-T01〜04・06〜08 の 7 本と SE-T05 の前半。SE-T09（CLI の有無で出力が変わらない）は**両方とも無出力になるため、スタブ無しでは空同士の比較で無意味に通る**。純粋に独立なのは SE-T05 の後半（`jq` 不在で無出力）だけ。

0012 は同じ構造の WE-T10 を 3/3 に送ると決めている（DDR i0009-04）。

## 決定

- **SE-T01〜04・T07・T08・T09 と SE-T05 の前半・SE-T06 の前半は 3/3 に送る**
- **この issue で実施するのは SE-T05 の後半（`jq` 不在で無出力・終了 0）と SE-T06 の後半（サブエージェントの開始では無出力）だけ**
- 仕様のテスト観点の表に「この issue で実施するか」の列を足し、行ごとに理由を書く
- issue #9 の受け入れ条件 1 の「テストが通る」は、**この issue で実装するフックのテスト**を指すと解釈する（i0009-04 と同じ）

## 理由

- SE-T08 は「`boundary.sh` と同じ position を伝えるか」が観点で、偽実装で代えると「偽実装と一致するか」に変わって観点が失われる
- SE-T09 は `boundary.sh` が無いと両方とも無出力になり、通っても何も保証しない（0005 f5）。無意味に通るテストを「通った」と数える方が受け入れ条件の判定を濁す
- SE-T07（8 KB 超）は、注入テキストそのものが `boundary.sh` の出力から組み立てられるため、8 KB のテキストを作る材料が無い
- 最小スタブを作る案は、忠実度をどこまで上げるかという新しい判断を生み、3/3 で本物を書くときに捨てる作業になる（i0009-04 と同じ理由）

## 却下した案

- **`boundary.sh` の最小スタブを `wip/tmp/` に置く**: 通っても「本物と一致する」証拠にならない。SE-T08 は原理的に代替できない
- **9 本すべてを 3/3 に送る**: SE-T05 の後半と SE-T06 の後半は `boundary.sh` に依らないので、この issue で通せるものまで送ることになる
- **`boundary.sh` をこの issue で実装する**: issue #9 のスコープ外と明記されている

## 影響

- `10_spec/hooks/00-SessionStart/session-start.md` テスト観点の表（実施可否の列）
- issue #9 の受け入れ条件 1 の解釈（結果報告と全体まとめに明記する）
- **0016 へ**: 実装フェーズのテスト計画で、`session-start` の実施本数は 9 本ではなく「2 本の半分」であることを前提にする
