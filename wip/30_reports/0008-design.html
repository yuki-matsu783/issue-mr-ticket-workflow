実施した内容と結果

  1. 1

    受け入れ基準の構成 ◎良 根拠: docs/00_requirement/vscode-ticket-board.md

    issue #13 の受け入れ条件 10 件を EARS（When 〜 Shall / If 〜 Then / Shall not）に展開した。メインフロー 7 件が表示・カード・件数・ファイルを開く・自動更新・更新コマンド・単一パネル、代替フロー 5 件が 0 件表示・空の列・見出し欠落・未表示での更新・再表示、例外フロー 9 件が解析失敗・未知の種類・番号の食い違い・対象なし・対象の消失・開けないファイル・1 枚の失敗・不一致パス・書き込み禁止、整合 5 件が状態の判定・対象ファイルの選別・frontmatter の解釈範囲・単体テスト・README にあたる。

    根拠を見る（実行コマンドと出力） 
    メイン 7 + 代替 5 + 例外 9 + 整合 5 = 26 件
仕様書「要件との対応」の行数 = 26 行

    結論

    受け入れ基準 26 件と仕様書の対応表 26 行が 1 対 1 で対応する。

  2. 2

    層の分離 ◎良 根拠: 調査 0004 章 3 / 仕様書「モジュール構成」

    調査 0004 が「vscode は拡張ホストの外で解決できない」と確定させたため、core/ は vscode を import しないという禁止事項を仕様に置き、単体テストの対象を core/ に限った。テスト観点 TB-T01〜TB-T17 はすべて core/ に対するもので、拡張ホスト層は README の手動確認に委ねた。

    根拠を見る（実行コマンドと出力） 
    仕様書 禁止事項: 「core/ 配下から vscode を import すること（単体テストが不可能になる）」

    結論

    自動テストできる範囲と人間の確認に委ねる範囲を、層の境界と一致させた。

  3. 3

    不備の識別子 ◎良 根拠: 仕様書「不備の識別子とメッセージ」

    機構の識別子台帳（フック共通仕様 §6）は AI アセット用でアプリの識別子を載せられないため、仕様書が台帳を兼ねる形にした。TB001（frontmatter を読めない）から TB007（ファイルを読めない）までの 7 種と、カードに出す文言の型を定めた。

    根拠を見る（実行コマンドと出力） 
    TB001 frontmatter / TB002 必須項目の欠落 / TB003 真偽値でない / TB004 未知の種類 /
TB005 見出しが無い / TB006 番号の食い違い / TB007 読み取り失敗

    結論

    アプリの識別子の置き場が機構に無いという穴を、仕様書で埋めた（候補 B3-3）。

  4. 4

    敵対的レビューと 0014 での修正 △注意 根拠: チケット 0014 の作業ログ

    設計の敵対的レビューが 20 件を挙げ、うち次の 4 件を 0014 で直した。とくに 1 件目は issue の受け入れ条件の取りこぼしで、設計計画が整合フローで扱うと約束していたものだった。

    指摘修正
    要件が issue の受け入れ条件 9 と 10 を落としている受け入れ基準を 19 → 26 件に増やした
    完了条件が「10 件すべて覆った」と偽っていたチケットの根拠欄を実態に直した
    仕様書が renderMissingWorkspace を宣言しつつ「提供しない」と書いている両方を削除した
    frontmatter の処理フロー 4 が、フロー配列とインラインマップの外側の記号を剥がす手順を落としている「先頭と末尾を先に取り除いてから」を明記した
    根拠を見る（実行コマンドと出力） 
    剥がし忘れを直さないまま実装していれば、実在のチケットすべてに TB002 が付いた

    結論

    設計の敵対的レビューが、実装前に致命的な取りこぼし 2 件を止めた。

設計への反映

  1. core/ から vscode を import しないことを、実装後に grep で機械的に確かめる
  2. out/ と node_modules/ は入れ子の .gitignore で除外する（調査 0005）
  3. テスト ID は TB-T01〜TB-T17 の 17 件。拡張ホスト層は README の手動確認に落とす
  4. frontmatter パーサの処理フローは 6 手順の順序が意味を持つ。手順 4 の記号の剥がしと手順 6 の引用符の扱いを取り違えると、実在のチケットが全滅する

想定と異なった点

計画時の見込み実際どう扱ったか
issue の受け入れ条件 10 件は素直に EARS へ写せる「1 枚の失敗で他を止めない」「表示中のいずれとも一致しないファイルを開かない」は複数のフローに分かれる例外フローを 9 件に増やし、要件との対応表で 1 対 1 に保った
仕様書の節構成は機構の型に従えばよい20-common-step-spec はスキル / エージェント / フックの 3 種しか型を持たない節構成をこの issue で決め、DDR i0013-02 に残した（候補 B3-1）
識別子は機構の台帳に登録する台帳は AI アセット専用仕様書が台帳を兼ねる形にした（候補 B3-3）

残課題

  • 要件定義書に「issue の受け入れ条件との対応」を書く場所が無く、issue → 要件の段の欠落を機械的に検出できない（候補 B3-4）
  • docs/ 配下の設計文書に対する機械的検査が未整備で、仕様書の自己矛盾はレビューでしか見つからない（候補 B3-5）
  • 単一ルート（workspaceFolders[0]）だけを見る制約を「仕様に明記する」と決めたが、仕様書に書き漏らした（候補 F14）
  • DoD のチェック進捗をカードに出すかの決定を記録し忘れた（候補 F16）
