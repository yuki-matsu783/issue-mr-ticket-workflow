# i0009-68. ホットパスの文字列処理はパターン照合を使わず位置ベースで書く

## 背景

`__hc_redact_to_reply`（記録に落とす前の伏字化）が 4000 文字の入力で **58 秒**かかった。フックはツール呼び出しごとに 5 本並列で走るので、この形が残っていたら機構は実用にならなかった。

規則ごとに計測したところ、正規表現を使う 4 規則はいずれも 70ms 程度で、犯人は規則 5 の

```bash
pre="${s%%"$m"*}"
```

だった。bash の `${s%%パターン*}` は `$m` が長いリテラル（ここでは 4000 文字）になると壊滅的に遅くなる。単体で 58442ms。位置ベースの O(n) ループに書き直して **101ms** になった（約 580 倍）。

同じ性質のものが `__hc_cap_json_field` にもあった。1 文字ずつ読むループが O(n^2) になっており、パラメータ展開だけの O(n) に書き直した。

## 決定

- **ホットパス（§1 の 5 本が通る経路）の文字列処理は、入力長に比例する時間で終わる形で書く**。具体的には
  - 長いリテラル（入力に由来する文字列）を `${s%%"$m"*}` / `${s##*"$m"}` のパターン位置に置かない。一致位置は位置ベースの走査で求める
  - 1 文字ずつ読むループ（`${s:i:1}` の繰り返し）を書かない
- **性能の根拠は規則ごとに測ってから書く**。全体の遅さから犯人を推測しない
- ホットパスの実行時間は 1 本あたり 1 秒以内を目安とし、登録後に実測で確かめる（0031 の実測では 5 本とも 323〜642ms）
- 性能を測るときは**他の重い処理を止めた状態で測る**

## 理由

- **bash のパターン照合の costs は入力長 × パターン長に効く**。パターンが定数なら気にならないが、伏字化の対象は「入力に現れた文字列」なので入力と同じ長さまで伸びる。設計時に「パターンは短い」という暗黙の前提が入っていた
- **1 回 58 秒は機構が止まるのと同じ**。フックはツール呼び出しのたびに走るので、遅さは機能の欠如と等価になる
- **測ってから直す**が実際に効いた。当初は正規表現の 4 規則を疑っていたが、規則ごとの計測で犯人が 5 番目だと分かった。推測で直していたら 70ms の側を最適化して終わっていた
- **代替が難しくない**。位置ベースの走査は素の bash で書け、外部プロセスを増やさない（`i0009-22` の fork 上限と両立する）
- **測定環境の統制も規約に含める**必要がある。0031 では「フック 1 回 = 約 1.9 秒」「`test_workflow_guard` は 5 分 07 秒」という誤った値を記録しており、いずれも全件テストを 2 本同時に走らせている最中の測定だった（静かな状態では 642ms と 1 分 47 秒）

## 却下した案

- **伏字化を `sed` / `perl` に出す**: 1 回のフック実行で fork が増える。`i0009-22`（ホットパスから外部プロセスを呼ばない）に反し、5 本並列ぶん効く
- **入力を先に切り詰めてからパターン照合する**: 切り詰めの位置が伏字の途中に来ると秘密の断片が残る。切り詰めは伏字化の**後**（`hc_append_jsonl` の 4 KB）でなければならない
- **長い入力のときだけ伏字化を諦める**: 長い入力ほど秘密が混ざる確率が高い。諦める側が逆
- **性能の上限をテストで固定する（時間ベースの assertion）**: 実行環境と負荷で揺れ、上記のとおり同じマシンでも 3 倍違う値が出る。書き方の規約として持つほうが安定して守れる
