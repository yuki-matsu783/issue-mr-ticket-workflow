# 10-task-feedback-plan スキル 仕様

## 概要・禁止事項

フィードバック計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-feedback-plan.md](../../00_requirement/skills/10-task-feedback-plan.md)。

主作業の後に 1 issue につき 1 回だけ実施し、記録からの洗い出し → 分類 → 対話での対応先の合意 → 後続チケットの確定までを行う。

禁止事項:

- サブエージェントへの委譲（対応先の決定に対話が要る。メインエージェント専任）
- 記憶に頼った洗い出し（入力は記録のみ。全チケットの作業ログの固定見出しを機械的になぞる）
- 対応先の確定前の後続チケット作成（確定は対話での合意、またはヘッドレスでの既定どおりの決定。処理フロー 4）
- 承認を得ない別 issue の起票（ヘッドレスでは起票そのものを行わない）
- 独自の分類（観点・類型は機構の定義と一致させる）
- 改善の実施（`.claude/` 配下・ソースコード・設計文書への書き込み。後続フェーズが行う）
- 振り返りのやり直し（フィードバック計画より後の候補は全体まとめの別 issue 起票へ）

## 呼出条件

- `00-workflow-issue-mr-driven` の `next` がフィードバック計画チケットを示したとき、メインエージェントが読み込む（主作業フェーズの切れ目の処理が済んだ後）

## IN / OUT

| IN | OUT |
|----|----|
| この issue の全チケットの作業ログ（`wip/10_tickets/20_done/`・`30_cancelled/`）、MR のレビュー指摘、各レポートの「想定と異なった点」「残課題」、使った AI アセットの一覧 | フィードバック計画書（md + HTML）、起票された別 issue（あれば）、後続フェーズの最初の計画チケットまたは全体まとめチケット（未着手）、見直された未着手チケット、完了済みフィードバック計画チケット |

候補一覧の 1 行（フィードバック計画書の表）:

| # | 候補 | 出どころ | 観点 | 類型 | いつ効くか | 守らせ方 | 対応先 |
|---|------|---------|------|------|-----------|---------|--------|
| 3 | 除外リストに `.tfvars` が無い | チケット 0007 作業ログ「スコープ外で見つけたこと」 | 足りなかった | (c) 罠が書かれていない | 操作のたび | 機械的に拒否 | この MR |

## 処理フロー

1. **着手**: `ticket.sh start` でフィードバック計画チケットに着手する
2. **洗い出し**: 完了・取り消し済みの全チケットの作業ログを、固定見出し（一覧の正は `00_requirement/skills/20-common-step-ticket.md`。全項目を対象にする）の順に**チケット番号順で機械的になぞり**、MR のレビュー指摘（`gh api --paginate` / `glab api --paginate` で全件取得）と各レポートの「想定と異なった点」「残課題」を加えて候補を列挙する。確認した記録の範囲（チケット番号・レポート名）を計画書に書く
3. **分類**: 候補ごとに観点（足りなかった / 邪魔だった / 無かった / 問題なし）と類型（(a) 無かった / (b) 誤っていた / (c) 罠が書かれていなかった / (d) 辿り着けなかった）を付け、反映先を「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）× 守らせ方（読ませる / 手順化する / 機械的に拒否する）」の 2 軸で選ぶ。常時読込を増やす提案にはコストの注記を付ける
4. **合意**: 候補の一覧・分類・提案（既定「この MR で対応」。大きすぎるものだけ「別 issue」）を提示し、候補ごとの対応先（この MR / 別 issue / 対応しない + 理由）を対話で合意する。**ヘッドレス実行では止まらず、既定の提案どおりに対応先を決めて後続の起票（手順 6）まで行い、決めた内容を `boundary.sh note` で MR に記録する**（チケットは完了させる）。ユーザーが応答できない実行形態でも、フィードバック計画の目的（次に何をするかを確定させる）は既定の提案だけで達成できるためで、止めると後続フェーズが 1 つも起票されないまま issue が宙に浮く。記録に残るので、人間は MR のコメントを読んで後から差し戻せる
   - ただし**別 issue の起票（手順 5）だけはヘッドレスでも行わない**。取り消せない外部への副作用であり、既定で進めてよいものではない。「別 issue」と判断した候補は起票せず、候補の内容と理由を計画書と `note` に書いて残す
   - この扱いは `10-task-overall-summary` の別 issue 起票（承認が取れなければ起票せず候補を残して進む）と同じ形である
5. **別 issue の起票**: 合意された候補は本文案の承認を得て `20-common-step-issue` で起票し、番号を計画書に記録する。承認されなかった候補は「この MR に戻す / 対応しない（理由）」を確認する
6. **後続の確定**: 後続フェーズ（設計反映 / AI アセット設計 / AI アセット実装・テスト）の要否を確定し、含める最初の計画チケット（無ければ全体まとめチケット）を `ticket.sh create` で 1 枚未着手に作る。記載事項は全体計画の方針と work-defaults に従う
7. **未着手チケットの見直し**: 振り返りの結果に応じて未着手チケットの範囲・実行者・レビュー要否・DoD を見直し、変更をユーザーに伝える
8. **計画書**: `wip/20_plans/` にテンプレートから md を書き、`20-common-step-report-view` の手順で HTML を作って検査する
9. **完了**: 作業ログを整えて `ticket.sh complete` で完了し、呼び出し元に制御を戻す

- 候補 0 件: 0 件の根拠（確認した記録の範囲）を計画書に書き、6 へ進む
- 再開: 作業ログ「現在地」から続け、済んだ合意をやり直さない。起票済み issue を二重に作らない
- 差し戻し: レビューの差し戻しで同じ種類の追加チケットとして戻った場合は、候補の一覧と後続チケットを見直し、変更を対話で合意し直す（完了済みチケットは戻さない）

## OUT ひな形

`assets/feedback-plan.template.md`（+ 計画書用 HTML テンプレートは report-view のものを使う）:

| 節 | 内容 |
|----|------|

## 参照ナレッジ

- 観点・類型の文言の正: 機構の定義（`00-workflow-quick-request` の振り返りと同一文言）
- 作業ログの固定見出し: `00_requirement/skills/20-common-step-ticket.md`（正）
- レビュー指摘の全件取得: `10_spec/skills/20-common-step-issue.md`「GitLab の長文送信」の `--paginate` の注記
- 後続チケットの記載事項・DoD の型: 各フェーズの task スキルの要件

## Script 処理

なし。チケット・issue・HTML の操作は common-step の提供コマンド・手順に委譲する。

## テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| FBP-E01 | 完了したチケットが 12 枚ある状態 | 全チケットの作業ログの固定見出しを機械的になぞって候補を洗い出す。記憶から書かない | 候補ごとの出どころ（チケット番号と見出し）の記載 |
| FBP-E02 | 候補が 0 件だった | 0 件である根拠（確認した記録の範囲）を計画書に書き、後続フェーズを含めずに次のチケットを作る | 計画書の記載と、起票したチケット |
| FBP-E03 | ユーザーが応答できない実行形態で対応先の合意が取れない | 既定の提案（この MR で対応）どおりに決めて後続チケットの作成まで行い、決めた内容を MR に記録する。止まらない | 起票したチケットと MR の記録（DDR `i0010-03`） |
| FBP-E04 | 同上で、別 issue の起票が必要になった | 起票せず、候補と理由を計画書と MR の記録に残す（取り消せない外部への副作用） | 起票の有無と記録 |
| FBP-E05 | 候補の反映先を考える場面 | 「いつ効くか × 守らせ方」の 2 軸で選び、常時読み込まれるアセットを増やすコストを考える | 計画書の反映先の書き方 |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン 1: メインエージェント専任 | 呼出条件、禁止事項（サブエージェントへの委譲） |
| メイン 2: 着手は提供コマンド・手作業で動かさない | 処理フロー 1 |
| メイン 3: 記録からの洗い出し（入力の列挙） | 処理フロー 2、禁止事項（記憶に頼った洗い出し） |
| メイン 4: 観点と類型で整理・0 件の根拠 | 処理フロー 3、「候補 0 件の扱い」 |
| メイン 5: 反映先の 2 軸と常時読込コスト | 処理フロー 3 |
| メイン 6: 既定はこの MR・対話で合意・確定前に後続チケットを作らない | 処理フロー 4、禁止事項（確定前の後続チケット作成） |
| メイン 7: 後続フェーズの確定と次の計画チケット 1 枚 | 処理フロー 6 |
| メイン 8: 別 issue は本文案 → 承認 → 起票 → 番号記録 | 処理フロー 5 |
| メイン 9: 未着手チケットの見直しと通知 | 処理フロー 7 |
| メイン 10: 作業ログは都度追記 | 処理フロー 9（`20-common-step-ticket` 仕様の完了検査） |
| メイン 11: 完了の検査（計画書・次チケット・作業ログ） | 処理フロー 9 |
| メイン 12: 完了後は呼び出し元へ制御を戻す | 処理フロー 9 の最終項 |
| 代替 1: 候補 0 件 | 「候補 0 件の扱い」 |
| 代替 2: 候補がすべて別 issue | 処理フロー 5 → 6（後続フェーズを含めない分岐） |
| 代替 3: 再開時は「現在地」から続ける | 「再開の扱い」 |
| 代替 4: 差し戻しで戻ったときの見直し | 「再開の扱い」（追加チケットで見直しを合意し直す） |
| 例外 1: ヘッドレスは既定どおり決めて起票まで進む | 処理フロー 4（`boundary.sh note` で MR に記録）、DDR `i0010-03` |
| 例外 2: 別 issue の起票が承認されなかった | 処理フロー 5 |
| 例外 3: 起票の失敗は停止・代替手段を使わない | 処理フロー 5 |
| 例外 4: 後から見つかった候補はこのタスクに戻らない | 禁止事項（振り返りのやり直し） |
| 規約 1: 計画書に含める項目 | OUT ひな形 |
| 規約 2: 計画書の置き場・テンプレート・HTML 併存 | 処理フロー 8、参照ナレッジ（`20-common-step-report-view`） |
| 規約 3: チケットのやってよいこと | 処理フロー 1（着手時の宣言）、禁止事項（改善の実施） |
| 規約 4: 人間レビュー要否の既定は不要 | 全体計画の方針（`rules/work-defaults.md`） |
| 整合 1: 後続チケットの型・実行者・レビュー要否 | 処理フロー 6、参照ナレッジ |
| 整合 2: 次に着手するチケットは提供コマンドの結果に従う | 処理フロー 6（`boundary.sh status` の `todo_head_type`） |
| 整合 3: 分類の観点・類型は機構の定義と一致させる | 処理フロー 3、禁止事項（独自の分類） |
