拒否側のフック 4 本（workflow-entry / workflow-state-guard / block-direct-git / workflow-guard）を実装した。判定規則はフック側に持たせず、共有ライブラリ（cmdpos.sh / scope.sh / hook-common.sh）の戻り値だけで分岐している。敵対的セルフレビューは 2 巡行い、1 巡目を「拒否をすり抜けられるか」、2 巡目を「正当な操作を止めていないか（= ロックアウト）」に分けた。実物へ入力を流すプローブで、読みだけでは出なかった 3 件が実測で出た。あわせて共有ライブラリの重大バグ（hook_read_state が常に空）を見つけて直した。全件テストは 2 ロケールで 25 本 / 161 件・FAIL 0。

◆特に見てほしい

  • r1（△注意）python が既定拒否（WF204）になること。実作業では一時スクリプトを python wip/tmp/x.py で走らせる場面が実際にある（このチケットでも使った）。commands.build-test に足すか、「wip/tmp/** のスクリプト実行」という分類を作るか、既定拒否のまま都度 ops を宣言するかの判断が要る
  • r2（△注意）作業ツリーの外への書き込みを WF209（判定不能）で拒否したこと。「範囲外だから WF201」でも「未記載だから WF202」でもなく、判定できない側に倒した。リポジトリの外に出す正当な作業（別リポジトリの参照など）を止める方に倒した判断なので見てほしい

実施した内容と結果

  1. 1

    .. を挟むと保護範囲をすり抜けられた ✕問題 根拠: プローブ A1 の実測（ask → deny）

    hook_rel_path はルート相対にするだけで . / .. を畳まない。wip/../.claude/settings.json は .claude/** のglob に一致しないので、保護範囲の拒否（WF201）ではなく未記載の確認（WF202）になっていた。確認は人間が答えれば通る経路なので、保護範囲が「確認すれば書ける範囲」に化けていた。

    根拠を見る（実行コマンドと出力） 
    （直す前）Write wip/../.claude/settings.json
{"permissionDecision":"ask","permissionDecisionReason":"WF202: wip/../.claude/settings.json は上限設定にも…"}
（直した後）
{"permissionDecision":"deny","permissionDecisionReason":"WF201: .claude/settings.json は 作業中チケット…"}

    結論

    workflow-guard の中でルート相対に直したあとに段を畳み、畳んだ結果で判定する。WG-T03 に . / .. を挟んだ 4 件を足して固定した。

  2. 2

    作業ツリーの外が承認単位になっていた ✕問題 根拠: プローブ B の実測（ask（承認単位 ..）→ deny）

    同じ経路で、リポジトリの外を指すパスは .. を承認単位として提示していた。承認されると ../ で始まるあらゆるパスが同じ扱いになる。

    根拠を見る（実行コマンドと出力） 
    （直す前）WF202: ../outside-evil.txt は…承認すると .. 以下が同じ扱いになる
（直した後）WF209: …は作業ツリー（<root>）の外を指すので、やってよいことの内側か判定できない

    結論

    畳んだ結果が絶対パスまたは .. で始まるものは WF209（判定不能）で拒否する。workflow-diff-check が 0038 で決めた「ルート相対でないパスを承認単位にしない」と同じ立場に揃えた。

  3. 3

    ふつうのシェルのループが既定拒否で止まった ✕問題 根拠: プローブ（2 巡目・偽陽性）の実測（deny → 許可）

    workflow-guard は分類できないコマンドを WF204 で拒否する（既定拒否）。cmdpos.sh は ; で段に割るので、for f in a b; do echo $f; done は 3 段になり、for と done が「分類外のコマンド」になっていた。拒否側フックの偽陽性はそのままロックアウトになる。

    根拠を見る（実行コマンドと出力） 
    （直す前）for f in a b; do echo $f; done
{"permissionDecision":"deny","permissionDecisionReason":"WF204: for はどの分類にも当たらない（既定拒否）…"}
（直した後）無出力（許可）

    結論

    scope.sh に _SC_SHELL_KEYWORDS（for / done / fi / esac / case / select / coproc / function）を足し、読み取り扱いにした。リダイレクトは段に残るので done > src/api/a.ts は従来どおり WF205 で止まる。

  4. 4

    hook_read_state が常に空を返していた（共有ライブラリ） ✕問題 根拠: workflow-entry のテストが全滅 → HK-T18 に退行テストを追加

    jq のプログラムは $review / $merge / $approvals / $entry の 4 つすべてを参照するのに、要求された副入力だけを渡していたためコンパイルに失敗し、出力が空になっていた。呼び手からは「壊れている」ではなく「無い（missing）」に見えるので、縮退と区別がつかない。0027/0028 由来で、workflow-diff-check の承認の記憶と subagent-stop-check の approvals 参照は効いていなかった。

    根拠を見る（実行コマンドと出力） 
    （直す前）hook_read_state entry → HC_ENTRY_STATE=missing（ファイルはある）
（直した後）ent=[ok] prompt_seq=1 declared_skill=00-workflow-quick-request

    結論

    要求しなかったものも null で必ず渡す。修正後に workflow-diff-check（48 件）と subagent-stop-check（57 件）を回し直して FAIL 0 を確認した。

  5. 5

    WF208 が入れ子の宣言行をすり抜けた ✕問題 根拠: WG-T09 に write / ops の行だけを差し替える 2 件を追加

    着手済みチケットの ticket_type / allow などの改変は WF208 で拒否する。判定は hook_read_input が jq で作る HOOK_FM_KEYS_TOUCHED に依るが、正規表現が行頭の allow: しか見ておらず、字下げされた write: の行だけを差し替える編集が素通りしていた。

    根拠を見る（実行コマンドと出力） 
    def fmkeys: "(^|\\n)([ \\t-]*(ticket_type|allow|executor|human_review|adversarial_review|predecessors)|[ \\t]+(write|ops))[ \\t]*:";

    結論

    字下げのある write: / ops: の行を判定に足した。- ops: … のような箇条書きは対象外なので、作業ログの追記は巻き込まない（負のコントロールもテストに入れた）。
