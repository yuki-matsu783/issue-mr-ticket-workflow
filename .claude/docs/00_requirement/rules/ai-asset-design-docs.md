# ai-asset-design-docs ルール

## 概要

AI アセット（スキル・フック・ルール・エージェント）の設計文書（`.claude/docs/` 配下）の正典規約を定める成果物ルールの要件を定義する。`design-docs` ルール（`apl/**` 用）とは独立で、設計文書に共通する規定（配置・正史のみ・DDR・用語辞書）も本ルールが自分で持つ。重なる規定は両方のルールに書き、内容を食い違わせない。

- **背景**: AI アセットの設計文書は、書き手が実装者本人になりがちで、要件書にスクリプト名・判定順といった内部構造が混ざりやすい。またアセットと文書の対応（1:1:1）が崩れると、どの文書がどのアセットの正か辿れなくなる。`.claude/docs/` を書くときに必要な規定が 1 本で揃うよう、この置き場の規約として独立に明文化する。
- **目的**: `.claude/docs/` 配下の文書が、アセットとの対応・視点・節構成の揃った形で書かれ、観点別レビューで横並びに検査できる状態を作る。
- **スコープ**:
  - 含む: このルールが定めるべき内容（配置、正史のみの記述、DDR の運用、用語辞書、1:1:1 対応、サブディレクトリ構成、外部視点の徹底、要件書の形）
  - 含まない: アプリ本体の設計文書（`apl/**`。`design-docs` ルール）、frontmatter のキー定義と `type` の値一覧（`markdown-docs` ルール）、SKILL.md 等アセット本体の書き方（`ai-asset-authoring` ルール）


### issue の受け入れ条件との対応

起点: issue #20（設計文書スキルをアプリ（apl/ 配下）に対応させる）

| issue の受け入れ条件 | 満たす受け入れ基準 |
|--------------------|------------------|
| 6. `ai-asset-design-docs` / `design-docs` ルールと相互に矛盾しない | 要件書の形（全 6 項目）、要件と仕様の順序と対応（全 2 項目）。`design-docs`「規約: requirement と spec」と対 |
| 8. `design-docs` ルールの適用範囲が `apl/**` になる（本ルールの相互参照が追随する） | 前提条件の 3 項目目、依存関係 |

## ユーザーストーリー

**[As a]** AI アセットの要件書・仕様書を書く AI として、

**[I want]** この置き場の規約（対応関係・視点・節構成・DDR の扱い）を 1 本のルールで確認したい。

**[So that]** セッションや書き手が変わっても同じ形の文書が揃い、レビューが構成の指摘で止まらないため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が `.claude/docs/` 配下の文書を作成・変更するとき、Shall このルールが収集され、この置き場の設計文書に必要な規定が本ルールだけで揃わなければならない（`design-docs` ルールの参照を要しない）。
- When このルールを書くとき、Shall 成果物ルールとして章スキーマ（`ルール体系.md`）に従わなければならない。

### 例外フロー

- If マージ済み DDR の内容を訂正する必要が出た場合、Then 新しい DDR で置き換え、旧 DDR は frontmatter の状態の更新だけで扱わなければならない（本文の書き換えで直さない）。
- If 複数のアセットにまたがる規定をどの文書に置くか迷う場合、Then 横断文書として直下に置くのではなく、正を 1 つのアセットの文書に決めて他から参照する形を先に検討しなければならない（横断文書は特定のアセットに紐づけられないものに限る）。

### 規約: 設計文書の配置とアセットとの対応

- When 設計文書を置くとき、Shall `.claude/docs/` 配下に、要件定義書を `00_requirement/`、仕様書を `10_spec/`、DDR を `20_ddr/`、用語辞書を `90_glossary/` の構成で置かなければならない。
- When アセットの設計文書を作るとき、Shall 要件定義書・仕様書・アセットは 1:1:1 で対応し、アセットごとに `00_requirement/<種類>/<アセット名>.md` と `10_spec/<種類>/<アセット名>.md` を持たなければならない（種類はスキル `skills/`、フック `hooks/`、ルール `rules/`、エージェント `agents/` などのサブディレクトリ）。
- When 特定のアセットに紐づかない横断的な文書を置くとき、Shall `00_requirement/` / `10_spec/` の直下に置き、サブディレクトリにはアセットに紐づく文書だけを置かなければならない。

### 規約: requirement と spec

- When requirement / spec を更新するとき、Shall それらは「その時点で有効な正史」だけを記述し、検討の経緯・却下した案・過去の版の内容・変更履歴の表を本文に残してはならない（履歴は git のコミット履歴と DDR で追う）。
- When アセットの要件書を書くとき、Shall 利用者（開発者・レビュアー・AI エージェント）から見た振る舞い（何ができ、何が拒否され、何が出力されるか）だけで書き、内部構造（スクリプト名・判定の順序・データのスキーマ・コマンドの構成）を含めてはならない（それらは仕様書に書く）。
- When アセットの要件書を書くとき、Shall 章順は 概要（背景・目的・スコープ。「含まない」には担い先）→ ユーザーストーリー → 受け入れ基準 → 前提条件 → 制約条件 → 依存関係 → 非機能要件でなければならない。
- When アセットの要件書を書くとき、Shall 受け入れ基準は EARS（When 〜 Shall / If 〜 Then / Shall not）で書き、節を メインフロー → 代替フロー → 例外フロー → 規約節（0〜3）→ 他のスキル・機構との整合（0〜1）の順に置かなければならない。先頭 3 節の見出しはこの文言で始め、規約節の見出しは `規約: <対象>` で始めなければならない。
- When メインフロー節を書くとき、Shall EARS 箇条書きの前に mermaid の `flowchart TD` を 1 つ置き、1 図のノードを 15 までとし、代替・例外への離脱点を識別子（`**[A1]**` / `**[E1]**`）で節と対応づけなければならない。
- When 自由記述（散文）を書くとき、Shall 概要の導入・背景・目的の 3 か所だけとし、合計 600 字以内に収めなければならない。
- When アセットの要件書を書くとき、Shall 関連ドキュメント節・レビュー記録節・変更履歴節を置いてはならない（関連は依存関係の節で足り、レビューの経緯は MR と DDR で追う）。
- When 要件書を新規作成するとき、または受け入れ基準を追加・変更する更新をするとき、Shall 概要章に「issue の受け入れ条件との対応」の小節を置き、起点の issue の受け入れ条件と、それを満たす受け入れ基準を対応づけなければならない（受け入れ基準を変えない更新と、既存文書への遡及適用は求めない）。
- When spec を変更するとき、Shall 対応する requirement より先に変えてはならず、要件側の誤り・不足を仕様側の辻褄合わせで吸収してはならない。
- When spec を書き終えるとき、Shall 「要件との対応」表が requirement の受け入れ基準を全件カバーし（行数が一致し）、実現箇所の無い要件（実装漏れ）と要件の無い節（過剰仕様）が無いことを確かめなければならない。

### 規約: DDR と用語辞書

- When 設計上の決定（複数案から選んだ・方針を変えた）が行われたとき、Shall その背景・決定・理由・却下案・影響が DDR に記録されなければならない。
- When DDR を命名するとき、Shall issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md` で命名し、issue を持たない DDR を作ってはならない。
- When DDR がマージされたあと、Shall 本文を変更してはならず、後続の決定で無効になった場合は frontmatter の `status` と置き換え先だけを更新しなければならない。`status` の値は `置き換え済み`（決定の全体が無効）/ `一部置き換え済み`（決定の一部だけが無効）/ `廃止`（後継を持たずに無効）の 3 つに限る。
- When 置き換えの関係を frontmatter に書くとき、Shall 置き換えられた側に `superseded_by`、置き換えた側に `supersedes` を対で持たせ、値はその DDR へのパスだけとしなければならない（散文・但し書きを値に混ぜない）。`status` が `一部置き換え済み` のときは、何が置き換わったかを `superseded_scope` に 1 行で書かなければならない。
- When DDR の一覧を参照するとき、Shall 一覧は各 DDR の frontmatter から生成されたものであり、手書きで保守されていてはならない。
- When 用語の意味を調べるとき、Shall 用語の定義（意味・目的・他の用語との関係）の正は用語辞書でなければならない。振る舞いの正（When / Shall）は requirement / spec が持ち、辞書と要件書で役割が重複してはならない。
- When 用語辞書に載せる語を決めるとき、Shall 複数の文書で使われ、かつ指し先や表記が揺れうる機構固有語（スキル名、ワークの種類、チケットの状態、機構が導入した概念、MR → PR のような用語の読み替え規則）に限らなければならない（一般的な開発用語は載せない）。
- When 辞書のエントリを書くとき、Shall 用語名と定義（2〜4 行）を持ち、別名・禁止表記（旧称・使わない言い方）があればあわせて持たなければならない。定義は辞書の中だけで読めて完結し、設計書へのリンクに頼ってはならない（参照の向きは常に設計書 → 辞書。辞書内の用語どうしの相互リンクはしてよい）。
- When 辞書を書くとき、Shall 振る舞いの要件（When / Shall、判定基準・数値・手順）を書いてはならない（正史の二重化を防ぐ）。
- When 収録済みの用語を文書で使うとき、Shall 辞書の表記に従い、初出箇所で辞書へリンクし、文書内で定義を再掲してはならない。禁止表記を使ってはならない。
- When 新しい機構固有語を導入するとき、Shall まず辞書に定義してから設計書でその語を使わなければならない（辞書が先、設計書が参照する）。収録語をリネームしたときは同じチケットの中で辞書を更新し、旧称は別名・禁止表記へ移さなければならない（あとでまとめて更新しない）。

## 前提条件

- `markdown-docs` ルールが frontmatter のキー定義・`type` の値一覧・テンプレート命名を持つこと（本ルールは再掲しない）
- DDR 一覧の生成手段は仕様書が定める
- 適用範囲は `.claude/docs/**` の paths で宣言し、`apl/**` には効かないこと

---

## 制約条件

- **技術的制約**: `design-docs` ルールとは適用範囲が交わらない。設計文書に共通する規定は両方のルールに書き、内容を食い違わせない
- **ビジネス的制約**: 文書の内容の妥当性は MR 上の人間レビューが判断する

---

## 依存関係

- `rules/ルール体系.md`（分類・章スキーマ・収集の要件）
- `rules/design-docs.md`（`apl/**` 側の対応ルール。重なる規定は内容を揃える）
- `markdown-docs` ルール（frontmatter 規約）
- `ai-asset-authoring` ルール（アセット本体側の書き方）

## 非機能要件

| 項目 | 説明 |
|------|------|
| 一貫性 | 要件書の節構成・見出し文言がアセット間で揃い、横並びレビューが構成差の指摘に時間を使わない。`design-docs` と重なる規定は内容を食い違わせない |
| 簡潔性 | `.claude/docs/` の規定が本ルール 1 本で揃う。同じファイルにマッチする他ルールの規定（frontmatter）は再掲しない |
