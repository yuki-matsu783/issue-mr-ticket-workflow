# i0009-44. 非機能要件からスコープ由来の恒久禁止を外し、自制に依存する統制を明記する

## 背景

ワーク境界のレビューで、要件定義書に 3 つのずれが見つかった。

1. **恒久禁止の混入**（非機能要件・テスト容易性）: 「静的検査は作成・変更のたびにローカルで行い、実施の有無を作業ログに残す（**自動実行の仕組みを外部のサービスに置かない**）」。この括弧は `i0009-19`（D6）の決定に由来するが、`i0009-19` の却下した案は「GitHub Actions で `shellcheck` を回す: リポジトリ設定の変更に当たる。**必要になったら別 issue で扱う**」と書いており、**恒久の禁止ではなくスコープ由来の一時的な判断**だった。要件に恒久の形で書くと、別 issue で扱う道が要件違反になる
2. **可用性の例外の欠落**: 「拒否側の仕組みは依存が壊れたとき拒否へ」と書かれているが、`i0009-11` が確定した打ち切り（fail-open）はこれの例外である。0014 はこの行を「偽」と名指ししながら、実際には例外フローに但し書きを足しただけで、非機能要件の行を直していなかった
3. **自制に依存する統制の未明記**: 制約条件は「自制に依存する統制は、該当する要件定義書にその旨を明記する」と定めている。メインフロー D の「設計や実装のタスクが外部の情報を必要としたとき、調査のタスクを起こして結論を持ち帰らなければならない」は、主語が機構ではなく、機構には「調査のタスクを起こしたか」を判定する手段が無い。それなのに但し書きが無かった

## 決定

- **1**: 括弧の恒久禁止を削り、要求の本体（ローカルで行う・実施の有無を作業ログに残す・**この記録は省略できない**）だけを書く。`i0009-19` の「記録は省略できないものとする」がそのまま要件になる
- **2**: 可用性の行に「**ただし判定そのものが制限時間内に終わらず打ち切られた場合は例外で、拒否側も通す側に倒れる**（例外フロー。塞げないため速さで守る）」を書き足す
- **3**: メインフロー D の当該行に「**この統制は機構が強制せず、計画のタスクとレビューの自制に依存する**」と、機構が強制する範囲（宣言していない外部への問い合わせのコマンドを拒否するところまで）を書き足す
- あわせて制約条件の自制の列挙から、コマンドによる外部への問い合わせを外す（`i0009-41` で機構が強制するようになったため）

## 理由

- **スコープ由来の判断を要件に恒久化しない**。「今回はやらない」と「これからもやってはいけない」は別のことで、要件に書くのは後者だけ。前者は DDR の却下した案と全体計画の保留に残る
- **非機能要件は読み手が振る舞いを予測する根拠になる**。「拒否側は拒否へ倒れる」だけを読むと、打ち切りでも止まると誤解する。例外フローに書いてあっても、非機能要件だけを読む人には届かない。**同じ事実は矛盾する場所すべてで揃える**（`ai-asset-design-docs` の堅牢性）
- **自制統制の明記は制約条件が自分で課した規約**。規約を作った当人の文書が従っていないと、他の要件書にも守らせられない
- **「報告と成果物が食い違う」を残さない**。0014 の報告は「偽の行を直した」と書いたが実際には直っていなかった。同じ指摘を 2 回受けないために、行そのものを直す

## 却下した案

- **1 について、括弧を「本 issue のスコープでは置かない」に書き換える**: 要件定義書は正史で、issue 固有の事情を書く場所ではない。スコープの話は全体計画と DDR に置く
- **2 について、例外フローへの参照だけを足す**（「例外フローを参照」）: 参照は読み飛ばされる。1 文で言い切れる内容なので書く
- **3 について、メインフロー D からこの行を削って計画スキルの要件書へ移す**: 「外部の情報が要るなら調査を起こす」は機構全体の方針で、`workflow-guard` 1 本の要件ではない。機構の要件定義書に置いたまま、強制されないことを明記するのが正しい
- **3 について、機構が強制できる形（調査タスクの存在を検査する）に変える**: 「この設計判断に外部の情報が必要だったか」は機構に判定できない。強制できないものを強制すると書かない
