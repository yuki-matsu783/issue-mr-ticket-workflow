この計画で何をするか

設計は「lib は #6 で既に正しい」という前提で書かれたが、境界レビュー 2 巡がその前提を崩した。hook-common.sh には設計が要求する 5 関数（hook_read_state / hc_append_jsonl / hc_json_write / hc_lock / hc_unlock）が無く、hook_read_input は副入力を受け取れず、scope.sh は web を知らず読み込み関数がパスを引数に取る。フック本体 11 本を書く前に lib の改修が要る。そのうえで T6（permissionDecision + 終了 0 の deny が実際に効くか）を 11 本を書き切る前に確かめる — 外れたときの手戻りが 11 本 + 登録ラッパー全部に及ぶため。拒否側の最も単純な 1 本（block-chmod）を lib と同じチケットで先に書き、それだけを単独で登録して T6 を確かめる ⓪ の段を段階登録の前に置く。

実装前に確定した 8 件

  1. 段階登録は 17 行（§1 の表が正）。案内側 12 行・拒否側 5 行。全体計画の「16 行 / ① 11 行」は subagent-start-check の PreToolUse Agent 登録（WF803）が増える前の数で、この計画で 17 行 / ① 12 行に組み直す
  2. T6 の確認は ⓪ で行い、そのときラッパーを付けない。ラッパーは「本体が起動できない = deny」なので、T6 が未確認の段で付けると本体の不調と登録方式の不調が区別できず、しかもラッパーは環境変数を見ないので環境変数で戻れない。⓪ は素の command で登録し最悪でも fail-open に留める
  3. T9（systemMessage の表示）は ① の後に確かめる。subagent-start-check の PreToolUse Agent 登録は案内側なので ① に入る。全体計画の 4c 表が「②-2 の後」と書いているのは 16 行時代の段の割り当てを参照した誤り
  4. HK-T01 の期待値は 17 行分の command 文字列の逐語一覧をフィクスチャ（.claude/hooks/tests/fixtures/settings-hooks.expected.tsv）に持つ。イベント名からディレクトリを機械変換できない行が 4 行あるため
  5. 読み込み行は雛形を先に直してから 22 本へ配る。現在の雛形は仕様と 3 点ずれている（FM_AVAILABLE を設定しない / fm_* スタブの戻り値が 1（仕様は 2）/ フォールバックの git rev-parse）
  6. 実装フェーズは DDR を書けない（ai-asset-implementation.deny に .claude/docs/**）。決定は作業ログに書き、0032 が棚卸ししてフェーズ 6 で DDR にする
  7. settings.json は許可範囲に入っているが AI は書かない。機構としては確認つきで書けるが、この issue の制約として登録は人間の操作。AI は JSON と手順を提示し登録後のコミットだけを行う
  8. フェーズ 7 は第 1 案（WORKFLOW_STATE_GUARD_ENFORCE=0 の新セッション）で通す。17 行の登録を保ったまま HK-T01 と全件が通る状態でマージできる唯一の案

方法とステップ

ステップ 1: 共通ライブラリと足場（0027）

1-1 読み込み行（i0009-36）。順序を守る: (1) assets/script.template.sh を仕様に合わせる（FM_AVAILABLE を設定 / fm_* スタブの戻り値を 1 → 2 / ルート解決 3 段目の扱いを確定）→ (2) assets/test.template.sh を揃える → (3) 残り 21 ファイルへバイト一致で配る → (4) SS-T05 を実装して通す（違うファイルを列挙して落ちる失敗ケースも）。

1-2 hook-common.sh。実装の型を 11 本で統一する（0006 f4）: HOOK_DENY_ID の代入 → lib の source → hook_init。この順でなければ読み込み行が出す WFx09 が既定の WF009 になる。

  • hook_read_input: stdin とパスが stdin に依存しない副入力を 1 回の jq で読む。存在するものだけ --rawfile、無いものは --argjson <名前> null（存在確認は [ -f ]）。HC_<名前>_STATE（ok / missing / broken）を立てる
  • hook_read_state: session_id に依存する副入力を 1 回の jq で読む。要るフックだけが呼ぶ
  • hc_* 4 関数: §1 の契約どおり。切り詰めは hc_append_jsonl が行い、2 秒と 60 秒は hc_lock が持つ。hc_lock は取得前に既存ロックの作成時刻を見て 60 秒より古ければ rmdir して強制解放し実行ログに 1 行残す（i0009-60）
  • 作成時刻は find <dir> -maxdepth 0 -mmin +1 で判定。hc_lock はホットパスではないので find の fork は上限に触れない。Windows の Git Bash での挙動は 0027 で実測して作業ログに残す

1-3 scope.sh: 読み込み 2 関数からパス引数を削る（i0009-48）/ scope_load_ticket の戻り値を 0・1・2 に分ける（i0009-16）/ web の 3 段判定（i0009-56）と出力先の走査（i0009-57）/ || true を || rc=$? に（i0009-35）/ hook-test を build-test と provided より先に判定。

1-4 config 3 ファイルを新規作成する。.claude/hooks/config/** は common.confirm なので 1 ファイルにつき WF203 の確認が出る。3 ファイルとも ⓪ より前に作る。

1-5 block-chmod 1 本とそのテスト（⓪ で使う）。1-6 .claude/rules/markdown-docs.md の参照不整合を解消する。

ステップ 2: ⓪ T6 の先行確認（0028）

  1. AI が貼る JSON 1 行分を提示する（ラッパー無しの素の command）: {"matcher": "Bash|PowerShell", "hooks": [{"type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/.claude/hooks/20-PreToolUse/block-chmod.sh\""}]}
  2. 登録前に人間がバックアップを取る
  3. 人間が登録し、AI が commit.sh でコミットする（WF203 は人間が承認）
  4. 新しいセッションで chmod +x を試し、permissionDecision: "deny" + 終了 0 で拒否されるかと decisions.jsonl の記録を見る
  5. 効いた: §3 の終了方式が確定。0030 以降はラッパー付きで進む
  6. 効かない: exit 2 + stderr へ切り替える。影響を受ける本体は 1 本だけで、手戻りは hook-common.sh の出力ヘルパに閉じる。仕様との食い違いは作業ログ「仕様からの逸脱」へ
  7. ロックアウト: WORKFLOW_BLOCK_CHMOD_ENFORCE=0 の新セッション。ラッパーを付けていないので必ず戻れる

ステップ 3: 案内側 6 本（0029）

0006 f5 の「重い 4 本と軽い 7 本」を案内側 / 拒否側の区切りの内側で満たす（重い 4 本のうち session-start と post-push-usage-report がここ、workflow-guard と workflow-state-guard が 0030）。

  • 案内側はラッパー無し（失敗は通す）
  • session-start は boundary.sh status --offline（3/3・未実装）が無ければ何も出さずに終了 0。依存する 8 件のテスト観点は書かずに #10 へ送る
  • post-push-usage-report は --accumulate と既定の両方で hc_lock usage-<branch> を取ってから加算する（i0009-61）。時刻の変換は自前の暦計算
  • subagent-start-check は PreToolUse Agent（WF801 の 2 経路・WF803）と SubagentStart（要点の注入）の両方に登録される 1 本
  • subagent-stop-check は PostToolUse Agent で tool_response.status で分岐し agentId（camelCase）を読む

ステップ 4: 拒否側の残り 4 本（0030）

  • ホットパスの jq の回数を実装で固定: block-chmod / block-direct-git / workflow-state-guard = 1 回、workflow-guard / workflow-entry = 2 回。make_counting_path で数え HK-T19 で固定
  • git / date / sed / find をホットパスで呼ばない。パス照合・コマンド分割は純 bash
  • 作業ツリーの解決（i0009-55）: cwd が HOOK_ROOT と異なるとき cwd から上向きに .claude を探す（[ -d ] の繰り返し。fork ゼロ）
  • 置き場の削除（i0009-59）: 正規化した元パスの前方一致で祖先（wip/10_tickets / wip）を拾う。rm -rf wip/tmp と rm -rf logs は通す
