# 10-task-overall-plan — issue を確定してフェーズ列を合意する

サブエージェントに委譲しない（人間との合意が本体なのでメインエージェント専任）。承認①②③を得る前に先へ進まない（承認なしの起票・ブランチ作成・計画チケット作成をしない）。`git commit` / `git push` を直接実行しない（common-step の提供コマンドのみ）。全体計画書に実施結果や経過を書かず、HTML ビューも作らない。closed な issue を勝手に再オープンしない。フィードバック計画より後のフェーズの要否をここで決めない。ソースコード・設計文書・`.claude/` 配下に書き込まない。

## 目的

issue から MR までの入口を 1 回で通し、この issue をどのフェーズ列で進めるかを人間と合意する。以後のすべてのタスクがこの計画書を入力にする。

- 要件: `.claude/docs/00_requirement/skills/10-task-overall-plan.md`
- 仕様（正。処理フロー 1〜10・OUT ひな形・eval ID OP-E01〜04）: `.claude/docs/10_spec/skills/10-task-overall-plan.md`

前提: 作業領域のチケットが全体計画チケット 1 枚だけであること。他のチケットが既にあれば状態の不整合として報告し、指示を待つ。

## 手順

1. **issue の確定**: `20-common-step-issue` の手順で類似の open issue を検索する（0 件なら closed も）。候補を提示して**承認①**（既存 #N で進める / 新規に起票する）を取る。番号・URL の指定があれば検索を省く。closed だけが見つかったときは「新規に起票 / 対応なし（過去の結論を採る）」を確認し、同じ不具合の再発なら再オープンの承認を選択肢に加える
2. **issue の内容の確定**: 既存の記述が計画に十分ならそのまま進む。不足があれば追記案、新規なら本文案を作り、**ブランチ名・MR タイトルの案と同時に承認②**を取ってから `20-common-step-issue` で追記・起票する。主目的がアプリと AI アセットにまたがる、または 1 MR に大きすぎるときは分割案を提示し、このセッションで扱う 1 つを決める（残りは起票のみ）
3. **マージ方式の確認**: `gh repo view --json squashMergeAllowed,mergeCommitAllowed,rebaseMergeAllowed` / `glab api "projects/:id" | jq .squash_option` で squash merge の可否と既定を確認する。squash が使えない・既定でないときは影響（作業領域の全履歴が main に残る）を警告し、設定変更は人間に委ねる（AI は変更しない）
4. **ブランチと draft MR**: 未コミットの変更があれば扱い（コミット / stash / 破棄 / 中断）を確認してから、`20-common-step-feature-mr` の手順で作成する。issue 番号・ブランチ名・MR 番号と URL を報告する
5. **種別の判定**: 受け入れ条件と変更対象から「アプリ / AI アセット」を判定し、根拠とともに提示する（「両方」は置かない。手順 2 で分割済みのはず）
6. **フェーズ列**: 種別のテンプレート（正は `00-workflow-issue-mr-driven` 仕様の対応表とフェーズ列テンプレート）を土台に組む。調査とフィードバック計画は必ず含める。主作業フェーズは迷ったら含める側に倒す（不要なら計画タスクの「対象なし」で即完了できる）。フィードバック計画より後は含めない
7. **方針**: `.claude/rules/work-defaults.md` があればそれを基準に、タスクの種類ごとの実行者・人間レビュー要否（理由付き）・やってよいことを**基準との差分**として組む。基準どおりの行は「基準どおり」と書く。基準が無ければスキルの既定（リスクの高いタスクは人間レビュー要）を使い、その旨を計画書に書く
8. **全体計画書と承認③**: `assets/overall-plan.template.md` から全体計画書（`wip/00_overall_plan/overall-plan.md`）を作って提示し、フェーズ列・実行者・レビュー要否・やってよいことの合意を `AskUserQuestion` で取る。却下されたら修正して再提示する。合意の内容（誰が・いつ・何に）を計画書に記録する
9. **最初の計画チケット**: `20-common-step-ticket` の `create` で調査計画チケットを **1 枚だけ**未着手に作る。記載事項は全体計画の方針から埋め、DoD は issue の受け入れ条件から導く
10. **完了**: 作業ログを整えて `ticket.sh complete <番号>` で全体計画チケットを完了し、`00-workflow-issue-mr-driven` に制御を戻す（切れ目の処理はそちら）

- **ヘッドレス実行**（承認が取れない）: 案（issue 案・計画案）をコミットせずに報告してセッションを終える
- **再開**: draft MR と全体計画書が既にあれば 1〜4 をやり直さない。既存の計画を提示して続きから進める（二重作成しない）

## OUT ひな形

`assets/overall-plan.template.md`（HTML ビューは作らない。1 画面程度）。

| 節 | 内容 |
|----|------|
| 対象 | issue 番号と URL・MR 番号と URL・ブランチ |
| 種別 | アプリ / AI アセットと判定根拠 |
| フェーズ列 | 採用した列・テンプレートとの差分と理由 |
| 受け入れ条件との対応 | 条件 × 満たすフェーズの表（条件の件数と行数を一致させる） |
| 方針 | タスクの種類ごとの実行者・人間レビュー要否（理由）・やってよいこと（`work-defaults` との差分表示） |
| 保留した点 | 判断を保留した項目と決める時期 |
| 合意の記録 | 承認①②③の内容・日時 |

## 参照

- issue の検索・起票・追記: `20-common-step-issue`
- ブランチと draft MR: `20-common-step-feature-mr`
- チケットの作成・完了: `20-common-step-ticket`
- コミット: `20-common-step-commit-push`
- タスクの構成（15 種・順序・種別テンプレート）: `00-workflow-issue-mr-driven`（正）
- 既定判断基準: `.claude/rules/work-defaults.md`（任意。無ければスキルの既定）
- 承認の記録の寿命: 切れ目ごとに MR コメントへ書き写す（呼び出し元の切れ目処理）

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 作業領域に他のチケットがある | 状態の不整合として報告し、指示を待つ。勝手に片付けない |
| 承認①②③が却下された | その段階に留まり、修正案を作り直すか停止する。先の段階に進まない |
| squash merge が使えない / 既定でない | 影響を警告して人間に委ねる。リポジトリ設定を AI が変更しない |
| 未コミットの変更がある | 扱いを確認してから手順 4 に入る。勝手に stash・コミット・破棄しない |
| CLI 未導入 / `origin` が対象外 | 各 common-step の対処に従い、報告して停止する |
| ヘッドレスで承認が取れない | 案を報告してセッションを終える。コミットしない |
| `ticket.sh complete` が TK005 | 列挙された未充足（DoD・作業ログ・未コミット）を埋めてから再実行する |
