# 0046 shlex の守備範囲と現行 cmdpos.sh との差分

- 対象 issue: #15 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/issues/15
- PR: #36 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/pull/36
- 計画: `wip/20_plans/0041-investigation-plan.md`（観点 A-1・A-2・A-3）

## サマリ

**`shlex` は `cmdpos.sh` の代わりにならない。** 供給できるのは「語割り」と「クォート除去」だけで、出力 10 項目のうち 8 項目は自前実装が丸ごと残る。それだけなら「一部を置き換える」判断もありえたが、50 件のコーパスで突き合わせると `shlex` 側に**実行位置の見落としが 6 件、実行されない語の誤検知が 1 件**出た。見落としは検査をすり抜ける方向の誤りで、フックの用途では致命的になる。

一方で `shlex` は現行実装の既知の弱点を 6 件で正しく解いている。とくに `git 'commit'`（クォートで割った語）は `cmdpos.sh` の仕様が「判定できない既知の制約」として `_` を返す入力で、`shlex` は `git commit` と正しく復元した。**照合役として使えば現行実装のバグを機械的に見つけられる**という筋は残る。

| 観点 | 結論の性質 | レビューの重み |
|---|---|---|
| A-1 出力 10 項目の切り分け | 注意（供給は 2 項目のみ） | ◆ |
| A-2 扱えない構文 5 種 | 問題（うち 3 種が判定を壊す） | ◆ |
| A-3 現行実装との差分 | 問題（見落とし 6 件・誤検知 1 件）／良（現行の弱点を 6 件で解消） | ◆ |

## 確かめられなかったこと

- **`shlex` を本番に置いた場合の総合的な正しさ**。試作は「段分割 + 実行体 + サブコマンド」に絞っており、`CP_WRITE_TARGETS` や `CP_OPAQUE` の再実装は行っていない。それらを足したときに新たな差分が出ないことは確かめていない
- **PowerShell 経路の網羅**。`cmdpos.sh` は PowerShell の前処理（ヒアストリング・行継続・呼び出し演算子）を持つが、本調査では最小入力 2 件を見ただけで、コーパスによる突き合わせは bash 経路のみ

## 実施した内容と結果

### A-1: `shlex` は出力 10 項目のどれを供給できるか

`cmdpos.sh` のヘッダ（`.claude/hooks/lib/cmdpos.sh:8-27`）が公開 API として挙げる 10 項目を、`shlex.shlex(posix=True, punctuation_chars=True)` の出力と突き合わせた。

| 出力 | shlex が供給するか | 残る自前実装 |
|---|---|---|
| `CP_EXE` | 部分的 | 語割りは供給される。basename 化・`.exe` の除去・小文字化・ラッパー（`sudo` `time` `env` `timeout` ほか 20 語）の読み飛ばし・変数代入の読み飛ばしはすべて自前 |
| `CP_ARGS` | 供給する | クォート除去まで `shlex` が行う。区切りバイトへの詰め直しだけが自前 |
| `CP_SUBCMD` | 供給しない | `git` のグローバルオプション表（値を別トークンで取る 6 種）を持って走査する処理は自前 |
| `CP_REDIRECTS` | 部分的 | `>` `>>` `<` は `punctuation_chars` で独立した語になる。ただし fd 番号（`2>`）は `2` と `>` に割れ、fd 複製（`>&`）と `&>` の区別、`/dev/null` の除外はすべて自前 |
| `CP_WRITE_TARGETS` | 供給しない | `cp` `mv` `tee` `touch` `mkdir` `rm` `truncate` `install` `ln` `sed` のオプション表と位置引数の解釈は完全に自前 |
| `CP_OPAQUE` | 供給しない | 実行系の語彙表と `-c` 等の併用判定は自前 |
| `CP_PROVIDED` | 供給しない | 提供コマンドのパス形の照合は自前 |
| `CP_DATA` | 供給しない（むしろ壊す） | ヒアドキュメントの追跡が無く、本文を実行位置の語として出す。下の A-2 と A-3 を参照 |
| `CP_GITLIKE` | 供給しない | 縮退時の代替判定なので `shlex` とは無関係 |
| `CP_DEGRADED` | 供給しない | bash の版数と 4096 文字という縮退条件は Python には無い。Python 版なら別の縮退条件を定義し直すことになる |

**答え**: 供給されるのは `CP_ARGS`（全面）と `CP_EXE`・`CP_REDIRECTS`（部分）の 3 項目。残る 7 項目は `shlex` の外側に自前で書く。`cmdpos.sh` 429 行のうち `shlex` に置き換わるのは正規化部（`_cp_normalize_to_reply` とその補助、おおよそ 120 行）に留まる。

### A-2: 扱えない構文 5 種の実際の出力

`python3 wip/tmp/probe.py a2` の出力から。左が入力、右が `shlex` の語の並び。

| 構文 | 入力 | `shlex` の語 | 何が起きるか |
|---|---|---|---|
| ヒアドキュメント本文 | `cat <<EOF⏎git commit⏎EOF` | `['cat', '<<', 'EOF', 'git', 'commit', 'EOF']` | 本文が普通の語になる。区切り記号を含むと段が増える（A-3 の c46） |
| コマンド置換 `$( )` | `echo "$(git commit -m x)"` | `['echo', '$(git commit -m x)']` | 1 語のまま。中の `git commit` は見えない |
| バッククォート | ``echo `git commit` `` | ``['echo', '`git', 'commit`']`` | バッククォートはただの文字。中身が展開されない |
| fd 複製 `2>&1` | `git push 2>&1 >/dev/null` | `['git', 'push', '2', '>&', '1', '>', '/dev/null']` | `2` が独立した語になる。fd 番号と引数の区別は付かない |
| 算術展開 `$(( ))` | `echo $((1<<2)); ls` | `['echo', '$', '((', '1', '<<', '2', '));', 'ls']` | `));` が 1 語になり、**その中の `;` が区切りとして働かない** |
| コメント | `ls # git commit` | `['ls']` | `commenters='#'` で正しく落ちる。ただし下の逆パターンあり |
| PowerShell ヒアストリング | `$x = @'⏎git push⏎'@` | `['$x', '=', '@\ngit push\n@']` | クォートとして解釈され本文が 1 語になる。偶然だが実害は無い |
| PowerShell 行継続 | ``git `⏎  push`` | ``['git', '`', 'push']`` | バッククォートが独立した語になり、`push` が引数に落ちる |

**答え**: 5 種のうち、**ヒアドキュメント・コマンド置換 / バッククォート・算術展開の 3 種が判定を壊す**。fd 複製と PowerShell は「自前実装が要る」で済む。

`commenters` には逆向きの罠がある。`shlex` の `commenters` は文字単位で、語頭かどうかを見ない。そのため `foo#bar git status` を `['foo']` に切り詰め、**`git status` を丸ごと落とす**。`cmdpos.sh` は直前の文字が語の切れ目かどうかを見ており（`cmdpos.sh:107-114`）、`foo#bar` を 1 語として扱う。

### A-3: 現行実装との差分（コーパス 50 件）

`wip/tmp/corpus.json` の 50 件を、現行 `cmdpos.sh`（`bash wip/tmp/bench.sh dump-corpus`）と `shlex` 版の試作（`python3 wip/tmp/probe.py a3`）に食わせ、「段の数 + 各段の実行体とサブコマンド」の署名で突き合わせた。コーパスは `test_cmdpos.sh` のテスト入力を土台に、ヒアドキュメントと算術展開の境界例を足したもの。

**一致 27 件 / 差分 23 件。** 差分を性質で分けると次のとおり。

#### 見落とし（実在するコマンドが `shlex` 側で見えない）— 6 件・危険

| # | 入力 | cmdpos | shlex |
|---|---|---|---|
| c19 | `echo "$(git commit -m x)"` | `git:commit` を検出 | 検出しない |
| c20 | ``echo `git commit` `` | `git:commit` を検出 | 検出しない |
| c27 | `echo $((1<<2)); ls` | 2 段（`ls` を検出） | 1 段（`ls` が消える） |
| c28 | `foo#bar git status` | `foo#bar` + 引数 `git status` | `foo` のみ（`git status` が消える） |
| c45 | `echo $((1<<2)); git commit` | 2 段（`git:commit` を検出） | 1 段（`git:commit` が消える） |
| c50 | `cat <<EOF⏎EOF⏎git push` | 2 段（`git:push` を検出） | 1 段（`git:push` が消える） |

いずれも**検査をすり抜ける方向**の誤り。`block-direct-git` や `workflow-guard` がこの入力を素通しすることになる。

#### 誤検知（実行されない語をコマンドとみなす）— 1 件

| # | 入力 | cmdpos | shlex |
|---|---|---|---|
| c46 | `cat <<EOF⏎foo; git push⏎EOF` | 1 段（本文はデータ） | 2 段（`git:push` を検出） |

bash が決して実行しないヒアドキュメント本文の `git push` を、実行位置の語として出す。c50 と合わせて、ヒアドキュメントの追跡が無いことが**両方向**の誤りを生んでいる。

#### `shlex` の方が正確 — 6 件

| # | 入力 | cmdpos | shlex |
|---|---|---|---|
| c31 | `git 'commit'` | `git:_`（判定できない。仕様が認める既知の制約） | `git:commit`（正しい） |
| c23 | `echo 'git commit'` | `echo:_` | `echo:git commit`（引数の値を復元） |
| c24 | `echo "git commit"` | `echo:_` | 同上 |
| c26 | `ls # git commit` | `ls:_`（コメントがプレースホルダとして残る） | `ls:`（引数なし。正しい） |
| c41 | `sed -i 's/a/b/' f.txt` | `sed:_` | `sed:s/a/b/` |
| c42 | `grep "git commit" file.txt` | `grep:_` | `grep:git commit` |

c31 が最も重い。`test_cmdpos.sh` は「クォートで割った語（`git 'commit'`）は判定できない（既知の制約。サブコマンドは `_` になる）」とコメント付きで現状を固定しており、`shlex` はこの制約を解消する。

#### 表現の違い・試作の粗さ — 10 件

`cmd 2>&1` `cmd >> app.log 2>&1` `cmd &> all.log` `cat <<< "data" | head` はリダイレクト演算子がサブコマンドに漏れているが、これは試作がリダイレクトを実行体の後ろで処理していないため。`shlex` の欠陥ではない。`eval "git commit"` と `bash -c 'git push'` は差が出るが、どちらも opaque と判定される段なので判定結果は変わらない。

**答え**: 差は 23 件出た。うち 7 件（見落とし 6・誤検知 1）が判定を誤る方向で、6 件は `shlex` の方が正確。残り 10 件は判定に影響しない。

## 設計への反映

- **本番置換は勧められない**。`shlex` に置き換えると、置き換えられるのは 429 行のうち正規化部 120 行程度で、その代償に 7 件の判定誤りが入る。うち 6 件は検査をすり抜ける方向で、フックの用途では受け入れがたい。同等の正しさを保つには、ヒアドキュメント追跡・コマンド置換の再帰・算術展開の読み飛ばし・語頭を見るコメント判定を Python 側で書き直すことになり、`shlex` を使う利点がほとんど残らない
- **照合役としては筋がある**。c31 のような「現行実装が `_` を返す入力」で `shlex` は正しい答えを出す。両者の差を機械的に取れば、現行実装が取りこぼしている入力を継続的に見つけられる。ただし差分の多く（10 件）は判定に影響しない表現差なので、比較する項目を絞る設計が要る
- **決めるには B 系（0043）の起動コストが要る**。本番置換の是非はここまでで十分に判断材料が揃ったが、照合役案を採るかどうかはテスト実行時間への影響を見てから決める

## 想定と異なった点

- **`shlex` のコメント処理が逆向きの誤りを生む**と分かった。計画では「コメントは `shlex` が扱えない構文」として数えていたが、実際は `commenters` で扱える。ただし語頭を見ないため `foo#bar` を切り詰めるという、想定していなかった見落としが出た
- **ヒアドキュメントが誤検知と見落としの両方を生む**。計画では「本文を語として出す（誤検知）」だけを想定していたが、区切り語の後に続く本物のコマンドを吸い込む見落とし（c50）も起きた
- **`punctuation_chars=True` が算術展開を壊す**。`));` が 1 語になるため、その後ろの段が消える。計画では算術展開を観点に挙げていなかった（`test_cmdpos.sh` の負のコントロールから拾って初めて分かった）

## 残課題

- **試作の網羅範囲**。`CP_WRITE_TARGETS` と `CP_OPAQUE` を `shlex` 版で再実装したときの差分は取っていない。本番置換を選ばないなら不要だが、選ぶなら必要
- **PowerShell 経路のコーパス**。bash 経路 50 件に対し、PowerShell は最小入力 2 件のみ。照合役案を採る場合、PowerShell も対象にするかは設計で決める
- **`shlex` の版差**。この環境は Python 3.11.15。`punctuation_chars` の挙動が古い版で異なるかは確認していない
