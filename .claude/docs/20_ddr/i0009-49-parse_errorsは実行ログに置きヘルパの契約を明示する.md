# i0009-49. `parse_errors` は実行ログに置き、書き込みヘルパの契約を明示する

## 背景

`i0009-23` は `usage/<branch>.json` の加算を `mkdir` ロックで直列化し、共通仕様 §5 に「取得できなければ最大 2 秒待って諦め、加算せずに **`parse_errors` を +1** して終了 0」と書いた。

ワーク境界の 2 巡目レビューで 2 つの問題が指摘された。

1. **循環**: `parse_errors` が `usage/<branch>.json` の中にあるなら、その +1 自体が同じ read-modify-write でロックを要る。ロックが取れなかったから諦めたのに、諦めたことを記録するのにロックが要るという循環になる。しかも `post-push-usage-report` 仕様の `usage/<branch>.json` のスキーマ列挙に `parse_errors` は無く、回復手順は「`logs/sh/hook-post-push-usage-report.log` の `parse_errors`」とログ側を指しており、**置き場が仕様内で 2 通り**あった
2. **ヘルパの契約が無い**: `i0009-38` が置いた `hc_append_jsonl` / `hc_json_write` / `hc_lock` / `hc_unlock` に、引数・戻り値・タイムアウト値・**切り詰めを誰が行うか**が書かれていなかった（説明は「4 KB 未満に切り詰めて」だけで、呼び手が切り詰めてから渡すのか関数が切るのかが決まっていない）

## 決定

- **`parse_errors` の置き場は実行ログ（`logs/sh/hook-<name>.log`）1 か所**とする。ロックを諦めたことも、transcript の解析に失敗したことも、ここに 1 行残す。**JSON の側には書かない**
- 共通仕様 §5 の該当箇所を「加算せずに実行ログへ 1 行残して終了 0」に直し、**JSON に書かない理由（循環）を添える**
- §1 に**ヘルパの契約の表**を置く（引数 / 戻り値 / 責任範囲）。要点は次の 3 つ
  - **切り詰めは `hc_append_jsonl` が行う**（`redact` を通したうえで 4 KB 未満に。`note` と `target` は合わせて 1 KB）。呼び手は切り詰めない
  - **タイムアウトの値（2 秒）は `hc_lock` が持つ**。呼び手は指定しない
  - **`hc_unlock` は冪等**（取っていなくても失敗しない）
- `hook_read_input` / `hook_read_state` も同じ表に載せ、戻り値と読む範囲を明示する

## 理由

- **記録の失敗が記録に依存してはいけない**。ロックが取れない状況で「取れなかった」を残すには、ロックの要らない経路が要る。追記だけのログは §5 の 1 段階目（4 KB 未満の `>>`）で競合しないので、この用途にちょうど合う
- **置き場が 2 通りある状態は、実装者がどちらかを選び、テストがもう一方を見る形で失敗する**。1 か所に決めるだけで消える
- **「4 KB 未満に切り詰める」は誰かが実際にやらないと守られない**。0021 の `fm_*` の呼び出し規約と同じ型の問題で、方針だけ書いても実装では消える。関数の側に寄せれば 11 本すべてで同じ結果になる
- **タイムアウトを引数にすると呼び手ごとに違う値が入る**。2 秒という数字は「案内側フックが人間を待たせない上限」から来ており、呼び手の都合で変える性質のものではない
- `usage/<branch>.json` は**利用者が読む集計結果**で、機構の内部事情（ロックを諦めた回数）を混ぜると読みにくくなる

## 却下した案

- **`parse_errors` を `usage/<branch>.json` に置き、+1 だけはロック無しの追記で行う**: JSON の一部だけをロック無しで書く形になり、`hc_json_write`（一時ファイル + `mv`）と混ざって壊れる
- **ロックを諦めたら記録しない**: 集計が欠けたことに誰も気づけない。`i0009-23` が「取りこぼしがあったことは記録から分かる」（要件の可用性）を求めている
- **専用の `logs/parse-errors.jsonl` を作る**: 追記だけのファイルが 1 本増えるが、実行ログに既に同じ役割（そのフックが何をしたか）があるので重複する
- **切り詰めを呼び手の責任にする**: 11 本が別々に閾値を持つ。`i0009-38` が共通化した理由がそのまま反対の根拠になる
- **`hc_lock` にタイムアウトを引数で渡せるようにする（既定 2 秒）**: 引数があると使われる。使われた瞬間に「どのフックが何秒待つか」を追う必要が生まれる

## 影響

- `10_spec/フック共通仕様.md` §1（ヘルパの契約の表）・§5（ロック失敗時の記録先と循環の理由）
- `10_spec/hooks/22-PostToolUse/post-push-usage-report.md`（`parse_errors` の置き場は実行ログ。加算にロックを使うことは 0026 が書く）
- **実装フェーズへ**: `hc_append_jsonl` は `redact` → 切り詰め → `>>` の順。`hc_lock` は取得時に `trap` へ解放を登録する
- 関連: `i0009-23`（並行書き込みの 3 段階）・`i0009-38`（ヘルパを `hook-common.sh` に置く）
