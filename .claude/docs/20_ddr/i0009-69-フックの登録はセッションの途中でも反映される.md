# i0009-69. フックの登録はセッションの途中でも反映される

## 背景

段階登録（⓪ → ① → ②-1〜②-5 の 7 段）の手順は、次の形で設計されていた。

> 人間が `settings.json` を貼り替える → **新しいセッションを開く** → 軽い操作を通して確認する

前提は「`settings.json` はセッション開始時に読まれる」。0028（⓪ の `block-chmod` の単独登録）でこの前提が外れた。18:40 に登録し、**同じセッションの** 18:42 の Bash 呼び出しでフックが発火した。0031 の段階 ① でも同じで、`cp` の直後の Bash 呼び出しで `workflow-diff-check` と `workflow-entry` が発火した。実測は 2 回とも一致している。

## 決定

- **段階登録の手順から「新しいセッションを開く」を外す**。貼り替えた直後の操作でそのまま確認してよい
- ただし**環境変数（`settings.json` の `env` と外部から与えるもの）は別**で、セッション開始時にしか読まれない（§4）。`WORKFLOW_PROBE_4C=1` や `WORKFLOW_<NAME>_ENFORCE=0` を効かせるには新しいセッションが要る
- ロックアウトの復旧手順が「`WORKFLOW_<NAME>_ENFORCE=0` の**新しい**セッション」と書いている箇所は、この理由で新セッションのままにする。フックの登録を戻す復旧（バックアップからの復元）のほうは、貼り戻した直後から効く
- 手順書では「登録は即時・環境変数は次のセッションから」を**対にして**書く

## 理由

- **手順が短くなる**。段階登録は 7 段あり、各段で人間がセッションを開き直すのは大きな手間。実際 0031 は 6 段を 1 セッションで通した
- **確認の即時性が上がる**。貼り替えの直後に軽い操作を通せるので、「どの段で壊れたか」が段と 1 対 1 で結びつく。セッションをまたぐと、その間の操作が交ざって切り分けが鈍る
- **両者を「新しいセッション」でまとめて覆っていると、なぜ新セッションが要るのかが分からなくなる**。理由が分からない手順は、コストが見合わないときに省かれる。省かれて困るのは環境変数の側（緊急停止が効かないまま「効かない」と誤読する）
- **復旧の速さにも効く**。ロックアウトしたときに登録を戻せばその場で復旧できると分かっていれば、復旧手段の選択が変わる

## 却下した案

- **安全側に倒して新しいセッションを開き続ける**: 実測で不要と分かったコストを払い続けることになる。段階登録は今後もフックを足すたびに走る手順で、1 回きりの節約ではない
- **「反映されることがある」と曖昧に書く**: 手順書としては「開く」と同義になる（読み手は安全側に倒す）。実測の結果は明確なので断定して書く
- **登録の反映契機を機構の側で確かめる仕掛けを作る**（起動時に `settings.json` のハッシュを記録する等）: 反映は Claude Code の挙動で、機構が観測しても手順が変わらない

## 影響

- `10_spec/フック共通仕様.md` §4（緊急停止。「環境変数はセッション開始時に読み込まれる」の記述に、登録は即時に反映されるという対比を添える）
- `10_spec/skills/20-common-step-ai-asset-creator.md`（`settings.json` を変える手順。段階登録の恒久の置き場）
