# 20-common-step-report-view スキル 仕様

## 概要・禁止事項

HTML ビュー作成の共通ステップの内部仕様。対応する要件は [00_requirement/skills/20-common-step-report-view.md](../../00_requirement/skills/20-common-step-report-view.md)。

Markdown を正文とし、HTML はテンプレートのコピーを Edit で埋めて作る。出力後に検査スクリプト `check-html.sh` に通す。

禁止事項:

- スクリプトや白紙からの HTML の組み立て（必ずテンプレートのコピーから）
- テンプレートの DOM 構造の改変（構造の変更はテンプレート自体の改訂として AI アセットフェーズへ）
- HTML にだけある情報を作ること（正文は Markdown）
- 片方（md / html）だけを更新して作業を終えること
- 検査を飛ばした提出、独自の色・記号の持ち込み
- 全体計画書への HTML ビューの作成

## 呼出条件

- 各実施タスク（結果レポート）・各計画タスク（フェーズ計画書）・`10-task-overall-summary`（統括レポート）が、md を書き終えて HTML を作るとき、および md を更新したとき

## IN / OUT

| IN | OUT |
|----|----|
| 正文の Markdown（`wip/30_reports/` または `wip/20_plans/`）、用途（レポート / 計画書） | 同じベース名の `.html`（検査通過済み）、検査結果（作業ログに残す） |

## IN / OUT サンプル

```bash
cp .claude/skills/20-common-step-report-view/assets/report.template.html wip/30_reports/0002-investigation.html
# （Edit で節を埋める）
bash .claude/skills/20-common-step-report-view/scripts/check-html.sh wip/30_reports/0002-investigation.html
# => OK: 検査 7 項目すべて通過（id 42 件 / リンク 17 件を確認）
# => RV001: プレースホルダが残っている: {{summary}}（1 件）
```

## 処理フロー

1. 対象を判定する: `wip/30_reports/` の結果レポート・統括レポートと `wip/20_plans/` の計画書は必須。全体計画書（`wip/00_overall_plan/`）には作らない
2. 用途に対応するテンプレート（レポート用 / 計画書用）を **Read で読み、同じベース名の HTML として Write で書き出す**。`cp` / `copy` のようなコマンドでの複製は使わない（コマンドによる書き込みは宣言の有無によらず WF205 で拒否されるので、`wip/20_plans/` のように書き込みを宣言したチケットでも通らない）
3. Edit で節を埋める。内容は md と同一（視覚化のみ）。テンプレートの節に対応しない内容は最も近い節へ収める。必須節（`data-required`）は削除できず、該当する内容が無いときも空にせず「無し」と 1 行書く（md 側も同じ。存在検査だけでは空を防げないため、書き忘れと「無い」を区別する）。空になる**任意**の節は節ごと削除してよく、それ以外の DOM 構造は変更しない
4. `check-html.sh` を実行し、失敗したら原因を直して再実行する（飛ばさない）
5. **md と HTML の対応を自分で確かめる**。`check-html.sh` は HTML の構文と必須節の存在しか見ないので、**md にあって HTML に無い節・表・行は検出できない**（HTML は構文として正しいままだから）。次を数えて突き合わせる: (a) md の `##` / `###` 見出しの数と HTML の `<h2>` / `<h3>` の数、(b) md の表の数と HTML の `<table>` の数、(c) 同じことを述べている箇所の**数値**（件数・行数）。食い違ったら HTML 側を直す。数えた結果を作業ログに残す
   - 数えるときは**同じ対象を指す 2 つの数**を並べる。結論の数なら md の `###` の見出し数と HTML の `<h3 id=` の数（`id` を持たない見出しはテンプレートの飾りなので数から外れる）。数え方をその都度決めると、次に数える人が違う数を出して食い違いに気づけない
   - **同じ数を 2 か所以上に書くときは内訳を必ず添える**（「27 件」ではなく「◎良 14 / △注意 12 / ✕問題 1 = 27 件」）。内訳があれば、片方を更新し忘れたときに足し算が合わなくなって気づける
   - **累積の数（タスク全体の合計・テスト ID の総数など）は 1 か所にだけ置き、他の箇所はそこを指す**。同じ累積値を複数の節に書くと、節を追記するたびに全部を直す必要が生じ、必ずどれかが古くなる
6. 検査結果（通過項目・確認件数）と、5 の突き合わせの結果を作業ログに残す
7. 以後 md を更新したら、同じ変更を HTML に反映して 4〜6 を繰り返す。**md だけを直して HTML を後回しにしない**（対の同期は push 前チェックが存在しか見ないため、内容のずれは残る）

## OUT ひな形

- `assets/report.template.html`（レポート用）と `assets/plan.template.html`（計画書用）。共通の規約:
  - 自己完結: 外部リソース参照なし・`<style>` は 1 つ・スクリプトなしで表示可能
  - ライト / ダーク両対応（`prefers-color-scheme`）
  - 視覚語彙: 結論の性質は 3 色 + 記号 + 文字（良 / 注意 / 問題）、レビューの重みは色相を使わず ◆（特に見てほしい）/ ◇（**判断が欲しい**）/ ・（細かいレビュー不要）。◇ の欄の見出しは「判断が欲しい」とし、「承認が欲しい（方針は決めた）」のように**書き手が方針を決めていることを前提にした文言にしない**。調査タスクは候補と比較軸を並べるところまでで決めないと定められており、決めていない状態で「承認が欲しい」と書ける欄しか無いと、置き場所の無い項目が生まれる
  - プレースホルダは `{{名前}}` 形式で、HTML コメントの中ではなく**要素の内容として**置く（消し忘れがブラウザで見えるため。書き方の説明はコメントで添えてよい）。必須節には `data-required` 属性を付け、検査の対象にする。`data-required` は `<section>` に限らず要素種別を問わず付けられ（サイドバーのメタ情報・見出しにも付く）、検査はこの属性だけで必須要素を集める
  - 必須節の一覧はテンプレートだけが持つ（この仕様書には書かない。テンプレートと検査の二重管理を避ける）。どの節を必須にするかの判断と経緯は DDR に残す。必須要素にはすべて `id` を付ける（検査の「要素名と出現順」の経路は予備で、テンプレート側では使わない）
  - テンプレートは `<body data-template="report">` / `<body data-template="plan">` を持ち、`check-html.sh` は対象 HTML のこの属性で必須節の導出元テンプレートを選ぶ（無ければ置き場のディレクトリ `30_reports` / `20_plans` で推定し、それもできなければ RV006）
  - 節構成はレポートが「サマリ → 確かめられなかったこと → 実施した内容と結果 → 設計への反映 → 想定と異なった点 → 残課題」、計画書が「この計画で何をするか → 対象と範囲 → 方法とステップ → 検証 → チケット → リスクと復旧（任意）→ スコープ外（任意）→ 保留した点 / 対象なし」（計画タスク共通の節。各計画タスクの要件の OUT はこの節に収める）
  - 計画の種類ごとの固有節（フィードバック計画の候補一覧・分類・振り分けなど、共通の節に収まらないもの）は、必須節の後（「保留した点 / 対象なし」の前）に `<section>` を追加してよい。テンプレートの節を置き換えたり削ったりしない限り、DOM 構造の改変には当たらない
- 初版は参考実装のレポートテンプレートを土台に、参考実装固有の記述を除いて作る（`i0001-05`）

### 種類ごとの OUT ひな形の節 → HTML の節（正）

各タスクの仕様が定める OUT ひな形の節を、HTML テンプレートのどの節に収めるかの対応。**書き手はこの表で行き先を決め、その場で判断しない**（判断がぶれると、同じ種類のレポートでも節の位置が変わり、レビュアーが探す場所を覚えられない）。

| OUT ひな形の節（各タスク仕様） | HTML の節 |
|---|---|
| 対象（issue・MR） | サイドバーのメタ情報（`data-required`） |
| 結論・答え・成果の要約 | サマリ |
| 確かめられなかったこと・確認できなかったこと | 確かめられなかったこと |
| 実施した内容・結果・一覧の表（候補 / 対象 / テスト ID など） | 実施した内容と結果 |
| 設計・後続フェーズへの反映（別 issue・追加チケットを含む） | 設計への反映 |
| 想定と異なった点・逸脱 | 想定と異なった点 |
| 残課題・保留した点・対象なしの根拠 | 残課題 |
| 計画書の「この計画で何をするか / 対象と範囲 / 方法とステップ / 検証 / チケット」 | 計画書テンプレートの同名の節 |
| 上のどれにも収まらない種類固有の節 | 必須節の後・「保留した点 / 対象なし」の前に `<section>` を足す |

### テンプレートの置き場（正）

| テンプレート | 置き場 | 理由 |
|---|---|---|
| HTML ビュー（`report.template.html` / `plan.template.html`） | このスキルの `assets/` | 種類によらず同じ骨格で、検査（`check-html.sh`）が同じディレクトリのテンプレートから必須節を導出する |
| md の**共通の型**（`report.template.md` / `plan.template.md`） | このスキルの `assets/` | 節構成は HTML ビューと 1 対 1 で対応する。別々の場所に置くと片方だけが更新される |
| md の**種類ごとの型**（`ai-asset-design-plan.template.md` など） | 各タスクスキルの `assets/` | 節の中身（何を書くか）はタスクの種類ごとに違い、その正は各タスクの仕様の「OUT ひな形」にある |

**共通の型は 1 か所に集約し、種類ごとの差分だけを各タスクスキルが持つ**（申し送り 0022 E4、保留 P3）。各タスクスキルの `assets/*.template.md` は、共通の型を丸ごと複製せず「共通の型に加えてこの節を持つ」形で書き、共通部分は `20-common-step-report-view` の `assets/` を参照する。15 本のタスクスキルが同じ節構成を逐語で持つと、節を 1 つ足すのに 15 か所を直すことになる。

md の共通の型（`report.template.md` / `plan.template.md`）は**この issue で新規に作る**（0003 の a7 が「結果報告の md テンプレートが存在しない」ことを検出した）。HTML ビューのテンプレートだけがあり md 側が無い状態は、md が正文であるという原則（要件書と `i0001-05`）と噛み合わない。
- 付録: 調査の生データなど正文に収まらない資料は、同じ置き場に `<連番>-<種類>-appendix-<記号>.md`（記号は `A` から）として置き、正文の md から参照する。付録に HTML は作らない（検査対象外）

## Script 処理

### check-html.sh <file.html>

**前提コマンド**: `bash`・`awk`・`grep`・`sed`。属性値と `id` の抽出は `awk` で行う（POSIX の `awk` で足り、`gawk` 固有の機能は使わない）。`awk` が無い環境では検査を縮退させず **RV009（環境の不備）**で止める（黙って通すと「検査した」という記録だけが残る。issue #6 の逸脱 D2-4）。引数・ファイルの誤り（RV008）と番号を分けるのは、受け取った側の対処が違うためである（RV008 は呼び出し方を直す、RV009 は実行環境に `awk` を入れる）。

検査は**全項目を実行して**未充足を全件列挙する。終了コードは成功 0 / 検査不合格 1 / 引数・ファイル不正 2（RV008。引数が 1 つでない・ファイルが無い・読めない・`.html` でない。検査に入る前に判定し、最終行は `RV008:`）/ 環境の不備 2（RV009。`awk` が無い。RV008 の判定の後、検査に入る前に判定し、最終行は `RV009:`）。導出元テンプレートを特定できない（`data-template` が無く置き場からも推定できない、またはテンプレートファイルが無い）ときは検査 6 の不合格 RV006（終了 1）として他の項目と一緒に列挙する。ログ: 共通 logger（`20-common-step-shell-script` の `scripts/logger.sh`。内部仕様は `10_spec/skills/20-common-step-shell-script.md`）を使う。使い分けは `rules/logger.md`。

| # | 検査 | 不合格の識別子 |
|---|------|---------------|
| 1 | プレースホルダ（`{{名前}}`）の残存が 0 件 | RV001 |
| 2 | 外部リソースの読み込み（`src` 属性・`<link href>`・CSS の `url()`・``）が 0 件。`<a href>` のハイパーリンク（issue・MR への参照）は表示の自己完結を損なわないため対象外 | RV002 |
| 3 | id の重複が無い | RV003 |
| 4 | ページ内リンク（`#id`）の参照先がすべて存在する | RV004 |
| 5 | `<style>` 要素がちょうど 1 つ | RV005 |
| 6 | テンプレートの必須節（`data-required` 付きの節）がすべて存在する | RV006 |
| 7 | 負のコントロール: 抽出した id・リンクが 0 件のとき「異常なし」とせず、抽出自体の故障を疑って不合格にする | RV007 |
| — | 引数・ファイル不正（検査に入る前。終了 2） | RV008 |
| — | 環境の不備（`awk` が無い。RV008 の後、検査に入る前。終了 2） | RV009 |

- 出力は `OK:`（確認した件数を添える。件数の明示が負のコントロールを兼ねる）または `RVxxx:` の列挙。属性値の抽出は二重引用符・シングルクォートの両方を対象にする（`src='...'` を素通ししない）
- 検査 6 の必須節一覧はテンプレート自身から導出する（テンプレートを読み `data-required` 属性を持つ要素を、要素種別を問わず `id`（無ければ要素名と出現順）で集める）。テンプレートと検査の二重管理をしない。必須要素が存在しても内容がプレースホルダのままなら検査 1 で、空なら「無し」と書く運用（処理フロー 3）で防ぐ（検査 6 は存在だけを見る）
- テンプレートは必須節の id と目次アンカーを常に持つ（正しく埋めた HTML で id・リンクが 0 件になることはない — RV007 の前提）

### テスト観点

| テスト ID | 種別 | 固定する振る舞い |
|-----------|------|----------------|
| RV-T01 | 正常系 | テンプレートを正しく埋めた HTML が OK（件数付き） |
| RV-T02 | 異常系 | プレースホルダ残存・外部参照・重複 id・破断リンク・style 2 つがそれぞれの RV で全件列挙。外部参照と id はシングルクォートの属性値でも同じ結果 |
| RV-T03 | 異常系 | 必須節を丸ごと削った HTML が RV006 |
| RV-T04 | 異常系 | 空に近い HTML（id/リンク 0 件）が RV007（出力なし＝合格にしない） |
| RV-T05 | 境界 | ページ内アンカー・`data:` URI・`<a href>` の外部リンクは外部リソースと数えない |
| RV-T06 | 境界 | `data-required` が `<section>` 以外（サイドバーの `dl`・`h1`）に付いていても検査 6 が拾い、削られていれば RV006。`data-template` の値で導出元が変わり、属性が無ければ置き場で推定する |
| RV-T07 | 異常系 | 引数なし・存在しないファイル・`.html` 以外が RV008・終了 2（最終行は `RV008:`）。導出元テンプレートを特定できない HTML は RV006・終了 1 |
| RV-T08 | 異常系 | `awk` が使えない環境（`PATH` から外した状態）で、正しい引数の正しい HTML を渡しても RV009・終了 2 になる（縮退して OK を返さない。RV008 とは別の番号で返る） |
