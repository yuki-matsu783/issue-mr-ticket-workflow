# 0043 ホットパスの起動コストの実測と実行環境の前提

- 対象 issue: #15 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/issues/15
- PR: #36 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/pull/36
- 計画: `wip/20_plans/0041-investigation-plan.md`（観点 B-1・B-2）

## サマリ

**解析そのものは `shlex` が圧勝し、プロセス起動で逆転する。** 起動を除いた解析時間は `shlex` 版 0.048 ms に対し現行 `cmdpos_parse` が 2.40 ms で、**`shlex` が 50 倍速い**。ところが Python のプロセス起動が 27.3 ms かかり、これは解析の 570 倍にあたる。ホットパスのフックは毎ツール呼び出しで起動し直す使い捨てプロセスなので、この 27.3 ms が丸ごと乗る。

現行のホットパス 1 本（bash 起動 + `cmdpos.sh` 読込 + 解析）が 6.62 ms。Python 版にすると 27.3 ms で、**1 本あたり +20.7 ms、5 本で +103 ms**。DDR i0009-22 が認めている外部プロセスは `jq` 1 回（3.85 ms）だけなので、Python の追加はその**予算の 7 倍**を 1 本ごとに使うことになる。

さらに、いちばん軽い起動でも壁は越えない。`python3 -S -c pass`（site を読まない空起動）が 10.9 ms、`import shlex` を足すだけで 21.5 ms。bash の空起動 2.40 ms に対して、**何もしない Python が 4.5 倍**である。

| 観点 | 結論の性質 | レビューの重み |
|---|---|---|
| B-1 ホットパスの増分の実測 | 問題（+103 ms／ツール呼び出し） | ◆ |
| B-2 Python 実装の前提 | 問題（fail-open を塞げないのに Python は全環境で保証されない） | ◆ |

## 確かめられなかったこと

- **Windows / Git Bash での実測**。この実行環境（Linux コンテナ）から測れない。仕様書は Git Bash での `git` 起動を約 95 ms としており、Windows ではプロセス起動の差がさらに開く見込みだが、実測の裏付けは無い
- **ホットパス 5 本を実際に同時起動させたときの壁時計時間**。本調査は 1 本ずつ直列に測った。5 本は並列に起動するため、コア数に余裕があれば壁時計は合計より短くなる。逆に CPU が詰まる環境では合計に近づく
- **`uv` を使った場合の起動時間**。`uv` はこの環境に無い。#15 本文の実測（`uv run --no-project` 29 ms）を引き継ぐに留めた

## 実施した内容と結果

### B-1: 起動コストの実測

`wip/tmp/bench.sh` と `wip/tmp/probe.py` で各 50 回測り、中央値を取った。単位はマイクロ秒。

| 対象 | 中央値 | 最小 | 最大 |
|---|---:|---:|---:|
| python 内 `shlex` 解析（プロセス起動なし） | **48** | 46 | 177 |
| `bash -c ':'` 起動 | 2,396 | 2,120 | 3,732 |
| bash 内 `cmdpos_parse`（プロセス起動なし） | **2,395** | 2,083 | 4,412 |
| `jq -n` 起動 | 3,850 | 3,465 | 6,346 |
| bash 起動 + `cmdpos.sh` 読込 + 解析 | **6,616** | 5,427 | 9,656 |
| `python3 -S -c pass`（site なしの空起動） | 10,892 | 9,804 | 13,308 |
| `python3 -S -c 'import shlex'` | 21,450 | 19,674 | 39,631 |
| `python3` 起動 + `probe.py` の解析 | **27,332** | 25,936 | 30,884 |

読み取れること。

- **解析そのものは `shlex` が 50 倍速い**（48 µs 対 2,395 µs）。純 bash の状態機械が文字単位のループで回っているぶん遅く、C 実装の `re` に乗る `shlex` が圧倒的に速い
- **その差は起動で消し飛ぶ**。Python の起動は解析の 570 倍（27,332 µs 対 48 µs）。1 回きりの使い捨てプロセスでは解析の速さが効かない
- **`import shlex` だけで 10.6 ms 増える**（10,892 → 21,450）。`shlex` は `re` を引き込むためで、最小限の起動でも避けられない
- **測定の揺れより差がはるかに大きい**。bash 版の最大値 9,656 µs に対し Python 版の最小値が 25,936 µs で、範囲が重ならない

**増分の見積り**。ホットパス 1 本が現行 6,616 µs、Python 版が 27,332 µs で、1 本あたり **+20,716 µs（+20.7 ms）**。ホットパス 5 本（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）が毎ツール呼び出しで走るので、直列に足すと **+103.6 ms／ツール呼び出し**。5 本は並列に起動するため壁時計はこれより短くなりうるが、CPU 時間としては 5 倍かかる。

**DDR i0009-22 との関係**。同 DDR は「ホットパスのフックが起動してよい外部プロセスは、stdin を解析する `jq` の 1 回だけ」と定めている。その `jq` が 3,850 µs。Python の追加は 27,332 µs で、**認められている外部プロセスの予算 1 本ぶんの 7.1 倍**にあたる。「1 秒以内」という目安には収まるが、DDR が「1 秒以内は検査できない形なので fork 回数で縛る」と決めた経緯からすると、目安のほうを持ち出して通す筋ではない。

### B-2: Python 実装にするための前提

読み取りのみで整理した。`cmdpos.sh` を Python にする場合、`.claude/` に次が要る。

| # | 必要になるもの | いまの状態 | 難しさ |
|---|---|---|---|
| 1 | **インタプリタの解決** | フックはリポジトリルートを fork なしで解決している（`BASH_SOURCE` からの上向き探索）。Python の場所は同じようには決められない。Windows では `python3` が PATH に無く `py` や `python` になる | 解決順を定義し、見つからないときの振る舞いを決める必要がある |
| 2 | **起動オプション** | — | `-S`（site を読まない）で 27.3 → 21.5 ms 程度。`-I` で環境変数の影響を排除。それでも bash の 2.4 ms には届かない |
| 3 | **import の最小化** | — | `shlex` は `re` を引き込み 10.6 ms。`json` を足せばさらに増える。stdin の JSON を `jq` で読んでいる現状と重複する |
| 4 | **DDR i0001-14 の基準を満たすこと** | 同 DDR は判定材料を「想定する全実行環境で確実にアクセスできるもの」に限っている。Python は Git Bash に同梱されない | 同 DDR は「全環境で確実にアクセスできる対象が増えた場合は、その対象への問い合わせを行ってよい」と逃げ道を用意している。`uv python install` で Python を配れば基準を満たしうるが、その `uv` 自体の配布が要る |
| 5 | **ブートストラップの入口** | `uv` を SessionStart フックで入れる案が #15 にある | SessionStart フック自身は Python 不在でも動く必要があり、bash で書くことになる。入れ子の依存が生じる |
| 6 | **失敗時の振る舞い** | DDR i0009-11 が「打ち切り（timeout）は fail-open で塞げないので、フックを速く保つことだけが対策」と決めている | Python が無い環境ではコマンド検査が丸ごと落ちる。bash 版のフォールバックを残すなら**同じ判定を 2 言語で二重に実装**することになり、両者の食い違いが新しいバグの種になる |

**答え**: 6 項目のうち 1・4・5・6 が設計上の判断を要する。とくに 6 が重い。フックは自動で走り、失敗したときの復旧手段が AI に無い（DDR i0001-14 の理由節）。Python 不在の環境で検査が落ちる形は、この機構の前提と噛み合わない。

## 設計への反映

1. **本番置換は採らない**。0046 の「判定誤りが 7 件入る」に加え、本調査の「+103 ms／ツール呼び出し」「DDR i0009-22 の予算の 7.1 倍」「Python 不在時に検査が落ちる」が重なる。3 つのうちどれか 1 つでも十分な却下理由になる
2. **DDR i0009-22 は維持する**。上書きの必要が無い。ただし「なぜ Python を入れなかったか」を新しい DDR に残し、次に同じ問いが出たときに実測から辿れるようにする
3. **照合役案の起動コストは問題にならない**。テストは毎ツール呼び出しではなく明示的に走らせるもので、27 ms の起動が 1 回増えても影響しない。0046 の「現行実装のバグを機械的に見つけられる」という利点だけが残る
4. **解析が 2.4 ms かかっている事実は別の話として残る**。`cmdpos_parse` は fork ゼロだが、bash の空起動と同じだけの時間を解析に使っている。速くする余地はあるが本 issue の範囲外

## 想定と異なった点

| 計画時の見込み | 実際 | どう扱ったか |
|---|---|---|
| Python 版は「起動のぶんだけ遅い」 | 解析そのものは 50 倍速く、起動で逆転する構図だった | 「解析 vs 起動」を分けて測り直し、両方を表に載せた |
| #15 の実測（`python3` 18.5 ms）を再現する | この環境では 27.3 ms（`json` `os` `shlex` を import）。`-S` で 21.5 ms まで下がる | 環境差として両方を記録し、増分の見積りには自分の実測を使った |
| B-2 は「何が必要か」の列挙で終わる | 失敗時の振る舞い（項目 6）が単なる列挙ではなく却下理由の 1 つになった | 設計への反映に格上げした |

## 残課題

- **Windows / Git Bash での実測**。計画どおり本 PR では行わない。実測が要ると設計フェーズが判断したらフィードバック計画で別 issue にする
- **ホットパス 5 本の並列起動の壁時計時間**。直列の合計（+103 ms）は上限側の見積り。実際の体感を知るには 5 本同時の測定が要る
- **`cmdpos_parse` 自体の 2.4 ms**。fork ゼロだが速くはない。ホットパスの目安（1 秒以内）には十分収まっているので、本 issue では扱わない
