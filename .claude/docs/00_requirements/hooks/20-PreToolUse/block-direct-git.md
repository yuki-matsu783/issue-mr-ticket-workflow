# block-direct-git フック

## 概要

コミットと push は提供コマンド経由でのみ行い、それを使う task スキルが手順を標準化する（横断要件書 E 節）。このフックは、AI が Bash / PowerShell ツールで `git` のコミット・push を直接実行しようとしたときに拒否し、使うべき提供コマンドと task スキルの名前を案内する。本書は GitLab の用語で書き、GitHub では MR → PR と読み替える。

- **背景**: 提供コマンドはメッセージ規約・対象ファイルの明示・クレデンシャルと副産物の自動除外・push 前チェックを担う。ドキュメント上の規則だけでは AI の遵守に依存し、直接実行されれば規約も除外もチェックも働かない。Claude Code の権限設定は複合コマンド（`cd x && git commit`）をすり抜けるため、コマンド文字列そのものを見る仕組みが要る。一方、部分一致で判定すると、コミットメッセージやヒアドキュメント、日本語の地の文に「commit」「push」が含まれるだけで誤って拒否され、参考実装では作業のたびに踏んでいた。
- **目的**: `git` のコミット・push の直接実行が確実に拒否され、実行でないものへの誤った拒否が起きず、拒否されたときに AI が正しい経路（提供コマンドと task スキル）へ戻れる状態を実現する。
- **スコープ**:
  - 含む: `git` のコミット・push の直接実行の検知と拒否、複合コマンド・ラッパー・パス付き実行体の扱い、誤検知の防止（コマンド位置の判定）、判定できないときの倒し方、提供コマンド経由の実行の許可、記録
  - 含まない: コミットメッセージの規約・対象ファイルの除外・push 前チェックの内容（提供コマンドと task スキルの要件）、コミット・push 以外の `git` 操作の統制、進行状態のファイルの保護（`workflow-state-guard`）

---

## ユーザーストーリー

**[As a]** 機構の保守者として、

**[I want]** AI がどんな形でコマンドを組み立てても、`git` のコミット・push の直接実行は止めて提供コマンドへ誘導したい。

**[So that]** すべてのコミット・push がメッセージ規約・除外・push 前チェックを経て行われ、レビュアーが差分で経緯を追えるため。

**[As a]** Claude Code で作業する開発者として、

**[I want]** issue 本文やコミットメッセージに「commit」「push」と書いただけで作業が止まらないでほしい。

**[So that]** 誤った拒否のたびに言い換えを考える手間を無くし、統制が本当に必要な場面だけで働くため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が Bash または PowerShell ツールで `git` のコミットをコマンドとして実行しようとしたとき、Shall フックは拒否し、コミットの提供コマンドとそれを使う task スキルの名前、「提供コマンド経由でやり直すこと」を伝えなければならない。
- When AI が Bash または PowerShell ツールで `git` の push をコマンドとして実行しようとしたとき、Shall フックは拒否し、push の提供コマンドとそれを使う task スキルの名前を伝えなければならない。
- When コミット・push が複合コマンドの中にあるとき（`cd x && git commit`、`;` や `||` での連結、パイプの後、`sudo` / `env` / `command` などの透過的なラッパーの後、`if` / `then` などの予約語の後）、Shall フックは同じように拒否しなければならない。
- When `git` が絶対パス・相対パス・`.exe` 付き（`/usr/bin/git`、`./git`、`git.exe`）で実行されるとき、Shall フックは同じように拒否しなければならない。
- When コミット・push のオプション（`--amend`、`--force`、`--no-verify`、`--tags` など）が付いているとき、Shall フックは同じように拒否しなければならない（オプションで例外を作らない）。
- When AI が提供コマンド（機構のスクリプト）を実行するとき、Shall not フックはそれを拒否してはならない。提供コマンドの内部で `git` のコミット・push が実行されることは対象外とする（フックが見るのはツールへ渡された呼び出し文字列だけ）。
- When コマンド文字列の中で「commit」「push」の語が、ヒアドキュメントの本文・クォートされた文字列・`#` から始まるコメント・検索の対象語（`grep` 等の引数）・日本語の地の文に現れるだけで、コマンドとして実行される位置に無いとき、Shall not フックは拒否してはならない。
- When `git` のコミット・push 以外のサブコマンド（`git status`、`git log`、`git diff`、`git add`、`git merge` など）が実行されるとき、Shall not フックは拒否してはならない。
- When ダブルクォートの中のコマンド置換（`"$(git commit ...)"`）のようにクォート内でも実行される形であるとき、Shall フックはそれを実行として扱い拒否しなければならない。
- When 文字列をコードとして受け取る実行系（`eval`、`bash -c`、`xargs`、`find -exec` など）がコマンド位置にあり、その中身を静的に読めないが「commit」「push」の語を含むとき、Shall フックは拒否側に倒さなければならない（実行を素通りさせる誤りより、実行でないものを止める誤りを選ぶ）。
- When 判定の依存（判定ライブラリ・必要な bash のバージョン）が満たせないとき、Shall フックは従来どおりの部分一致に縮退して判定を続け、縮退していることをメッセージに含めなければならない（誤った拒否は増えるが素通りは増やさない）。
- When 1 行が判定できる長さを超えるコマンドであるとき、Shall フックは部分一致に縮退しなければならない。
- When フックが拒否したとき、Shall その記録（拒否の種類・コマンドの先頭部分）が残り、フィードバック計画の振り返りで AI とユーザーが参照できなければならない。記録に機密情報を含めない。
- When 拒否メッセージを出すとき、Shall メッセージはコミットと push を機械的に区別できる識別子を持ち、使うべき提供コマンドと task スキルの名前を含んでいなければならない。
- When 縮退した判定で拒否したとき、Shall メッセージに「縮退した判定で拒否した可能性があること」と、コマンド文字列内の語を言い換える対処（`.claude/rules/` の AI が渡すコマンド文字列の規約）を含めなければならない。
- When Claude Code の権限設定（`permissions.deny`）でも `git` のコミットを拒否しているとき、Shall not フックはそれに依存せず、多重防御として併用しなければならない（権限設定だけでは複合コマンドを止められない）。
- When `workflow-state-guard` が draft 解除の直接実行を判定するとき、Shall コマンド位置の判定はこのフックと共有され、複製されていてはならない。
- When 提供コマンドによる状態の変更（チケットの着手・完了、レビュー依頼・完了、マージ前作業）がコミットを伴うとき、Shall それらは提供コマンドの内部で行われ、このフックの拒否の対象にならない。

### 代替フロー

- If push 前チェックの項目を意図的に飛ばす必要がある場合、Then それは push の提供コマンドが用意する「飛ばした項目と理由を MR の差分として残す」手段で行い、このフックを緊急停止して直接 push してはならない。
- If `glab` / `gh` が使えない環境で提供コマンドが外部委任モードで動いている場合、Then コミット・push は変わらず提供コマンド経由で行われ、このフックの判定は変わらない。
- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは判定を行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If AI がこのフックに拒否された場合、Then AI は提供コマンドと task スキルの手順に従ってやり直し、コマンド文字列の分割や別の実行系での迂回・権限設定の変更・フックの登録解除を行ってはならない。
- If フックの入力が解釈できない場合（ツールへの入力が壊れている等）、Then フックは拒否側に倒し、拒否の理由に機構の不調であることを含めなければならない。

## 前提条件

- コミットと push の提供コマンドと、それを使う task スキルが導入されていること
- Claude Code のフック機構が使え、Bash / PowerShell ツールへ渡されたコマンド文字列を実行前に検査できること
- 実行環境が Windows の git bash（MSYS bash 4.3 以上）であること。満たさない環境では縮退した判定で動く

---

## 制約条件

- **技術的制約**: 実体は bash で書き、外部プロセスを起動しない純粋な判定でホットパス（すべてのコマンド実行）に耐える。PowerShell ツールからの実行も検知の対象に含めるが、実処理は bash に統一する。PowerShell のバックスラッシュ区切りのパスは見逃しうることと、PowerShell 固有の構文（ヒアストリング・呼び出し演算子 `&` など）の扱いは仕様に明記し、判定できない形は拒否側に倒す。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: 緊急停止（機構全体 / このフックだけ）は環境変数で行い、ユーザーが新しいセッションに対して設定する。AI は同じセッションの中で設定できない。push 前チェックを飛ばす通常の手段は提供コマンド側の「飛ばした事実を差分に残す」手段であり、緊急停止をその代わりに使わない
- **外部的制約**: 意図的な文字列の分割などによる回避への対抗は目的としない（既定動作を安全側へ倒す仕組みであり、安全境界ではない）

## 依存関係

- コミットの提供コマンドとそれを使う task スキル（案内先。未作成）
- push の提供コマンドとそれを使う task スキル（案内先。push 前チェックと飛ばす手段を持つ。未作成）
- `workflow-state-guard`（コマンド位置の判定を共有。未作成）
- `.claude/rules/`（AI が渡すコマンド文字列の規約、bash 規約、Git 運用）
- `.claude/settings.json`（権限設定による多重防御）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | すべてのコマンド実行の前に働くため、コミット・push と無関係なコマンドは外部プロセスを起動せずに体感できない時間で通す |
| セキュリティ | 記録とメッセージにコマンド文字列に含まれうる機密情報（トークン・パスワード）を出力しない |
| 可用性 | 判定できないとき・依存が満たせないときは拒否側に倒し、素通りさせない。縮退はメッセージで分かる |
| 保守性 | コマンド位置の判定は 1 か所に持ち、他のフック（`workflow-state-guard`）と共有する。複製する場合はテストで同一性を固定する |
| テスト容易性 | コマンド文字列を与えて拒否 / 許可を単体テストでき、誤検知の代表例（ヒアドキュメント・クォート・コメント・地の文）と複合コマンドの代表例がテストに含まれる。テストは合否件数を出力し失敗時に非 0 で終わる |
