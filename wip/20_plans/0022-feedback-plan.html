方法とステップ

1. 洗い出し（記録から機械的に）

全チケットの固定見出しをチケット番号順になぞり、レポート・計画書・PR コメントを加えて 54 件を列挙した。各行に出どころ（チケット番号 + 見出し、またはレポート名 + 節名）を付けた。

2. 分類（観点 × 類型 × 反映先の 2 軸）

観点: 足りなかった / 邪魔だった / 無かった / 問題なし。類型: (a) 無かった / (b) 誤っていた / (c) 罠（形・条件）が書かれていなかった / (d) 辿り着けなかった。反映先: いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）× 守らせ方（読ませる / 手順化する / 機械的に拒否する）。常時読込を増やす候補（F1 ルール 11 本）にはコストの注記を付けた。

3. 対応先の決定（既定「この MR」）

大きすぎるもの（ルール 11 本）と、フック本体・ワークフロースキルが要るもの（2/3・3/3）だけを別 issue にした。承認④の自律運用のため、決定はメインエージェントが行い PR #7 のコメントで人間がいつでも覆せる形にした。別 issue の起票は行わない（外部への書き込みは自律運用の範囲外。全体まとめで一覧にする）。

4. 後続の確定

AI アセット設計計画チケット 0026 を 1 枚起こす。実装を伴う候補（HK-T15・SP-E 改名・test-lib・skill.template・識別子・SKILL.md）は 0026 が実装チケットの要否を判断する。
