# 20-common-step-commit-push スキル

## 概要

コミット・push の共通ステップの要件を定義する。この機構ではコミットと push は提供コマンド経由でのみ行え（直接実行は機構が拒否する）、このスキルがその使い方 — 対象の選び方・メッセージの作り方・除外・push 前チェックへの向き合い方 — を標準化する。すべてのタスク・ワークフローはコミット・push をこのスキルの手順で行う。

- **背景**: コミットの直接実行を許すと、全ファイル一括ステージによる巻き込み（他セッションの作業・クレデンシャル・副産物）、AI 生成を示すフッターの混入、直前コミットの書き換えが起きる。push も、未コミットの取り残しやレポートの md / HTML の不同期のまま飛ぶ。操作を提供コマンドに寄せ、その正しい使い方を 1 か所に置きたい。
- **目的**: 小さく分かれた読めるコミットが規約どおりのメッセージで積まれ、push が常に前チェックを通った状態で行われ、チェックを飛ばした場合はそれがレビュアーに見える状態を作る。
- **スコープ**:
  - 含む: コミットの手順（対象の確認・まとまりの判定・除外・メッセージ生成・提供コマンドの実行）、メッセージ規約、push の手順（前チェック・未充足時の対処・意図的スキップの記録）、失敗時の振る舞い
  - 含まない: 提供コマンドの実装と検知・拒否の仕組み（フックの要件・仕様）、push 前チェックの項目の定義（仕様書）、コミットのタイミングの判断（各タスクの手順）

---

## ユーザーストーリー

**[As a]** AI の変更をレビューする開発者として、

**[I want]** コミットが論理的なまとまりごとに規約どおりのメッセージで分かれ、push は常に前チェックを通っていてほしい。

**[So that]** 差分が読め、巻き込み事故（秘密情報・他作業のファイル）が仕組みで防がれ、チェックの省略が隠れないため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When コミットするとき、Shall スキルはコミット対象のファイルを明示して提供コマンドに渡さなければならない（全ファイルの一括ステージは使えない）。対象は自分がこの作業で作成・変更したファイルだけとし、身に覚えのない変更を含めてはならない。
- When コミット対象を決めるとき、Shall スキルは変更内容から prefix（Conventional Commits + `ai-asset`）と論理的なまとまりを判定し、異なるまとまりが混ざっているときは複数のコミットに分けなければならない。
- When コミットメッセージを作るとき、Shall 件名は `<prefix>: <日本語の説明>` の 1 行で「何を」「どう」変えたかが分かる形にし、AI の生成物であることを示すフッターや生成モデル名を含めてはならない。
- When 提供コマンドがクレデンシャル類・開発の副産物を自動で除外したとき、Shall スキルは除外されたファイルの一覧をユーザーへの報告に含めなければならない（黙って落とさない）。
- When push するとき、Shall スキルは提供コマンド経由で行い、push 前チェック（未コミットの変更・作業中のチケット・レポートの md と HTML の同期・draft 解除後の作業領域、など仕様で定める項目）の結果に従わなければならない。未充足なら push されず、伝えられた理由を解消してから再実行する。
- When コミット・push が成功したとき、Shall スキルは何をコミットしたか（件数と要旨）と push の結果を呼び出し元の作業ログまたは報告に残さなければならない。

### 代替フロー

- If 変更が複数の prefix・まとまりにまたがる場合、Then スキルはまとまりごとに対象ファイルを分けて順にコミットしなければならない（1 コミット = 1 まとまり）。
- If push 前チェックの項目を意図的に飛ばす必要がある場合、Then スキルは飛ばす項目と理由を、MR の差分としてレビュアーに見える形で記録してから飛ばさなければならない（レビュアーに見えない無効化はできない）。
- If コミット対象に他セッション・他作業の変更が混ざっている場合、Then スキルはそれらを対象に含めず、自分のファイルだけをパスで指定しなければならない。

### 例外フロー

- If `git` のコミット・push を直接実行して機構に拒否された場合、Then スキルは伝えられた提供コマンドとこのスキルの手順でやり直し、拒否の迂回（フックの無効化・検知を避ける書き方）を試みてはならない。
- If コミット対象が 1 つも無い場合、Then スキルはコミットせず、その旨を報告しなければならない（空コミットは提供コマンドが明示的に許す場面 — MR 作成時の差分作りなど — に限る）。
- If コミットや push が失敗した場合、Then スキルは自動でロールバック（reset 等）せず、状況を報告して判断を仰がなければならない。
- If コミット時の検査（フック）が失敗した場合、Then スキルは検査の無効化で通さず、原因を直してから再実行しなければならない。
- If 直前のコミットに誤りが見つかった場合、Then スキルは書き換え（amend）ではなく訂正の新規コミットで直さなければならない。

### メッセージと除外の規約

- When prefix を選ぶとき、Shall Conventional Commits の一覧に `ai-asset`（`.claude/` 配下の AI が読むアセットの変更。スクリプト等のテストを持つ実装コードは除く）を加えた中から選ばなければならない。
- When 除外リストに無い新種の副産物を見つけたとき、Shall スキルはそれをコミットに含めず、除外リストと `.gitignore` への追加を改善候補として作業ログに残さなければならない。

### 他のスキル・機構との整合

- When タスク・ワークフローのスキルがコミット・push の手順を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。
- When コミットのタイミング（チケットの状態変更時・成果物の節目）を決めるとき、Shall 呼び出し元のスキルの手順に従い、このスキルは 1 回のコミット・push の作法だけを担わなければならない。

---

## 前提条件

- コミット・push の提供コマンドと、直接実行を拒否する機構が導入されていること
- Git リポジトリで、リモート（origin）が設定されていること

---

## 制約条件

- **技術的制約**: 直前のコミットの書き換え・検査の無効化・全ファイルの一括ステージはできない（提供コマンドが提供しない）
- **ビジネス的制約**: コミット履歴は人間がレビュー・追跡に使うもの。メッセージは日本語で、読み手は人間とする
- **外部的制約**: 検知・拒否・除外の実装はフックと仕様書が正。このスキルは使い方を標準化する

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | コミット件名から変更の種類と内容が分かり、push 前チェックのスキップは MR の差分から辿れる |
| 一貫性 | どのスキルから使っても同じ prefix 一覧・同じメッセージ規約・同じ除外リストが適用される |
| 安全性 | クレデンシャル類は除外リストで常に落ち、除外の事実が必ず報告される |
| 冪等性 | 同じ操作の再実行で履歴が壊れない（失敗時は自動で巻き戻さない） |
