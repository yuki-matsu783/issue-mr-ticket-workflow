アプリの成果物の置き場を apl/<アプリ名>/ に切り直し、設計文書を書く機構（ルール・共通ステップスキル・要件書テンプレート・許可範囲設定）をそれに対応させた。既存の VS Code チケットボード拡張のソース 18 ファイルと設計文書 7 ファイルも新しい置き場へ移し、機構内の参照を更新した。issue の受け入れ条件 11 件はすべて満たし、機械的検査は 3 系統すべて通っている。人間レビューの代わりにフェーズごとに敵対的レビューを 1 回ずつ実施し、指摘は 1 件も取り下げずに対応した。

◆特に見てほしい

判断に困っている

  • 許可範囲（scope-limits.json）の割り方 — design / design-feedback が apl/*/docs/、implementation が apl/*/src/ apl/*/test/ と app ルート直下の列挙
  • apl/*/* の広すぎた許可を列挙に変えた件 — アプリルート直下に置きたいファイルが将来増えたときの追随の手当
  • DDR の frontmatter に status / superseded_by / supersedes / superseded_scope を導入した件 — 語彙を 3 値に固定してよいか

◇承認が欲しい

方針は決めた

  • アプリ向け仕様書の 7 番目の節を「画面・出力の構造」に一般化した件（DDR i0020-04）
  • commands.build-test にアプリの npm --prefix 3 本を足した件と、npm install を意図的に外した理由
  • 別 issue に送った 5 件（#29〜#33）の切り方

・細かいレビューは不要

ほぼ確実

  • 拡張のビルド設定とパス解決 — クリーンな作業ツリーで npm ci → compile → test を通し 47 件 pass を確認済み
  • 旧置き場の残存 — git ls-files で 0 件を確認済み
  • HTML ビューの形式 — check-html.sh の 7 項目をすべて通過済み

確かめられなかったこと（この結果が言っていないこと）

  • フックが settings.json に未登録（#9）のため、許可範囲の判定は実運用では走っていない。今回の設定変更が実際に効くかは #9 の完了後にしか確かめられない
  • 既存の要件定義書 46 件が新しい形（mermaid・規約節・issue の受け入れ条件との対応）に追随していない（#8）。遡及適用はルール上も求めていない
  • 設計文書の形の機械的検査は issue #24 に寄せた。#24 のスコープ外である仕様書の形の検査をどこで担うかは決めていない

実施条件（測った対象・環境）

  • マージは行わない（CLAUDE.md の規定）。draft の解除までで止める
  • 人間レビューの代わりに、フェーズごとに敵対的レビューを 1 回ずつ実施し、その対応をもって承認として扱った（利用者の指示）
  • GitHub 操作は gh CLI が使えないため GitHub MCP を用いた
  • 10-task-* スキル本体と work-boundary.sh / merge-prep.sh / finalize.sh が無いため、対応する仕様書の手順どおりメインエージェントが手で実施した

設計への反映

  1. アプリの成果物は apl/<アプリ名>/ をルートに src/ test/ docs/ とビルド設定を置く。設計文書は docs/00_requirement 10_spec 20_ddr 90_glossary の 4 つ
  2. 許可範囲は design / design-feedback = apl/*/docs/、implementation = apl/*/src/ apl/*/test/ とアプリルート直下の列挙。アプリルートを丸ごと許可しない
  3. 設計文書を書く共通ステップは <設計文書ルート> を最初に決め、渡されなければ推測せず呼び出し元に確かめる
  4. アプリ向け仕様書は機構と同じ 10 節固定。該当が無い節も「なし（理由）」で残す
  5. アプリのエラー識別子はそのアプリの仕様書が台帳を兼ねる。機構の台帳（フック共通仕様 §6）には登録しない
  6. DDR の置き換えは frontmatter の status（置き換え済み / 一部置き換え済み / 廃止）と superseded_by / supersedes / superseded_scope で表す
  7. commands.build-test には依存導入とコンパイルまで列挙する。npm install は package-lock.json を書き換え得るので入れない

想定と異なった点

計画時の見込み実際どう扱ったか
apl/*/* は * が / を跨がないので安全アプリルート直下の任意のファイル（CLAUDE.md・.gitignore を含む）が無確認で書けた。判定順 (2) の common.protected は type allow が当たると飛ばされる許可を 6 ファイルの列挙に変え、リポジトリルートでの扱いと揃えた（フェーズ 4）
設計文書の移動は implementation の 1 チケットで済むimplementation は apl/*/docs/ を deny しており、design 側は apl/*/src/ を deny する。どの種別も両方を動かせないソースをフェーズ 4、設計文書をフェーズ 6 に分け、旧置き場の削除は判定順 (7) の確認で通した
節名の改名は見出しの検索で足りる同じ仕様書の対応表 6 か所の略記と render.ts のヘッダ 1 行が旧名のまま残った。DDR の「影響」に事実と異なる断言を書いていた波及 7 か所を直し、DDR i0020-04 の影響を書き直した（フェーズ 6）
status に 一部置き換え済み と書けばよいルールが定義していた語彙は 置き換え済み / 廃止 の 2 つだけで、定義の無いキーと値を先に使ってしまった要件書 2 本とルール 2 本に 3 値と 3 キーを定義してから使う形に直した
commit.sh で全コミットを作れる親ディレクトリごと消えた削除だけのコミットは git add が受け付けず、ファイル無しの起動も拒否される2 コミットだけ git commit を直接使い、コマンドが担う検査を手で満たして作業ログに記録し、#31 を立てた
