# i0009-66. 4c プローブは記録の 10 キー固定と業務条件のために別経路で仕込む

## 背景

フェーズ 4c は「登録済みの本物のフックが受け取る入力」を実測するフェーズである。素直に考えれば既存の記録（`logs/hooks/decisions.jsonl`）を読めば済むはずだった。実際には 2 つの理由で読めない。

1. **`decisions.jsonl` は 10 キー固定**（`ts` / `session_id` / `hook` / `event` / `decision` / `id` / `tool` / `target` / `ticket` / `note`。共通仕様 §5）。T2〜T7 が知りたい `permission_mode` / `tool_response.status` / `tool_response.agentId` / `agent_type` / `model` / `source` / `run_in_background` を入れる場所が 1 つも無い。§5 の表は正なので、実測のために恒久的にキーを増やすのは筋が悪い
2. **`systemMessage` を出す経路が業務条件に縛られている**。T9（`systemMessage` が PreToolUse で人間に届くか）を測るには `PreToolUse:Agent` で実際に `systemMessage` を出す必要があるが、WF801 / WF803 は `subagent_type` が `task-executor` かつチケットの `executor` が `main` 以外のときにしか発火しない。`.claude/agents/` は空で `task-executor` の実装が無いので、**通常の操作では 1 度も出ない**

## 決定

- 実測用のプローブを `lib/probe-4c.sh` として**別ファイル**に置き、環境変数 `WORKFLOW_PROBE_4C=1` のときだけ有効にする。既定では副作用ゼロ
- プローブは 2 つのことをする
  - (a) 対象 7 フィールドの**値**と、その他のキーの有無・型を `logs/hooks/probe-4c.jsonl` に落とす
  - (b) `subagent-start-check` が `Agent` の呼び出しで**業務条件によらず** `systemMessage` を 1 つ出す
- 出力は `hc_append_jsonl` 経由にする（伏字化と 4 KB 切り詰めを得るため。並列のフックが 4 KB を超える行を書くと JSONL が割れる）
- プローブの呼び出しは**入力の読み込み直後・早期 return より前**に置く（`session-start` は `boundary.sh` 不在で無出力終了する経路があり、後ろに置くと 1 行も残らない）
- 実測が終わったら**プローブごと撤去する**。撤去の完了は `grep -rn 'WORKFLOW_PROBE_4C\|probe-4c' .claude` が 0 件であることで確かめる
- 逸脱が 2 件あることを承知で行う。`rules/logger.md` の「値ではなく有無・長さを書く」からの逸脱（値を落とすのは上記 7 フィールドに限る）と、§5 の `logs/` の表に無いパスを一時的に増やすこと。どちらも撤去で戻す

## 理由

- **測るための仕掛けを本番の記録の形に混ぜない**。10 キーは機械が読む契約で、実測の都合で増やすと戻すときに読み手が壊れる。逆に増やしたまま放置されると、記録の形が「なぜこのキーがあるのか」の分からないもので膨らむ
- **業務条件から切り離さないと、測れないものを「測って出なかった」と誤読する**。T9 で `systemMessage` が観測されなかったとき、それが「届かない」なのか「そもそも出していない」なのかを区別できない。プローブ (b) が無条件に 1 件出すことで、**負のコントロール**（`probe-4c.jsonl` に該当行がある = フックは起動して出力もしている）が成立し、観測の欠如を結論として使えるようになる
- **環境変数にしたのは AI が自分で有効にできないため**（§4）。有効化は人間がセッションを起動するときの操作で、AI が測りたいときに勝手に記録を増やせない。Bash ツールで前置しても外側のフックプロセスには届かない
- **一時的な逸脱は、撤去の証跡とセットなら受け入れられる**。恒久の仕様変更ではなく、期限（0031 の実測の終了）と検査手段（`grep` 0 件）が最初から決まっている。実際、撤去のときに `SE-T06` の前半の検査がプローブの assertion に寄生していたことが分かり、本来の検査を書き直せた

## 却下した案

- **`decisions.jsonl` に測定用のキーを足す**: §5 の表を実測のために変えることになり、戻し忘れが機構の記録の形として残る
- **`note` に JSON を詰め込む**: 10 キーは維持できるが、`note` が人間向けの自由文という性質を失う。4 KB の切り詰めで先に落ちるのも `note` なので、測りたい値が消える
- **業務条件を満たす状況を作って測る**（`.claude/agents/` に `task-executor` を実装し、チケットの `executor` を書き換える）: 測定のために正史のアセットを増やし、測定のために状態を偽装することになる
- **プローブを本体のフックに `if` で埋め込んだまま残す**: 既定で副作用が無くても、ホットパスに分岐と `source` が 1 本ぶん残る。撤去を前提にしたほうが「消し忘れ」を `grep` で検査できる
- **`--output-format stream-json` のヘッドレス実行だけで測る**: 対話 UI で人間に届くかという問いには答えられない（実際、この 2 つの面で結果が分かれた）

## 影響

- `10_spec/フック共通仕様.md` §5（`logs/` の表。プローブのパスは恒久の記載にしない）・§12（実測で 9 項目すべてが決着した）
- 実装は 0029 で仕込み、0031 の実測後に撤去済み（`grep` 0 件を確認）
- 関連: `i0009-52`（通知しない場合も skip を記録し縮退時は自分で判定する）・`i0009-54`（`systemMessage` の実測を T9 として登録した）・`i0009-71`（T9 が外れた結果の縮退）
- **今後の実測へ**: 本番の記録の形を変えずに測りたいときは、環境変数で切る別ファイルのプローブ + 負のコントロール + 撤去の `grep` 検査、という同じ型を使う
