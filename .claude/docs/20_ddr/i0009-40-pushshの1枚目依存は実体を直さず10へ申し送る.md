# i0009-40. `push.sh` の 1 枚目依存は実体を直さず #10 へ申し送る

## 背景

`i0009-18` は G8（作業中チケットが 2 枚以上のときの扱い）に対し「提供コマンドの実体は直さない / 検知は `workflow-guard` の WF207 が担う / **#10（3/3）への申し送りは出さない**」と決めた。その根拠として、残るリスクを「`run-tests.sh` が誤ったチケットの `allow.ops` で判定し得るが、影響はテストを走らせるかどうかに閉じており、**作業領域外への書き込みやリモート操作には及ばない**」と書いた。

ワーク境界のレビューで、この根拠が実体と食い違うことが分かった。

```
push.sh:98   ticket="${doing[0]}"                          # 名前順の 1 枚目
push.sh:99   ops="$(fm_list "$ticket" allow.ops ...)"
push.sh:100  if grep -qx -- "remote-write:push" <<<"$ops"; then  # → 項目 2 を通す
```

`push.sh` の push 前チェック 項目 2 も 1 枚目だけを読む。作業中が 2 枚のとき、**push を宣言していない側のチケットで作業していても、1 枚目の宣言で push が通る**。影響はリモートに及び、`i0009-18` の根拠は成り立たない。

## 決定

- `i0009-18` の理由と影響を訂正する（「リモート操作には及ばない」は偽）
- **この issue では実体を直さない**。提供コマンド（`push.sh`）の修正は #9 のスコープ外（フック本体と `settings.json` 登録が対象）
- **#10（3/3）への申し送りとして残す**。全体計画に「#10 への申し送り」の表を設け、完了処理の issue コメント（承認⑥）に含める
- `i0009-18` の「実体の修正は**不要**」は `ticket.sh` / `run-tests.sh` に限る

## 理由

- **根拠が偽のまま決定だけを残さない**。`i0009-18` の決定（実体を直さない）はスコープの都合として今も妥当だが、「直さなくてよい理由」が偽なら、後から読む人が同じ判断を再現できない。決定を保ち、根拠を訂正するのが正しい直し方
- **リスクの実質は小さいが、ゼロではない**。2 枚以上は `ticket.sh start` を通らない経路（git 操作での復元・手動移動・機構の破損）でしか作れず、WF207 が提供コマンド以外を止めている。それでも `push.sh` は提供コマンドなので WF207 を通り、push はリモートへの取り消しにくい操作である
- **申し送りは安い**。3 行の修正を #10 で行うだけで閉じる。ここで「不要」と書いてしまうと、#10 の計画がこの穴を知らないまま進む

## 却下した案

- **この issue で `push.sh` を直す**: 提供コマンドの実体は #9 の対象外で、`20-common-step-commit-push` の実装とテストに波及する。フック本体 11 本と登録という本題から外れる
- **`i0009-18` の決定ごと覆して提供コマンドに件数検査を足す**: `i0009-18` の「同じ判定を 4 か所に置かない」は今も妥当。#10 で直すのは `push.sh` の項目 2 が**どのチケットを読むか**であって、件数検査を足すこととは限らない（全枚の宣言を見る形でも閉じる）
- **WF207 に `push.sh` も止めさせる**: WF207 が提供コマンドを通すのは復旧のためで、2 枚を 1 枚に戻す作業のあとに push できなくなると詰む
- **申し送りを結果報告にだけ書く**: `wip/30_reports/` は完了処理のリセットで消える。#10 に届く経路（issue コメント）に載せる必要がある
