    WF801 は systemMessage + additionalContext の 2 経路。17 行は維持する ✕問題 根拠: 公式 hooks.md:988・:972・:926、境界レビュー S1

  2. 2

    MCP は宣言の有無だけを強制し、種別は強制しない △注意 根拠: 境界レビュー R4、要件 workflow-guard のリモート書き込みの行

    mcp__.* を matcher に持つのは workflow-state-guard の 1 行だけで、workflow-entry と workflow-guard は MCP を含まない。gh / glab が使えない環境で MCP に切り替えた瞬間（外部委任モードは実際にこれを想定している）、mcp__github__create_issue などが WF101 も WF206 も通らずに素通りする。決定（強制する側）: workflow-entry の matcher に mcp__.* を足す — 宣言の有無の判定にはツールの種類が要らないので、分類できなくても安く確実に効く（WE-T11 を新設）。決定（強制しない側）: workflow-guard には足さない — MCP のツール名はサーバが定義するもので remote-write:<種別> に機械的に対応づけられず、パターンを書くほど当たらない名前に対して「守っている」という誤った安心が生まれる（redact と同じ構造の問題）。誤分類で正当な操作を止めると外部委任モードが使えなくなる。§13 と要件に理由付きで書いた。

  3. 3

    workflow-state-guard は MCP の draft 解除だけを見て、他は許可する ◎良 根拠: 境界レビュー R5、workflow-state-guard.md 制御方式

    state-guard の制御方式は「書き込みツール（対象パス）」「実行ツール（コマンド列）」「入力不正 → deny WF309」の 3 分岐しか無く、MCP ツールを受け止める分岐が無かった。mcp__github__get_issue は file_path も command も持たないので入力不正に落ち、許可カーブアウトの条件（「対象パスが読める」）も満たせず、すべての MCP 呼び出しが WF309 で拒否される。決定: 制御方式に MCP の分岐を新設（入力不正の 1 つ前）。mcp__*pull_request* / *merge_request* の draft:false → WF304、それ以外の MCP は許可。理由は「このフックが守るのは進行状態ファイル・置き場・draft 解除の 3 つで、MCP ツールがそのうち触り得るのは draft 解除だけ」。拒否側に倒す原則は「保護対象に関わり得るのに判断できない」場合のもので、関わり得る範囲が静的に分かるなら適用対象ではない。

    実測への依存: 無し（判定の分岐の設計）

    根拠を見る（読んだ箇所と出力）
