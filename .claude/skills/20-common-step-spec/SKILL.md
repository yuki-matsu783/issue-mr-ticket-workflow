# 20-common-step-spec — 要件を全件カバーする、推測なしに実装できる仕様を書く

対応する要件定義書が無い仕様書を先に作らない。要件側の誤り・不足を仕様側の辻褄合わせで吸収しない（要件の修正を呼び出し元に返す）。共有される内部構造は 1 つの仕様書に置き、他は参照する。経緯・変更履歴を本文に書かない。「関連するドキュメント」「レビュー記録」の節を置かない。未決事項を黙って省略しない（TBD は理由付きで明示）。書く内容の合意は呼び出し元が担う。

- 要件: `.claude/docs/00_requirement/skills/20-common-step-spec.md`
- 仕様（正。種別ごとの節構成・エラー識別子の規則・eval ID SC-E01〜03）: `.claude/docs/10_spec/skills/20-common-step-spec.md`

## 手順

1. **設計文書ルートと要件の存在確認**: 対象の系統で `<設計文書ルート>` を決める（AI アセットなら `.claude/docs/`、アプリならアプリルート `apl/<アプリ名>/` の `docs/`）。渡されていなければ**推測せず**呼び出し元に確かめる。`<設計文書ルート>/00_requirement/<種別があれば 種別/><対象名>.md` があることを確認し、無ければ「要件が先」として呼び出し元に返す。置き場は `<設計文書ルート>/10_spec/<要件と同じ相対パス>.md`（要件と同名 1:1）。ルール（`00_requirement/rules/*.md`）には仕様書を作らない（機械が読む表の形式は、読む側のフックの仕様書へ）
2. **対応表の左列を先に作る**: 要件の受け入れ基準を**全件**書き出し、「要件との対応」表の左列（`メイン: 〜` / `代替: 〜` / `例外: 〜` / `整合: 〜`）を先に埋める（書き終わりの検査に使う）
3. **種別の節構成に沿って書く**（frontmatter は要件書と同じ項目で `type: spec`）。粒度の基準は「実装・テストが追加の推測なしに作れる」こと: コマンドの名前と引数・入出力・判定の順序と条件・データの形式・エラー識別子と文言・ファイルとテンプレートの配置

   | 種別 | 節構成 |
   |------|--------|
   | スキル | 概要・禁止事項 / 呼出条件 / IN / OUT / IN / OUT サンプル / 処理フロー（手順が薄い場合は省略可）/ OUT ひな形 / 参照ナレッジ / Script 処理（テスト観点含む）/ 要件との対応 |
   | エージェント | 概要・禁止事項 / 呼出条件 / IN / OUT / IN / OUT サンプル / ツール権限 / 定義ひな形 / 参照ナレッジ / 要件との対応 |
   | フック | 概要・禁止事項 / 呼出条件（イベント・matcher・登録）/ 入出力 / 制御方式 / エラー識別子とメッセージ / 回復手順 / 記録（logs/）/ テスト観点 / 要件との対応 |
   | アプリ | 概要・禁止事項 / 配置 / 起動と入口 / モジュール構成 / データの形 / 処理フロー / 画面・出力の構造 / 不備の識別子とメッセージ / テスト観点 / 要件との対応（10 節固定） |
   | ルール | 仕様書を作らない |

   - スクリプトを持つスキルは Script 処理にサブコマンド・判定順・エラー識別子・テスト観点（テスト ID `<接頭辞>-T<2 桁>`）を書く。スクリプトが無ければ「なし」と理由を書き、テスト観点は eval ID（`<接頭辞>-E<2 桁>`）の表で定義する（実装計画がテスト ID の無いアセットを起こせないため）
   - エラー識別子: フックは `WF` + 3 桁（百の位がフック、下 2 桁が種類。`x09` は判定不能、`x9x` は情報）、スキルのスクリプトは種別の接頭辞（`TK` / `CP` / `RV` / `FN` / `BD` など）。識別子と回復の案内を 1:1 で対応させる。採番台帳は `.claude/docs/10_spec/フック共通仕様.md` §6 が正で、新しい接頭辞・範囲は**そこに追加してから**使う
   - アプリの識別子: `<2 文字の接頭辞>` + 3 桁（例: チケットボード拡張の `TB001`）。**そのアプリの仕様書「不備の識別子とメッセージ」節が台帳を兼ねる**ので、機構の採番台帳（`フック共通仕様` §6）には登録しない。新しい接頭辞を決めるときは `apl/*/docs/10_spec/` を検索し、既存のアプリと重ならないことを確かめてから使う
   - アプリの「画面・出力の構造」節は 10 節の 1 つとして**必ず置く**。画面（Webview / TUI）や定形の出力（レポート・生成物）を持たないアプリは「なし（画面・定形出力を持たない）」と 1 行書いて節を残す（省くと「持たない」と「書き忘れ」を区別できない）
4. **TBD の明示**: 決められない箇所は TBD として「何が未決か・決めるために要る情報」を書く（黙って省略しない）
5. **対応表の右列と検査**: 右列（実現箇所 = 処理フロー n / OUT ひな形 / 禁止事項 など）を埋め、実現箇所の無い要件（実装漏れ）と要件の無い節（過剰仕様）が無いことを確認する。対応表の行数が要件の受け入れ基準の数と一致すること
6. **更新**: 正史を直接書き換える。要件側の変更が先にあることを確認する（仕様が要件より先に変わらない）。要件側に誤り・不足があれば仕様で吸収せず、要件の修正を呼び出し元に返す

## 参照

- テンプレート: 持たない（種別ごとの節構成が上の表で固定され、既存の仕様書が手本になるため。書き出しの揺れが目立てば `assets/` にテンプレート化する）
- 書き方の手本: `.claude/docs/10_spec/skills/20-common-step-ticket.md`（スクリプトを持つスキル）、`.claude/docs/10_spec/skills/20-common-step-issue.md`（スクリプトを持たないスキル）、`.claude/docs/10_spec/hooks/20-PreToolUse/workflow-guard.md`（フック）
- エラー識別子・テスト ID・eval ID の採番台帳: `.claude/docs/10_spec/フック共通仕様.md` §6
- 要件と仕様の線引き（外部の観察者基準）: `20-common-step-requirement`
- 節構成の決定の経緯: DDR `i0001-29`
- 呼び出し元: `10-task-design-exec` / `10-task-ai-asset-design-exec`（内容の合意と人間レビュー）

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 対応する要件定義書が無い | 仕様書を作らない。「要件が先」として呼び出し元に返す |
| 要件の受け入れ基準に対応表の行が無い（実装漏れ）/ 要件の無い節がある（過剰仕様） | 節を足すか削る。要件に無い振る舞いが要るなら要件の追加を呼び出し元に返す |
| 要件側に誤り・不足がある | 仕様で辻褄を合わせない。要件の修正箇所を呼び出し元に返す |
| 決められない箇所がある | TBD と、何が未決か・決めるために要る情報を書く |
| 新しいエラー識別子・テスト ID・eval ID が要る | 先に `フック共通仕様` §6 の台帳に接頭辞・範囲を追加してから使う |
| 新しいアプリの識別子の接頭辞が要る | 機構の台帳には登録しない。`apl/*/docs/10_spec/` を検索して衝突が無いことを確かめ、そのアプリの仕様書「不備の識別子とメッセージ」節に定義する |
| アプリが画面・定形出力を持たない | 「画面・出力の構造」節を省かない。「なし（画面・定形出力を持たない）」と 1 行書いて節を残す |
| 呼び出し元が設計文書ルート（AI アセットかアプリか）を渡していない | 推測して書き始めない。どちらの系統かを呼び出し元に確かめる |
| 共有する内部構造を複数の仕様書に書きそうになった | 1 つの仕様書に置き、他は参照にする |
| ルールの仕様書を求められた | 作らない。機械が読む表の形式は、読む側のフックの仕様書に書く |
| 「関連するドキュメント」「レビュー記録」「変更履歴」を求められた | 置かない。理由を添えて返す |
