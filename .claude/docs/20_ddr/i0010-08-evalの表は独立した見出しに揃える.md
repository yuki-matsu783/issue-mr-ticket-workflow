# eval の表は独立した見出しに揃える

## 背景

`20-common-step-spec` 仕様は「スキルとエージェントは種類を問わずテスト観点（eval）節を持ち、機械テストは `Script 処理` の中、eval は独立した節に置く」と定めている。ところが既存の仕様書は 2 通りに分かれていた。この issue で新設した 19 本は `## テスト観点（eval）`、先に書かれた 5 本（`20-common-step-ai-asset-creator` / `20-common-step-feature-mr` / `20-common-step-issue` / `20-common-step-requirement` / `20-common-step-spec`）は `## Script 処理` の下の `### テスト観点（eval）` である。

同じ種類の情報が文書によって別の階層にあると、読む側も機械的に抜き出す側も置き場を 2 通り想定することになる。

## 決定

- eval の表の見出しは **`## テスト観点（eval）`（`##` の階層）に統一する**
- 既存の 5 本を `###` から `##` へ上げる
- `20-common-step-spec` 仕様の節構成の規定にこの階層を明記する

## 理由

- **スクリプトを持たないアセットでは親見出しが成立しない**。5 本はどれも `## Script 処理` の本文が「なし。<理由>」の 1 行だけで、その下に eval の表がぶら下がっている。eval は Script 処理の一部ではないので、この形だと「スクリプトが無いのに Script 処理の中に表がある」という読み方になる
- **機械テストと eval を別の節に置く理由が階層に表れる**。機械テストはスクリプトの入出力を固定するもので `Script 処理` に属し、eval はスキルの手順どおりの振る舞いを見るもので、スクリプトの有無と関係が無い。同じ `##` に置けば、両者が並列であることが見出しから分かる
- **昇格しても文脈が切れない**（5 本すべてで確認した）。`## Script 処理` の中身は「なし。<理由>」の 1 行で完結しており、eval の表がそこから出ても、前の節に残る文章は自足している

## 却下した案

- **19 本を `###` に下げて 5 本に合わせる**: スクリプトを持たないアセット（エージェント 2 本を含む）では親となる `## Script 処理` 自体が無いか「なし」の 1 行で、下げる先が無い。19 本を直す量も 5 本より多い
- **どちらでもよいことにして仕様に書かない**: 揺れが残り、次に書く人がまた迷う。節構成を固定することが `20-common-step-spec` の役目である
- **`## テスト観点` に機械テストと eval の両方を集める**: 機械テストはスクリプトの記述（引数・終了コード・ログ）と一緒に読むほうが分かりやすく、`Script 処理` から切り離すと参照が増える

## 影響

- 5 本の仕様書の見出しを `### テスト観点（eval）` から `## テスト観点（eval）` に変える
- `10_spec/skills/20-common-step-spec.md` の節構成の規定に階層の指定を追加する
