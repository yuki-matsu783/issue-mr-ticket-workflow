◆特に見てほしい

判断に困っている

  • f5（△注意）: D5 で ops 上限を広げないと決めたこと。0014 で web を強制しないと決めた以上、上限に足しても機構の振る舞いは変わらない。それでも足さないのは「設計中に外部を見たくなったら調査タスクを起こす」圧力を残すためで、運用の窮屈さと引き換えになっている
  • f6（△注意）: D6 で shellcheck を CI に載せないと決めたこと。「記録を省略できない」だけで実効性を担保しているので、レビューで省略の連続を見つけられなければ静的検査が形骸化し得る

    D5: ops 上限を広げず、外部が必要なら調査タスクを起こす △注意 根拠: 0014 の DDR i0009-12（web は強制しない）、0012〜0014 の実績

    investigation 以外の実施タスク（design / ai-asset-design / design-feedback / implementation）は ops に web を持たない。決定: 広げない。scope-limits.json の実体も変えない。0014 で web は機構が強制しないと決めたので、上限に足しても機構の振る舞いは変わらず、変わるのは「計画が宣言できるかどうか」だけ。上限に無いことが「まず調査を起こせ」という設計の圧力になる。要件（メインフロー D）に「設計や実装のタスクが外部の情報を必要としたときは、外部への問い合わせを宣言できる範囲を広げるのではなく、調査のタスクを起こして結論を持ち帰る」を 1 行足した。実績として、この issue の 0012〜0014 は 0007 の調査結果を参照することで済んでおり、しかも根拠が調査結果として残った。

  6. 6

    D6: shellcheck を CI に載せず記録を必須にする △注意 根拠: CLAUDE.md の制約条件（リポジトリ設定の変更禁止）、run-tests.sh の責務

    決定: CI で回さない。run-tests.sh にも組み込まない。処理フロー 5 のローカル検査を続け、実施の有無の記録を省略できないものにした（「実行した」か「不在で省略した」のどちらかを必ず作業ログに書く）。理由は 3 つ: (1) CI 設定の変更はリポジトリの設定変更に当たりスコープ外、(2) 機構が守るのは「AI が作業している最中に止める」ことで CI は別レイヤ、(3) run-tests.sh に混ぜるとテストランナー（振る舞い）と静的検査（形）の責務が混ざり、shellcheck 不在の環境で TR005（環境不備・終了 2）になってテストを回せない環境が増える。要件の非機能（テスト容易性）に「静的検査は作成・変更のたびにローカルで行い、実施の有無を作業ログに残す（自動実行の仕組みを外部のサービスに置かない）」と書いた。

    実測への依存: 無し（方針まで。CI 設定は変えていない）

却下: GitHub Actions で shellcheck を回す
      → リポジトリ設定の変更に当たる。必要になったら別 issue
