# 20-common-step-spec スキル 仕様

## 概要・禁止事項

仕様書の作成・更新の共通ステップの内部仕様。対応する要件は [00_requirement/skills/20-common-step-spec.md](../../00_requirement/skills/20-common-step-spec.md)。

種別ごとの節構成の**正史はこの仕様書**（決定の経緯は DDR `i0001-29`）。書く内容の合意は呼び出し元が担う。

禁止事項:

- 対応する要件定義書が無い仕様書の先行作成
- 要件側の誤り・不足を仕様側の辻褄合わせで吸収すること（要件の修正を呼び出し元に返す）
- 共有される内部構造の重複定義（1 つの仕様書に置き、他は参照）
- 経緯の本文への記載・変更履歴の記録（要件書と同じ方針）
- 「関連するドキュメント」「レビュー記録」の節
- 未決事項の黙った省略（TBD は理由付きで明示）

## 呼出条件

- `10-task-design-exec`・`10-task-ai-asset-design-exec` が仕様書を作成・更新するとき

## IN / OUT

| IN | OUT |
|----|----|
| 対応する要件定義書（存在必須）、実現方法の設計内容（呼び出し元で合意済み） | `.claude/docs/10_spec/<要件と同じ相対パス>.md`（要件と同名 1:1）。ルールには作らない |

## IN / OUT サンプル

- `00_requirement/skills/20-common-step-ticket.md` → `10_spec/skills/20-common-step-ticket.md`
- `00_requirement/hooks/20-PreToolUse/workflow-guard.md` → `10_spec/hooks/20-PreToolUse/workflow-guard.md`
- ルール（`00_requirement/rules/*.md`）→ 仕様書なし（機械が読む表の形式は、読む側のフックの仕様書へ）

## 処理フロー

1. 対応する要件定義書の存在を確認する（無ければ要件が先であることを呼び出し元に返す）
2. 要件の受け入れ基準を**全件**書き出し、「要件との対応」表の左列を先に作る（書き終わりの検査に使う）
3. 種別の節構成（下記）に沿って書く。粒度の基準は「実装・テストが追加の推測なしに作れる」こと: コマンドの名前と引数・入出力・判定の順序と条件・データの形式・エラー識別子と文言・ファイルとテンプレートの配置
4. 決められない箇所は TBD として「何が未決か・決めるために要る情報」を書く
5. 対応表の右列を埋め、実現箇所の無い要件（実装漏れ）と要件の無い節（過剰仕様）が無いことを確認する
6. 更新時は正史を直接書き換え、要件側の変更が先にあることを確認する（仕様が要件より先に変わらない）

### 種別ごとの節構成（正史）

| 種別 | 節構成 |
|------|--------|
| スキル | 概要・禁止事項 / 呼出条件 / IN / OUT / IN / OUT サンプル / 処理フロー（手順が薄い場合は省略可）/ OUT ひな形 / 参照ナレッジ / Script 処理（テスト観点含む。スクリプトが無ければ「なし」と理由を書き、テスト観点は eval ID（`<接頭辞>-E<2 桁>`。台帳は `フック共通仕様` §6）の表で定義する — 実装計画が「テスト ID の無いアセット」を起こせないため）/ 要件との対応 |
| エージェント | 概要・禁止事項 / 呼出条件 / IN / OUT / IN / OUT サンプル / ツール権限 / 定義ひな形 / 参照ナレッジ / 要件との対応 |
| フック | 概要・禁止事項 / 呼出条件（イベント・matcher・登録）/ 入出力 / 制御方式 / エラー識別子とメッセージ / 回復手順 / 記録（logs/）/ テスト観点 / 要件との対応 |
| ルール | 仕様書を作らない |

- frontmatter は要件書と同じ項目で `type: spec`
- エラー識別子: フックは `WF` + 3 桁（百の位がフック、下 2 桁が種類。`x09` は判定不能、`x9x` は情報）、スキルのスクリプトは種別の接頭辞（チケット `TK`、コミット・push `CP`、HTML 検査 `RV`、片付け `FN`、切れ目 `BD`）。識別子と回復の案内を 1:1 で対応させる。採番台帳は `10_spec/フック共通仕様.md` §6 が正で、新しい接頭辞・範囲はそこに追加してから使う

## OUT ひな形

テンプレートは持たない（種別ごとの節構成が上の表で固定されており、既存の仕様書が手本になるため）。仕様書が増えて書き出しの揺れが目立てば `assets/` にテンプレート化する。

## 参照ナレッジ

- 要件と仕様の線引き: `20-common-step-requirement`（外部の観察者基準）
- 節構成の決定の経緯: DDR `i0001-29`
- 既存の仕様書（`10_spec/skills/20-common-step-ticket.md` ほか）: 書き方の手本

## Script 処理

なし。対応表の全件性の検査（要件の AC 数と表の行数の突合）は将来の設計文書検査に統合する想定で、それまでは処理フロー 2・5 が担う。

### テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| SP-E01 | 要件定義書がある状態で仕様書の作成依頼 | 種別ごとの節構成に従い、「要件との対応」表が要件の受け入れ基準を全件カバーする | 節構成の一致、対応表の行数と AC 数の一致 |
| SP-E02 | スクリプトを持つスキルの仕様 | Script 処理にサブコマンド・判定順・エラー識別子・テスト観点（テスト ID）を書き、識別子は採番台帳に追加してから使う | テスト ID の存在、台帳との一致 |
| SP-E03 | スクリプトを持たないスキルの仕様 | Script 処理に「なし」と理由を書き、テスト観点は eval ID で定義する | eval ID の存在 |

## 要件との対応

| 要件（受け入れ基準） | 実現箇所 |
|--------------------|---------|
| メイン: 要件と同名で同じ種別ディレクトリに置く（1:1） | IN・OUT、サンプル |
| メイン: frontmatter・要件との対応が読み取れる構成 | 処理フロー 2・5、節構成の表 |
| メイン: 実装・テストが推測なしに作れる粒度 | 処理フロー 3 |
| メイン: 共有する内部構造は 1 か所・他は参照 | 禁止事項 |
| メイン: 更新は正史の書き換え | 処理フロー 6、禁止事項 |
| 代替: 決められない仕様は TBD を明示 | 処理フロー 4 |
| 代替: 要件側の誤りは要件の修正を返す | 処理フロー 6、禁止事項 |
| 例外: 要件が無ければ先に作らない | 処理フロー 1 |
| 例外: 未合意の決定を含めない | 呼出条件（合意済みが IN） |
| 整合: 要件に内部構造を見つけたら移す提案 | `20-common-step-requirement` 処理フロー 4 と対で運用 |
| 整合: 関連ドキュメント・レビュー記録の節を置かない | 禁止事項 |
