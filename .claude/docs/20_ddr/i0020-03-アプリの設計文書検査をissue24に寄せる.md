# アプリの設計文書に対する機械的検査を issue #24 に寄せる

## 背景

`design-docs` と `ai-asset-design-docs` はどちらも「章立て・禁止節の不在・DDR の命名・一覧の生成状態の機械的検査は、設計文書検査（仕様書が定める）に統合する。整備されるまでは……セルフレビューと MR 上のレビューで見る」と将来形で書いており、検査は存在しない。

issue #20 の受け入れ条件 5 は「アプリ配下の設計文書に対する機械的検査の要否が判断され、入れる場合は検査項目が定義されている」で、要否の判断を求めている。同時に issue #24（設計文書検査の実装）が、要件書の章順・節順・図のノード数・識別子の対応・分量を機械的に検査する仕組みを扱っている。

## 決定

- issue #20 では機械的検査を実装しない。設計文書検査は issue #24 に寄せる
- #24 に次の 2 件を申し送る
  1. **対象ルートが 2 つになる**: 検査の対象は `.claude/docs/` と、各アプリの `apl/<アプリ名>/docs/`。#24 の設計は最初から両方を見る形にする
  2. **仕様書の形の検査の担い先**: #24 はスコープ外に「仕様書（`10_spec/`）の形の検査」を挙げている。一方 #20 の動機の 1 つは仕様書の自己矛盾（ある関数を宣言しつつ「提供しない」と書いていた）で、これは #24 の外に落ちる。#24 のスコープを広げるか別 issue を起こすかを別途決める
- 整備されるまでは、`20-common-step-requirement` のセルフレビュー 14 項目と `20-common-step-spec` の「要件との対応」表の全件カバー、および MR 上のレビューが担う。この扱いは両ルールの「テスト・機械的検査」章に既に書かれており、変更しない

## 理由

- **#24 が 1 セットで要求している**: #24 の受け入れ条件は 検査の仕様 / 実行手段 / 既存 45 件への適用 / テスト（正常系・違反ごとの異常系・負のコントロール）/ 両ルールの記述を実在の手段に向ける / セルフレビューからの委譲 の 6 件。#20 の中で一部だけ作ると #24 がそれを作り直すことになる
- **#20 の条件 5 は判断で満たせる**: 条件は「要否が判断され、**入れる場合は**検査項目が定義されている」。入れないという判断とその根拠を残せば満たせる
- **今回の変更が #24 の前提を変える**: 対象ルートが 2 つになるのは #20 の決定の帰結で、#24 が設計を始める前に伝わっている必要がある。申し送りとして残すのが、実装するより確実に効く

## 却下した案

- **章順と禁止節だけの簡易な検査を今回入れる**: 数十行のスクリプトで書けるが、#24 が「未充足を全件列挙して終了コードで区別」「違反ごとの異常系テスト」「負のコントロール」まで求めているため、簡易版は必ず置き換えになる。置き換えられる前提のスクリプトをリポジトリに入れると、#24 の着手時に「既存を活かすか捨てるか」の判断が余分に増える
- **#24 に寄せたうえで #20 の受け入れ条件 5 を「対象外」に変更する**: issue の受け入れ条件を後から緩めることになる。条件の文言は「要否が判断され」なので、判断を残せばそのまま満たせる
- **#24 を待たずに #20 の中で #24 ごと実装する**: #20 の 1 PR が過大になる。#24 は既存 45 件への適用と違反一覧の出力まで含み、別の PR に値する規模

## 影響

- issue #24 に申し送り 2 件を伝える必要がある。伝達はフィードバック計画（フェーズ 5）で issue コメントとして行うか、#24 の本文に追記するかを人間が判断する
- `design-docs` と `ai-asset-design-docs` の「テスト・機械的検査」章は将来形のまま残る。実在の手段を指す形に直すのは #24 の受け入れ条件
