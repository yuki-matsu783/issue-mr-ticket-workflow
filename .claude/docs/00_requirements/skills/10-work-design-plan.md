# 10-work-design-plan スキル

## 概要

設計フェーズの計画ワークの要件を定義する。調査結果レポートの候補と比較軸、issue の受け入れ条件から、**どの設計書を・どんな骨子で書くか**と判断点の結論方針を決めて設計計画書にまとめ、設計チケット群と次のフェーズの計画チケットを起こして設計計画チケットを完了する。設計書そのものは書かない（`10-work-design-exec`）。

- **背景**: 設計を計画なしに始めると、書くべき文書の過不足や受け入れ条件の取りこぼしが設計書を書き終えるまで見えない。調査が並べた候補のどれを採るかも、書きながら決めると根拠が残らない。何を書くか・何を決めるかを先に 1 枚にし、人間が設計に入る前に方向を正せるようにしたい。
- **目的**: 設計書の一覧（新規 / 更新・置き場・骨子）と判断点の結論方針を、受け入れ条件との対応付きでレビュー可能な計画書として残し、1 設計書 = 1 チケットの目安で設計を区切る。
- **スコープ**:
  - 含む: 設計計画書の作成、判断点の結論方針、設計書の一覧と骨子、設計チケット群と次の計画チケットの作成、設計計画チケットの着手から完了まで、「対象なし」の扱い、再開時の扱い、呼び出し元への結果報告
  - 含まない: 設計書の作成（`10-work-design-exec`）、AI アセット（`.claude/` 配下）の設計（AI アセット設計フェーズ）、フェーズ列の決定（`10-work-overall-plan`）、ワークの切れ目の処理（`00-workflow-issue-mr-driven`）、チケットの状態遷移と宣言範囲の強制の仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 設計書が書かれる前に、どの文書がどんな骨子で作られ、調査で並んだ候補のどれをどの根拠で採るつもりかを 1 枚の計画で確認したい。

**[So that]** 方向違いの設計書が書き上がってから直す手戻りを避け、決定の根拠を残した状態で設計に入れるため。

---

## 受け入れ基準（Acceptance Criteria）

### 設計計画書の内容

- When 設計計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、判断点の結論方針（調査結果の候補から採る案と比較軸ごとの根拠。決めきれない点は「設計チケットで結論を書く」と明示）、設計書の一覧（新規 / 更新の別・置き場・各文書の骨子）、受け入れ条件との対応（どの条件がどの設計書の受け入れ基準・テストシナリオに落ちるか）、設計チケットの一覧、判断を保留した点。
- When 設計書の一覧を決めるとき、Shall 対象はアプリ本体の設計文書の置き場（`docs/` 配下。既存の構成があればそれに従う）とし、`.claude/` 配下の文書を含めてはならない（AI アセットの設計は AI アセット設計フェーズで扱う）。
- When 判断点の結論方針を書くとき、Shall 調査結果レポートの根拠と矛盾しない形で書き、調査結果に無い新しい事実を根拠にする場合はその根拠を計画書に添えなければならない。
- When 設計計画書を書くとき、Shall 「これから何をするか」だけを書き、設計の本文を書き始めてはならない（骨子まで）。
- When 設計計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### メインフロー

- When このワークに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、調査結果レポート・全体計画書・issue の受け入れ条件・既存の設計文書を入力に進めなければならない。
- When 設計計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 設計計画書の案ができたとき、Shall スキルは 1 設計書 = 1 チケット（小さければ要件定義書 + 仕様書で 1 枚）の目安で設計チケット群（1 枚以上）を未着手に作らなければならない。互いに依存しないチケットは並列に進めてよいことを記す。
- When 設計チケットを作るとき、Shall その DoD は「設計書が機構のテンプレートに沿って作成（更新）されている」「設計計画書の骨子の各節が埋まりプレースホルダが無い」「受け入れ条件 <X> が受け入れ基準 / テストシナリオに落ちている」「設計中の決定の経緯（採らなかった案と理由）が DDR に残っている」の型で書かなければならない。
- When 設計チケット群を作り終えたとき、Shall スキルは全体計画書のフェーズ列で設計の次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: ワークの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When 設計計画チケットを完了するとき、Shall 設計計画書（md + HTML）・設計チケット群・次の計画チケットが存在し、DoD（計画書に結論方針・設計書の一覧と骨子・受け入れ条件との対応がある / 設計チケットの DoD が設計書と対応している / 次の計画チケットがある）がすべて満たされ、作業ログが機構のチケットテンプレートの項目に沿って書かれ、必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 設計計画チケットを完了したとき、Shall スキルは結果報告（計画書の場所、設計チケットの枚数と並列にできる組、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「結論方針が調査結果の根拠と整合しているか。決めきれない点が明示されているか」「設計書の一覧に過不足がないか（新規か既存の更新で済むか）」「骨子が受け入れ条件を漏れなく受け止めているか」「設計チケットの粒度と次の計画チケットの種類」を挙げなければならない。

### 設計計画チケットの扱い

- When 設計計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、設計文書（`docs/` 配下）・ソースコード・`.claude/` 配下を書けてはならない（設計書は設計チケットで書く）。
- When 設計計画チケット・設計チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければどちらも「要」を既定としなければならない（設計は後工程への影響が大きい）。

### 他のスキル・機構との整合

- When 調査結果レポート・全体計画書を参照するとき、Shall スキルはそれらを書き換えず、疑義があれば結果報告の「見てほしい点」に書かなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When 設計書のテンプレートと書き方に言及するとき、Shall not スキルは要件定義書・仕様書の書き方を再掲せず、設計書作成の task スキルを参照しなければならない。

### アルタナティブフロー（代替経路）

- If 受け入れ条件が設計文書の変更を必要としないと分かった場合、Then スキルは設計計画書に「対象なし」とその根拠を書き、設計チケットを起こさず次の計画チケットだけを作って設計計画チケットを即座に完了しなければならない（設計フェーズを省かない）。
- If 調査フェーズが「対象なし」で終わっていて調査結果レポートが無い場合、Then スキルは全体計画書と issue の受け入れ条件だけで計画を書き、根拠の不足を「見てほしい点」に明示しなければならない。
- If 再開時に設計計画チケットが作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、計画書・チケットを二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのワークに戻った場合、Then スキルは設計計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残さなければならない。

### 例外フロー（エラーケース）

- If 調査結果レポートの候補だけでは結論方針を立てられない場合、Then スキルは推測で決めず、「設計チケットで結論を書く」または「調査の追加が要る」として結果報告に書き、判断を人間レビューに委ねなければならない。
- If 計画書やチケット以外への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、その内容を設計チケットに回さなければならない。
- If 全体計画書のフェーズ列に設計の次のフェーズが書かれていない場合、Then スキルは次の計画チケットを推測で作らず、不整合として報告しなければならない。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

---

## 前提条件

- 調査フェーズのワークの切れ目の処理（レビュー要ならレビュー完了）が済み、設計計画チケットが未着手にあること
- 設計計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと提供コマンド、設計書作成の task スキルが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずに「判断を保留した点」と「見てほしい点」に書く。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 判断点の結論方針と設計書の構成は人間レビューで確定する。スキルは案を出し、レビュー前に設計書を書き始めない
- **外部的制約**: 対象はアプリ本体の設計文書に限る。`.claude/` 配下は AI アセット設計フェーズで扱う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 設計計画書に issue 番号・MR 番号が残り、受け入れ条件 → 設計書 → チケットの対応を辿れる |
| 一貫性 | チケットの記載事項・DoD の型・作業ログは他の work スキルと同じ。フェーズの名前は `00-workflow-issue-mr-driven.md`「ワークの構成」と一致する |
| 簡潔性 | 設計計画書は骨子までに留め、設計の本文を先取りしない |
| 冪等性 | 再開時に計画書とチケットを二重に作らない |
