# 0019 AI アセット設計結果 — 並列実行の前提と登録の書き方

## サマリ

設計ワークの境界レビュー 1 巡目の指摘のうち、**並列実行と登録の書き方に関わる 7 件（R1・R2・R10・R11・R12・R19・R22）**を仕様に反映した。更新した文書は仕様 6 本・要件 1 本、新規の DDR は 6 件（`i0009-20`〜`25`）。

根っこは 1 つ。公式の「**All matching hooks run in parallel.**」を、これまでの設計が読み落としていた。ここから 4 つの帰結が出た。

1. **順序に頼れない**（R1・R19）: `順` 列を `位置` に改め、「先に拒否したフックが理由を返す」「安価→高価の順序」を捨てた。**各フックの拒否理由は単独で読んで成立する文面**にする
2. **fork が 5 倍になる**（R11）: 「1 秒以内」だけでは守り方が決まらないので、**ホットパスで起動してよい外部プロセスは stdin 解析の `jq` 1 回だけ**という検査できる上限に置き換えた。§2 の `git rev-parse` 依存も外した
3. **同じ記録に同時に書く**（R22）: `logs/` の並行書き込みを 3 段階（追記は 4 KB 未満 / 読み書きは一時ファイル + `mv` / 加算は `mkdir` ロック）で規定し、`HK-T17` を足した
4. **共有ライブラリが状態を持つとレースになる**（R2）: `push_detect` から状態ファイルの読み書きを外し、**進捗の起点は呼び手が引数で渡す**形にした

あわせて、登録を **`${CLAUDE_PROJECT_DIR}` 基準の絶対パス**に変えた（R10。相対パスのままだと cwd がルート以外のとき拒否側 5 本が 127 で落ち、ラッパーが全操作を deny してロックアウトする）。登録表には `command` 文字列の材料（`--accumulate` の 2 行、実体のディレクトリと登録先イベントが一致しない 4 行）を注記した（R12）。

- ◎良 4 件 / △注意 2 件 / ✕問題 1 件

## レビューしてほしい観点

### ◆特に見てほしい（判断に困っている）

- **f2（✕問題）ホットパスの fork 上限を「`jq` 1 回」にした**こと。検査できる形にはなったが、**この上限で本当に足りるか**を実装前に見てほしい。特に `workflow-guard` は `scope-limits.json`（JSON）とチケットの frontmatter を読む必要があり、`jq` を 2 回目に呼びたくなる場面が出る（`scope-limits.json` の読み込みを `jq` ではなく純 bash で行うか、`hook_read_input` の 1 回に相乗りさせるかの設計が要る）
- **f4（△注意）`push_count` を `push-state.json` の `count` と独立に数える**ことにした。レポート名 `report-<branch>-<count>.md` の番号が 2 系統になるので、人間が読むときに「compact-prompt の回数」と一致しなくなる

### ◇承認が欲しい（方針は決めた）

- **f1** `位置` 列への改名と、拒否理由を単独で成立する文面にする方針
- **f3** 登録を `${CLAUDE_PROJECT_DIR}` 基準の絶対パスにすること（フェーズ 4b の人間の操作がこの形になる）
- **f5** 並行書き込みの 3 段階（`mkdir` ロックは 2 秒で諦めて加算せず終了 0）

### ・細かいレビューは不要（ほぼ確実）

- **f6** 登録表の注記（`--accumulate` の 2 行・ディレクトリ不一致の 4 行）と HK-T01 が変換で照合しないこと
- **f7** §2 の `git rev-parse` を読み込み行の解決結果に置き換えたこと

## 確かめられなかったこと（この結果が言っていないこと）

- **`jq` 1 回で全フックが書けるか**を実装で確かめていない（f2 の懸念）。特に `workflow-guard` の `scope-limits.json` の読み方は 0021（ライブラリのインターフェース）と実装フェーズの担当
- **`mkdir` ロックが Git Bash で期待どおり原子的に振る舞うか**を実測していない（POSIX の保証に依拠）
- **4 KB（`PIPE_BUF`）が Windows の Git Bash でも成立するか**を実測していない。`decisions.jsonl` の 1 行は通常 200〜500 バイトなので余裕はあるが、保証の根拠は POSIX の記述
- `${CLAUDE_PROJECT_DIR}` が実際にどう展開されるか（worktree のとき何を指すか）を実測していない
- 並列実行そのものを**観測していない**。公式の記述に依拠している（実測はフェーズ 4c）

## 実施した内容と結果

### f1. 順序に頼る記述をすべて外した ◎良

公式は「**All matching hooks run in parallel.** If you define the same handler in more than one settings file, it runs once.」と明記している（`hooks.md:414`）。これまでの設計は 3 か所でこれに反していた。

- **§1 の `順` 列**を **`位置`**（`settings.json` の配列上の位置であって実行順ではない）に改めた
- **§1 の「先に拒否したフックが理由を返す」**を「複数が同時に deny を返し得る。**どの理由が AI に見えるかは不定**として扱い、**各フックの拒否理由は単独で読んで成立する文面**にする（他のフックが先に判定した前提を書かない）」に変えた
- **「安価で範囲の広い判定 → 高価で狭い判定」**という順序による絞り込みを削り、「各フックが単独で軽いことだけが性能を決める」にした
- **各フック仕様の「〜の後、〜の前」を 5 本**（`block-chmod` / `block-direct-git` / `workflow-state-guard` / `workflow-guard` / `post-push-usage-report`）で「共通仕様 §1 の N 行目。**位置であって実行順ではない**」に書き換えた（R19 の `workflow-guard` の「最後に実行」も含む）
- **HK-T01** の照合対象を「イベント・matcher・フック・**配列上の位置**」に書き直した（位置は `settings.json` に実在する情報なので照合からは外さない）

結論: 事実と食い違う前提が消えた。実装者が「先に走るフックが弾くから省ける」という最適化を入れる余地が無くなった。DDR `i0009-21`。

### f2. ホットパスの目安を「`jq` 1 回」という検査できる上限に置き換えた ✕問題

`i0009-11` が置いた「ホットパスで 1 秒以内」は**結果であって守り方ではない**（実装者が守れているか判断できず、テストにも落ちない）。しかも §2 が「作業ツリーの位置は `git rev-parse --show-toplevel` を基準にする」と書いており、素直に読むと各フックが毎回 git を起動する — `20-common-step-shell-script` 仕様が「Git Bash で**約 95 ms/回**」を理由に否定した方式を、共通仕様が要求していた。

- **決定**: ホットパスのフックが起動してよい外部プロセスは、**stdin を解析する `jq` の 1 回だけ**（`git` / `date` / `sed` / `find` を呼ばない）。`test-lib.sh` の `make_counting_path` で**呼び出し回数として検査**する（HK-T05・HK-T13 と同じ方式）
- §2 の「`git rev-parse --show-toplevel` を基準にする」を「**読み込み行が解決したリポジトリルート（`LOGGER_ROOT` / `HOOK_ROOT`）を基準にする**」に変え、「フック本体から `git rev-parse` を呼ばない」を明記した
- 並列実行なのでホットパス 5 本は**同時に**起動する。1 本あたりの fork がそのまま 5 倍のプロセスになることも §1 に書いた

**なぜ ✕ か**: 上限は決めたが、**この上限で全フックが書けるかを確かめていない**。`workflow-guard` は `scope-limits.json`（JSON）とチケットの frontmatter を読む必要があり、`jq` の 2 回目を呼びたくなる。`frontmatter.sh` は純 bash なので frontmatter 側は問題ないが、`scope-limits.json` の読み方は未決（0021 と実装フェーズの担当）。上限を決めた以上、守れない場合は上限か設計のどちらかを直すことになる。

結論: 「速さで守る」という `i0009-11` の決定が、検査できる形になった。ただし実装可能性は未確認。DDR `i0009-22`。

### f3. 登録を `${CLAUDE_PROJECT_DIR}` 基準の絶対パスにした ◎良

登録の雛形は `bash .claude/hooks/<NN-Event>/<name>.sh` という**リポジトリルート相対パス**だった。公式は 2 つのことを言っている。

- 「**Handlers run in the current directory** with Claude Code's environment.」（cwd が**消えていた**場合だけ、起動ディレクトリ → プロジェクトルート → ホーム → temp の順にフォールバックする）
- 「**Use absolute paths** … In shell form, wrap it in double quotes」

cwd はリポジトリルートとは限らない（Claude が `cd` した後・worktree・サブディレクトリ）。フォールバックは cwd が消えたときにしか働かない。

- **決定**: `command` を **`bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/<NN-Event>/<name>.sh"`** にする。ラッパー付きの拒否側 5 登録も同じ形
- **なぜ重大か**: 相対パスが解決できないと `bash` は終了 **127**。ラッパーの `||` はまさにこれを拾うので、**拒否側 5 本すべてが同時に deny を返し、書き込み・実行・プランモード・起動のすべてが止まる**。この状態から AI 側でできることは無い（ファイルを直そうにも書き込みが deny される）。案内側 6 本は同じ状況で**静かに動作停止**する
- HK-T01 の照合対象に `command` 文字列そのものを含めた

結論: 実装計画が一番避けたい形のロックアウトの経路が 1 つ塞がった。DDR `i0009-20`。

### f4. `push_detect` から状態を外し、進捗の起点を呼び手が持つ形にした △注意

`push-detect.sh` の検知条件 3 は「`push-state.json[b].sha` が HEAD と異なる」で、この関数を `post-push-compact-prompt`（正）と `post-push-usage-report`（共有）の 2 本が使う。ところが compact-prompt は本体の最後で `push-state.json[b]` を `{sha: head, count+1}` に更新する。

- compact-prompt が先に走ると、usage-report の検知は条件 3 が偽になり **集計しない**
- 並列実行なのでどちらが先かは不定 = **レース**（時々レポートが出る／出ない）
- レポート名の `<count>` も `push-state.json[b].count` を読むので、`count+1` の前か後かで番号がずれる

- **決定**: `push_detect <起点 sha>` は**状態ファイルを読まず書かない**。起点は呼び手が渡す（compact-prompt = `push-state.json[b].sha` / usage-report = `usage/<branch>.json` の **`last_push_sha`**（新設））
- `usage/<branch>.json` に `last_push_sha` と **`push_count`** を足し、レポート名の `<count>` は `push_count` で数える。usage-report は **`push-state.json` を一切参照しない**
- `HK-T13` から状態ファイルの読み書きを外し、`UR-T07` に「`push-state.json` が先に更新された状態でも `last_push_sha` が古ければ検知が通る」を足した

**△ の理由**: レポートの通し番号が 2 系統（`push-state.json` の `count` と `usage` の `push_count`）になる。緊急停止で片方だけを止めると番号がずれるが、それは意図した独立性の裏返しでもある。人間が読むときの混乱を減らすなら、レポート本文に「このブランチで <push_count> 回目の push」と明記する現行の書き方で足りると判断した。

結論: 共有ライブラリが特定の状態ファイルを持つ設計（`i0009-17` と同じ形の誤り）が解消した。DDR `i0009-24`。

### f5. `logs/` の並行書き込みを 3 段階で規定した △注意

§5 は同時書き込みについて何も書いていなかった。公式は「All matching hooks run in parallel」に加えて「`PostToolUse` … **fires concurrently when Claude makes parallel tool calls**」と明記している。競合し得るのは 3 種類。

| ファイル | 書く側 | 競合の形 | 規則 |
|---|---|---|---|
| `decisions.jsonl` | 全フック（PreToolUse で 7 本） | 追記の割れ | 1 行を **4 KB（`PIPE_BUF`）未満**に保つ。`note` と `target` は合わせて 1 KB まで |
| `approvals.json` / `push-state.json` | diff-check / compact-prompt | 書きかけを読む | 一時ファイル（`<name>.tmp.<pid>`）+ `mv` |
| `usage/<branch>.json` | usage-report（並行するサブエージェントの SubagentStop） | 加算が消える | **`mkdir <name>.lock`** で直列化。取れなければ**最大 2 秒で諦め、加算せず `parse_errors` を +1 して終了 0** |

- `mkdir` を選んだのは移植性（`flock` は Git Bash に無いことがある）。`mkdir` は存在すれば失敗するので原子的
- 2 秒で諦めるのは案内側フックが本体を止めないため。集計が 1 回抜けるのはセッションが止まるより軽く、抜けたことは `parse_errors` に残る
- 新規テスト **`HK-T17`** で固定した
- 要件の非機能（可用性）にも外部から見える性質として 1 文足した:「複数の判定が同時に走って同じ記録に書いても、記録は壊れず、取りこぼしがあったことは記録から分かる」

**△ の理由**: `mkdir` ロックの原子性も 4 KB の追記保証も **POSIX の記述に依拠**しており、Git Bash（MSYS）で実測していない。実装フェーズで `HK-T17` を通すまでは仮定。

結論: 並列実行から出る 3 つ目の帰結を塞いだ。DDR `i0009-23`。

### f6. 登録表に `command` 文字列の材料を注記した ◎良

表の 5 列だけでは `command` を組み立てられない。**引数を取る登録が 2 行**（SubagentStop / Stop の `--accumulate`）と、**実体のディレクトリと登録先イベントが一致しない行が 4 行**ある。

- §1 の「実体」の説明に「**`<NN-Event>` は主たるイベント**で、登録先のイベントと一致しないことがある（DDR `i0001-24`）」を明記した
- 登録表の直後に「表に現れない登録の細部」として 2 行と 4 行を列挙した
- **HK-T01 は「イベント名 → ディレクトリ」の機械的な変換で照合しない**。17 行分の `command` 文字列の一覧を期待値として持つ
- 変換で照合しようとすると 4 行の例外を変換規則に埋め込むことになり、「表が正」という建て付けが崩れる

結論: HK-T01 が書ける状態になった。DDR `i0009-25`。

### f7. §2 の作業ツリーの解決を読み込み行に一本化した ◎良

f2 に含まれるが、独立した是正なので分けて記す。§2 の「`cwd` ではなく `git rev-parse --show-toplevel` を基準にする（サブディレクトリからの実行に備える）」という意図（サブディレクトリ対応）は、読み込み行の解決順（`BASH_SOURCE` からの上向き探索 → `CLAUDE_PROJECT_DIR` → `git rev-parse`）が**既に満たしている**。手段が二重になっていただけで、参考実装 `hook-common.sh:18` も git を呼んでいない。

結論: 「サブディレクトリからの実行に備える」を満たしたまま、fork を 1 つ減らせる。

## 残課題

- **f2 の実装可能性**: `jq` 1 回で `workflow-guard` が書けるかは 0021 と実装フェーズで確かめる。書けなければ上限か設計を直す
- `mkdir` ロックと 4 KB 追記の保証は **POSIX の記述に依拠**しており、Git Bash（MSYS）での実測は `HK-T17` を通すまで無い
- `${CLAUDE_PROJECT_DIR}` が worktree で何を指すかを確かめていない（フェーズ 4c）
- レポートの通し番号が 2 系統（`push-state.json` の `count` と `usage` の `push_count`）になった。運用してみて混乱するようなら片方に寄せる
- 並列実行の帰結として**まだ点検していない箇所**がある可能性: 今回は §1・§2・§5・§11 と 5 本のフック仕様を見たが、`workflow-entry` の「プロンプト境界の処理」と `session-start` は並列の対象になる登録が 1 つずつなので触っていない。他イベントに同名フックが増えたときに再点検が要る
