# 10-task-design-feedback-plan — 設計書と実装の差分を分類する

共通手順の禁止事項（`10-task-investigation-plan` の冒頭が正）に加えて、設計書もコードも書き換えない（突き合わせは読み取りだけ。書き戻しは設計反映チケット）。実装漏れを「設計書を実装に合わせる」ことで解消する計画を立てない（設計書は正のまま、実装追加を提案する）。別 issue 候補（受け入れ条件外の変更）をチケット化しない。差分の判断を保留したまま分類済みとして扱わない（保留は「保留した点」へ）。

## 目的

実装で生じた設計書とのずれを分類し、どこをどう書き戻すかを決める。実装漏れと「設計書が古い」の線引きをここで確定させる。

- 要件: `.claude/docs/00_requirement/skills/10-task-design-feedback-plan.md`
- 仕様（正。固有手順・4 分類・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-design-feedback-plan.md`
- 処理の共通手順（正）: `10-task-investigation-plan` の「計画タスクの共通手順（正）」

## 手順

共通手順（着手 → 入力の確認 → 計画書 → 実施チケット群 → 次の計画チケット → 完了 → 結果報告）は `10-task-investigation-plan` に従う。ここでは固有部分だけを示す。

- 計画書の**差分一覧**は、実装結果レポートの逸脱一覧・計画外の変更を起点に、設計書の節とコード・テストを読み取りだけで突き合わせて作る。行ごとに次の 4 分類のどれかを付ける
  - **一致**: 対応不要
  - **設計書が古い**: 実装が正しく設計書が追いついていない → 書き戻す（経緯は DDR）
  - **実装漏れ**: 設計書が正しく実装が足りない → 書き戻さず、実装の追加を結果報告で提案する（受け入れ条件に関わるなら実装の追加チケットの提案、そうでなければ残課題）
  - **設計に無い決定**: 実装中に決めたことが設計書に無い → 設計書に追記し、経緯を DDR に残す
- 1 チケット = 関連する設計書のまとまり（機能単位）
- **設計反映チケットの DoD の型**: 「差分一覧の {{行}} が設計書 {{節}} に反映され、行が『一致』に消し込まれている」「経緯が DDR に残っている」「テスト ID が実装のテストと対応している」
- 差分が 0 件（すべて一致）なら「対象なし」として次の計画チケット（全体まとめ）だけを作る
- 人間レビュー要否の既定（方針が無い場合）: 設計反映計画チケット「要」
- **見てほしい点の固定項目**: 分類の妥当性（特に実装漏れと設計書が古いの線引き）/ 書き戻し方針が実装の実態と合っているか / 実装漏れの扱い（受け入れ条件との関係）/ 次の計画チケット

## OUT ひな形

`assets/design-feedback-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR・突き合わせた設計書とレポート |
| 差分一覧 | 設計書の節 × 実装の実態 × 分類 × 方針（表） |
| 書き戻し方針 | 設計書ごとの直し方・DDR の要否 |
| 実装漏れ一覧 | 提案（実装追加チケット / 残課題 / 別 issue 候補） |
| 受け入れ条件の確認 | 条件ごとに設計書と実装の双方で満たされているか |
| 設計反映チケット | まとまりごとのチケットと依存 |
| 保留した点 / 対象なし | 該当時 |

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 実装漏れか設計書が古いか判断できない | 分類済みとして扱わない。「保留した点」に書き、見てほしい点に載せる |
| 実装漏れを設計書側で吸収したくなった | 吸収しない。設計書は正のまま、実装の追加を提案する |
| 受け入れ条件外の差分が見つかった | チケット化しない。別 issue 候補として結果報告に書く |
| 差分が 0 件 | 「対象なし」として次の計画チケットだけを作る。フェーズを省かない |
| 共通手順で止まった（TK002 / TK005 / RV00x） | `10-task-investigation-plan` の「エラー時の対処」に従う |
