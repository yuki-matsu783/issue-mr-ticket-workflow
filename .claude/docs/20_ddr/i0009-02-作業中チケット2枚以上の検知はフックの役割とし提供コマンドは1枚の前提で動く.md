# i0009-02. 作業中チケット 2 枚以上の検知はフックの役割とし、提供コマンドは 1 枚の前提で動く

## 背景

issue #9 の申し送り G8 は「作業中チケットが 2 枚以上あるとき `push.sh` / `run-tests.sh` / 完了検査が 1 枚目しか見ない非対称」を挙げていた。実物を読むと次のとおり。

- **1 枚目しか見ない**: `run-tests.sh:86`（`ticket="${doing[0]}"` で `allow.ops` を読む）、`push.sh:98`（同型）、`ticket.sh:334`（`next` が `DOING_FILES[0]` を返す）
- **件数で見る**: `ticket.sh:208`（`start` は 1 枚でもあれば TK002 で拒否）
- **非対称ではない**: 完了検査（`ticket.sh complete`）は番号引数から `find_ticket` するので、そもそも 1 枚目を見ていない

`workflow-guard` の仕様は既に「2 枚以上は異常（WF207）」を持っており、提供コマンド以外の書き込み・実行を拒否する。

## 決定

- 2 枚以上の状態を検知して止めるのは **`workflow-guard` の WF207 の役割**とし、提供コマンドは「1 枚である」前提で動いてよいことを仕様に明記する
- WF207 は `ask` ではなく `deny`（ヘッドレス実行でも同じ結果になる）
- 提供コマンド側の実体（`run-tests.sh` / `push.sh` / `ticket.sh next`）は**変更しない**

## 理由

- 2 枚以上は `ticket.sh start` が防いでいるので、通常の経路では発生しない。発生するのは手動でファイルを動かした場合か機構が壊れた場合で、それはまさに「機構の異常」としてフックが止める場面
- 提供コマンド 3 本に件数判定を足すと、同じ判定が 4 か所（フック + 3 本）に散る。判定の重複は機構の保守で最も避けたい形（`tool_class` と `entry-skills.txt` の二重定義と同種）
- フックが止めていれば、提供コマンドが 1 枚目を読んで誤った `allow.ops` を使う状況にはそもそも到達しない

## 却下した案

- **提供コマンド 3 本を件数判定に直す**: `push.sh` は `20-common-step-commit-push` 配下、`ticket.sh` は `20-common-step-ticket` 配下で、issue #9 の実装フェーズの許可範囲（`.claude/hooks/**` と `20-common-step-shell-script/**`）から外れる。3/3 送りになり、この issue では閉じられない
- **`ticket.sh next` だけ件数を返す**: `next` は「次に何をするか」を返すコマンドで、異常検知の窓口としては役割が違う
- **フックと提供コマンドの両方で見る**: 二重定義。片方だけ直したときに食い違う

## 影響

- `10_spec/hooks/20-PreToolUse/workflow-guard.md` 制御方式 2（非対称の注記とヘッドレスの帰結）
- `00_requirement/hooks/20-PreToolUse/workflow-guard.md` 受け入れ基準（提供コマンドは検知の責任を負わない）
- `10_spec/skills/20-common-step-shell-script.md`・`20-common-step-ticket.md`・`20-common-step-commit-push.md`（1 枚である前提で動く旨。0015 が書く）
