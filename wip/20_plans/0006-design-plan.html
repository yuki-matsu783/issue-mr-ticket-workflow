この計画で何をするか

調査で出た事実から採る案を確定し、要件定義書 1 本と仕様書 1 本の骨子を決めて、設計実施チケット 1 枚に落とす。設計書の中身そのものは書かない。

決めたこと

  • 設計書は要件 1 本 + 仕様 1 本。拡張は 1 つの機能のまとまりなので分割しない
  • 設計チケットは 1 枚（要件と仕様を同じチケットで書く）
  • アプリ向けの仕様書の節構成は機構が定めていないので、この計画で決めて DDR に残す

対象と範囲

入力は調査結果レポート 0003（実形と壊れ方）/ 0004（ビルド・テスト環境）/ 0005（境界と置き場）/ 0007（VS Code API）。書く設計書は次の 4 本。

方法とステップ

調査結果の候補から採る案を、比較軸ごとの根拠付きで確定する。

  1. 1

    成果物の置き場

    issue #13 の詳細欄は tools/vscode-ticket-board/ だが、上限設定の implementation.allow にも common.allow にも入らない。採る案は src/vscode-ticket-board/（テストは同ディレクトリ内の test/）。設計文書は docs/00_requirement/ と docs/10_spec/。受け入れ条件は場所を規定していないので条件は変わらない。src/vscode-ticket-board/.gitignore に node_modules/ と out/ を書く。

  2. 2

    frontmatter の読み方

    汎用 YAML ライブラリは壊れた入力で例外を投げうるため、受け入れ条件 7 のために握り潰しが要る。扱う形は 5 種類に限られる。採る案はサブセット専用の自前パーサで、値の妥当性検査はパーサの外に置く。

  3. 3

    ビルドとテスト

    採る案は TypeScript + tsc -p . + node --test out/test/*.test.js。開発依存は typescript / @types/node / @types/vscode の 3 つ。@vscode/test-electron は使わない。package-lock.json をコミットする。

  4. 4

    層の分け方

    vscode は VS Code ホストの外では解決できないため、単体テストの対象にできるのは vscode を import しないコードだけ。走査・パース・ボード組み立て・HTML 生成を vscode に依存しない層に置き（読み取りは node:fs）、コマンド登録・Webview の生成・watcher の購読だけを vscode 依存層にする。

  5. 5

    更新の戦略

    FileSystemWatcher はファイル移動のイベントを持たず、状態変更は onDidDelete + onDidCreate に割れ順序も保証されない。採る案は差分更新をやめ、3 イベントのいずれでも 4 ディレクトリを全部読み直す方式。短時間の連続イベントは短い遅延でまとめて 1 回にする。

  6. 6

    Webview の作り

    採る案は外部リソースを一切読まない自己完結 HTML を文字列で生成し webview.html に代入する方式。localResourceRoots は空、asWebviewUri は使わない。CSP は default-src 'none' から組み、スクリプトは nonce 付きインラインのみ。retainContextWhenHidden は使わず onDidChangeViewState で読み直す。

決めきれない点（設計チケットで結論を書く）

  • 連続イベントをまとめる遅延の具体値と、その根拠
  • DoD のチェック進捗をカードに出すか。受け入れ条件には無い。出すなら要件の受け入れ基準に足す
  • 不備の表示の粒度。「取得できなかったキー名」「不正な値」をどこまで出すか
  • アプリ向け仕様書の節構成。機構は スキル / エージェント / フック の 3 種しか定めていない
