# i0050-09. タスクの切れ目は合流を先に行い、敵対的レビューと範囲の確定はその後にする

## 背景

`i0050-03` で合流をタスクの切れ目に固定し、`00-workflow-issue-mr-driven` では合流を切れ目の処理の先頭（push の直前）に置いていた。一方、敵対的レビューは切れ目の処理より前（手順 2a）に置かれている。この 2 つを並べると、実行の順序は「切れ目の判定 → 敵対的レビュー → 合流 → push」になる。

この順序には 2 つの穴がある。

- **敵対的レビューが成果を見ない。** 並列区間の成果はサブブランチにしかなく、合流前の本流の `HEAD` にも `20_done/` にも現れない。レビュー対象の差分（前の切れ目の `head_sha`..`HEAD`）に 1 行も入らないので、レビュアーは指摘 0 件で通す。`executor` の突き合わせ（レビュー対象を作った実行者と別のモデルで起動する）も、前のタスクのチケットで行われる
- **二重着手の経路が開く。** 敵対的レビューで指摘が出ると手順 2a-4 は追加チケットを起こして手順 2 へ戻る。合流前の本流では、作業ツリーで完了したチケットが `00_todo/` に残ったままなので、`ticket.sh next` がそれを返す。同じチケットに 2 回目の着手が起きる

あわせて、並列区間中の本流での `at_boundary` と `next` の振る舞いが決まっていなかった。`at_boundary` は全作業ツリーの `doing` を見る形になっていたが、`last_task`（完了チケットの集合）は本流の `20_done/` だけを見るので、合流前に確定させると空か、前のタスクのものになる。

## 決定

- **切れ目に達したときの順序を固定する: `boundary.sh status`（切れ目の候補）→ 合流（手順 2c）→ 敵対的レビュー（手順 2a）→ push（手順 3-1）以降。**
- **合流を独立した手順 2c として切れ目の処理（手順 3）の外に出す。** 手順 3 は push から始まる。合流は「切れ目の処理の 0 番目」ではなく「切れ目の処理に入る前に済ませること」である
- **どの作業ツリーの `doing` も空になった時点は「切れ目の候補」にすぎない。** `at_boundary`・`last_task`・`review_required` は、合流の後に `status` をもう一度実行して確定させる
- **並列区間の本流の `ticket.sh next` は補正しない。** 作業ツリー側で着手・完了したチケットを本流の `next` から除く探索は `ticket.sh` に持たせず、呼び出し元が並列区間の間 `next` を着手の指示として使わないことで守る（要件 **[A12]**）
- 合流できないとき（`WT003` / `WT004`）は、敵対的レビュー・push・レビュー依頼のいずれにも進まない（要件 **[E8]** の適用範囲を push とレビュー依頼から 3 つに広げる）

## 理由

- 敵対的レビューの値は「別の目で成果を見る」ことにある。成果が差分に現れない状態でレビューを走らせると、上限回数（タスクごとに 1 回）だけが消費され、指摘 0 件という記録が残る。**レビューを省いたより悪い**（省いたことにならない）
- 二重着手は、合流を先に済ませれば構造的に起きない。本流の `wip/` が揃った後は `next` が正しく次を返す。順序を固定するのがいちばん安い塞ぎ方である
- `last_task` の材料は完了チケットのファイルそのもの（`20_done/` の frontmatter）で、合流前の本流にはそれが無い。「見えていないものを数えない」ためには、確定の時点を合流の後に置くしかない
- `ticket.sh next` に作業ツリー横断の探索を持たせない: `ticket.sh` は 1 つの作業ツリーの `wip/` を見る前提で書かれており、横断探索を入れると採番・着手・完了のすべてが他の作業ツリーの状態に依存する。`at_boundary` の横断判定（`worktree.sh list` を 1 回呼ぶ）は切れ目の判定という 1 か所に閉じているが、`next` は毎回呼ばれる。**依存を増やす場所を 1 か所に留める**
- 合流の失敗で止まる範囲を 3 つに広げるのは、順序を変えた当然の帰結である（合流が最初なので、失敗すれば後続はすべて行われない）

## 却下した案

- **合流を push の直前に置いたまま、敵対的レビューだけを合流の後へ動かす**: 結果の順序は同じだが、「切れ目の処理（手順 3）の途中に手順 2a が挟まる」形になり、手順の番号と実行順が食い違う。読み手が順序を再構成できなくなる
- **敵対的レビューの対象差分にサブブランチを含める（`git diff` の範囲を工夫する）**: 複数のサブブランチの差分を 1 つの patch に合成すると、衝突する変更が両方載った患者のような patch になり、レビュアーが「どちらが本流に入るのか」を判断できない。合流の結果を見せるほうが正確で、実装も単純である
- **合流前でも `20_done/` を作業ツリー横断で数える**: `last_task` の材料が本流の外にあることになり、`boundary.sh` が他の作業ツリーの `wip/` を読むことになる。`i0050-02`（進行状態は共有ルートに一本化し、`wip/` は作業ツリー側）と噛み合わない
- **`ticket.sh next` に「他の作業ツリーの `10_doing/` と `20_done/` を除く」を持たせる**: 二重着手は塞げるが、`next` が毎回 `worktree.sh list` を呼ぶことになり、`session-start`（`boundary.sh status --offline` 経由）の応答時間に効く。並列区間は例外的な区間なので、常時のコストを払わない
- **二重着手を `ticket.sh start` の側で塞ぐ（他の作業ツリーで着手済みなら拒否）**: 同じく横断探索が要る。加えて、拒否は「起きてから気づく」形で、順序の固定（起こさない）より弱い

## 影響

- `00_requirement/skills/00-workflow-issue-mr-driven.md`: 合流の受け入れ基準を「敵対的レビューと push のどちらよりも前に」に改め、「切れ目とタスクの範囲は合流の後に確定する」を足す。代替 **[A12]**（並列区間では `next` を着手の指示に使わない）と、例外 **[E8]** の範囲の拡大
- `10_spec/skills/00-workflow-issue-mr-driven.md`: 手順 3-0 を**手順 2c** として独立させ、固定順を宣言する。手順 2a の冒頭と手順 2-7 の分岐をその順序に合わせる。「切れ目の判定（正）」に「並列区間での確定の時点と `next` の扱い」を置き、`BD-T21` に合流の前後で `next` と `last_task` が変わることを足す。`WFD-E09` の判定方法に順序と patch の中身を含める

- 実装フェーズは `BD-T21` を「合流の前後で 2 回 `status` を取る」形で書く
