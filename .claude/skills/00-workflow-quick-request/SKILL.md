# 00-workflow-quick-request — 範囲を宣言して軽作業だけを済ませる

判定表で 1 つでも issue-MR 側に該当する依頼を軽作業として進めない（迷ったら重い側）。`.claude/` 配下（スキル・フック・ルール・エージェント・設定・設計文書）に書き込まない。**文言修正も例外にしない**。宣言に無いファイルへの変更・振る舞いの変更・4 ファイル以上の変更を黙って続けない。`git commit` / `git push` を直接実行せず、default ブランチ上で指示なしにコミット・push せず、勝手にブランチを作らない。既存の未コミットの変更に干渉しない（stash・破棄・巻き込みコミットをしない）。`glab issue` / `gh issue` を自前で組み立てない。振り返りを省略せず（質問・説明だけでも行う）、見送った候補を黙って捨てない。起票した issue への着手を持ちかけない。切り替えを次のプロンプトに先送りしない。ワークスペース外のパス（OS の一時ディレクトリ）を使わない（一時ファイルは `wip/tmp/`）。

## 目的

issue と MR を作るまでもない依頼を、範囲を先に宣言してから最小限で片付ける。終わりに AI アセットの効き目を棚卸しし、改善候補を落とさない。

- 要件（判定表の正）: `.claude/docs/00_requirement/skills/00-workflow-quick-request.md`
- 仕様（正。処理フロー 0〜6・ヘッドレスの扱い）: `.claude/docs/10_spec/skills/00-workflow-quick-request.md`
- 対になる振り分け: `00-workflow-issue-mr-driven`（開発作業）

スクリプトは持たない（状態遷移が無く、すべての操作が単発で済むため）。

## 手順

### 0. 判定

依頼を次の表に当て、**1 つでも issue-MR 側に該当すれば軽作業として進めない**。

| 観点 | 軽作業（このスキル） | issue-MR 駆動（`00-workflow-issue-mr-driven`） |
|---|---|---|
| 成果物 | 回答・説明・調査結果のみ、または振る舞いを変えないファイル変更 | コード・設定の変更を伴う開発作業 |
| 振る舞い | 変わらない（typo、コメント、ドキュメント、フォーマット、設定値の微調整） | 変わる（機能追加、バグ修正、リファクタリング、依存の追加・更新） |
| 規模 | 1〜3 ファイル、同一ディレクトリ内に閉じる | 複数モジュールにまたがる、または 4 ファイル以上 |
| 検証 | 目視・既存テストの実行で足りる | テストの追加・変更やレビューが必要 |
| 追跡 | 経緯をリモート（GitLab / GitHub）に残す必要が無い | issue / MR で経緯を追いたい、他の人がレビューする |
| 対象 | `.claude/` 配下以外 | `.claude/` 配下のアセット（スキル・フック・ルール・エージェント・設定・設計文書）の作成・変更はすべて。文言修正も例外にしない |
| ユーザーの指定 | 「軽く」「issue 不要」「質問」など | 「issue 駆動で」「MR にして」「#N をやって」など |

1. 判定結果と根拠を 1 行で示す（例: 「判定: 軽作業（README の typo 1 か所。振る舞いは変わらず 1 ファイル）」）
2. issue-MR 側 → その旨を伝え、`00-workflow-issue-mr-driven` を Skill ツールで読み込んで切り替え、このスキルの手順を続けない。ユーザーが issue 番号や MR の URL を添えた依頼も同様
3. 境界上で決められない → 重い側に倒すか、`AskUserQuestion` で「軽作業として進める / issue-MR 駆動で進める」を確認する

### 1. 状態確認（ファイルの変更を伴うとき。質問・説明だけなら省略）

1. `git branch --show-current`、`git status --short`、`ls wip/10_tickets/00_todo wip/10_tickets/10_doing wip/10_tickets/20_done` を確認する
2. 現在のブランチが default と異なる → `AskUserQuestion` で「このまま現在のブランチで実施 / default ブランチに切り替えて実施 / 中断」を確認する（切り替えは未コミットの変更が無いときだけ。あれば触らずに現在のブランチで実施するか中断する）
3. チケットがある（issue-MR 駆動の作業が進行中）→ その旨を示し、`AskUserQuestion` で「このブランチで軽作業を実施してよいか」を確認する。承認されなければ実施せず、`00-workflow-issue-mr-driven` での再開を案内して終える
4. 未コミットの変更がある → 触らず、対象ファイルが既に変更されていないかを確認する（変更されていれば重ねて編集しない旨を伝えて確認する）

### 2. 範囲の宣言

「やること」「触るファイル（無ければ無し）」「やらないこと」を 2〜4 行で宣言する。この宣言が範囲超過の判定基準になる。

### 3. 実施

1. 宣言した範囲の中でだけ作業する。既存テストの対象に触れる変更なら、そのテストを実行して結果を確認する
2. **範囲超過の検知**: 宣言に無いファイルを触る必要が出た / 振る舞いの変更が必要になった / 変更が 4 ファイル以上になった のいずれかで作業を止め、`AskUserQuestion` で「軽作業として範囲を広げる（宣言を更新）/ `00-workflow-issue-mr-driven` に切り替える / ここまでで止める」を確認する。切り替える場合は、ここまでの変更を残すか戻すかも確認する（戻すときはユーザーが明示的に選んだファイルだけ `git checkout -- <path>`）
3. 既存テストを壊した → 修正が範囲内なら直し、超えるなら 2 の確認へ
4. コミットが要る（ユーザーの指示がある、または feature ブランチ上で成果を残す合意がある）→ `bash .claude/skills/20-common-step-commit-push/scripts/commit.sh`（対象ファイルを明示）。push はユーザーの指示があるときだけ `push.sh`。default ブランチ上ではユーザーの指示があるときだけ

### 4. 報告

「変更したファイルと要点（変更が無ければ回答そのもの）」「確認した内容（実行したテスト・目視）」「積み残し・気づいた問題」「見送り」を報告する。

### 5. 振り返り

1. 今回のプロンプトで使った AI アセット（読み込んだスキル・働いたフック・参照したルール・エージェント・`CLAUDE.md`）を棚卸しし、アセットごとに**観点**（足りなかった / 邪魔だった / 無かった / 問題なし）と**類型**（(a) アセットが無かった / (b) あったが誤っていた / (c) あったが罠が書かれていなかった / (d) あったのに辿り着けなかった）を付けて表にする。列は アセット / 観点 / 類型 / 候補。文言は `10-task-feedback-plan` と同一
2. 候補（問題なし以外）が 0 件 → 「候補なし」と報告して完了（確認しない）
3. 候補ごとに `AskUserQuestion` で「issue として記録だけする（着手しない）/ issue を作って `00-workflow-issue-mr-driven` で進める / 今回は不要」を確認する（候補が複数なら 1 回の質問にまとめてよい）

### 6. 候補の扱い

- **記録だけ**: `20-common-step-issue` の作成の手順で起票する。種別「改善・最適化」、優先度は「低」を既定、本文にテンプレートの節に加えて「発端」（このプロンプトの依頼の要約・振り返り表の該当行・再現の手がかり）を書く。本文案はユーザーに見せて承認を得てから投稿する。起票後はブランチ・MR・実作業に進まず、番号と URL を報告する
- **進める**: **同じプロンプトの中で** `00-workflow-issue-mr-driven` を Skill ツールで読み込み、次を引き継いで開始する: `summary`（候補の要約）/ `acceptance`（何が直れば解消か）/ `issue_kind`（改善・最適化）/ `asset_type`（AI アセット）。フェーズ列と検索語は渡さない。issue の内容・ブランチ名・MR タイトルの承認は切り替え先で改めて取る
- **今回は不要**: 報告に「見送り」として候補と理由を残す。同じ候補が繰り返し見送られていると分かるときは「記録だけする」を勧める

### ヘッドレス（ユーザーが応答できない実行形態）

- `AskUserQuestion` で待つ確認をすべて行わない（作業領域にチケットがあるときの続行確認、default ブランチでの続行確認、範囲超過の扱い、振り返りの候補ごとの対応先）。現在のブランチのまま宣言の範囲内だけを実施し、範囲超過は「ここまでで止める」に倒す
- 振り返りの候補は報告に含めるだけで完了扱いとし、issue を作らない
- 作業領域にチケットがある場合は実施せず、その旨を報告して終える
- ヘッドレスかどうかは `WORKFLOW_HEADLESS=1` または `CI` が真値のとき

## 参照

- 対になる振り分け（開発作業）: `00-workflow-issue-mr-driven`
- issue の起票: `20-common-step-issue`
- コミットと push: `20-common-step-commit-push`
- 観点・類型の文言（同一）: `10-task-feedback-plan`
- 振り分けの宣言の記録: `workflow-entry` フック（宣言はプロンプトごと。作業領域にチケットがある間は再宣言を求められない）

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 振り分けの宣言が無いとして操作を拒否された | 迂回しない。このスキルまたは `00-workflow-issue-mr-driven` を Skill ツールで読み込んでから元の操作をやり直す |
| `.claude/` 配下を直す必要が出た | 軽作業として直さない。`00-workflow-issue-mr-driven` に切り替える（文言修正も同じ） |
| 宣言の範囲を超えた | 手順 3-2 の確認を行う。黙って続けない |
| 既存テストを壊した | 修正が範囲内なら直し、超えるなら手順 3-2 の確認へ |
| 未コミットの変更が既にある | 触らない。stash・破棄をせず、対象ファイルが既に変更されていないかを確認してから進める |
| default ブランチ上でコミットを求められた | ユーザーの指示があるときだけ行う。指示が無ければ変更を残したまま報告する |
| 切り替え先で `gh` / `glab` が未導入・未認証 | 切り替え先の手順に従って導入・認証を案内して停止する。軽作業として代替しない |
| ヘッドレスで確認が取れない | 確認を行わず宣言の範囲内だけを実施し、範囲超過は「ここまでで止める」に倒す |
