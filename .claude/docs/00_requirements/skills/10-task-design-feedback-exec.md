# 10-task-design-feedback-exec スキル

## 概要

設計反映フェーズの実施タスクの要件を定義する。設計反映計画書の差分一覧と書き戻し方針に従って設計反映チケットを順に実施し、設計書（要件定義書・仕様書）を実装と一致する正史に更新し、実装中に生まれた決定の経緯を DDR に残す。コードは触らない。タスクの最後に設計反映結果レポートをまとめる。

- **背景**: 書き戻しは「実装を根拠に設計書を直す」作業であり、根拠なく埋めると設計書が推測で汚れ、実装漏れを設計書の側で消すと受け入れ条件が骨抜きになる。差分一覧を証跡として、全行が「一致」になるまでを追える形にしたい。
- **目的**: 差分一覧の「書き戻す」「追記する」の行をすべて実装を根拠に反映し、全行を「一致」（または理由付きの保留）にし、マージ時点で設計書と実装が一致している状態を作る。
- **スコープ**:
  - 含む: 設計反映チケットの実施（着手から完了まで）、設計書の書き戻しと DDR の作成、差分一覧の消込、設計反映結果レポート（md + HTML）の作成、再開・差し戻しの扱い、呼び出し元への結果報告
  - 含まない: 差分の分類と書き戻し方針の決定（`10-task-design-feedback-plan`）、実装の修正（実装フェーズの追加チケット）、AI アセットの設計文書（AI アセット設計フェーズ）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 実装で決まったことが設計書に書き戻され、差分一覧の全行が消し込まれた状態をレビューしたい。

**[So that]** マージ後に設計書だけを読んでも実装と食い違わず、次の issue の調査・設計が正しい正史から始められるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、設計反映計画書（差分一覧・書き戻し方針）・設計反映チケット群・実装の差分と作業ログ・設計書を入力に進めなければならない。
- When 設計反映チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットが担う設計書だけを書き戻さなければならない。
- When 設計書を書き戻すとき、Shall スキルは実装（ファイル・シンボル・テスト）を根拠に該当の節を更新し、推測で埋めてはならない。本文はその時点の正史だけになるよう書き換え、経緯（実装中に決めた理由・採らなかった案）は DDR に残す。
- When 設計に無かった決定事項を追記するとき、Shall スキルは要件定義書の受け入れ基準・仕様書のテストシナリオが実際のテストと対応するよう更新し、テスト ID を合わせなければならない。
- When 差分一覧の行を反映し終えたとき、Shall スキルは設計反映計画書のその行を「一致」に更新しなければならない（書き戻しの証跡）。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 設計反映チケットを完了するとき、Shall DoD（設計書の節が実装と一致 / 決定事項が追記され経緯が DDR にある / 差分一覧の該当行が「一致」）が根拠付きで満たされ、プレースホルダが無く、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 1 枚の設計反映チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の設計反映チケットに着手しなければならない（タスクの切れ目ではない）。
- When すべての設計反映チケットが完了したとき、Shall スキルは設計反映結果レポートを仕上げ、結果報告（完了したチケットの一覧、更新した設計書と DDR の一覧、残った差分とその理由、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「差分一覧の全行が『一致』か、残った行に理由があるか」「書き戻した内容の根拠（ファイル・シンボル）」「設計書の構成・用語が壊れていないか」「設計書の書き換えで受け入れ条件が骨抜きになっていないか（実装漏れを設計側で消していないか）」を挙げなければならない。

### 代替フロー

- If 再開時に設計反映チケットが作業中で書き戻しが途中の場合、Then スキルは作業ログの「現在地」と差分一覧の消込状態から続きを進め、同じ節を二重に直してはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは設計書と DDR を直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残し、レポートを追記・修正しなければならない。
- If 書き戻しの途中で新たな差分（計画の差分一覧に無いずれ）を見つけた場合、Then スキルは差分一覧に行を追加して分類し、自分のチケットの範囲なら反映し、範囲外なら残した理由とともに結果報告に含めなければならない。

### 例外フロー

- If 書き戻しの途中で実装側の誤りに気付いた場合、Then スキルはコードを直さず、差分一覧に「実装漏れ」として追記し、実装の追加チケットの提案を結果報告に含めなければならない（設計書を実装の誤りに合わせない）。
- If 設計書と実装の両方が曖昧でどちらに合わせるべきか決められない場合、Then スキルはその行を保留のまま両案を書き、判断を人間レビューに委ねなければならない（勝手に決めない）。
- If ソースコードや `.claude/` 配下への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、コードに関することは「実装漏れ」に、AI アセットに関することは作業ログの「AI アセットに反映すべき内容」に記録して先へ進まなければならない。
- If 設計反映計画書が無い、またはチケットが差分一覧と対応しない場合、Then スキルは書き戻しを始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。
- If HTML ビューの機械的検査で問題が見つかった場合、Then スキルは解消してから完了しなければならない。

### 設計反映結果レポートの内容

- When すべての設計反映チケットが完了するとき、Shall 設計反映結果レポートが作業領域のレポートの置き場に 1 つあり、同じ名前の HTML ビューが併存しなければならない（Markdown が正文。テンプレートのコピーと Edit で作り、機械的検査の結果を作業ログに残す）。
- When 設計反映結果レポートを書くとき、Shall 機構のレポートの節順に沿って次を含めなければならない: 更新した設計書と節・DDR の一覧（根拠つき）、差分一覧の消込結果（一致 / 保留とその理由）、実装漏れの一覧と提案、想定と異なった点、残課題。

### 設計反映チケットの扱い

- When 設計反映チケットが作業中のとき、Shall そのチケットの「やってよいこと」はアプリ本体の設計文書の置き場（DDR を含む）・計画書の差分一覧の消込・レポートの置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、ソースコード・テスト・`.claude/` 配下を書けてはならない。
- When チケットを新しいコンテキスト・別モデル（チケットの実行者がタスクのモデルと異なる場合）で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。チケット群を並列に実施してはならない（DDR i0001-23）。
- When 設計反映チケットの人間レビュー要否を参照するとき、Shall チケットの記載に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 実装の差分・作業ログを参照するとき、Shall スキルはそれらを書き換えず、書き戻しの根拠として引用しなければならない。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルは更新後の設計書と設計反映結果レポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

---

## 前提条件

- `10-task-design-feedback-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、設計反映チケットが未着手にあること
- 設計反映チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- レポートのテンプレート（md + HTML）と、チケットの着手・完了の提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。決められない差分は保留して両案を残し、人間レビューで確定する
- **ビジネス的制約**: 書き戻しの採否と「実装を正としてよいか」の最終判断は MR 上の人間レビューが行う
- **外部的制約**: コードは触らない。設計文書は正史のみ・経緯は DDR という機構のドキュメント体系に従う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 差分一覧の行 → 設計書の節 → 実装の根拠 → DDR と辿れ、消込の状態がレビューで確認できる |
| 一貫性 | 設計書の更新は既存の構成・用語・テンプレートに合わせる。レポートの節順・視覚語彙・検査は他の実施タスクと同じ |
| 簡潔性 | 書き戻しは実装と一致させるのに必要な範囲に留め、無関係な節のリライトをしない |
| 冪等性 | 再開時に同じ節・同じ DDR を二重に作らない |
