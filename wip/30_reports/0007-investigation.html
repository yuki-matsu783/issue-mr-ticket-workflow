実施した内容と結果

  1. 1

    SubagentStart の実在と agent_id / agent_type は仕様どおり ◎良 根拠: 公式 hooks リファレンス（イベント一覧・matcher 表）/ Agent SDK hooks

    SubagentStart は「When a subagent is spawned」として実在し、matcher は agent type（general-purpose・Explore・Plan・カスタム名）に対して評価される。§1 の登録は matcher 無しなので問題ない。agent_id / agent_type はサブエージェント内で入る共通フィールドで、Python SDK では SubagentStart / SubagentStop の必須フィールド。agent_type の値はエージェント名（例 "Explore"）。

    根拠を見る（引用と出力） 
    | `SubagentStart` | When a subagent is spawned |
| `SubagentStart` | agent type | `general-purpose`, `Explore`, `Plan`, custom agent names … |
agent_id / agent_type: 「required fields on `SubagentStart` and `SubagentStop`」（Python SDK）

    結論

    §12 T4 のうち「SubagentStart イベントの実在」「agent_id」は確認済みとして消せる。

  2. 2

    model は SubagentStart の入力に含まれない（公式は SessionStart のみ） ✕問題 根拠: 公式 hooks リファレンス「Only SessionStart hooks can receive a model field」

    仕様 §2 と subagent-start-check 制御方式 4 は、SubagentStart の入力の model とチケットの executor を比較して WF801 を出す設計。しかし公式は model を受け取れるのは SessionStart だけと明記し、「常に含まれるとは限らない」とも断っている。SDK 側にも SubagentStart の model は現れない。

    根拠を見る（引用と出力） 
    公式: 「Only `SessionStart` hooks can receive a `model` field, and Claude Code doesn't always include it.」
仕様 §2: 「agent_id / agent_type / model（SubagentStart。model が無い版では実行者の比較を行わない）」
hook-common.sh: .tool_input.model // .model → PostToolUse Agent の tool_input.model は読める

    結論

    WF801 は仕様の縮退（PostToolUse Agent の tool_input.model と executor の事後比較）を本線にする。(a) 一本化 / (b) SubagentStart では model があれば使う、は排他ではなく (b) を残して (a) を足すのが確実。

  3. 3

    permissionDecision: "defer" は実在するが、機構では使わない ◎良 根拠: Agent SDK hooks ドキュメント（値の列挙と優先順位）

    値は allow / deny / ask / defer の 4 つで確定し、優先順位は deny > defer > ask > allow。defer は「クエリを終了して後で再開する」ためのもので、フックが判断を保留する意味ではない。機構が使う場面は無い。

    根拠を見る（引用と出力） 
    「For `PreToolUse` hooks, this is where you set `permissionDecision` ("allow", "deny", "ask", or "defer")…
 If you return "defer", the query ends so you can resume it later.」
「`deny` takes priority over `defer`, which takes priority over `ask`, which takes priority over `allow`.」

    結論

    §12 T3 の「defer の採用は別途判断」への答えは「採用しない」。理由を 1 行書いて TBD を閉じられる。

  4. 4

    tool_response の構造は公式に記載が無い △注意 根拠: 公式 hooks リファレンス（PostToolUse の節が取得範囲外）/ Agent SDK hooks

    3 つの URL を読んだが、PostToolUse の入力例も tool_response のフィールド定義も見つからなかった。exit_code / exitCode / returnCode / code のどれが来るかは公式からは決められない。

    根拠を見る（引用と出力） 
    取得した URL: code.claude.com/docs/en/hooks / hooks.md / agent-sdk/hooks
いずれも PostToolUse の入力例なし（PreToolUse の例のみ提示）
検索結果に「tool_response は plan と filePath を持つ」= Plan ツール固有の記述のみ

    結論

    仕様の現行方針（4 候補を順に読む・どれも無ければ 0・interrupted は失敗）を維持し、実測後に 1 つへ絞る。§12 T7 は残す。

  5. 5

    matcher は tool 名の完全一致または正規表現で、WebFetch / WebSearch を対象にできる ◎良 根拠: 公式 hooks リファレンスの matcher 評価表

    PreToolUse / PostToolUse / PostToolUseFailure / PermissionRequest / PermissionDenied は tool 名に対して評価される。WebFetch|WebSearch と書けば強制対象にできる。§1 の登録表の matcher も、この規則で正しく評価される（mcp__.* は . を含むので正規表現）。

    matcher の値評価
    "*" / "" / 省略すべてに一致
    英数字・_・-・空白・,・| だけ完全一致、または | / , 区切りの完全一致リスト
    それ以外の文字を含むJavaScript の正規表現（アンカーなし）
    根拠を見る（引用と出力） 
    | `PreToolUse`, `PostToolUse`, … | tool name | `Bash`, `Edit|Write`, `mcp__.*` |

    結論

    D3「web の強制の可否」は技術的には可能で、残るのは方針判断（強制するか、宣言の記録に留めるか）だけ。

  6. 6

    仕様に無いフックイベントが 7 種類ある △注意 根拠: 公式 hooks リファレンスのイベント一覧

    仕様 §1 が扱う 7 イベントのほかに PostToolUseFailure / PostToolBatch / PreCompact / PostCompact / PreModelSwitch / PostModelSwitch / PermissionRequest / PermissionDenied / Notification / SessionEnd がある。機構に効きそうなのは PostToolUseFailure（push 検知の終了コード判定を分けられる）と PermissionRequest（21-PermissionRequest/ が空のまま用意されている）。

    根拠を見る（引用と出力） 
    | `PostToolUseFailure` | No | Shows stderr to Claude; the tool already failed… |
| `PostToolBatch` | … | A full batch of tool calls resolves … |
| `PermissionDenied` | … | Auto mode denies a tool call … |

    結論

    この issue では扱わない（スコープは 11 本）。PostToolUseFailure の活用と 21-PermissionRequest の空ディレクトリは 3/3 の検討事項へ。

  7. 7

    exit 2 は JSON より優先し、PreToolUse をブロックする ◎良 根拠: 公式 hooks リファレンス（exit code 2 の説明とイベント別の表）

    exit 2 は JSON 出力より強く、PreToolUse ではツール呼び出しをブロックする。公式の例（block-rm.sh）は permissionDecision: "deny" の JSON を返す形で、JSON による deny も正規の経路として示されている。加えて「PreToolUse でフックがタイムアウトで打ち切られるとツール呼び出しをブロックする」ことも明記されている。

    根拠を見る（引用と出力） 
    「exit 2 means a blocking error. On events that can block, exit 2 blocks whether or not you print JSON:
 even a JSON `permissionDecision` of "allow" can't override it.」
「`PreToolUse` | Yes | Blocks the tool call」
「On `PreToolUse`, a hook canceled at its timeout blocks the tool call.」

    結論

    §12 T6 は「効く」方に傾くが明示はされていないので実測は残す。外れた場合の縮退（exit 2 + stderr）は公式が保証しており、手戻りは終了方式の書き換えに限られる。

  8. 8

    §12 T5 は #6 で「文書上は前提どおり・実機確認は未了」と結論づけられていた △注意 根拠: git show bb2a527 -- wip/30_reports/0003-investigation.md（#6 の Q3）

    #6 の結論は「tool_input のキーは Bash と同じ構造」で前提どおり。ただし実機確認は行われていない（一時フックの settings.json 登録を auto モードの分類器が拒否したため）。「2/3 でフックを登録した直後の最初の PowerShell 呼び出しで確認する」という申し送りがある。

    根拠を見る（引用と出力） 
    #6 の 0003-investigation.md Q3:
「一時フック … を .claude/settings.json に登録しようとしたが、auto モードの分類器が拒否した。迂回はしない」
「実機確認は 2/3 でフックを正式に登録した直後の最初の PowerShell ツール呼び出し
（decisions.jsonl に tool: PowerShell が残る）で自然に得られる」

    結論

    T5 は「文書上は解決済み・実機確認をこの issue で行う」。実装フェーズの検証項目に T5 を 1 行足す。

  9. 9

    git 'commit' は bash 経路では素通りする（仕様の穴） △注意 根拠: 共通仕様 §7-9 / block-direct-git 制御方式 3 / cmdpos.sh / test_cmdpos.sh:226

    共通仕様 §7-9 は「クォートで割った語（git 'commit'）は _ になり、呼び出し側は『特定できない』として扱う」と定める。実装もそのとおりで exe=git / subcmd=_ になる（CP_GITLIKE は実行体が _ のときだけ立つ）。ところが block-direct-git は「特定できないときに拒否側へ倒す」を PowerShell 経路にしか書いていないため、現状の仕様どおりに実装すると bash では許可される。

    根拠を見る（引用と出力） 
    §7-9: 「クォートで割った語（git 'commit'）は `_` になり、呼び出し側は「特定できない」として扱う」
block-direct-git 制御方式 3: 「PowerShell の入力で … 特定できないときだけ拒否側に倒す」
test_cmdpos.sh:226  run_cmd dump "'git' commit" → exe=_ / gitlike=1（git 'commit' は gitlike=0）

    結論

    制御方式 3 に「実行体が git で第 1 サブコマンドが `_` → deny WF403」を bash 経路にも足すのが §7-9 と D2 の意図に沿う。テストは BG-T01 に 1 ケース追加。
