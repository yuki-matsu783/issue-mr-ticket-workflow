# i0009-56. `web` の判定順は送信側と出力先を先に見る

## 背景

`i0009-41` は `curl` / `wget` を `web` の実行分類として通すと決め、「書き込みの穴を新たに開けない」の根拠に**出力先オプション**（`-o` / `-O` / `--output` / `--remote-name`）だけを挙げた。

ワーク境界の 2 巡目レビューで、**送信側**が勘定されていないことが分かった。

| 形 | 何が起きるか |
|---|---|
| `curl -T a.md <url>` / `--upload-file` | ローカルのファイルを外部へ送る |
| `curl -d @a.md <url>` / `--data-binary @a.md` | 同上（ファイルの中身が本文になる） |
| `curl -F file=@a.md <url>` | 同上（multipart） |
| `curl -X POST https://api.github.com/repos/…/issues` | **issue の起票**そのもの |
| `wget --post-file=a.md <url>` / `--method=PUT` | 同上 |

これらは `remote-write:<種別>`（WF206）が統制している対象そのもので、改定前は `curl` が既定拒否（WF204）だったため閉じていた。`i0009-41` の改定後は、`web` を宣言した `investigation` チケットから**宣言していないリモート書き込み**が通る。出力先を持たないので WF205 にも落ちない。

## 決定

`web` の判定を**順序つき**にする（共通仕様 §8・`workflow-guard` 制御方式 6）。

1. **送信側の形は `web` として通さない** → **deny WF206**（宣言の有無によらず）
   - `curl`: `-T` / `--upload-file` / `-d` / `--data` / `--data-raw` / `--data-binary` / `--data-urlencode` / `-F` / `--form` / `-X`（`--request`）の値が `GET` / `HEAD` 以外
   - `wget`: `--post-file` / `--post-data` / `--body-file` / `--body-data` / `--method` の値が `GET` / `HEAD` 以外
2. **出力先を持つ形は書き込みとして扱う** → 出力先パスに §8 の判定を当て、`wip/tmp/**` / `logs/**` 以外なら **deny WF205**
3. 残りが `web`。宣言と上限の両方にあれば許可、無ければ **deny WF204**

宣言があっても 1・2 は免除しない。`WG-T17` で固定する。

## 理由

- **`web` の宣言は「外部を見てよい」の許可であって「外部に書いてよい」の許可ではない**。`i0009-41` が出力先について書いたのと同じ論理が、送信側にもそのまま当てはまる
- **改定で閉じていた経路を開けてはならない**。改定前の既定拒否は乱暴だったが、副作用として送信側も塞いでいた。分類を足すときは「今まで塞がっていたもののうち、何が通るようになるか」を数える必要がある（これが 2 巡目で 3 回見つかった型）
- **順序でしか表せない**。「送信側かつ出力先あり」（`curl -T a.md -o out <url>`）のような形があるので、独立した条件ではなく判定順として書く。最も強い拒否（WF206）を先に置く
- **`-X GET` を通す**のは、`curl` が既定で GET なので `-X GET` は意味を変えないため。ここで拒否すると、単に冗長に書いた取得が止まる
- **識別子は WF206 を再利用する**。「宣言していないリモートへの書き込み」という意味がそのまま当てはまり、新しい番号を作る理由が無い

## 却下した案

- **送信側も `web` の宣言で通す**: `web` を宣言した調査チケットから issue の起票や MR の編集ができる。`remote-write:<種別>` の統制が丸ごと迂回される
- **送信側を `remote-write:unknown` として宣言できるようにする**: 種別が特定できないリモート書き込みを宣言可能にすると、`remote-write:*` の種別分けが意味を失う。`gh` / `glab` を使えば種別が特定でき、それが正しい経路
- **オプションを厳密に解析する（`getopt` 相当）**: 不要。オプション名の前方一致で足りる（`i0009-39`・`i0009-57` と同じ線引き）
- **`curl` を既定拒否に戻す**: `i0009-41` が解いた倒錯（記録が残る `curl` が塞がれ、記録が残らない `WebFetch` が通る）に逆戻りする
