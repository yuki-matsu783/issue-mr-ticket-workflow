## 方針

基準は `.claude/rules/work-defaults.md`。以下の差分を除き**基準どおり**。

### 差分 1: 全タスクの実行者をメインエージェントにする

- 何を: 実行者
- どちらへ: サブエージェント（opus / sonnet）→ メインエージェント
- なぜ: `10-task-*` スキルは `.claude/docs/10_spec/skills/` に仕様があるだけで `.claude/skills/` に実体が無い（未実装分は open issue #9・#10）。サブエージェントに渡す手順書が存在しないため、渡しても仕様どおりに動かない。`.claude/agents/` も空でエージェント定義が無い。work-defaults.md「調整の書き方」が認める、プロジェクトの一時的な事情による一律の差分として扱う

### 差分 2: 敵対的レビューは汎用サブエージェントで代替する

- 何を: 敵対的レビューの担い手
- どちらへ: 専用レビューエージェント → 観点を明示した汎用サブエージェント
- なぜ: `.claude/agents/` が空で専用エージェントが無い。要否（design / implementation は要）は基準どおり変えない

### 差分 3: ワーク境界の運用を手作業で行う

- 何を: レビュー依頼と完了の確認
- どちらへ: `work-boundary.sh` / `merge-prep.sh` → PR コメントと人間への報告
- なぜ: 両スクリプトが未実装（issue #9・#10）。承認ポイント（各ワーク後のレビュー・マージ前作業の承認・issue コメントの本文承認）は省かず、同じタイミングで人間に確認する

### 差分 4: 人間レビューを敵対的レビューに置き換える（2026-09-02 の合意で追加）

- 何を: 各ワーク境界のレビューの担い手
- どちらへ: 人間レビュー（承認④で待つ）→ ワークごとに 1 回の敵対的レビュー（サブエージェント）
- なぜ: ユーザーの明示的な指示。人間レビュー待ちで止まらず最後まで進める。`work-defaults.md` の「人間レビュー」列は要否ではなく担い手が変わる扱いにし、レビュー自体は省かない
- どうやる: 各ワーク（チケット type）の完了・push のあとに、そのワークの差分と成果物を対象とした敵対的レビューを 1 回実施する。指摘は同じ type の追加チケットで対応するか、対応しない理由を作業ログに残す
- 残る人間の承認: マージ前作業への進行と issue コメントの本文（外部への副作用のため最後にまとめて確認する）

### やってよいこと（allow）

| フェーズ | write | ops |
|---|---|---|
| 調査 | `wip/**` | read |
| 設計 | `wip/**`, `docs/**` | read |
| 実装・テスト | `wip/**`, `src/vscode-ticket-board/**` | read, build-test |
| フィードバック計画 / 全体まとめ | `wip/**` | read |

`.claude/` 配下（機構本体も `.claude/docs/` も）はどのフェーズでも変更しない。

**訂正（2026-09-02。調査 0005 と敵対的レビューの指摘 5）**。この表は当初、設計の write に `.claude/docs/00_requirement/**` と `.claude/docs/10_spec/**` を挙げ「このリポジトリの設計文書の置き場がそこであるため」と書き、実装の write に `tools/vscode-ticket-board/**` を挙げていた。どちらも誤りだった。上限設定 `scope-limits.json` の `design` は `.claude/**` を deny して `docs/**` を許可し、`implementation` は `src/**` と `tests/**` だけを許可する。`.claude/docs/` はアプリではなく AI アセットの設計文書の置き場である（`ai-asset-design` type の領分）。調査 0005 章 1・2 の結論に合わせて上の表を直した。
