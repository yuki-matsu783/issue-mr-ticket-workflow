# work-defaults ルール

## 概要

タスクの種類ごとの既定判断基準（既定の実行者・人間レビュー要否とその理由・調整してよい条件）を定める行動ルールの要件を定義する。全体計画タスクが各チケットの実行者と人間レビュー要否を提案するときの基準であり、プロジェクトごとに置き換えられる。参考実装には無い新設のルール。

- **背景**: 既定をスキルに固定するとプロジェクトごとの調整のたびにスキルを直すことになり、既定を持たないと issue ごとに提案がぶれて合意の往復が増える。「このプロジェクトでどこまで AI に任せるか」の方針はスキルの手順ではなくプロジェクトの規約に属する。
- **目的**: 全体計画の提案が「基準どおり」か「この issue では基準から外す」かの差分で読め、合意が速く済む状態を作る。
- **スコープ**:
  - 含む: このルールが定めるべき内容（タスク種ごとの既定値の項目。**並列してよいかを含む**）、全体計画からの参照のされ方、ルールが無い場合の振る舞い
  - 含まない: タスクの種類の定義（`00-workflow-issue-mr-driven.md`「タスクの構成」が正）、提案と合意の手順（`10-task-overall-plan.md` が正）、**並列実施の起動と作業ツリーの割り付けの手順**（`00-workflow-issue-mr-driven` が正）、ルールの書式（表の形などは仕様書が定める）

### issue の受け入れ条件との対応

起点: issue #50（worktree 上での機構の健全性と、1 issue 内の同一フェーズのチケット並列実施）。この更新で追加した受け入れ基準は A4 に対応する。

| issue #50 の受け入れ条件 | 満たす受け入れ基準 |
|---|---|
| A4: 1 issue の中で同じフェーズの依存しないチケットを並列に実施する方式について、採否と理由が新しい DDR に残っている | メインフロー「このルールを書くとき、Shall …**並列してよいか**…を持たなければならない」／「計画タスクは常に直列で本流を進めることと、既定は並列にしないことを明示しなければならない」（方式の既定値をこのルールが持つ。採否と理由そのものは DDR `i0050-01`・`i0050-06`、発効の保留は DDR `i0050-08` が担う） |

A1・A2・A3・A5・A6 はこの書の対象外（A1 と A5 はフックの要件・仕様、A2 と A6 は `20-common-step-worktree` と `00-workflow-issue-mr-driven`、A3 は `00-workflow-issue-mr-driven` が担う）。

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** どの種類のタスクをどのモデルに任せ、どこで人間が見るかの既定をプロジェクトの規約として決めておきたい。

**[So that]** issue のたびに同じ議論を繰り返さず、全体計画は基準からの差分だけを判断すれば済むため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 全体計画タスクが各チケットの実行者と人間レビュー要否を提案するとき、Shall このルールが置かれていればそれを基準にし、issue の性質に応じた調整は基準との差分として理由付きで提案されなければならない。
- When このルールを書くとき、Shall すべてのタスクの種類（15 種。正は `00-workflow-issue-mr-driven.md`「タスクの構成」）について、**既定の実行者**・**人間レビュー要否**・**敵対的レビューの要否**・**並列してよいか**・**その理由**・**調整してよい条件**を持たなければならない。
- When 並列してよいかを書くとき、Shall **計画タスクは常に直列で本流を進めること**（チケットの採番が本流の計画タスクだけで行われる前提が立つため）と、**実施タスクは依存しないチケットどうしなら並列にしてよいこと**、および**既定は並列にしないこと**を明示しなければならない。並列にする場合の実行者・レビュー要否の既定は変えない。あわせて、**並列実施そのものの発効が保留されている間は、この列が「よい」であっても並列にしないこと**（可否の列はタスクの性質を表すだけで、使えるかどうかは振り分けスキルが持つ）を明示しなければならない。
- When 既定の実行者を書くとき、Shall 「サブエージェント（Claude Code のサブエージェントで選択できるモデルを指定）」または「メインエージェント（モデルはセッション依存。指定なし）」のどちらかで書かなければならない。メインエージェント担当のタスク（全体計画・フィードバック計画・全体まとめ）は後者で書き、サブエージェント起動時のモデル検査の比較対象にしない。
- When このルールを書くとき、Shall タスクの実行者とは別に、**敵対的レビュアーの既定のモデル**・**タスクごとの実施回数の上限**・**レビュー対象を作った実行者と同じモデルで起動しないこと**を持たなければならない（レビュアーの既定は実行者の表とは別の表に置き、取り違えられない形にする）。
- When プロジェクトがこのルールを調整するとき、Shall ルールファイルの編集だけで置き換えられ、スキル本体の変更を要してはならない。

### 代替フロー

- If このルールが置かれていない場合、Then 全体計画はスキルの既定（リスクの高いタスクは人間レビュー要）を使い、基準が無かった旨を全体計画書に書かなければならない。
- If タスクの種類が追加された場合、Then このルールに行を追加すれば全体計画の提案に反映されなければならない。

### 例外フロー

- If このルールに載っていないタスクの種類のチケットを起こす必要がある場合、Then 全体計画はスキルの既定に倒し、基準に無いことを明示してユーザーと合意しなければならない（黙って既定を作らない）。
- If 既定のモデルで敵対的レビュアーを起動できない場合（そのモデルが使えない・呼び出しがエラーを返す）、Then このルールは代替の決め方を示さなければならない。代替に求めるのは「レビュー対象を作った実行者と別のモデルであること」だけで、モデルを差し替えても実施回数は消費したものとして数え、差し替えたモデル名は切れ目の記録に残さなければならない（レビューを省いたことにしない）。

### 見直しの入力

- When フィードバック計画や振り返りで既定判断基準を見直すとき、Shall チケットに機械的に記録された着手・完了の時刻と作業ログを材料にでき、見直しの結果はこのルールの編集として反映されなければならない。

## 前提条件

- タスクの種類と担当（メインエージェント / サブエージェント）は `00-workflow-issue-mr-driven.md`「タスクの構成」が正であること
- チケットの着手・完了の時刻は提供コマンドが機械的に記録すること
- 行動ルール（章スキーマ対象外）であり、効くタイミングは全体計画のとき

---

## 制約条件

- **技術的制約**: 実行者に指定できるのは Claude Code のサブエージェントで選択できるモデルに限る
- **ビジネス的制約**: 基準は提案の既定であって強制ではない。issue ごとの最終決定は全体計画でユーザーと合意する（必要になれば強制への格上げを別途検討する）
