# design-docs — アプリ本体の設計文書（apl/<アプリ名>/docs/）の正典規約

アプリ本体の設計文書は「その時点で有効な正史」だけを書き、決定の経緯は DDR に、用語の定義は用語辞書に置く。requirement は利用者から見た振る舞い、spec は内部構造。適用範囲は `apl/**` だけで、AI アセットの設計文書（`.claude/docs/**`）は `ai-asset-design-docs` ルールが独立に持つ（共通する規定は両方に書き、内容を食い違わせない）。frontmatter のキーと `type` の値一覧は `markdown-docs` ルールが正で、ここでは再掲しない。

## 適用範囲

- `apl/**` の成果物を作成・変更するとき（アプリルート `apl/<アプリ名>/` の下の ソース `src/`、テスト `test/`、設計文書 `docs/`、ビルド設定）。設計文書は `docs/00_requirement/` / `docs/10_spec/` / `docs/20_ddr/` / `docs/90_glossary/`
- 文書の内容の妥当性は MR 上の人間レビューが判断する。このルールは形（置き場・書き分け・書いてはいけないもの）を定める

## 構造・配置

- アプリの成果物はアプリごとに `apl/<アプリ名>/` を**アプリルート**としてまとめる。直下にソース `src/`、テスト `test/`、設計文書 `docs/`、ビルド設定（`package.json` 等）と入れ子の `.gitignore` を置く
- 設計文書の置き場はアプリルートの `docs/00_requirement/`（要件定義書）/ `docs/10_spec/`（仕様書）/ `docs/20_ddr/`（DDR）/ `docs/90_glossary/`（用語辞書）の 4 つ。他のディレクトリに設計文書を置かない
- 1 アプリ 1 対象。要件定義書と仕様書は `00_requirement/<アプリ名>.md` と `10_spec/<アプリ名>.md` の同名 1:1（AI アセット側のような種類ディレクトリを持たない）。複数の対象を立てたくなったら文書を分けずにアプリの分割を検討する
- 仕様書の種別ごとの節構成の正は `.claude/docs/10_spec/skills/20-common-step-spec.md`、要件書のテンプレートは `20-common-step-requirement` スキルの `assets/requirements.template.md`。ここで再掲しない
- requirement と spec の書き分け: requirement は利用者から見た振る舞い（何ができ、何が拒否され、何が出力されるか）、spec は内部構造（コマンドの構成・状態の持ち方・判定の手順・データの形式）。requirement に内部構造が混ざったら spec へ移す
- DDR は設計上の決定（複数案から選んだ・方針を変えた）ごとに 1 ファイル。命名は issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md`。issue を持たない DDR を作らない
- DDR の一覧は各 DDR の frontmatter から生成する。手書きの一覧を保守しない（生成手段は仕様書が定める）
- 用語辞書は「用語の定義（意味・目的・他の用語との関係）」の正。振る舞いの正（When / Shall）は requirement / spec が持ち、辞書と要件書で役割を重複させない

## 書式・可読性

- requirement / spec は正史のみ。検討の経緯・却下した案・過去の版の内容・変更履歴の表・「以前は〜」を本文に残さない（履歴は git のコミット履歴と DDR で追う）
- 要件書の形: 章順は 概要（背景・目的・スコープ。「含まない」には担い先）→ ユーザーストーリー → 受け入れ基準 → 前提条件 → 制約条件 → 依存関係 → 非機能要件。受け入れ基準は EARS（When 〜 Shall / If 〜 Then / Shall not）で書き、節は **メインフロー → 代替フロー → 例外フロー → 規約節（0〜3）→ 他のスキル・機構との整合（0〜1）** の順。先頭 3 節はこの文言で始め、規約節の見出しは `規約: <対象>` で始める
- メインフロー節は EARS 箇条書きの前に mermaid の `flowchart TD` を 1 つ置く。図は箇条書きの要約で、図にだけある情報を作らない。1 図の `M<n>` ノードは 15 まで（離脱先と次節への参照ノードは数えない）。超えたら利用者から見た一区切りで節に分け、節ごとに 1 図を置いて参照ノードで繋ぐ
- 代替・例外フローの各項目は先頭に識別子（`**[A1]**` / `**[E1]**`）を持ち、図の離脱先の参照ノードの ID と一致させる
- 自由記述（散文）で書いてよいのは 概要の導入・背景・目的 の 3 か所だけで、合計 600 字以内。他の章は定型（箇条書き・表・EARS・図）で書く
- 要件書に「関連するドキュメント」節・「レビュー記録」節・「変更履歴」節を置かない（関連は依存関係の節で足り、レビューの経緯は MR と DDR で追う）
- 要件書を新規作成するとき、または受け入れ基準を追加・変更する更新をするときは、概要章に「issue の受け入れ条件との対応」の小節を置き、起点の issue の受け入れ条件を全件、それを満たす受け入れ基準と対応づける（受け入れ基準を変えない更新と、既存文書への遡及適用は求めない）
- DDR は 背景 / 決定 / 理由 / 却下した案 / 影響 を持つ
- 辞書のエントリは 用語名 + 定義（2〜4 行）+ 別名・禁止表記（旧称・使わない言い方。あれば）。定義は辞書の中だけで読めて完結させ、設計書へのリンクに頼らない
- 辞書に振る舞いの要件（When / Shall、判定基準・数値・手順）を書かない
- 収録済みの用語を文書で使うときは辞書の表記に従い、初出箇所で辞書へリンクし、文書内で定義を再掲しない。禁止表記を使わない
- 辞書に載せる語は、複数の文書で使われ、かつ指し先や表記が揺れうるプロジェクト固有語（アプリが導入した概念・コンポーネント名・用語の読み替え規則）に限る。一般的な技術用語は載せない
- frontmatter（`type` / `title` / `description` / `tags` / `keywords`）の規約は `markdown-docs` ルールに従う（再掲しない）

## セキュリティ

- 該当なし — 設計文書は共有前提の記述で秘密情報を含めない一般則は文書全般の規約（`markdown-docs`）が担い、設計文書に固有の規定は無い

## 堅牢性

- マージ済みの DDR は本文を変更しない。後続の決定で無効になったときは frontmatter の状態（置き換え済み / 廃止）と置き換え先だけを更新する
- マージ済み DDR の内容を訂正する必要が出たら、新しい DDR で置き換え、旧 DDR は frontmatter の状態の更新だけで扱う（本文の書き換えで直さない）
- 新しい固有語は、まず辞書に定義してから設計書で使う（辞書が先、設計書が参照する）。収録語をリネームしたときは同じチケットの中で辞書を更新し、旧称は別名・禁止表記に残す
- spec は対応する requirement より先に変えない（要件の変更が先）。要件側の誤り・不足を仕様側の辻褄合わせで吸収しない
- 他の文書と矛盾する記述を見つけたら、片方だけ直さず、矛盾する文書を特定して同じ変更の中で揃える

## パフォーマンス

- 該当なし — 設計文書は読み物で実行時の性能観点が無い。探索は frontmatter 索引で足りる長さと粒度（1 対象 1 文書）を保つことは「構造・配置」が担う

## テスト・機械的検査

- 章立て・受け入れ基準の節順・禁止節の不在・メインフローの図のノード数・図と節の識別子の一致・規約節の命名と個数・自由記述の分量・DDR の命名・一覧の生成状態の機械的検査は、設計文書検査（仕様書が定める）に統合する。整備されるまでは、要件書・仕様書の作成手順（`20-common-step-requirement` 処理フロー 14、`20-common-step-spec` 処理フロー 5）のセルフレビューと MR 上のレビューで見る
- 仕様書の「要件との対応」表は要件の受け入れ基準を全件カバーする（行数が一致する）。実現箇所の無い要件（実装漏れ）と要件の無い節（過剰仕様）を仕様書の書き終わりに確かめる
- レビューで見る観点は本ルールの各章。別のチェックリスト文書を作らない
