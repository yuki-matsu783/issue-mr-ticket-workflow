決めた方針の承認 / 決められない点の判断

  • ◇ の副題を「決めた方針の承認 / 決められない点の判断」にした。仕様は見出しの文言だけを定めていて副題は定めていないので、両方の使い方が読めるようにこちらで決めた

ほぼ確実

  • 消し込み表の列は「走査した記録 / 抽出した項目 / 行き先」の 3 列。仕様の記述をそのまま列にした
  • 番号は末尾に足し、既存の BD001〜BD005 / FN001〜FN003 を振り直していない
  • 引数・環境の誤りのテストは原因ごとに ID を分けず、1 つの ID に 3 原因を並べた
  • SKILL.md には要約だけを書き、正は仕様書という関係を崩していない

確かめられなかったこと（この結果が言っていないこと）

  • テンプレートの見出しの変更が、実際のレポート作成で読みやすくなったか: 効果は eval でしか測れず、実装フェーズでは eval を実行しない → 人間の判断

実施した内容と結果

  1. 1

    レビューの重みの ◇ の見出しを「判断が欲しい」に変えた ◎良 根拠: 20-common-step-report-view 仕様 OUT ひな形の視覚語彙

    report.template.html の 2 か所（冒頭のガイドコメントと #focus-want のラベル）と report.template.md の 1 か所を変えた。副題は「決めた方針の承認 / 決められない点の判断」とし、本文のガイドも「自分で決めた判断と根拠、または決めずに候補と比較軸を並べた点」に直した。

    根拠を見る（実行コマンドと出力） 
    grep -rn '承認が欲しい' .claude/skills/*/assets/
=> 0 行

grep -rn '承認が欲しい' .claude/skills/
=> .claude/skills/20-common-step-report-view/SKILL.md:25（S4 の担当）

    結論

    調査タスクのように「決めない」と定められたタスクでも、判断を仰ぐ項目の置き場ができた。

  2. 2

    フィードバック計画のひな形に消し込み表の節を足した ◎良 根拠: 10-task-feedback-plan 仕様 OUT ひな形・処理フロー 2

    「確認した記録の範囲」と「改善候補の一覧」の間に「消し込み表」の節を置いた。列は 走査した記録 / 抽出した項目 / 行き先（候補 #n / 既に反映済み / 候補にしない + 理由）。ガイドに「行数が『確認した記録の範囲』の件数と一致することを確かめてから候補の一覧へ進む」と「この表が無いと拾ったのに載せ損ねた項目が誰にも気づかれない」を書いた。あわせて同じひな形の類型のガイドが省略形だったので、機構の定義と同じ文言に直した。

    結論

    この issue のフィードバック計画が初版で 26 件を落とした直接の原因（表の不在）が、ひな形の側で塞がった。

  3. 3

    引数・環境の誤りを BD006 / FN004 に分けた ◎良 根拠: 両スキル仕様のエラー識別子・DDR i0010-07

    boundary.sh と finalize.sh の arg_ng が、呼び方が成立していない誤り（未知のサブコマンド・値の無いオプション・依存コマンドの不在）を前提未充足と同じ 001 で返していた。終了コードだけが 2 で違うため、番号を見た呼び手が前提を直そうとしてしまう。番号を末尾に足した BD006 / FN004 に変え、コメントも逸脱の記録から番号の意味の説明に書き換えた。

    変更は 1 行ずつの 2 か所で、既存の BD001〜BD005 / FN001〜FN003 は振り直していない。振り直すとテストの期待値・実装・レポートの記述が連動して壊れる。

    ロックアウト対策として踏んだ経路と結果 
    commit.sh -m "fix: 引数・環境の誤りを BD006 / FN004 に分ける（S2） (#10)" ...
=> OK: 2 ファイルをコミットした（96c2b1d）

boundary.sh status   => {"at_boundary":false,"position":"in_task",...}  exit 0
boundary.sh bogus    => BD006: 引数・環境の誤り — 不明なサブコマンド: bogus  exit 2
finalize.sh bogus    => FN004: 引数・環境の誤り — 不明なサブコマンド: bogus  exit 2

    結論

    提供コマンド 6 本すべてが「引数・環境の誤り」の専用番号を持つ状態に揃った。

  4. 4

    テスト BD-T19 / FN-T18 を足した ◎良 根拠: 両スキル仕様のテスト観点

    1 つの ID に 3 つの原因（未知のサブコマンド / 値を取るオプションに値が無い / 必要な外部コマンドが無い）を並べた。依存コマンドの不在は test-lib.sh の make_restricted_path bash git で jq の無い PATH を作って踏ませている。

    同じ ID の中で、-h と --help が終了 0 で使い方を出すことと、前提未充足が BD001 / FN001 と終了 1 のまま変わらないことも確かめている。番号を分けた変更が、分けるべきでない側まで動かしていないことを 1 つのケースで見られる。

    結論

    既存の BD-T03 / BD-T09 / BD-T16 / FN-T02 / FN-T10 は期待値を変えずに通っている。
