# i0001-05. HTML ビューはレポートと各フェーズの計画書に必須、全体計画書には作らず、テンプレートのコピーと編集で作る

## 背景

依頼では「レポートは HTML のビューを提供し、テンプレートをコピーしたうえで Edit コマンドで修正して使う」ことが求められた。参考実装 MR-driven-workflow は計画・レポートの両方に HTML ビューを必須とし（8 箇所で md と html を同期）、テンプレートは共通 DOM + 4 スタイルで提供している。同期の二重管理コストが弱点として挙がっている。

当初は「レポートに必須・計画書は任意」としていたが、2026-09-01 のレビューで「全体計画書には作らない、各フェーズの計画書には必須」に改めた。

## 決定

- HTML ビューは次に**必須**: `wip/30_reports/` の各実施タスクの結果レポートと全体まとめの統括レポート、`wip/20_plans/` の各フェーズの計画書（調査 / 設計 / 実装・テスト / 設計反映 / AI アセット設計 / AI アセット実装・テストの計画書）
- `wip/00_overall_plan/` の**全体計画書には作らない**（1 画面程度の短い文書で、合意はチャットと全体計画書本文で取るため）
- Markdown が正文、HTML はその視覚化。両者は同じベース名で併存させ、内容を同期させる（片方だけ更新しない）
- HTML はスキルの `assets/` にある `*.template.html` を同じベース名でコピーし、Edit で節を埋める。生成スクリプトで HTML を組み立てない
- テンプレートは自己完結（外部リソース無し）、ライト / ダーク両対応。複数デザインを提供する場合は `<style>` 以外の DOM を同一にし、同一性をテストで固定する
- 節構成と視覚語彙（結論の性質は 3 色 + 記号 + 文字、レビューの重みは色相を使わず ◆ / ◇ / ・）は MR-driven-workflow のレポートテンプレートを踏襲する。計画書のテンプレートも同じ視覚語彙を使う
- 出力後に機械的検査（プレースホルダ 0 件・リンク破断 0 件・重複 ID 無し・外部依存 0 件・`<style>` が 1 つ）を行い、結果を作業ログに残す

## 理由

- 各フェーズの計画書は「計画 → 人間レビュー → 実施」の型でレビューの対象になる。計画のレビューは調査・設計・実装の方向を正す最も効く機会であり、レポートと同じ読みやすさで見せる価値がある
- 全体計画書はフェーズ列と方針の一覧で短く、合意はチャットで取って本文に記録する。HTML の同期コストに見合わない
- コピーして編集する方式は、AI が節の意味を理解しながら埋めるため、生成スクリプトより内容の質が安定し、テンプレートの改訂も HTML を直すだけで済む
- Markdown を正文にすることで、frontmatter 索引・grep・DDR への反映が Markdown だけを対象にできる

## 却下した案

- **計画書の HTML を任意にする（当初案）**: 同期箇所が減るが、計画のレビューがフェーズごとに Markdown と HTML で揃わず、レビュアーの読み方が一定しない。計画書はレビュー対象なのでレポートと同じ扱いにする
- **全体計画書にも HTML を必須にする（MR-driven-workflow 方式）**: レビュー体験は揃うが、全体計画書は短く合意もチャットで取るため、同期コストだけが残る
- **Markdown から HTML を生成するスクリプトを作る**: 同期漏れが無くなるが、節構成・視覚語彙を Markdown 側の記法で表現する規約が別途要り、依頼の「コピーして Edit で修正」から外れる
- **HTML だけを正文にする**: ファイルが 1 つで済むが、frontmatter を持てず索引・検索の対象にできない

## 影響

- 要件定義書 F 節、`10-task-overall-plan.md`（全体計画書は HTML 無し）、各計画タスクの要件定義書（計画書に HTML ビュー必須）
- push 前チェックに「レポート・計画書の md と html の同期」を含める
- テンプレートはレポート用と計画書用を用意し、初版は MR-driven-workflow の `reports-clean.template.html` を土台に、参考実装固有の記述（flow-id 等）を除いて作る
