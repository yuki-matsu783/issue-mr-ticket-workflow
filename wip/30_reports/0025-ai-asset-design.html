  1. 1

    worktree では cwd 側の作業ツリーを採る ✕問題 根拠: 境界レビュー A3、hooks.md:594-602

    i0009-20 が登録を ${CLAUDE_PROJECT_DIR} 基準にし、i0009-22 が git rev-parse --show-toplevel を禁じた結果、HOOK_ROOT は本流のチェックアウトを指し続ける。公式は「Claude が worktree に入ると ${CLAUDE_PROJECT_DIR} はセッション開始時のプロジェクトルートに留まる」「cwd が Claude に追随する」と明記している。すると workflow-guard は本流の空の wip/10_tickets/10_doing/ を見て「0 枚 → 即座に許可」となり、すべての書き込みと実行が素通りする。旧仕様（cwd で git rev-parse）なら worktree 側に解決していたので、0019 の改定で悪化していた。決定: (1) cwd が HOOK_ROOT と異なり、cwd から上向きに .claude を持つディレクトリが見つかるならそれを作業ツリーとする、(2) そうでなければ HOOK_ROOT。上向き探索は [ -d ] の繰り返しで git を呼ばない。スクリプトの置き場は常に HOOK_ROOT、logs/ と wip/ は作業ツリー側。

    実測への依存: あり（フェーズ 4c で worktree に入って確かめる）

    根拠を見る（読んだ箇所と出力）

  2. 2

    web の判定順は送信側を先に見る ◎良 根拠: 境界レビュー A4、i0009-41 の理由

    i0009-41 は「書き込みの穴を新たに開けない」の根拠に出力先オプションだけを挙げ、送信側を勘定していなかった。curl -T a.md <url>（アップロード）、curl -d @a.md <url>（ファイルの中身を本文に）、curl -F file=@a.md（multipart）、curl -X POST https://api.github.com/repos/…/issues（issue の起票そのもの）、wget --post-file= / --method=PUT — これらは remote-write:<種別>（WF206）が統制している対象で、改定前は既定拒否で閉じていた。決定: 判定を順序つきにする。(1) 送信側は宣言の有無によらず deny WF206（-X GET / --method=GET は通す）、(2) 出力先を持つ形は書き込みとして WF205 の判定、(3) 残りが web。宣言があっても (1)(2) は免除しない。

    実測への依存: 無し（オプションの意味論）

    根拠を見る（読んだ箇所と出力） 
    送信側として拒否する形（deny WF206。宣言の有無によらず）
  curl:  -T / --upload-file / -d / --data / --data-raw / --data-binary /
         --data-urlencode / -F / --form / -X（--request）の値が GET・HEAD 以外
  wget:  --post-file / --post-data / --body-file / --body-data /
         --method の値が GET・HEAD 以外

順序でしか表せない理由:
  「送信側かつ出力先あり」（curl -T a.md -o out ）の形があるので
  独立した条件ではなく判定順として書く。最も強い拒否（WF206）を先に置く

-X GET を通す理由: curl は既定で GET。-X GET は意味を変えないので、
  ここで拒否すると冗長に書いた取得が止まるだけ

識別子は WF206 を再利用（「宣言していないリモートへの書き込み」がそのまま当てはまる）
DDR: i0009-56 / テスト: WG-T17

    結論

    「web の宣言は外部を見てよいの許可であって、外部に書いてよいの許可ではない」を判定順に落とした。分類を足すときは「今まで塞がっていたもののうち何が通るようになるか」を数える必要がある。

  3. 3

    出力先の取り出しは cmdpos_args の走査 ◎良 根拠: 境界レビュー A5、cmdpos_operands の定義

    i0009-41 の影響と 0022 の申し送りは、出力先オプションの照合に cmdpos_operands（i0009-39）が使えると書いていた。実際には使えない — オプション本体（-o）が落ちるので、どれが URL でどれが出力先かを区別できない。この結果に §8 の判定を当てると、出力先を持たない curl <url> でも URL がパスとして判定され、WG-T15 が固定した「通る」と食い違う。決定: cmdpos_args の引数列を先頭から走査し、-o / --output / --output-dir（wget は -O）を見つけたらその次の語を出力先とする（等号形は前方一致）。curl -O / --remote-name と wget の既定は出力先の語を取らず、URL の basename を作業ツリー基準のカレントに作るものとして扱う。:// を含む語は URL とみなし出力先として扱わない。

    実測への依存: 無し（関数の定義と当てる先の対応）

    根拠を見る（読んだ箇所と出力） 
    cmdpos_operands の定義（§7-9）
  CP_ARGS[i] から `-` で始まる語と `--` 以降を除いた位置引数

curl https://x/y -o wip/tmp/a   → REPLY_OPERANDS = [https://x/y, wip/tmp/a]
curl -o wip/tmp/a https://x/y   → REPLY_OPERANDS = [wip/tmp/a, https://x/y]
curl https://x/y                → REPLY_OPERANDS = [https://x/y]   ← 出力先なし
  → どれが URL でどれが出力先か区別できない

cmdpos_operands が悪いのではなく、当てる先を間違えていた
  （rm / git rm のように「位置引数だけが意味を持つ」コマンド向けの関数）

却下: cmdpos.sh に cmdpos_option_value を足す（等号形・結合形に踏み込む。i0009-39 の範囲外）
      web では常に書き込みの判定を当てる（curl  が WG-T15 と矛盾）
      REPLY_OPERANDS の最後の語を出力先とみなす（curl -o out  で破れる）
DDR: i0009-57 / 0022 の申し送りも訂正

    結論

    i0009-39 の線引き（ライブラリは整形まで / 意味論は呼び手）は守られた。0022 の申し送りも訂正した。
