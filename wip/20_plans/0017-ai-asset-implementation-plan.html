この計画で何をするか

設計フェーズで固めた正史から、アセット本体 57 件を作る実装チケット 9 枚を起こす。あわせて、この issue で足す機械テスト 33 件を各ステップに配り、旧名 111 件の参照更新と 0 件判定の検索を決め、中核 3 か所のロックアウト対策を付ける。着手の前に、19 アセットの仕様書に eval の表が無いという設計の欠落を設計チケット 1 枚で閉じる。

決めたこと

  • 保留 P6（作成物の割り付け）: 57 件を 9 枚に割った。固定順（設定・定義 → 中核 → 中核のテスト → スキル・エージェント → 参照更新）に並べ、連番を実行順に振った
  • 保留 P2（boundary.sh をこの issue の切れ目で使うか）: 使わない。作りかけのコマンドに自分の進行を依存させると失敗の切り分けができず、切れ目の証跡が 2 系統に割れる。実運用は次の issue から
  • 保留 P1'（session-start.sh の 1 行）: S4（チケット 0027）。ロックアウト対策は SE-T10（SE-T05 後半はパスを踏まないので使わない）
  • 設計への差し戻し: 19 アセットの eval の表が無い。実装計画で埋めず、設計チケット 0023 を先頭に置く

提供コマンド自身を作るステップ（S2・S3）

boundary.sh と finalize.sh はこの機構が自分の作業に使う提供コマンドなので、書いた直後の 1 回目が壊れているとそのチケットを終わらせる手段が無くなる。両ステップの手順に次を明示する。

  1. スクリプトを書く
  2. commit.sh で自分をコミットする（この 1 回目が検証を兼ねる。boundary.sh / finalize.sh 自身はまだ手順に組み込まない）
  3. テストを書いて run-tests.sh --filter で対象だけ実行する
  4. ticket.sh complete <番号>
  5. 失敗したら git reset --hard <base_sha> で戻す（base_sha はチケットの frontmatter に機構が記録している）
