# i0009-24. push 検知を状態非依存にし、進捗の起点は呼び手が持つ

## 背景

`push-detect.sh` の `push_detect` は push の成功を 3 条件で判定していた。

1. コマンド列に `push.sh` または実行位置の `git push` がある
2. HEAD がリモートに反映された（`@{upstream}` との一致）
3. **`push-state.json[b].sha` が HEAD と異なる**（前回 push から進んでいる）

この関数を `post-push-compact-prompt`（正）と `post-push-usage-report`（共有）の 2 本が使う。ところが compact-prompt は本体の最後で **`push-state.json[b]` を `{sha: head, …}` に更新する**。

境界レビュー（付録 A の R2）が指摘したのは次の帰結である。

- compact-prompt が先に走ると、usage-report が `push_detect` を呼んだ時点で `push-state.json[b].sha == HEAD` になり、**条件 3 が偽**。usage-report は集計しない
- `i0009-21` のとおりフックは**並列**に走るので、実際にはどちらが先かが不定 = **レース**（時々レポートが出る／出ない）
- さらにレポート名 `report-<branch>-<count>.md` の `count` も `push-state.json[b].count` を読むので、compact-prompt の `count+1` の前か後かで番号がずれる

受け入れ条件の「push 成功で対応工数レポートが出る」が満たせない。

## 決定

- **`push_detect <起点 sha>` は状態ファイルを読まず書かない**。条件 3 の比較対象は**呼び手が引数で渡す**
- 起点は呼び手ごとに別の状態から取る:
  - `post-push-compact-prompt` → `logs/push-state.json[b].sha`（このフック専用の状態）
  - `post-push-usage-report` → `logs/usage/<branch>.json` の **`last_push_sha`**（新設）
- `logs/usage/<branch>.json` に **`last_push_sha`** と **`push_count`** を足す。レポート名の `<count>` は `push_count` で数え、`push-state.json` の `count` とは独立にする
- `post-push-usage-report` は **`push-state.json` を一切参照しない**
- `HK-T13`（lib 単体）から状態ファイルの読み書きを外し、`UR-T07` に「`push-state.json` が先に `sha = HEAD` へ更新された状態でも `last_push_sha` が古ければ検知が通る」を足す

## 理由

- **共有ライブラリが特定の状態ファイルを持つ設計が誤り**。`i0009-17`（ライブラリは分類まで / 照合は呼び手）と同じ形の問題で、「前回どこまで進んだか」は呼び手ごとに違う概念なのに、ライブラリが 1 つに決めていた
- 起点を引数にすれば、フックが何本増えても、どの順で走っても互いに影響しない。並列実行の下で正しさが順序に依存しない形になる
- `usage/<branch>.json` には既に `since_sha`（投稿の起点）があり、状態を持つ場所として自然。`since_sha` は「投稿に成功したら進む」で、`last_push_sha` は「push を検知したら進む」と役割が違うので別のキーにする
- `push_count` を分けたのは、レポートの通し番号が compact-prompt の実行有無に左右されないようにするため（compact-prompt を緊急停止しても usage-report の番号は連続する）

## 却下した案

- **登録順を「usage-report を先」にする**: `i0009-21` のとおり並列実行なので順序を指定できない
- **`push-state.json` の更新を Stop など後段の 1 か所に移す**: 「どのフックが更新するか」を新たに決める必要があり、Stop は push を伴わないターンでも走るので条件が増える。起点を分ける方が単純
- **usage-report も `push-state.json` を読み、自分用のキー（`usage_sha`）を同じファイルに足す**: 2 本のフックが同じファイルを read-modify-write することになり、`i0009-23` のロックが要る。ファイルを分ければロックが要らない
- **検知条件 3 を捨てる（進んでいるかを見ない）**: `push.sh` を空振りで実行しただけでレポートが出る。「push するものが無かった成功は検知しない」という既存の意図を壊す
