# 10-task-investigation-plan スキル

## 概要

フェーズ列で全体計画の次に来る調査計画タスクの要件を定義する。調査フェーズで**何を明らかにするか**を決めるタスクであり、全体計画書の「判断が必要になりそうな点」と issue の受け入れ条件から問いを立て、調査計画書にまとめ、問いに答える調査チケット群と、次のフェーズの計画チケットを起こして調査計画チケットを完了する。調査そのものは行わない（`10-task-investigation-exec`）。

- **背景**: 調査を計画なしに始めると、読む範囲が際限なく広がる一方で、後の計画（設計・実装・AI アセット設計）が判断に使う答えが揃わない。「どの問いに答えれば次の計画が立てられるか」を先に決め、人間がその問いの妥当性を見てから調べ始めたい。
- **目的**: 次の計画タスクが判断に使える答えの一覧（調査観点）を定め、1 観点のまとまり = 1 チケットで調査を区切り、調査の範囲・方法・成果物の形をレビュー可能な計画書として残す。
- **スコープ**:
  - 含む: 調査計画書の作成、調査観点の導出、調査チケット群と次の計画チケットの作成、調査計画チケットの着手から完了まで、「対象なし」の扱い、再開時の扱い、呼び出し元への結果報告
  - 含まない: 調査の実施と調査結果レポート（`10-task-investigation-exec`）、フェーズ列の決定（`10-task-overall-plan`）、タスクの切れ目の処理と人間レビューの依頼（`00-workflow-issue-mr-driven`）、チケットの状態遷移と宣言範囲の強制の仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 調べ始める前に「何を・どこを・どう調べ、何が分かれば次に進めるか」を 1 枚の計画で確認したい。

**[So that]** 調査が広がりすぎたり、後の計画に効かない調査に時間を使ったりせず、必要な答えが揃った状態で次の計画に入れるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、全体計画書・issue の受け入れ条件・リポジトリの現状（読むだけ。深掘りは調査チケットで行う）を入力に進めなければならない。
- When 調査計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。作業中のチケットが既に別にあるときは着手できない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 調査計画書の案ができたとき、Shall スキルは調査観点を 1 観点のまとまり = 1 チケットになるよう区切り、調査チケット群（1 枚以上、少数）を未着手に作らなければならない。各調査チケットの依存関係（先行チケット）が分かるようにする。
- When 調査チケットを作るとき、Shall その DoD は「観点『<問い>』への答えが調査結果レポートに書かれている」「根拠（ファイル・行・コマンドの出力）が添えられている」「答えが出なかった問いは理由付きで残課題に残っている」の型で書かなければならない。
- When 観点にリポジトリ外の情報が要るもの（外部技術調査。ライブラリ・ツールの比較検討など）が含まれるとき、Shall 計画書はそれを外部技術調査のチケットとして明示し、チケットの「やってよいこと」に外部への問い合わせを含めて人間の合意を得なければならない（明示のないチケットはリポジトリ内の読み取りに限る）。
- When 観点に既存のテスト・ビルドを動かして確かめる必要があるものが含まれるとき、Shall 計画書はそれを実行するコマンドと範囲とともに明示し、チケットの「やってよいこと」に実行を含めなければならない（明示のないチケットは実行しない。書き込みは一時ディレクトリに限る）。
- When 調査の確かめ方を計画するとき、Shall not 機構自身の設定（`.claude/` 配下）への一時的な変更を計画してはならない（機構の上限が拒否する経路であり、既存の記録で代えるか AI アセット実装フェーズの検証に回す）。
- When 調査チケット群を作り終えたとき、Shall スキルは全体計画書のフェーズ列で調査の次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない（次がフィードバック計画ならフィードバック計画のチケット）。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: タスクの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと（書き込んでよい範囲・実行してよい操作の分類）、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When 調査計画チケットを完了するとき、Shall 調査計画書・調査チケット群・次の計画チケットが存在し、DoD（計画書に観点・対象と方法・成果物の形がある / 調査チケットの DoD が観点に対応している / 次の計画チケットがある）がすべて満たされ、作業ログが機構のチケットテンプレートの項目に沿って書かれ、必須項目（AI アセットに反映すべき内容。0 件なら根拠）が埋まっていなければならない。完了は提供コマンドで行い、必須項目が欠けていれば完了は拒否される。
- When 調査計画チケットを完了したとき、Shall スキルは結果報告（計画書の場所、調査チケットの枚数、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。push・MR 本文の更新・レビュー依頼は呼び出し元が行う。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「調査観点が判断点と受け入れ条件を網羅しているか」「チケットの粒度と枚数」「調査の範囲が実装に踏み込んでいないか」「次の計画チケットの種類がフェーズ列と一致しているか」を挙げなければならない。

### 代替フロー

- If 全体計画書に「判断が必要になりそうな点」が無い、または受け入れ条件から調査で答えるべき問いが立たない場合、Then スキルは調査計画書に「対象なし」とその根拠を書き、調査チケットを起こさず次の計画チケットだけを作って調査計画チケットを即座に完了しなければならない（調査フェーズを省かない）。
- If 再開時に調査計画チケットが既に作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、計画書・チケットを二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは調査計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残さなければならない。
- If issue の種別が AI アセットで、調べる対象が `.claude/` 配下のアセットである場合、Then スキルは読む対象をアセット（スキル・フック・ルール・設定）とその要件・仕様・DDR とし、問いの立て方は同じでなければならない。

### 例外フロー

- If 全体計画書が無い、または対象 issue・フェーズ列が読み取れない場合、Then スキルは調査計画書を書かず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。
- If 全体計画書のフェーズ列に調査の次のフェーズが書かれていない場合、Then スキルは次の計画チケットを推測で作らず、不整合として報告しなければならない（フィードバック計画は必ず含まれるはずのため）。
- If 計画書やチケット以外への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、その箇所を計画書の対象に書いて調査チケットに回さなければならない。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

### 調査計画書の内容

- When 調査計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、調査観点（調査で答えを出す問いの一覧。それぞれがどの判断点・受け入れ条件に効くか）、問いごとの対象と方法（読む場所・確かめ方。書き込みは行わない）、調査チケットの一覧（どの問いをどのチケットが担うか）、成果物の形（調査結果レポートに何が書かれていれば次の計画タスクが判断できるか）、判断を保留した点。
- When 調査観点を導くとき、Shall 全体計画書の「判断が必要になりそうな点」と issue の受け入れ条件を出発点にし、答えが出ても次の計画に効かない問いを含めてはならない。
- When 調査計画書を書くとき、Shall 「これから何をするか」だけを書き、調査で分かったことや経過を書いてはならない（分かったことは調査結果レポートへ）。
- When 調査計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### 調査計画チケットの扱い

- When 調査計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、ソースコード・設計文書・`.claude/` 配下を書けてはならない。調査で触りたくなった箇所は計画書の対象に書き、実施タスクか後続のフェーズに回す。
- When 調査計画チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければ「要」（調査の問いの妥当性を人間が見る）を既定としなければならない。
- When 調査チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければ「要」を既定としなければならない。

### 他のスキル・機構との整合

- When 全体計画書のフェーズ列・受け入れ条件との対応を参照するとき、Shall スキルはそれを書き換えず、疑義があれば結果報告の「見てほしい点」に書かなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When チケットの着手・完了・作業ログの書き方を説明する必要があるとき、Shall not スキルは手順を再掲せず、本書の「メインフロー」と提供コマンドの使い方に従わなければならない。

## 前提条件

- `10-task-overall-plan` が全体計画書を置き、調査計画チケットを未着手に作ってから、`00-workflow-issue-mr-driven` がこのタスクを呼ぶこと
- 調査計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと、チケットの着手・完了の提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずに「判断を保留した点」と「見てほしい点」に書き、人間レビューで確定する。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 調査観点の妥当性は人間レビューで確定する。スキルは案を出し、レビュー前に調査を始めない
- **外部的制約**: 計画タスクではリポジトリを読むだけで、ソースコード・設計文書・`.claude/` 配下を書き換えない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 調査計画書とチケットに issue 番号・MR 番号が残り、各調査観点がどの判断点・受け入れ条件に効くかを辿れる |
| 一貫性 | チケットの記載事項と DoD の型は他の task スキルと同じ。フェーズの名前は `00-workflow-issue-mr-driven.md`「タスクの構成」と一致する |
| 簡潔性 | 調査計画書は 1 画面程度、調査チケットは 3〜4 枚以内を目安にし、超えるなら問いを絞るか粒度を上げる |
| 冪等性 | 再開時に計画書とチケットを二重に作らない |
