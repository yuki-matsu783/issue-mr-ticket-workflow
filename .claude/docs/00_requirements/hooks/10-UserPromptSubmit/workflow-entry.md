# workflow-entry フック

## 概要

`CLAUDE.md`「作業の振り分け」は、ユーザーからのすべての依頼を `00-workflow-issue-mr-driven` か `00-workflow-quick-request` のどちらかを Skill ツールで読み込んでから着手すると定めている。このフックは、その読み込み（本書では「宣言」と呼ぶ）が行われたことをプロンプトごとに機械的に確認し、宣言のないまま作業に入ろうとする操作を拒否して、読み込むべきスキルを AI に案内する。本書は GitLab の用語で書き、GitHub では MR → PR と読み替える。

- **背景**: 振り分けは指示だけでは読み飛ばしを検知できない。依頼の内容を問わず「宣言 → 作業」の順序を守らせ、宣言の有無を記録として追える仕組みが要る。一方で `00-workflow-issue-mr-driven` の作業中は、ワークの途中・レビュー待ち・全体まとめで作業領域を片付けたあとの push と draft 解除まで、プロンプトごとに再宣言を求めると作業が止まる。
- **目的**: プロンプトごとに宣言を強制しつつ、issue-MR 駆動の作業が進行中である間は継続とみなして再宣言を求めない状態を実現する。
- **スコープ**:
  - 含む: 宣言の記録と判定、未宣言時の拒否と案内、継続条件（チケットの有無・レビュー待ち・マージ前作業中）、スラッシュ起動の扱い、サブエージェントでの扱い、ユーザーが応答できない実行形態への対応、緊急停止、記録
  - 含まない: 振り分けスキルの中身（各スキルの要件定義書が正）、宣言後にスキルの手順が守られているかの検証、チケットの作業中に宣言した範囲を強制すること（`workflow-guard`）、進行状態の保護（`workflow-state-guard`）

---

## ユーザーストーリー

**[As a]** `.claude/` 配下のフック・スキルを保守する開発者として、

**[I want]** 振り分けスキルが読み込まれたことをプロンプトごとに機械的に確認し、読み飛ばしたまま作業に入ったら止めてほしい。

**[So that]** `CLAUDE.md` の指示だけに頼らず、振り分けの実施漏れを確実に防げるため。

**[As a]** issue-MR 駆動で作業を進める開発者として、

**[I want]** チケットを進めている間やレビュー待ちの間は、「はい」「続けて」のようなフォローアップのたびに再宣言を求められたくない。

**[So that]** 作業の流れを止めずに、振り分けの統制と両立できるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When ユーザーが新しいプロンプトを送ったとき、Shall フックはそれ以前のプロンプトでの宣言を無効にし、そのプロンプトに対する宣言を改めて求めなければならない（「はい」「続けて」のようなフォローアップも例外にしない）。
- When AI が Skill ツールで振り分けスキル（`00-workflow-issue-mr-driven` / `00-workflow-quick-request`）のいずれかを読み込んだとき、Shall フックはそれを現在のプロンプトに対する宣言として記録しなければならない。
- When プロンプトの 1 行目が振り分けスキルのスラッシュ起動（`/00-workflow-issue-mr-driven` など）であるとき、Shall フックはそれを宣言として扱わなければならない。
- When 宣言のないまま AI がファイルの書き込み、コマンドの実行、プランモードへの移行、サブエージェントやワークフローの起動を試みたとき、Shall フックはその操作を拒否し、「このプロンプトでは振り分けが宣言されていないこと」「Skill ツールで読み込むべきスキルの名前（2 つ）」「読み込んでから元の操作をやり直すこと」を AI に伝えなければならない。
- When 宣言のないまま AI がファイルの読み取り・検索・一覧表示など状態を変えない操作を行うとき、Shall not フックはそれを拒否してはならない（振り分けの判定に必要な確認を妨げない）。
- When 宣言済みのプロンプトの中で AI が操作を行うとき、Shall not フックは宣言の有無以外の判定を行ってはならない（宣言した範囲の強制は `workflow-guard` の責務）。
- When 作業領域にチケット（未着手 / 作業中 / 完了のいずれか）があるとき、Shall フックは `00-workflow-issue-mr-driven` の作業が進行中とみなし、宣言の有無にかかわらず操作を許可しなければならない（その間の統制は `workflow-guard` が担う）。
- When 作業領域のチケットがすべて完了し、最後のワークのレビュー依頼が出されてレビュー待ちであるとき、Shall フックは同様に継続とみなして許可しなければならない。
- When 全体まとめで作業領域のチケットが片付けられたあと、マージ前作業（衝突確認・issue への通知・push・draft 解除）が進行中であることを機構の進行状態から確認できるとき、Shall フックは継続とみなし、チケットが無い状態でもそれらの操作を拒否せず、再宣言も求めてはならない。
- When 継続とみなして許可したとき、Shall フックはその根拠（チケットがある / レビュー待ち / マージ前作業中）を記録に残さなければならない。
- When 振り分けスキルとして認める名前を決めるとき、Shall それは `CLAUDE.md`「作業の振り分け」の表と一致していなければならず、スキルを追加・改名するときは両方を合わせて更新しなければならない。
- When サブエージェントが操作を行うとき、Shall フックはメインエージェントで行われた宣言または継続条件をそのまま適用し、サブエージェントに改めて宣言を求めてはならない（サブエージェントは振り分けスキルを読み込まない）。
- When 拒否メッセージを出すとき、Shall メッセージは他のフックの拒否と機械的に区別できる識別子を持ち、対処を含んでいなければならない。
- When 判定（宣言の記録・許可・拒否・継続）を行ったとき、Shall その記録が残り、振り返りのときに AI とユーザーが参照できなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない（`CLAUDE.md`「作業の振り分け」）。停止が設定されたセッションでは、フックは判定を行わず、停止していることが記録から分かるようにしなければならない。
- If 宣言の判定に使う記録が壊れている、または存在しない場合、Then フックは未宣言として扱わなければならない（拒否側に倒す。継続条件は別途評価する）。

### 例外フロー

- If ユーザーが応答できない実行形態（`claude -p`、CI）で未宣言の操作が試みられた場合、Then フックはユーザーへの確認を使わず、拒否と案内だけで AI 自身が Skill ツールで復旧できなければならない。
- If AI がこのフックに拒否された場合、Then AI は案内されたスキルを Skill ツールで読み込んでから元の操作をやり直さなければならず、緊急停止の設定・別の手段での迂回を行ってはならない。

## 前提条件

- `CLAUDE.md`「作業の振り分け」が、すべての依頼を振り分けスキルのどちらかを読み込んでから着手すると定めていること
- 振り分けスキル `00-workflow-issue-mr-driven` / `00-workflow-quick-request` が導入されていること
- Claude Code のフック機構が使え、プロンプトの送信・Skill ツールの読み込み・各ツールの実行の前後でフックを動かせること

---

## 制約条件

- **技術的制約**: 判定は「Skill ツールで振り分けスキルが読み込まれたか」だけであり、その後の手順の遵守までは検証しない。判定の材料は機構の記録と作業領域・進行状態のファイルに限り、AI の説明や会話の内容を材料にしない。実体は bash で書き、Windows の git bash で動く
- **ビジネス的制約**: 緊急停止（機構全体 / このフックだけ）は環境変数で行い、ユーザーが新しいセッションに対して設定する。AI は同じセッションの中で設定できない
- **外部的制約**: 継続条件（レビュー待ち・マージ前作業中）の判定は、レビュー依頼と完了・マージ前作業の提供コマンドが残す進行状態と同じ規則で行い、独自の判定を持たない

## 依存関係

- `.claude/skills/00-workflow-issue-mr-driven/`、`.claude/skills/00-workflow-quick-request/`（宣言として認めるスキル）
- `CLAUDE.md`「作業の振り分け」（振り分けスキルの一覧・再宣言の規則・緊急停止の条件）
- `workflow-guard`（継続中の統制を担う。未作成）
- `workflow-state-guard`、レビュー依頼と完了・マージ前作業の提供コマンド（レビュー待ち・マージ前作業中の判定の元になる進行状態。未作成）
- `session-start`（現在地の通知。継続条件と同じ判定を共有する。未作成）

## 非機能要件

| 項目 | 説明 |
|------|------|
| ヘッドレス耐性 | ユーザーが確認に応答できない環境でも、拒否のあとに AI が自力で復旧できる |
| 追跡性 | 宣言・許可・拒否・継続の判定が記録に残り、プロンプト単位で追える。記録に機密情報を含めない |
| パフォーマンス | 対象外の操作（読み取り）や継続中の判定は体感できない時間で終わる |
| 一貫性 | 振り分けスキルの一覧は `CLAUDE.md` と一致し、拒否メッセージの識別子は他のフックと重ならない |
| テスト容易性 | 入力（プロンプト・ツール呼び出し）と作業領域の状態を与えて、許可 / 拒否と案内文を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
