# 20-common-step-issue スキル

## 概要

issue 操作の共通ステップの要件を定義する。リポジトリのホスト（GitLab / GitHub）を判定し、対応する CLI（`glab` / `gh`）で issue を検索・閲覧・作成・追記する手順を標準化する。全体計画タスク（issue の確定）とフィードバック計画・全体まとめ（別 issue の起票）から使われる。issue の状態・タイトル・既存の記述は変えない。

- **背景**: issue 操作はコマンドの組み立て（ホストごとの CLI の違い・検索条件・本文の渡し方）を毎回考えると揺れ、長い本文をコマンドライン引数に埋め込むと壊れる。また issue は人間の資産であり、AI が既存の記述や状態を書き換えると経緯が失われる。
- **目的**: どの呼び出し元からでも同じ手順で、検索は再現でき、作成・追記は承認済みの本文だけがファイル経由で正しく投稿され、既存の記述・状態が保たれる状態を作る。
- **スコープ**:
  - 含む: ホストの判定、issue の検索（open 優先・0 件なら closed も）、閲覧、作成（承認済みの本文・テンプレート）、末尾への追記、結果の報告
  - 含まない: どの issue で対応するかの判断と承認（`10-task-overall-plan`）、起票の承認（呼び出し元）、issue の状態変更・クローズ・再オープン（行わない。close はマージ後に人間）、コメントの投稿（作業中の issue へは書き込まない）、リモート書き込みの可否の判定（チケットの宣言と機構）

---

## ユーザーストーリー

**[As a]** issue で作業を管理する開発者として、

**[I want]** AI の issue 操作が、検索は同じ条件で再現でき、書き込みは承認した本文の作成と末尾への追記だけであってほしい。

**[So that]** issue の経緯が AI に書き換えられず、投稿された内容が承認したものと一致するため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When issue を操作するとき、Shall スキルはリポジトリのリモートからホスト（GitLab / GitHub）を判定して対応する CLI を選び、判定できない場合は推測せずユーザーに確認しなければならない。
- When issue を検索するとき、Shall スキルはキーワード（日本語と英語の両方）で open の issue を検索し、0 件なら closed も含めて再検索し、結果を番号・タイトル・状態・URL の表で呼び出し元に返さなければならない。使った検索語と件数を添える。
- When issue を閲覧するとき、Shall スキルは番号を指定して本文（目的・受け入れ条件・やらないこと）を取得し、呼び出し元に返さなければならない。
- When issue を作成するとき、Shall スキルは呼び出し元で承認済みのタイトルと本文だけを使い、本文は `wip/tmp/` に置いたファイルから渡さなければならない（コマンドライン引数に長文を埋め込まない）。作成した issue の番号と URL を報告する。
- When 既存の issue に追記するとき、Shall スキルは承認済みの追記内容を既存本文の末尾に加え、既存の記述を消したり書き換えたりしてはならない。
- When 操作を終えたとき、Shall スキルは実行した操作（検索条件 / 作成・追記した issue の番号と URL）を呼び出し元に返し、呼び出し元が作業ログに残せるようにしなければならない。

### 代替フロー

- If 呼び出し元が issue 番号または URL を指定した場合、Then スキルは検索を省略してその issue を閲覧しなければならない。
- If 検索結果が多すぎる場合、Then スキルは上位（10〜20 件程度）に絞って提示し、絞り込みに使った条件を添えなければならない。

### 例外フロー

- If CLI が未導入・未認証の場合、Then スキルは導入・認証の手順を呼び出し元に返して停止し、Web への直接リクエストで代替してはならない。
- If issue の作成・追記に失敗した場合、Then スキルはコマンドと出力を呼び出し元に返して停止し、別の手段で再試行してはならない（二重投稿を防ぐ）。
- If 承認されていない本文で作成・追記を求められた場合、Then スキルは実行せず、承認が先であることを呼び出し元に返さなければならない。
- If 状態変更（クローズ・再オープン）やコメント投稿を求められた場合、Then スキルは行わず、このスキルの範囲外であることを返さなければならない。

### 他のスキル・機構との整合

- When issue へ書き込むとき、Shall その書き込みが作業中のチケットの「やってよいこと」に宣言されていることを前提とし、宣言外での実行は機構に拒否される。
- When 本文のテンプレート（種別・概要・受け入れ条件・スコープ外）を使うとき、Shall このスキルが持つテンプレートを使い、受け入れ条件は後のフェーズで DoD に落とせる粒度で書かなければならない。
- When 呼び出し元が issue 操作を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。

---

## 前提条件

- リポジトリが GitLab または GitHub でホストされ、`glab`（GitHub では `gh`）CLI が導入・認証済みであること
- 書き込みを行う場合、呼び出し元のチケットに issue の起票・追記が宣言されていること

---

## 制約条件

- **技術的制約**: 本文は常にファイル経由で渡す。一時ファイルは `wip/tmp/` に置く
- **ビジネス的制約**: issue の内容の承認は呼び出し元（人間との合意）が済ませる。このスキルは承認済みの内容を正確に反映するだけ
- **外部的制約**: issue の状態・タイトル・既存の記述を変えない。作業中の issue へのコメント投稿は行わない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 再現性 | 検索は使った条件を添えて返し、同じ条件で再実行できる |
| 追跡性 | 作成・追記した issue の番号と URL が呼び出し元の記録に残る |
| 一貫性 | GitLab / GitHub のどちらでも同じモード（検索・閲覧・作成・追記）と同じ制約で動く |
| 安全性 | 承認されていない本文・既存記述の書き換え・状態変更は実行されない |
