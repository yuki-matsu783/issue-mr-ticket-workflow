# i0001-21. ワーク層を廃してタスクと呼び、旧タスク層は共通ステップ層に改名する

## 背景

当初の 3 層は「ワークフロー（ワークの組み合わせ）/ ワーク（タスクの組み合わせ）/ タスク（作業レベルの手順）」だった。しかし要件を書き進めると、ワークの実体は「同じ種類のチケット群」であり、作業レベルの単位はチケットが担っていて、「ワーク = タスクの組み合わせ」の「タスク」に対応するスキルはほぼ存在しない（チケット操作・issue 操作などの共通ユーティリティだけが旧タスク層に残る）ことが分かった。「ワーク」は層を埋めるために作った語で、定義と実態がずれていた。

## 決定

- 層の呼び名とスキルの接頭辞を次に改める

| 層 | 接頭辞 | 実現単位 | チェックポイントの承認者 |
|---|---|---|---|
| ワークフロー | `00-workflow-*` | タスクの組み合わせ | 人間（MR レビュー または AskUserQuestion） |
| タスク（旧: ワーク） | `10-task-*` | チケットの組み合わせ | 敵対的レビューエージェント（複数チケット完了時点）と、切れ目の MR レビュー |
| 共通ステップ（旧: タスク） | `20-common-step-*` | チケットの実施で共通に使う作業レベルの手順 | 実行者自身のセルフレビュー |

- 「ワーク」の語は使わない。「ワークの切れ目」→「タスクの切れ目」、「work スキル」→「task スキル」、「ワーク別の既定判断基準」→「タスク別の既定判断基準」
- 共通ステップは複数の呼び出し元（タスクの実施・ワークフローの処理）から使われる手順だけをスキル化する。特定タスク専用の作業はチケットとして起こし、その型は task スキル（`10-task-*`）が定める
- 既存の要件定義書・DDR・`CLAUDE.md` の 3 層表・メモはこの用語に一括で追従する（`ワークフロー` / `ワークスペース` / `ワークツリー` / `ネットワーク` / `フレームワーク` は対象外）

## 理由

- 「タスク」がチケットで実体化される作業単位を指すなら、フェーズ単位のまとまり（旧ワーク）を「タスクの集まり = タスク」ではなく別の語で呼ぶ必要があったが、実際にはチケットが作業単位なので、旧ワークを「タスク」と呼び「タスク = チケットの組み合わせ」とする方が日常語に近い
- 旧タスク層のスキル（チケット操作・issue 操作・設計書作成など）は「タスクそのもの」ではなく「タスクの中で繰り返し使う手順」であり、「共通ステップ」の方が役割を正しく表す
- 実装（スキル本体・フック）が始まる前の要件定義だけの段階であり、改名のコストが最も低い

## 却下した案

- **ワークの語を維持し、タスク = チケットと注記で定義する**: 変更が最小だが、「ワーク」という造語と「タスクのスキルはほぼ無い」という不自然さが残り続ける
- **workflow / task / common-task にする**: common-task が「タスクの部品」なのに同じ「タスク」を名乗り、層の違いが読み取りにくい
- **全タスク（旧ワークの中身）を個別スキル化して定義どおりにする**: 呼び出し元が 1 つのスキルが 30〜45 本でき、1:1:1 の文書が倍増する

## 影響

- スキルの要件定義書 15 本を `10-task-*` に、`20-task-ticket` を `20-common-step-ticket` に改名
- `CLAUDE.md` の 3 層表、DDR i0001-06 / 08 / 10 / 11 / 16 / 18 のタイトルと本文、その他の DDR・要件書の用語を一括更新
- `自己改善ワークフロー機構.md` と hooks の要件書（他セッション作業分）は未反映。それぞれの編集が確定した後に追従する
- 用語辞書に タスク / チケット / 共通ステップ の定義を載せる（AI アセット設計フェーズ）
