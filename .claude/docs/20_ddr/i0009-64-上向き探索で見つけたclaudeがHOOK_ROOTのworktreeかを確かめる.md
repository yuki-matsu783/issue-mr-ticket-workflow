# i0009-64. 上向き探索で見つけた `.claude` が `HOOK_ROOT` の worktree かを確かめる

## 背景

`i0009-55` は「worktree では `cwd` 側の作業ツリーを採る」と決め、その手段を「`cwd` から上向きに `.claude` を持つディレクトリを探す（`git` を呼ばない）」と定めた。共通仕様 §2 はそこまでしか書いていない。

0027 の実装で、**候補を検査せずに採ると機構が全面バイパスされる**ことが分かった。`cwd` は worktree に入ったときだけでなく `cd` でも動く。このリポジトリには `参考ディレクトリ/agent-workflow/.claude` と `参考ディレクトリ/MR-driven-workflow/.claude` が実在し、どちらも空の `wip/10_tickets/10_doing/` を持つ。したがって

```
cd 参考ディレクトリ/agent-workflow
```

とするだけで `hook_doing_ticket` が 0 枚を返し、`workflow-guard` は「作業中チケットが無い」経路に落ちて**書き込みも実行もすべて素通り**する。参考実装を置いていないリポジトリでも、`.claude` を持つ別のチェックアウトが祖先または子孫にあれば同じことが起きる。

## 決定

- 上向き探索で見つけた候補は、**`HOOK_ROOT` の worktree であることを確かめてから**作業ツリーとして採る。確かめられなければ `HOOK_ROOT` に倒す
- 判定は fork ゼロの 2 経路のどちらかが成り立つこと。片方でよい
  1. 候補直下の `.git` がファイルで、その `gitdir:` が `$HOOK_ROOT/.git/worktrees/` 配下を指す
  2. `$HOOK_ROOT/.git/worktrees/*/gitdir` のいずれかが候補の `.git` を指す
- 候補が `HOOK_ROOT` 自身（本流）のときはこの検査の対象外
- §2 の作業ツリーの決め方に、この確認を手順として足す

## 理由

- **無効化はロックアウトより悪い**（`i0009-55` の理由をそのまま引き継ぐ）。ロックアウトは気づいて直せるが、無効化は静かに全部通る。`cd` 1 回で機構が消えるのは、攻撃でなくても事故で踏む
- **`.claude` の存在は「同じリポジトリの作業ツリー」を意味しない**。ディレクトリの有無は誰でも作れるので、判定材料として弱すぎる
- **2 経路のどちらかにしたのは、参照の向きが片方だけ壊れている状態でも通すため**。`git worktree` は worktree 側 → 本流と本流 → worktree 側の 2 方向の参照を持ち、ディレクトリを移動した後（`git worktree repair` 前）は片方が古い。両方を要求すると正しい worktree を本流に倒してしまう
- **`git` を呼ばない**。判定はファイルの読み取りと glob だけで、`i0009-22` の fork 上限に影響しない
- **確かめた側に倒すのが安全側**。判定できないときは `HOOK_ROOT`（本流の状態）で判定する。本流のチケットで判定されるのは厳しすぎることはあっても、素通りにはならない

## 却下した案

- **`cwd` で `git rev-parse --show-toplevel` を実行して解決する**: `i0009-55` の却下と同じ理由（約 95 ms/回。ホットパス 5 本が同時に走ると毎ツール呼び出しで 475 ms）
- **`cwd` が `HOOK_ROOT` の配下かどうかだけで判定する**: worktree はリポジトリの外に置くのが普通で（0031 の実測でも親ディレクトリの兄弟に作った）、正しい worktree を弾く
- **候補を採らず常に `HOOK_ROOT` に倒す**: `i0009-55` の worktree 対応そのものが消える
- **見つけた候補をそのまま採り、記録に警告を残す**: 記録は事後で、素通りは止まらない。無効化に対する対策にならない
- **`.claude/hooks/` の実体があることを候補の条件にする**: worktree には `.claude/hooks/` の実体があるので判定にならず（分岐元のコミットの内容が入っている）、参考実装の `.claude` も同様に実体を持つ

## 影響

- `10_spec/フック共通仕様.md` §2（作業ツリーの解決に worktree の確認を追加）
- 実装は 0027 の `__hc_is_worktree_of` が該当。HK-T18 が「偽の worktree（`.git` ファイルと `gitdir` の相互参照）では worktree 側に解決する」「`.claude` を持つだけの別ディレクトリではルートに解決する」の 2 ケースを固定している。相互参照を双方向にしたのは 0036
- 関連: `i0009-55`（`cwd` 側の作業ツリーを採る）・`i0009-22`（フック本体から `git` を呼ばない）・`i0009-20`（登録は `${CLAUDE_PROJECT_DIR}` 基準の絶対パス）
- **残る穴**: worktree の中の書き込みは事前判定（`workflow-guard`）では止まるが、事後の差分検査（`workflow-diff-check` / WF601）は本体の作業ツリーだけを見る（0031 の実測。0039 の C3 として別に扱う）
