この計画で何をするか

設計は「lib は #6 で既に正しい」という前提で書かれたが、境界レビュー 2 巡がその前提を崩した。hook-common.sh には設計が要求する 5 関数が無く、hook_read_input はイベント固有フィールド（prompt / source / tool_response / run_in_background）も副入力も取らず、cmdpos.sh には cmdpos_operands が無く、scope.sh は web を知らず読み込み関数がパスを引数に取る。フック本体 11 本を書く前に lib の改修が要る。そのうえで T6（permissionDecision + 終了 0 の deny が実際に効くか）を 11 本を書き切る前に確かめる — 外れたときの手戻りが 11 本 + 登録ラッパー全部に及ぶため。拒否側の最も単純な 1 本（block-chmod）を lib と同じチケットで先に書き、それだけを単独で登録して T6 を確かめる ⓪ の段を段階登録の前に置く。

実装前に確定した 11 件

  1. 段階登録は 17 行（§1 の表が正）。案内側 12 行・拒否側 5 行。全体計画の「16 行 / ① 11 行」は subagent-start-check の PreToolUse Agent 登録（WF803）が増える前の数で、この計画で 17 行 / ① 12 行に組み直す
  2. 各段で AI が渡すのは「その段までの PreToolUse 配列の全文」。HK-T01 は配列上の位置まで照合する。人間が末尾に足していくと最終配列が [4,1,7,2,3,5,6] になって HK-T01 が落ちる。位置は AI が保証し、人間は貼り替えるだけ
  3. T6 の確認は ⓪ で行い、そのときラッパーを付けない。ラッパーは「本体が起動できない = deny」なので、T6 が未確認の段で付けると本体の不調と登録方式の不調が区別できず、しかもラッパーは環境変数を見ないので環境変数で戻れない。⓪ は素の command で登録し最悪でも fail-open に留める
  4. 4c の実測は 10 項目（T2・T3・T4・T5・T7・T9 と tool_response.status・agent_type・worktree・ホットパスの実行時間）。T1 と T8 は §12 が既に取り消し線で「解決（TBD ではない）」としているので含めない（T8 は機械テスト HK-T16 が固定する）。T6 は ⓪ で確認済み。T5 は §12 に生きた TBD として残っており全体計画の申し送りにもあるので必ず含める
  5. T9 と入力フィールドの実測は「4c プローブ」で行う。decisions.jsonl は 10 キー固定で permission_mode / model / tool_response / agent_type を入れる場所が無く、systemMessage を出す WF801 / WF803 は subagent_type が task-executor（実装が無い）で executor が main 以外のときにしか発火しない。WORKFLOW_PROBE_4C=1 のときだけ有効な一時的な観測経路を仕込み、実測後に取り除く
  6. ② の後には git worktree add / claude -p / mv が workflow-guard に止まる（前 2 つは読み取り一覧に無く WF204、mv は WF205）。4c を「② より前に測るもの」と「② の後でしか測れないもの」に分ける。worktree は作成を ② より前に済ませ、② の後にそこで Claude を起動する
  7. HK-T01 の期待値は 17 行分の command 文字列の逐語一覧をフィクスチャに持つ。イベント名からディレクトリを機械変換できない行が 4 行あるため。うち拒否側 5 行は fail-closed ラッパー（|| printf … WFx09 …）まで含めた逐語で、x はフックごとに違う（workflow-entry = WF109 / workflow-guard = WF209 / workflow-state-guard = WF309 / block-direct-git = WF409 / block-chmod = WF509）
  8. 読み込み行は雛形を先に直してから配る。^__ss_load() { を持つのは 22 ファイル（雛形 2 + 実体 20）。SS-T05 の走査範囲は .claude/hooks/** と .claude/skills/*/scripts/** なので assets/test.template.sh は検査対象外
  9. 実装フェーズは DDR を書けない（ai-asset-implementation.deny に .claude/docs/**）。決定は作業ログに書き、0032 が棚卸ししてフェーズ 6 で DDR にする
  10. settings.json は許可範囲に入っているが AI は書かない。登録は人間の操作。AI は JSON と手順を提示し登録後のコミットだけを行う
  11. フェーズ 7 は第 1 案（WORKFLOW_STATE_GUARD_ENFORCE=0 の新セッション）で通す。17 行の登録を保ったまま HK-T01 と全件が通る状態でマージできる唯一の案

方法とステップ

ステップ 1: 共通ライブラリと足場（0027）

1-1 読み込み行（i0009-36）。順序を守る: (1) assets/script.template.sh を仕様に合わせる（FM_AVAILABLE を設定 / fm_* スタブの戻り値を 1 → 2 / ルート解決 3 段目の git rev-parse は残す）→ (2) assets/test.template.sh を揃える（SS-T05 の検査対象外だが揃える）→ (3) 実体 20 本へバイト一致で配る（grep -rl '^__ss_load() {' .claude の 22 件から雛形 2 本を除いた分。リポジトリ全体では 24 件あるが wip/tmp/*.sh.new の 2 本は走査範囲外なので触らない） → (4) 配った後にもう一度 grep して差分 0 を確かめる → (5) SS-T05 を実装して通す。

1-2 hook-common.sh。実装の型を 11 本で統一する（0006 f4）: HOOK_DENY_ID の代入 → lib の source → hook_init。

  • hook_read_input の 1 回の jq を拡張する（取らないと拒否側 4 本が hook_field を追加で呼びホットパスの上限を破る）: prompt（split("\n")[0] で 1 行目だけ）・source・tool_response.status / agentId・tool_input.run_in_background・agent_transcript_path・tool_input.old_string / new_string / content / edits（WF208。全文は要らない — frontmatter の 6 キーに触れたかの真偽 1 個に畳む）・tool_input.draft（WF304）
  • tool_class から 00-workflow-* の接頭辞判定を除く（DDR i0009-03）。Skill は常に declare
  • 副入力の受け渡しの形を先に決める（この計画で唯一「やってみないと形が決まらない」箇所。0027 の最初にここだけを片付ける）: 区切りバイトの割り当て（現在 __HC_US / _SC_US / CP_ARGS がすべて 0x1E で衝突。副入力の行区切りに 0x1D・列区切りに 0x1F を割り当てる）／scope-limits.json の射影は全 type を出す（ticket_type は frontmatter.sh を読んで初めて分かる = hook_read_input の後）／検証エラーで jq を落とさない（実体の scope.sh:43-56 は error 終了させる作りで、共有の jq に持ち込むとstdin の解析ごと落ちる — i0009-47 と HK-T18 が禁じている形。HC_LIMITS_STATE=broken として返す）
  • 同じ 1 回でパスが stdin に依存しない副入力を読む。存在するものだけ --rawfile、無いものは --argjson <名前> null（存在確認は [ -f ]）。HC_<名前>_STATE を立てる
  • hook_read_state: session_id に依存する副入力を 1 回の jq で読む
  • 作業ツリーの解決（§2・i0009-55）を hook-common.sh に入れる。HOOK_ROOT（スクリプトの置き場）と HOOK_WORKTREE を分け、hook_doing_ticket / hook_record / hook_session_dir / hook_rel_path は HOOK_WORKTREE を基準にする
  • 候補が HOOK_ROOT の worktree であることを必ず確かめる。公式は cwd を「worktree に入った後の worktree ルート、かつ Claude が cd した後の新しいディレクトリ」と定めており cd だけでも動く。このリポジトリには 参考ディレクトリ/agent-workflow/.claude と 参考ディレクトリ/MR-driven-workflow/.claude が実在し、どちらも wip/10_tickets/10_doing/ を持つ（空）。cd 参考ディレクトリ/agent-workflow しただけで hook_doing_ticket が 0 枚を返し、workflow-guard が「作業中 0 枚 → 判定しない」に落ちてガードが全面バイパスされる。判定は fork ゼロで書ける 2 通り: (a) 候補直下の .git がファイルで gitdir: が HOOK_ROOT 配下を指す、(b) HOOK_ROOT/.git/worktrees/* の名前列と突き合わせる。仕様 §2 への書き戻しは 0032 へ
  • hc_* 4 関数: §1 の契約どおり。切り詰めは hc_append_jsonl、2 秒と 60 秒は hc_lock。hc_lock は取得前に既存ロックの作成時刻を見て 60 秒より古ければ強制解放（i0009-60）。判定は find <dir> -maxdepth 0 -mmin +1（hc_lock はホットパスではない）

1-3 cmdpos.sh: cmdpos_operands <i> を足す（rm -rf a b → a b、mv -v src dst → src dst）。解釈は呼び手が行う。lib に置かないと workflow-state-guard にコマンド意味論を持たせることになり i0009-39 が却下した案に戻る。

1-4 scope.sh: 読み込み 2 関数からパス引数を削る（i0009-48）/ scope_load_ticket の戻り値を 3 状態に（i0009-16）/ web の 3 段判定（i0009-56）と出力先の走査（i0009-57）/ SC_TARGETS と SC_CLASS（write / opaque を含む）は実体で統一し仕様のずれは 0032 へ / || true を || rc=$? に（i0009-35）/ hook-test の判定順は 既に実装済みなので確認するだけで触らない。

1-5 config 3 ファイルを新規作成する。WF203 を出す workflow-guard は ② で登録されるので、② より前に作れば確認は出ない（⓪ より前である必要は無い）。1-6 block-chmod 1 本とそのテスト。

ステップ 2: ⓪ T6 の先行確認（0028）

  1. AI が PreToolUse 配列の全文（この段では 1 要素、ラッパー無しの素の command）を提示する
  2. 登録前に人間がバックアップを取る
  3. 人間が登録し、AI が commit.sh でコミットする（この段では workflow-guard が未登録なので WF203 は出ない）
  4. 新しいセッションで chmod +x を試し、permissionDecision: "deny" + 終了 0 で拒否されるかと decisions.jsonl の記録を見る
  5. 効いた: 終了方式が確定。0030 以降はラッパー付きで進む
  6. 効かない: exit 2 + stderr へ切り替える。影響を受ける本体は 1 本だけで、手戻りは hook-common.sh の出力ヘルパに閉じる
  7. ロックアウト: WORKFLOW_BLOCK_CHMOD_ENFORCE=0 の新セッション。ラッパー無しなので必ず戻れる

⓪ の後、block-chmod は本番で生きたまま 0029・0030 が進む。chmod を使う作業が出たら上の環境変数で回避する。

ステップ 3: 案内側 6 本（0029）

  • 案内側はラッパー無し（失敗は通す）
  • session-start は boundary.sh status --offline（3/3・未実装）が無ければ何も出さずに終了 0。依存する 8 件のテスト観点は書かずに #10 へ送る
  • post-push-usage-report は --accumulate と既定の両方で hc_lock usage-<branch> を取ってから加算する
  • subagent-start-check は PreToolUse Agent と SubagentStart の両方に登録される 1 本。subagent-stop-check は tool_response.status で分岐し agentId（camelCase）を読む
  • 6 本に「4c プローブ」を仕込む（WORKFLOW_PROBE_4C=1 のときだけ有効）

ステップ 4: 拒否側の残り 4 本（0030）

  • ホットパスの jq の回数を実装で固定: block-chmod / block-direct-git / workflow-state-guard = 1 回、workflow-guard / workflow-entry = 2 回。hook_field を追加で呼ばない
  • git / date / sed / find をホットパスで呼ばない
  • 作業ツリーの基準は HOOK_WORKTREE（0027 で lib に入れたもの）。各フックが自前で解決しない
  • 置き場の削除（i0009-59）: cmdpos_operands で位置引数を取り、前方一致で祖先（wip/10_tickets / wip）を拾う。rm -rf wip/tmp と rm -rf logs は通す。自前で再パースしない

ステップ 5: 段階登録とフェーズ 4c の実測（0031）

WORKFLOW_PROBE_4C=1 は人間が設定する。環境変数はセッション開始時に読まれ AI は設定できない（§4）。Bash ツールで前置しても外側のフックプロセスには届かない。① の登録後、人間が WORKFLOW_PROBE_4C=1 を設定した新しいセッションを起動する。

各段で AI が渡すのは「その段までの PreToolUse 配列の全文」。人間は配列ごと貼り替える。位置は §1 の表の順に合わせる。段ごとに新しいセッションで軽い操作を通す。② の後は common.confirm により WF203 の確認が出る（人間が承認する）。

HK-T09 は機械テストであって実登録の破壊試験ではない

ロックアウトの復旧手段の使い分け

  1. 1 本のフックの判定が誤って deny を出す → WORKFLOW_<NAME>_ENFORCE=0 を設定した新しいセッション（block-chmod なら WORKFLOW_BLOCK_CHMOD_ENFORCE=0。§4 の命名規則）
