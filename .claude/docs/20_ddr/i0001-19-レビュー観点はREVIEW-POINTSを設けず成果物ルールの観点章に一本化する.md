# i0001-19. レビュー観点は REVIEW-POINTS を設けず成果物ルールの観点章に一本化する

## 背景

参考実装（MR-driven-workflow）は「rules = 規約の知識の正」と「REVIEW-POINTS = ディレクトリごとの一行チェックリスト」の二本立てで、敵対的レビューは対象ファイルの祖先ディレクトリから観点表を収集して入力にしていた。この構成は「正はどちらが持つか」「収集の到達性のためにあえて重複させる」といった二重管理の注記を手で保守する必要があった。本機構のルールには 2 つの目的がある: (1) 実装・テスト時に、書くファイル種別に効くルールを一括参照できる、(2) レビュー時に、観点別のレビューエージェントが担当観点の章だけを各ルールから抽出してファイルを横並びでチェックできる。

## 決定

- REVIEW-POINTS（ディレクトリごとのレビュー観点表）の層を設けない。レビュー観点は `.claude/rules/` の**成果物ルール**の章として持つ
- ルールを**成果物ルール**（レビュー対象として残る成果物の書き方。章スキーマに従う）と**行動ルール**（作業の進め方・その場限りの操作の規約。章スキーマ対象外）に 2 分類する
- 成果物ルールは「適用範囲 / 構造・配置 / 書式・可読性 / セキュリティ / 堅牢性 / パフォーマンス / テスト・機械的検査」の 7 章を固定の見出し文言・固定の順で持つ。定めが無い章は見出しを残して「該当なし」と根拠 1 行を書く
- 実際に踏んだ罠は該当観点の章の中に出所（issue 番号）付きで書き、罠専用の章に隔離しない
- 適用範囲は frontmatter の `paths`（グロブ）で宣言し、収集はディレクトリの遡りではなく paths のマッチで決める。実装時は「書くファイルにマッチする全ルールの全章」、レビュー時は「対象ファイル群にマッチする成果物ルールの指定観点の章」を機械的に集める

## 理由

- 規約とチェックリストの正が 1 箇所になり、片方だけ直して食い違う事故と重複回避の注記の保守が消える
- 実装する AI とレビューエージェントが同じ文書を見るため、「書くときは知らされず、レビューで初めて指摘される」観点が構造的に生じない
- 章の見出しを固定すると観点別の抽出が機械的にでき、「該当なし」の明記で「ルールが無い」と「書き忘れ」をエージェントが区別できる
- paths ベースの収集は、ディレクトリ遡り方式が抱えていた到達性の問題（対象の指定方法によって収集されない観点表が出る）を持たない

## 却下した案

- **参考実装どおり rules と REVIEW-POINTS の二本立て**: 実績はあるが、二重管理の注記の保守が必要で、実装時とレビュー時で参照する文書が分かれる
- **ディレクトリごとの観点表のみ（rules を持たない）**: レビューは成立するが、実装時に「この種別のファイルを書くためのルール一式」を 1 箇所で参照できない
- **章を固定せずルールごとに自由な構成**: 書きやすいが、観点別の横並び抽出が機械的にできず、レビューエージェントごとに読み方の実装が要る
- **罠を「既知の罠」章に集約**: 罠カタログとしては読みやすいが、観点章の純度が壊れ、観点別エージェントが担当観点の罠を見落とす

## 影響

- `自己改善ワークフロー機構.md` I 節の敵対的レビューの文言（「ディレクトリごとのレビュー観点表」→ 成果物ルールの観点章）
- `00_requirement/rules/ルール体系.md`（2 分類・章スキーマ・一覧を要件化）
- 観点別レビューエージェント（敵対的レビューを含む）の入力仕様と、ルール収集・抽出スクリプトの仕様（paths マッチ方式）
- 参考実装の REVIEW-POINTS の中身は、対応する成果物ルールの観点章の材料として取り込む
