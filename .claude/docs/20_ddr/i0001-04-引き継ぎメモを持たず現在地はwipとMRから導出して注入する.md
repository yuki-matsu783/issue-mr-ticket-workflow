# i0001-04. 引き継ぎメモを持たず現在地は wip と MR から導出して注入する

## 背景

参考実装 MR-driven-workflow は `HANDOFF.md`（43 ステップの進捗表・ヘッダ・次にやること）を AI が更新し、SessionStart フックがその一部を注入する。進捗表の更新漏れ・記号の誤り・ループ周回数の表現・`set-header` の表記ゆらぎなど、引き継ぎファイル自体の保守に専用スクリプトと複数の DDR を要していた。一方 agent-workflow は `wip/10_tickets/` のチケット配置と `review-state.json` から境界とレビュー状態をスクリプトが決定論的に導出しており、手書きの進捗表を持たない。

## 決定

- 手書きの引き継ぎファイル（`HANDOFF.md` 相当）を置かない
- 現在地は次から導出する: 現在のブランチと MR（`gh`）、`wip/10_tickets/` の todo / doing / done の配置、レビュー状態ファイル、マージ前作業の状態ファイル、全体計画のフェーズ列
- SessionStart フック（startup / resume / clear / compact）が、ブランチ・issue・MR・チケットの先頭・レビュー状態・次に読み込むスキル・未返信スレッド数を導出して注入する。ファイルの中身は注入しない
- 「次にやること」に相当する情報は doing / todo チケットの本文（目的・DoD）が担う

## 理由

- 状態遷移はすべてスクリプト経由（i0001-03）なので、状態は常にファイルから導出でき、AI が別途書き写す必要が無い
- 引き継ぎファイルは AI の記述精度に依存し、実態とずれても検知できない。導出なら実態と一致する
- compact 後も同じ導出で復元でき、「読んだつもり」の認識喪失に依存しない

## 却下した案

- **HANDOFF.md を採用し、更新をスクリプトで機械化する（MR-driven-workflow 方式）**: 人間が 1 ファイルで現状を読めるが、同じ情報が wip とファイルの 2 箇所に存在し同期が要る
- **注入せず、再開時に AI が `status` サブコマンドを叩く運用にする**: 実装が単純だが、compact 直後に AI がそれを叩くこと自体を保証できない

## 影響

- 要件定義書 J 節
- 人間が現状を一目で読みたい要求には、MR 本文（ワークごとの要約が積み上がる）と統括レポートで応える
- 注入サイズの目安は 8 KB。超過時は警告を添え、切り詰めない
