hooks/lib 5 本の公開 API は 11 本のフック仕様の前提をほぼそのまま満たす（欠け 0 / 未使用 0）。ただし結線の注意点が 4 件: tool_class の二重定義、案内側の frontmatter 読み込み経路（§12 T8）、HOOK_DENY_ID の設定順序、各フックが自前で書く 9 種類の処理。参考実装から流用できるのはテストの骨格までで、本体 11 本（うち 7 本は相当物なし）は書き起こしになる。

  • f6・f7: 参考実装からはテストの骨格だけを流用し、本体は仕様どおりに書き直す

  2. 2

    tool_class の振り分けスキル判定が entry-skills.txt と二重定義になる △注意 根拠: hook-common.sh:156-166 / workflow-entry 仕様 呼出条件・WE-T07

  3. 3

    案内側フックが frontmatter を読む経路が未定（§12 T8 そのもの） △注意 根拠: scope.sh:20 の読み込み行 / 20-common-step-shell-script 仕様「読み込み行」

    scope.sh は先頭で __ss_load frontmatter deny を実行し、読めないと deny JSON を出して終了 0 する。これを source するのは拒否側の workflow-guard だけでなく、案内側の workflow-diff-check と subagent-stop-check も。案内側の「判定できないときは黙って通す」と矛盾する。subagent-start-check は scope.sh が要らないので __ss_load frontmatter nop で自前に読める。

    結論

    (a) scope.sh のポリシーを nop にして呼び手が失敗を deny に倒す（§12 T8 の縮退案と一致）/ (b) 案内側専用ラッパ / (c) T8 の実測待ち。(a) を推す。

    参考実装の deny は exit 2 + stderr で、permissionDecision + 終了 0 の実績が無い △注意 根拠: workflow-guard.sh:15 / workflow-entry.sh:16 / block-chmod.sh:17-18 / workflow-boundary.sh:17

    T6（permissionDecision + 終了 0 の deny が効くか）は参考実装が回避していた点でもある。段階登録 ②-1 で最初に確かめる段取りは妥当で、外れると 11 本 + §1 ラッパーが変わるため後回しにできない。
