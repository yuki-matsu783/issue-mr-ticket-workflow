# i0050-05. チケットの採番は本流だけが行い、作業ツリーでは新規作成しない

## 背景

チケットの連番は、実行している作業ツリーの `wip/10_tickets/` を走査して「既存の最大 + 1」で採られる。他の作業ツリーもリモートも見ない。作業ツリーを分けて並列に実施すると、次が起きる。

- 2 つの作業ツリーが同時にチケットを作ると**どちらも同じ番号**を採る
- 種類が同じなら同名ファイルになり、合流時に衝突して人が気づく
- **種類が違えば別名ファイル（`0011-design.md` と `0011-investigation.md`）になり、合流は衝突せずに成功し、同じ番号のチケットが 2 枚並ぶ**
- 番号で 1 枚を引く処理は先に当たった 1 枚を返し、切れ目の一覧は番号だけを積むので、**同じ番号が 2 回並んだ一覧**がレビュー依頼に載る。気づく機会が無い

この経路は実測で再現した（2 つの作業ツリーがどちらも `0011` を採り、`git merge` が衝突せず合流し、未着手の置き場に `0011-` が 2 枚並んだ）。

一方で、**並列するのは「既に番号が決まった実施チケット」だけ**である。チケットを新しく作るのは計画タスク（`*-plan`）と、レビュー指摘の追加チケットを起こす切れ目の処理で、どちらも直列に本流を走る。

## 決定

- **チケットの新規作成は本流でだけ行う。** 本流でないチェックアウト（作業ツリー）で新規作成が求められたら拒否し、本流で作るよう案内する（`ticket.sh create` の **TK009**）
- **着手・完了・取り消し・次の提示は作業ツリーでも行える。** 対象はそのとき実行している作業ツリーの作業領域とする
- **番号の体系（`<4 桁>-<種類>.md`）と、番号でチケットを引く処理、切れ目の判定は変えない**
- **本流かどうかの判定は、リポジトリルート直下の `.git` がディレクトリか（作業ツリーではファイル）で行う。** 判定の正は `20-common-step-worktree` 仕様に 1 か所だけ置き、`ticket.sh` と `push.sh` はそれを使う

## 理由

- 計画タスクは常に直列で本流を走り、そこで実施チケットの番号が全部決まる。並列するのは番号が決まった後のチケットだけなので、**採る場所を本流 1 か所に限れば重複が構造的に起きない**。検知して直す形ではなく、起こさない形にできる
- 番号体系を変えずに済むので、番号でチケットを引く処理・切れ目の判定・レビュー依頼の一覧の書式に波及しない。実装の変更は `create` の入口に検査を 1 つ足すだけで閉じる
- 着手・完了まで本流に寄せると並列そのものが成立しない（作業ツリーで実施したチケットの状態を本流から動かすことになる）ので、**作成だけを分ける**
- 判定を `.git` の種類で行うのは、`git` を呼ばずに済み、フックが使う共有ルート（進行状態・ロック・集計の置き場）と同じ根を指すため。別 clone を使う運用ではその clone のルートが本流になり、clone ごとに独立して番号を採る（clone をまたぐ合流はリモートを経由するので、そこは別の話になる）

## 却下した案

- **複合キー（issue 番号 + 作業ツリー識別子）や ULID に変える**: ファイル名の規約・番号でチケットを引く処理・切れ目の判定・レビュー依頼の一覧の並び順まで波及する。番号が単調増加であることに依存している判定（先行チケットの解決、最小連番の提示）も作り直しになる。得られるのは「作業ツリーでも作れる」ことだけで、割に合わない
- **合流時に番号の重複を検査する**: 重複してから気づく形になる。直すには `ticket.sh` を経ない手作業の振り直し（ファイル名の変更と先行チケットの参照の書き換え）が要り、`ticket.sh` の「手動で動かさない」という前提に反する
- **採番のときに他の作業ツリーの `wip/10_tickets/` も走査する**: 走査の時点で他の作業ツリーが未作成なら重複を防げず（同時に作れば両方が相手を見ない）、作業ツリーの集合を解決するコストが `create` のたびに乗る。競合を消すにはロックが要り、共有ルートのロックを提供コマンドから取る仕組みを新たに作ることになる
- **番号の予約（本流であらかじめ番号だけ確保する）**: 実質は「本流で作る」と同じことを 2 段階でやる形で、予約と実体の対応が壊れたときの復旧が増える
- **作業ツリーでも作れるようにして、重複は人が直す**: 種類が違うと衝突せずに合流するので、人が気づく機会が無い

## 影響

- `00_requirement/skills/20-common-step-ticket.md` の例外フローに、作業ツリーでの新規作成の拒否を書く（**並列実施を行う場合**の採番の重複を構造的に塞ぐ規定であることを明示する）
- `10_spec/skills/20-common-step-ticket.md` の `create` に本流の検査を手順 0 として置き、`TK009` とテスト観点 `TICKET-T13` を足す
- `10_spec/フック共通仕様.md` §6 の採番台帳を `TK001–009` に更新する
- 本流かどうかの判定は `10_spec/skills/20-common-step-worktree.md` が正で、`20-common-step-commit-push` の push 前チェック 項目 5 も同じ判定を使う
- 並列で実施するチケットは、計画タスクが本流であらかじめ起こしておく必要がある。切れ目でレビュー指摘の追加チケットを起こすのも本流の処理なので、既存の流れは変わらない
