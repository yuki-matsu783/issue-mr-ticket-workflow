# i0050-04. 分類の穴は提供コマンドとオプション判定の限定適用で塞ぎ、`cd` は通さない

## 背景

issue #50（worktree を作業ツリーの単位に据える）の調査で、`scope.sh` のコマンド分類の穴が **4 層**に分かれることが分かった。

| 層 | 何が起きるか | 規模 |
|---|---|---|
| L1 | git のサブコマンドが `unknown` に落ちる（`worktree` / `checkout` / `switch` / `stash` / `merge-tree` / `version` / `help` を含む） | 実体 174 件のうち 145 件 |
| L2 | `_SC_READ_ONLY_CMDS` に無い基本コマンドが `unknown` に落ちる（`cd` を含む） | 候補 95 件のうち 67 語 |
| L3 | 分類より手前（`cmdpos.sh` の正規化）で実行体を取り違え、引数だったはずの語が実行体の段になる | 実績 9 件 |
| L4 | **逆向き**。`read` に分類されるのに状態を変えられる（`branch -d` / `symbolic-ref <name> <ref>` / `reflog expire` / `diff --output=` / `-c diff.external=<コマンド>`） | 5 件 |

L1〜L3 は「通らない」＝作業の手数の問題で、L4 は「通ってしまう」＝統制の問題である。とくに `git -c diff.external=<コマンド> diff` は、`read` 分類のまま**任意コマンドを実行できる**。手数の側だけを直すと、**分類を広げた記録だけが残って統制の穴が残る**。

一方で本 issue は worktree 運用を正とするので、「作業ツリーを作る・一覧する・合流する・片付ける」を AI が行える経路が要る。現状はそのすべてが `unknown`（WF204）で、機構が worktree 運用を支えられない。

## 決定

- **worktree の作成・合流・後始末は、分類を広げずに提供コマンド `worktree.sh`（`20-common-step-worktree`）で通す。** 提供コマンドは分類を問わず許可されるので、`scope.sh` の白名簿を伸ばさずに操作だけを通せる
- **`git worktree list` だけは `read` に落とす**（サブコマンドの次の語が `list` のときに限る）。読み取りだけの形で、提供コマンドを起動するまでもない
- **逆向きの穴 5 件は、「サブコマンド + オプション」の判定を 6 か所に限って足して閉じる**（`worktree` / `branch` / `symbolic-ref` / `reflog` / `--output=` / グローバル `-c`・`--config-env`）。白名簿全体をオプション込みに作り替えることはしない
- **グローバル `-c` / `--config-env` は設定名を見ずに一律 `unknown` に倒す。** 危険な設定名の列挙は網羅できず、漏れた名前が `read` のまま通るため
- **`cd` は分類に足さない**（`unknown` のまま）。これは意図的な緩和ではなく、判定の起点を 1 つに保つための設計判断として仕様に書く
- **`cmdpos.sh` の正規化 2 件（P-1・P-2）はどの案とも独立に直す。** ダブルクォートの中の `$(( ))` を算術として読み飛ばすこと、コマンド置換・プロセス置換の閉じ括弧の後ろの語を新しい段の実行体にしないこと
- **上記以外の分類外は既定拒否のまま残す。** L1 の残り（`checkout` / `switch` / `stash` / `merge-tree` ほか）と L2 の残りは広げない

## 理由

- **既定拒否の原則を緩めない。** 仕様 §8 の「どの分類にも当たらない = 拒否」は機構の土台で、白名簿を伸ばす形（案 A・案 E）はこの既定を実質的に緩める。提供コマンドと宣言は、どちらも**記録が残る口**である
- **`cd` を通すと判定の起点がずれる。** `workflow-guard` の書き込み先の解決は `hook_rel_path` が `HOOK_WORKTREE` を起点に畳むだけで、`cd` の効果を追跡しない。`cd` を `read` に足すと `cd <他の場所> && echo x > a.txt` の `a.txt` が自分の作業ツリーの相対パスとして判定され、**作業ツリーの外への書き込みが「通してよいもの」として通る**。起点を追跡する実装を足すのは、fork ゼロ・O(1) というホットパスの制約と噛み合わない。作業ツリーの中で作業するときの作業ディレクトリは最初からその作業ツリーなので、`cd` は要らない
- **L4 を本 issue で閉じるのが最も安全である。** 本 issue は同じ `scope_classify` の git 分岐に手を入れるので、同じ改修で閉じれば二度開けずに済む。別 issue へ送ると、分類を広げた記録だけが残って穴が残る状態になる
- **オプション判定を 6 か所に限れば、維持コストは限定される。** 白名簿全体をオプション込みにすると git の版ごとに追随が要り、`scope.sh` が `curl` のオプションについて既に認めている「網羅的かは確かめられない」という負債が拡大する。閉じる向き（通っていたものを止める）にしか効かない規則に限れば、漏れがあっても穴が増えることはない
- **一律 `unknown` は網羅を要さない。** `-c` の設定名を列挙する形は、列挙の漏れがそのまま穴になる。正当な用途は素の形で足りる

## 却下した案

- **案 A（既存の一覧に足す。最小差分）**: `cd` の起点ずれと `git worktree add` の巻き込み（`worktree` を丸ごと `read` にすると `add` / `remove --force` まで通る）という**性質の違うものを 1 つの分類に混ぜる**ことになる。L4 は閉じない
- **案 B（新しい分類 `ops` の値を足して宣言制にする）**: 提供コマンドで足りる。分類が 1 つ増えると `scope-limits.json`・仕様 §8・`work-defaults.md` の 3 か所に波及し、type ごとに「どの種類に許すか」を決める判断が新たに要る
- **案 C の全面適用（白名簿をサブコマンド + オプションに作り替える）**: 維持コストが跳ね上がり、読み取り形の判定漏れで**今まで通っていた読み取りが落ちる**。閉じる向きに限った限定適用で L4 は閉じられる
- **案 E（`scope-limits.json` に前方一致の許可リストを足す）**: 前方一致は粗く（`git worktree ` と書くと `remove --force` まで通る）、仕様と設定の二重管理になる。「設定を読まないと何が通るか分からない」状態を作る
- **`-c` / `--config-env` の危険な設定名を列挙して拒否する**: 列挙から漏れた名前が `read` のまま通る。網羅を主張できない場所で網羅に頼らない
- **`cd` を通したうえで、引数が作業ツリーの内側であることを検査する / 起点を `cd` に追随させる**: 段ごとに作業ディレクトリの状態を持つことになり、`cmdpos.sh` の「段を独立に判定する」形とホットパスの制約（fork ゼロ・純 bash）に反する。得られるのは手数の改善だけで、統制は必ず弱くなる
- **L4 を別 issue へ送る**: 本 issue が同じ分岐を作り替えるので、送ると同じ場所を二度開けることになる

## 影響

- `10_spec/フック共通仕様.md` §8 に「サブコマンド + オプション」の限定適用 6 件・`cd` を足さないこと・既定拒否のまま残す範囲を書く。§7-1 に P-1・P-2 を書く。§11 の `HK-T05`（正規化）と `HK-T15`（分類）に、閉じる側と通す側の対で観点を足す
- `10_spec/hooks/20-PreToolUse/workflow-guard.md` の制御方式 6 に、`git worktree list` は通り `add` / `remove` は WF204、`cd` は WF204 であることと、`worktree.sh` の作業ツリーの置き場を指す引数を書き込み判定の対象にしないことを書く（`WG-T21`）
- `20-common-step-worktree`（新規。設計チケット 0014）は、この決定に従って `add` / `list` / `merge` / `remove` を提供コマンドとして持ち、置き場の妥当性を自分で検査する
- L1 の残り（145 件のうち `worktree list` 以外）と L2 の残り（`cd` を含む 67 語）は開かない。必要になったら、提供コマンドを足すか `allow.ops` の宣言で通す
- 提供コマンドの識別がルート相対表記に限られる制約（`cwd` がルートでない経路では提供コマンドを呼べない）は、`cd` を通さない決定と対になって残る。作業ツリーを切り替えるときはツール側の作業ディレクトリをその作業ツリーのルートにする
