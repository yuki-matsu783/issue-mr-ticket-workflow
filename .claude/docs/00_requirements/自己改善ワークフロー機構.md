# 自己改善ワークフロー機構

## 概要

Claude Code 上での開発作業を、issue を起点に MR（本書は GitLab の用語で書く。GitHub では MR → PR、`glab` → `gh` と読み替える）上で人間がレビューしながら、チケット単位で進めるワークフロー機構の要件を定義する。機構は自分自身（`.claude/` 配下の AI アセット）を改善対象に含み、作業のたびに得た知見をスキル・フック・ルール・設計文書へ還流させる。

本書は機構を利用者（開発者・レビュアー・AI エージェント）から見た振る舞いとして定義する。内部の構造（スクリプトの構成・状態の持ち方・判定の手順）は仕様書が定める。

- **背景**: 参考実装が 2 系統ある。`参考ディレクトリ/agent-workflow` は 3 層スキル（workflow / work / task）とチケット駆動、宣言した範囲の機械的な強制とワーク境界の統制を持つ。`参考ディレクトリ/MR-driven-workflow` は commit / push の提供コマンド経由の強制、レポートの HTML ビュー、DDR、敵対的レビュー、frontmatter 規約と bash 規約を持つ。本機構は両者の長所を 1 つに統合し、このリポジトリを clone すればそのまま使える形で提供する。
- **目的**:
  1. すべての開発作業が 1 issue = 1 ブランチ = 1 MR に紐づき、人間のレビューが必要な箇所では必ずレビューを経て進む
  2. AI が各チケットで「やってよいこと」「誰がやるか」「人間レビューが要るか」を宣言し、逸脱は機械的に拒否される
  3. commit / push を含む状態の変更が提供コマンド経由に限られ、AI の自己申告では状態が進まない
  4. レビュー用の成果物（レポート）が人間の読みやすい HTML ビューで提供される
  5. 決定の経緯は DDR に、現在有効な要件・仕様は requirements / spec に分けて残り、作業の知見が AI アセットへ還流する
- **スコープ**:
  - 含む: 作業の振り分け、ワークの種類とワーク境界、チケット駆動の運用、宣言した範囲の強制、commit / push の提供コマンドとそれを使うスキル、レポートと HTML ビュー、ドキュメント体系（requirements / spec / DDR / 用語辞書 / ルール）、フィードバック計画での振り返りと AI アセットへの反映、セッションをまたぐ再開
  - 含まない: MR のマージ（人間が行う）、他リポジトリへの配布と配布先からの収穫、Gemini CLI 等の他エージェント向け複製、対応工数レポート、スライド生成
- **文書の構成**: 要件定義書・仕様書・スキルは 1 : 1 : 1 で対応させ、スキルごとに `00_requirements/<スキル名>.md` と `10_spec/<スキル名>.md` を持つ。本書は特定のスキルに紐づかない横断的な要件を持ち、スキル固有の手順・承認ポイントは各スキルの要件定義書が正とする。分割済み: `00-workflow-issue-mr-driven.md`。未分割の節は該当スキルの設計時に順次分割する

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼を issue と MR に紐づけ、レビューが必要なところだけ MR 上でレビューしながら、AI に細かいチケットを 1 枚ずつ進めてほしい。

**[So that]** AI が何をしているかを常に把握でき、逸脱を機械的に止められ、レビューの負担を必要な箇所に絞れるため。

**[As a]** レビュアーとして、

**[I want]** 各ワークの成果を、結論・確度・見てほしい点が前半にまとまった HTML ビューで読みたい。

**[So that]** 差分の細部に入る前に全体像と確度をつかみ、レビューの重点を決められるため。

**[As a]** 機構の保守者として、

**[I want]** 作業中に見つかったアセットの不備や欠落を、振り返りで型どおりに洗い出し、issue や設計文書へ確実に残したい。

**[So that]** 同じ罠を繰り返さず、機構が使うたびに良くなるため。

## 受け入れ基準（Acceptance Criteria）

### A. 作業の振り分け

- When ユーザーから依頼を受けたとき、Shall AI は依頼の内容を問わず、開発作業向け（`00-workflow-issue-mr-driven`）か軽作業向け（`00-workflow-quick-request`）のどちらかの振り分けスキルを読み込んでから着手しなければならない。
- When 振り分けスキルを読み込まないまま AI がファイルの書き込みやコマンドの実行を試みたとき、Shall 機構はその操作を拒否し、どちらのスキルを読み込むべきかを AI に伝えなければならない（読み取りだけの操作は拒否しない）。
- When 開発作業と判定されたとき、Shall AI はコードに触る前に issue を確定し、issue 番号を含む feature ブランチと issue に紐づく draft MR を作ってから作業に入らなければならない（承認ポイントと手順は `00-workflow-issue-mr-driven.md` が正）。
- When 軽作業と判定されたとき、Shall AI は作業範囲を宣言してから進め、終了時に使った AI アセットの改善要否を確認しなければならない。

### B. ワークの種類とワーク境界

- When 全体計画を立てるとき、Shall AI は次の 15 種のワークから、その issue で使うフェーズ列を決め、ユーザーの合意を得なければならない。全体計画までのやり取り（issue の確定・ブランチと MR の作成・全体計画）とフィードバック計画は人間との細かい対話が要るため、サブエージェントに委ねずメインエージェントが行う。

| # | ワーク名 | 種別 | 担当 | 主な成果物 |
|---|---|---|---|---|
| 1 | 全体計画 | 計画 | メインエージェント | 全体計画書（フェーズ列・受け入れ条件との対応・各チケットの実行者とレビュー要否の方針）と最初の計画チケット |
| 2 | 調査計画 | 計画 | サブエージェント | 調査計画書、調査チケット群、次の計画チケット |
| 3 | 調査実施 | 実施 | サブエージェント | 調査結果レポート（md + HTML） |
| 4 | 設計計画 | 計画 | サブエージェント | 設計計画書（書く設計文書の一覧と骨子）、設計チケット群 |
| 5 | 設計実施 | 実施 | サブエージェント | 要件定義書・仕様書（アプリ本体向け `docs/`）、設計結果レポート |
| 6 | 実装・テスト計画 | 計画 | サブエージェント | 実装計画書（変更対象・許可範囲案・テスト方針）、実装チケット群 |
| 7 | 実装・テスト実施 | 実施 | サブエージェント | コードとテスト、実装結果レポート |
| 8 | フィードバック計画 | 計画 | メインエージェント | ここまでの振り返り（チケットの作業ログ・レビュー指摘・拒否の記録から洗い出した反映すべき内容）と、候補ごとの「この MR で対応 / 別 issue」の決定、後続フェーズ（設計フィードバック・AI アセット設計・AI アセット化）のチケットの作成・修正、別 issue の起票 |
| 9 | 設計フィードバック計画 | 計画 | サブエージェント | 実装と設計文書の差分一覧と書き戻し計画 |
| 10 | 設計フィードバック実施 | 実施 | サブエージェント | 実装に合わせて更新した設計文書、DDR |
| 11 | AI アセット設計計画 | 計画 | サブエージェント | `.claude/docs/` に書く要件・仕様の一覧と骨子 |
| 12 | AI アセット設計実施 | 実施 | サブエージェント | `.claude/docs/` の要件定義書・仕様書・用語辞書・DDR |
| 13 | AI アセット化計画 | 計画 | サブエージェント | 変更するフック・スキル・ルール・エージェント・設定の一覧とテスト方針 |
| 14 | AI アセット化実施 | 実施 | サブエージェント | フック・スキル・ルール・エージェント・設定とそのテスト |
| 15 | 全体まとめ | まとめ | サブエージェント（承認が要る操作はメインエージェント） | 残った反映すべき内容の別 issue 起票、default ブランチとの衝突解消、統括レポート（md + HTML）、MR 本文の最終化、関連 issue へのコメント、作業領域の片付け、push、draft 解除 |

- When フェーズ列を決めるとき、Shall 全体計画は issue の種別（アプリ / AI アセット。両方を含む issue は両方）を判定してユーザーと合意し、種別ごとのテンプレートを土台にしなければならない。先頭は全体計画、末尾は全体まとめとし、調査とフィードバック計画は必ず含める。

| issue の種別 | フェーズ列のテンプレート |
|---|---|
| アプリ（`docs/`・ソースコードの変更が主目的。AI アセットへは副産物として反映） | 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計フィードバック / AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |
| AI アセット（`.claude/` 配下の変更が主目的） | 調査 → AI アセット設計 → AI アセット化 → フィードバック計画 → 追加の AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |

- When テンプレートを当てるとき、Shall 主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット化）は依頼の性質に応じて全体計画で含め、フィードバック計画より後のフェーズは全体計画では決めずフィードバック計画で決めなければならない。フィードバック計画以外のフェーズは「計画 → 実施」の対で並べる（片方だけの採用は不可）。
- When フェーズを並べるとき、Shall 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計フィードバック → AI アセット設計 → AI アセット化 → 全体まとめ の順とし、含めないフェーズだけを飛ばさなければならない。
- When 含めたフェーズでやることが無いと計画ワークで分かったとき、Shall そのフェーズを省くのではなく、計画チケットを「対象なし」として即座に完了し、次のフェーズの計画チケットを起こさなければならない（まだ行っていない全体計画の段階で「やらない」と判断しない）。
- When フィードバック計画を行うとき、Shall メインエージェントはユーザーと対話しながら、ここまでのワークで得た反映すべき内容（チケットの作業ログ・レビュー指摘・拒否と確認の記録・レポートの「想定と異なった点」）を振り返り、候補ごとに「この MR で対応する」か「別 issue として起票する」かを決め、設計フィードバック・AI アセット設計・AI アセット化のチケットを作成・修正しなければならない。既定はこの MR で対応し、変更が大きくなりすぎる場合に別 issue とする。振り返りと候補の取捨の機会はこの 1 回だけとし、以後のワークで見つかったものは全体まとめで別 issue にする。
- When 全体計画とフィードバック計画以外のワークを実施するとき、Shall 各ワークは原則としてサブエージェント（独立したコンテキスト）で実施され、メインエージェントはワークの起動・結果の受け取り・ワーク境界の処理（push・MR 本文更新・レビュー依頼）に徹しなければならない。ワークを担当するサブエージェントのモデルは全体計画で合意する。
- When ワークの中のチケットを実施するとき、Shall チケットは既定ではそのワークのサブエージェントの中で順に実施され、互いに依存しないチケット群を並列に進めたいとき、または新しいコンテキストで実施したいとき（チケットの実行者がワークのモデルと異なるときを含む）に限り、チケット単位でさらにサブエージェントに分割しなければならない。分割したチケットにも宣言した範囲の強制（D 節）が同じように働く。
- When 1 つのワーク（同じ種類のチケット群）が完了したとき、Shall そこをワーク境界とし、そのワークのチケットに 1 枚でも「人間レビュー要」のものがあれば、MR 上の人間レビューが完了するまで次のワークに進めてはならない。
- When ワークのチケットがすべて「人間レビュー不要」のとき、Shall AI は人間レビューを待たずに次のワークへ進んでよいが、そのワークの成果を push し、MR 本文に要約を追記し、レビューを省略したことをユーザーに報告しなければならない。
- When 計画ワークが完了するとき、Shall その計画ワークは同じフェーズの実施チケット群と、次のフェーズの計画チケット 1 枚を作成済みでなければならない（チケットを最初に全件作らない）。
- When ワークが承認され次のワークに進むとき、Shall AI はまだ着手していないチケットの内容（範囲・実行者・レビュー要否・DoD）をレビュー結果や新しい知見に合わせて修正してよく、修正した場合はその内容を人間に伝えなければならない。
- When 全体まとめのワークを行うとき、Shall フィードバック計画より後のワークで新たに見つかった反映すべき内容の別 issue 起票（承認を得て。この MR では対応しない）→ default ブランチとの衝突解消 → 統括レポートの作成 → MR 本文の最終化 → 関連 issue へのコメント → 作業領域の片付け → push → draft 解除 の順に行い、マージは行わず停止しなければならない。振り返りと候補の取捨はフィードバック計画で 1 回だけ行い、全体まとめでは繰り返さない。人間の承認が要る操作（衝突解消・issue へのコメント投稿）はメインエージェントが承認を取って行う。

### C. チケット駆動の運用

- When 開発作業の振り分けが決まったとき、Shall 最初に全体計画チケットが作業中に置かれ、issue の確定からフェーズ列の合意までがそのチケットの中で行われなければならない（以降のプロンプトで振り分けの再宣言を求められないようにするため）。
- When チケットを作るとき、Shall チケットは次を明記しなければならない: ワークの種類、状態、先行チケット、**実行者（担当する LLM モデル）**、**人間レビューの要否とその理由**、**このチケットでやってよいこと**（書き込んでよい範囲・実行してよい操作の分類）、目的、完了条件（DoD）。
- When 全体計画でユーザーと合意するとき、Shall 各チケットの実行者と人間レビュー要否の方針（どの種類・規模の作業を誰に任せ、どこで人間が見るか）を合意の対象に含めなければならない。
- When チケットに実行者が記載されているとき、Shall そのチケットは記載されたモデルで実施され、別のモデルで実施してはならない。
- When チケットに着手・完了するとき、Shall AI は提供コマンドで未着手 → 作業中 → 完了へ状態を進め、手作業でファイルを動かしてはならない。
- When 作業中のチケットが既に 1 枚あるとき、Shall 機構は 2 枚目の着手を拒否しなければならない（同時に作業中のチケットは 1 枚）。
- When チケットを完了するとき、Shall DoD がすべて満たされ、作業ログ（うまくいったこと・うまくいかなかったこと・仕様からの逸脱・**AI アセットに反映すべき内容**）が書かれていなければならない。サブエージェントが実施したチケットも同じで、後のフィードバック計画がこの記録だけで振り返れる粒度で残す。
- When 次に着手するチケットを選ぶとき、Shall AI は提供コマンドが示す「次のチケット」と「次に読み込むスキル」に従い、目視で判断してはならない。
- When MR のマージ前に作業領域（全体計画・チケット・計画書・レポート・進行状態）を片付けるとき、Shall 片付けは提供コマンドで行い、main に残したい要約は MR 本文・issue コメント・`.claude/docs/` に書き写されていなければならない。

### D. 宣言した範囲の強制

- When チケットが作業中のとき、Shall AI の書き込みと操作は、そのチケットに宣言された「やってよいこと」の範囲でのみ許可されなければならない。
- When 宣言の範囲外の書き込み・操作が試みられたとき、Shall 機構はそれを拒否し、AI に「何に違反したか・どのチケットの作業中か・次に取るべき対処」を伝えなければならない。対処には「迂回せず、必要ならユーザーに提案する」ことを含める。
- When チケットが宣言できる範囲を決めるとき、Shall ワークの種類ごとの上限（書き込んでよい範囲・禁止範囲・操作の分類）はユーザーが管理する設定が定め、チケットの宣言でその上限を超えて権限を広げられてはならない。
- When 作業中のチケット自身の種類や宣言を AI が書き換えようとしたとき、Shall 機構はそれを拒否しなければならない。
- When 設定にも宣言にも無い範囲へ書き込もうとしたとき、Shall 機構は拒否ではなくユーザーへの確認とし、承認された範囲は同じセッション内では再確認しなくてよい。ユーザーが応答できない実行形態では確認は拒否として扱われる。
- When AI アセットを変更するとき、Shall AI アセット設計のチケットは `.claude/docs/` のみ、AI アセット化のチケットはフック・スキル・ルール・エージェント・設定のみを書け、それ以外のチケットからは `.claude/` 配下を書けてはならない。
- When 機構が許可・確認・拒否のいずれかを判定したとき、Shall その記録が残り、振り返りのときに AI とユーザーが参照できなければならない。
- When 機構が進行状態を記録したファイルを AI が直接書き換えようとしたとき、Shall 機構はそれを拒否しなければならない（チケットの作業中かどうかを問わない）。

### E. commit / push の提供コマンド経由の強制

- When AI がコミットまたは push を行うとき、Shall それぞれ提供コマンド経由でのみ行え、`git` のコミット・push を直接実行しようとすると拒否され、使うべきコマンドとスキルが伝えられなければならない。
- When 直接実行を検知するとき、Shall コミットメッセージ・ヒアドキュメント・コメント・日本語の地の文に「commit」「push」の語が含まれるだけでは拒否されてはならない。
- When コミットの提供コマンドを使うとき、Shall メッセージと対象ファイルを明示して渡す必要があり、直前のコミットの書き換え・フックの無効化・全ファイルの一括ステージはできてはならない。クレデンシャル類と開発副産物は自動で除外され、除外した事実が AI に伝えられる。
- When コミットメッセージを作るとき、Shall 件名は `<prefix>: <日本語の説明>` の 1 行で「何を」「どう」変えたかを含み、AI 生成物であることを示すフッターや生成モデル名を含めてはならない。prefix は Conventional Commits に `ai-asset`（`.claude/` 配下の AI が読むアセットの変更）を加えたものとする。
- When push の提供コマンドを使うとき、Shall push 前チェック（未コミットの変更が無い・作業中のチケットが無い・レポートの md と HTML が同期している、など仕様で定める項目）が行われ、未充足なら push されずに理由が伝えられなければならない。
- When push 前チェックの項目を意図的に飛ばすとき、Shall 飛ばした項目と理由が MR の差分としてレビュアーに見える形で記録されなければならない。レビュアーに見えない無効化手段は提供しない。
- When AI がこれらの提供コマンドを使うとき、Shall コミット用・push 用の task スキルが手順を標準化し、他のスキルはそのスキルを参照して使わなければならない。
- When 提供コマンドによる状態の変更（チケットの着手・完了、レビュー依頼・完了、マージ前作業）がコミットを伴うとき、Shall それらのコミットもコミットメッセージの規約に従わなければならない。

### F. レポートと HTML ビュー

- When 実施ワーク（調査・設計・実装・設計フィードバック・AI アセット設計・AI アセット化）と全体まとめが完了するとき、Shall 結果が `wip/30_reports/` に Markdown で書かれ、同じ名前の HTML ビューが併存しなければならない。Markdown が正文で、HTML はその視覚化である。
- When HTML ビューを作るとき、Shall AI は提供されたテンプレートをコピーし、Edit で節を埋め、使わない任意の節を削除し、雛形の痕跡（プレースホルダ）を 1 つも残してはならない。
- When HTML ビューをブラウザで開いたとき、Shall ネットワーク接続なしで表示でき、ライト / ダークどちらのテーマでも読めなければならない。
- When レポートを読むとき、Shall 「サマリ（総括・件数・重点レビュー依頼）→ 確かめられなかったこと → 実施した内容と結果 → 設計への反映 → 想定と異なった点 → 残課題」の順に並び、結論の性質（良 / 注意 / 問題）とレビューの重み（特に見てほしい / 承認が欲しい / 細かいレビュー不要）が別の軸で、色だけに頼らず記号と文字でも読み取れなければならない。
- When レポートのテンプレートに複数のデザインがあるとき、Shall デザインを切り替えても書き方（節・プレースホルダ・検査手順）が変わってはならない。
- When HTML ビューを出力したあと、Shall AI は雛形の痕跡・壊れたリンク・重複した見出し ID・外部リソースへの依存が無いことを確認し、結果をチケットの作業ログに残さなければならない。
- When 計画書（全体計画・各計画ワークの計画書）を書くとき、Shall 計画には「これから何をするか」のみを書き、実施結果はレポートへ分離しなければならない。計画書の HTML ビューは任意とする。
- When 全体まとめを行うとき、Shall 統括レポートが issue の受け入れ条件との対応、各ワークのレビュー結果（省略した場合はその旨）、フィードバック計画で決めた対応（この MR で対応したもの・別 issue に起票したもの）、残課題を 1 つにまとめ、その要約が MR 本文と issue コメントに書き写されなければならない。

### G. ドキュメント体系

- When 機構自身の設計を書くとき、Shall 要件定義書を `.claude/docs/00_requirements/`、仕様書を `.claude/docs/10_spec/`、DDR を `.claude/docs/20_ddr/`、用語辞書を `.claude/docs/90_glossary/` に置かなければならない。アプリ本体の設計文書は `docs/` 配下に同じ運用で置く。
- When requirements / spec を更新するとき、Shall それらは「その時点で有効な正史」だけを記述し、検討の経緯・却下した案・過去の版の内容・変更履歴の表を本文に残してはならない（履歴は git のコミット履歴と DDR で追う）。
- When requirements を書くとき、Shall 利用者から見た振る舞い（何ができ、何が拒否され、何が出力されるか）で記述し、内部構造（コマンドの構成・状態の持ち方・判定の手順）は spec に書かなければならない。
- When 設計上の決定（複数案から選んだ・方針を変えた）が行われたとき、Shall その背景・決定・理由・却下案・影響が DDR に記録されなければならない。DDR は issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md` で命名し、issue を持たない DDR は作らない。
- When DDR がマージされたあと、Shall 本文を変更してはならず、後続の決定で無効になった場合は frontmatter の状態（置き換え済み / 廃止）と置き換え先だけを更新しなければならない。
- When DDR の一覧を参照するとき、Shall 一覧は各 DDR の frontmatter から生成されたものであり、手書きで保守されていてはならない。
- When リポジトリ内に Markdown を作るとき、Shall OKF 準拠の frontmatter（`type` 必須、`title` / `description` / `tags` / `keywords` 推奨）が付いていなければならない。ただし issue / MR に投稿される本文や断片、機構が解釈する専用 frontmatter を持つチケットは対象外とし、SKILL.md とエージェント定義の既存 `description` は上書きしない。
- When テンプレートファイルを置くとき、Shall 名前が `<名前>.template.md` / `.template.html` / `.template.sh` に統一され、テンプレートは完成形として正しい `type` を含んでいなければならない。
- When 用語を調べるとき、Shall 用語辞書は正典（requirements / spec）への案内役に徹し、辞書自身が用語を再定義していてはならない。

### I. 自己改善（振り返りと AI アセットへの反映）

- When フィードバック計画を行うとき、Shall AI はその issue でここまでに使った AI アセット（スキル・フック・ルール・エージェント・CLAUDE.md）と、チケットの作業ログ（うまくいかなかったこと・AI アセットに反映すべき内容）、拒否・確認の記録、レポートの「想定と異なった点」「重点レビュー依頼」、MR のレビュー指摘を入力として、改善候補を洗い出さなければならない。
- When 改善候補を分類するとき、Shall 「足りなかった」「邪魔だった」「無かった」「問題なし」の観点と、「(a) アセットが無かった」「(b) あったが誤っていた」「(c) あったが罠が書かれていなかった」「(d) あったのに辿り着けなかった」の類型で整理し、候補が 0 件のときも 0 件である根拠をレポートに残さなければならない。
- When 改善候補の反映先を決めるとき、Shall 「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / 操作のたび）」と「守らせ方（読ませる / 手順化する / 機械的に拒否する）」の 2 軸で選び、常時読込のアセットを増やすコストを考慮しなければならない。
- When 改善候補の対応先を決めるとき、Shall 既定ではこの MR の AI アセット設計・AI アセット化のフェーズで対応し、変更が大きくなりすぎる場合に限り別 issue として起票しなければならない（起票は承認を得てから）。設計文書への反映は設計フィードバックのフェーズで行う。
- When 実施ワークの成果を人間レビューに出す前に、Shall AI は敵対的レビュー（経緯を知らされない読み取り専用のレビュアーが、ディレクトリごとのレビュー観点表に沿って欠陥を探す）を実施でき、指摘は MR のインラインコメントとして投稿され、人間の指摘と同列に返信されなければならない。実施回数はフェーズごとに上限を持ち、上限を緩める手段を用意しない。
- When 軽作業（`00-workflow-quick-request`）が終わるとき、Shall フィードバック計画と同じ観点・類型で使った AI アセットの改善要否を確認し、「issue として記録だけする」を選べなければならない。

### J. セッションをまたぐ継続

- When セッションが開始・再開・compact されたとき、Shall AI は現在のブランチ・issue・MR・チケットの状態・レビュー状態・次に読み込むべきスキルを知らされ、手書きの引き継ぎメモに頼らずに再開できなければならない。
- When 振り分けスキルの再宣言を求めるとき、Shall チケット（未着手 / 作業中 / 完了のいずれか）が作業領域にある間は継続とみなし、再宣言を要求してはならない。
- When 全体まとめで作業領域を片付けたあとに push と draft 解除を行うとき、Shall チケットが無い状態でもこれらの操作が拒否されず、振り分けの再宣言も求められてはならない。
- When レビュー依頼・完了・マージ前作業の進行状態を扱うとき、Shall それらは AI の申告ではなく MR への実操作（コメント投稿・レビュー取得）の証跡に基づいて進み、証跡は MR の差分としてレビュアーが確認できなければならない。

### アルタナティブフロー（代替経路）

- When issue と MR を作らずにチケット駆動だけを試すとき、Shall ワーク境界の承認をチャット上の確認で取る単独実行モードを提供し、その経路は証跡が会話上の承認に依存することを仕様に明記しなければならない。
- When `glab` / `gh` CLI が使えない環境のとき、Shall MR 操作を外部（MCP ツール等）に委ねるモードを提供し、証跡の強度が CLI 実行時より劣ることが記録されなければならない。
- When 小さな依頼でワーク境界の往復が過剰なとき、Shall チケットの人間レビュー要否を「不要」に倒し、やることの無いフェーズは計画ワークで即座に完了することで対処し、必須フェーズの省略やワークの種類の統合では対処してはならない。
- When レビュアーがチャットでレビュー判断を伝えたとき、Shall AI はその判断を MR の通常コメントとして記録してからレビュー完了の手続きに進まなければならない。

### 例外フロー（エラーケース）

- When 機構が操作を拒否したとき、Shall AI は進行状態の直接編集・別の手段での迂回・機構の無効化を行わず、伝えられた対処に従うか、ユーザーに提案しなければならない。
- When レビュー完了の手続きが「変更要求あり」または「未返信のスレッドあり」で止まったとき、Shall AI は同じ種類の追加チケットで対応し、スレッドに返信してから再実行しなければならない。
- When マージ前の衝突判定で default ブランチとの衝突が検知されたとき、Shall AI は衝突ファイルを示して承認を得てから `git merge` で取り込み、`git rebase` や片側丸ごと採用で解消してはならない。
- When 機構自身の依存（jq・設定・補助ファイル）が壊れていて判定できないとき、Shall 拒否側の仕組み（宣言範囲の強制・commit / push の強制）は拒否へ倒し、案内側の仕組み（セッション開始時の現在地の通知）は何も出さずに通す。どちらへ倒すかは仕様に明記する。
- When ユーザーが応答できない実行形態で承認が必要になったとき、Shall AI は承認が必要な内容を報告してセッションを終え、次回セッションの再開から続けなければならない。
- When 承認が得られずに却下されたとき、Shall AI はその段階に留まり、先の段階（issue 作成・ブランチ作成・マージ前作業・issue への投稿）へ進んではならない。

## 前提条件

- リポジトリは GitLab または GitHub でホストされ、対応する CLI（`glab` / `gh`）が導入・認証済みである（未導入時は導入を案内して停止する）。初版の動作確認はこのリポジトリ（GitHub）で行う
- 実行環境は Windows の git bash（MSYS bash 4.3 以上）と `jq` を前提とし、WSL / Linux での動作は未検証として扱う
- MR は squash merge され、ブランチ上の作業領域（`wip/`）の履歴は main に残らない
- ユーザーは MR 上でレビュー（approve / comment / changes requested / インラインコメント）を行える
- 1 issue = 1 ブランチ = 1 MR。1 セッションは 1 つの MR だけを扱う
- チケットの実行者として指定できるモデルは、Claude Code のサブエージェントで選択できるモデルに限る
- Claude Code のサブエージェントは入れ子で起動できない前提とし、チケット単位のサブエージェントはメインセッション（オーケストレータ）が起動する。この前提が変わった場合は仕様側で起動元を見直す

## 制約条件

- **技術的制約**:
  - 機構の実体（フック・スクリプト）は bash で書き、bash 規約（H 節）に従う。PowerShell からの操作も検知対象に含めるが、実処理は bash に統一する
  - Claude Code の権限設定だけでは複合コマンドを止められないため、強制は機構側が担う（権限設定は多重防御として併用してよい）
  - HTML ビューは自己完結とし、Claude Code の Artifact 機能に依存しない（ローカルでブラウザを開けば読める）
- **ビジネス的制約**:
  - MR のマージ・issue の内容・レビュー完了の判断は人間が行う。AI は draft 解除までで止まる
  - 他人の issue への投稿など取り消せない外部への副作用は、本文そのものの承認を得てから行う
- **外部的制約**:
  - GitLab の場合、インラインコメントは 1 件ずつ投稿され、MR 作成直後は差分の参照情報が未確定のことがある。GitHub の場合、インラインコメントの投稿はまとめて成功または失敗する
  - `glab` / `gh` は人間のアカウントで認証されるため、AI の投稿は本文先頭の署名で識別する

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | 対象外の操作に対する機構の判定は体感できない時間（数十 ms）で終わる。セッション開始時の通知は 8 KB を目安とし、超過時は警告を添える |
| セキュリティ | AI が書いた宣言を信頼せず、権限の上限はユーザー管理の設定が決める。クレデンシャル類はコミットから自動除外される。判定の記録に機密情報を出力しない。悪意ある迂回への対抗は目的としない（既定動作を安全側へ倒す仕組みであり、安全境界ではない） |

| テスト容易性 | 機構の実体は単体テストでき、テストは合否件数を出力し失敗時に非 0 で終わる |

| 一貫性 | 振り返りの観点・類型の文言をフィードバック計画と軽作業の両方で揃える。レポートのテンプレートはデザインを変えても書き方が同じ |
