# i0009-42. 打ち切りの fail-open に権限設定と事後ゲートを採らない

## 背景

`i0009-11` は「フックの打ち切り（timeout）は fail-open であり、登録ラッパーも `trap ERR` も効かない。塞ぐ手段は速さだけ」と決め、要件にも「**この経路は塞げないため**、判定は打ち切りに達しない速さで終わる」と書いた。

ワーク境界のレビューで、`i0009-11` の却下した案が**機構の外側の手段を検討していない**ことが指摘された。公式には次の 2 つの経路がある。

- `hooks.md:1744`（PreToolUse の decision control）: 「[Deny and ask rules] are still evaluated regardless of what the hook returns」— ユーザーが管理する権限設定の拒否規則は、フックの結果（打ち切りを含む）に関係なく評価される
- `hooks.md:867`（Exit code 2 behavior per event）: `PostToolBatch` の終了 2 は「Stops the agentic loop before the next model call」— ツール実行後に agentic loop を止められる

さらに要件の制約条件は「Claude Code の権限設定だけでは複合コマンドを止められないため、強制は機構側が担う（**権限設定は多重防御として併用してよい**）」と既に書いており、「塞げない」という断定と整合していなかった。

## 決定

- **どちらも機構の決定には含めない**。`i0009-11` の方針（速さで守る）を維持する
- `i0009-11` の却下した案に 2 案を**理由付きで**加える
- 要件の例外フローの文言を「この経路は塞げないため」から「**機構の中にこの経路を塞ぐ手段は無い**ため」に変え、**機構の外側の多重防御（権限設定）は打ち切りの影響を受けないので併用してよい**と書き足す（制約条件との整合）

## 理由

- **`permissions.deny` は有効だが機構の持ち物ではない**。`.claude/settings.json` は `common.confirm` に置いて毎回確認にしている対象で、機構（`.claude/hooks/**`）が自分の弱点を補うために書き換えてよいものではない。ユーザーが併用するのは自由で、要件の制約条件がそれを認めている
- **権限設定に寄せると「止まったつもりで止まっていない」を作る**。要件の技術的制約が言うとおり、権限設定だけでは複合コマンド（`a && b`）を止められない。打ち切りの穴を埋める目的で規則を並べても、埋まるのは単純なコマンドの一部だけで、埋まったと誤解する害の方が大きい
- **`PostToolBatch` は「実行前に止める」を満たさない**。機構が守る対象（push・issue への投稿・ファイルの削除）は、事後に agentic loop を止めても既に起きている。得られるのは「次のモデル呼び出しを止める」だけで、フックが 1 本増えて全ツール呼び出しの後に走るコストに釣り合わない
- **穴を認めて書くことに価値がある**。`i0009-11` の趣旨は「守れていない経路がある」と正直に書くことだった。外側の手段を検討したうえで採らないと書けば、その趣旨は保たれ、後から読む人が同じ検討を繰り返さずに済む

## 却下した案

- **`permissions.deny` に機構が規則を書き込む**: 上記のとおり持ち物の境界を越える。しかも複合コマンドを止められないので穴は埋まらない
- **`PostToolBatch` フックを 1 本足して事後に止める**: 実行前に止められない以上、機構の目的に寄与しない
- **要件から「塞げない」の断定だけを消す**: 断定を消すだけでは、読み手が「では何をすれば塞がるのか」を知らないままになる。外側の手段があること（と、それが機構の決定ではないこと）まで書く
- **`permissions.deny` の併用手順を機構のドキュメントに書く**: ユーザーの環境と方針に依存し、機構が保証できない。制約条件の 1 行（併用してよい）に留める
