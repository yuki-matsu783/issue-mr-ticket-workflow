# i0009-30. 作業中と完了チケットの削除を `workflow-state-guard` が塞ぐ

## 背景

`workflow-state-guard` の実行ツールの判定は「`mv` / `cp` / `git mv` / `touch` / リダイレクトの**宛先**が `10_doing/` → WF302、`20_done/` → WF303」だった。**`rm` が一覧に無く、しかも「宛先」の判定**なので、`rm wip/10_tickets/20_done/0003.md` はどの条件にも当たらない。

境界レビュー（付録 A の R23）の指摘: 作業中チケットが 0 枚の切れ目では `workflow-guard` も判定しない（判定順 1「作業中チケット 0 枚 → 許可」）ので、**削除は誰にも止められない**。

完了チケットは機構の判定材料である。

- `workflow-entry` の継続条件（`00_todo` / `10_doing` / `20_done` のいずれかにチケットがある間は宣言を求めない）
- `workflow-diff-check` の先行チケットの完了判定（WF602）
- `ticket.sh next` の `predecessors` の解決

消えると、これらが静かに違う答えを返すようになる。

## 決定

制御方式 3（実行ツール）に**元（消える側）の判定**を足す。

- `rm` / `git rm` / `mv` / `git mv` の**元**が `wip/10_tickets/10_doing/**` → **deny WF302**
- 同じく `20_done/**` → **deny WF303**
- メッセージの対処: 作業中の取り消しは `ticket.sh cancel`、完了済みは触らない
- テスト `SG-T02` に `rm` のケース（`wip/tmp/` の `rm` は通る負のコントロール付き）を足す

## 理由

- **削除は置き場から状態を消す操作**で、作成・移動と同じ強度で守るべきもの。「宛先」だけを見ていたのは、`ticket.sh` が作る／動かす経路を想定していたからで、消す経路を見落としていた
- **切れ目に守りが無いのは意図的な緩和ではない**。§13 の「継続条件の窓」は「切れ目の処理に必要な書き込みを妨げない」ための緩和で、そこで機構が守ると明言しているのは「進行状態・コミット / push・`chmod`」。チケットの置き場は state-guard 自身が「進行状態」と定義している（概要）ので、緩和の対象ではない
- state-guard は作業中チケットの有無を問わず判定する（呼出条件）ので、切れ目でも効く。追加の登録も要らない

## 却下した案

- **`workflow-guard` の側で塞ぐ**: 切れ目では判定しないので効かない。作業中チケットの有無に依らず働く state-guard が正しい持ち主
- **`rm` を全面的に禁止する**: `wip/tmp/**` の掃除など正当な `rm` がある。対象を置き場に限る
- **§13 に「削除は強制しない」と書いて緩和にする**: 消えたときの影響（継続条件・先行判定が静かに変わる）が大きく、緩和として釣り合わない
- **`.gitignore` や権限で守る**: `wip/10_tickets/**` は git 管理下（チケットはコミットされる）なので `.gitignore` は使えず、権限は `chmod` 禁止と衝突する

## 影響

- `10_spec/hooks/20-PreToolUse/workflow-state-guard.md` 制御方式 3・`SG-T02`
- **実装フェーズへ**: `cmdpos.sh` が返すコマンド列から「元」の位置の引数を取る必要がある（`rm <paths...>` / `git rm <paths...>` / `mv <src> <dst>`）。`mv` は元と宛先の両方を見る
