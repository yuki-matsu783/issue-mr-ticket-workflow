# フック共通仕様

各フックの要件定義書が「フック横断の仕様書が正として定める」と委ねた事項をここに置く。個々のフックの仕様（`10_spec/hooks/<NN-Event>/<name>.md`）はこの文書を前提に差分だけを書く。

## 1. 置き場と登録

- 実体: `.claude/hooks/<NN-Event>/<name>.sh`（bash。`bash <パス>` で呼ぶため実行権限は不要）。**`<NN-Event>` は「主たるイベント」**で、登録先のイベントと一致しないことがある（DDR i0001-24。実際に一致しない登録が 3 行ある — 下表の注記）。テストは同じディレクトリの `tests/test_<name>.sh`（雛形は `20-common-step-shell-script`）
- **フックが読む外部データ**: `.claude/hooks/config/`（1 ファイル 1 用途。`scope-limits.json` / `task-types.tsv` / `blocked-commands.txt` / `entry-skills.txt` / `model-aliases.txt`）。**フックのディレクトリに `assets/` は置かない**（`assets/` はスキル配下のテンプレート等に限る。DDR i0009-10）。`config/` 配下は `common.confirm` に当たるため、新規作成時に毎回 WF203 の確認が入る
- 共有ライブラリ: `.claude/hooks/lib/`
  - `hook-common.sh`: 入力 JSON の読み取り（`jq`。上限と 2 段の内訳は §1 の「`jq` は最大 2 回」。DDR i0009-46）、緊急停止の判定、記録（`logs/`）、deny / ask / additionalContext の出力ヘルパ、セッション状態の読み書き、`redact`（§3）、`tool_class`（§2）、記録の書き込みヘルパ（下表）
    - **副入力の渡し方（DDR i0009-47）**: `--slurpfile` を使わない。**存在するファイルだけを `--rawfile <名前> <パス>` で文字列として渡し、`jq` の中で `fromjson? // null` に通す**。存在しないファイルは `--argjson <名前> null` に差し替える（存在の確認は `[ -f ]`。bash の組み込みなので fork しない）。理由は `--slurpfile` が**副入力の破損・不在で呼び出しごと失敗して stdout を空にする**ため（実測: 終了 2・stdout 空）。それでは設定 1 ファイルの破損が `tool_name` の取得すら奪い、WF210 の復旧経路（`workflow-guard` 制御方式 3）と既定値へのフォールバック（`workflow-state-guard` 制御方式 0・DDR i0009-29）が実装できない
    - 副入力が読めなかった（不在・破損）ことは `HC_<名前>_STATE`（`ok` / `missing` / `broken`）で呼び手に伝える。**呼び手のフックがそれをどう扱うかはフックの制御方式が決める**（拒否側は自分で deny に倒すか既定値で続けるかを選ぶ）

    | 関数 | 引数 | 戻り値 | 責任範囲 |
    |---|---|---|---|
    | `hook_read_input [limits]` | 読む副入力の名前（省略可） | 0 / 1（stdin が JSON でない）/ 2（`jq` 不在） | stdin と、**パスが stdin に依存しない副入力**（`scope-limits.json`）を **1 回の `jq`** で読み、`HOOK_*` と `HC_*` に置く |
    | `hook_read_state [review] [merge] [approvals] [entry]` | 読む副入力の名前 | 0 / 1（`jq` 不在） | **1 回の `jq`** でまとめて読み、`HC_*` に置く。要るフックだけが呼ぶ。**要求されなかった名前も `--argjson <名前> null` で必ず渡す**（`jq` のプログラムは 4 つの変数をすべて参照するので、1 つでも欠けるとコンパイルに失敗して出力が空になり、読めたはずの副入力まで `missing` に化けて縮退と区別できなくなる。HK-T18） |
    | `hc_append_jsonl <file> <line>` | 追記先・1 行 | 0 / 1（書けない） | `redact`（§3）を通し、**この関数が** 4 KB 未満に切り詰め（`note` と `target` は合わせて 1 KB）、`…` を付けて `>>` で追記する。呼び手は切り詰めない |
    | `hc_json_write <file> <content>` | 置き換え先・内容 | 0 / 1 | `<name>.tmp.<pid>` へ書いて `mv`。呼び手は一時ファイル名を作らない |
    | `hc_lock <name>` | ロック名 | 0（取れた）/ 1（**2 秒**で諦めた） | `mkdir <name>.lock`。**取得を試みる前に、既存のロックの作成時刻が 60 秒より古ければ陳腐化とみなして `rmdir` し、強制解放を実行ログに 1 行残す**（打ち切りでは `trap` が効かないため。§3・DDR i0009-60）。取得できたら `trap` に解放を登録する。2 秒と 60 秒の値はこの関数が持ち、呼び手は指定しない |
    | `hc_unlock <name>` | ロック名 | 常に 0 | `rmdir`。取っていなくても失敗しない（冪等） |

    （lib 単体のテスト観点は §11 HK-T06〜T08・T10・T17・T18）
  - `cmdpos.sh`: コマンド位置の判定（§7）。`block-direct-git` が正で、`block-chmod` / `workflow-guard` / `workflow-state-guard` / `post-push-*` が共有する（lib 単体のテスト観点は §11 HK-T05・T12）
  - `scope.sh`: 許可範囲の判定（§8）。`workflow-guard` が正で、`workflow-diff-check` / `subagent-stop-check` が共有する（lib 単体のテスト観点は §11 HK-T11・T15・T16）
  - `push-detect.sh`: push の検知。`post-push-compact-prompt` が正で、`post-push-usage-report` が共有する（lib 単体のテスト観点は §11 HK-T13）
  - `transcript.sh`: transcript の解析（使用量の集計を 1 関数に閉じる）。`post-push-usage-report` が正（lib 単体のテスト観点は §11 HK-T14）。時刻の変換は自前の暦計算で行う（Windows の jq 1.6 では `strptime` / `fromdateiso8601` が動かない）
  - `lib/` の外にある依存: `frontmatter.sh`（`.claude/skills/20-common-step-shell-script/scripts/`。`scope.sh` がチケットの frontmatter を読むために `source` する。§7・§9。**`scope.sh` 側の読み込みポリシーは `nop`** で、読めなければ `fm_*` が**出力なし・戻り値 2** のスタブになり `FM_AVAILABLE=0` が立つ（§8 の「出力の形」・`20-common-step-shell-script` 仕様「読み込み行」）。失敗をどう扱うかは呼び手のフックが決める（拒否側は自分で deny に倒し、案内側は何も出さずに通す。§12 T8 — `20-common-step-shell-script` 仕様「読み込み行」））
- 登録: `.claude/settings.json` の `hooks` に、イベントごとに `{"matcher": ..., "hooks": [{"type": "command", "command": "bash \"${CLAUDE_PROJECT_DIR}/.claude/hooks/<NN-Event>/<name>.sh\""}]}` で登録する。**パスは `${CLAUDE_PROJECT_DIR}` を基準にした絶対パスで書き、ダブルクォートで囲む**（公式は「Use absolute paths: specify full paths for scripts. … In shell form, wrap it in double quotes」と定める）。相対パス（`bash .claude/hooks/...`）にしてはならない — フックは**実行時のカレントディレクトリ**で起動され（公式「Handlers run in the current directory with Claude Code's environment.」）、Claude が `cd` した後や worktree ではリポジトリルート以外になり得る。そこで相対パスが解決できないと終了 127 になり、**拒否側 5 登録のラッパーが全操作を deny してロックアウトする**（DDR i0009-20）。登録の正は次の表（各フックの仕様「呼出条件」と一致させる。テスト HK-T01 で照合）

1 行 = 1 登録（イベント × matcher × フック）。`位置` は同じイベント内での `settings.json` の**配列上の位置**であって**実行順ではない** — 公式は「**All matching hooks run in parallel.**」と明記しており、同じイベントに一致するフックはすべて同時に起動する（DDR i0009-21）。HK-T01 はこの表と `settings.json` を行単位で照合する（イベント・matcher・フック・配列上の位置）。**全 16 行**（フック 11 本 + 複数登録 5 行）。内訳は SessionStart 1 / UserPromptSubmit 1 / PreToolUse 6 / PostToolUse 4 / SubagentStart 1 / SubagentStop 2 / Stop 1。うち**拒否側は 5 行**（PreToolUse の 2〜6）で、残る 11 行が記録・案内側。**`subagent-start-check` を PreToolUse `Agent` に登録する行は無い** — 起動前に人間へ届く経路（`systemMessage`）が実在しないため（§3）、実行者の不一致（WF801）と background 起動（WF803）の検知は `subagent-stop-check`（PostToolUse `Agent`）に一本化する。

|---|---|---|---|---|
| 1 | SessionStart | — （全 source） | session-start | 案内 |
| 1 | UserPromptSubmit | — | workflow-entry | プロンプト境界の処理（記録のみ） |

| 2 | PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|EnterPlanMode\|Agent\|Workflow\|mcp__.*` | workflow-entry | 未宣言の拒否（拒否側。MCP は宣言の有無だけを見る — DDR i0009-27） |
| 3 | PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|mcp__.*` | workflow-state-guard | 進行状態・置き場・draft 解除の保護（拒否側。MCP は draft 解除の直接実行の検知用） |

- **表に現れない登録の細部**（HK-T01 が照合する `command` 文字列の材料）:
  - **引数を取る登録が 2 行**: SubagentStop と Stop の `post-push-usage-report` は `--accumulate` を渡す（`command` は `bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/22-PostToolUse/post-push-usage-report.sh" --accumulate`）
  - **実体のディレクトリと登録先イベントが一致しない行が 3 行**: `13-SubagentStop/subagent-stop-check.sh` を PostToolUse に、`22-PostToolUse/post-push-usage-report.sh` を SubagentStop と Stop に登録する。ディレクトリは**主たるイベント**を表す（DDR i0001-24）
  - したがって HK-T01 は「イベント名 → ディレクトリ」の機械的な変換で照合できない。**この表に対応する `command` 文字列の一覧**（16 行分）を検査の期待値として持つ
- **`timeout` は登録に明示しない**（既定に従う: `command` 型は 600 秒。ただし `UserPromptSubmit` に登録するものは Claude Code が既定を 30 秒に下げる）。打ち切られた場合の挙動は §3 の fail-open を参照。フックの実行時間は**ホットパス（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）で 1 秒以内**を目安とする。ただし「1 秒」は結果であって守り方ではないので、**検査できる上限**を置く: **ホットパスのフックが起動してよい外部プロセスは `jq` だけで、呼び出しは最大 2 回**（`git` / `date` / `sed` / `find` を呼ばない。ルートの解決は読み込み行が fork なしで行い、パス照合・コマンド分割は純 bash で行う）。2 回の内訳は固定で、増やしてよい理由は無い（DDR i0009-46）:
  - **1 回目（`hook_read_input`）**: stdin と、**パスが stdin に依存しない副入力**（`scope-limits.json`。置き場が `HOOK_ROOT` 固定）をまとめて読む
  - **2 回目（`hook_read_state`。要るフックだけ）**: **パスが stdin の解析結果に依存する副入力**（`logs/review-state.json`・`logs/merge-state.json`・`logs/sessions/<session_id>/approvals.json`・`entry.json`）を読む。`approvals.json` / `entry.json` は `session_id` に依存し、`session_id` は stdin にしか無い（渡す環境変数は公式に無い）ので、この 2 つを 1 回目に混ぜることは**原理的にできない**。`review-state.json` / `merge-state.json` は共有ルート（§2）の下にあり置き場だけならフックの起動時に決まるが、**読むのは 2 本のフックだけ**なので、全フックが通る 1 回目には混ぜずに 2 回目でまとめて読む
  - したがって `block-chmod` / `block-direct-git` / `workflow-state-guard` は 1 回、`workflow-guard` / `workflow-entry` は 2 回
この上限は `test-lib.sh` の `make_counting_path` で呼び出し回数として検査する（HK-T05・HK-T13 と同じ方式）。ホットパス 5 本は毎ツール呼び出しで**同時に**起動するため、1 本あたりの fork がそのまま 5 倍になる。実測はフェーズ 4c
- 同じイベントに複数のフックがあるとき、1 つでも deny を返せば操作は拒否される。**フックは並列に走る**ので、複数が同時に deny を返し得る。そのときどの理由が AI に見えるかは**不定**として扱い、**各フックの拒否理由は単独で読んで成立する文面**にする（他のフックが先に判定した前提を書かない）。判定は互いに独立で、順序による絞り込み（安価な判定で高価な判定を省く）は成立しない — 各フックが単独で軽いことだけが性能を決める
- **拒否側の 5 登録は fail-closed のラッパーで登録する**: `command` を `bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/<NN-Event>/<name>.sh" || printf '%s' '{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"WFx09: フック <name> を実行できない（構文エラー・ファイル不在・異常終了）。.claude/hooks の状態を確認してユーザーに報告すること"}}'` の形にする（`x` はそのフックの百の位）。ラッパーの `||` はフック本体が起動できず何も出力しなかった場合（構文エラー・ファイル不在・`source` の失敗）の縮退で、本体が deny を出した経路は終了 0 で戻るためラッパー側の deny は重ならない（§3）。フック本体が構文エラーで起動できない・ファイルが無い・`trap` の登録前に落ちた場合も deny になる（HK-T09）。案内側はラッパー無し（失敗は通す）

## 2. 入力

- stdin に JSON。共通フィールド: `session_id`、`transcript_path`、`cwd`、`hook_event_name`、`permission_mode`（`default` / `plan` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions`）、`prompt_id`。**サブエージェント内のツール呼び出し（PreToolUse / PostToolUse）にも `agent_id` / `agent_type` が付き、`session_id` は親と同じ値になる**（宣言・承認の記憶がサブエージェントにもそのまま適用される根拠。§5）。`Bash` と `PowerShell` の `tool_input` は同じ形（`command` / `description` / `timeout` / `run_in_background`）で、フックは `tool_input.command` をそのまま読む。イベント別: `tool_name` / `tool_input`（PreToolUse・PostToolUse）、`tool_response`（PostToolUse）、`prompt`（UserPromptSubmit）、`source`（SessionStart）、`agent_id` / `agent_type`（SubagentStart。**`model` は来ない** — 公式は「Only `SessionStart` hooks can receive a `model` field」と明記する。DDR i0009-06）、`agent_transcript_path`（SubagentStop）
- **実行者（モデル）の比較は PostToolUse `Agent` の `tool_response.resolvedModel`（実際に使われたモデル）で行う**。起動前に読める `PreToolUse:Agent` の `tool_input.model` は**呼び出し側が明示したときだけ来る**（未指定なら `tool_input` は `subagent_type` / `prompt` / `description` の 3 つだけになり、サブエージェントは既定モデルで走る）。**値が無いことを「チケットの `executor` と一致した」と読んではならない** — 比較する値そのものが無い状態であり、宣言と違うモデルで走っていても検知できない
- **サブエージェントの起動は既定で background**。公式は「`"completed"` for foreground subagents, `"async_launched"` for background subagents. **As of v2.1.198, subagents run in the background by default**, so an omitted `run_in_background` also produces `"async_launched"`」「For background subagents, the tool returns when the task moves to the background … a background launch **returns immediately**」と定める。したがって **PostToolUse `Agent` は既定では「サブエージェントが走り終わった後」ではなく「起動した直後」に発火する**。この違いは 2 つの用途で逆に効く（DDR i0009-50・i0009-51）:
  - **起動の事実に関する通知**（WF801 = 実行者の不一致）: 起動直後に届くので**有利**。サブエージェントがほとんど動かないうちにメインエージェントが気づける
  - **作業後の検査**（WF811〜813）: 起動直後では**作業前の作業領域を見る**ことになり成立しない。`tool_response.status` で分岐し、`async_launched` では検査しない
- **ツールが失敗した呼び出し（exit≠0）では PostToolUse フックが 1 本も起動しない**。成功した呼び出しだけが PostToolUse に届くので、`tool_response` に終了コードのフィールドは無く、**「PostToolUse に届いた = 成功」**として扱ってよい（`post-push-*` の成功判定はこれに拠る。DDR i0009-07）。裏返しとして、**失敗した呼び出しの副作用（途中まで書けた `Write`・途中で落ちたスクリプト）は PostToolUse の検査に載らない** — 作業後の検査（`workflow-diff-check` の差分検知）は次に成功したツール呼び出しまで遅れる。これは検知の抜けではなく遅れであり、遅れて必ず拾われる
- **`tool_response` のフィールド名は camelCase**（`status` / `agentId` / `content` / `resolvedModel` / `totalTokens` / `usage` …）。イベントの共通入力フィールド側は snake_case（`agent_id` / `agent_transcript_path`）で、**同じものを指す名前が経路によって違う**（DDR i0009-53）
- **`Agent` の `tool_input` に `run_in_background` は公式の表に無い**（表にあるのは `prompt` / `description` / `subagent_type` / `model`）。省略時が background なので、**`tool_input.run_in_background` が明示的に `false` でなければ background として扱う**。起動後は `tool_response.status`（`async_launched` / `completed`）が確定した答えを持つので、PostToolUse `Agent` ではそちらを見る
- ツールの分類（`hook-common.sh` の関数 `tool_class`）:

| 分類 | ツール |
|---|---|
| 書き込み | `Edit` `Write` `MultiEdit` `NotebookEdit` |
| 実行 | `Bash` `PowerShell` |
| 読み取り | `Read` `Glob` `Grep` `LS` `WebFetch` `WebSearch` など上記以外 |
| プランモード | `EnterPlanMode` |
| 起動 | `Agent` `Workflow` |
| 宣言 | `Skill`（`tool_input.skill` の値は見ない。振り分けスキル名かどうかの照合は `workflow-entry` が `.claude/hooks/config/entry-skills.txt` で行う — DDR i0009-03・i0009-17） |

- 判定の材料はこの入力・作業領域（`wip/`）・`logs/`・設定ファイルに限る。フックはリモートに問い合わせない（DDR i0001-14）。CLI の有無・認証・ネットワークに左右されない
- **作業ツリーの三分**: フックは 3 つの根を区別する。1 つの名前で兼ねない（兼ねると、作業ツリーが 2 つ以上あるときに「スクリプトの置き場」「判定の対象」「issue に属する進行状態の置き場」が同じ値に潰れ、判定の対象を変えると進行状態まで一緒に動く）

  | 名前 | 変数 | 指すもの | そこに置かれるもの |
  |---|---|---|---|
  | 置き場 | `HOOK_ROOT` | 読み込み行が解決したリポジトリルート（本流のチェックアウト） | フック・共通ライブラリ・`hooks/config/` の実体、`settings.json` |
  | 判定対象の作業ツリー | `HOOK_WORKTREE` | その操作が行われた作業ツリー（下の解決順で決まる。`HOOK_ROOT` 自身のこともある） | `wip/`、判定記録 `logs/hooks/decisions.jsonl`、実行ログ `logs/sh/` |
  | 共有ルート | `HOOK_SHARED_ROOT` | 1 つの issue・1 つのブランチ・1 つの MR に属する進行状態を集める根 | `logs/mr.json` / `logs/review-state.json` / `logs/review-history.jsonl` / `logs/merge-state.json`、`logs/locks/`、`logs/usage/<branch>.json`、`logs/sessions/<session_id>/`（§5 が正） |

  - **`HOOK_SHARED_ROOT` の値は `HOOK_ROOT` と同一に固定する**。環境変数や設定ファイルからの上書きは受け付けない — 進行状態の置き場を外から動かせると、`workflow-state-guard` の保護対象そのものを外から外せることになり、拒否側の保護が環境変数 1 つで無効になる。名前を別に持つのは、別 clone を使う運用（`00_requirement/自己改善ワークフロー機構.md`「前提条件」）を扱うときに、値の解決だけを変えれば参照側（進行状態を読む全フックと提供コマンド）を触らずに済むようにするため
  - **同一リポジトリの作業ツリーの集合**（`hook_worktrees`）: `HOOK_ROOT` と、`<HOOK_ROOT>/.git/worktrees/<名前>/gitdir` に登録されているすべての作業ツリーのルート。読み取りは glob と組み込みの読み込みだけで行い、`git` を呼ばない（ホットパスの fork 上限。§1）。**登録が stale（指し先が実在しない・相互参照が片方向）でも集合には残す** — この集合は「保護してよい範囲」を広げるためだけに使い、`HOOK_WORKTREE` の決定（下の解決順）には使わないので、余分に含めても緩まない
- 作業ツリーの位置: `cwd` ではなく**読み込み行が解決したリポジトリルート**（`LOGGER_ROOT` / `HOOK_ROOT`）を基準にする（サブディレクトリからの実行に備える。解決順は `20-common-step-shell-script` 仕様「読み込み行」で、`BASH_SOURCE` からの上向き探索 → `CLAUDE_PROJECT_DIR` → `git rev-parse` の順）。**フック本体から `git rev-parse --show-toplevel` を呼ばない** — Git Bash で約 95 ms/回かかり、ホットパスの fork 上限（§1）に反する。`git rev-parse` は読み込み行の最終手段としてだけ使う（DDR i0009-22）
- **worktree に入ったときの基準**（DDR i0009-55）: 公式は「Claude が worktree に入ると **`${CLAUDE_PROJECT_DIR}` はセッション開始時のプロジェクトルートに留まる**（本流のスクリプトが動く）。**`cwd` が Claude に追随する**（入力 JSON の `cwd` が worktree のルートになる）」と定める。したがって `HOOK_ROOT` は**本流のチェックアウト**を指し続け、そのままでは `workflow-guard` が本流の空の `wip/10_tickets/10_doing/` を見て「0 枚 → 許可」となり、**機構が worktree の中で丸ごと無効になる**。これを避けるため、フックは次の順で作業ツリーを決める:
  1. 入力 JSON の `cwd` が `HOOK_ROOT` と異なり、かつ `cwd` から上向きに探して `.claude` を持つディレクトリが見つかり、**そのディレクトリが `HOOK_ROOT` の worktree であることを確かめられた**なら、そのディレクトリを作業ツリーとする（上向き探索は純 bash の `[ -d ]` の繰り返しで、`git` を呼ばない = fork 上限に影響しない）
  2. そうでなければ `HOOK_ROOT`
  - **worktree であることの確認は省けない**。`cd` するだけで `cwd` は動き、リポジトリの中には参考実装など `.claude` と空の `wip/10_tickets/10_doing/` を持つディレクトリが実在し得る。確認せずに上向き探索の結果を採ると、**そこへ `cd` するだけで作業中チケットが 0 枚に見え、`workflow-guard` が全面バイパスされる**
  - 確認は**相互参照が成立すること**を要求する（fork ゼロ・O(1)）: 候補の `.git` ファイルの `gitdir:` が `<HOOK_ROOT>/.git/worktrees/<名前>` を指し、**かつ**その `<名前>/gitdir` が候補の `.git` を指し返すこと。片方向（登録側から探すだけ）では、worktree を作って消した後の stale な登録が残っているだけで、そのパスに後から置いたディレクトリが worktree として信用される。パスの比較の前に `.` / `..` を畳み、大文字小文字とパス区切り（`\` / `/`）の差を吸収する
  - 本流のチェックアウトの配下にある worktree（`git worktree add ./sub-wt`）も、相互参照が成立するなら正当な作業ツリーとして扱う（配下を一律に弾くと、その中で機構が本流の `wip/` / `logs/` を見ることになり、この節が防ごうとしている状態そのものになる）
  - **スクリプトの置き場（`.claude/hooks/lib/` の `source` 元）は常に `HOOK_ROOT`** で、作業ツリーとは別に扱う。worktree 側に `.claude/hooks/` の実体が無い場合でも本流の実体で動く
  - **例外: 状態を自分で解決する提供コマンドは、作業ツリー側の実体を呼ぶ**。フックが提供コマンドを起動して現在地・チケットの状態を得る場合（`session-start` の `boundary.sh status --offline`）は `$HOOK_WORKTREE/.claude/skills/<スキル>/scripts/<コマンド>.sh` を使う。提供コマンドは自分の読み込み行（`LOGGER_ROOT`）1 本で置き場と作業ツリーを兼ねるので、`HOOK_ROOT` 側の実体を呼ぶと**本流の作業領域を見て答える**。知りたいのは操作が行われた作業ツリーの現在地なので、実体もそちら側から取る。作業ツリー側に実体が無いときは何も出さずに通し、不在を `skip` の理由に残す（黙って本流の実体にフォールバックしない — どちらの作業領域を見た答えかが分からなくなる）
  - `wip/` と、判定記録・実行ログ（`logs/hooks/decisions.jsonl` / `logs/sh/`）は**作業ツリー側**に置く。issue に属する進行状態・ロック・集計は**共有ルート**に置く（§5 が置き場の正）
  - 要件は並行作業の手段として worktree を挙げている（`00_requirement/自己改善ワークフロー機構.md`「前提条件」）ので、この経路は例外ではなく想定内である
- **作業ツリーをまたぐパスの畳み込み**（`hook_rel_path`）: フックが受け取るパスは、`HOOK_WORKTREE` の配下とは限らない（AI は他の作業ツリーや共有ルートの絶対パスを直接渡せる）。畳み込みは次の順で行い、結果として「どのツリーの、ルート相対のどのパスか」の対を返す。
  1. `HOOK_WORKTREE` の配下 → そのツリーのルート相対パス
  2. 共有ルートの配下 → 共有ルートのルート相対パス
  3. 同一リポジトリの作業ツリーの集合（上の `hook_worktrees`）のいずれかの配下 → **そのツリー**のルート相対パス
  4. どれの配下でもない → 畳めない。**同一リポジトリの外**であることが確定するので、リポジトリ内の保護対象とは無関係として扱う
  - 比較の前に `.` / `..` を畳み、大文字小文字とパス区切り（`\` / `/`）の差を吸収する（`__hc_winpath` と同じ正規化）
  - **1〜3 のどれかに畳めたパスは、そのツリーの中のパスとして各フックの判定に掛ける**。「自分の作業ツリーの外だから見ない」としない — 進行状態と完了済みチケットの保護は、どの作業ツリーから書かれても同じように効かなければならない
  - **正規化そのものに失敗した / 作業ツリーの集合を読めなかったときは、4（無関係）に倒さず「判定できない」を返す**。呼び手のフックは判定できないときの規約（下）に従う
- **判定できないときの倒し方**（DDR i0010-09）: 作業ツリーの解決・パスの畳み込みに失敗したとき、**拒否できるフック**（`workflow-guard` / `workflow-state-guard`）は許可側に倒さず deny（`WF209` / `WF309`）に倒す。**案内側のフック**（`workflow-diff-check` / `subagent-start-check`）は deny を出せないので、黙って通す代わりに「判定できなかったこと」を additionalContext で伝える側に倒す。ヘッドレス（§10）でも同じで、確認に置き換えて先送りしない

## 3. 制御方式

| 目的 | イベント | 出力 |
|---|---|---|
| 拒否 | PreToolUse | stdout に `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<識別子>: <理由と対処>"}}`、終了 0 |
| 確認 | PreToolUse | 同上で `permissionDecision: "ask"`（理由に確認の根拠とチケットを含める）。ヘッドレス（§10）では `deny` に置き換える |
| 許可 | PreToolUse | 何も出力せず終了 0 |
| プロンプトの補足 | UserPromptSubmit | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}` |
| 操作後の通知 | PostToolUse | `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"<識別子>: ..."}}`（AI のコンテキストに入る。操作は取り消せない） |
| セッション開始の注入 | SessionStart | stdout のテキスト（そのままコンテキストに入る） |
| サブエージェントへの注入 | SubagentStart | `{"hookSpecificOutput":{"hookEventName":"SubagentStart","additionalContext":"..."}}` |
| メインへの通知（サブエージェントの起動直後・終了） | PostToolUse（`Agent`） | additionalContext。SubagentStop 側は記録だけ行う（SubagentStop の出力はサブエージェント側にしか届かないため） |

- **`systemMessage`（トップレベルの `{"systemMessage":"..."}`）を人間へ届く経路として使わない**。公式は「Warning message shown to the user」と定めるが、**対話 UI には表示されない**（SDK のメッセージ列には載る）。AI にも届かないので、対話セッションではどちらにも届かない。人間に伝えたい事柄は、AI が読む `additionalContext` に載せて AI から報告させるか、拒否・確認の理由文に載せる
- **`additionalContext` は「次のモデル要求」で読まれる**。公式は入る位置を「PreToolUse … next to the tool result」「Claude reads the reminder on the next model request」と定めるので、PreToolUse に登録しても AI が読むのは**そのツールの結果と同時**であり、ツールの実行前に AI へ割り込むことはできない（DDR i0009-26）
- **識別子の付き方が `hook_notify` と `hook_inject` で違う**。`hook_notify` は本文の先頭に `<識別子>: ` を自分で付けて出力する。`hook_inject` は**付けない**（`decisions.jsonl` の `id` には記録されるが、出力本文には現れない）。したがって注入（`inject`）で識別子を AI に見せたいフックは、**本文の先頭に自分で識別子を置く**（置かないと `additionalContext` に識別子の文字列が 1 つも現れず、AI も人間も番号で引けない）
- 拒否・確認・通知の文面は日本語で、先頭に識別子（§6）、続けて「何が起きたか」「対処」。ファイルの中身・差分の内容・環境変数の値・トークン・個人情報を含めない。コマンドの引用は先頭 80 文字まで
- 案内側のフック（session-start / diff-check / subagent-* / post-push-*）は依存が壊れたら**何も出さずに通す**。拒否側のフック（entry / guard / state-guard / block-*）は判定できなければ**拒否側に倒し**、理由に「機構の不調」を含める（`WFx09` 系の識別子）。無関係と確定できる操作は止めない
- **打ち切り（timeout）は fail-open**: `command` 型のフックが `timeout` に達すると Claude Code はそれを打ち切り、**出力を破棄して判定なしとして扱う**。`PreToolUse` では「A timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call.」と明記されており、ツール呼び出しは通常のパーミッションフローへ進む。**§1 のラッパーの `||` も §3 の `trap ERR` も、打ち切られた場合には効かない**（プロセスごと終了させられ、出力が捨てられるため）。これはフェイルクローズドの原則の唯一の穴で、塞ぐ手段は「フックを速く保つ」ことだけ（§1 のホットパス 1 秒の目安）。既定の 600 秒に達するフックは実装の誤り（無限ループ・応答しない外部プロセス）とみなす。DDR i0009-11
- フック自身の実行エラー（bash の異常終了）は Claude Code に非ブロッキングエラーとして扱われ操作が通ってしまうため、拒否側のフックは `trap ERR` で捕捉して deny を出し、**終了コード 0 で終了する**（非 0 で終わると §1 のラッパーが 2 つ目の deny を連結し、JSON として読めなくなる）。判定結果の伝達は常に stdout の JSON で、終了コードは使わない（`20-common-step-shell-script` 仕様「終了コード」）。`trap` が効かない経路（構文エラー・ファイル不在）は §1 の登録ラッパーが deny に倒す
- **機密情報のマスク**（全フック共通。`hook-common.sh` の `redact`）: 記録・拒否理由・通知に含めるコマンド文字列・パス・本文は、出力前に `redact` を通す。マスク対象: `ghp_` / `gho_` / `github_pat_` / `glpat-` で始まる語、`Bearer <語>`、`token=` / `password=` / `passwd=` / `secret=` と、`api` `access` `private` `auth` `client` `secret_access` に `_key=` / `-key=` / `key=` が続くキー（大文字小文字を問わない。値に `/` を含む秘密 — AWS のシークレットアクセスキー等 — はここで拾う）に続く語、`AKIA` で始まる 20 文字、40 文字以上の 16 進 / base64 様の語（`/` を含む語はパスと区別できないため対象外。ハイフンを 2 個以上含み大文字を含まない語（ブランチ名・チケット名）と、英小文字と `_` だけの語（識別子）は秘密と見なさず残す）。置換は `***`。各パターンは置換結果 `***` に再一致しない形にする（再一致すると置換が止まらない）。HK-T06 はマスク後の記録を検査する。`redact` は**最後の砦**であり、一次防御は「そもそも値を出さない」こと（環境変数の値・トークン・ファイルの中身を記録・理由・通知に載せない）。接頭辞決め打ちのパターンは当たらない値をマスクできず「マスクした」という誤った安心を与えるため、パターンが当たることを HK-T10 で固定し、新しい種類の秘密情報が現れたらパターンを足す

## 4. 緊急停止

- 機構全体: `WORKFLOW_ENFORCE=0`。フック単位: `WORKFLOW_<NAME>_ENFORCE=0`（`<NAME>` はフック名を大文字スネークにしたもの。例: `WORKFLOW_ENTRY_ENFORCE=0`、`WORKFLOW_GUARD_ENFORCE=0`、`BLOCK_DIRECT_GIT` → `WORKFLOW_BLOCK_DIRECT_GIT_ENFORCE=0`）
- 環境変数はセッション開始時に読み込まれるため同じセッション内では変えられない。AI は設定できず、ユーザーに「どちらを止めるか」と新しいセッションでの実行を伝える（`CLAUDE.md`「作業の振り分け」）
- 停止中のフックは判定・注入を行わず、`decisions.jsonl` に `{"decision":"disabled"}` を 1 行残す（session-start は停止中である旨を注入内容の先頭 1 行に出す）
- push 前チェックを飛ばす目的での停止は不可（`wip/push-check-skip.md` が正規の手段 — commit-push 仕様）

## 5. 記録と状態（`logs/`）

`logs/` はリポジトリ直下、`.gitignore` 済み、片付けの対象外（DDR i0001-28）。**どの根の下の `logs/` かは記録ごとに決まる**（§2 の三分。`共有` = `HOOK_SHARED_ROOT` / `ツリー` = `HOOK_WORKTREE`）。

| パス | 根 | 内容 | 書く側 | 寿命 |
|---|---|---|---|---|
| `logs/sh/<name>.log` | ツリー | 実行ログ（共通 logger。`LOGGER_NAME=hook-<name>`） | 全フック | 手動削除まで |
| `logs/hooks/decisions.jsonl` | ツリー | 判定の記録 1 行 1 件: `{"ts","session_id","agent_id","cwd","hook","event","decision":"allow\|ask\|deny\|notify\|inject\|disabled\|skip","id":"WFxxx","tool","target","ticket","note"}` | 全フック | 振り返りの材料。全体まとめの後も残す |
| `logs/sessions/<session_id>/entry.json` | 共有 | 振り分けの宣言状態: `{"prompt_seq","declared_skill","declared_at","continuation":"tickets\|review\|merge_prep\|null"}` | workflow-entry | セッション限り |
| `logs/sessions/<session_id>/approvals.json` | 共有 | 未記載パスの承認の記憶: `[{"scope":"<親ディレクトリ or ファイル>","ticket","at"}]` | workflow-diff-check（書く）/ workflow-guard（読む） | セッション限り |
| `logs/usage/<branch>.json` | 共有 | 使用量の蓄積（ブランチ単位。内側にセッション別・サブエージェント別の内訳と `posted` / `since_sha` / `last_push_sha` / `push_count`） | post-push-usage-report（Stop / SubagentStop / push 時）、`boundary.sh`（`posted`） | 投稿成功で `since_sha` を進める（ファイルは残す）。`last_push_sha` は push 検知の起点で、`push-state.json` とは独立（DDR i0009-24） |
| `logs/usage/report-<branch>-<count>.md` | 共有 | 対応工数レポート本文 | post-push-usage-report | 手動削除まで |
| `logs/locks/<name>.lock` | 共有 | 読んで書き換える記録の排他（`hc_lock` / `hc_unlock`） | 全フック | 処理の終わりに解放。60 秒より古いものは陳腐化として強制解放 |
| `logs/push-state.json` | 共有 | ブランチごとの前回 push 時点: `{"<branch>":{"sha","at","count"}}`。**`post-push-compact-prompt` 専用**で他のフックは読まない | post-push-compact-prompt | 手動削除まで |
| `logs/mr.json` / `logs/review-state.json` / `logs/review-history.jsonl` / `logs/merge-state.json` | 共有 | 提供コマンドの進行状態（`00-workflow-issue-mr-driven` / `10-task-overall-summary` 仕様） | boundary.sh / finalize.sh | フックは読むだけ |

- **置き場の分け方の根拠**（DDR i0050-02）: 進行状態・ロック・集計は「issue と MR に属する」情報で、issue も MR もブランチも 1 つしか無いので、作業ツリーごとに分ける意味が無い。分けると、worktree の中では宣言が無い扱い（WF102）になり、承認を取り直すことになり、MR / レビュー / マージの状態が `missing` に落ちる。ロックと集計はブランチ単位の資源なので、分けると排他も集計も成立しない。逆に**判定記録と実行ログは「どの作業ツリーで何が起きたか」の記録**なので作業ツリー側に残し、合流後も追えるように `cwd`（判定時の作業ツリー）と `agent_id`（メインなら空）を記録に足す
- **並列実施を行う場合**、作業ツリーを新しく作った側は `logs/` を空から用意する必要が無い（進行状態・承認・集計・ロックは共有ルートの同じファイルを指すため）。作業ツリー側に用意されるのは `logs/hooks/` と `logs/sh/` の 2 つだけで、いずれも追記専用なので不在でも作られる。**並列実施を行わない場合も**この置き場は同じで、作業ツリーが 1 つなら三分はすべて同じディレクトリに解決される

- **`logs/mr.json` の MR 番号のキーは `.mr`**（正の形は `{"host","issue","mr","url"}` — `00-workflow-issue-mr-driven` 仕様）。`.number` / `.iid` は別実装が書いた記録を読むための受け皿にすぎず、フックは `.mr` → `.number` → `.iid` の順に見て最初に見つかった値を使う。新しく書く側は `.mr` だけを書く

- **並行書き込みの規則**（フックは並列に走る — §1。PostToolUse は「Claude が並列にツールを呼ぶと同時に発火する」ことが公式に明記されている。DDR i0009-23）:
  - **追記だけのファイル（`*.jsonl` / `*.log`）**: 1 行を `>>` で追記する。**1 行は 4 KB（`PIPE_BUF`）未満に保つ**（超えると追記が割れて JSONL が壊れる）。`decisions.jsonl` の `note` と `target` は合わせて 1 KB を超えないよう切り詰め、切り詰めた旨を末尾に `…` で示す
  - **読んで書き換えるファイル（`approvals.json` / `push-state.json` / `usage/<branch>.json`）**: 同じディレクトリ内の一時ファイル（`<name>.tmp.<pid>`）へ書いてから `mv` で置き換える（同一ファイルシステム内の rename は原子的）。読み手が書きかけを掴むことがなくなる
  - **read-modify-write が競合し得るもの**（`usage/<branch>.json` — 並行するサブエージェントの SubagentStop が同時に加算し得る）は、`mkdir <name>.lock` によるロックで直列化する（`mkdir` は存在すれば失敗するので原子的。取得できなければ**最大 2 秒待って諦め、加算せずに実行ログ（`logs/sh/hook-<name>.log`）へ 1 行残して終了 0**。案内側なので通す）。**諦めた回数を JSON の側に書かない** — その書き込み自体が同じ read-modify-write でロックを要り、循環するため（`parse_errors` の置き場は実行ログ 1 か所。DDR i0009-49）。ロックディレクトリは処理の最後に `rmdir` し、`trap` でも消す。**ただし打ち切り（timeout）では `trap` も効かない**（§3 の fail-open）ので、`hc_lock` は取得を試みる前に**ロックディレクトリの作成時刻が 60 秒より古ければ陳腐化とみなして `rmdir` してから取り直す**（強制解放したことは実行ログに 1 行残す）。これが無いと、重い `post-push-usage-report` が打ち切られたときにロックが残り続け、以後の集計が恒久的に止まる（DDR i0009-60）
  - `logs/sessions/<session_id>/` はセッション単位なので競合しないが、同一セッション内の並列ツール呼び出しでは `approvals.json` が競合し得るため上の規則に従う
- セッション状態は `session_id` で分離し、並行する別セッションと混ざらない（共有ルートに置くので、作業ツリーが違っても同じ `session_id` なら同じ記憶を読む）。サブエージェント内のツール呼び出しは親と同じ `session_id` を持つため（§2）、宣言・承認の記憶はそのまま適用される
- `logs/sessions/` の 7 日より古いディレクトリは session-start が非侵襲的に削除する（失敗しても通す）
- `logs/` への書き込みは `workflow-guard` の許可範囲の判定対象外（機構自身の記録）。ただし進行状態ファイルへの AI の直接書き込みは `workflow-state-guard` が拒否する

## 7. コマンド位置の判定（`cmdpos.sh`）

入力: コマンド文字列（Bash / PowerShell）。出力: 実行位置にあるセグメントの列。各セグメント = `exe`（実行体の basename）/ `args[]` / `redirects[]`（`>` `>>` `2>` `&>` `<>` の宛先パス）/ `write_targets[]`（`cp` `mv` `tee` `touch` `mkdir` `rm` `truncate` `sed -i` `install` `ln` の書き込み先引数）/ `opaque`（判定不能）。呼び出し側はこの出力だけを見て判定し、コマンド文字列を再パースしない（規則の複製禁止）。純 bash（外部プロセス無し）。

チケットの frontmatter（§9）の読み取りは `.claude/skills/20-common-step-shell-script/scripts/frontmatter.sh`（`source` 専用・純 bash。入れ子キー `allow.write` とインラインマップ `human_review` に対応。仕様は `20-common-step-shell-script`）を `hooks/lib` から `source` して行い、フック側に frontmatter の解釈を重複して持たない（依存の向きは logger と同じ。DDR i0006-01）。

1. 前処理（正規化）: ヒアドキュメント本文（`<<TAG`〜`TAG`、`<<'TAG'`、`<<-`）、`#` コメント（行頭または空白の後）、シングルクォート文字列を除去。ダブルクォート文字列は本文を除去するが、その中の `$(...)` と `` ` ` `` は展開して実行位置として扱う
   - **算術展開 `$(( ))` はコマンド置換ではない**。ダブルクォートの中でも外でも同じ規則で、`$((` から対応する `))` までを丸ごと読み飛ばして 1 語の `_` に潰す（**段を割らない**）。ダブルクォートの中だけこの検査を欠くと、`echo "$((n+1))"` が `(` `(` `n+1` `)` `)` に割れて `n+1` が実行体の段になり、読み取りだけのコマンドが分類外（WF204）で落ちる
   - **コマンド置換 `$( )` / `` ` ` `` と、プロセス置換 `<( )` / `>( )` は、中身を実行位置として解析したうえで、外側の 1 語としては `_` に潰す**。**閉じ括弧の後ろに続く語を新しい段の実行体にしない** — `sed -n "$(grep -n X f | cut -d: -f1),+45p" path/to/file.sh` の `file.sh` や、`comm -12 <(sort -u a.txt) b.txt` の `b.txt` は、いずれも**引数**であって実行体ではない。段の区切りは `(` `)` という文字そのものではなく、置換の**開始と終了の対応**で決める
   - 潰れた語が**実行体の位置**にあるときは従来どおり `_` として扱う（`$(which git) push` は何が走るか分からないので呼び手が拒否側に倒す）。**引数の位置**にあるときは引数の 1 語として残し、その段の実行体を書き換えない。呼び出し側から見えるのは、置換の中の段（実行位置）と、置換を含む段の 2 つだけになる
   - **除去は内部プレースホルダへの置き換えで行い、段を組み立てるときに `_` へ戻す**。呼び出し側から見えるトークンは常に `_` で、内部プレースホルダは出力に現れない。入力に生のプレースホルダが混じっていた場合は先に `_` へ潰す（潰さないと、段がデータだけに見えて実行位置の判定から外れる）
   - 内部プレースホルダの割り当て（3 つとも制御文字。用途を重ねない）:

     | バイト | 名前 | 用途 |
     |---|---|---|
     | `\x01` | 複製リダイレクト | `>&` `<&`（ファイル記述子の複製）を書き込みリダイレクトと取り違えないための保護 |
     | `\x02` | `&>` リダイレクト | `&>`（stdout+stderr）を「バックグラウンドの `&`」による分割から守るための保護 |
     | `\x03` | データ | ヒアドキュメント本文・コメントの内容。段の組み立て時に `_` へ戻し、その段が**データだけか**を `CP_DATA[i]` に記録する |

   - **`#` の直前が改行のときも語の切れ目とみなす**（行頭のコメント）。切れ目に改行を含めないと、`# コメント` が実行体 `#` の段になり、コメントの中の語が引数として残る（bash はコメント行を丸ごと無視する）
2. 分割: `;` `&&` `||` `|` `|&` 改行 `(` `)` `{` `}` `&`（バックグラウンド）で分割。ただし**コマンド置換・算術展開・プロセス置換に属する括弧は 1 で処理済み**なので、ここでは区切りにしない（1 を通った後の文字列には残っていない）
3. 各セグメントの先頭から透過ラッパーを剥がす: `sudo` `doas` `env`（`VAR=val` の並び含む）`command` `builtin` `exec` `time` `nice` `ionice` `nohup` `setsid` `stdbuf` `timeout` `if` `then` `else` `elif` `while` `until` `do` `!`（この一覧が正で、実装の語彙表と同じ集合。HK-T05 は全要素を踏む）
4. 実行体を正規化: ディレクトリ部と `.exe` を除いた basename（`/usr/bin/git`、`./git`、`git.exe` → `git`）
5. 不透明な実行系が実行位置にあれば、そのセグメントを `opaque` とする。2 系統ある: (a) 無条件に opaque — `eval` `xargs` `ssh` `watch` `flock` `parallel` `invoke-expression` `iex`（後の 2 つは PowerShell の eval 相当。入れないと `Invoke-Expression "git commit"` が素通りする）、および `find` の引数に `-exec` `-execdir` `-ok` `-okdir` があるもの / (b) コード文字列を渡すオプション（`-c` `-e` `-E` `--command` `-command` `-encodedcommand` `-ec`）を伴うときだけ opaque — `bash` `sh` `zsh` `ksh` `dash` `busybox` `python` `python3` `perl` `ruby` `node` `deno` `pwsh` `powershell`（`pwsh script.ps1` のようにスクリプトファイルを渡す形は opaque ではない）。この 2 つの一覧が正で、実装の語彙表と同じ集合。呼び出し側は「opaque かつ対象語（`commit` / `push` / `chmod` / 状態ファイル名等）を含む」なら拒否側に倒す
6. PowerShell: `;` と改行で分割、呼び出し演算子 `&` と `.` を剥がす、ヒアストリング `@'`〜`'@` / `@"`〜`"@` を除去、バッククォート行継続を結合。バックスラッシュ区切りのパスは basename 化で吸収できない形（`.\git.exe` は吸収できる）があり得るため、実行位置のトークンに語としての `git`（`git` / `git.exe` / パス付き。`CP_GITLIKE`）があり、かつ第 1 サブコマンドが対象語（呼び出し側が渡す。block-direct-git なら `commit` / `push`）であるか、サブコマンドが特定できないときに限り拒否側に倒す（`git status` / `diff` / `add` / `fetch` は通す）
7. 縮退: bash 4.3 未満、または 1 コマンドが 4096 文字を超えるときは判定を行わず `degraded` を返し、呼び出し側は部分一致（対象語の有無）で判定して「縮退した判定」をメッセージに含める（`ai-command-style` ルールの言い換えを案内）
8. **提供コマンドの識別**: 実行体が `bash`（または `sh`）で第 1 引数が**コマンド文字列上でリポジトリルート相対の表記（`.claude/` 始まり）**で `.claude/skills/*/scripts/*.sh` または `.claude/hooks/**/*.sh` に一致するセグメントだけが「提供コマンド」。`cwd` による解決は行わず、絶対パス・`./` 付き・他の相対指定・basename だけの指定（`bash commit.sh`、`/tmp/commit.sh`、`bash ./.claude/skills/x/scripts/y.sh`）は提供コマンドとして扱わない。第 1 引数がクォート・変数展開・コマンド置換を含みパスとして確定できないセグメントも同様に通常の判定にかける（識別漏れを許可側に倒さない）。提供コマンドの起動は常にルート相対表記で行う（各スキルの手順が正）。フックが見るのはツールへ渡された文字列だけなので、提供コマンド内部の `git` 実行や `logs/` 書き込みはそもそも判定の対象に現れない（DDR i0004-05）。提供コマンドの引数に現れるパス（`commit.sh -m .. <files>`）は `workflow-guard` が書き込みと同じ判定を適用する
9. **出力の形**: 結果は呼び出し元のシェルに bash の配列として置く（純 bash・fork なしで判定できる形）。`CP_COUNT`（セグメント数）/ `CP_DEGRADED`（縮退なら 1）/ `CP_EXE[i]`（実行体。クォートやコード文字列で確定できないときは `_`）/ `CP_ARGS[i]`（引数。区切りバイトは RS（0x1E）。`cmdpos_args <i>` が `REPLY_ARGS` 配列に展開するので、呼び出し側は自分で分割しない）/ `CP_SUBCMD[i]`（第 1 サブコマンド。git はグローバルオプションを飛ばした後の語。クォートで割った語（`git 'commit'`）は `_` になり、呼び出し側は「特定できない」として扱う。**語が 1 つも無い段**（`git` 単独、PowerShell のヒアストリングのようにデータごと潰れた段）は**空**になり、`_` とは区別する — 空は実行しても何も起きないので通し、`_` は何が走るか分からないので拒否側に倒す）/ `CP_REDIRECTS[i]` / `CP_WRITE_TARGETS[i]`（同じ 0x1E 区切り）/ `CP_OPAQUE[i]` / **`CP_DATA[i]`**（1 = その段はデータだけ（ヒアドキュメント本文・コメント行）で実行位置ではない。bash はどちらも決して実行しないので、呼び出し側は実行体の判定から外す。正規化は「潰れたクォート」もデータも同じ `_` にするため、両者を区別できるのはこの印だけで、外すと「本文に禁止語を書いただけ」で拒否側に倒れる）/ `CP_PROVIDED[i]`（提供コマンドならそのルート相対パス）/ `CP_GITLIKE[i]`（実行体が `_` で、コマンド文字列に語としての `git`（`git` / `git.exe` / パス付き）があるとき 1。`digit` / `legit` / `github` には立たない — 6 の PowerShell 判定の材料）/ `CP_LOWER`（小文字化した全文）。補助関数: `cmdpos_has_git_subcommand <sub>`（実行位置に `git <sub>` があるか）、`cmdpos_has_provided <path>`（提供コマンドがあるか）、**`cmdpos_operands <i>`**（`CP_ARGS[i]` から `-` で始まる語と `--` 以降の区切りを除いた**位置引数**を `REPLY_OPERANDS` 配列に展開する。`rm -rf a b` → `a b`、`mv -v src dst` → `src dst`。削除対象か宛先かの解釈は呼び手が行う — `workflow-state-guard` は `rm` / `git rm` なら全部を「元」、`mv` なら最後を宛先・それ以外を元として扱う。DDR i0009-39）

## 8. 許可範囲の判定（`scope.sh`）と上限設定

- **`web`（外部への問い合わせ）はコマンド側だけを強制する**（DDR i0009-12・i0009-41）。
  - **`Bash` の取得コマンド（`curl` / `wget`）は `web` に分類する**。`allow.ops` と `types[t].ops` の両方に `web` があれば許可、無ければ **deny WF204**。宣言が実際に効く唯一の経路がここで、取得の事実は `decisions.jsonl` に残る
  - **判定は次の順で行う**（順序を変えると穴が開く。DDR i0009-56）:
    1. **送信側の形は `web` として通さない**。`curl` の `-T` / `--upload-file` / `-d` / `--data` / `--data-raw` / `--data-binary` / `--data-urlencode` / `-F` / `--form` / `-X`（`--request`）の値が `GET` / `HEAD` 以外、`wget` の `--post-file` / `--post-data` / `--body-file` / `--body-data` / `--method`（`GET` / `HEAD` 以外）のいずれかがあれば、**宣言の有無によらず deny WF206**（リモートへの書き込み）。これらはローカルのファイル内容を外部へ送る、または API を直接書き換える操作で、`remote-write:<種別>` が統制している対象そのものである。改定前は `curl` が既定拒否だったため閉じていた経路で、`web` を通す決定はこれを開けてはならない
    2. **出力先を持つ形は書き込みとして扱う**（`curl` の `-o` / `--output` / `-O` / `--remote-name` / `--output-dir`、`wget` の既定動作と `-O <file>`）。出力先パスに §8 の判定を当て、`wip/tmp/**` / `logs/**` 以外なら **deny WF205**。出力先を持たない `curl <url>`（既定は標準出力）と `wget -O -` は書き込みに当たらない
    3. 残りが `web` として、宣言と上限の両方にあれば許可
  - **出力先の取り出し方**（DDR i0009-57）: `cmdpos_operands`（`-` 始まりを落とす）**では取れない** — オプション本体が落ち、残った語のうちどれが URL でどれが出力先かを区別できないため。`cmdpos_args` で得た引数列を**先頭から走査**し、上記の出力先オプションを見つけたら**その次の語**を出力先とする（`--output=<path>` の等号形は前方一致で拾う）。`-O` / `--remote-name` と `wget` の既定は出力先の語を取らず、**URL の basename を作業ツリー基準のカレント**に作るものとして扱う。`://` を含む語は URL とみなし、出力先として扱わない
  - **`WebFetch` / `WebSearch` は強制しない**。matcher に書けば PreToolUse で捕まえられる（公式の matcher は tool 名の完全一致または正規表現）が、登録しない。理由は 2 つ: (1) `scope_classify` はコマンド列を前提にしており、`tool_name` だけの入力に同じ分類を当てられない、(2) これらは副作用が読み取りに閉じ、機構が守る対象（作業領域外への書き込み・コミット / push・進行状態）に当たらない。この 1 点は §13 の意図的な緩和として残る
- 上限設定: `.claude/hooks/config/scope-limits.json`（ユーザー管理。`workflow-guard` の仕様が形式の正）。構造:

  - 裸の形（`npm test`）の効き方: コマンドの分類はセグメント文字列の**前方一致だけ**を見て、実行時の作業ディレクトリを見ない。したがって裸の形はリポジトリのどのディレクトリで実行される `npm test` にも当たる。アプリルートで作業するときの手数を優先してこれを許容する（アプリルート以外に `package.json` を置かない前提）。許容できない事情が出たら、裸の形を落として `--prefix` 形だけにし、README のビルド手順もそちらへ揃える
  - `.claude/hooks/config/task-types.tsv` は 6 列（番号・type・タスク名・担当・スキル名・対の相手）のタブ区切りで、1 行目は `#` 始まりのヘッダ行（読み手はコメントとして飛ばす）

- **`scope.sh` の読み込み関数は JSON のファイルを開かない**（DDR i0009-48）。`scope_load` と `scope_load_approvals` は、`hook-common.sh` の `hook_read_input` / `hook_read_state` が既に取り出した `HC_*` を読んで `SC_*` に詰め替えるだけで、パスを引数に取らない。理由は、JSON を読むのは `jq` 1 か所に限る（ホットパスの上限を関数の側から破れないようにする）ためと、`scope.sh` を `source` する 4 本のフックが「自分が何回 `jq` を呼ぶか」を数えられるようにするため。副入力が読めなかった（不在・破損）ことは `HC_<名前>_STATE` から分かり、`SC_ERROR` と**戻り値 1** に写す（不在と破損を戻り値では区別せず、区別が要る呼び手は `HC_<名前>_STATE` を直接見る）
- 例外は **`scope_load_ticket <ticket.md>`** で、これはパスを引数に取る。チケットの frontmatter は `frontmatter.sh`（純 bash）が読み、`jq` を使わないため上限に関わらない

  - **判定結果は戻り値ではなく `SC_DECISION` / `SC_ID` / `SC_STAGE` で返す**（判定関数の戻り値は常に 0）。戻り値を判定結果に使うと、下の 3 状態の規約と衝突するため
  - **戻り値 0 / 1 / 2 の規約は「読み込み」の 3 関数だけに適用する**: 0 = 読めた / 1 = **読めなかった**（チケット・設定の記載不正、または副入力の不在・破損。呼び手は `WF211` / `WF210`）/ 2 = `frontmatter.sh` を読み込めていない（機構の破損。呼び手は `WFx09`）。**戻り値 2 を返すのは `scope_load_ticket` だけ** — `frontmatter.sh` を `source` するのがこの関数だけで、他の 2 つは `jq` が読んだ結果を詰め替えるにすぎないため。**述語関数（`scope_match` / `scope_op_declared`）は真偽を返す**ので、この規約の対象外（DDR i0009-34）
  - `scope.sh` 自身は読み込み行を `nop` で使い何も出力しない（§12 T8・`20-common-step-shell-script` 仕様「読み込み行」）。`fm_*` の戻り値 2 は `scope_load_ticket` の戻り値 2 としてそのまま呼び手へ返す（1 と 2 を潰さない）
- 判定順（書き込み対象パス `p`、作業中チケットの type `t`、宣言 `d`）: (1) `p` が `logs/**`（state_files を除く）→ 対象外（機構自身の記録。state_files は `workflow-state-guard` が同時に deny を返すため通常はここに来ない（フックは並列に走るので「先に」は成立しない。§1） — 来た場合も (7) で ask になり二重判定にはならない） / (2) `common.protected` に一致し、かつ `types[t].allow` に明示されていない → **deny WF201** / (3) `types[t].deny` に一致 → **deny WF201** / (4) `common.confirm` または `types[t].confirm` に一致 → **ask WF203**（毎回） / (5) **許可範囲** `A` に一致 → **allow**。`A` = `common.allow` ∪（`d.write` が指定されていれば `d.write ∩ types[t].allow`、未指定なら `types[t].allow`）。宣言は上限の内側で**絞る**役で、`d.write` の上限外の要素は無視する / (6) `approvals.json` の承認済み範囲（`scope` に完全一致、または `scope/` 配下）に一致 → **allow**。承認単位 `"."` は認めない（全パスが allow になるため。記録にあっても無視する） / (7) それ以外 → **ask WF202**（承認単位は親ディレクトリ。`file_granular` に載るファイルと、リポジトリルート直下のファイルはファイル単位）。`workflow-diff-check` / `subagent-stop-check` も同じ `A` で範囲外を判定する
- 操作の分類 `ops`: `read`（状態を変えない読み取り系コマンド。一覧の正は `scope.sh` の `_SC_READ_ONLY_CMDS`（`ls cat head tail grep rg jq wc sort diff test echo pwd which type shellcheck stat file date awk cut tr od` など）と `_SC_GIT_READ_SUBCMDS`（`git status/log/diff/show/branch/rev-parse/fetch/ls-files/blame` など）、および `bash -n <file>`・`find`（`-exec` 系を伴わないもの）。**`_SC_GIT_READ_SUBCMDS` に載っていても、下の「サブコマンド + オプション」の限定適用（`branch` / `symbolic-ref` / `reflog` / `--output=` / グローバル `-c`）が先に効く**。`worktree` は白名簿には無いが `list` だけ限定適用で `read` になる。`command -v x` は透過ラッパー `command` を剥がした後の `-v x` で判定されるため読み取りとしては扱われない（必要なら `which x` / `type x` を使う））/ `build-test`（`commands.build-test` に列挙されたコマンド（`npm test` 等）、または実行体が `bash`（または `sh`）で第 1 引数が `tests/` か `test/` で始まる `*.sh`（リポジトリ直下のテスト）であるもの。入れ子の置き場（`packages/x/tests/*.sh`）や参考実装など他の場所のテストは、調査計画・実装計画が `commands.build-test` に前方一致の文字列で列挙する（列挙が無ければ WF204 で止まり、案内に従って列挙を足す）。使えるのは作業中チケットの `allow.ops` に `build-test` があるときだけ）/ `hook-test`（実行体が `bash`（または `sh`）で第 1 引数が `.claude/hooks/**/tests/*.sh`・`.claude/skills/*/scripts/tests/*.sh`。`scope.sh` の分類では `build-test` と提供コマンド（`provided`）の識別より**先**に判定する — `workflow-guard` の制御方式 6 が「提供コマンド → 許可」を先に置くのは `scope.sh` の分類結果に対してであり、`CP_PROVIDED` を直に見て素通ししてはならない — これらのパスは `tests/` 配下でも提供コマンドの形でもあるため）/ `remote-read`（`gh` / `glab` の `view` `list` `api` の GET・`status`）/ `remote-write:<種別>`（`push` は push.sh、`issue-create` `issue-append` `mr-create` `mr-edit` `mr-comment` `attach` `draft-ready` は対応する `gh` / `glab` サブコマンド）/ `merge-base`（`git merge origin/<default>`）/ `web`（外部技術調査の取得コマンド `curl` / `wget`。出力先を持つ形は書き込みとして §8 の判定を当てる。`WebFetch` / `WebSearch` は §1 の matcher 外で**機構は強制しない**（§8 冒頭・§13・DDR i0009-12・i0009-41））。提供コマンドは分類を問わず許可（前提検査はコマンド側）
- **`read` の一覧に入れるものと入れないもの**（判定規則はフック側に複製せず `scope.sh` に置く）:
  - **シェルのキーワードだけの段は `read`** に分類する（`for` `done` `fi` `esac` `case` `select` `coproc` `function`）。`for f in a b; do …; done` のようなループは `do` / `done` が独立した段になり、これらを一覧に入れないと「分類外のコマンド」で WF204 になってふつうのループが全部止まる。外部プロセスを起動しない語なので読み取りとして安全で、リダイレクトは段に残るため `done > out.txt` は従来どおり書き込みとして拾われる
  - **`python` / `python3` / `perl` / `ruby` / `node` / `deno` は `read` に入れない**（分類外 = WF204）。引数のスクリプトが何をするかはコマンド文字列から判定できず、読み取りと言い切れないため。コード文字列を渡す形（`-c` / `-e`）は §7-5 の `opaque` としてさらに厳しく扱う。作業ツリー内の一時スクリプトを走らせたいときは、`commands.build-test` への列挙か、チケットの `allow.ops` で分類を宣言する経路を使う
  - **PowerShell の読み取り系コマンドレットは `read`** に分類する。`PowerShell` は §1 の matcher に入っており、入れないと `Get-Content` / `Select-String` のような読むだけの操作がすべて WF204 で止まる。対象は `get-content` `get-childitem` `get-item` `get-itemproperty` `get-location` `get-command` `get-help` `get-date` `get-member` `test-path` `resolve-path` `split-path` `join-path` `select-string` `select-object` `where-object` `foreach-object` `sort-object` `group-object` `measure-object` `compare-object` `convertfrom-json` `convertto-json` `format-list` `format-table` `write-output` `write-host` と、`gc` `gci` `gi` `gl` `gcm` `sls` `select` `where` `foreach` の別名。**照合は小文字化して行う**（PowerShell のコマンド名は大文字小文字を区別しない）。書き込み系（`set-content` `out-file` `add-content` `new-item` `remove-item` `copy-item` `move-item`）は一覧に入れず、分類外として WF204 で止める
- **git の分類は「サブコマンド名だけ」ではなく「サブコマンド + オプション」で決める（限定適用）**。広げるのではなく**穴を閉じる**ための規則で、対象は次の 6 つに限る（それ以外のサブコマンドの扱いは変えない。網羅は主張しない）。DDR `i0050-04`。

  | # | 形 | 分類 | 判定 |
  |---|---|---|---|
  | 1 | `git worktree <sub>` | `list` だけ `read`、それ以外は `unknown` | サブコマンドの次の語が `list` なら `read`。`add` / `remove` / `move` / `prune` / `repair` / `lock` / `unlock`、および**語を確定できないとき**は `unknown`（作成・削除・移動は提供コマンド `worktree.sh` を通す） |
  | 2 | `git branch` | 既定 `read`、書き込みオプションがあれば `unknown` | 引数に `-d` `-D` `--delete` `-m` `-M` `--move` `-c` `-C` `--copy` `-f` `--force` `-u` `--set-upstream-to` `--unset-upstream` `--edit-description` のいずれかがあれば `unknown`。無ければ `read`（`-a` `-v` `--list` `--show-current` などの読み取り形は従来どおり通る） |
  | 3 | `git symbolic-ref` | 既定 `read`、書き換え形は `unknown` | `-d` / `--delete` があるか、**位置引数が 2 つ以上**（`<name> <ref>` の代入形）なら `unknown`。位置引数 1 つ（読み取り）は `read` |
  | 4 | `git reflog <sub>` | `show` と `exists` は `read`、それ以外は `unknown` | サブコマンド省略時は `show` とみなす。`expire` / `delete` / `drop`、および語を確定できないときは `unknown` |
  | 5 | `git <read サブコマンド> --output=<file>` | `write`（`SC_TARGETS` に出力先） | `diff` / `log` / `show` / `format-patch` などの読み取り形でも、`--output=<file>` / `--output <file>` があれば書き込みとして扱い、出力先パスを `SC_TARGETS` に入れる（呼び手が §8 の判定順を当てて WF205 を決める）。`git` は `_CP_WRITE_CMDS` に無いので、この規則が無いと任意のパスへ書ける |
  | 6 | `git -c <name>=<value> …` / `git --config-env=<name>=<var> …` | 一律 `unknown` | **設定名を見ない**。`-c` / `--config-env` があればサブコマンドが何であれ `unknown` に倒す |

  - **6 が設定名を見ない理由**: 実行や書き込みを誘発する設定名（`diff.external` / `core.pager` / `sequence.editor` / `core.editor` / `*.textconv` …）を列挙する形では、列挙から漏れた名前が `read` のまま通る。`-c diff.external=<コマンド>` は `read` 分類のまま**任意コマンドを実行できる**形なので、ここは網羅に頼らず安全側（一律 `unknown`）に倒す。正当な用途（`git -c core.pager=cat log`）は素の形で足り、どうしても要るならチケットの `allow.ops` で分類を宣言する経路を使う
  - **2〜4 で「オプションを見て `unknown` に倒す」形は、通っていたものを止める向きにしか働かない**。逆向き（`unknown` を `read` にする）は 1 の `worktree list` だけである
- **`cd` は分類に足さない**（`unknown` → WF204 のまま）。理由は 2 つで、①`workflow-guard` の書き込み先の解決は `hook_rel_path`（§2）が `HOOK_WORKTREE` を起点に畳むだけで **`cd` の効果を追跡しない**ため、`cd` を `read` に足すと `cd <他の場所> && echo x > a.txt` の `a.txt` が自分の作業ツリーの相対パスとして判定され、作業ツリーの外への書き込みが通る ②作業ツリーの中で作業するときの作業ディレクトリは最初からその作業ツリーなので `cd` は要らない。**これは §13 の意図的な緩和ではなく、判定の起点を 1 つに保つための設計判断**である
  - **帰結として、提供コマンドは作業ツリーのルートを作業ディレクトリとしてルート相対表記で呼ぶ**（§7-8）。作業ディレクトリがルートでない経路では提供コマンドを起動できない（`cd` で移れないため）。作業ツリーを切り替えるときは、ツール側の作業ディレクトリをその作業ツリーのルートにして始める
- **上の 6 つ以外の「分類外」は既定拒否のまま残す**。`checkout` / `switch` / `stash` / `merge-tree` / `version` / `help` のような git のサブコマンドと、`_SC_READ_ONLY_CMDS` に無い基本コマンドは `unknown`（WF204）のままで、本節はそれらを広げない。既定拒否の原則（「どの分類にも当たらない = 拒否」）を保ち、必要な操作は**提供コマンド**か**チケットの `allow.ops` の宣言**という記録の残る口で通す
- チケットの宣言 `d` は frontmatter の `allow`（§9）。`d.ops` に無い分類は使えず、`d.write` を指定すれば `types[t].allow` のうちその範囲だけが書ける（どちらも上限の内側で絞る役。`common.allow` は宣言によらず常に書ける）。ただし `read` / `remote-read` と提供コマンド（`provided`）は宣言によらず常に可 — 読むだけの操作と機構の操作が宣言漏れで止まらないため

## 9. チケットの機械可読項目

チケットの記載事項は frontmatter（YAML）に置き、フックと提供コマンドはこれを読む（人間もここを読む。表への転記はしない）。読み取りは `frontmatter.sh`（§7）に統一し、ファイル名 `<連番>-<種類>.md` の種類とこの `ticket_type` が食い違うときは frontmatter を正とする:

```yaml
---
type: ticket
ticket_type: implementation        # タスクの種類（.claude/hooks/config/task-types.tsv の type）
predecessors: ["0006"]             # 先行チケット
executor: "sonnet"                 # 実行者（サブエージェントのモデル）または main
human_review: {required: true, reason: "..."}
adversarial_review: {required: false, reason: "..."}  # 敵対的レビュー要否（切れ目の前。00-workflow-issue-mr-driven 手順 2a が読む。既定は rules/work-defaults.md）
allow:
  write: ["src/auth/**", "tests/auth/**"]   # 書き込んでよい範囲（上限の内側）
  ops: ["read", "build-test", "remote-read"] # 実行してよい操作の分類
started_at: ...                    # ticket.sh が記録
completed_at: ...
base_sha: ...                      # 差分基準点
cancelled_at: ...                  # ticket.sh cancel が記録（取り消したチケットのみ）
cancel_reason: "..."               # 同上
---
```

`ticket.sh` が書く文字列値（`cancel_reason` 等）は YAML の二重引用符の規則でエスケープする（`\` → `\\`、`"` → `\"`。改行は空白に置く）。

`workflow-guard` は作業中チケットの frontmatter のうち `ticket_type` `allow` `executor` `human_review` `adversarial_review` `predecessors` への書き込み（Edit / Write）を改変として拒否し（WF208）、本文（DoD のチェック・作業ログ）は許可する。**入れ子のキー（字下げのある `write:` / `ops:` の行）も同じく改変として見る** — 親の `allow:` の行に触れずに `  write: [...]` の行だけを差し替えれば宣言を書き換えられるため、親キーだけを見ていると素通りする。判定を**字下げのある行に限る**ことで、作業ログの箇条書き（`- ops: …`）を巻き込まない。`workflow-diff-check` は `ticket_type` が着手時のコミット値から変わっていれば警告する（WF603）。

## 10. ヘッドレスの判定

`WORKFLOW_HEADLESS=1` または `CI` が真値のとき、フックは「ユーザーが応答できない」とみなし、`ask` を `deny` に置き換える（理由に「計画タスクで宣言を十分に列挙する必要がある」を含める）。スキル側（`00-workflow-quick-request` 等）も同じ変数で判定する。`claude -p` の自動検知は入力に判別材料が無いため行わない（フェーズ 4c で実測した。`SessionStart` の `source` は対話と同じ `startup` で、ヘッドレスを示すフィールドは 1 つも来ない。`permission_mode` はヘッドレスで `plan`・対話で `auto` だったが、対話でもプランモードなら `plan` になるので判別の決め手にならない）。

## 13. 意図的な緩和（機構が強制しないもの）

- **継続条件の窓**: 作業領域にチケット（未着手 / 作業中 / 完了のいずれか）がある間は宣言を求めない（要件・`CLAUDE.md`）。作業中チケットが無い切れ目・レビュー待ちの間は `workflow-guard` も判定しないため、この間に別の依頼が無宣言で書き込める。これは「切れ目の処理に必要な書き込みを妨げない」ための意図的な緩和で、機構が守るのは進行状態・コミット / push・`chmod`（常時フック）まで。別の依頼を始めるときの「チケットを完了するか todo に戻してから宣言し直す」（`CLAUDE.md`）と、軽作業の「チケットがあるブランチでは確認してから」（quick-request 仕様 1-3）はスキルの手順で守る
- **外部への問い合わせ（`web`）のうち `WebFetch` / `WebSearch`**: PreToolUse に登録せず、宣言の有無によらず素通りさせる（§8）。コマンド側（`curl` / `wget`）は `web` の分類として強制するので、緩和はツール側の 2 つに限る。**記録が残るコマンドの側だけを止めて記録の残らないツールを素通りさせる倒錯を避けるための線引き**であり、緩和の理由は「副作用が読み取りに閉じる」ことである
- **MCP 経由のリモート書き込みの種別**: `mcp__.*` は `workflow-entry` の matcher に含めて**宣言の有無**は強制するが、`workflow-guard` は**種別（issue 作成 / コメント / MR 編集）を宣言と突き合わせない**。MCP のツール名はサーバが定義するもので `remote-write:<種別>` に機械的に対応づけられず、誤分類で正当な操作を止めると外部委任モード（`gh` 不在時のフォールバック）が使えなくなるため。draft 解除だけは `workflow-state-guard` が `mcp__*pull_request*` / `*merge_request*` の `draft:false` として塞ぐ（DDR i0009-27）。**種別だけでなく許可範囲（`allow.write` のパス照合）も判定しない** — `workflow-guard` の matcher に `mcp__.*` が無いため、MCP のサーバがファイルを書くツールを提供していればチケットの許可範囲の外にも書ける。宣言（`workflow-entry`）と状態（`workflow-state-guard`）は効いているので「宣言のないセッションが黙って書く」ことは防げるが、**MCP を繋ぐときはそのサーバが何を書けるかを人が確かめる**前提に立つ
- **worktree への移動そのもの**: `EnterWorktree` / `ExitWorktree` はどの matcher にも入れない。移動は読み書きではなく、移った先でも `workflow-guard` は書き込み先パスを**その作業ツリー**（`HOOK_WORKTREE`。§2 の解決順が `cwd` から決める）基準で解決して判定するため（許可範囲・作業ツリー外・`WF208` はいずれも worktree の中で効くことを実測で確認した）。**worktree に移っても許可範囲は広げられない**
- **同一リポジトリの外への書き込み**: `hook_rel_path` がどの根の配下にも畳めないパス（OS の一時ディレクトリ・別 clone・別リポジトリ）は、進行状態・置き場の保護（`workflow-state-guard`）の対象にならない。保護対象はリポジトリの中にしか無いためで、作業ツリーの外への書き込みそのものは、作業中チケットがあるときに `workflow-guard` が WF209 で止める。**作業中チケットが無い切れ目では、リポジトリの外への書き込みは誰も止めない**
- **`git merge` によるマージコミット**: `merge-base` の分類で許可され、メッセージは git が生成する（`commit.sh` の規約検査を経ない）。取り込みに限る（DDR i0004-07）
