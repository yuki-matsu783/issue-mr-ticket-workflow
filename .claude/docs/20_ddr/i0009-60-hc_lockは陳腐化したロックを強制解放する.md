# i0009-60. `hc_lock` は陳腐化したロックを強制解放する

## 背景

`i0009-23` / `i0009-38` は `usage/<branch>.json` の read-modify-write を `mkdir <name>.lock` で直列化し、解放を「処理の最後に `rmdir`、`trap` でも消す」と定めた。`i0009-23` の理由は「**ロックの解放漏れが一番怖い**」だった。

ワーク境界の 2 巡目レビューで、その対策（`trap`）が**効かない場面がある**ことが指摘された。共通仕様 §3 が自ら書いているとおりである。

> §1 のラッパーの `||` も §3 の `trap ERR` も、**打ち切られた場合には効かない**（プロセスごと終了させられ、出力が捨てられるため）

`post-push-usage-report` は transcript を解析する重い処理で、ロックを保持したまま打ち切られる可能性がいちばん高い。そうなると**ロックディレクトリが残り続け**、以後の Stop / SubagentStop は毎回 2 秒待って諦め、使用量の集計が恒久的に止まる（しかも 2 秒の遅延が常時乗る）。

## 決定

`hc_lock <name>` は取得を試みる前に、**ロックディレクトリの作成時刻が 60 秒より古ければ陳腐化とみなして `rmdir` してから取り直す**。

- 強制解放したことは**実行ログに 1 行残す**（`parse_errors` と同じ置き場。`i0009-49`）
- 60 秒以内のロックは陳腐化とみなさず、従来どおり最大 2 秒待って諦める
- `HK-T20` で固定する: 60 秒超のロックを置いても次の実行が回復して加算に成功する / 60 秒以内のロックは 2 秒で諦める（負のコントロール）/ 強制解放が実行ログに残る

## 理由

- **`trap` が効かない経路が仕様に明記されている以上、それを前提にした回復手段が要る**。「解放漏れが一番怖い」と書いておきながら、いちばん起きやすい経路（打ち切り）に対策が無かった
- **60 秒はロックの保持時間の上限より十分長い**。`hc_lock` が守るのは `usage/<branch>.json` の read-modify-write（JSON を 1 つ読んで加算して書く）で、正常なら数十 ms。60 秒残っているロックは持ち主が死んでいるとみなしてよい
- **`UserPromptSubmit` の既定タイムアウトが 30 秒、`command` 型の既定が 600 秒**（`i0009-11`）なので、60 秒は「打ち切られたフックのロック」を確実に拾い、かつ「生きているフックのロック」を誤って奪わない範囲にある。`post-push-usage-report` は案内側で `UserPromptSubmit` ではないが、正常時に 60 秒かかるなら別の問題（`i0009-11` の「600 秒に達するフックは実装の誤り」）
- **強制解放の記録が要る**。黙って奪うと、実際に 2 つのプロセスが同時に加算して壊れたときに原因が追えない
- **`hc_lock` に閉じれば全フックに効く**（`i0009-38` の「各フックが自作しない」と同じ理由）

## 却下した案

- **PID をロックディレクトリに書き、プロセスの生死で判定する**: プロセスの生死の確認に `kill -0` や `/proc` を使うことになり、Windows の Git Bash で移植性が無い。しかも PID は再利用される
- **`flock` を使う**: Git Bash に `flock` が無いことがある。`mkdir` を選んだのはそのため（`i0009-23`）
- **陳腐化の判定をせず、諦めたら記録だけ残す**: 集計が恒久的に止まる状態が続く。実行ログを人間が読んで手で消すまで直らない
- **タイムアウトを 2 秒から伸ばす**: 残置ロックには効かない（永遠に取れない）。案内側フックが人間を待たせる時間も伸びる
- **`session-start` が古いロックを掃除する**: セッションを開き直すまで直らない。`logs/sessions/` の 7 日より古いディレクトリの削除と同じ扱いにするには、頻度が合わない
