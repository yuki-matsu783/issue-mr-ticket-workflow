# 10-task-design-exec スキル 仕様

## 概要・禁止事項

設計実施タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-design-exec.md](../../00_requirement/skills/10-task-design-exec.md)。処理フローの共通手順は `10_spec/skills/10-task-investigation-exec.md`「実施タスクの共通手順（正）」に従い、ここでは固有部分だけを書く。

禁止事項（共通手順の禁止事項に加えて）:

- ソースコード・`.claude/` 配下への書き込み（コードに書きたい内容は仕様書のインターフェース定義へ、AI アセットに書きたい内容はフィードバック計画へ）
- 実装の詳細（コード）への踏み込み
- 設計計画書・調査結果レポートの書き換え（骨子どおりに書けないときは「未解決事項」へ）
- 既存設計書の本文への変更履歴・経緯の記載（経緯は DDR）
- 推測で骨子を変えること

## 呼出条件

- `next` が設計チケットを示したとき、全体計画で合意した実行者（サブエージェント）で読み込まれる

## IN / OUT

| IN | OUT |
|----|----|
| 設計計画書（結論方針・一覧・骨子）、調査結果レポート、issue の受け入れ条件、既存の設計文書 | アプリルート `apl/<アプリ名>/` の `docs/` 配下の要件定義書・仕様書（新規 / 更新）と DDR、設計結果レポート（md + HTML）、完了済みの設計チケット群、結果報告 |

## IN / OUT サンプル

- 成果物: `docs/requirements/auth.md`（EARS の受け入れ基準）、`docs/spec/auth.md`（インターフェース・処理フロー・エラー・テストシナリオ AUTH-T01〜T05）、`docs/ddr/....md`（採らなかった案）
- 結果報告の見てほしい点: 「受け入れ条件が受け入れ基準・テストシナリオに漏れなく落ちているか / 判断点の結論が調査結果と矛盾しないか / 仕様が実装可能な粒度か・コードに踏み込みすぎていないか / 既存設計書との整合」

## 処理フロー

共通手順に加えて（3 の実施）:

- 書き方の正は `20-common-step-requirement`・`20-common-step-spec`（章立て・EARS・正史のみ・線引き）。置き場はアプリ本体の設計文書の置き場（`docs/` 配下。既存の構成に従う）
- 要件定義書: 受け入れ条件を EARS（When / Shall、If / Then、Shall not）の受け入れ基準に落とし、前提・制約・依存を書く
- 仕様書: 入出力・処理フロー・インターフェース・エラーハンドリング・テストシナリオを実装可能な粒度で書き、テストシナリオにテスト ID を振る（実装の DoD と対応させる）
- 「設計チケットで結論を書く」とされた判断点は根拠付きで正史に書き、採らなかった案と理由を DDR に残す
- 既存設計書の更新は本文をその時点の正史に書き換える
- 書き終えたらプレースホルダ 0 件と、用語・インターフェースが既存の設計書と整合していることを確認する
- 骨子どおりに書けない（前提が崩れた）場合は書ける範囲を書き、「未解決事項」と代わりの案をレポートに残す（必要なら設計計画の追加チケットを結果報告で提案）
- 見てほしい点の固定項目: 受け入れ条件の落とし込みの網羅 / 結論の根拠と調査結果との整合 / 実装可能な粒度とコードへの踏み込み / 既存設計書との整合

## OUT ひな形

設計結果レポート（report-view のレポートテンプレート）に次を含める: 作成・更新した設計書と DDR の一覧 / 判断点の結論とその根拠の要約 / 受け入れ条件 × 受け入れ基準・テストシナリオの対応表 / 想定と異なった点 / 残課題（骨子どおりに書けなかった点・未解決事項）。

## 参照ナレッジ
