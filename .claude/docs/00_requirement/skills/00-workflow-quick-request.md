# 00-workflow-quick-request スキル

## 概要

issue と MR を作るまでもない軽作業のための振り分けスキルの要件を定義する。`00-workflow-issue-mr-driven` と対になり、`CLAUDE.md`「作業の振り分け」によりすべての依頼はこのどちらかを読み込んでから着手する。

- **背景**: 質問・説明・typo 修正のような依頼まで issue と MR に紐づけると手続きが作業量を上回る。一方で振り分けを省くと、軽作業のつもりで始めた変更が振る舞いの変更や複数ファイルに及び、経緯もレビューも残らない。「本当に軽作業か」を最初に判定し、範囲を宣言して、超えたら止まる軽量な進め方が要る。また軽作業でも AI アセットの不備には気づくため、その知見を捨てずに issue へつなぐ出口が要る。
- **目的**: 判定 → 宣言 → 実施 → 報告 → 振り返り の順序を固定し、軽作業を issue / MR / チケット無しで素早く進めつつ、範囲の逸脱と AI アセットの無断変更を防ぎ、改善候補を issue として残せる状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md）、軽作業かどうかの判定基準、状態確認、作業範囲の宣言、実施と範囲超過時の停止、報告、振り返り（使った AI アセットの棚卸しと改善要否の確認）と issue 起票への接続、`00-workflow-issue-mr-driven` への切り替え
  - 含まない: issue / ブランチ / MR の作成とチケット駆動の実作業（`00-workflow-issue-mr-driven`）、振り分けの宣言を強制する仕組み（フックの要件）、issue 作成の操作手順（common-step スキル）

---

## ユーザーストーリー

**[As a]** 質問・説明・小さな修正のような軽い依頼をこなす開発者として、

**[I want]** issue や MR を作らずに、範囲を宣言してから軽作業を進めてもらい、範囲を超えそうなら止まってほしい。

**[So that]** 過重な手続きを踏まずに素早く対応でき、軽作業のつもりが大きな変更に膨らむことを防げるため。

**[As a]** 機構の保守者として、

**[I want]** 軽作業の中で見つかった AI アセットの不備も、その場で振り返って issue として残したい。

**[So that]** 小さな依頼のときにだけ気づく罠を取りこぼさないため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 軽作業と判定し、ファイルの変更を伴うとき、Shall スキルは着手前に現在のブランチ・未コミットの変更・チケットの有無を確認しなければならない（質問・説明だけなら省略してよい）。
- When 作業に入る前に、Shall スキルは「やること」「触るファイル（無ければ無し）」「やらないこと」を 2〜4 行で宣言しなければならない。この宣言が範囲超過の判定基準になる。
- When 実施するとき、Shall スキルは宣言した範囲の中でだけ作業し、既存テストの対象に触れる変更なら実行して結果を確認しなければならない。
- When 実施が完了したとき、Shall スキルは変更したファイルと要点（変更が無ければ回答そのもの）、確認した内容、積み残しと気づいた問題を報告しなければならない。
- When 報告のあと、Shall スキルは質問・説明だけの依頼でも省略せず、今回のプロンプトで使った AI アセット（スキル・フック・ルール・エージェント・CLAUDE.md）を棚卸しし、「足りなかった」「邪魔だった」「無かった」「問題なし」の観点と「(a) アセットが無かった」「(b) あったが誤っていた」「(c) あったが罠が書かれていなかった」「(d) あったのに辿り着けなかった」の類型で振り返らなければならない。観点と類型の文言は `00-workflow-issue-mr-driven` のフィードバック計画と揃える。
- When 振り返りで改善候補があるとき、Shall スキルは候補ごとに「issue として記録だけする（着手しない）」「issue を作って `00-workflow-issue-mr-driven` で進める」「今回は不要」をユーザーに確認しなければならない。`.claude/` 配下のアセットは軽作業の中で直接修正しない（文言修正も含む）。
- When 「issue として記録だけする」が選ばれたとき、Shall スキルは候補を issue（種別: 改善・最適化、優先度は低を既定、発端の振り返りを添える）として起票し、ブランチ・MR・実作業に進んではならない。起票した issue への着手はユーザーの明示的な指示を待つ。
- When 「issue を作って `00-workflow-issue-mr-driven` で進める」が選ばれたとき、Shall スキルはその場で `00-workflow-issue-mr-driven` を読み込み、要約・受け入れ条件・種別・issue 種別（AI アセット）を引き継いで開始しなければならない（次のプロンプトに先送りしない）。issue の内容やブランチの承認は切り替え先で改めて取る。
- When 「今回は不要」が選ばれた候補があるとき、Shall スキルは報告に「見送り」として残し、黙って捨ててはならない。見送りが積み上がってきたら「issue として記録だけする」を勧める。
- When 振り返りで候補が無かったとき、Shall スキルは「候補なし」と報告して完了とし、確認を求めなくてよい。

### 代替フロー

- If 判定が issue-MR 側だった場合、Then スキルはその旨を伝えて `00-workflow-issue-mr-driven` を読み込んで切り替え、このスキルの手順を続けてはならない。
- If ユーザーが issue 番号や MR の URL を添えて依頼した場合、Then スキルは軽作業ではなく issue-MR 駆動として扱わなければならない。
- If 作業中に宣言の範囲を超えると分かった場合（宣言に無いファイルを触る必要が出た、振る舞いの変更が必要になった、4 ファイル以上になった）、Then スキルは作業を止め、「軽作業として範囲を広げる」「`00-workflow-issue-mr-driven` に切り替える」「ここまでで止める」をユーザーに確認しなければならない。切り替える場合はここまでの変更を残すか戻すかも確認する。
- If 未コミットの変更が既にある場合、Then スキルはそれに触らず、対象ファイルが既に変更されていないかを確認してから進めなければならない。切り替え先へ引き継ぐときも勝手に stash・破棄しない。

### 例外フロー

- If 振り分けの宣言が無いとして機構に操作を拒否された場合、Then スキルはこのスキルまたは `00-workflow-issue-mr-driven` を読み込んでから元の操作をやり直し、迂回してはならない。
- If 変更が既存テストを壊した場合、Then 修正が軽作業の範囲内なら直し、範囲を超えるなら止めて確認しなければならない。
- If 振り返りから `00-workflow-issue-mr-driven` に切り替えたが `glab`（GitHub では `gh`）が未導入・未認証だった場合、Then 切り替え先の手順に従って導入・認証を案内して停止し、軽作業として代替してはならない。

### 判定基準

- When 依頼を受けたとき、Shall スキルは次の観点で軽作業かどうかを判定し、**1 つでも issue-MR 側に該当すれば軽作業として進めてはならない**。

| 観点 | 軽作業（このスキル） | issue-MR 駆動（`00-workflow-issue-mr-driven`） |
|---|---|---|
| 成果物 | 回答・説明・調査結果のみ、または振る舞いを変えないファイル変更 | コード・設定の変更を伴う開発作業 |
| 振る舞い | 変わらない（typo、コメント、ドキュメント、フォーマット、設定値の微調整） | 変わる（機能追加、バグ修正、リファクタリング、依存の追加・更新） |
| 規模 | 1〜3 ファイル、同一ディレクトリ内に閉じる | 複数モジュールにまたがる、または 4 ファイル以上 |
| 検証 | 目視・既存テストの実行で足りる | テストの追加・変更やレビューが必要 |
| 追跡 | 経緯をリモート（GitLab / GitHub）に残す必要が無い | issue / MR で経緯を追いたい、他の人がレビューする |
| 対象 | `.claude/` 配下以外 | `.claude/` 配下のアセット（スキル・フック・ルール・エージェント・設定・設計文書）の作成・変更はすべて。文言修正も例外にしない |
| ユーザーの指定 | 「軽く」「issue 不要」「質問」など | 「issue 駆動で」「MR にして」「#N をやって」など |

- When 判定したとき、Shall スキルは判定結果と根拠を 1 行でユーザーに示さなければならない。
- When 境界上で判断できないとき、Shall スキルは重い側（`00-workflow-issue-mr-driven`）に倒すか、軽作業として進めるか issue-MR 駆動で進めるかをユーザーに確認しなければならない。

### 承認ポイント

- When 境界上の判定、チケットがあるブランチでの実施、範囲超過時の扱い、振り返りの候補の扱いを決めるとき、Shall スキルは選択肢を提示してユーザーの判断を得なければならない。
- When 現在のブランチが default ブランチと異なる状態で変更を伴うとき、Shall スキルは「このまま現在のブランチで実施する」「default ブランチに切り替えて実施する」「中断する」を確認しなければならない。
- When ユーザーが応答できない実行形態のとき、Shall スキルは確認を行わず現在のブランチのまま進め、振り返りの候補は報告に含めるだけにして完了扱いとし、issue も作ってはならない。ただし作業領域にチケットがある場合は実施せず、その旨を報告して終える。

### 他のスキル・機構との整合

- When このスキルが読み込まれるとき、Shall それはユーザーのプロンプトごとに行われ、前のプロンプトでの読み込みを引き継いではならない。ただし `00-workflow-issue-mr-driven` の作業中（作業領域にチケットがある間）は再宣言を求められない。
- When 作業領域にチケット（未着手 / 作業中 / 完了）があるとき、Shall スキルは issue-MR 駆動の作業が進行中であることを示し、このブランチで軽作業を実施してよいかをユーザーに確認し、承認されたときだけ実施しなければならない。承認されなければ実施せず、issue-MR 駆動の作業の再開を案内する。
- When 軽作業でコミットや push を行うとき、Shall スキルは提供コマンド（とそれを使う common-step スキル）経由でのみ行い、default ブランチ上ではユーザーの指示があるときだけコミット・push しなければならない（勝手にブランチを切らない・コミットしない）。
- When issue を起票するとき、Shall スキルは自前で `glab issue` / `gh issue` を組み立てず、issue 操作の common-step スキルの手順に従わなければならない。
- When 一時ファイルが要るとき、Shall スキルは `wip/tmp/` に置き、ワークスペース外のパスを使ってはならない。

## 前提条件

- `CLAUDE.md`「作業の振り分け」により、プロンプトごとにこのスキルまたは `00-workflow-issue-mr-driven` の読み込みが求められ、機構がそれを強制すること
- `.claude/` 配下の変更は例外なく `00-workflow-issue-mr-driven` で行うこと（`CLAUDE.md`）。この定めへの `CLAUDE.md`・旧世代スキルの追従は、本機構の AI アセット実装フェーズの変更対象（参照更新の一覧）に含める
- 対になる `00-workflow-issue-mr-driven` が導入済みで、振り返りからの切り替えを受け付けること

---

## 制約条件

- **技術的制約**: 判定に迷ったら重い側に倒す。「軽い」は規模ではなく振る舞いが変わらないことで判断する（1 行でもロジックの変更はバグ修正 = issue-MR 側）
- **ビジネス的制約**: 起票した issue への着手はユーザーが決める。スキルから着手を持ちかけない
- **外部的制約**: ユーザーが応答できない実行形態では確認を行わず、状態変更を伴う操作（ブランチ切り替え・issue 起票）を自動で行わない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 軽量性 | issue / MR / チケットを作らず、判定と宣言だけで作業を開始・完了できる。質問・説明だけなら状態確認を省ける |
| 安全性 | 宣言した範囲を超えたら黙って進めず、必ず止まって確認する。`.claude/` 配下を直接変更しない |
| 一貫性 | 振り返りの観点・類型の文言を `00-workflow-issue-mr-driven` のフィードバック計画と揃える |
| 追跡性 | 見送った候補も報告に残す。起票した issue には発端の振り返りが書かれている |
