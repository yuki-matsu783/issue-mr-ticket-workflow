# i0009-22. ホットパスのフックは `jq` だけを許し、本体から `git` を呼ばない

> **回数の上限は `i0009-46` が定める**（stdin と固定パスの副入力で 1 回 + `session_id` 依存の副入力で 1 回 = 最大 2 回）。この DDR が定めるのは「`jq` 以外の外部プロセスを起こさない」「本体から `git` を呼ばない」「回数を機械で数える」の 3 つである。

## 背景

`i0009-11` で「打ち切り（timeout）は fail-open で塞げないので、フックを速く保つことだけが対策」と決め、§1 に「ホットパス 5 本（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）で 1 秒以内」という目安を置いた。

境界レビュー（付録 A の R11）で 2 つの問題が指摘された。

1. **「1 秒以内」は結果であって守り方ではない**。実装者が守れているかを判断できず、テストにも落ちない
2. **§2 が「作業ツリーの位置は `git rev-parse --show-toplevel` を基準にする」と書いており**、これを素直に読むと各フックが毎回 git を起動する。`20-common-step-shell-script` 仕様は読み込み行の解決順の理由として「フックが毎ツール呼び出しで git を起動することになる（Git Bash で**約 95 ms/回**）」を挙げており、自分で否定した方式を §2 が要求している。参考実装 `hook-common.sh:18` も git を呼んでいない

さらに `i0009-21` で確定したとおり、ホットパス 5 本は毎ツール呼び出しで**同時に**起動する。1 本あたりの fork がそのまま 5 倍のプロセスになる。

## 決定

- 「1 秒以内」は目安として残しつつ、**検査できる上限**を併記する: **ホットパスのフックが起動してよい外部プロセスは、stdin を解析する `jq` の 1 回だけ**（`git` / `date` / `sed` / `find` を呼ばない）
  - ルートの解決は読み込み行が fork なしで行う（`BASH_SOURCE` からの上向き探索）
  - パス照合・コマンド分割は純 bash で行う（`cmdpos.sh` は既に純 bash）
  - 時刻は bash 組み込みの `printf '%(...)T'` で取る（`logger.sh` は既にそう）
- この上限は `test-lib.sh` の `make_counting_path` で**呼び出し回数として検査**する（HK-T05・HK-T13 と同じ方式）
- §2 の「`git rev-parse --show-toplevel` を基準にする」を「**読み込み行が解決したリポジトリルート（`LOGGER_ROOT` / `HOOK_ROOT`）を基準にする**」に変え、「フック本体から `git rev-parse --show-toplevel` を呼ばない。`git rev-parse` は読み込み行の最終手段としてだけ使う」を明記する

## 理由

- **上限が数えられる形なら、テストで固定できる**。「1 秒以内」は実行環境（Windows / Linux、ディスク、同時実行数）で変わるので、CI にも回帰にも使えない。fork の回数なら環境に依らず決まる
- 既に同じ方式の実績がある。`push-detect.sh` の「fork ゼロの前置フィルタ」（HK-T13）と `cmdpos.sh` の「fork なし」（HK-T05）は `make_counting_path` で回数を数えて検査している
- 案内側のフック（`post-push-*` / `session-start` / `workflow-diff-check` / `subagent-*`）は git を呼ぶ必要があり、ホットパスではない（ツールの成否が確定した後に走る）ので上限の対象外にする
- §2 の記述は「サブディレクトリからの実行に備える」という意図で書かれていたが、その意図は読み込み行の解決順（`BASH_SOURCE` からの上向き探索）が既に満たしている。手段が二重になっていただけ

## 却下した案

- **「1 秒以内」だけを残す**: 守れているかを実装者もレビュアーも判断できない。`i0009-11` が「速さで守る」と決めた以上、速さを検査可能にしないと決定が空手形になる
- **`jq` も禁止して純 bash の JSON パーサを書く**: stdin の JSON は入れ子とエスケープを含み、純 bash の自作パーサは壊れやすい。1 回に抑えるのが現実的な落としどころ（`hook_read_input` が 1 回で全フィールドを取る形は参考実装で既に実現している）
- **`git rev-parse` の結果をセッション単位でキャッシュする**: キャッシュファイルの読み書きが別の I/O を生み、しかも worktree の切り替えで陳腐化する。読み込み行の解決で足りる

## 影響

- `10_spec/フック共通仕様.md` §1（ホットパスの上限）・§2（作業ツリーの位置）
- **実装フェーズへ**: ホットパス 5 本のテストに `make_counting_path` による fork 回数の検査を入れる
- **フェーズ 4c へ**: 実行時間の実測は引き続き行う（上限を守っていても遅い場合の発見のため）
