# session-start フック

## 概要

セッションが開始・再開・クリア・compact されるたびに、現在のブランチ、作業領域のチケットの配置、機構の進行状態から「今どこにいて、次に何を読み込むべきか」を導出して AI に伝えるフックの要件を定義する。手書きの引き継ぎメモは置かず、現在地は常にリポジトリ内のファイルから導出する（DDR i0001-04）。本書は GitLab の用語で書き、GitHub では MR → PR と読み替える。

- **背景**: 長い作業では compact やセッションの再開で AI の認識が失われ、どのチケットまで進んだか・レビュー待ちか・次にどのスキルを読むかが分からなくなる。参考実装の手書きの引き継ぎファイルは更新漏れと実態のずれを生み、その保守に専用の仕組みを要した。本機構では状態遷移がすべて提供コマンド経由で行われ、MR の作成・レビュー依頼と完了・マージ前作業の結果はその時点で進行状態に記録されるため、現在地はリポジトリ内のファイルだけから決定論的に導出できる。
- **目的**: セッションの境界で AI が現在地と次の一手を知らされ、手書きのメモに頼らず、再開時に全体計画ワークをやり直さずに続きから進められる状態を実現する。
- **スコープ**:
  - 含む: 導出して伝える項目と導出の元、伝えない項目（ファイルの中身・リモートの現在値）、進行中の作業が無いときの扱い、MR が記録されていないときの扱い、サブエージェントでの扱い、注入量の目安と超過時の扱い、依存が壊れたときの倒し方、frontmatter 索引の最新化（索引機構の導入後）
  - 含まない: 現在地の判定規則そのもの（ワークの切れ目・レビュー状態・マージ前作業の提供コマンドが定める。このフックはその結果を伝える）、MR 上のレビュー結果・指摘・未返信スレッドの取得（レビュー完了の提供コマンド）、再開の手順（`00-workflow-issue-mr-driven`）、振り分けの強制（`workflow-entry`）

---

## ユーザーストーリー

**[As a]** セッションをまたいで作業を続ける開発者として、

**[I want]** セッションを開き直したり compact が起きたりしても、AI が現在のブランチ・issue・MR・チケット・レビューの状態を把握した状態から始めてほしい。

**[So that]** 引き継ぎメモを自分で書いたり、AI に状況を説明し直したりせずに続きへ進めるため。

**[As a]** 機構の保守者として、

**[I want]** 伝える現在地が手書きではなく、リポジトリ内のファイルから導出されていてほしい。

**[So that]** 伝えられる内容が実態とずれず、更新漏れという保守の負担が無くなるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When セッションが開始・再開・クリア・compact されたとき、Shall フックは次を導出して AI に伝えなければならない: 現在のブランチ、ブランチ名から抽出した issue 番号、機構が記録している MR の番号と URL、作業領域のチケットの状態（未着手の先頭・作業中・完了の最後）、現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み / マージ前作業中）、次に読み込むべきスキル（現在地から機械的に決まるもの）、レビュー依頼の証跡（依頼した時点と対象）、マージ前作業の進捗（進行中のとき。draft 解除済みかを含む）。
- When 導出するとき、Shall フックは現在のブランチ、作業領域のチケットの配置、提供コマンドが記録した進行状態（MR の作成・レビュー依頼と完了・マージ前作業の証跡）、全体計画書の有無だけを元にしなければならない。
- When 現在地を伝えるとき、Shall フックは提供コマンドが定める判定規則と同じ結果を伝え、独自の判定を持ってはならない。
- When 内容を伝えるとき、Shall not フックはチケット・計画書・レポートなどファイルの中身を注入してはならない（「次にやること」はチケットの本文が担い、AI が必要に応じて読む）。
- When レビュー待ちまたはレビュー済みを伝えるとき、Shall フックは MR 上のレビュー結果・指摘・未返信スレッドの内容や件数を伝えず、それらはレビュー完了の提供コマンドで取得することを案内しなければならない。
- When 次に読み込むべきスキルを伝えるとき、Shall 対応する work スキルが存在しない場合はその旨を伝え、存在するかのように案内してはならない。
- When 作業領域にチケットが無く、機構が記録している MR も無いとき、Shall フックは「進行中の作業は無い」ことと、依頼ごとに `CLAUDE.md`「作業の振り分け」に従うことだけを伝えなければならない（default ブランチにいるときも同じ）。
- When 作業領域にチケットが無く、機構が記録している MR があるとき、Shall フックは MR の情報と、レビュー待ちまたはマージ前作業中のいずれかであればその現在地を伝えなければならない。
- When AI が伝えられた現在地から再開するとき、Shall `00-workflow-issue-mr-driven` は全体計画ワークをやり直さず、伝えられた現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み）から続けられなければならない。レビュー待ちのときはその旨が伝わり、AI はレビュー完了の連絡がない限り応答を終える。
- When `workflow-entry` が継続条件（チケットの有無・レビュー待ち・マージ前作業中）を判定するとき、Shall このフックが伝える現在地と同じ判定の元（作業領域と進行状態）を使い、両者の結果が食い違ってはならない。
- When 実行環境が異なるとき（`glab` / `gh` の有無・認証の状態・ネットワークの到達性が異なる環境）、Shall フックは同じ作業領域と進行状態に対して同じ内容を伝えなければならない。
- When サブエージェントのセッションが開始されたとき、Shall not フックは何も注入してはならない（メインエージェントのコンテキストにだけ現在地を置く）。
- When 注入する内容が目安（8 KB）を超えるとき、Shall フックは切り詰めずに全量を伝えたうえで、超過している旨の警告を添えなければならない。
- When frontmatter 索引の機構が導入されているとき、Shall フックはセッション開始のたびに索引を非侵襲的に最新化してよく、失敗してもセッションの開始を妨げてはならない（索引機構の導入前は何もしない）。
- When フックが現在地を伝えたとき、Shall 伝えた内容の要約（ブランチ・MR 番号・現在地・注入量）が記録に残らなければならない。記録と注入内容に環境変数の値・トークン・個人情報を含めない。
- When 伝える内容を組み立てるとき、Shall 人間が読んでも分かる日本語で、項目ごとに 1 行にまとめ、AI が次の一手を決めるのに必要な情報だけを含めなければならない。

### 代替フロー

- If 現在のブランチが feature ブランチの命名（issue 番号を含む）に従っているのに、機構が MR を記録していない場合（機構の外で MR が作られた、記録が失われた等）、Then フックは「MR の記録が無い」ことを伝え、ブランチ・MR 作成の task スキル（提供コマンド）で既存の MR を紐づけ直すよう案内しなければならない。
- If issue と MR を作らずにチケット駆動だけを試す単独実行モードで動いている場合、Then フックは MR の情報を「無し」として伝え、チケットの状態と現在地だけを伝えなければならない。
- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは何も伝えず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If フックの依存（`jq`・`git`・補助ファイル）が壊れて現在地を導出できない場合、Then フックは何も出さずにセッションの開始を通さなければならない（案内側の仕組みは通す側に倒す。拒否側の `workflow-entry` / `workflow-guard` は別に働く）。
- If 進行状態のファイルが壊れている場合、Then フックはその旨を伝え、導出できる残りの項目だけを伝えなければならない。

## 前提条件

- 状態遷移（チケットの着手・完了、レビュー依頼・完了、マージ前作業）がすべて提供コマンド経由で行われ、現在地がリポジトリ内のファイルから導出できること（DDR i0001-03 / i0001-04）
- ブランチ・MR 作成の task スキル（提供コマンド）が、作成した MR の番号と URL を進行状態に記録すること
- Claude Code のフック機構が、セッションの開始・再開・クリア・compact のそれぞれでフックを動かし、サブエージェントの開始を区別できること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。手書きの引き継ぎファイルを読まない・要求しない
- **ビジネス的制約**: 伝えるのは現在地と次の一手であり、作業の内容や判断を先回りしない
- **外部的制約**: compact 後の要約は内容を指定できないため、現在地は要約に頼らずこのフックが毎回伝える

---

## 依存関係

- ワークの切れ目の判定・レビュー依頼と完了・マージ前作業の提供コマンド（現在地の判定規則と進行状態。未作成）
- ブランチ・MR 作成の task スキルと提供コマンド（MR の番号と URL の記録元。未作成）
- `workflow-entry`（継続条件の判定を共有。未作成）
- `00-workflow-issue-mr-driven`（伝えられた現在地からの再開）
- frontmatter 索引の機構（導入後に最新化を行う。未作成）
- `.claude/rules/`（bash 規約、ユーザーが応答できない実行形態の考慮）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | リポジトリ内のファイルと git だけを読み、セッションの開始を体感できるほど待たせない |
| セキュリティ | 注入内容と記録に環境変数の値・トークン・個人情報を含めない |
| 可用性 | 依存が壊れたときは何も出さずに通し、セッションの開始を止めない。CLI の有無・認証・ネットワークに左右されず同じ内容を伝える |
| 一貫性 | 現在地・次のスキルは提供コマンドの判定と同じ結果になり、`workflow-entry` の継続条件と食い違わない |
| 簡潔性 | 注入は 8 KB を目安とし、項目ごとに 1 行。ファイルの中身を含めない |
| テスト容易性 | 作業領域の状態と進行状態を与えて、伝える内容を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
