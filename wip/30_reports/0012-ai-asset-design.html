  1. 1

    e1. 作業ツリーの三分を §2 に定義し、共有ルートは別の変数として持って値を HOOK_ROOT に固定した ◎良 根拠: 10_spec/フック共通仕様.md §2（計画書 P3・保留 P2）

    10_spec/フック共通仕様.md §2 に、フックが区別する 3 つの根を表で置いた。

    名前変数指すものそこに置かれるもの
    置き場HOOK_ROOT読み込み行が解決したリポジトリルート（本流）フック・共通ライブラリ・hooks/config/・settings.json
    判定対象の作業ツリーHOOK_WORKTREEその操作が行われた作業ツリーwip/、logs/hooks/decisions.jsonl、logs/sh/

    計画書の保留 P2（変数を分けるか決め打つか）は分けるで決着させた。ただし値の解決は HOOK_ROOT と同一に固定し、環境変数・設定からの上書きを受け付けない。理由は 2 つで、①名前を分けておけば、別 clone を使う運用（要件の前提条件が認めている）を扱うときに値の解決だけを変えればよく、進行状態を読む全フック・全提供コマンドを触らずに済む ②上書きの口を開けると、進行状態の置き場を動かすことで workflow-state-guard の保護対象そのものを外から外せる（拒否側の保護が環境変数 1 つで無効になる）。

    e2. 進行状態・ロック・集計を共有ルートへ、判定記録と実行ログを作業ツリー側へ分けた ◎良 根拠: 10_spec/フック共通仕様.md §1・§5（計画書 P3 / 束 1 の 6・7）

    §5 の表に「根」の列を足し、記録ごとの置き場を 1 か所で読めるようにした。共有ルート側は mr.json / review-state.json / review-history.jsonl / merge-state.json / locks/ / usage/<branch>.json / sessions/<session_id>/ / push-state.json、作業ツリー側は hooks/decisions.jsonl と sh/<name>.log の 2 つだけである。logs/locks/<name>.lock は表に無かったので行を足した（実装は使っており、束 1 の 7 が名指ししている対象なので、置き場を決める以上は表に載っている必要がある）。

    decisions.jsonl のスキーマに cwd（判定時の作業ツリー）と agent_id（サブエージェントの識別）を足し、HK-T06（記録のスキーマ）にその検査と負のコントロール（メインの呼び出しでは agent_id が空）を書き足した。

    この決定が §1 の別の記述に効いていた。 §1 は「jq は最大 2 回」の内訳として「logs/ は作業ツリー側に置き、作業ツリーは stdin の cwd を読んで初めて決まるので、この 4 つを 1 回目に混ぜることは原理的にできない」と書いていた。進行状態を共有ルートへ寄せると review-state.json / merge-state.json の置き場はフックの起動時に決まるので、この理由付けは成り立たなくなる。2 回目が要る理由を session_id 依存（approvals.json / entry.json）に置き換え、review-state / merge-state を 1 回目に混ぜない理由を「読むのが 2 本のフックだけだから」に書き直した。

    e3. 作業ツリーをまたぐ絶対パスの保護漏れ（A1-2）を、無条件の記述で閉じた ◎良 根拠: 調査 e5 / e51（03-state-guard.txt）・計画書 P8 / 束 2 の 2

    調査 e5 / e51 の A1-2（cwd が worktree のとき、本流の logs/mr.json と wip/10_tickets/20_done/*.md を絶対パスで書き換えても止まらない）を、要件と仕様の両方に無条件で書いた（並列を採らなくても作業ツリーが 2 つあれば踏むため）。

    • 要件: 「別の作業ツリーにある進行状態のファイル・チケットの置き場を絶対パスで指して…操作しようとしたとき、Shall フックは自分がいる作業ツリーの中の同じ対象と同じ理由・同じ識別子で拒否しなければならない（保護は作業ツリーの数に依らない）」をメインフローに追加。裏側として「同じリポジトリの外への書き込みは拒否してはならない」も置いた
    • 仕様: 「対象パスの畳み込み」の節を制御方式の前に置き、hook_rel_path の結果を 3 通り（同一リポジトリのいずれかの根の配下 → 畳んだ相対パスで照合 / どの根の配下でもない → 許可 / 判定できない → WF309）に分けた。このフックは「畳めた根がどれか」を見ないことを明示した

    「畳めないパスを拒否側に倒す」は、「リポジトリの外と確定できるもの」と「位置を確定できないもの」を分けて書いた。前者まで拒否すると OS の一時ディレクトリへの正当な書き込みが止まるので、i0010-09 の適用対象は後者に限る。この線引きは §13 の「意図的な緩和」にも 1 項目として書いた。畳み込みの規則そのものは workflow-state-guard に閉じず、共通仕様 §2 に hook_rel_path の振る舞いとして置いた（workflow-guard の __wg_rel も同じ規則を要るため。判定順は 0013 が書く）。
