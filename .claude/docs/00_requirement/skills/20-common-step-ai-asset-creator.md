# 20-common-step-ai-asset-creator スキル

## 概要

AI アセット作成の共通ステップの要件を定義する。`.claude/` 配下のアセット（スキル・フック・ルール・エージェント・settings.json）を仕様書に沿って作成・変更する手順 — 命名、標準構成、テストの範囲、変更の作法 — を標準化する。AI アセット実装・テストの実施タスクから使われる。

- **背景**: AI アセットはそれ自体が後続の AI の振る舞いを決めるため、構成や書き方がぶれるとワークフロー全体の挙動がぶれる。またアセットは通常のコードと違い、効果の検証（eval）が高コストで、機械的に検証できる部分（スクリプト・フック）とできない部分（文章の指示）が混ざる。
- **目的**: どのアセットも仕様書と 1:1 に対応した標準の形で作られ、機械的に検証できる部分はテストで守られ、検証できない部分は eval の定義として残る状態を作る。
- **スコープ**:
  - 含む: アセットの種類と置き場所・命名の判断、スキルの標準構成（本文・assets・scripts）、仕様書との対応、機械テストの実施、eval 定義の作成、settings.json の変更の作法
  - 含まない: アセットの要件・仕様の作成（AI アセット設計のタスク）、eval の実行（人間の明示的な依頼時のみ）、テンプレートや提供コマンドの中身の設計（各仕様書）

---

## ユーザーストーリー

**[As a]** AI アセットを保守する開発者として、

**[I want]** どのアセットも仕様書どおりの標準の形で作られ、スクリプトとフックはテストで守られ、指示文の効果は eval 定義として検証可能な形で残ってほしい。

**[So that]** アセットの変更がワークフローを壊していないかを機械的に確かめられ、壊れたときに仕様から差分を特定できるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When アセットを作るとき、Shall スキルは対応する仕様書を読み、仕様に書かれた構成・名前・配置に正確に従わなければならない（仕様に無い構造を追加で発明しない）。
- When スキルを作るとき、Shall 3 層（ワークフロー `00-workflow-*` / タスク `10-task-*` / 共通ステップ `20-common-step-*`）のどれに属するかを役割から判断して命名し、本文・テンプレート（`assets/`）・スクリプト（`scripts/`）の標準構成で置かなければならない。
- When スクリプト・フックなど機械的に実行できるものを作ったとき、Shall テスト（正常系・境界・異常系）を書いて実行し、結果を作業ログに残さなければならない。
- When スキル・ルールなど指示文の効果が機械的に検証できないものを作ったとき、Shall eval の定義（何を比較し何をもって効果ありとするか）を作成して置き、実行はしてはならない（実行は人間が明示的に依頼したときだけ）。
- When settings.json を変更するとき、Shall 変更する項目だけの最小差分にし、変更前の値と変更理由を作業ログに残さなければならない。
- When 作成・変更を終えたとき、Shall 仕様書との対応（仕様のどの節をどのファイルが実現したか）を確認し、結果を呼び出し元に返さなければならない。
- When アセット（またはその一部）を別の置き場へ移すとき、Shall スキルは移した先にファイルがあり元に無いことに加え、**それを指していた参照がすべて移した先を指していること**を確かめてから完了としなければならない。参照が残ったままの状態を移設の完了としてはならない。
- When 名称やパスを変えて参照を更新するとき、Shall スキルは新しい名前が古い名前を部分文字列として含む場合に偽陽性を除く検索式を使い、期待値を「残るものの件数と場所」で書き、置換先の無い古い名前（廃止・言い換え）は置換の一覧と分けて 1 件ずつ変更後の文を示さなければならない。

### 代替フロー

- If 既存のアセットを変更する場合、Then スキルは既存の構成・記法に合わせて差分を小さくし、仕様の変更を伴わない書き換え（リファクタリング）と仕様の変更を 1 つの変更に混ぜてはならない。
- If 仕様に無い判断が必要になった場合、Then スキルは実装側で決めず、仕様書への追記を呼び出し元に返さなければならない。

### 例外フロー

- If 対応する仕様書が無い・仕様が未決の場合、Then スキルはアセットを作らず、設計が先であることを呼び出し元に返さなければならない。
- If テストが失敗した場合、Then スキルはテストの無効化や期待値の書き換えで通さず、原因を直すか、仕様側の誤りとして呼び出し元に返さなければならない。
- If フックの動作確認で既存のワークフローを壊す振る舞いを見つけた場合、Then スキルはそのまま組み込まず、影響を報告して判断を仰がなければならない。

### 他のスキル・機構との整合

- When アセットのファイルをコミットするとき、Shall `20-common-step-commit-push` に従い、prefix は `ai-asset`（テストを持つスクリプト等の実装コードは除く）を使わなければならない。
- When 各タスクのスキルがアセット作成の手順を説明するとき、Shall not 手順を再掲せず、このスキルを参照しなければならない。

## 前提条件

- 対象アセットの要件定義書・仕様書が存在し、レビュー済みであること
- 作業が AI アセット実装・テストのチケットとして着手されていること

---

## 制約条件

- **技術的制約**: アセットは `.claude/` 配下の規定の場所に置く。テストが実行できる環境で作る
- **ビジネス的制約**: eval の実行は高コストのため人間の明示的な依頼時のみ。普段は定義の作成まで
- **外部的制約**: アセットの構成・中身の正は仕様書。このスキルは作る作法を標準化する

---

## 依存関係

- `10-task-ai-asset-implementation-exec`（呼び出し元）
- `20-common-step-requirement`・`20-common-step-spec`（対応する設計書の形）
- `20-common-step-commit-push`（コミットの作法）

---

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 仕様の節とアセットのファイルの対応が確認され、作業ログから辿れる |
| 検証性 | 機械的に実行できるものはテストが付き、できないものは eval 定義が付く |
| 一貫性 | 同じ種類のアセットは同じ構成・同じ命名で作られる |
| 安全性 | settings.json は最小差分でしか変わらず、変更前の値が記録される |
