# subagent-start-check フック

## 概要

タスクとチケットの実施はサブエージェントに委ねられ、実行者（LLM モデル）は全体計画で合意されてチケットに書かれる。このフックはサブエージェントの起動時点で、起動したモデルと対象チケットの実行者の不一致を検知して伝え、対象チケットの要点をサブエージェントに注入する。着手はサブエージェントの中で提供コマンドにより行われるため、起動の時点でチケットは未着手のことが多い。**1 つの作業ツリーの中ではチケットは 1 枚ずつ順に進む**ため、その作業ツリーの未着手の先頭チケットが次に実施されるチケットと一致し、対象チケットは「その作業ツリーの作業中のチケット、無ければその作業ツリーの未着手の先頭チケット」とする。

- **背景**: 誤ったモデルで起動しても、サブエージェントの完了後に気づいたのではタスクが丸ごと誤ったモデルで実施された後になる（サブエージェント起動の操作の完了は、サブエージェントの終了と同時のため、操作のあとの検知では遅い）。また `session-start` はサブエージェントには何も注入しない設計のため、サブエージェントが自分のチケットの範囲・DoD を知る手段は起動時のプロンプトに依存する。
- **目的**: 起動の瞬間に実行者の不一致が分かって起動し直しの判断が早くでき、サブエージェントが自分のチケットの宣言を知った状態で作業を始められる状態を実現する。
- **スコープ**:
  - 含む: 起動したモデルとチケットの実行者の比較と通知、対象チケットの要点の注入、**対象チケットをどの作業ツリーから採るかの決まり**、記録、緊急停止
  - 含まない: 不一致の拒否（行わない。続けるか起動し直すかは AI が判断する）、宣言した範囲の強制（`workflow-guard`。サブエージェントの中でも同じように働く）、サブエージェント終了時の整合チェック（`subagent-stop-check`）、起動するモデルの決定（全体計画とチケット）、作業ツリーの作成そのもの（`20-common-step-worktree` の提供コマンドと実行基盤の隔離）

## ユーザーストーリー

**[As a]** 全体計画で実行者を合意した開発者として、

**[I want]** 合意と違うモデルでサブエージェントが起動されたら、その場で知らせてほしい。

**[So that]** タスクが誤ったモデルで丸ごと実施される前に、起動し直せるため。

**[As a]** チケットを実施するサブエージェントとして、

**[I want]** 自分のチケットのやってよいことと DoD を作業の最初から知っていたい。

**[So that]** 範囲外に踏み出して拒否されてから気づくのではなく、最初から範囲の中で進められるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 対象チケットを決めるとき、Shall それは 1 つの作業ツリーの中で一意に決まらなければならない（その作業ツリーの作業中のチケット 1 枚、無ければその作業ツリーの未着手の先頭 1 枚）。他の作業ツリーのチケットを対象にしてはならない。
- When 起動したモデルと実行者の不一致を検知するとき、Shall 対象チケットは**起動を指示した側（呼び出し元）の作業ツリー**のものでなければならない（起動の指示はそこで行われ、起動された側の作業ツリーはこの時点ではまだ無いことがある）。
- When 起動されたサブエージェントに要点を注入するとき、Shall 対象チケットは**起動されたサブエージェントが動く作業ツリー**のものでなければならない（サブエージェントが読むのは自分の作業ツリーのチケットであり、注入がそれと食い違うと、範囲外の作業を範囲内だと思わせることになる）。
- When 起動されたサブエージェントが動く作業ツリーを確定できないとき、Shall not フックは呼び出し元の作業ツリーのチケットで代用してはならない。要点を注入せず、要点を注入していないことをサブエージェントに伝えなければならない（代用は「別のチケットの範囲を正しいものとして渡す」ことになり、黙って注入しないより害が大きい）。
- When サブエージェントが起動され、対象チケットに実行者（LLM モデル）が書かれているとき、Shall フックは起動したモデルと比較し、異なる場合はその不一致（チケットの実行者・起動したモデル・対象のチケット）をメインエージェントに伝え、記録に残さなければならない。
- When 不一致を伝えるとき、Shall フックは**サブエージェントが動き出す前にユーザーへ**伝えなければならない（人間が中断して起動し直せるように）。**AI へは遅くともサブエージェントの結果と同時に**伝える。AI に起動前に伝えることは実行基盤の仕組み上できないため、これを求めない。どちらの経路も使えない版では事後の通知だけに縮退してよい。
- When 不一致を伝えるとき、Shall not フックは起動を妨げてはならず、続けるか起動し直すかは AI がチケットの実行者に従って判断しなければならない。
- When 起動したモデルと対象チケットの実行者が一致するとき、対象チケットが無いとき、または実行者の記載が無いとき、Shall not フックは不一致の通知をしてはならない。
- When 起動されたサブエージェントが**タスクの実施者ではない**とき（レビュアー・探索など）、Shall not フックは不一致の通知をしてはならない。チケットの実行者はタスクの実施者に対する指定であり、それ以外の役割には当てはまらないため。
- When タスクの実施者が**完了を待たない形（background）で起動される**とき、Shall フックはその旨と、完了後の検査がメインエージェントに届かないことを伝えなければならない。起動は妨げない。
- When 起動したモデルをフックの入力から特定できないとき、Shall not フックは通知をしてはならない（誤った警告を出さない）。**起動時にモデルを明示せずエージェント定義の既定に任せた場合、モデルは特定できない**（この場合は比較そのものが行われない）。
- When サブエージェントが起動され、対象チケットがあるとき、Shall フックは対象チケットの要点（チケット名・タスクの種類・やってよいこと・DoD）をサブエージェントのコンテキストに注入しなければならない。チケット本文の全文や、その他のファイルの中身は注入しない。
- When 対象チケットが無いとき（チケットが 1 枚も無い）、Shall not フックは何も注入してはならない。
- When フックが通知・注入を行ったとき、Shall その記録（対象のチケット・**対象を採った作業ツリー**・起動したモデル・注入の要約）が残らなければならない。記録と注入内容に機密情報を含めない。
- When 通知するとき、Shall メッセージは他のフックと機械的に区別できる識別子を持たなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは通知も注入も行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If 対象チケットが読めない・実行者の記載が解釈できない場合、Then フックは何も伝えずに通さなければならない（案内側の仕組み。チケットの記載の不正は `workflow-guard` が拒否する）。
- If 作業ツリーを確定できない場合（作業ツリーの一覧を読めない・位置を決められない）、Then フックは起動を止めず、要点を注入せず、**判定していないことを伝えて**記録に残さなければならない（案内側なので拒否はできないが、黙って通すと「対象チケットが無い」と区別がつかない）。
- If フックの入力が解釈できない場合、Then フックは何もせずに通し、サブエージェントの起動を止めてはならない。

## 前提条件

- チケットが実行者（LLM モデル）・やってよいこと・DoD を機構が解釈できる形で持っていること（チケットテンプレート）
- 同じリポジトリに作業ツリーが 2 つ以上ある状態があり得ること。チケットの置き場は作業ツリーごとにあり、1 つの作業ツリーでは同時に 1 枚だけが作業中であること
- Claude Code のフック機構がサブエージェントの起動時にフックを動かし、起動したモデルを入力から特定できること（特定できない場合は通知しない）
- 実行者として指定できるモデルはサブエージェントで選択できるモデルに限ること

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。判定の材料はフックへの入力と作業領域のファイルに限る。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: 実行者の決定と変更は全体計画・未着手チケットの見直しで行い、フックは検知と通知だけを担う
- **外部的制約**: 起動は妨げない（拒否ではなく通知。起動し直しの判断は AI が行う）。起動時のプロンプトに対象のタスク・チケット・文脈のありかを記載するのはオーケストレータ（`00-workflow-issue-mr-driven`・`task-executor`）の責務であり、このフックの注入はその多重防御に徹する（注入が働かない実行形態では起動プロンプトだけが経路になる）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | 起動のたびに働くため、判定と注入は体感できない時間で終える |
| セキュリティ | 記録と注入内容に環境変数の値・トークン・個人情報を含めない |
| 可用性 | 判定できないときは何もせずに通し、サブエージェントの起動を止めない |
| 簡潔性 | 注入はチケットの要点だけに絞り、全文や他のファイルを含めない |
| テスト容易性 | 起動の入力と作業領域の状態を与えて、通知と注入の内容を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
