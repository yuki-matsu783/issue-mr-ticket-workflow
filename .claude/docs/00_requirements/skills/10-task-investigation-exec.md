# 10-task-investigation-exec スキル

## 概要

調査フェーズの実施タスクの要件を定義する。`10-task-investigation-plan` が立てた問い（調査観点）に沿って調査チケットを順に実施し、リポジトリを読むだけで根拠付きの答えを集め、調査結果レポートにまとめる。答えを出すのが仕事であり、設計・実装の決定や修正は行わない（候補と比較軸を並べるところまで）。

- **背景**: 調査は「調べたこと」ではなく「次の計画タスクが判断に使える答え」を残さないと意味がない。また調査のついでにコードを直したり方針を決めたりすると、レビューを経ない決定が紛れ込む。調査を読み取りに限定し、答え・根拠・答えが出なかった理由をレビュー可能な形で残したい。
- **目的**: 調査観点のすべてに「根拠付きの答え」または「答えが出なかった理由」を揃え、選択肢のある問いには候補と比較軸を並べ、次の計画タスクとレビュアーが同じレポートで判断できる状態を作る。
- **スコープ**:
  - 含む: 調査チケットの実施（着手から完了まで）、調査結果レポート（md + HTML）の作成、答えの根拠の残し方、決めないことの線引き、再開・差し戻しの扱い、呼び出し元への結果報告
  - 含まない: 調査観点とチケットの決定（`10-task-investigation-plan`）、調査結果を使った決定（次の計画タスク）、タスクの切れ目の処理と人間レビューの依頼（`00-workflow-issue-mr-driven`）、チケットの状態遷移と宣言範囲の強制の仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** 調査の答えを、根拠と「確かめられなかったこと」込みの 1 つのレポートで確認したい。

**[So that]** 推測が事実として次の計画に流れ込むのを防ぎ、答えの出なかった問いを認識したうえで先に進めるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、調査計画書（観点・対象と方法・成果物の形）と調査チケット群を入力に進めなければならない。
- When 調査チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットが担う観点だけを調べなければならない。
- When 調査するとき、Shall スキルは読み取りだけ（ファイルの閲覧・検索・履歴や既存のテスト結果・記録の読み取り）で行い、ファイルの書き換え・ビルドやテストの実行・リポジトリ外への問い合わせを行ってはならない。
- When 調査結果をまとめるとき、Shall 最初のチケットでレポートを作り、以降のチケットは同じレポートに節を追記し、md と HTML を同期させなければならない（片方だけ更新しない）。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 調査チケットを完了するとき、Shall DoD（観点への答えがレポートにある / 根拠が添えられている / 答えが出なかった問いは理由付きで残課題にある）が満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば完了は拒否される。
- When 1 枚の調査チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の調査チケットに着手しなければならない（タスクの切れ目ではない）。
- When すべての調査チケットが完了したとき、Shall スキルは結果報告（完了したチケットの一覧、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。push・MR 本文の更新・レビュー依頼は呼び出し元が行う。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「すべての観点に答えまたは理由があるか」「根拠が具体的か」「候補と比較軸が次の計画の判断に足りるか」「調査の範囲を超えた決定をしていないか」を挙げ、確かめられなかったことと残課題を明示しなければならない。

### 代替フロー

- If 再開時に調査チケットが作業中でレポートに書きかけの節がある場合、Then スキルは作業ログの「現在地」から続きを進め、レポートの節を二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケット（追加の観点・根拠の補強）としてこのタスクに戻った場合、Then スキルは既存のレポートに Edit で追記・修正し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残さなければならない。
- If issue の種別が AI アセットで、調べる対象が `.claude/` 配下のアセットである場合、Then スキルは読む対象をアセット（スキル・フック・ルール・設定）とその要件・仕様・DDR・過去の作業ログとし、答えと根拠の残し方は同じでなければならない。
- If 調査の途中で観点自体が的外れだと分かった場合、Then スキルは観点を書き換えず、その観点には「答えが出なかった理由」として経緯を書き、代わりに立てるべき問いを「残課題」に提案しなければならない。

### 例外フロー

- If レポートとチケット以外への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、直したい内容を修正案としてレポートに書き、後続のフェーズに回さなければならない。
- If ビルド・テストの実行など読み取りを超える操作が機構に拒否された場合、Then スキルは既存の記録（テスト結果のログ・CI の記録・ドキュメント）を読んで代え、実行が必要なことを「確かめられなかったこと」に理由付きで書かなければならない。
- If 調査計画書が無い、または調査チケットの観点が計画書と対応しない場合、Then スキルは調査を始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。
- If HTML ビューの機械的検査で雛形の痕跡・壊れたリンク・外部依存が見つかった場合、Then スキルは解消してから完了しなければならない。

### 調査結果レポートの内容

- When 調査結果レポートを書くとき、Shall 対象 issue と MR を明記し、機構のレポートの節順（サマリ → 確かめられなかったこと → 実施した内容と結果 → 設計への反映 → 想定と異なった点 → 残課題）に沿って、調査観点ごとに次を書かなければならない: 答え、根拠（ファイル・行・コマンド出力の要約）、結論の性質（良 / 注意 / 問題）とレビューの重み。
- When 答えを書くとき、Shall 根拠を必ず添え、推測を事実のように書いてはならない（確かめられなかったことは推測と明示して「確かめられなかったこと」に置く）。
- When 選択肢が複数ある問いに答えるとき、Shall 候補と比較軸（変更量・リスク・既存パターンとの整合など）を並べるところまでとし、どれにするかを決めてはならない（決定は次の計画タスクと人間レビュー）。
- When 答えが出なかった問いがあるとき、Shall 理由付きで「残課題」に残し、答えが出たことにしてはならない。
- When 調査中に想定外の事実（不具合・技術的負債・ドキュメントと実装の食い違い）を見つけたとき、Shall 直さずに「想定と異なった点」または「残課題」に書き、チケットの作業ログ「スコープ外で見つけたこと」にも残さなければならない。
- When 調査結果レポートを置くとき、Shall 作業領域のレポートの置き場にタスクで 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。HTML は提供されたテンプレートをコピーして Edit で埋め、出力後の機械的検査の結果を作業ログに残す）。

### 調査チケットの扱い

- When 調査チケットが作業中のとき、Shall そのチケットの「やってよいこと」はレポートの置き場・チケットの置き場（状態と作業ログ）・`wip/tmp/` への書き込みと読み取り系の操作に限り、ソースコード・設計文書・`.claude/` 配下を書けてはならない。
- When 調査計画書で並列に進めてよいとされたチケット群を並列で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。並列にしたチケットも同じレポートに集約する（節の担当を分けて衝突させない）。
- When 調査チケットの人間レビュー要否を参照するとき、Shall チケットの記載（計画タスクが全体計画の方針から決めたもの）に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 調査計画書・全体計画書を参照するとき、Shall スキルはそれらを書き換えてはならない。計画の見直しが必要だと分かったときは、レポートの「残課題」と結果報告の「見てほしい点」に書き、判断は人間レビューと次の計画タスクに委ねる。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルは調査結果レポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

---

## 前提条件

- `10-task-investigation-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、調査チケットが未着手にあること
- 調査チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- レポートのテンプレート（md + HTML）と、チケットの着手・完了の提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずにレポートの「残課題」と「見てほしい点」に書く。レポートはタスクで 1 つ
- **ビジネス的制約**: 調査結果から何を採るかの決定は次の計画タスクと人間レビューが行う。スキルは答え・根拠・候補を揃えるまで
- **外部的制約**: 実施タスクだが書き込みはレポートとチケットに限る（調査は読み取り専用）。リポジトリ外への問い合わせを行わない（この禁止は機構では強制されず — 読み取り操作は種類を問わず許可される — スキルの自制による）

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | レポートに issue 番号・MR 番号が残り、観点 → 答え → 根拠（ファイル・行）を辿れる |
| 一貫性 | レポートの節順・視覚語彙・HTML の検査は他の実施タスクのレポートと同じ。作業ログと DoD の型は他の task スキルと同じ |
| 簡潔性 | レポートのサマリは観点ごとに数行で読め、詳細は「実施した内容と結果」に置く |
| 冪等性 | 再開時にレポートの節とチケットを二重に作らない |
