# 10-task-ai-asset-implementation-exec スキル

## 概要

AI アセット実装・テストフェーズの実施タスクの要件を定義する。計画書のステップに従って実装チケットを順に実施し、アセット（スキル・フック・ルール・エージェント・設定）を作成・変更してテストで確かめ、既存アセット・文書の参照を更新する。機構の中核（フック等）は小さく変えて都度テストし、壊れたときは復旧手順で戻す。仕様からの逸脱は作業ログに残す。タスクの最後に AI アセット実装結果レポートをまとめる。

- **背景**: AI アセットの変更は機構自身に効くため、フックの構文エラー 1 つで AI のセッションが止まり得る。またスキルの雛形の痕跡や旧い参照が残ると、機構が古い手順を案内し続ける。変更を小刻みなテストと検査で確かめながら進め、壊れても戻れる形にしたい。
- **目的**: すべてのテスト ID が既存テストの回帰とあわせて通り、雛形の痕跡と旧い参照が検索で 0 件になり、逸脱の記録が揃った状態でアセットの変更をレビューに出す。
- **スコープ**:
  - 含む: 実装チケットの実施（着手から完了まで）、アセットの作成・変更とテスト、都度テストと復旧、参照更新、プレースホルダ・frontmatter の検査、仕様からの逸脱の記録、AI アセット実装結果レポート（md + HTML）の作成、再開・差し戻しの扱い
  - 含まない: 変更対象・テスト方針の決定（`10-task-ai-asset-implementation-plan`）、機構の設計文書の修正（AI アセット設計フェーズ。逸脱として記録して回す）、アプリ本体のコード（実装・テストフェーズ）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** 自己改善する機構を運用する開発者として、

**[I want]** アセットの変更が、テストの結果・雛形と旧参照の検査・仕様からの逸脱の一覧とセットでレビューに出てきてほしい。

**[So that]** 機構が壊れた状態や古い参照が残った状態でマージされるのを防ぎ、機構の変更を安心して受け入れられるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、計画書（変更対象・テスト方針・ステップ・参照更新の一覧・ロックアウト対策）・実装チケット群・機構の設計文書を入力に進めなければならない。
- When 実装チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットのステップだけを実施しなければならない。
- When 実装するとき、Shall スキルは計画のステップ順（設定・定義 → 機構の中核 → そのテスト → スキル・ルール → 参照更新）に進め、テスト ID に対応する機械的に実行できるテスト（フック・スクリプトのテスト）を追加して既存のテストとあわせて通ることを確認し、機械的に検証できないアセット（スキル・ルール・エージェント）は eval（評価シナリオ）の定義を作成・更新しなければならない。
- When eval を扱うとき、Shall スキルは定義の作成・更新までとし、評価の実行（スキルあり / なしで複数回実施して比較する等）を行ってはならない。評価の実行は人間が明示的に依頼したときだけ行う。
- When 機構の中核（フック等。自分のセッションを止め得るもの）を変えるとき、Shall スキルは小さく変えて都度テストを実行し、動かなくなったら計画書の復旧手順（変更前の状態に戻す）で復旧してから原因を作業ログに書かなければならない。機構の強制の無効化による迂回は、ユーザーの明示的な指示があるときだけ行える。
- When スキル・ルール・エージェントを作成・変更するとき、Shall アセット作成の common-step スキルのテンプレートと既存アセットの型に従い、完了前に雛形の痕跡（プレースホルダ）と frontmatter の整合を検査して 0 件にしなければならない。
- When 参照更新を行うとき、Shall 計画書の一覧に従って既存アセット・文書の参照を更新し、旧い名前・手順の残存を検索で確認して 0 件にしなければならない（新たに見つかった参照は一覧に追記して更新する）。
- When 仕様どおりに実装できない・仕様が誤っている・仕様に無い判断をした、のいずれかが起きたとき、Shall スキルはその場で作業ログの「仕様からの逸脱」に内容と理由を書き、機構の設計文書を直してはならない（後続にフィードバック計画があればそこで、無ければ全体まとめの別 issue で扱う）。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し、完了時にまとめて書いてはならない。
- When 実装チケットを完了するとき、Shall DoD（アセットが仕様書のとおり / 機械テストが既存とあわせて通り eval の定義が更新されている / プレースホルダと frontmatter の検査が 0 件 / 参照更新が済み残存 0 件）が実行結果を根拠に満たされ、差分がチケットの「やってよいこと」に収まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 1 枚の実装チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の実装チケットに着手しなければならない（タスクの切れ目ではない）。
- When すべての実装チケットが完了したとき、Shall スキルは AI アセット実装結果レポートを仕上げ、結果報告（完了したチケットの一覧、テスト結果、検査結果、逸脱の一覧、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「機械テストのテスト ID がすべて通り既存テストの回帰が無いか」「eval の定義がテストシナリオと対応しているか（実行は依頼時のみ）」「差分が計画の変更対象に収まっているか。計画外の変更の理由」「雛形の痕跡・旧参照の検査結果」「仕様からの逸脱の一覧」「機構の中核を変えた場合、復旧手順が機能したか（使った場合）」を挙げなければならない。

### 代替フロー

- If 再開時に実装チケットが作業中でアセットが書きかけの場合、Then スキルは作業ログの「現在地」とテストの状態から続きを進め、同じ変更をやり直してはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは指摘をテストで再現できるものはテストから直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残し、レポートを追記・修正しなければならない。
- If 計画に無いアセットを変更する必要が分かった場合、Then スキルは理由を作業ログの「判断と根拠」に書いてから最小限で変更し、結果報告の「見てほしい点」に明示しなければならない。範囲が大きく変わるなら変更せず、計画の追加チケットを結果報告で提案する。

### 例外フロー

- If テストが通らず DoD を満たせない場合、Then スキルはチケットを完了にせず、原因と試したことを作業ログに書き、判断が要ることを結果報告で呼び出し元に返さなければならない（通ったことにしない）。
- If 機構の中核の変更で自分のセッションの操作が止まった場合、Then スキルは復旧手順で変更前に戻すことを最優先し、戻せない状態なら現状と試したことを報告して停止しなければならない（強制の無効化で続行しない）。
- If 機構の設計文書やアプリのコードへの書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、設計文書に関することは「仕様からの逸脱」に、アプリに関することは「スコープ外で見つけたこと」に記録して先へ進まなければならない。
- If 計画書が無い、または実装チケットが計画のステップと対応しない場合、Then スキルは実装を始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。

### AI アセット実装結果レポートの内容

- When すべての実装チケットが完了するとき、Shall AI アセット実装結果レポートが作業領域のレポートの置き場に 1 つあり、同じ名前の HTML ビューが併存しなければならない（Markdown が正文。テンプレートのコピーと Edit で作り、機械的検査の結果を作業ログに残す）。
- When レポートを書くとき、Shall 機構のレポートの節順に沿って次を含めなければならない: 作成・変更したアセットの一覧（仕様書との対応）、テスト結果（機械テストのテスト ID ごとの結果・既存テストの回帰確認・実行方法。eval は作成・更新した定義の一覧と「未実行」であることの明記）、検査結果（雛形の痕跡・旧参照の残存が 0 件であること）、仕様からの逸脱の一覧、想定と異なった点、残課題（テストで確かめられなかったこと・計画外の変更とその理由）。

### AI アセット実装チケットの扱い

- When 実装チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画の変更対象（アセット本体）・レポートの置き場・チケットの置き場・`wip/tmp/` への書き込みと、機構のテストの実行に限り、機構の設計文書・アプリのコードと文書を書けてはならない。
- When チケットを新しいコンテキスト・別モデル（チケットの実行者がタスクのモデルと異なる場合）で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。チケット群を並列に実施してはならない（DDR i0001-23）。
- When 実装チケットの人間レビュー要否を参照するとき、Shall チケットの記載に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 計画書・機構の設計文書を参照するとき、Shall スキルはそれらを書き換えてはならない。見直しが必要だと分かったときは、作業ログとレポートに残して提案する。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルはアセットの差分とレポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

## 前提条件

- `10-task-ai-asset-implementation-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、実装チケットが未着手にあること
- 実装チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 機構のテストがローカルで実行できること（実行方法は計画書に書かれている）
- アセット作成の common-step スキル・レポートのテンプレート（md + HTML）・チケットの提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は作業ログとレポートに残し、人間レビューで確定する。変更中の機構は自分にも効くため、統制との衝突は迂回せず記録して進める
- **ビジネス的制約**: アセットの変更の採否は MR 上の人間レビューが行う。機構の強制の無効化はユーザーの明示的な指示があるときだけ
- **外部的制約**: 機構の設計文書は直さない。リモートへの操作はタスクの切れ目で呼び出し元が行う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | テスト ID で仕様書とテストが結ばれ、参照更新と検査の結果が検索の根拠付きでレポートに残る |
| 安全性 | 機構の中核の変更は小さく変えて都度テストし、復旧手順で常に変更前へ戻れる。壊れた状態でタスクを終えない |
| 一貫性 | レポートの節順・視覚語彙・検査は他の実施タスクと同じ。作業ログと DoD の型は他の task スキルと同じ |
| 冪等性 | 再開時に同じ変更・同じテストを二重に作らない |
