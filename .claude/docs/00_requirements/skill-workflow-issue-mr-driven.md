# workflow-issue-mr-driven スキル

## 概要

ユーザーの依頼を GitHub の issue と draft MR（PR）に紐づけてから実作業に入り、ワークの切れ目ごとに MR 上の人間レビューを挟んで進める、開発作業向けの振り分けスキルの要件を定義する。このスキルは順序と承認ポイントを司るオーケストレータであり、issue / ブランチの操作は task スキルに、各ワークの実施は work スキルに、状態遷移はスクリプトに委ねる。機構全体の要件は `自己改善ワークフロー機構.md` が持つ。

- **背景**: チケット駆動の実作業だけでは「その作業がどの issue に対するもので、どの MR に載るのか」「どこで人間が確認するのか」が決まらない。作業の起点を issue に固定し、issue の確定・ワーク境界・マージ前作業に必ず人間の判断を挟みたい。
- **目的**: 「依頼 → 既存 issue の照合 → 承認 → issue の確定 → feature ブランチと draft MR → 全体計画 → （計画ワーク → レビュー → 実施ワーク → レビュー）× フェーズ → 全体まとめ → レビュー → マージ前作業 → draft 解除 → 停止」の順序を固定し、すべての作業が 1 issue = 1 ブランチ = 1 MR に紐づき、レビュー完了なしに次のワークへ進まない状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md と参照資料）、issue 追記・issue 通知のテンプレート、類似 issue の判定基準、承認ポイントの定義、ワークループの制御（次の work スキルの選択・push・MR 本文更新・レビュー依頼と完了・追加チケットへの差し戻し）、完了処理の順序、再開判定
  - 含まない: MR のマージ（人間が行う）、issue / ブランチ / MR の具体的な操作手順（`task-gh-issue` / `task-gh-feature`）、各ワークの内容（`work-*`）、チケットの権限統制とワーク境界の判定ロジック（フックとスクリプトの仕様）、レビューの自動化、GitLab 対応

---

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼した作業を、既存 issue との照合と自分の承認を経て issue と MR に紐づけ、ワークごとに MR 上でレビューしながら進めてほしい。

**[So that]** 重複した対応や issue に紐づかない変更を防ぎ、AI の作業を段階ごとに確認でき、依頼・合意・作業・成果の経緯を GitHub 上で追えるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When ユーザーから開発作業の依頼を受けたとき、Shall スキルは実作業を始める前に依頼を要約（summary / kind / keywords / acceptance / out_of_scope）し、既存の issue（open を優先、0 件なら closed も）を検索して類似候補を提示しなければならない。
- When 類似する issue が見つかったとき、Shall スキルはその issue で対応するかをユーザーに確認し、承認を得るまで issue の変更・ブランチ作成・実作業を行ってはならない。
- When 既存 issue で対応することが承認されたとき、Shall スキルは今回の依頼内容と受け入れ条件を issue の末尾に追記する案を提示し、承認後に `task-gh-issue` で追記しなければならない（既存の記述は消さない）。
- When 類似する issue が見つからなかったとき、Shall スキルは新しい issue の案（タイトル・種別・概要・詳細・受け入れ条件・スコープ外・優先度）とブランチ名・MR タイトルを提示し、承認後に `task-gh-issue` で作成しなければならない。
- When issue が確定したとき、Shall スキルは `task-gh-feature` で issue 番号を含む feature ブランチ（`feature-<N>-<slug>` / `fix-<N>-<slug>`）と、`Closes #N` を持つ draft MR を作成し、番号と URL を控えなければならない。
- When ブランチと MR が作成されたとき、Shall スキルは issue 番号・MR の URL・受け入れ条件を引き継いで `work-overall-plan` を読み込み、全体計画（フェーズ列）と最初の計画チケットの作成まで進めなければならない。
- When 1 つのワーク（同じ type のチケット群）が完了したとき、Shall スキルは push スクリプトで push し、MR 本文にそのワークの要約を追記し、レビュー観点（差分範囲・見てほしい点・次のワーク）を添えてレビュー依頼スクリプト（`request`）でレビューを依頼し、応答を終えなければならない。
- When レビュー完了の連絡を受けたとき、Shall スキルはレビュー完了スクリプト（`complete`）を実行し、通った場合に返された指摘を提示して対応要否を確認し、対応が必要なものは同じ type の追加チケットとして todo に起こしてから再度ワークループに入らなければならない（完了済みチケットを doing に戻さない）。
- When 指摘が 0 件、または追加チケットのワークもレビューを通ったとき、Shall スキルは境界判定スクリプトの `todo_head_type` から次の work スキル（`work-<phase>-plan` / `work-<phase>-exec` / `work-wrap-up`）を選んで読み込み、todo と doing が空になるまで繰り返さなければならない。
- When 全体まとめのワークがレビューを通ったとき、Shall スキルは MR 本文を統括レポートの要約（変更内容・受け入れ条件との対応・動作確認・残課題）で最終更新し、マージ前作業に進む承認を得なければならない。
- When マージ前作業が承認されたとき、Shall スキルはマージ前作業スクリプトで「wip の片付け → default ブランチとの衝突確認 → 関連 issue へのコメント → draft 解除」を順に実行し、各ステップの記録と再検証を通ったときだけ draft を解除して、マージは行わず停止しなければならない。

### 承認ポイント

- When どの issue で対応するか（既存 / 新規 / 別候補 / 分割）を決めるとき、Shall スキルは `AskUserQuestion` で選択肢を提示し、明示的な承認を得なければならない。
- When issue に書く内容（本文 / 追記）を確定するとき、Shall スキルはブランチ名・MR タイトルも同時に提示し、明示的な承認を得なければならない。
- When 各ワークの完了後にレビューを依頼したとき、Shall スキルは応答を終えて人間のレビューを待ち、`AskUserQuestion` でセッションを塞いではならない。取得した指摘への対応要否の確認には `AskUserQuestion` を使ってよい。
- When 全体まとめ完了後にマージ前作業へ進むとき、Shall スキルは明示的な承認を得なければならない。承認後は draft 解除まで改めて確認しない。
- When default ブランチとの衝突を解消するとき、Shall スキルは衝突ファイルと解消方針を提示して承認を得てから `git merge` で取り込み、`git rebase` や片側丸ごと採用を使ってはならない。
- When 関連 issue にコメントを投稿するとき、Shall スキルは投稿先の issue 番号と本文そのものを提示して承認を得なければならない。
- When ヘッドレス実行で承認が得られないとき、Shall スキルは承認が必要な内容（衝突・通知本文など）を報告してセッションを終え、次回セッションの再開判定から続けなければならない。

### 他のスキル・スクリプト・フックとの整合

- When issue を検索・作成・追記するとき、Shall スキルは自前で `gh issue` を組み立てず `task-gh-issue` の手順に従わなければならない。
- When ブランチと MR を作成・更新するとき、Shall スキルは `task-gh-feature` の手順に従わなければならない。
- When コミット・push・チケット移動・レビュー状態・マージ前作業を進めるとき、Shall スキルは専用スクリプト（とそれを使う task スキル）経由でのみ行い、`git` のコミット・push の直接実行、状態ファイルの直接編集、`gh pr ready` の直接実行を行ってはならない（フックが拒否する）。
- When `wip/10_tickets/10_doing/` にチケットがあるとき、Shall not スキルは `gh` コマンドや push を実行してはならない（GitHub 操作はワーク境界で doing が空のときにのみ行う）。
- When 次に読み込む work スキルを選ぶとき、Shall スキルは目視で type を比べず境界判定スクリプトの出力に従い、対応するスキルが無ければ不整合として報告して停止しなければならない。
- When ワークループの実施中であるとき、Shall not スキルはチケット運用の手順（着手・完了・作業ログ・DoD）を再掲せず、`work-ticket-driven` の手順を参照しなければならない。

### アルタナティブフロー（代替経路）

- If 現在のブランチに open な MR があり、`wip/10_tickets/` にチケット（todo / doing / done）がある場合、Then スキルは issue の照合からやり直さず、境界判定スクリプトの `at_boundary` と `review_state` で現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み）を確定して再開しなければならない。`requested` のときはレビュー完了の連絡がない限り `complete` を実行せず応答を終える。
- If 類似候補が closed な issue のみである場合、Then スキルは再オープンして対応するか新規に作るかをユーザーに確認しなければならない。
- If 依頼が複数の独立した問題を含む場合、Then スキルは issue を分割する案を提示し、ユーザーが選んだ 1 つから着手しなければならない（1 issue = 1 MR）。
- If ユーザーが issue 番号や URL を指定した場合、Then スキルは検索を省略し「既存 issue で対応」として扱ってよい。
- If 依頼が `workflow-quick-request` の振り返り、または全体まとめの改善候補から「issue を作って進める」と合意して切り替えて来た場合、Then スキルは引き継がれた summary / acceptance / kind / フェーズ列をそのまま用い、依頼の要約に関する質問を省略してよい。ただし未コミットの変更の確認と承認は省略しない。
- If issue を起票しただけで着手の指示が無い場合、Then スキルはブランチ作成に進まず、着手はユーザーの明示的な指示を待たなければならない。
- If 小さな依頼でワーク境界の往復が過剰な場合、Then スキルは全体計画でのフェーズ省略（理由付き）と、レビュー依頼への「approve のみで可」の添え書きで対処し、type をまとめてはならない。
- If `gh` CLI が使えない環境の場合、Then スキルはスクリプトの外部委任モード（MCP ツールで GitHub 操作を代行し結果を引数で渡す）を使い、WebFetch / curl へ落としてはならない。

### 例外フロー（エラーケース）

- If `gh` が未インストール・未認証である場合、Then スキルは導入・認証を案内し、作業を開始してはならない。
- If `origin` が GitHub でない場合、Then スキルは対象外として報告して停止しなければならない。
- If 作業ツリーに未コミットの変更がある場合、Then スキルはブランチ作成前に変更内容を示し、扱い（コミット / stash / 破棄 / 中断）をユーザーに確認しなければならない（自分で判断しない）。
- If MR 作成が「差分なし」で失敗した場合、Then スキルは空コミットを作成して再試行しなければならない。
- If issue の作成・追記や MR の作成に失敗した場合、Then スキルは失敗したコマンドと出力を報告し、別の手段で代替してはならない。
- If レビュー依頼（`request`）が前提未充足（未コミット / 未 push / MR なし / 境界でない / 既に依頼済み）で止まった場合、Then スキルは未充足を解消して再実行し、境界でなければ次のチケットに着手しなければならない。
- If レビュー完了（`complete`）が `CHANGES_REQUESTED` または未返信スレッドで止まった場合、Then スキルは同じ type の追加チケットで対応し、返信スクリプトでスレッドに返信してから再実行しなければならない。状態ファイルを直して通そうとしない。
- If マージ前作業の前提（todo / doing が空・最後のワークが `completed`・未コミット無し・衝突無し・通知先あり）が満たせない場合、Then スキルはスクリプトが返す未充足を報告し、該当する手順（ワークループ / レビュー / 衝突解消 / 通知先の指定）へ戻らなければならない。
- If 承認①②③⑤⑥で却下された場合、Then スキルはその段階に留まり、先の段階へ進んではならない。

## 前提条件

- 対象プロジェクトが GitHub 上の Git リポジトリで、`origin` が GitHub を指していること
- `gh` CLI がインストール・認証済みで、issue と MR の作成権限があること
- チケット駆動の仕組み（`work-*` スキル、境界判定・レビュー・マージ前作業のスクリプト、権限統制フック、テンプレート）が導入済みであること
- `workflow-quick-request` と対になる振り分けとして、`CLAUDE.md`「作業の振り分け」から呼ばれること

---

## 制約条件

- **技術的制約**: GitHub（`gh` CLI）を前提とする。用語として「MR」は PR と同義に扱う。1 セッションは 1 つの MR だけを扱う
- **ビジネス的制約**: MR のマージ・issue の内容・レビュー完了の判断は人間が行う。AI は draft 解除で止まる
- **外部的制約**: 権限統制フックとスクリプトの統制に従い、スキル側に迂回経路を書かない。フック側に GitHub 操作の許可を追加しない

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | issue 検索は `--limit` を付け、候補提示は上位 10 件程度に絞る |
| セキュリティ | issue / MR の本文に環境変数の値・トークン・個人情報を書かない。`--body-file` の一時ファイルはリポジトリ外に置く |
| 可用性 | GitHub に接続できない場合でも、依頼の要約と issue 案の作成（ローカル）までは進められる |
| 追跡性 | ブランチ名・MR 本文・全体計画・統括レポート・issue コメントのすべてに issue 番号を残す |
| 冪等性 | 再開時に issue 照合・ブランチ作成をやり直さず、現在地から続けられる |
| 可読性 | SKILL.md は順序と承認ポイントに集中し、委譲先の手順を再掲しない。読むタイミングごとの詳細は `references/` に分割する |
