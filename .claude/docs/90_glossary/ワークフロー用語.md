# ワークフロー用語

### 振り分け

依頼ごとに、開発作業（`00-workflow-issue-mr-driven`）か[軽作業](#軽作業)（`00-workflow-quick-request`）のどちらのワークフロースキルで進めるかを決めて読み込むこと。機構はこの読み込みを作業の入口として扱う。

### タスク

issue の作業を分割する単位で、同じ種類の[チケット](#チケット)群として実現され、計画と実施を対にして進める。タスクの完了地点が[タスクの切れ目](#タスクの切れ目)になる。

### タスクの切れ目

1 つのタスクが完了し、次のタスクへ進む前の境界。push・MR 本文の更新・人間レビューなど、タスクの中では行わない境界処理をここで行う。[並列実施](#並列実施)を行ったときは、各[作業ツリー](#作業ツリー)の成果を[本流](#本流)へ[合流](#合流)する単位でもある（どの作業ツリーにも作業中の[チケット](#チケット)が無い時点なので、合流の前提が揃う）。

### フェーズ列

1 つの issue で実施するタスクの並び。issue の種別ごとのテンプレートを土台に、[全体計画](#全体計画)でユーザーと合意して確定する。

### 全体計画

開発作業の最初に行うタスク。issue の確定、feature ブランチと draft MR の作成、フェーズ列の選択、各チケットの[実行者](#実行者)と[人間レビュー要否](#人間レビュー要否)の合意までを担う。メインエージェントが行う。

### フィードバック計画

実装より後に置く振り返りのタスク。[作業ログ](#作業ログ)・レビュー指摘・拒否の記録から AI アセットへ反映すべき内容を洗い出し、この MR で対応するか別 issue に起票するかを決める。メインエージェントが行う。

### 全体まとめ

issue の最後に行うタスク。統括レポートの作成、MR 本文の最終化、[作業領域](#作業領域)の片付け、draft 解除までを担い、マージは行わない。メインエージェントが行う。

### チケット

作業の最小単位。タスクの種類・状態・先行チケット・実行者・人間レビュー要否・[やってよいこと](#やってよいこと)・目的・[DoD](#dod)・[作業ログ](#作業ログ)を持つファイルで、[提供コマンド](#提供コマンド)により未着手 → 作業中 → 完了と進む。

### やってよいこと

チケットが宣言する、書き込んでよい範囲と実行してよい操作の分類。機構が書き込み・操作を許可するか拒否するかを判定するときの入力になり、上限はタスクの種類ごとにユーザーが管理する設定が定める。

### 承認単位

宣言にも設定にも無いパスへの書き込みを人間が承認したとき、以降は同じ承認で書けると見なす範囲。原則は書こうとしたファイルの親ディレクトリ。ファイル単位でしか承認できない場所（設定で個別に指定したファイルと、リポジトリ直下のファイル）はファイルそのものが単位になる。リポジトリ全体を 1 つの承認単位にすることはできない。

### 実行者

チケットを担当する LLM モデル。チケットに明記され、[全体計画](#全体計画)で合意する。既定値は[タスク別の既定判断基準](#タスク別の既定判断基準)が持つ。

### 人間レビュー要否

そのチケットの成果を[タスクの切れ目](#タスクの切れ目)で人間が MR 上でレビューするかどうかの宣言。理由とセットでチケットに明記され、既定値は[タスク別の既定判断基準](#タスク別の既定判断基準)が持つ。

### タスク別の既定判断基準

タスクの種類ごとの既定の実行者・人間レビュー要否とその理由・調整してよい条件をまとめた規約。[全体計画](#全体計画)が各チケットの実行者とレビュー要否を提案するときの基準で、プロジェクトごとに置き換えられる。

### DoD

チケットの完了条件。何をもって完了とするかの項目群で、チケット完了時の検査対象になる。

### 作業ログ

チケットに書き込む固定見出しの作業記録。現在地・判断と根拠・拒否や確認の記録・AI アセットに反映すべき内容などを持ち、[フィードバック計画](#フィードバック計画)の集約とセッション再開の入力になる。

### 提供コマンド

機構が用意する、状態の変更を担うスクリプト群。チケットの状態遷移・commit / push・レビュー依頼と完了・マージ前の片付けはこれを通して行い、AI の自己申告では状態が進まない。**それを使うスキルの `scripts/` 配下に置く**（`.claude/skills/<スキル名>/scripts/<コマンド名>.sh`）。機構がイベントで呼ぶフック（`.claude/hooks/`）とは呼ばれ方が違うので置き場で分ける（DDR `i0010-01`）。起動はリポジトリルート相対の表記で行い、絶対パスや `./` 付きでは提供コマンドとして識別されない。

### 敵対的レビュー

経緯を知らされない読み取り専用のレビュアー（サブエージェント）が、[成果物ルール](./ドキュメント体系用語.md#成果物ルール)の[観点章](./ドキュメント体系用語.md#観点章)に沿って欠陥を探すレビュー。人間レビューの前段として使う。レビュアーは対象を作った実行者と別のモデルで動く（同じモデルは同じ癖で同じ見落としをするため）。

### 軽作業

issue と [MR](#mr) を作らずに、範囲を宣言してから進める作業。質問・調査・振る舞いを変えない小さな修正が該当し、`00-workflow-quick-request` で進める。

### 単独実行モード

issue と MR を作らず、チケット駆動だけを使う実行形態。タスクの切れ目の承認は MR ではなくチャット上の確認で取る。

### 外部委任モード

`glab` / `gh` CLI が使えない環境で、リモート操作（issue / MR の操作）を MCP ツールに代行させる実行形態。証跡の強度は CLI 実行時より劣る。

### MR

マージリクエスト。機構の文書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

### 作業領域

チケット・計画書・レポート・進行状態など、ブランチ限りの作業ファイルを置く `wip/` 配下の領域。マージ前に片付けられ、main には残らない。

### 作業ツリー

1 つのリポジトリに対して作られる、独立した作業ディレクトリ（git worktree）。それぞれが自分の[作業領域](#作業領域)と自分のブランチを持ち、同時に作業中の[チケット](#チケット)は 1 つの作業ツリーにつき 1 枚を上限とする。[並列実施](#並列実施)の単位であり、機構の判定（宣言した範囲の強制・差分の基準点・実行者の照合）はどの作業ツリーで操作が行われたかで一意に決まる。

- 別名: worktree
- 禁止表記: ワークツリー、作業木

### 本流

その clone で最初から使われているチェックアウト（`git worktree` で後から足したものではないほう）。[共有ルート](#共有ルート)と同じディレクトリを指し、チケットの新規作成・push・[合流](#合流)はここでだけ行う。

- 禁止表記: メインツリー、main worktree

### 共有ルート

1 つの issue・1 つのブランチ・1 つの [MR](#mr) に属する進行状態（レビューの状態・MR の記録・ロック・使用量の集計）を集める根。[作業ツリー](#作業ツリー)を複数使っても 1 つだけ存在し、[本流](#本流)と同じディレクトリを指す。作業ツリーごとに分かれるのは[作業領域](#作業領域)と判定・実行の記録で、進行状態は分かれない。

### 合流

[作業ツリー](#作業ツリー)で積んだ成果（そのブランチのコミット）を[本流](#本流)のブランチへ取り込むこと。[タスクの切れ目](#タスクの切れ目)に[提供コマンド](#提供コマンド)経由で行い、自動で解けない衝突が出たときは中断して人に返す。合流したかどうかとその結果は記録に残る。

- 別名: マージ（ただし MR のマージとは別。issue の成果を default ブランチへ入れる操作は人間が行う「マージ」で、合流はローカルの取り込みを指す）

### 並列実施

1 つの issue の中で、同じフェーズの依存しない[チケット](#チケット)を複数の[作業ツリー](#作業ツリー)で同時に進めること。既定は行わない。行っても issue・ブランチ・[MR](#mr) の数は増えず、成果は[タスクの切れ目](#タスクの切れ目)で 1 つの feature ブランチへ[合流](#合流)する。

### 並列区間

[並列実施](#並列実施)を始めてから、成果を[合流](#合流)し終えるまでの区間。この区間では 1 つのレポートを複数の[作業ツリー](#作業ツリー)が同時に書くため、書き方に制約（自分の節だけを追記し、共通部の更新は合流する側が 1 回だけ行う）が掛かる。

### wip/tmp

一時ファイル（issue / MR に投稿する本文、その場限りのスクリプト、中間結果）の置き場。コミット対象外で、ワークスペース外のパス（OS の一時ディレクトリなど）の代わりに使う。
