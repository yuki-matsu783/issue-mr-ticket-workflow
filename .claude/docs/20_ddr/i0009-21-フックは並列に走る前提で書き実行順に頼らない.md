# i0009-21. フックは並列に走る前提で書き、実行順に頼らない

## 背景

§1 の登録表は `順` 列を「同じイベント内での `settings.json` の配列順（**実行順**）」と定義し、次の 3 つがその前提の上に立っていた。

- §1「1 つでも deny を返せば拒否される。…**先に拒否したフックが理由を返す**。順序は**安価で範囲の広い判定 → 高価で狭い判定**」
- HK-T01「`settings.json` の登録が §1 の表と一致する（イベント・matcher・**順序**）」
- 各フック仕様の呼出条件「state-guard の後、block-direct-git の前」「entry → state-guard → block-* の後、最後に実行」など 5 本

設計ワークの境界レビュー（付録 A の R1）で、公式に次の記述があることが確認された。

> **All matching hooks run in parallel.** If you define the same handler in more than one settings file, it runs once.

同じイベントに一致するフックはすべて同時に起動する。配列順は実行順ではない。

## 決定

- `順` 列を **`位置`**（`settings.json` の**配列上の位置**であって実行順ではない）に改める
- §1 の「先に拒否したフックが理由を返す」を「**複数が同時に deny を返し得る。どの理由が AI に見えるかは不定**として扱い、**各フックの拒否理由は単独で読んで成立する文面**にする（他のフックが先に判定した前提を書かない）」に変える
- 「安価な判定 → 高価な判定」という順序による絞り込みは成立しないので削り、**各フックが単独で軽いことだけが性能を決める**と書く
- 各フック仕様（`block-chmod` / `block-direct-git` / `workflow-state-guard` / `workflow-guard` / `post-push-usage-report`）の「〜の後、〜の前」を「共通仕様 §1 の N 行目。位置であって実行順ではない」に書き換える
- HK-T01 の照合対象を「イベント・matcher・フック・**配列上の位置**」と書き直す（位置は `settings.json` の記述として意味があるので照合対象には残す）

## 理由

- 事実と食い違う前提を残すと、実装者が「先に走るフックが弾くから、こちらは判定を省ける」という最適化を入れてしまう。並列では省けない
- 拒否理由の文面の書き方が変わる。順序を前提にすると「entry を通っているので宣言はある」といった前提を理由に書けるが、並列ではその前提が成り立たない
- 性能の見積もりも変わる。5 本が**同時に**起動するので、1 本あたりの fork がそのまま 5 倍のプロセスになる（`i0009-22` のホットパスの fork 上限はこれを踏まえた）
- 位置そのものは `settings.json` に実在する情報なので、HK-T01 の照合からは外さない（外すと登録の並びが自由になり、表との突合が緩む）

## 却下した案

- **順序に依存する設計を維持し、1 つのフックにまとめて内部で順に判定する**: 11 本を 1 本に統合することになり、緊急停止（`WORKFLOW_<NAME>_ENFORCE=0`）の粒度・テストの粒度・要件との 1:1:1 がすべて崩れる
- **HK-T01 から位置の照合を外す**: 位置は実在する情報で、表と `settings.json` の突合の手がかりとして有効。意味づけを直せば足りる
- **拒否理由の重複を「最初に返ったものだけ表示される」と仮定して放置する**: 公式に順序の保証が無い以上、仮定を書けない

## 影響

- `10_spec/フック共通仕様.md` §1（`位置` 列の定義・deny の重なり・順序による絞り込みの削除）・§11（HK-T01）
- `10_spec/hooks/20-PreToolUse/block-chmod.md` / `block-direct-git.md` / `workflow-state-guard.md` / `workflow-guard.md`、`22-PostToolUse/post-push-usage-report.md` の呼出条件
- 関連: `i0009-22`（ホットパスの fork 上限）・`i0009-23`（並行書き込み）・`i0009-24`（push 検知のレース）はいずれも並列実行から派生した決定
