# 10-task-ai-asset-design-exec スキル

## 概要

AI アセット設計フェーズの実施タスクの要件を定義する。AI アセット設計計画書の骨子と結論方針に従って設計チケットを順に実施し、機構の設計文書の置き場（`.claude/docs/`）に要件定義書・仕様書・用語辞書を作成・更新し、決定の経緯を DDR に残す。アセット本体（スキル・フック・ルール・エージェント・設定）は触らない。タスクの最後に AI アセット設計結果レポートをまとめる。

- **背景**: 機構の振る舞いの正は設計文書にあり、アセット本体から書き始めると「どう動くべきか」の合意より先に「どう動くか」が決まってしまう。要件・仕様を先に固め、実装・テストフェーズがそれを落とすだけの状態にしたい。
- **目的**: 受け入れ条件（または改善候補）を漏れなく受け入れ基準とテスト ID 付きのテストシナリオに落とし、判断の結論を根拠付きで正史に、経緯を DDR に残し、実装・テストフェーズが判断に使える文書と、レビュアーが読むレポートを揃える。
- **スコープ**:
  - 含む: 設計チケットの実施（着手から完了まで）、要件定義書・仕様書・用語辞書の作成・更新、横断文書との整合、DDR の作成、AI アセット設計結果レポート（md + HTML）の作成、再開・差し戻しの扱い、呼び出し元への結果報告
  - 含まない: 文書の一覧と骨子の決定（`10-task-ai-asset-design-plan`）、文書の書式そのもの（設計書作成の common-step スキルとドキュメント規約が正）、アセット本体の変更（AI アセット実装・テストフェーズ）、アプリ本体の設計文書（設計フェーズ）、タスクの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** 自己改善する機構を運用する開発者として、

**[I want]** アセットが変更される前に、その変更の要件・仕様・ヘッドレス時の帰結が文書としてレビューできる状態になっていてほしい。

**[So that]** 機構の変更を文書で合意してから実装に進め、後から「なぜこうなっているか」を要件・仕様・DDR で追えるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このタスクに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、AI アセット設計計画書（結論方針・一覧・骨子）・調査結果レポートまたはフィードバック計画の決定・既存の機構の設計文書を入力に進めなければならない。
- When 設計チケットに着手するとき、Shall スキルは提供コマンドで 1 枚ずつ未着手 → 作業中に進め、そのチケットが担う文書だけを書かなければならない。
- When 要件定義書を書くとき、Shall 受け入れ条件（または改善候補）を EARS 形式の受け入れ基準に落とし、受け入れ基準の節順（メインフロー → 代替フロー → 例外フロー → その他の細かい記述）と外部から見た振る舞いで書き、内部構造（スクリプト名・判定順・スキーマ）を書いてはならない（それらは仕様書へ）。
- When 仕様書を書くとき、Shall 入出力・判定・エラー・テストシナリオを実装可能な粒度で書き、テストシナリオにはテスト ID を振ってシナリオごとに「機械的に実行できるテストで確かめる」か「eval（評価シナリオ）で確かめる」かを区別し、人間の確認を伴う設計にはヘッドレス実行時の挙動と代替経路を書かなければならない。
- When 文書を作成・更新するとき、Shall 1:1:1 の原則（アセット名と同名・種類ごとのサブディレクトリ）と機構のドキュメント規約（frontmatter・正史のみ）に従い、本文はその時点の正史だけになるよう書き、経緯（採らなかった案と理由）は DDR に残さなければならない。
- When 横断文書・用語辞書に影響する変更をしたとき、Shall 該当箇所を整合するよう更新し、用語の定義を二重に持たせてはならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し、完了時にまとめて書いてはならない。
- When 設計チケットを完了するとき、Shall そのチケットの DoD（文書がテンプレートに沿いプレースホルダが無い / 受け入れ条件がテスト ID 付きのシナリオに落ちている / 横断文書・用語辞書が整合 / 経緯が DDR にある / 確認を伴う設計はヘッドレス時の挙動がある）が根拠付きで満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 1 枚の設計チケットが完了し同じ種類のチケットが未着手に残っているとき、Shall スキルは次の設計チケットに着手しなければならない（タスクの切れ目ではない）。
- When すべての設計チケットが完了したとき、Shall スキルは AI アセット設計結果レポートを仕上げ、結果報告（完了したチケットの一覧、作成・更新した文書と DDR の一覧、レポートの場所とサマリ、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「受け入れ条件（または改善候補）が受け入れ基準・テストシナリオに漏れなく落ちているか」「要件が外部の振る舞いで書かれ内部構造が仕様に分離されているか」「ヘッドレス時の挙動」「既存の文書・用語との整合」を挙げなければならない。

### 代替フロー

- If 再開時に設計チケットが作業中で文書が書きかけの場合、Then スキルは作業ログの「現在地」から続きを進め、文書・DDR・レポートの節を二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのタスクに戻った場合、Then スキルは文書と DDR を直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残し、レポートを追記・修正しなければならない。
- If 計画書の骨子どおりに書けない（前提が崩れた）場合、Then スキルは推測で骨子を変えず、書ける範囲を書いたうえで「未解決事項」と代わりの案をレポートに残し、判断を人間レビューに委ねなければならない。

### 例外フロー

- If アセット本体（スキル・フック・ルール・エージェント・設定）への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、その内容を仕様書に書いて実装・テストフェーズに回さなければならない（設計 → 実装の順を崩さない）。
- If 計画書が無い、または設計チケットが計画書の一覧と対応しない場合、Then スキルは書き始めず、状態の不整合として結果報告に書いて呼び出し元に戻さなければならない。
- If HTML ビューの機械的検査、またはプレースホルダの検査で問題が見つかった場合、Then スキルは解消してから完了しなければならない。

### AI アセット設計結果レポートの内容

- When すべての設計チケットが完了するとき、Shall AI アセット設計結果レポートが作業領域のレポートの置き場に 1 つあり、同じ名前の HTML ビューが併存しなければならない（Markdown が正文。テンプレートのコピーと Edit で作り、機械的検査の結果を作業ログに残す）。
- When レポートを書くとき、Shall 機構のレポートの節順に沿って次を含めなければならない: 作成・更新した文書と DDR の一覧、判断の結論とその根拠の要約、受け入れ条件（または改善候補）との対応表、想定と異なった点、残課題（骨子どおりに書けなかった点・未解決事項）。

### AI アセット設計チケットの扱い

- When 設計チケットが作業中のとき、Shall そのチケットの「やってよいこと」は機構の設計文書の置き場（要件・仕様・用語辞書・DDR）・レポートの置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、アセット本体・アプリのコードと文書を書けてはならない。
- When チケットを新しいコンテキスト・別モデル（チケットの実行者がタスクのモデルと異なる場合）で実施したいとき、Shall スキルはチケット単位のサブエージェントの起動を呼び出し元に要求し、自分で入れ子に起動してはならない。チケット群を並列に実施してはならない（DDR i0001-23）。
- When 設計チケットの人間レビュー要否を参照するとき、Shall チケットの記載に従い、実施側で変えてはならない。

### 他のスキル・機構との整合

- When 計画書・調査結果・フィードバック計画書を参照するとき、Shall スキルはそれらを書き換えてはならない。骨子の見直しが必要なら「未解決事項」に残して提案する。
- When 人間レビューの前に敵対的レビューを行うと決められているとき、Shall スキルは文書とレポートをその対象にでき、指摘には人間の指摘と同じ扱いで対応しなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。

## 前提条件

- `10-task-ai-asset-design-plan` の計画が人間レビューを終え（レビュー不要の方針ならその処理を経て）、設計チケットが未着手にあること
- 設計チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 設計書作成の common-step スキル・機構のドキュメント規約・レポートのテンプレート（md + HTML）・チケットの提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない（結論は計画書・調査結果・受け入れ条件から導く）。判断に迷う点は「未解決事項」に残す
- **ビジネス的制約**: 機構の変更の採否は MR 上の人間レビューで確定する。スキルは根拠付きの正史と DDR を揃えるまで
- **外部的制約**: 書くのは設計文書であり、アセット本体は書かない。正史のみ・経緯は DDR という機構のドキュメント体系に従う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 受け入れ条件（または改善候補）→ 受け入れ基準 → テストシナリオ（テスト ID）→ 実装・テストフェーズの DoD と辿れ、経緯は DDR から辿れる |
| 一貫性 | 文書は 1:1:1 の原則・テンプレート・既存文書の用語に合わせる。レポートの節順・視覚語彙・検査は他の実施タスクと同じ |
| 簡潔性 | 文書は実装が判断に使う粒度までとし、アセットの本文（スキルの手順の文面等）を先取りしない |
| 冪等性 | 再開時に文書・DDR・レポートを二重に作らない |
