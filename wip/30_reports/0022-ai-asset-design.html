  2. 2

    web は curl / wget を実行分類として強制する ✕問題 根拠: 境界レビュー S3、lib/scope.sh:29・workflow-guard.md:55

    i0009-12 は「WebFetch だけを止めても抜け道が残る（Bash の curl まで止めるのは過剰）」を理由の 1 つに挙げていた。実体はその逆で、curl / wget は _SC_READ_ONLY_CMDS に無く、制御方式 6 の末尾で既定拒否（WF204）になる。しかも curl は decisions.jsonl に残り、WebFetch は matcher 外で記録すら残らない。記録が残る側だけが塞がれ、記録が残らない側が素通りする倒錯だった。決定: curl / wget を scope_classify の web に分類し、allow.ops と types[t].ops の両方にあれば許可・無ければ WF204。ただし出力先を持つ形（curl -o / -O / --output / --remote-name、wget の既定と -O <file>）は先に書き込みとして判定し、出力先が wip/tmp/** / logs/** 以外なら WF205。WebFetch / WebSearch は i0009-12 のとおり強制しない。

    実測への依存: あり（オプションの列挙の網羅性・調査の実務を止めないか）

    根拠を見る（読んだ箇所と出力） 
    lib/scope.sh:29   _SC_READ_ONLY_CMDS に curl / wget は無い
workflow-guard.md:55  上記のいずれにも該当しない → deny WF204（既定拒否）
→ curl は「抜け道」ではなく既に塞がれている

食い違っていた記述 6 か所:
  i0009-12 の理由（抜け道が残る）・却下した案
  §8「web を宣言したときだけ通る」・§13 の緩和の行
  要件 制約条件（自制の列挙）
  i0009-19 D5 の理由（上限に足しても振る舞いは変わらない）

決定後の判定順: 出力先の書き込み判定 → web の宣言判定

  curl -o wip/tmp/a.md URL  許可

    打ち切りの fail-open に権限設定と事後ゲートを採らない ◎良 根拠: 境界レビュー S4、hooks.md:1744・:867

    i0009-11 は打ち切りを「塞げない唯一の穴」として速さで守ると決めたが、却下した案が機構の外側の手段を検討していなかった。公式には permissions.deny（フックの結果に関係なく評価される）と PostToolBatch の終了 2（agentic loop を止める）がある。しかも要件の制約条件は既に「権限設定は多重防御として併用してよい」と書いており、例外フローの「この経路は塞げないため」と整合していなかった。決定: どちらも機構の決定には含めない。permissions.deny は (1) .claude/settings.json がユーザーの持ち物で機構が書き換える対象でない、(2) 複合コマンドを止められないので「止まったつもりで止まっていない」を作る。PostToolBatch は取り返しがつかない操作は既に実行された後で「実行前に止める」を満たさない。例外フローを「機構の中にこの経路を塞ぐ手段は無い」に直し、外側の多重防御は併用してよいと書いた。

    実測への依存: 一部あり（permissions.deny が打ち切りの影響を受けないことは公式の記述のみ）
