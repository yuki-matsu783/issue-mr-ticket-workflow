# i0001-02. チケットの権限宣言は type 定義を上限とし宣言で広げられない

## 背景

本機構では doing チケットの frontmatter に「そのタスクでやってよいこと」（書き込めるパス・実行できるコマンドの分類）を書き、フックが違反を exit 2 で拒否する。チケットの frontmatter は AI 自身が書くため、そこに書いたものをそのまま信頼すると、AI が自分で権限を広げられる。

## 決定

- チケットの frontmatter は許可範囲を**宣言**する（`allowed_paths` と、コマンド分類の宣言）。フックは宣言に無いパス・コマンドを拒否する
- 各 type の上限（許可パス・禁止パス・コマンド分類）は、ユーザーが管理する設定ファイル（`workflow-types.json` 相当）が定める
- 判定順は「type の deny → type の ask → type の allow → global の deny → global の ask → チケットの宣言 → global の allow → セッション記憶 → 未記載は警告付き ask」。**チケットの宣言は deny のあとに評価される**ため、deny を宣言で覆せない
- doing 中のチケットの `type` と宣言を書き換える操作はフックが拒否する

## 理由

- 「設定ファイルはユーザーが管理する（信頼する）、チケットは AI が書く（信頼しない）」という信頼境界を明確にすることで、宣言による自己特権昇格を防げる
- 宣言をチケットに書かせることで、レビュアーはチケットを読むだけで「この作業で何が触られうるか」を確認できる
- 未記載パスを拒否ではなく警告付き確認にすることで、想定外の作業を止める判断をユーザーに残しつつ、承認済みはセッション内で繰り返し聞かない

## 却下した案

- **チケットの宣言だけで判定する（type 定義を持たない）**: 設定が 1 箇所で済むが、AI が宣言を書く時点で権限が決まるため統制にならない
- **type 定義だけで判定する（チケットに宣言を書かない）**: 参考実装 agent-workflow に近く堅牢だが、依頼された「チケットにやってよいことを書く」を満たさず、同じ type のチケットが常に同じ範囲を触れてしまい粒度が粗い
- **未記載パスを一律拒否する**: 最も安全だが、計画時に列挙し漏れたパスのたびに止まり、ヘッドレス実行では回復手段が無い

## 影響

- 要件定義書 D 節
- チケットテンプレートは OKF frontmatter を持たず、フックが解釈する専用 frontmatter（`type` / `status` / `depends_on` / 宣言）だけを持つ
- ヘッドレス実行では ask が拒否になるため、計画ワークで宣言を十分に列挙する必要がある（仕様に明記する）
