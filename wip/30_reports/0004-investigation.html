npm レジストリに到達でき、拡張の開発依存は問題なく取得できた。TypeScript でのコンパイルと Node 標準テストランナーでの実行も実測で通った。TypeScript + tsc + node --test の構成を採るのが妥当で、退避路を使う必要はない。一方で vscode モジュールは VS Code ホストの外では解決できず、純ロジックの分離が設計上の制約になる。

  • 3◎良
  • 2△注意
  • 0✕問題

◆特に見てほしい

判断に困っている

  • vscode に触れる層を薄く保つ設計（パーサとボード組み立てを純関数に寄せ、エントリだけが vscode を触る）でよいか。受け入れ条件 9・10 を満たすうえでほぼ必須の制約（章 3）

◇承認が欲しい

方針は決めた

  • @vscode/test-electron を使わず node --test だけにする判断。VS Code の実ホストを起動する統合テストは書かない（章 5）

・細かいレビューは不要

ほぼ確実

  • npm が使えること、Node v22.22.2 / npm 10.9.7 というバージョン（章 1）

確かめられなかったこと（この結果が言っていないこと）

  • @vscode/test-electron は npm 上に存在することを確認しただけで実際に走らせていない。VS Code バイナリのダウンロードが必要で、この環境での成立性は未確認
  • 拡張を VS Code に読み込ませて Webview が実際に描画されるかは確認していない。この環境に VS Code の GUI が無く、受け入れ条件 1〜8 の最終確認は人間の手元で行う必要がある
  • npm ci での再現性は package-lock.json の生成を確認しただけで、別環境での再現は試していない

実施条件（測った対象・環境）

  • 作業は使い捨ての wip/tmp/npm-probe/ 内のみ。完了時に削除した
  • Node v22.22.2 / npm 10.9.7 / npx 10.9.7
  • npm レジストリは https://registry.npmjs.org/。環境変数のプロキシ設定が入った状態

実施した内容と結果

  1. 1

    npm レジストリへの到達と依存の取得 ◎良 根拠: npm view / npm install の出力

    npm view typescript version がバージョンを返し、レジストリに到達できることを確認した。続けて開発依存 3 つを実際に入れ、package-lock.json も生成された。

    根拠を見る（実行コマンドと出力） 
    $ npm view typescript version
7.0.2

$ npm install --no-audit --no-fund typescript@5 @types/node@22 @types/vscode@1.90
added 4 packages in 2s

$ ./node_modules/.bin/tsc --version
Version 5.9.3

$ ls node_modules/@types/vscode/index.d.ts
node_modules/@types/vscode/index.d.ts

    結論

    Q3 の答えは「取得できる」。退避路に倒れる必要はない。

  2. 2

    tsc でのコンパイルと Node 標準テストランナー ◎良 根拠: tsc -p . と node --test の出力

    target: ES2022 / module: Node16 / strict: true の設定で src/ と test/ をコンパイルし、結果に対して Node 標準のテストランナーを走らせて 3 件すべて通った。なお node --test にディレクトリを渡すと MODULE_NOT_FOUND で落ちるため、glob でファイルを渡す必要がある。

    根拠を見る（実行コマンドと出力） 
    $ ./node_modules/.bin/tsc -p .
（出力なし。exit=0）

$ node --test out/test/*.test.js
# tests 3
# pass 3
# fail 0

$ node --test out/test/
Error: Cannot find module '.../out/test'
  code: 'MODULE_NOT_FOUND'

    結論

    tsc でビルドし node --test でテストする構成が成立する。外部のテストランナーは要らない。

  3. 3

    vscode モジュールはホスト外で解決できない △注意 根拠: require('./out/src/uses-vscode.js') の出力

    import * as vscode from "vscode" を含むモジュールは型としてはコンパイルが通るが、素の Node では読み込めない。vscode は VS Code の拡張ホストが実行時に注入するモジュールで、npm には実体が無い（@types/vscode は型定義だけ）。

    根拠を見る（実行コマンドと出力） 
    $ cat src/uses-vscode.ts
import * as vscode from "vscode";
export function hello(): string { return vscode.version; }

$ ./node_modules/.bin/tsc -p .
（出力なし。exit=0 — 型は @types/vscode で解決される）

$ node -e "require('./out/src/uses-vscode.js')"
Error: Cannot find module 'vscode'
  code: 'MODULE_NOT_FOUND',

    結論

    単体テストの対象にできるのは vscode を import しないコードだけ。走査・frontmatter 解析・ボード組み立て・HTML 生成を vscode に依存しない層に置き、vscode を触るのはエントリだけにする。ファイル読み取りは node:fs を使う。

  4. 4

    依存ゼロの退避路 ◎良 根拠: node --experimental-strip-types --test の出力

    Q3 が肯定だったので採らないが、退避路が実在することは確認した。Node 22 の型注釈除去で TypeScript をコンパイルせず直接テストできる。ただし import 指定子を .ts で書く必要があり、既定の設定のままでは tsc が拒否する。

    訂正（敵対的レビューの指摘 9）: 当初この節は「tsc の Node16 解決とは両立しない」と書いていたが誤り。TypeScript 5.7 以降の rewriteRelativeImportExtensions を allowImportingTsExtensions と併せれば .ts 指定子のままコンパイルが通り、出力は .js に書き換わる。今回入れた 5.9.3 はこのオプションを持つ。

    根拠を見る（実行コマンドと出力） 
    $ node --experimental-strip-types --test test/parse.ts.test.ts
# tests 3
# pass 3
# fail 0

$ ./node_modules/.bin/tsc -p .
test/parse.ts.test.ts(3,34): error TS5097: An import path can only end with a '.ts'
extension when 'allowImportingTsExtensions' is enabled.

    結論

    Q4 の答えは「満たせる」。採らない理由は「両立しない」ではなく、Q3 が肯定でありビルド前提の構成が素直に組めるためである。オプションを 2 つ足して型注釈除去に寄せる利点が無い。

  5. 5

    テストランナー候補の入手性 △注意 根拠: npm view の出力

    候補はいずれも入手できるが、どれも Node 標準のテストランナーで代替できる。依存は少ないほうが受け入れ条件 10 を満たしやすい。

    パッケージバージョン判断
    @vscode/test-cli0.0.15採らない
    @vscode/test-electron3.1.0採らない。VS Code バイナリのダウンロードが要り、この環境で未検証
    mocha12.0.0採らない。Node 標準で足りる
    vitest4.1.11採らない。Node 標準で足りる
    esbuild0.28.2採らない。バンドルは不要

    結論

    開発依存は typescript / @types/node / @types/vscode の 3 つに絞る。

設計への反映

  1. 開発依存は typescript / @types/node / @types/vscode の 3 つに絞る（章 1・章 5）
  2. ビルドは tsc -p .、テストは node --test out/test/*.test.js を npm スクリプトに固定する（章 2）
  3. vscode を import する層としない層を分ける。パーサ・走査・ボード組み立て・HTML 生成は vscode に依存させず node:fs で読む（章 3）
  4. VS Code の実ホストを起動する統合テストは書かない。画面の確認は人間の手元で行う前提を README に書く（章 5）
  5. package-lock.json をコミットして再現性を確保する（章 1）

想定と異なった点

計画時の見込み実際どう扱ったか
プロキシ環境なので npm レジストリに届かない可能性がある問題なく到達し、4 パッケージが 2 秒で入った退避路は確認だけして採らないことにした（章 4）
@types/vscode を入れれば vscode を使うコードもテストできる型は解決されるが実行時には解決されないvscode に依存しない層への分離を設計の制約として明記した（章 3）
node --test にディレクトリを渡せるディレクトリだと MODULE_NOT_FOUND になるglob でファイルを渡す。npm スクリプトに書いて固定する（章 2）

残課題

  • 拡張を VS Code に読み込ませた実機確認をこの環境で行えない。受け入れ条件 1〜8 のうち Webview の見た目に関わる部分は、実装フェーズで自動テスト可能な形（HTML 生成関数の出力の検査）に落とし、実機確認は人間に委ねる
  • @vscode/test-electron をこの環境で走らせられるかは未確認。将来 CI を組む際に再検討する
#13 / #14 — 結果の正文は同名の .md。外部依存を持たない自己完結 HTML。
