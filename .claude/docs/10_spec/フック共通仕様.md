# フック共通仕様

各フックの要件定義書が「フック横断の仕様書が正として定める」と委ねた事項をここに置く。個々のフックの仕様（`10_spec/hooks/<NN-Event>/<name>.md`）はこの文書を前提に差分だけを書く。

## 1. 置き場と登録

- 実体: `.claude/hooks/<NN-Event>/<name>.sh`（bash。`bash <パス>` で呼ぶため実行権限は不要）。テストは同じディレクトリの `tests/test_<name>.sh`（雛形は `20-common-step-shell-script`）
- 共有ライブラリ: `.claude/hooks/lib/`
  - `hook-common.sh`: 入力 JSON の読み取り（`jq`）、緊急停止の判定、記録（`logs/`）、deny / ask / additionalContext の出力ヘルパ、セッション状態の読み書き、`redact`（§3）、`tool_class`（§2）（lib 単体のテスト観点は §11 HK-T03・T04・T06〜T08・T10）
  - `cmdpos.sh`: コマンド位置の判定（§7）。`block-direct-git` が正で、`block-chmod` / `workflow-guard` / `workflow-state-guard` / `post-push-*` が共有する（lib 単体のテスト観点は §11 HK-T05・T12）
  - `scope.sh`: 許可範囲の判定（§8）。`workflow-guard` が正で、`workflow-diff-check` / `subagent-stop-check` が共有する（lib 単体のテスト観点は §11 HK-T11・T15）
  - `push-detect.sh`: push の検知。`post-push-compact-prompt` が正で、`post-push-usage-report` が共有する（lib 単体のテスト観点は §11 HK-T13）
  - `transcript.sh`: transcript の解析（使用量の集計を 1 関数に閉じる）。`post-push-usage-report` が正（lib 単体のテスト観点は §11 HK-T14）。時刻の変換は自前の暦計算で行う（Windows の jq 1.6 では `strptime` / `fromdateiso8601` が動かない）
  - `lib/` の外にある依存: `frontmatter.sh`（`.claude/skills/20-common-step-shell-script/scripts/`。`scope.sh` がチケットの frontmatter を読むために `source` する。§7・§9。読み込みに失敗した拒否側フックは deny に倒す — `20-common-step-shell-script` 仕様「読み込み行」）
- 登録: `.claude/settings.json` の `hooks` に、イベントごとに `{"matcher": ..., "hooks": [{"type": "command", "command": "bash .claude/hooks/<NN-Event>/<name>.sh"}]}` で登録する。登録の正は次の表（各フックの仕様「呼出条件」と一致させる。テスト HK-T01 で照合）

1 行 = 1 登録（イベント × matcher × フック）。`順` は同じイベント内での `settings.json` の配列順（実行順）。HK-T01 はこの表と `settings.json` を行単位で照合する。

| 順 | イベント | matcher | フック | 役割 / 側 |
|---|---|---|---|---|
| 1 | SessionStart | — （全 source） | session-start | 案内 |
| 1 | UserPromptSubmit | — | workflow-entry | プロンプト境界の処理（記録のみ） |
| 1 | PreToolUse | `Skill` | workflow-entry | 宣言の記録 |
| 2 | PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|EnterPlanMode\|Agent\|Workflow` | workflow-entry | 未宣言の拒否（拒否側） |
| 3 | PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|mcp__.*` | workflow-state-guard | 進行状態・置き場・draft 解除の保護（拒否側。MCP は draft 解除の直接実行の検知用） |
| 4 | PreToolUse | `Bash\|PowerShell` | block-chmod | 拒否側 |
| 5 | PreToolUse | `Bash\|PowerShell` | block-direct-git | 拒否側 |
| 6 | PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|EnterPlanMode\|Agent\|Workflow` | workflow-guard | 宣言範囲の強制（拒否側） |
| 1 | PostToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell` | workflow-diff-check | 案内 |
| 2 | PostToolUse | `Bash\|PowerShell` | post-push-compact-prompt | 案内 |
| 3 | PostToolUse | `Bash\|PowerShell` | post-push-usage-report | 案内 |
| 4 | PostToolUse | `Agent` | subagent-stop-check | メインへの通知（§3） |
| 1 | SubagentStart | — | subagent-start-check | 案内 |
| 1 | SubagentStop | — | subagent-stop-check | 記録 |
| 2 | SubagentStop | — | post-push-usage-report `--accumulate` | サブエージェント分の蓄積 |
| 1 | Stop | — | post-push-usage-report `--accumulate` | 応答完了時の蓄積 |

- 同じイベントに複数のフックがあるとき、1 つでも deny を返せば操作は拒否される。拒否側のフックは互いに独立に判定し、先に拒否したフックが理由を返す。順序は「安価で範囲の広い判定 → 高価で狭い判定」
- **拒否側の 5 登録は fail-closed のラッパーで登録する**: `command` を `bash .claude/hooks/<NN-Event>/<name>.sh || printf '%s' '{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"WFx09: フック <name> を実行できない（構文エラー・ファイル不在・異常終了）。.claude/hooks の状態を確認してユーザーに報告すること"}}'` の形にする（`x` はそのフックの百の位）。ラッパーの `||` はフック本体が起動できず何も出力しなかった場合（構文エラー・ファイル不在・`source` の失敗）の縮退で、本体が deny を出した経路は終了 0 で戻るためラッパー側の deny は重ならない（§3）。フック本体が構文エラーで起動できない・ファイルが無い・`trap` の登録前に落ちた場合も deny になる（HK-T09）。案内側はラッパー無し（失敗は通す）

## 2. 入力

- stdin に JSON。共通フィールド: `session_id`、`transcript_path`、`cwd`、`hook_event_name`、`permission_mode`（`default` / `plan` / `acceptEdits` / `auto` / `dontAsk` / `bypassPermissions`）、`prompt_id`。サブエージェント実行中は `agent_id` / `agent_type` も付く。`Bash` と `PowerShell` の `tool_input` は同じ形（`command` / `description` / `timeout` / `run_in_background`）で、フックは `tool_input.command` をそのまま読む。イベント別: `tool_name` / `tool_input`（PreToolUse・PostToolUse）、`tool_response`（PostToolUse）、`prompt`（UserPromptSubmit）、`source`（SessionStart）、`agent_id` / `agent_type` / `model`（SubagentStart。`model` が無い版では実行者の比較を行わない）、`agent_transcript_path`（SubagentStop）
- ツールの分類（`hook-common.sh` の関数 `tool_class`）:

| 分類 | ツール |
|---|---|
| 書き込み | `Edit` `Write` `MultiEdit` `NotebookEdit` |
| 実行 | `Bash` `PowerShell` |
| 読み取り | `Read` `Glob` `Grep` `LS` `WebFetch` `WebSearch` など上記以外 |
| プランモード | `EnterPlanMode` |
| 起動 | `Agent` `Workflow` |
| 宣言 | `Skill`（`tool_input.skill` が振り分けスキル名のとき） |

- 判定の材料はこの入力・作業領域（`wip/`）・`logs/`・設定ファイルに限る。フックはリモートに問い合わせない（DDR i0001-14）。CLI の有無・認証・ネットワークに左右されない
- 作業ツリーの位置: `cwd` ではなく `git rev-parse --show-toplevel` を基準にする（サブディレクトリからの実行に備える）

## 3. 制御方式

| 目的 | イベント | 出力 |
|---|---|---|
| 拒否 | PreToolUse | stdout に `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<識別子>: <理由と対処>"}}`、終了 0 |
| 確認 | PreToolUse | 同上で `permissionDecision: "ask"`（理由に確認の根拠とチケットを含める）。ヘッドレス（§10）では `deny` に置き換える |
| 許可 | PreToolUse | 何も出力せず終了 0 |
| プロンプトの補足 | UserPromptSubmit | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}` |
| 操作後の通知 | PostToolUse | `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"<識別子>: ..."}}`（AI のコンテキストに入る。操作は取り消せない） |
| セッション開始の注入 | SessionStart | stdout のテキスト（そのままコンテキストに入る） |
| サブエージェントへの注入 | SubagentStart | `{"hookSpecificOutput":{"hookEventName":"SubagentStart","additionalContext":"..."}}` |
| メインへの通知（サブエージェント終了） | PostToolUse（`Agent`） | additionalContext。SubagentStop 側は記録だけ行う（SubagentStop の出力はサブエージェント側にしか届かないため。実装時に届き方を検証し、届くなら PostToolUse 登録を外す — TBD） |

- 拒否・確認・通知の文面は日本語で、先頭に識別子（§6）、続けて「何が起きたか」「対処」。ファイルの中身・差分の内容・環境変数の値・トークン・個人情報を含めない。コマンドの引用は先頭 80 文字まで
- 案内側のフック（session-start / diff-check / subagent-* / post-push-*）は依存が壊れたら**何も出さずに通す**。拒否側のフック（entry / guard / state-guard / block-*）は判定できなければ**拒否側に倒し**、理由に「機構の不調」を含める（`WFx09` 系の識別子）。無関係と確定できる操作は止めない
- フック自身の実行エラー（bash の異常終了）は Claude Code に非ブロッキングエラーとして扱われ操作が通ってしまうため、拒否側のフックは `trap ERR` で捕捉して deny を出し、**終了コード 0 で終了する**（非 0 で終わると §1 のラッパーが 2 つ目の deny を連結し、JSON として読めなくなる）。判定結果の伝達は常に stdout の JSON で、終了コードは使わない（`20-common-step-shell-script` 仕様「終了コード」）。`trap` が効かない経路（構文エラー・ファイル不在）は §1 の登録ラッパーが deny に倒す
- **機密情報のマスク**（全フック共通。`hook-common.sh` の `redact`）: 記録・拒否理由・通知に含めるコマンド文字列・パス・本文は、出力前に `redact` を通す。マスク対象: `ghp_` / `gho_` / `github_pat_` / `glpat-` で始まる語、`Bearer <語>`、`token=` / `password=` / `passwd=` / `secret=` と、`api` `access` `private` `auth` `client` `secret_access` に `_key=` / `-key=` / `key=` が続くキー（大文字小文字を問わない。値に `/` を含む秘密 — AWS のシークレットアクセスキー等 — はここで拾う）に続く語、`AKIA` で始まる 20 文字、40 文字以上の 16 進 / base64 様の語（`/` を含む語はパスと区別できないため対象外。ハイフンを 2 個以上含み大文字を含まない語（ブランチ名・チケット名）と、英小文字と `_` だけの語（識別子）は秘密と見なさず残す）。置換は `***`。各パターンは置換結果 `***` に再一致しない形にする（再一致すると置換が止まらない）。HK-T06 はマスク後の記録を検査する。`redact` は**最後の砦**であり、一次防御は「そもそも値を出さない」こと（環境変数の値・トークン・ファイルの中身を記録・理由・通知に載せない）。接頭辞決め打ちのパターンは当たらない値をマスクできず「マスクした」という誤った安心を与えるため、パターンが当たることを HK-T10 で固定し、新しい種類の秘密情報が現れたらパターンを足す

## 4. 緊急停止

- 機構全体: `WORKFLOW_ENFORCE=0`。フック単位: `WORKFLOW_<NAME>_ENFORCE=0`（`<NAME>` はフック名を大文字スネークにしたもの。例: `WORKFLOW_ENTRY_ENFORCE=0`、`WORKFLOW_GUARD_ENFORCE=0`、`BLOCK_DIRECT_GIT` → `WORKFLOW_BLOCK_DIRECT_GIT_ENFORCE=0`）
- 環境変数はセッション開始時に読み込まれるため同じセッション内では変えられない。AI は設定できず、ユーザーに「どちらを止めるか」と新しいセッションでの実行を伝える（`CLAUDE.md`「作業の振り分け」）
- 停止中のフックは判定・注入を行わず、`decisions.jsonl` に `{"decision":"disabled"}` を 1 行残す（session-start は停止中である旨を注入内容の先頭 1 行に出す）
- push 前チェックを飛ばす目的での停止は不可（`wip/push-check-skip.md` が正規の手段 — commit-push 仕様）

## 5. 記録と状態（`logs/`）

`logs/` はリポジトリ直下、`.gitignore` 済み、片付けの対象外（DDR i0001-28）。

| パス | 内容 | 書く側 | 寿命 |
|---|---|---|---|
| `logs/sh/<name>.log` | 実行ログ（共通 logger。`LOGGER_NAME=hook-<name>`） | 全フック | 手動削除まで |
| `logs/hooks/decisions.jsonl` | 判定の記録 1 行 1 件: `{"ts","session_id","hook","event","decision":"allow\|ask\|deny\|notify\|inject\|disabled\|skip","id":"WFxxx","tool","target","ticket","note"}` | 全フック | 振り返りの材料。全体まとめの後も残す |
| `logs/sessions/<session_id>/entry.json` | 振り分けの宣言状態: `{"prompt_seq","declared_skill","declared_at","continuation":"tickets\|review\|merge_prep\|null"}` | workflow-entry | セッション限り |
| `logs/sessions/<session_id>/approvals.json` | 未記載パスの承認の記憶: `[{"scope":"<親ディレクトリ or ファイル>","ticket","at"}]` | workflow-diff-check（書く）/ workflow-guard（読む） | セッション限り |
| `logs/usage/<branch>.json` | 使用量の蓄積（ブランチ単位。内側にセッション別・サブエージェント別の内訳と `posted` / `since_sha`） | post-push-usage-report（Stop / SubagentStop / push 時）、`boundary.sh`（`posted`） | 投稿成功で `since_sha` を進める（ファイルは残す） |
| `logs/usage/report-<branch>-<count>.md` | 対応工数レポート本文 | post-push-usage-report | 手動削除まで |
| `logs/push-state.json` | ブランチごとの前回 push 時点: `{"<branch>":{"sha","at","count"}}` | post-push-compact-prompt | 手動削除まで |
| `logs/mr.json` / `logs/review-state.json` / `logs/review-history.jsonl` / `logs/merge-state.json` | 提供コマンドの進行状態（`00-workflow-issue-mr-driven` / `10-task-overall-summary` 仕様） | boundary.sh / finalize.sh | フックは読むだけ |

- セッション状態は `session_id` で分離し、同じ作業ツリーで並行する別セッションと混ざらない。サブエージェント内のツール呼び出しは親と同じ `session_id` を持つため、宣言・承認の記憶はそのまま適用される（違えば実装時に `agent_id` から親を引く — TBD）
- `logs/sessions/` の 7 日より古いディレクトリは session-start が非侵襲的に削除する（失敗しても通す）
- `logs/` への書き込みは `workflow-guard` の許可範囲の判定対象外（機構自身の記録）。ただし進行状態ファイルへの AI の直接書き込みは `workflow-state-guard` が拒否する

## 6. 識別子の採番台帳

識別子は `<接頭辞><3 桁>`。テスト ID は `<接頭辞>-T<2 桁>`（機械テスト）、eval ID は `<接頭辞>-E<2 桁>`（eval。定義のみで実行は人間の判断）で、これらの接頭辞は所属アセットの仕様が持つ（台帳への登録義務はエラー識別子の接頭辞だけ。下表のテスト ID・eval ID の行は参考で、ID の重複は `run-tests.sh --ids` が検出する）。フックは `WF` で百の位がフック、下 2 桁が種類。`x09` は「判定不能で拒否側に倒した」で、拒否側のフック（1xx〜5xx）だけが持つ（案内側の 6xx〜9xx は拒否しないので欠番）。情報通知の識別子に番号の規則は設けず、各フックの表で種別「情報」と明記する。回復の案内と 1:1 で対応させる（各フック仕様の表が詳細）。

| 範囲 | 持ち主 | 概要 |
|---|---|---|
| WF101–109 | workflow-entry | 101 未宣言の拒否 / 102 記録破損（未宣言扱い） / 109 判定不能 |
| WF201–219 | workflow-guard | 201 禁止・保護範囲 / 202 未記載パスの確認 / 203 毎回確認範囲 / 204 分類外コマンド / 205 コマンドによる書き込み / 206 未宣言のリモート書き込み / 207 作業中 2 枚目・複数 / 208 チケット自身の改変 / 209 判定不能 / 210 設定不正 / 211 チケット記載不正 / 212 プランモード / 213 ヘッドレスで確認不可 |
| WF301–309 | workflow-state-guard | 301 進行状態ファイルの直接操作 / 302 作業中への直接移動・作成 / 303 完了への直接移動・作成 / 304 draft 解除の直接実行 / 309 判定不能 |
| WF401–409 | block-direct-git | 401 コミット / 402 push / 403 縮退判定での拒否 / 409 入力不正 |
| WF501–509 | block-chmod | 501 禁止コマンド / 509 入力不正 |
| WF601–609 | workflow-diff-check | 601 範囲外の差分 / 602 先行チケット未完了 / 603 種類の改変 / 604 基準点なし |
| WF701–709 | session-start | 701 現在地（情報） / 702 進行状態破損 / 703 MR 未記録 / 704 スキル不在 |
| WF801–809 | subagent-start-check | 801 実行者の不一致 / 802 要点の注入（情報） |
| WF811–819 | subagent-stop-check | 811 作業中のまま残ったチケット / 812 未コミット差分 / 813 範囲外の差分 |
| WF901–909 | post-push-compact-prompt | 901 参照リンク（情報） / 902 前回 push 記録なし / 903 MR 未記録 |
| WF911–919 | post-push-usage-report | 911 レポート（情報） / 912 記録読めず / 913 状態破損 |
| HK-T | フック共通 | 共通のテスト観点（§11） |
| TK001–008 | ticket.sh | `20-common-step-ticket`（008 は引数・環境の誤り） |
| CP001–008 | commit.sh / push.sh | `20-common-step-commit-push`（007 は引数・環境の誤り、008 は `git commit` 自体の失敗） |
| RV001–008 | check-html.sh | `20-common-step-report-view`（008 は引数・ファイル不正） |
| FN001–003 | finalize.sh | `10-task-overall-summary` |
| BD001–005 | boundary.sh | `00-workflow-issue-mr-driven` |
| LG / SS | logger.sh / shell-script | テスト ID のみ |
| TR001–006 | run-tests.sh | `20-common-step-shell-script`（テストランナー。提供コマンド。テスト ID は TR-T） |
| FR-T | frontmatter.sh | `20-common-step-shell-script`（`source` 専用の frontmatter 読み取りライブラリ。テスト ID のみ） |
| AC-E / FM-E / IS-E / RQ-E / SC-E | 20-common-step-{ai-asset-creator, feature-mr, issue, requirement, spec} | eval ID のみ（スクリプトを持たないスキルのテスト観点。`spec` は `SC-E` — `SP-T`（subagent-stop-check）と接頭辞を重ねない） |

新しいエラー識別子の接頭辞・範囲はこの表に追加してから使う。

**アプリ（`apl/<アプリ名>/`）の不備・エラーの識別子はこの台帳の対象外**。アプリごとに 2 文字の接頭辞 + 3 桁を使い、そのアプリの仕様書「不備の識別子とメッセージ」節が台帳を兼ねる（`20-common-step-spec` 仕様「アプリの識別子」が正）。新しい接頭辞は `apl/*/docs/10_spec/` を検索して既存のアプリと重ならないことを確かめてから使う。

## 7. コマンド位置の判定（`cmdpos.sh`）

入力: コマンド文字列（Bash / PowerShell）。出力: 実行位置にあるセグメントの列。各セグメント = `exe`（実行体の basename）/ `args[]` / `redirects[]`（`>` `>>` `2>` `&>` `<>` の宛先パス）/ `write_targets[]`（`cp` `mv` `tee` `touch` `mkdir` `rm` `truncate` `sed -i` `install` `ln` の書き込み先引数）/ `opaque`（判定不能）。呼び出し側はこの出力だけを見て判定し、コマンド文字列を再パースしない（規則の複製禁止）。純 bash（外部プロセス無し）。

チケットの frontmatter（§9）の読み取りは `.claude/skills/20-common-step-shell-script/scripts/frontmatter.sh`（`source` 専用・純 bash。入れ子キー `allow.write` とインラインマップ `human_review` に対応。仕様は `20-common-step-shell-script`）を `hooks/lib` から `source` して行い、フック側に frontmatter の解釈を重複して持たない（依存の向きは logger と同じ。DDR i0006-01）。

1. 前処理: ヒアドキュメント本文（`<<TAG`〜`TAG`、`<<'TAG'`、`<<-`）、`#` コメント（行頭または空白の後）、シングルクォート文字列を除去。ダブルクォート文字列は本文を除去するが、その中の `$(...)` と `` ` ` `` は展開して実行位置として扱う
2. 分割: `;` `&&` `||` `|` `|&` 改行 `(` `)` `{` `}` `&`（バックグラウンド）で分割
3. 各セグメントの先頭から透過ラッパーを剥がす: `sudo` `doas` `env`（`VAR=val` の並び含む）`command` `builtin` `exec` `time` `nice` `ionice` `nohup` `setsid` `stdbuf` `timeout` `if` `then` `else` `elif` `while` `until` `do` `!`（この一覧が正で、実装の語彙表と同じ集合。HK-T05 は全要素を踏む）
4. 実行体を正規化: ディレクトリ部と `.exe` を除いた basename（`/usr/bin/git`、`./git`、`git.exe` → `git`）
5. 不透明な実行系が実行位置にあれば、そのセグメントを `opaque` とする。2 系統ある: (a) 無条件に opaque — `eval` `xargs` `ssh` `watch` `flock` `parallel`、および `find` の引数に `-exec` `-execdir` `-ok` `-okdir` があるもの / (b) コード文字列を渡すオプション（`-c` `-e` `-E` `--command` `-command` `-encodedcommand` `-ec`）を伴うときだけ opaque — `bash` `sh` `zsh` `ksh` `dash` `busybox` `python` `python3` `perl` `ruby` `node` `deno` `pwsh` `powershell`（`pwsh script.ps1` のようにスクリプトファイルを渡す形は opaque ではない）。この 2 つの一覧が正で、実装の語彙表と同じ集合。呼び出し側は「opaque かつ対象語（`commit` / `push` / `chmod` / 状態ファイル名等）を含む」なら拒否側に倒す
6. PowerShell: `;` と改行で分割、呼び出し演算子 `&` と `.` を剥がす、ヒアストリング `@'`〜`'@` / `@"`〜`"@` を除去、バッククォート行継続を結合。バックスラッシュ区切りのパスは basename 化で吸収できない形（`.\git.exe` は吸収できる）があり得るため、実行位置のトークンに語としての `git`（`git` / `git.exe` / パス付き。`CP_GITLIKE`）があり、かつ第 1 サブコマンドが対象語（呼び出し側が渡す。block-direct-git なら `commit` / `push`）であるか、サブコマンドが特定できないときに限り拒否側に倒す（`git status` / `diff` / `add` / `fetch` は通す）
7. 縮退: bash 4.3 未満、または 1 コマンドが 4096 文字を超えるときは判定を行わず `degraded` を返し、呼び出し側は部分一致（対象語の有無）で判定して「縮退した判定」をメッセージに含める（`ai-command-style` ルールの言い換えを案内）
8. **提供コマンドの識別**: 実行体が `bash`（または `sh`）で第 1 引数が**コマンド文字列上でリポジトリルート相対の表記（`.claude/` 始まり）**で `.claude/skills/*/scripts/*.sh` または `.claude/hooks/**/*.sh` に一致するセグメントだけが「提供コマンド」。`cwd` による解決は行わず、絶対パス・`./` 付き・他の相対指定・basename だけの指定（`bash commit.sh`、`/tmp/commit.sh`、`bash ./.claude/skills/x/scripts/y.sh`）は提供コマンドとして扱わない。第 1 引数がクォート・変数展開・コマンド置換を含みパスとして確定できないセグメントも同様に通常の判定にかける（識別漏れを許可側に倒さない）。提供コマンドの起動は常にルート相対表記で行う（各スキルの手順が正）。フックが見るのはツールへ渡された文字列だけなので、提供コマンド内部の `git` 実行や `logs/` 書き込みはそもそも判定の対象に現れない（DDR i0004-05）。提供コマンドの引数に現れるパス（`commit.sh -m .. <files>`）は `workflow-guard` が書き込みと同じ判定を適用する
9. **出力の形**: 結果は呼び出し元のシェルに bash の配列として置く（純 bash・fork なしで判定できる形）。`CP_COUNT`（セグメント数）/ `CP_DEGRADED`（縮退なら 1）/ `CP_EXE[i]`（実行体。クォートやコード文字列で確定できないときは `_`）/ `CP_ARGS[i]`（引数。区切りバイトは RS（0x1E）。`cmdpos_args <i>` が `REPLY_ARGS` 配列に展開するので、呼び出し側は自分で分割しない）/ `CP_SUBCMD[i]`（第 1 サブコマンド。git はグローバルオプションを飛ばした後の語。クォートで割った語（`git 'commit'`）は `_` になり、呼び出し側は「特定できない」として扱う）/ `CP_REDIRECTS[i]` / `CP_WRITE_TARGETS[i]`（同じ 0x1E 区切り）/ `CP_OPAQUE[i]` / `CP_PROVIDED[i]`（提供コマンドならそのルート相対パス）/ `CP_GITLIKE[i]`（実行体が `_` で、コマンド文字列に語としての `git`（`git` / `git.exe` / パス付き）があるとき 1。`digit` / `legit` / `github` には立たない — 6 の PowerShell 判定の材料）/ `CP_LOWER`（小文字化した全文）。補助関数: `cmdpos_has_git_subcommand <sub>`（実行位置に `git <sub>` があるか）、`cmdpos_has_provided <path>`（提供コマンドがあるか）

- チケットの宣言 `d` は frontmatter の `allow`（§9）。`d.ops` に無い分類は使えず、`d.write` を指定すれば `types[t].allow` のうちその範囲だけが書ける（どちらも上限の内側で絞る役。`common.allow` は宣言によらず常に書ける）。ただし `read` / `remote-read` と提供コマンド（`provided`）は宣言によらず常に可 — 読むだけの操作と機構の操作が宣言漏れで止まらないため

## 9. チケットの機械可読項目

チケットの記載事項は frontmatter（YAML）に置き、フックと提供コマンドはこれを読む（人間もここを読む。表への転記はしない）。読み取りは `frontmatter.sh`（§7）に統一し、ファイル名 `<連番>-<種類>.md` の種類とこの `ticket_type` が食い違うときは frontmatter を正とする:

```yaml
---
type: ticket
ticket_type: implementation        # タスクの種類（.claude/hooks/config/task-types.tsv の type）
predecessors: ["0006"]             # 先行チケット
executor: "sonnet"                 # 実行者（サブエージェントのモデル）または main
human_review: {required: true, reason: "..."}
adversarial_review: {required: false, reason: "..."}  # 敵対的レビュー要否（切れ目の前。00-workflow-issue-mr-driven 手順 2a が読む。既定は rules/work-defaults.md）
allow:
  write: ["src/auth/**", "tests/auth/**"]   # 書き込んでよい範囲（上限の内側）
  ops: ["read", "build-test", "remote-read"] # 実行してよい操作の分類
started_at: ...                    # ticket.sh が記録
completed_at: ...
base_sha: ...                      # 差分基準点
cancelled_at: ...                  # ticket.sh cancel が記録（取り消したチケットのみ）
cancel_reason: "..."               # 同上
---
```

`ticket.sh` が書く文字列値（`cancel_reason` 等）は YAML の二重引用符の規則でエスケープする（`\` → `\\`、`"` → `\"`。改行は空白に置く）。

`workflow-guard` は作業中チケットの frontmatter のうち `ticket_type` `allow` `executor` `human_review` `adversarial_review` `predecessors` への書き込み（Edit / Write）を改変として拒否し（WF208）、本文（DoD のチェック・作業ログ）は許可する。`workflow-diff-check` は `ticket_type` が着手時のコミット値から変わっていれば警告する（WF603）。

## 10. ヘッドレスの判定

`WORKFLOW_HEADLESS=1` または `CI` が真値のとき、フックは「ユーザーが応答できない」とみなし、`ask` を `deny` に置き換える（理由に「計画タスクで宣言を十分に列挙する必要がある」を含める）。スキル側（`00-workflow-quick-request` 等）も同じ変数で判定する。`claude -p` の自動検知は入力に判別材料が無いため行わない（実装時に `permission_mode` 等で判別できると分かれば追加する — TBD）。

## 13. 意図的な緩和（機構が強制しないもの）

- **継続条件の窓**: 作業領域にチケット（未着手 / 作業中 / 完了のいずれか）がある間は宣言を求めない（要件・`CLAUDE.md`）。作業中チケットが無い切れ目・レビュー待ちの間は `workflow-guard` も判定しないため、この間に別の依頼が無宣言で書き込める。これは「切れ目の処理に必要な書き込みを妨げない」ための意図的な緩和で、機構が守るのは進行状態・コミット / push・`chmod`（常時フック）まで。別の依頼を始めるときの「チケットを完了するか todo に戻してから宣言し直す」（`CLAUDE.md`）と、軽作業の「チケットがあるブランチでは確認してから」（quick-request 仕様 1-3）はスキルの手順で守る
- **`git merge` によるマージコミット**: `merge-base` の分類で許可され、メッセージは git が生成する（`commit.sh` の規約検査を経ない）。取り込みに限る（DDR i0004-07）
