# チケットボード拡張のフィードバック計画

## 対象

- 対象 issue: #13 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/issues/13
- PR: #14 https://github.com/yuki-matsu783/issue-mr-ticket-workflow/pull/14
- チケット: 0012-feedback-plan
- 棚卸しの対象: 完了した 14 枚のチケット（0001〜0011 / 0013 / 0014 / 0015）の作業ログ「AI アセットに反映すべき内容」「スコープ外で見つけたこと」「仕様からの逸脱」

## この計画で何をするか

溜まった反映候補を 3 つの行き先に振り分ける。

| 行き先 | 判断の基準 |
|---|---|
| 本 issue の設計反映フェーズ | `docs/` 配下（本拡張の要件・仕様・DDR）だけで閉じ、issue #13 の受け入れ条件の解釈を変えないもの |
| 別 issue | `.claude/` 配下（AI アセット）の変更を要するもの。本 issue のどのフェーズも `.claude/**` への書き込み許可を持たず、CLAUDE.md も AI アセットの変更を専用のフェーズ列で進めることを求めている |
| 対応しない | 既存 issue と重複するもの、判断の材料が足りないもの |

振り分けの結果、**設計反映フェーズを立てる**。AI アセット設計 / AI アセット実装のフェーズは本 issue では立てない。

## 対象と範囲

含む: 反映候補の振り分けと、後続フェーズの要否の決定、次の計画チケットの起票。
含まない: 別 issue の作成そのもの（外部への副作用のため、本計画では案の提示までとし、作成はユーザーの承認を得てから行う）。`.claude/` 配下のいかなる変更。

## 方法とステップ

1. 本チケット（0012）で振り分けを確定し、この計画書と HTML ビューを残す
2. 次の計画チケット `0016-design-feedback-plan` を未着手で作る。設計反映フェーズは A1〜A11 を対象とする
3. 設計反映計画が実施チケットを起こし、`docs/` の要件・仕様・DDR を実装に合わせる
4. 設計反映の完了後に全体まとめへ進む。別 issue（B1〜B4）の起票は完了処理でユーザーの承認を得て行う

## 検証

- A1〜A11 が設計反映の実施チケットの DoD にすべて現れること（本計画書の表と 1 対 1 で照合する）
- 設計反映の後、仕様書「要件との対応」の行数が要件の受け入れ基準 26 件と一致したままであること
- 本計画書の HTML ビューが `check-html.sh` の 7 項目を通ること

## チケット

| 番号 | 種類 | 内容 | 状態 |

| 0012 | feedback-plan | 本計画（振り分けの確定） | 作業中 |

## リスクと復旧

| リスク | 兆候 | 復旧 |
|---|---|---|
| 設計反映で仕様を実装に合わせた結果、要件の受け入れ基準と食い違う | 「要件との対応」表の行が実現箇所を失う | 要件側を変えず、実装と仕様のどちらが正かを DDR に残して決め直す |
| A11 のように 1 行に複数の逸脱をまとめた項目が、実施チケットで取りこぼされる | 実施チケットの DoD の根拠欄が「A11」とだけ書かれる | 設計反映計画で A11 を 3 つに割る |
| 別 issue の起票が承認されず、AI アセットの不備が記録ごと消える | 完了処理の `reset-wip` で `wip/` が消える | 起票前に PR 本文と issue コメントへ B1〜B4 の要約を残す |

## スコープ外

- `.claude/` 配下のいかなる変更（B1〜B4 の実作業）
- 別 issue の作成そのもの
- C2 の挙動追加（複数ルート・シンボリックリンク・`capabilities`）

## 保留した点 / 対象なし

- B1 と既存 issue #9 / #10 / #11 の重複範囲は未確認。起票の直前に `list_issues` で確認する（本チケットの許可範囲は `wip/**` の書き込みと読み取りのみで、GitHub 操作はチケット作業の外で行う）
- A7 は「型から `cspSource` を削る」「仕様に受け取るだけと書く」の 2 案があり、どちらにするかは設計反映で決める。型を削ると `src/**` の変更も要るため、設計反映では仕様側に寄せる案を既定とする
