# subagent-stop-check フック

## 概要

サブエージェントに委ねたタスクやチケットが終わったとき、作業領域の実態（チケットの状態・差分）が結果報告と食い違っていないかを終了の時点で機械的に確かめ、食い違いの兆候をメインエージェントに伝えるフックの要件を定義する。

- **背景**: サブエージェントが失敗・中断すると、チケットが作業中のまま残ったり、未コミットの差分が残ったりする。オーケストレータは「チケットの状態を機構から確認し、作業中のまま残ったチケットを報告してユーザーの指示を待つ」（`00-workflow-issue-mr-driven` の例外フロー）ことになっているが、確認を覚えていることに依存し、忘れると次の操作が `workflow-guard` に拒否されて初めて気づく。
- **目的**: サブエージェントの終了の瞬間に作業領域の実態が伝えられ、オーケストレータが結果報告と突き合わせて次の一手（完了の手続き・ユーザーへの報告）を確認漏れなく選べる状態を実現する。
- **スコープ**:
  - 含む: 終了時の作業領域の検査（作業中のまま残ったチケット・未コミットや許可範囲外の差分）、AI への通知と対処の案内、記録、緊急停止
  - 含まない: チケットの状態の変更や差分の巻き戻し（行わない）、宣言した範囲の事前の強制（`workflow-guard`）と操作ごとの差分検知（`workflow-diff-check`）、起動時の検査（`subagent-start-check`）、失敗・中断への対処そのもの（`00-workflow-issue-mr-driven` とユーザー）

---

## ユーザーストーリー

**[As a]** サブエージェントにタスクを委ねるオーケストレータ（メインエージェント）として、

**[I want]** サブエージェントが終わった瞬間に、作業中のまま残ったチケットや残った差分を知らせてほしい。

**[So that]** 結果報告を鵜呑みにせず実態と突き合わせられ、失敗・中断の後始末を確認漏れなくユーザーに報告できるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When サブエージェントが終了したとき、Shall フックは作業領域を調べ、次のいずれかに該当があればメインエージェントに伝えなければならない: 作業中のまま残っているチケット、未コミットの差分・未追跡ファイル（機構自身の記録・一時ファイルの置き場を除く）、許可範囲外のパスに残っている差分。
- When 該当が無いとき、Shall not フックは何も伝えてはならない。
- When 伝えるとき、Shall フックは対処として「サブエージェントの結果報告と突き合わせること」「完了していれば提供コマンドで完了の手続きを行うこと」「失敗・中断であれば作業中のまま残ったチケットをユーザーに報告し、勝手に完了にしないこと」を含めなければならない。
- When 作業中のチケットが残っていることが正常な運用の場合（チケットの着手・完了をメインエージェントが代行する形など）、Shall フックの通知は異常の断定ではなく実態の報告として書かれ、判断は AI に委ねられなければならない。
- When サブエージェントの終了を検査するとき、Shall not フックはチケットを移動・完了させたり、差分を巻き戻したり（破壊的操作）してはならない。
- When フックが通知したとき、Shall その記録（終了したサブエージェント・検知した内容の要約）が残り、フィードバック計画の振り返りで AI とユーザーが参照できなければならない。記録と通知に機密情報を含めない。
- When 通知するとき、Shall メッセージは他のフックと機械的に区別できる識別子を持ち、対象（チケット名・パス）を具体的に含まなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは検査を行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If 作業領域や差分の取得に失敗した場合、Then フックは何も伝えずに通さなければならない（案内側の仕組み。事前の拒否は `workflow-guard` が担っている）。
- If フックの入力が解釈できない場合、Then フックは何もせずに通し、サブエージェントの終了処理を止めてはならない。

---

## 前提条件

- チケットの状態が作業領域のファイル配置から機械的に分かること
- Claude Code のフック機構がサブエージェントの終了時にメインエージェント側でフックを動かせること
- 許可範囲の判定の元（タスクの種類ごとの上限・チケットの宣言）が `workflow-guard` と共有されていること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。判定の材料はフックへの入力と作業領域のファイル・git のローカル操作に限る。許可範囲の判定規則は `workflow-guard` / `workflow-diff-check` と 1 か所で共有し、複製しない。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: 後始末の判断（完了の手続き・ユーザーへの報告・チケットを未着手へ戻す）は AI とユーザーが行い、フックは実態の報告だけを担う
- **外部的制約**: サブエージェントの結果報告そのものの真偽は判定できない（作業領域の実態との食い違いを示すだけ）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | サブエージェントの終了のたびに働くため、検査は git のローカル操作だけで体感できない時間で終える |
| セキュリティ | 記録と通知に環境変数の値・トークン・個人情報を含めない |
| 可用性 | 検査に失敗しても何も伝えずに通し、サブエージェントの終了とメインエージェントの継続を止めない |
| 一貫性 | 許可範囲の判定は `workflow-guard` / `workflow-diff-check` と同じ結果になる |
| テスト容易性 | 作業領域の状態を与えて、通知の有無と内容を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
