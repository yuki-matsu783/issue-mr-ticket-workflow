この計画で何をするか

DDR i0001-23 は「並列時だけ別ブランチ・別作業ツリーに分ける」案を「1 issue = 1 ブランチ = 1 MR の原則と衝突し、統合のコストが利得を上回る」として却下した。本フェーズは、この却下理由が git worktree という具体的な手段のもとで今も成り立つかを、測れる問いに分解して答える。効く受け入れ条件は A1（worktree 上で機構が健全に動くことの実測）と A4（並列実施の採否と理由を DDR に残す）で、A5・A6 には「並列を採用する場合に何が要るか」の材料として効く。

決めたこと

  • 調査観点を 6 つ（A〜F）に分け、1 観点 = 1 調査チケット（0004〜0009）に割り付ける。次の計画チケットは ai-asset-design-plan を 1 枚（0010）。
  • 全体計画書の保留 P1（並列の採否）はここでは決めない。判断材料だけを揃えて AI アセット設計計画（0010）へ渡す。
  • 全体計画書の保留 P3 は本計画で決着させる ── ユーザー実行で回す。先に scope.sh の穴を直してから実測する道は採らない。
  • 実測が要る問いは調査から外さず、「予測 + そのまま貼れるコマンド列」の形で調査結果レポートに残し、実行は人間に回す。実行結果は wip/tmp/worktree-probe/ に置き、観点 F（0009）が突き合わせる。

実測の扱い（この計画の前提）

全体計画書の差分 2 のとおり、scope.sh の git 分類に checkout / switch / worktree が無く、どの allow.ops を宣言しても AI からは実行できない（WF204: … はどの分類にも当たらない（既定拒否））。本チケットの実施中にも cd が同じ理由で 2 回拒否された。したがって worktree を実際に作る実測は、(1) 調査チケット 0004〜0007 が読み取りで答えられるところまで答えて残余を実測手順にする → (2) 実行の依頼は 0008 完了時点の切れ目で呼び出し元がまとめてユーザーに渡す → (3) 結果を wip/tmp/worktree-probe/ に受け取る → (4) 0009 が予測と突き合わせる、の順で行う。

調査観点

読み取りで答えられる問いと、実測でしか答えが出ない問いを混ぜず、後者は「予測 + 実測手順」の形に落として観点の中に残す。答えが次の計画（0010）に効かない問い ── worktree 一般の運用ノウハウ、他プロジェクトでの並列開発事例 ── は観点に含めない。

観点問いどの判断点・受け入れ条件に効くか

方法とステップ

読み取りで答えが出る観点を先に片付け、実測は 1 回にまとめる。実測の実行が人間側に依存するため、実測を待つ箇所を 1 か所（S6 の直前）に集めるのが順序の理由である。

  1. 1

    S1 観点 A ── フック側の作業ツリー解決（チケット 0004 / 先行 —）

    grep -rn "HOOK_ROOT\|HOOK_WORKTREE" .claude/hooks/ で全参照を機械的に抜き、1 件ずつ「スクリプトの置き場（HOOK_ROOT が正）」「作業ツリーの状態（HOOK_WORKTREE が正）」のどちらを指すべきかを判定して表にする。読む場所は lib/hook-common.sh（__hc_resolve_worktree / __hc_is_worktree_of）、20-PreToolUse/*.sh、22-PostToolUse/*.sh、10-UserPromptSubmit/workflow-entry.sh、00-SessionStart/session-start.sh、13-SubagentStop/subagent-stop-check.sh、lib/tests/test_hook_common.sh、フック共通仕様 §2、DDR i0009-55。既存テストが検証済みの範囲を特定し、残余を実測手順にする。外部調査は不要。

  2. 2

    S2 観点 B ── 提供コマンドと logs/ 状態ファイル（チケット 0005 / 先行 0004）

    grep -n 'LOGGER_ROOT\|logs/' を各スクリプトに当てて状態ファイルへの依存を全件抜き、「コマンド × 依存する状態ファイル × 無いときの振る舞い（既定値 / 警告 / 停止）」の表を作る。__ss_load の探索順（BASH_SOURCE 上向き → CLAUDE_PROJECT_DIR → git rev-parse）に、相対パス起動と本流の絶対パス起動を当てはめて解決先を書き分ける。読む場所は .claude/skills/*/scripts/*.sh の __ss_load 行、5 本の提供コマンド、logger.sh、.gitignore（logs/）、logs/ 配下の実ファイル一覧、各コマンドの仕様書。残余を実測手順にする。外部調査は不要。

  3. 3

    S3 観点 C ── サブエージェントを別 worktree で動かせるか（チケット 0006 / 先行 —）

    Claude Code / Agent ツールの公式ドキュメントを WebFetch で読み、作業ディレクトリ／worktree を指定できるかを引用（URL と該当行）付きで確定する。取得できないときは「不明」と明記して実測手順に落とす。あわせて 12-SubagentStart/subagent-start-check.sh、.claude/agents/task-executor.md、00-workflow-issue-mr-driven/SKILL.md の起動手順と assets/subagent-prompt.template.md を読み、logs/hooks/decisions.jsonl の過去レコードからサブエージェント実行時の cwd の実値を拾って呼び出し元と一致していたかを見る。外部調査 要（allow.ops に web）。

  4. 4

    S4 観点 D ── ブランチ構成と合流コスト（チケット 0007 / 先行 0004, 0005）

    選択肢（detached HEAD / サブブランチ + 合流 / --force）ごとに表を作り、成立可否・合流手順・衝突の種類を書く。衝突の件数は git log --diff-filter=R --name-status -- wip/10_tickets/ などで過去 issue の実データから見積もる（1 チケットあたりの rename 件数・同一ファイルへの追記回数）。読む場所は ticket.sh（採番・ファイル移動・状態遷移コミット）、commit.sh / push.sh の push 前チェック 4 項目、00-workflow-issue-mr-driven/SKILL.md の切れ目、boundary.sh。DDR i0001-23 の却下理由の各文に対して「今も成り立つ / 成り立たない」を根拠付きで判定する。外部調査 要（git 公式の worktree 制約のみ。allow.ops に web）。

  5. 5

    S5 観点 E ── scope.sh の git 分類の穴（チケット 0008 / 先行 —）

    git help -a などで得た git サブコマンド一覧を _SC_GIT_READ_SUBCMDS と突き合わせ、unknown に落ちるものを全件列挙する。cd のように _SC_READ_ONLY_CMDS に無い基本コマンドも同様に洗う。読む場所は lib/scope.sh（scope_classify / _SC_GIT_READ_SUBCMDS / _SC_READ_ONLY_CMDS）、block-direct-git.sh、workflow-guard.sh（WF204 / WF205）、config/scope-limits.json、lib/tests/test_scope.sh、該当仕様。塞ぎ方は最低 2 案（既存分類への追加 / 新分類の導入）を挙げ、案ごとに block-direct-git.sh との関係・影響するテスト ID・拒否が緩む範囲を書く。外部調査は不要。

  6. 6

    （切れ目）実測の依頼と受け取り（チケットなし / 先行 0008）

    呼び出し元（メインエージェント）が 0004〜0007 の実測手順をまとめてユーザーに渡し、実行結果を wip/tmp/worktree-probe/ に受け取る。AI は git worktree add / git checkout -b を実行できない（WF204 既定拒否）ため、この 1 か所だけが人間の手を要する。

  7. 7

    S6 観点 F ── 実測結果の突き合わせ（チケット 0009 / 先行 0004〜0008）

    wip/tmp/worktree-probe/ 配下の実測結果と wip/30_reports/0004-investigation.md の A〜D の予測を 1 対 1 で並べ、「一致 / 不一致（実測が正） / 未取得」の 3 値で判定する。不一致は原因の候補まで書く。未取得は理由と再実行手順を残課題へ。A1 の「動かない箇所」一覧と保留 P1 の判断材料を確定する。外部調査は不要。

  8. 8

    S7 次フェーズの計画（チケット 0010 / 先行 0004〜0009）

    AI アセット設計計画。全体計画書のフェーズ列 #3 に対応する。

全体計画書の保留 P3 の決着

全体計画書の保留 P3「調査で必要な実測を、ユーザー実行で回すか、先に git 分類の穴を直してから回すか」は、本計画でユーザー実行で回すと決めた。理由は 3 つ。

  1. 穴を先に直すのはフェーズ列（調査 → AI アセット設計 → AI アセット実装）の逆行で、scope.sh は中核（フック共通ライブラリ）にあたるため、設計と実装計画のレビューを飛ばして触ることになる
  2. 塞ぎ方そのものが設計判断であり（観点 E で 2 案以上を出す）、調査の途中で 1 案を実装で固定すると、設計フェーズの選択肢が調査の都合で狭まる
  3. 実測は worktree の作成・削除を含む数コマンドで、1 回にまとめれば人間の手間は小さい。恒常的な迂回路を先に作るほどの頻度ではない

この決着により、全体計画書の保留 P3 は解消済みとして扱う（全体計画書自体は書き換えない）。
