# 許可範囲内の削除を通す判定の形

## 背景

`workflow-guard` はコマンドによる書き込み（リダイレクト・`cp` / `mv` / `rm` など）を一律に WF205 で拒否していた。Edit / Write にはファイルを消す手段が無いので、この状態では **AI がファイルを 1 つも削除できない**。`.claude/` 配下のアセットを移設・整理するチケットは、新しい場所に置くことはできても古い場所から消せず、移設が完了しない。

一方で、削除を無条件に通すと拒否側の担保が一気に緩む。`rm -rf .claude` の 1 行で機構そのものが消え、`rm logs/review-state.json` で進行状態の記録が消え、`rm -rf .claude/hooks/*` のようにシェルが展開する前の文字列は宣言と照合しても意味を持たない。

## 決定

削除だけを行う段（実行体が `rm`、または `git` でサブコマンドが `rm`）を、**次を順に当てて**判定する。1 つでも当たれば WF205 で拒否する。

1. 対象を読み取れない（オプションだけ・`--pathspec-from-file` のように対象がコマンドの外にある）
2. 対象がディレクトリを指す（末尾 `/`・`-r` / `-R` 付き・実在するディレクトリ）
3. 対象に展開前の文字列が含まれる（`*` `?` `[` `{` `$` `` ` `` `~` `,`）
4. 対象が進行状態のファイル（`common.state_files`）に当たる
5. 上を通ったうえで、**置き場（`common.allow` のうち提供コマンドが管理しないもの）か、チケットの `allow.write` の宣言のどちらかに一致しない**

リダイレクト先は削除とは別に、これまでどおり書き込みとして判定する。作成・更新（`echo x > file`・`cp`・`mv`）は WF205 のまま変えない。

## 理由

- **消せないことが実害を出していた**。移設の完了条件（参照も移す）を満たせず、古い置き場が残り続ける
- **削除は「作成・更新」より危険度が高いのに、判定は簡単**。作成・更新は中身の妥当性まで見ないと危険度が測れないが、削除は「何を消すか」だけで測れる。だからこそ、消す対象の条件を厳しくすることで安全側に寄せられる
- **ディレクトリを外したのは、配下に紛れる保護対象を数え漏らすため**。`rm -rf .claude/hooks/config` は宣言に一致していても、その配下に毎回確認の対象や拒否の対象が含まれる。配下を全部たどって照合する実装より、「ディレクトリごとの削除は通さない」と決めるほうが漏れない
- **展開前の文字列を外したのは、照合が成立しないため**。`.claude/hooks/*` は宣言のグロブ `.claude/hooks/**` に文字列として一致してしまうが、実際に消えるのはシェルが展開した後の実体で、その中身は判定していない
- **進行状態のファイルを外したのは、`logs/**` が置き場として通ってしまうため**。`logs/` は提供コマンドが書く場所として通す設計だが、その中の `mr.json` / `review-state.json` / `merge-state.json` は機構の記録そのもので、消えると現在地が失われる

## 却下した案

- **削除も一律に拒否したまま、提供コマンドに削除のサブコマンドを足す**: 削除の対象はアセットの整理・移設・一時ファイルの片付けと多岐にわたり、1 つのコマンドの引数に収まらない。使い方を覚えるコストも高い
- **`allow.write` に一致すれば無条件に通す**: `common.allow` によって `wip/20_plans/` `wip/30_reports/` `wip/10_tickets/00_todo/` が宣言なしで消せる状態になる。他のタスクの成果物や未着手のチケットを、宣言もせずに消せてよい理由が無い
- **ディレクトリの配下を再帰的に照合して、保護対象を含まなければ通す**: 実装が重く、シンボリックリンクや実行時に増えるファイルで判定がぶれる。得られる利便（ディレクトリごと消せる）に見合わない
- **展開後の文字列を機構が自分で展開して判定する**: フックが受け取るのはコマンド文字列で、実行時のカレントディレクトリと `shopt` の状態に依存する展開を機構側で再現すると、実際に消えるものとずれる
