  adversarial-reviewer サブエージェントの起動プロンプトのひな形。
  起動の前に git diff <基準SHA>..HEAD > wip/tmp/adversarial-<n>.patch を書き出しておく
  （レビュアーは Bash を持たないので、自分で差分を取れない）。
  起動の前にモデルを突き合わせる: レビュー対象を作った実行者と定義の model が同じなら、
  Agent ツールの model で別のモデルに差し替える。差し替えたらレビュー依頼コメントにモデル名を添える。
  経緯（git log・作業ログ・計画書の「判断と根拠」・過去のレビュー）は渡さない。
  {{名前}} は全部埋め、このコメントは渡す前に消す。
-->

対象: 差分 `wip/tmp/adversarial-{{n}}.patch`（`{{基準SHA}}..{{HEAD}}`）
ファイル: {{対象ファイルの一覧}}
種類: {{コード / 文書}}

観点:
- [{{ルール名}}/{{章}}] {{観点の内容}}

{{観点が集まらなかった場合は「観点: 無し（一般観点で見てほしい）」と書く}}

進め方:

1. 渡された観点で対象を突き合わせる
2. 観点の外も探す（境界値・エラー経路・波及先・説明と実体の食い違い）
3. 対象が「N 件すべて反映した」「すべて通る」のような**まとめの主張**を含むなら、何件かを抜き取って実体と突き合わせる
4. 各指摘に 1 回反証を試みる（実装の意図の推測で取り下げてはならない）
5. 裏取りできたものだけ `verified: true` にし、確度を申告する（裏取りなしで 0.7 以上を付けない）

出力: 下記スキーマの JSON だけを返す。講評・要約の散文は書かない。

```json
[
  {"path": "...", "line": 0, "severity": "high|medium|low", "confidence": 0.0,
   "problem": "何が問題か", "when": "どの入力・状況で起きるか",
   "fix": "どう直すか", "perspective": "観点名 または 観点外", "verified": true}
]
```

配列の後に、該当すれば次を添える（無ければ省く）。

- `{"unreviewed": [{"path": "...", "reason": "..."}]}` — 読めなかった対象
- `{"checked_ok": [{"perspective": "...", "what": "...", "how": "..."}]}` — 指摘になりうると思って**実際に中身を見に行き、見た結果として否定できた**もの。該当の無い観点を「問題なし」と並べるのはこれに当たらない
- `{"sampled": [{"claim": "...", "source": "...", "result": "一致|不一致|確かめられない"}]}` — まとめの主張の抜き取り検証。`不一致` は指摘としても配列に載せる

欠陥が無ければ `[]` を返す。水増しの軽微な指摘を足さない。
