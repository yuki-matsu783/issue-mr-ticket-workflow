# 10-task-ai-asset-implementation-plan スキル 仕様

## 概要・禁止事項

AI アセット実装・テスト計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-ai-asset-implementation-plan.md](../../00_requirement/skills/10-task-ai-asset-implementation-plan.md)。処理フローの共通手順は `10_spec/skills/10-task-investigation-plan.md`「計画タスクの共通手順（正）」に従い、ここでは固有部分だけを書く。

禁止事項（共通手順の禁止事項に加えて）:

- アセット本体・テストを書き始めること
- 要件・仕様の書き換え（不備は AI アセット設計への差し戻し提案）
- テスト ID の無いアセット変更をステップに入れること
- 中核（フック・settings.json）の変更を、そのテストより後ろのステップやスキル変更と同じチケットに置くこと
- 参照更新一覧を検索せずに書くこと（一覧には検索語と検索結果を添える）

## 呼出条件

- `next` が AI アセット実装計画チケットを示したとき、全体計画で合意した実行者（サブエージェント）で読み込まれる

## IN / OUT

| IN | OUT |

## IN / OUT サンプル

- ステップ: 「1 `settings.json` の matcher 追加 → 2 `workflow-diff-check.sh` の除外判定 → 3 その機械テスト WD-T06 → 4 スキル `20-common-step-ticket` の説明更新 → 5 参照更新（旧名 `diff-check` の 3 箇所）」
- 結果報告の見てほしい点: 「ステップ順が固定順に沿い中核とテストが隣接しているか / テスト ID の割付（機械 / eval）の漏れ / 参照更新一覧の検索根拠 / ロックアウト対策の妥当性」

## 処理フロー

共通手順に加えて:

- 仕様書にテスト ID が無い（または受け入れ条件に対応するテスト観点が無い）場合は実装チケットを起こさず、不足を結果報告に書いて AI アセット設計（`ai-asset-design`）の追加チケットを起こす提案を返す
- ステップは**固定順**で並べる: 設定・定義（`settings.json`・frontmatter・テンプレート）→ 中核（フック・提供コマンド）→ 中核の機械テスト → スキル・ルール・エージェント → 参照更新（名称・パスの変更に伴う他文書の追随）。中核の変更と機械テストは同じチケットか隣接するチケットにする
- **計画書の記述順とチケットの実行順を一致させる**（申し送り 0022 E2）。ステップに割り付けたチケットの連番は、`ticket.sh next` が返す順（先行の解決を挟んだ最小連番）と同じ並びになるように振る。順序が入れ替わる依存があるなら `predecessors` で表し、計画書のステップの順番を実行順に合わせて書き直す。「計画書では 3 番目だが実際は 1 番目に走る」状態を残さない
- **提供コマンド自身を変えるステップ**（`ticket.sh` / `commit.sh` / `push.sh` / `boundary.sh` / `finalize.sh` などを書き換えるもの）には、**変更後の自分のコマンドで自分をコミット・完了させる最初の操作**を手順として明示する（申し送り 0031）。書き換えた直後の 1 回目が壊れていると、そのチケットを完了させる手段が無くなる。ステップの記述に「変更 → `commit.sh` で自分をコミット（この 1 回目が検証を兼ねる） → `ticket.sh complete`」の並びを書き、失敗時に戻す基準点（`base_sha`）を添える
- テスト方針: 仕様のテスト観点をステップに割り付け、**機械テスト**は実行コマンドを、**eval** は定義（入力・期待する振る舞い・判定方法）を書く。eval は実装フェーズでは定義までで、実行は人間の判断
- **テスト ID の割付表は機械的に作る**（申し送り 0022）。仕様書からテスト ID を抜き出す検索（例: `grep -rhoE "\b[A-Z]{2,7}-(T|E)[0-9]{2}\b" .claude/docs/10_spec/ | sort -u`）を計画書に載せ、その出力を左列にして割付表を組む。目視で拾うと仕様に書いたのに割り付いていない ID が残る。抜き出しの結果と割付表の行数が一致することを計画書に書く
- **テストを実行するチケットは `build-test` と `hook-test` を両方宣言する**（申し送り 0022）。`allow.ops` の分類は `scope.sh` が実行体と第 1 引数で決めており、`.claude/hooks/**/tests/*.sh` と `.claude/skills/*/scripts/tests/*.sh` は `hook-test`、`commands.build-test` に列挙されたコマンドとリポジトリ直下の `tests/*.sh` は `build-test` になる。どちらを踏むかは実行するテストの置き場で決まるので、**テストを走らせるチケットには両方を書く**。片方だけだと WF204 で止まり、チケットの許可範囲を広げる相談が発生する
- AI アセット実装チケットの DoD の型: 「{{アセット}} が仕様書 {{節}} のとおりになっている」「機械テスト {{ID}} が通る（実行方法）」「eval {{ID}} が定義されている（実行しない）」「プレースホルダ・frontmatter の検査が 0 件」「参照更新の検索で旧名が 0 件（DDR・用語辞書の別名を除く）」
- **実装結果レポートの作成は最初の実装チケットの DoD に入れる**（申し送り 0022）。実施タスクの共通手順はレポートを最初のチケットで作ると定めるが、DoD に書かれていないと後回しにされ、最後のチケットでまとめて書くことになる。最初のチケットの DoD に「実装結果レポート（md + HTML）があり `check-html.sh` が通っている」を置く
- **参照更新一覧**は変更する名称・パスごとに `Grep` の検索語・ヒット箇所を計画書に書き、DDR と用語辞書の別名は除外として明示する。0 件検索は「検索した」ことの記録として残す。**検索語は行末に依存しない形で書く**（申し送り 0038）。`foo\.sh$` のような形は、同じ名前が行の途中に現れる箇所を取りこぼす。**期待値は「残るもの」で書く**（「旧名が 0 件」ではなく「`grep` の結果が DDR の N 件と用語辞書の M 件だけ」）。0 件を期待値にすると、検索語が間違っていて何もヒットしない場合と区別が付かない
- **期待値が変更対象に依存するテストを洗い出して同じチケットの許可範囲に入れる**（申し送り 0038）。名称・パスを変えると、それを入力や期待値に持つテストが赤くなる。変更対象ごとに `grep -rn "<旧名>" --include="test_*.sh"` を実行し、ヒットしたテストファイルをそのステップの `allow.write` に加える。「実装は直したがテストが古いまま」は同じチケットの中で閉じる
- **値の往復（書く側と読む側）が要る修正は、両側の許可範囲を同じチケットに置く**（申し送り 0034 / 0035）。書き出す側だけを直すと読み取り側が古い形を期待して壊れ、読み取り側だけを直すと書き出しが追いつかない。エスケープ・シリアライズ・状態ファイルのスキーマのように往復するものは、**書く側・読む側・その両方を検証するテスト**の 3 点をひとまとまりのステップにする
- **ロックアウト対策**: 中核（入口ガード・フック・`settings.json`）を変えるステップには、変更後の最初の操作で自分が止まる可能性と復旧手順（どのファイルを基準点に戻すか。強制無効化 `WORKFLOW_ENTRY_ENFORCE=0` はユーザーの明示があるときだけ）を書く
- 許可範囲案はステップごとに最小（`.claude/` 配下の対象アセット・テスト・`logs/`）。ただし上の 3 つ（テストの `ops` 両方・依存するテストファイル・値の往復の両側）は「最小」より優先する。狭すぎる宣言は WF204 / WF205 で止まり、チケットの途中で範囲を広げる相談になるためで、**その相談を避けるために計画の段階で入れておく**のが最小化より大事である
- 人間レビュー要否の既定（方針が無い場合）: AI アセット実装計画チケット「要」、中核を含む実装チケットも「要」
- 見てほしい点の固定項目: ステップ順と中核・テストの隣接 / テスト ID の割付の漏れ / 参照更新一覧の検索根拠 / ロックアウト対策
