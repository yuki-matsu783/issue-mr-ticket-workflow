# アプリ向け仕様書の節構成をチケットボード拡張の仕様書で定める

## 背景

`.claude/skills/20-common-step-spec` は、仕様書の節構成を種別ごとに固定している。定められているのはスキル・エージェント・フックの 3 種で、いずれも AI アセットである。

このリポジトリには `design-docs` ルールがあり、アプリ本体の設計文書を `docs/00_requirement/` と `docs/10_spec/` に置くことを定めているが、仕様書の節構成は定めていない。チケットボード拡張はアプリ本体であり、当てはまる型が無い。

## 決定

チケットボード拡張の仕様書 `docs/10_spec/vscode-ticket-board.md` の節構成を次のとおりとする。

概要・禁止事項 / 配置 / 起動と入口 / モジュール構成 / データの形 / 処理フロー / HTML の構造と CSP / 不備の識別子とメッセージ / テスト観点 / 要件との対応

このうち「概要・禁止事項」「処理フロー」「テスト観点」「要件との対応」は機構のスキル向け節構成から採り、「配置」「起動と入口」「モジュール構成」「データの形」「HTML の構造と CSP」「不備の識別子とメッセージ」はアプリ固有として追加した。

不備の識別子は `TB` + 3 桁とし、この仕様書がその台帳を兼ねる。

## 理由

- 機構のスキル向け節構成のうち、「要件との対応」表による実装漏れ・過剰仕様の検査と、テスト ID の割付は種別によらず有効なので残した
- 「IN / OUT」「呼出条件」はスキルがエージェントから呼ばれる前提の節で、利用者がコマンドで起動するアプリには合わない。代わりに「起動と入口」を置いた
- アプリは複数のモジュールに分かれ、型と関数の署名が実装の契約になる。「モジュール構成」と「データの形」を独立した節にしないと、実装が推測なしに作れる粒度に届かない
- 識別子の接頭辞は、機構の台帳 `.claude/docs/10_spec/フック共通仕様.md` §6 が AI アセット用であり、アプリの識別子はその管理対象に含まれない。仕様書が自分で台帳を持つのが自然

## 却下した案

- **スキル向けの節構成をそのまま流用する**: 「呼出条件」「IN / OUT サンプル」「OUT ひな形」「参照ナレッジ」がアプリに合わず、空節か無理な読み替えになる
- **節構成を決めずに書く**: 次にアプリの仕様書を書くときに毎回決め直すことになり、書式が揺れる
- **`20-common-step-spec` にアプリ種別を追加してから書く**: `.claude/skills/**` への書き込みは AI アセット実装タスクの領分で、この issue のフェーズ列に含まれない。設計タスクの許可範囲は `docs/**` に限られる

## 影響

- 次にこのリポジトリでアプリ本体の仕様書を書くとき、この DDR が先例になる
- 機構側の `20-common-step-spec` にアプリ種別の節構成を追加する余地が残る。フィードバック計画で別 issue にするか判断する
