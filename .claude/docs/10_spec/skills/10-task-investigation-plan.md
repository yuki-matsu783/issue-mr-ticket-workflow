# 10-task-investigation-plan スキル 仕様

## 概要・禁止事項

調査計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-investigation-plan.md](../../00_requirement/skills/10-task-investigation-plan.md)。

**計画タスク（`10-task-*-plan`）に共通する処理フローの正はこの仕様書**で、他の計画タスクの仕様は差分だけを書く。

禁止事項:

- 計画書・チケット・`wip/tmp/` 以外への書き込み（ソースコード・設計文書・`.claude/` 配下。調べたい・直したい箇所は計画書の対象に書いて実施チケットへ）
- 全体計画書・issue の受け入れ条件の書き換え（疑義は結果報告の「見てほしい点」へ）
- 次の計画チケットの推測での作成（フェーズ列に無ければ不整合として報告）、次の次のチケットの先回り作成
- 計画書への調査結果・経過の記載（「これから何をするか」だけ）
- 計画書・チケットの二重作成（再開時は現在地から）
- 目視での次チケット選択（`ticket.sh next` に従う）

## 呼出条件

- `00-workflow-issue-mr-driven` の `next` が調査計画チケットを示したとき、全体計画で合意した実行者（サブエージェントのモデル）で読み込まれる。サブエージェントはユーザーと対話しない（計画タスクに承認ポイントは無い）

## IN / OUT

| IN | OUT |
|----|----|
| 全体計画書（フェーズ列・方針・判断が必要になりそうな点）、issue の受け入れ条件、リポジトリの現状（読むだけ） | 調査計画書（`wip/20_plans/`、md + HTML）、調査チケット群（未着手、少数）、次の計画チケット 1 枚、完了済みの調査計画チケット、結果報告 |

## IN / OUT サンプル

- 計画書: `wip/20_plans/0002-investigation-plan.md` / `.html`
- 調査チケット: `0003-investigation.md`（観点「既存の認証ミドルウェアはどこで空パスワードを弾いているか」）、`0004-investigation.md`（観点「バリデーション層のテストの有無と形式」）
- 次の計画チケット: `0005-design-plan.md`
- 結果報告: 「計画書 0002、調査チケット 2 枚、次は 0005 設計計画。見てほしい点: 観点が受け入れ条件 2 を網羅しているか / 2 枚の粒度 / 実装に踏み込んでいないか / 次の種類がフェーズ列と一致するか」

## 処理フロー

### 計画タスクの共通手順（正）

1. **着手**: `ticket.sh start <番号>`（作業中が他にあれば TK002 で止まる）。以後、作業ログはその都度追記する
2. **入力の確認**: 全体計画書（対象 issue・フェーズ列・方針）と前フェーズの成果物を読む。全体計画書が無い・フェーズ列が読めない・前フェーズの成果物とチケットが対応しない場合は計画書を書かず、状態の不整合として結果報告に書いて呼び出し元に戻す
3. **計画書**: `wip/20_plans/<自チケット連番>-<種類>.md` をテンプレートから作り、`20-common-step-report-view` の手順で同名 HTML を作って検査する。内容は各仕様の OUT ひな形
4. **実施チケット群**: `ticket.sh create` で 1 枚以上作る。DoD は各仕様の型、先行チケットで依存を示す。実行者・人間レビュー要否・やってよいことは全体計画の方針（と `rules/work-defaults.md`）に従い、外す場合は理由をチケットに書く
5. **次の計画チケット**: 全体計画書（フィードバック計画以降はフィードバック計画書）のフェーズ列で次に来る計画チケットを 1 枚だけ作る（次が無ければ全体まとめ）。その `predecessors` には 4 で作った実施チケット群の全番号を入れる（`ticket.sh next` は先行が未完了のチケットを飛ばすため、実施群が終わるまで計画チケットは走らず、レビュー指摘の追加チケットも先行に加えるだけで割り込める）。フェーズ列に書かれていなければ作らず不整合として報告する。「対象なし」の場合は 4 を飛ばし、計画書に対象なしの根拠を書いてこの 1 枚だけを作る
6. **完了**: `ticket.sh complete`（DoD: 計画書がある / 実施チケットの DoD が計画書と対応 / 次の計画チケットがある。作業ログの必須項目・成果物のコミット済みも検査される）
7. **結果報告**: 計画書の場所・実施チケットの枚数・次の計画チケット・レビューで見てほしい点（各仕様の固定項目）を呼び出し元に返す。push・MR 本文更新・レビュー依頼は呼び出し元

- 再開: 作業ログ「現在地」から続け、計画書・チケットを二重に作らない
- 差し戻し（同種の追加チケットで戻る）: 計画書と起票済みの未着手チケットを直し、完了済みは戻さない。対応を「判断と根拠」に残す
- 書き込みの拒否: 範囲を広げる確認を求めず、その内容を計画書の対象に書いて実施チケットへ回す
- 次の計画チケットが無いまま完了しようとしても DoD で拒否される（作ってから完了）

### 調査計画の固有手順

- 3 の計画書で、**調査観点**は全体計画書の「判断が必要になりそうな点」と issue の受け入れ条件から導き、答えが次の計画に効かない問いは含めない。1 観点のまとまり = 1 チケット
- 観点にリポジトリ外の情報が要るもの（外部技術調査）があれば、計画書で外部技術調査のチケットとして明示し、その「やってよいこと」に外部への問い合わせ（`allow.ops` の `web`）を含める（明示のないチケットはリポジトリ内の読み取りに限る）。この宣言は `curl` / `wget` に対して機構が強制する（`WebFetch` / `WebSearch` は強制されない。`フック共通仕様` §8。DDR i0009-41）
- 観点に**既存のテスト・ビルドを動かして確かめる**必要があるもの（例: 参考実装のテストが実行環境で通るか）があれば、計画書の「対象と方法」に実行するコマンドと範囲を書き、そのチケットの「やってよいこと」に `allow.ops` の `build-test` を含める（明示のないチケットは実行しない。上限の型は `フック共通仕様` §8。DDR i0006-05）
- `.claude/**` への一時的な変更（`settings.json` へのフックの一時登録など）は計画しない。機構の上限（`investigation` は `.claude/**` を deny、`settings.json` は毎回確認）が拒否する経路であり、確かめたいことは既存の記録（transcript・`logs/`）で代えるか、AI アセット実装フェーズの検証に回す
- issue の種別が AI アセットなら、読む対象は `.claude/` 配下のアセットとその要件・仕様・DDR（問いの立て方は同じ）
- 調査チケットの DoD の型: 「観点『{{問い}}』への答えが調査結果レポートに書かれている」「根拠（ファイル・行・コマンドの出力）が添えられている」「答えが出なかった問いは理由付きで残課題に残っている」
- 人間レビュー要否の既定（方針が無い場合）: 調査計画チケット・調査チケットとも「要」
- 見てほしい点の固定項目: 観点が判断点と受け入れ条件を網羅しているか / チケットの粒度と枚数 / 調査の範囲が実装に踏み込んでいないか / 次の計画チケットの種類がフェーズ列と一致しているか

## OUT ひな形

`assets/investigation-plan.template.md`（HTML は report-view の計画書用テンプレート）:

| 節 | 内容 |
|----|------|
| 対象 | issue・MR |
| 調査観点 | 問いの一覧と、それぞれがどの判断点・受け入れ条件に効くか |
| 対象と方法 | 問いごとの読む場所・確かめ方（書き込みなし）。外部技術調査は明示 |
| 調査チケット | どの問いをどのチケットが担うか・依存 |
| 成果物の形 | 調査結果レポートに何が書かれていれば次の計画が判断できるか |
| 保留した点 | 判断を保留した項目 |
| 対象なし | 該当時のみ: 根拠 |
