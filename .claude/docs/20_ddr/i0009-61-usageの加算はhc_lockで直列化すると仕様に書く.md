# i0009-61. `usage` の加算は `hc_lock` で直列化すると仕様に書く

## 背景

`i0009-23` は並行書き込みを 3 段階で規定し、3 段階目（read-modify-write が競合し得るもの）の例として `usage/<branch>.json` を挙げ、影響に「`10_spec/hooks/22-PostToolUse/post-push-usage-report.md`（`usage/<branch>.json` の加算をロックで直列化）」と書いた。

ワーク境界の 2 巡目レビューで、**当該仕様に「ロック」の語が 1 つも無い**ことが分かった（`grep -n 'ロック\|lock' post-push-usage-report.md` の一致は 0 件）。実際に競合するのは `--accumulate` の制御方式 4（「`logs/usage/<branch>.json` の該当セッション … に加算し `last_offset` を更新する」）で、ここに `mkdir` ロックも 2 秒での諦めも `hc_lock` の使用も書かれていなかった。一時ファイル + `mv`（2 段階目）は「既定」側にだけ入っていた。

**R22（1 巡目の指摘）は §5 と `HK-T17` では閉じたが、実装される側の仕様では閉じていなかった** — `i0009-58` が規約にした「横断で決めた規則を個別の仕様まで降ろす」の型そのものである。

## 決定

- `post-push-usage-report` の `--accumulate` の加算に **`hc_lock usage-<branch>` を取ってから加算する**ことを明記する
- 取れなければ **2 秒で諦めて加算せず、実行ログに 1 行残して終了 0**（案内側なので通す。`i0009-49`）
- 「既定」側の加算にも同じ規則を当てる
- ロックの陳腐化（60 秒）は `hc_lock` が持つ（`i0009-60`）ので、この仕様には書かない（数値を 2 か所に置かない）

## 理由

- **競合する当人の仕様に書かなければ実装されない**。`§5` は共通の規則で、`HK-T17` は lib 単体のテスト。フック本体を書く人が読むのは個別仕様なので、そこに無ければ素の `>` で書く実装になる
- **`usage/<branch>.json` は並行するサブエージェントの SubagentStop が同時に加算し得る**（`i0009-23` の想定そのもの）。しかも `i0009-50` で「サブエージェントは既定で background」と分かったので、**複数のサブエージェントが同時に走っている状態が既定**である。競合の確率は当初の想定より高い
- **数値は 1 か所に置く**。2 秒（`hc_lock`）と 60 秒（陳腐化）はどちらも `hc_lock` の契約で、個別仕様は「`hc_lock` を使う」とだけ書く（`i0009-49` の契約の表と揃う）

## 却下した案

- **`§5` への参照だけを書く**（「並行書き込みは §5 に従う」）: どの操作にどの段階を当てるかが読み手の判断になる。`--accumulate` の加算が 3 段階目だと明示する
- **ロックを使わず、加算を追記だけのファイル（JSONL）に変える**: 集計を読むたびに全行を畳む必要があり、`usage/<branch>.json` を「そのまま読める集計結果」として使う設計（`post-push-usage-report` の出力）が崩れる
- **`hc_json_write`（一時ファイル + `mv`）だけで済ませる**: read-modify-write の競合は防げない（2 つのプロセスが同じ古い値を読んで、後勝ちで片方の加算が消える）

## 影響

- `10_spec/hooks/22-PostToolUse/post-push-usage-report.md` `--accumulate` 制御方式 4・既定の加算
- `20_ddr/i0009-23`（影響に挙げた反映が済んでいなかったことの解消）
- 関連: `i0009-38`（`hc_lock` を `hook-common.sh` に）・`i0009-49`（諦めたときの記録先）・`i0009-60`（陳腐化）・`i0009-58`（横断→個別に降ろす規約）
