  1. 1

    章の骨格とフロー節の順序は全件守られている ◎良 根拠: 45 件の全数集計

    ## 概要 の下位項目（**背景** / **目的** / **スコープ** / 含む: / 含まない:）は 45 件すべてに存在する。制約条件 の **技術的制約** ラベルも 45 件すべてにある。受け入れ基準の 1〜3 番目の節は メインフロー → 代替フロー → 例外フロー の順で、45 件すべてが規定文言で始まっている。

    根拠を見る（実行コマンドと出力） 
    概要の下位項目の出現数 (n=45): {'**背景**': 45, '**目的**': 45, '**スコープ**': 45, '含む:': 45, '含まない:': 45}
制約条件の項目数: 中央値3 最大11 最小2 / 「技術的制約」ラベルあり 45 件

    結論

    テンプレートが固定している部分は機能している。改訂はテンプレートの章立てではなく、受け入れ基準の内側に限定してよい。

  2. 2

    メイン / 代替 / 例外の振り分けに判定基準が無く、同じ性質の記述が別の節に入っている ✕問題 根拠: 節の中身の読み合わせ

    同じ「呼び出し元に返して止まる」振る舞いが、書によって代替にも例外にも入る。

    記述置かれている節書
    同名のブランチが既に存在する → 上書きせず別案を返す代替フロー20-common-step-feature-mr
    未コミットの変更がある状態で呼ばれた → ブランチを作らず返す例外フロー20-common-step-feature-mr
    push 前チェックを意図的に飛ばす → 理由を差分に残してから飛ばす代替フロー20-common-step-commit-push
    直前のコミットに誤りが見つかった → 訂正の新規コミットで直す例外フロー20-common-step-commit-push

    前の 2 行はどちらも「前提が満たされず、処理を進めずに呼び出し元へ返す」で性質が同じなのに節が違う。後ろの 2 行はどちらも「失敗ではないが通常と違う道を通る」で性質が同じなのに節が違う。

    さらに、同じ代替フローの中に性質の違うものが同居している。20-common-step-feature-mr の代替フローは 2 項目あり、片方（ブランチ名の衝突）は停止して呼び出し元の判断を仰ぐ、もう片方（open な MR が既にある）は別の道で目的を達成して完了する。読み手は節名からどちらか判別できない。

    根拠を見る（実行コマンドと出力） 
    $ awk '/^### 代替フロー/{f=1} /^## 前提条件/{f=0} f' skills/20-common-step-feature-mr.md
### 代替フロー
- If 同名のブランチが既に存在する場合、Then スキルは上書きせず、別の slug を提案して呼び出し元に確認を返さなければならない。
- If 現在のブランチに紐づく open な MR が既にある場合、Then スキルは新しく作らず、既存の MR の番号と URL を返さなければならない（1 ブランチ = 1 MR）。

    結論

    「誰が起点か（利用者の選択 / 環境の状態 / 外部の失敗）」と「その道の終わり方（目的を達成する / 達成せず返す）」の 2 軸で判定基準を作れば、上の 4 例はいずれも一意に決まる。設計で軸を確定する。

  5. 5

    自由記述のばらつきは章の中ではなく、受け入れ基準の 4 番目以降の節に出ている △注意 根拠: 4 番目以降の節見出しの全数集計と自由記述章の文字数分布

    自由記述章の粒度は揃っている。## 概要 は中央値 714 字、最小 517 字、最大 1,716 字で、最大の 1 件（唯一の横断文書）を除けば 517〜1,078 字に収まる。非機能要件 の表も中央値 4 行、最小 2 行、最大 7 行で安定している。

    揺れているのは受け入れ基準の 4 番目以降の節で、45 件に合計 45 個の節があり、見出しは 30 種類ある。

    見出し件数
    他のスキル・機構との整合23
    承認ポイント3
    用語辞書 / 正史のみの記述 / DDR の運用各 2
    その他（調査結果レポートの内容、要件書の形、判定基準、タスクの構成 など 27 種類）各 1

    規定文言は「他のスキル・機構との整合」だけで、それ以外の 27 種類は各書が独自に切った節。中身を見ると「他のアセットとの関係」ではなく「その書が定める成果物の中身の規定」で、整合とは別の役割を持っている。

    根拠を見る（実行コマンドと出力） 
    概要章: 平均749 中央値714 最大1716 最小517 (n=45)
非機能要件の行数: 平均4.2 中央値4 最大7 最小2
4番目以降の節見出し: 45 個 / 30 種類（最頻「他のスキル・機構との整合」23 件）

    結論

    「自由記述を減らす」よりも「4 番目以降の節に何を置けるか」を規定するほうが効く。設計では、名前付きの規約節を正式な型として認めるか、整合の節に寄せるかを決める。

  6. 6

    mermaid の GitHub 上のレンダリング範囲を一次情報で確認できなかった △注意 根拠: egress 制限によりアクセス不可

    Web 検索の二次情報では、mermaid は issue・PR・Discussions・wiki・リポジトリ内の Markdown で描画され、複雑なファイルはタイムアウトして平文にフォールバックすることがある、とされる。PR の差分表示で描画されるかは、二次情報の中でも記述が分かれた。

    リポジトリ内に mermaid の既存利用は 1 件も無い。既存の図は SKILL.md の ASCII アート（00-workflow-issue-mr-driven の冒頭）で、要件書には図が無い。

    根拠を見る（実行コマンドと出力） 
    {"error_type":"EGRESS_BLOCKED","domain":"docs.github.com",
 "message":"Access to docs.github.com is blocked by the network egress proxy."}

    結論

    描画される場所に依存しない設計にする。PR の差分は行単位なので、mermaid のソースが平文のまま読めることを型の要件にする（1 行 1 ノード、ノード名を意味のある日本語にする、など）。描画の有無は人間のレビュアーが GitHub 上で実地に確認できるため、残課題として渡す。

設計への反映

  1. フローの判定基準を「起点（利用者の選択 / 環境の状態 / 外部の失敗）」×「終わり方（目的を達成する / 達成せず返す）」の 2 軸で定める。2 の 4 例が一意に決まることを確認する
  2. メインフローのノード数上限を 12〜15 の範囲で確定する。3 の分布を根拠として書に残す
  3. 分割ルールは 4 の前例（メインフロー: <名前>）を明文化し、分けた図どうしの参照方法を足す
  4. mermaid 記法は「ソースが平文で読める」ことを要件に置く。描画されない場所があっても成立する形にする（6）
  5. 受け入れ基準の 4 番目以降の節を型として規定する（5）。反映先は要件書と ai-asset-design-docs ルール
  6. 自由記述章は現状で揃っているため、分量の目安を追認する形で書く（中央値 714 字を根拠に上限の目安を置く）
