block-chmod 1 本だけを settings.json に登録し（fail-closed ラッパー無し）、T6（permissionDecision: deny + 終了 0 が実際に効くか）を測った。結論は「効いた」。exit 2 + stderr への切り替えは要らない。同時に 0036 で「代償」として受け入れた過剰拒否を、登録から 3 回目の Bash 呼び出しで踏んだ。原因は 0036 の想定（実行体の難読化）ではなくヒアドキュメントで、cmdpos が「クォート・コメント・ヒアドキュメント本文」を同じ _ に潰すため、実行位置ですらない本文が「実行体を特定できない段」として数えられていた。

◆特に見てほしい

判断に困っている

  • r1（✕問題）過剰拒否の頻度が実測で「登録から 3 回目」だった。0036 では「実運用でこの形をどれだけ踏むかは測れていない」と書いたが、実測の答えがこれ。しかもこのプロジェクトはヒアドキュメントで一時スクリプトを書く運用で、かつ chmod について書く文書を大量に作るので踏み続ける。0029 / 0030 の前に直すべきだと考えており、追加チケットを提案する（3 章）
  • r2（△注意）拒否理由の文面が、実際に踏む状況と噛み合っていない。「実行権限の変更は不要で、スクリプトは 'bash <パス>' で実行する」は、文書に chmod と書いただけで踏んだ読み手には何の案内にもならない（3 章）

◇承認が欲しい

方針は決めた

  • r3: chmod +x <ファイル> ではなく chmod --version で測ったこと（拒否が効かなかった場合でも権限が変わらないため。1 章）
  • r4: .gitignore に .claude/settings.json.bak-* を足したこと。このチケットの allow.write の範囲外で、逸脱として記録した（4 章）

・細かいレビューは不要

ほぼ確実

  • 登録した JSON 1 件の中身（matcher Bash|PowerShell / bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/20-PreToolUse/block-chmod.sh"）
  • decisions.jsonl の 10 項目の名前（2 章）

確かめられなかったこと（この結果が言っていないこと）

  • 測ったのは deny の 1 経路だけ。allow / ask の効き方、systemMessage の到達、additionalContext は測っていない（0031 の 4c）
  • フックの実行コストは測っていない。登録状態での 1 回あたりの上乗せは 0031 で測る
  • ラッパー（fail-closed）の振る舞いは測っていない（0031 の ②）
  • 拒否が「終了 0 + deny JSON」だったことは、フックの実装がその経路しか持たないことから言っている。Claude Code 側がどちらの形を受け取ったかを外から直接観測してはいない
  • 過剰拒否の全体像は測っていない。ヒアドキュメント由来の 1 経路を切り分けただけで、ほかにどんな形が _ の段を作るかは網羅していない
  • 1 セッション・1 ホストでの実測。ほかの OS・ほかのセッションでの再現は見ていない

実施した内容と結果

  1. 1

    T6 は効いた ◎良 根拠: 登録状態での実測 1 件

    chmod --version（権限を変えないので、拒否が効かなかった場合でも副作用が無い）を実行したところ、ツール呼び出しがブロックされ permissionDecisionReason の全文が届いた。block-chmod の拒否経路は hook_deny → __hc_emit_decision deny → exit 0 の 1 本しかない。

    根拠を見る（実行コマンドと出力） 
    （ツール呼び出しがブロックされ、次が表示された）
WF501: 禁止コマンド 'chmod' の実行。実行権限の変更は不要で、スクリプトは 'bash <パス>' で実行する。
権限変更が本当に必要なら、迂回せずユーザーに提案すること

    結論

    exit 2 + stderr への切り替えは不要。hook-common.sh の出力ヘルパも block-chmod も変更していない。仕様 §3 との食い違いも無い。

  2. 2

    記録は 10 項目すべて埋まり、session_id が実値になった ◎良 根拠: decisions.jsonl の 1 行

    単体実行（bash <script> < 入力 JSON）では session_id が unknown だったところが、登録して走ると実値が入る。ticket にも作業中チケットが入り、__hc_resolve_worktree → doing の走査が登録状態でも動いていることが分かる。

    根拠を見る（実行コマンドと出力） 
    {"ts":"2026-09-02T18:42:49+09:00","session_id":"ee9cc8e9-880f-493f-9396-316e4fe45fa9",
 "hook":"block-chmod","event":"PreToolUse","decision":"deny","id":"WF501","tool":"Bash",
 "target":"chmod: chmod --version 2>&1 | head -1; echo \"rc=$?\"",
 "ticket":"0028-ai-asset-implementation.md","note":"禁止コマンド 'chmod' の実行。…"}

許可側は静か: 登録後の Bash 呼び出し 10 数回に対し、増えたのは拒否の 2 行だけ

    結論

    0031 の T2（記録の突き合わせ）はこの形で設計できる。

  3. 3

    過剰拒否を登録から 3 回目で踏んだ ✕問題 根拠: 再現 4 形 + 対照 5 形

    登録から 3 回目の Bash 呼び出し（ヒアドキュメントで .py を書く操作）が WF501 で拒否された。理由は「実行体を特定できないため拒否側に倒した」。切り分けると原因はクォート一般ではなくヒアドキュメントだった。cmdpos.sh:52 は「クォート・コメント・ヒアドキュメント本文をプレースホルダ _ へ潰す」と書いてあり、実装もそのとおり。3 つの別物が同じ _ になる。0036 が入れた _bc_exe_unknown は「実行体がすべて _ = 潰れたクォート由来 = 難読化」と読むので、ヒアドキュメント本文の _ を難読化と誤読する。本文は実行位置ですらない（bash は決して実行しない）。

    根拠を見る（実行コマンドと出力） 
                                    判定    正規化後の段
1 ヒアドキュメント（再現）      DENY    [0]cat [1]_
2 同じ内容・禁止語だけ除く      ALLOW   [0]cat [1]_
3 ヒアドキュメント無し          ALLOW   [0]echo
4 禁止語 + 変数展開             ALLOW   [0]echo
5 禁止語のみ                    ALLOW   [0]echo
6 変数展開のみ                  ALLOW   [0]echo
7 禁止語 + クォート内の改行     ALLOW   [0]printf

ヒアドキュメントの 4 形すべてで同じ段ができる:
<<'PY'（クォート付き）  [0]cat [1]_
<<PY（クォート無し）    [0]cat [1]_
<<-PY                   [0]cat [1]_
<< PY（空白あり）       [0]cat [1]_
ヒアドキュメント無し    [0]cat [1]x      ← 対照

    結論

    対照（3〜7）がすべて ALLOW であることから、0036 が代償として想定していた形とは別の経路だと分かる。迂回せず、同じ内容を Write ツールで書いてから python <ファイル> で実行した（環境変数での無効化・語の分割・別構文での言い換えは、いずれも拒否の回避なので採らない）。

  4. 4

    宣言した許可範囲から外れた操作を 1 件行った △注意 根拠: TK003 で止まったため

    .gitignore に .claude/settings.json.bak-* を 1 行足した。このチケットの allow.write は .claude/hooks/** と .claude/settings.json だけなので範囲外。人間が取ったバックアップが未追跡のまま残り、ticket.sh complete の「チケット以外に未コミットの変更がある」検査（TK003）で止まったため。

    根拠を見る（実行コマンドと出力） 
    取れる手は 3 つ:
 (a) バックアップをコミットする   → ローカルの安全網をリポジトリに持ち込むので採らない
 (b) 消す                         → 0031 の ② が終わるまで人間の復旧手段を奪うので採らない
 (c) 追跡外にする                 → これにした

$ bash .claude/skills/20-common-step-ticket/scripts/ticket.sh complete 0028
- チケット以外に未コミットの変更がある（1 件: .claude/settings.json.bak-0028 ）
TK003: 完了できない。未充足 1 件

    結論

    workflow-guard は未登録なので機械的には止められなかった。登録後は同じ操作が止まるはずで、そのときは宣言を直してから行う。

  5. 5

    「新しいセッションが要る」は不要だった △注意 根拠: 登録 18:40 → 発火 18:42

    事前の想定では settings.json の変更はセッション開始時にしか読まれないので再起動が要ると考えていたが、同じセッションの途中で登録が反映された。

    根拠を見る（実行コマンドと出力） 
    18:40  人間が .claude/settings.json に hooks.PreToolUse を 1 件登録
18:42:42  ticket.sh start 0028（通常の Bash 呼び出し・通る）
18:42:49  chmod --version → WF501 deny（= このセッションで発火している）

    結論

    段階登録の手順から「新しいセッションを開く」を外してよい。

設計への反映

  1. 追加チケット（最優先。0029 の前）: ヒアドキュメント本文の _ を実行位置として数えない。cmdpos が本文（およびコメント）由来の段に印を付け、block-chmod がその段を実行体の判定から外す。併せて拒否理由に「何が判定を妨げたか」を添える
  2. 追加チケット（0029 の前）: hook_record のログ用の値と JSON 用の値を分ける／HOOK_SESSION_ID と HOOK_NAME も __hc_json_str に通す。0029 / 0030 の 10 本がすべて hook_record を使うので先に直す
  3. 0031 へ: T6 が効いたので ① ② は計画どおり。手順から「新しいセッションを開く」を外す。ただし過剰拒否を先に片付けないと、拒否側 4 本を足した段階で作業が止まる危険がある
  4. 0032 へ: チケットの allow.write に「自分の作業ログの置き場（wip/10_tickets/**）」を必ず含める規約が要る

想定と異なった点

計画時の見込み実際どう扱ったか
settings.json の登録は新しいセッションでないと効かない同じセッションの途中で反映された段階登録の手順から「新しいセッションを開く」を外すことを提案
0036 の過剰拒否は「実行体に難読化があり、かつ禁止語に言及する」形実際に踏んだのはヒアドキュメント。対照（禁止語 + クォート + 展開）はすべて ALLOW原因を cmdpos の _ の多義性まで切り分け、追加チケットを提案
過剰拒否の頻度は測れない登録から 3 回目で踏んだ0036 の r1 に対する実測の答えとして記録
チケットの allow.write は作業に足りている作業ログの置き場（wip/**）が入っていなかった逸脱として記録し、規約の候補を 0032 へ送った

残課題

  • ヒアドキュメント由来の過剰拒否（追加チケットで解消）。未解消のまま 0030 の拒否側 4 本を足すと作業が止まる
  • 拒否理由の文面が過剰拒否の状況と噛み合っていない（同上）
  • hook_record のログの値が JSON エスケープ済み／HOOK_SESSION_ID と HOOK_NAME が __hc_json_str を通っていない
  • allow.write に wip/** が無いチケットが残っている（0029 以降も要確認）
  • shellcheck の未導入（環境の制約）
  • バックアップ .claude/settings.json.bak-0028 は追跡外で残る。0031 の ② が安定したら人間が消す
