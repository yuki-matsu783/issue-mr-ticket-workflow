# 10-task-design-plan — 設計書の一覧と骨子を決める

共通手順の禁止事項（`10-task-investigation-plan` の冒頭が正）に加えて、設計文書（アプリルートの `docs/` 配下）の**本文を書き始めない**（骨子まで。本文は設計チケット）。`.claude/` 配下の文書を設計書の一覧に含めない（AI アセット設計フェーズの担当）。調査結果の根拠と矛盾する結論方針を書かず、調査結果に無い事実を根拠なしに使わない。決めきれない判断点を推測で決めない。

## 目的

調査で並んだ候補から採る案を決め、どの設計書に何を書くかを骨子まで固めて設計チケットに割る。

- 要件: `.claude/docs/00_requirement/skills/10-task-design-plan.md`
- 仕様（正。固有手順・OUT ひな形）: `.claude/docs/10_spec/skills/10-task-design-plan.md`
- 処理の共通手順（正）: `10-task-investigation-plan` の「計画タスクの共通手順（正）」

## 手順

共通手順（着手 → 入力の確認 → 計画書 → 実施チケット群 → 次の計画チケット → 完了 → 結果報告）は `10-task-investigation-plan` に従う。ここでは固有部分だけを示す。

- 入力に調査結果レポートが無い（調査が「対象なし」だった）ときは、全体計画書と受け入れ条件だけで計画を書き、根拠の不足を見てほしい点に明示する
- 計画書の**結論方針**は、調査結果の候補から採る案を比較軸ごとの根拠付きで書く。決めきれない点は「設計チケットで結論を書く」と明示するか、調査の追加を結果報告で提案する
- **設計書の一覧**はアプリルート `apl/<アプリ名>/` の `docs/` 配下（既存の構成に従う）を対象に、新規 / 更新の別・置き場・骨子を書く
- 設計チケットは**関連する機能のまとまり**単位にする（1 チケット = 1 まとまりの要件定義書 + 仕様書。設計書 1 つずつに割らない）
- **設計チケットの DoD の型**: 「設計書が機構のテンプレートに沿って作成（更新）されている」「設計計画書の骨子の各節が埋まりプレースホルダが無い」「受け入れ条件 {{X}} が受け入れ基準 / テストシナリオに落ちている」「設計中の決定の経緯が DDR に残っている」
- 人間レビュー要否の既定（方針が無い場合）: 設計計画チケット・設計チケットとも「要」
- **見てほしい点の固定項目**: 結論方針と調査結果の整合・決めきれない点の明示 / 設計書の一覧の過不足（新規か更新か）/ 骨子が受け入れ条件を漏れなく受けるか / 設計チケットの粒度と次の計画チケットの種類

## OUT ひな形

`assets/design-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR |
| 判断点の結論方針 | 採る案と比較軸ごとの根拠。決めきれない点の明示 |
| 設計書の一覧 | 新規 / 更新・置き場（アプリルートの `docs/` 配下）・骨子 |
| 受け入れ条件との対応 | 条件 × 設計書の受け入れ基準・テストシナリオ |
| 設計チケット | 機能のまとまりごとのチケットと依存 |
| 保留した点 / 対象なし | 該当時 |

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 調査結果レポートが無い | 全体計画書と受け入れ条件だけで書き、根拠の不足を見てほしい点に明示する |
| 判断点が決めきれない | 推測で決めない。設計チケットで結論を書くと明示するか、調査の追加を提案する |
| 設計書の置き場が既存の構成と合わない | 勝手に構成を変えず、保留した点に書いて見てほしい点に載せる |
| 共通手順で止まった（TK002 / TK005 / RV00x） | `10-task-investigation-plan` の「エラー時の対処」に従う |
