# 20-common-step-requirement — 要件は外から見える振る舞いだけを、正史として書く

内部構造（スクリプト名・コマンド・判定順・スキーマ・実パス）は書かず仕様書へ回す。経緯（検討・却下案・変遷）は本文に書かず DDR へ分離する。本文に変更履歴・追記の印を残さない。「関連するドキュメント」「レビュー記録」「変更履歴」の節を置かない。合意されていない決定を書かない。同じ内容を複数の書に書かない（1 か所に書き、他は参照）。図にだけある情報（EARS の箇条書きに無い条件・分岐・禁止）を作らない。図を外部ファイル・画像・外部サービスで持たない。規約節にフロー（順序・分岐）を置かない。書く内容の合意は呼び出し元が担う。

- 要件: `.claude/docs/00_requirement/skills/20-common-step-requirement.md`
- 仕様（正。章順・節の順序・判定順・図の記法とノード数・識別子・自由記述の分量・DDR の形式・eval ID RQ-E01〜07）: `.claude/docs/10_spec/skills/20-common-step-requirement.md`

## 手順

1. **配置と命名**: 対象の種別からディレクトリ（`skills/` / `hooks/<イベント番号ディレクトリ>/` / `agents/` / `rules/`）を決め、対象と同名のファイルにする（1 対象 1 書。2 アセットを 1 書にまとめない）。横断的な内容はどれか 1 つの書に寄せ、他からは参照する
2. **新規作成**: `cp .claude/skills/20-common-step-requirement/assets/requirements.template.md .claude/docs/00_requirement/<種別>/<対象名>.md` し、frontmatter（`type: requirement` / `title` / `description` / `tags` / `keywords`）と章を順に埋める。章順は 概要（背景・目的・スコープ）→ ユーザーストーリー → 受け入れ基準 → 前提条件 → 制約条件 → 依存関係 → 非機能要件。各章のガイド（HTML コメント）は記入時に消す。スコープの「含まない」には担い先を添える
3. **受け入れ基準の節構成**: EARS（`When 〜 Shall` / `If 〜 Then` / `Shall not`）で書き、節を メインフロー → 代替フロー → 例外フロー → 規約節（0〜3）→ 他のスキル・機構との整合（0〜1）の順に置く。先頭 3 節の見出しは規定文言で始める（補足の後置は可）
4. **節の振り分け**: 記述ごとに次を上から問い、**最初に当たった**節に置く。当たらない・複数に当たると判断したら、自分で決めず記述と理由を呼び出し元に返す

   | 順 | 問い | 置き場 |
   |---|---|---|
   | 1 | 目的を達成するすべての実行が通る道か | メインフロー |
   | 2 | 起点が正常か（呼び出し元の入力・選択の違い / 対象が既に目的の状態にある / 複数の正しい入力形式） | 代替フロー |
   | 3 | 起点が異常か（前提の不充足 / 外部の失敗 / 機構の拒否 / 利用者の誤用 / 壊れた状態） | 例外フロー |
   | 4 | フローではなく成果物・データの中身の規定か | 規約節 |
   | 5 | 他のアセットとの関係の規定か | 他のスキル・機構との整合 |

   判定は**起点**で決め、終わり方は検算に使う。代替フローの項目はすべて目的を達成して終わる（達成せず返す項目が代替にあれば起点の判定を誤っている。多くは前提の不充足で例外が正しい）。例外フローは、返して止まることも回復してメインに戻ることもある
5. **メインフローの図**: EARS 箇条書きの**前**に mermaid の `flowchart TD` を 1 つ置く。ノード ID は `M1`, `M2`, … の通し番号（分割しても文書全体で継続）、判定は `{…}`、通常は `[…]`、離脱は破線 `-.->`。1 行に 2 つ以上の辺を連ねない。ラベルは日本語の動作・判定。1 図の `M` ノードは 15 まで（離脱先 `A<n>` / `E<n>` と次節への `N<n>` は数えない）。超えたら `### メインフロー: <一区切りの名前>` で分割し、節ごとに 1 図を置いて `N<n>([次: メインフロー: <次の節名>])` で繋ぐ（一区切り = 承認・引き渡し・状態の確定が起きる点。15 以下でも一区切りが明確なら分けてよい）。分割してもなお 1 節が 15 を超えるなら、対象の分割を呼び出し元に返す
6. **離脱点の対応付け**: 代替・例外フローの各項目の先頭に `**[A1]**` / `**[E1]**` を置き、図の参照ノードの ID と一致させる。図に離脱点が無い項目にも識別子を付ける
7. **規約節**: 見出しは `### 規約: <対象>` で始め、1 書に 3 節まで。置けるのは成果物・データの中身の規定で、順序・分岐は置かない。他のアセットとの関係は `### 他のスキル・機構との整合`（1 節まで）に置き、受け入れ基準の最後にする
8. **自由記述の分量**: 自由記述は 概要の導入・背景・目的 の 3 か所だけで、合計 600 字以内。他の章は定型（箇条書き・表・EARS・図）。スコープの「含む」「含まない」・前提条件・依存関係は各 5 項目以内、非機能要件は 3〜6 行。超える必要が出たら目安を無視せず、対象の分割か仕様書への移動を呼び出し元に提案する
9. **線引きの判定**: 記述ごとに「外部の観察者（利用者・レビュアー）に見えるか」を問い、見えないもの（実現手段）は仕様書へ回す。既存の要件書に内部構造を見つけたら、仕様書へ移す提案を呼び出し元に返す
10. **経緯の分離**: 決定に検討・却下案があれば DDR `.claude/docs/20_ddr/i<issue 番号 4 桁>-<連番 2 桁>-<タイトル>.md`（`type: ddr`。背景 / 決定 / 理由 / 却下した案 / 影響）を起こし、本文には現在の正だけを書く
11. **更新**: 既存の書は該当箇所を直接書き換える（履歴・「以前は〜」を残さない）。他の書と矛盾したら、矛盾する書を特定して呼び出し元に返す（片方だけ直さない）
12. **セルフレビュー**: 仕様書「セルフレビュー項目」13 項目を全件確認して呼び出し元に返す。章順・節順・禁止節の不在・EARS の形式・プレースホルダの残存に加えて、1 図のノード数（15 以下）・図の識別子と節の識別子の一致・図にあって箇条書きに無い分岐が無いこと・規約節の命名と 3 節以内・自由記述 600 字以内・一意に決まらない記述を残していないことを見る

## エラー時の対処

| 状況 | 対処 |
|------|------|
| 書こうとする内容が内部構造（コマンド・判定順・スキーマ） | 要件書に書かず、仕様書（`20-common-step-spec`）へ回す |
| 判定順を当てても節が一意に決まらない | 自分で決めない。記述と当てはまらなかった理由を呼び出し元に返す |
| 代替フローに「目的を達成せず返す」項目がある | 起点の判定を誤っている。多くは前提の不充足で、例外フローへ移す |
| 1 図が 15 ノードを超える | 詰め込まない。一区切り（承認・引き渡し・状態の確定）で節を分け、節ごとに 1 図を置いて参照ノードで繋ぐ |
| 分割しても 1 節が 15 を超える | 対象が 1 書に収まっていない。対象の分割を呼び出し元に返す |
| 図にだけ書きたい条件・分岐が出てきた | 図に足さず、先に EARS の箇条書きに足す（図は箇条書きの要約） |
| 規約節が 4 つ以上になる | 対象の分割か仕様書への移動を呼び出し元に提案する |
| 自由記述が 600 字に収まらない | 削るか、対象の分割・仕様書への移動を呼び出し元に提案する（目安を無視しない） |
| 決定に経緯・却下案がある | 本文に書かず DDR を起こし、本文は現在の正だけにする |
| 他の要件書・仕様書と矛盾する | 片方だけ直さない。矛盾する書と箇所を特定して呼び出し元に返す |
| 合意されていない決定を書くよう求められた | 書かない。合意を呼び出し元に返す |
| 2 アセットを 1 文書にまとめる依頼 | 1 アセット 1 文書に分ける。分けられない理由があれば返す |
| 「関連するドキュメント」「レビュー記録」「変更履歴」を求められた | 置かない（git の履歴と MR、DDR が担う）。理由を添えて返す |
| セルフレビューでプレースホルダ・ガイドのコメントが残っている | 埋めるか消してから返す |
