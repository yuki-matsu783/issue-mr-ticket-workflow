# i0050-03. 合流はタスクの切れ目に固定し、提供コマンド経由でのみ行う

## 背景

1 issue 内の同一フェーズのチケットを並列に実施すること（`i0050-01`）と、並列の単位を作業ツリーに置くことは決まったが、**作業ツリーの成果を feature ブランチへ戻す道が無い**。調査で次が分かっている。

- `git cherry-pick` / `rebase` / `am` は `block-direct-git` が WF401 で拒否する。`git merge <ローカルブランチ>` は `scope.sh` の分類で `unknown` → WF204 になる。AI が通せる合流は実質 2 つ（作業中チケットが 0 枚のときの `git merge` の素通りと、成果物をコピーして積み直す形）しかない
- 成果物をコピーして積み直す形は、チケットの移動を手で行うことになり、`ticket.sh` の前提（TK004「手動で動かさず `ticket.sh` で扱う」）に正面から反する。履歴と差分の基準点も失われる
- 合流をチケットごとに行うと、合流先の `10_doing/` が 2 枚になって WF207 が提供コマンド以外のすべての操作を止め、残ったチケットの差分の基準点が合流前を指したままになる。**どちらもタスクの切れ目（作業中 0 枚）で合流すれば起きない**
- 1 合流あたりの手作業は、過去 issue の実データから 25〜45 箇所と見積もられた。チケットごとに合流すると 1 issue で 1000 箇所を超え、タスクの切れ目に限れば 250 箇所前後に収まる
- 合流したという事実を残す場所が `logs/` に無い。`decisions.jsonl` には `cwd` も `agent_id` も無く（`i0050-02` で追加した）、どの作業ツリーの成果をいつ取り込んだかを後から辿れない

あわせて、`i0004-07` が `git merge` を `block-direct-git` の対象外にした理由の 1 つ「取り込み以外の `merge`（ブランチ間の統合）は `merge-base` 分類で `origin/<default>` 以外を拒否できる」が、**実装では成り立っていない**ことが分かった。`merge` の分類は引数のどこかに `origin/` があるかだけで決まるので `git merge origin/<任意のブランチ>` が `merge-base` になり、逆にローカルブランチの合流は `unknown` に落ちるが、**作業中チケットが 0 枚のときは `workflow-guard` が判定に入らないため素通りする**。合流はまさに作業中 0 枚の時点で行われるので、この統制は合流に対しては効いていない。

## 決定

- **合流の単位はタスクの切れ目**とする。合流に関わるどの作業ツリーも作業中のチケットが 0 枚であることを、合流の前提検査に置く
- **合流の実行者は AI** とし、**提供コマンド `worktree.sh merge`（`20-common-step-worktree`）経由でのみ**行う。人間の手作業を合流の必須手順にしない
- **`scope.sh` の `merge` 分類は広げない。** `merge-base` の意味は「既定ブランチの取り込み」のままにし、ローカルブランチの合流は `unknown`（WF204）のままにする。合流は分類ではなく提供コマンドで通す（`i0050-04` の「分類を広げず提供コマンドで通す」と同じ方針）
- **合流の前提検査は 6 項目**（本流で実行している / 本流と対象の双方に未コミットの変更が無い / 本流と対象の双方の作業中チケットが 0 枚 / 対象が同じ issue に属するブランチである）を全件実施し、1 つでも欠ければ 1 件も合流しない
- **自動で解けない衝突が出たら合流を中断して合流前の状態へ戻し、失敗として終える。** 衝突の中身を見て一方に寄せない（成果物の内容の判断を機械にさせない）。呼び出し元は解消を試みず人に返す
- **合流の記録は共有ルートの `logs/worktree-merges.jsonl`** に 1 回 1 行で残す。成功・取り込み済み・中断のいずれでも残す
- **サブブランチはリモートへ push しない。** 合流は常にローカルで行い、push は本流だけで行う（`20-common-step-commit-push` の push 前チェック 項目 5）

## 理由

- タスクの切れ目に固定すると、WF207（作業中 2 枚）と差分の基準点の破れが**構造的に起きなくなる**。合流の回数も 1 issue あたり 10 回前後に収まり、手作業の総量が 1/4 になる
- 提供コマンド経由なら、①既定拒否の原則を緩めずに合流だけを通せる（`scope.sh` は無変更で `provided` 分類が当たる）②前提検査と「解けない衝突は人へ返す」判定をコマンドが持てる ③合流したことをコマンドが記録できる。`i0004-07` が「取り込み用の提供コマンド」を却下した理由は「衝突解消（対話が要る）をスクリプトに閉じ込められない」だったが、**本決定は衝突解消をスクリプトに閉じ込めず、中断して人に返す**ので、その理由に当たらない
- マージコミットのメッセージは `commit.sh` の規約検査を通らないが、提供コマンドが規約に合う既定の件名（`chore: 作業ツリー <名前> の成果を合流する`）を与えるので、規約外のコミットが履歴に載らない
- 記録を `decisions.jsonl` に相乗りさせないのは、あちらが**フックの判定**の記録で書く側が全フックに限られているためと、合流は issue に属する事実で作業ツリーを片付けた後も残らなければならないため
- **`merge` 分類を広げないのは、`i0004-07` の統制の意図を保つため**である。上の背景のとおり実装では合流に対して効いていないが、それは分類の粗さと `workflow-guard` の制御方式（作業中チケットが無ければ何もしない）の帰結であって、分類を広げて追認すべきものではない

## 却下した案

- **J1 人間が合流する**: 並列の利得を人間の手数が相殺する。合流の頻度が上がるほど不利になり、レポートの衝突を人が解くことは「内容の判断を人がする」ことでもあるので、その部分だけは残しても全体を人に寄せる理由にならない
- **J2 `scope.sh` の `merge` 分類をローカルブランチの合流まで広げる**: `i0004-07` が利点として挙げた「取り込み以外の `merge` を拒否できる」を明示的に手放すことになる。マージコミットのメッセージが `commit.sh` の規約検査を通らない経路も増える。提供コマンドで足りるので、既定拒否の原則を崩す必要が無い
- **J4 成果物をコピーして本流で積み直す**: `ticket.sh` の TK004「手動で動かさない」に正面から反し、履歴と `base_sha` が失われる。チケットの状態遷移コミットを作り直すことになる
- **J5 レポートを 1 チケット 1 本に分割して衝突源を消す（全面適用）**: 旧運用への逆戻りで、「1 つのタスクの結論を読むのに複数のファイルを開く」問題が再発する。共通部の更新を並列区間から外すだけ（部分適用）で衝突の主因が消えるので、全面適用の必要が無い
- **合流をチケットごとに行う**: 合流先の `10_doing/` が 2 枚になって WF207 が全操作を止め、復旧には作業ログと `base_sha` を失う手作業が要る。手作業の総量も 4 倍になる
- **解けない衝突を AI が解消して合流を続ける**: レポートの衝突はどちらの記述が正かの判断であり、機械にさせると片方の成果が黙って消える
- **合流の記録を `logs/sh/worktree.log`（実行ログ）で足りるとする**: 自由書式なので後から機械で追えない。合流の一覧を出す用途に耐えない
- **`merge` 分類を「合流も含む」に読み替えたうえで `-c` などの危険なオプションを個別に弾く**: 分類の網羅に頼る形で、`i0050-04` が退けた考え方と同じ

## 影響

- `00_requirement/skills/20-common-step-worktree.md` と `10_spec/skills/20-common-step-worktree.md`（新規）が、`merge` の前提検査・衝突時の中断・記録・エラー識別子 `WT003` / `WT004` / `WT007` とテスト観点 `WT-T04`〜`WT-T06`・`WT-T12` を持つ
- `10_spec/フック共通仕様.md` §5 に `logs/worktree-merges.jsonl` を登録し、§6 に `WT001`〜`WT008` を登録する
- 切れ目での合流の起動（いつ `worktree.sh merge` を呼ぶか）は `00-workflow-issue-mr-driven` が持つ
- `i0004-07` のうち、**「取り込み以外の `merge` は `merge-base` 分類で拒否できる」という理由の記述だけ**が無効になる（分類は変えないが、作業中チケットが 0 枚のときは `workflow-guard` が判定に入らないので、拒否は実効ではない）。`block-direct-git` が `merge` を対象外にする決定と、`merge-base` 分類の意味は有効なまま
- **残る穴**: 作業中チケットが 0 枚のときに `git merge <ローカルブランチ>` が素通りすることと、`git merge origin/<既定ブランチ以外>` が `merge-base` に分類されることは、本決定では閉じない。前者は `workflow-guard` の制御方式 1 の帰結、後者は `merge` 分類の粗さで、どちらも合流の手順とは別の根を持つ。別 issue で扱う
