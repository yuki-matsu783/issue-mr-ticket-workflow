S1（0018）は実装フェーズの入口の設定を 2 つ変えた。①.claude/hooks/config/scope-limits.json の types["ai-asset-implementation"].allow に .gitignore を足し（.gitattributes と同じ「common.protected を明示で判定順 (2) を通す」形）、②.gitignore に .claude/worktrees/ を足した。①→② の順を守り、②が WF201 にならず 判定 stage 5 の allow で記録されたことをもって、変えた判定を実際に踏んだことを確かめた。機械テストは HK-T01 / HK-T02 とも PASS、jq -e . も成功、変更直後の Write と提供コマンド ticket.sh next も通り、機構は自分を止めていない。一方で common.confirm の壁は計画書の保留 P5 のとおり顕在化し、①の編集は呼び出し元のメインエージェントが代行した。さらに、宣言済みのパスでも workflow-diff-check が WF601（許可範囲外）を出し続けることが分かった。どちらも仕様どおりの振る舞いなので仕様は直さず、逸脱として記録した。

  1. 1

    scope-limits.json の ai-asset-implementation の allow に .gitignore を足した ◎良 根拠: git diff 9c2e4d7 / jq -e . が終了コード 0

    types["ai-asset-implementation"].allow の末尾（".gitattributes" の後ろ）に ".gitignore" を 1 要素だけ足した。差分は 1 行の置換。形は .gitattributes と同じで、common.protected に居るパスを型の allow に明示することで判定順 (2) を抜ける（フック共通仕様 §8「上限設定」）。.gitignore は common.confirm には入っていないので、明示だけで stage 5 の allow に落ちる。scope-limits.json が壊れると WF210 で全書き込みが止まるため、計画書のロックアウト対策どおり編集は 1 回にまとめ、直後に構文を確かめた。この編集は実行者（サブエージェント）ではなく呼び出し元のメインエージェントが代行した（理由は f4 と D3）。

    実装フェーズが .gitignore を書けるようになり、構文も壊れていない。

    common.confirm の壁と WF601 の見え方のずれが、計画書の想定どおり（一部は想定外に）出た △注意 根拠: 実行者側の deny と、以後全ツール呼び出しに付く WF601
