### ◆特に見てほしい（0017 分）

- **並列実施の発効を保留した**（e34）。指摘 3 に対して、示された 3 案のうち **(b)** を採った。決め手は 2 つ。①呼び出し元が用意した作業ツリーをサブエージェントに割り当てる指定が実行基盤に無く、起動プロンプトの記載では `cwd` が移らない（`subagent-start-check` 自身がそう書いている）。②基盤の隔離（案 a）に寄せる形は、**後片付け**が本機構の性質と正面から衝突する — チケットごとに `commit.sh` でコミットし `ticket.sh complete` が未コミット無しを検査するので、サブエージェントが終わる時点の作業ツリーは**必ず clean** になり、それは「変更が無ければ自動で片付ける」の発火条件そのものである。**設計上の採否（`i0050-01`）は取り消さず、発効だけを条件付きにした**が、`i0050-01` を部分置き換えにする判断なので、採否ごと取り消すべき／逆に (a) で発効させるべきなら差し戻してほしい
- **合流を手順 3-0 から手順 2c へ移し、0015 が決めた順序（R56 の決着）を上書きした**（e36）。0015 は「`boundary.sh status` → `merge`、`merge` が落ちたら切れ目の処理に進まない」で決着させたが、その位置（切れ目の処理の 0 番目 = 敵対的レビューの後）だと、レビュアーが並列区間の成果を 1 行も見ずに上限 1 回を消費する。**0015 の決定を明示的に変えた箇所**なので、変更の当否を見てほしい（DDR `i0050-09`）

### ◇判断が欲しい（0017 分）

- **`last_task` の既出集合（`covered`）を成り立たせるために、`request` / `skip` / `complete` の記録の追記点を動かした**（e37）。従来は `complete` が「直前の状態」を `review-history.jsonl` に追記していたが、それだと `skip` で閉じた切れ目が上書きで消える。**上書きする側（`request` / `skip`）が上書きの直前に追記する**形に一本化し、`complete` の追記をやめた。既存の `BD-T` の期待値に影響し得る
- **フック共通仕様 §13 に緩和の項目を 1 つ足した（R53 の決着）**（e38）。指摘 4 は識別子 `R53` を添えていたが、§13 の項目は番号を持たない形なので**番号を振らず**、本文に残課題 R53 への参照を書いた。R53 は「別 issue（`workflow-guard` の制御方式 1 の見直し）」として残す扱いのままである（塞ぐ決定はしていない）
- **eval を 2 件新設した**（`WFD-E10` = 指示されても手順 2b を始めない／`TXE-E09` = 自分の `cwd` が渡された作業ツリーでなければ始めずに返す）。どちらも「やらないこと」を測る eval で、判定方法は呼び出し回数 0 件と結果報告の記載に置いた

### ◆特に見てほしい（0015 分）

- **計画書の文書一覧に無い `subagent-stop-check` の仕様に触った**（e32）。A5 は「実行者照合が worktree ごとに一意に決まることが仕様に明記され、**機械テストで確認されている**」を求めるが、`WF801`（実行者の不一致）を発行するのは `subagent-stop-check` で、その仕様には作業ツリーの記述もテスト観点も無かった（0013 が残した R49・R50）。**A1〜A6 の全件充足を DoD に持つ本チケットで拾わないと、A5 は文書の上でだけ閉じて実装で閉じない**と判断し、経路の表（PostToolUse = 呼び出し元 / SubagentStop = 起動された側）・`WF815`（作業ツリーを確定できないため判定していない）・`SP-T09`（機械テスト）を足した。**識別子を 1 つ増やしたので、計画の範囲を超えたと見るなら差し戻してほしい**
- **`boundary.sh` の切れ目の判定（`last_task`）を「番号の連続」から「`ticket_type` のまとまり + `completed_at` の順」に作り替えた**（e27）。調査 e31 が指摘した取りこぼし（並列で種類が交互に完了すると、どの切れ目にも入らずレビューを受けないチケットが出る）を塞ぐためだが、**既存の判定の書き換え**であり、`BD-T01`（既存テスト）の期待値に影響し得る。あわせて「2 種類以上あれば古いほうを先に切り、残りは次の切れ目へ持ち越す」という新しい振る舞いを足した

### ◇判断が欲しい（0015 分）

- **`at_boundary` の判定に `worktree.sh list`（外部プロセス）を足した**（e27）。`boundary.sh` はフックではないので fork 上限（共通仕様 §1）の対象外だが、**管理対象の作業ツリーが 1 つも無いときは呼ばない**という条件付きにして、並列を使わない運用のコストを 0 にした。`session-start` は `boundary.sh status --offline` を呼ぶので、この 1 回がフック経由で効く可能性がある（`--offline` でも作業ツリーの一覧は必要）。実装で計測して重ければ、`--offline` では追加判定を省く形に倒してよい
- **合流を切れ目の処理の「手順 3-0」（push より前）に置いた**（e26）。合流しないまま push すると作業ツリー側の成果が MR に載らないので前に置いたが、`push.sh` の前チェックと `worktree.sh merge` の前提検査は条件が重なる（R56）。**判定の順序を `boundary.sh status` → `merge` に固定し、二重の判定は許す**（`merge` が落ちたら切れ目の処理に進まない）ことで決着させた
- **`isolation: worktree` を「`worktree.baseRef` が設定されているときだけ置く」とし、設定そのものは本 issue では置かない**（e29）。設定は `common.confirm` で人の確認が要り、実効性（この環境で `isolation` が解釈されるか）も未確認なので、**既定は「隔離を使わない」側に倒れる**。並列実施は作業ツリーを呼び出し元が切る形で成立するので、隔離が使えなくても設計は崩れない

### ◆特に見てほしい（0014 分）

- **`git merge` の素通りの穴を、本 issue では閉じずに残した**（e22）。合流は `worktree.sh merge` に一本化したが、`git merge <ローカルブランチ>` を AI が直接打っても、**タスクの切れ目（作業中チケット 0 枚）では `workflow-guard` が判定に入らないので素通りする**。合流はまさにその時点で行われるので、「提供コマンドを通す」は**規約であって強制ではない**。閉じるには `workflow-guard` の制御方式 1（作業中チケットが無ければ何もしない）に手を入れることになり、0013 が確定させた仕様と、切れ目でのすべての操作の扱いに波及する。残課題 R53 として別 issue に出したが、**本 issue で閉じるべきなら差し戻してほしい**
- **合流の記録先を決めるためにフック共通仕様 §5 に行を 1 つ足した**（e19）。計画書の割り付けでは 0014 が触るのは §6 だけだが、保留 P3（合流の記録をどこに置くか）が 0014 に投げられており、記録の置き場の正は §5 の表なので、そこに登録しないと台帳が不完全になる。0012 が書いた §5 の記述は 1 文字も変えず、表に 1 行と根拠の箇条書き 1 行を足した

### ◇判断が欲しい（0014 分）

- **本流かどうかの判定を「リポジトリルート直下の `.git` がディレクトリか」の 1 つに決め、`worktree.sh` / `ticket.sh` / `push.sh` の 3 つで共有した**（e20）。`git` を呼ばずに済み、フック側の共有ルート（`HOOK_SHARED_ROOT`）と同じ根を指す。正は `20-common-step-worktree` 仕様に 1 か所だけ置き、他の 2 つは参照する形にした
- **push の本流限定に新しいエラー識別子を作らず、push 前チェックの「項目 5」にした**（e21）。チケットの DoD が push 側には「テスト ID が振られている」だけを求め、エラー識別子を求めていないことに合わせた。項目 4 と同じく**スキップ記録では飛ばせない**ようにしてある
- **`WT-E`（eval ID の接頭辞）を §6 の主表の `WT001–008` の行で登録した**（e17）。下の「eval ID の接頭辞」の表は「issue #10 で作る 19 のアセット」を固定するものと本文が明記しているので、そこに 20 行目を足さず、主表の行に併記した

## 実施した内容と結果

### e1. 作業ツリーの三分を §2 に定義し、共有ルートは別の変数として持って値を `HOOK_ROOT` に固定した ◎良

`10_spec/フック共通仕様.md` §2 に、フックが区別する 3 つの根を表で置いた。

| 名前 | 変数 | 指すもの | そこに置かれるもの |
|---|---|---|---|
| 置き場 | `HOOK_ROOT` | 読み込み行が解決したリポジトリルート（本流） | フック・共通ライブラリ・`hooks/config/`・`settings.json` |
| 判定対象の作業ツリー | `HOOK_WORKTREE` | その操作が行われた作業ツリー | `wip/`、`logs/hooks/decisions.jsonl`、`logs/sh/` |
| 共有ルート | `HOOK_SHARED_ROOT` | issue・ブランチ・MR に属する進行状態を集める根 | `logs/` の進行状態・ロック・集計・セッション状態 |

計画書の保留 P2（変数を分けるか決め打つか）は**分ける**で決着させた。ただし値の解決は `HOOK_ROOT` と同一に固定し、環境変数・設定からの上書きを受け付けない。理由は 2 つで、①名前を分けておけば、別 clone を使う運用（要件の前提条件が認めている）を扱うときに値の解決だけを変えればよく、進行状態を読む全フック・全提供コマンドを触らずに済む ②上書きの口を開けると、進行状態の置き場を動かすことで `workflow-state-guard` の保護対象そのものを外から外せる（拒否側の保護が環境変数 1 つで無効になる）。

あわせて、**同一リポジトリの作業ツリーの集合**（`HOOK_ROOT` と `.git/worktrees/*/gitdir` に登録されたすべて）を §2 に定義した。この集合は「保護してよい範囲」を広げるためだけに使い、`HOOK_WORKTREE` の決定には使わないので、stale な登録が混ざっても判定は緩まない（緩むのは `HOOK_WORKTREE` の決定側だけで、そちらは従来どおり相互参照の双方向を要求する）。

### e2. 進行状態・ロック・集計を共有ルートへ、判定記録と実行ログを作業ツリー側へ分けた ◎良

§5 の表に「根」の列を足し、記録ごとの置き場を 1 か所で読めるようにした。共有ルート側は `mr.json` / `review-state.json` / `review-history.jsonl` / `merge-state.json` / `locks/` / `usage/<branch>.json` / `sessions/<session_id>/` / `push-state.json`、作業ツリー側は `hooks/decisions.jsonl` と `sh/<name>.log` の 2 つだけである。`logs/locks/<name>.lock` は表に無かったので行を足した（実装は `logs/locks/<name>.lock` を使っており、束 1 の 7 が名指ししている対象なので、置き場を決める以上は表に載っている必要がある）。

`decisions.jsonl` のスキーマに `cwd`（判定時の作業ツリー）と `agent_id`（サブエージェントの識別）を足し、`HK-T06`（記録のスキーマ）にその検査と負のコントロール（メインの呼び出しでは `agent_id` が空）を書き足した。

**この決定が §1 の別の記述に効いていた。** §1 は「`jq` は最大 2 回」の内訳として「`logs/` は作業ツリー側に置き、作業ツリーは stdin の `cwd` を読んで初めて決まるので、この 4 つを 1 回目に混ぜることは原理的にできない」と書いていた。進行状態を共有ルートへ寄せると `review-state.json` / `merge-state.json` の置き場はフックの起動時に決まるので、この理由付けは成り立たなくなる。**2 回目が要る理由を `session_id` 依存（`approvals.json` / `entry.json`）に置き換え**、`review-state` / `merge-state` を 1 回目に混ぜない理由を「読むのが 2 本のフックだけだから」に書き直した。

### e3. 作業ツリーをまたぐ絶対パスの保護漏れ（A1-2）を、無条件の記述で閉じた ◎良

### e9. 宣言範囲の強制が「その作業ツリーの作業中チケット 1 枚」で一意に決まることを書き、WF207 の意味を確定させた ◎良

`workflow-guard` の要件と仕様に、受け入れ条件 A5 のうち**宣言範囲の強制**の一意性を落とした。決めたのは 3 点。

1. **判定に使うチケットは `HOOK_WORKTREE` の `10_doing/` の 1 枚だけ**で、他の作業ツリーの `10_doing/` は枚数にも材料にも入れない。`HOOK_ROOT` と `HOOK_SHARED_ROOT` はチケットの探索に使わない（設定 `scope-limits.json` の置き場だけが `HOOK_ROOT`）
2. **`WF207` は「1 作業ツリーあたり 2 枚以上」**を指す。リポジトリ全体では、作業ツリーが N 個あれば最大 N 枚が同時に作業中になり得る。要件側にも「別の作業ツリーに作業中のチケットがあることを理由に拒否してはならない」を書いた
3. **「書き込み先がどの作業ツリーの中か」と「判定の根拠になるチケットがどの作業ツリーのものか」は別物**である。前者は `hook_rel_path`（§2）が畳んだ結果、後者は常に `HOOK_WORKTREE` の 1 枚。この 2 つを分けて書かないと、他ツリーの絶対パスを書いたときに「どちらのチケットの宣言で判定するのか」が読み手に委ねられる

あわせて、0012 が「設計への反映 1」で 0013 に送った項目（`__wg_rel` にも §2 の畳み込みが要る）を制御方式 5 に落とした。**畳んだ結果は 4 通り**に分かれる: 自ツリー配下 → そのまま / **他の作業ツリー配下 → そのツリーのルート相対で同じ判定**（「自分の外だから見ない」としない）/ 共有ルート配下 → 共有ルート相対 / **どの根の配下でもない（外と確定）→ WF209** / **位置を確定できない → WF209**。0012 が `workflow-state-guard` で採った「外と確定 → 許可 / 確定できない → 拒否」との違いは意図的で、`workflow-guard` は**作業中チケットがある間はリポジトリの外へ書かせない**（保護対象の有無ではなく許可範囲の体系の外だから止める）。この非対称は §13 の「同一リポジトリの外への書き込み」の記述と一致している。
