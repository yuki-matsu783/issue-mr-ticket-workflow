# 10-work-implementation-plan スキル

## 概要

実装・テストフェーズの計画ワークの要件を定義する。設計書（仕様書のインターフェース・処理フロー・テストシナリオ）をコードに落とすための変更対象・許可範囲案・テスト方針・実装ステップを実装計画書にまとめ、実装チケット群と次のフェーズの計画チケットを起こして実装計画チケットを完了する。コードは書かない（`10-work-implementation-exec`）。

- **背景**: 実装を計画なしに始めると、変更が仕様の対応を離れて広がり、テストが後回しになり、チケットの「やってよいこと」も実態と合わなくなる。どのファイルを・どのテストで確かめながら・どの順で変えるかを先に決め、人間が差分の範囲とテストの網羅を実装前に見られるようにしたい。
- **目的**: 変更対象を仕様書のインターフェースと対応付け、テストシナリオ（テスト ID）を単体・結合などのテストに割り付け、検証可能なステップに区切った実装チケット群を、最小の許可範囲案とともにレビュー可能な計画書として残す。
- **スコープ**:
  - 含む: 実装計画書の作成、変更対象と許可範囲案、テスト方針（テスト ID との対応・失敗ケース・実行方法）、実装チケット群と次の計画チケットの作成、実装計画チケットの着手から完了まで、「対象なし」の扱い、再開時の扱い、呼び出し元への結果報告
  - 含まない: コードとテストの作成（`10-work-implementation-exec`）、設計書の内容の決定（設計フェーズ）、フェーズ列の決定（`10-work-overall-plan`）、ワークの切れ目の処理（`00-workflow-issue-mr-driven`）、許可範囲を強制する仕組み（仕様書）

---

## ユーザーストーリー

**[As a]** issue を AI に任せる開発者として、

**[I want]** コードが書かれる前に、どのファイルがどこまで変わり、どのテストで何を確かめるのかを 1 枚の計画で確認したい。

**[So that]** 仕様と対応しない変更やテストの抜けを実装前に正し、差分レビューを計画に照らして行えるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このワークに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、設計書（インターフェース・処理フロー・テストシナリオ）・調査結果レポート・issue の受け入れ条件・リポジトリのビルドとテストの仕組み（読むだけ）を入力に進めなければならない。
- When 実装計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 実装計画書の案ができたとき、Shall スキルは実装ステップを検証可能な単位（テストが通る・ビルドが通る）で区切り、1〜2 ステップ = 1 チケットの目安で実装チケット群（1 枚以上）を未着手に作らなければならない。互いに依存しないチケットは並列に進めてよいことを記す。
- When 実装チケットを作るとき、Shall その DoD は「<変更対象> が仕様書 <節> のとおり実装されている」「テスト <テスト ID> が追加され、失敗ケースを含めて通る（実行方法つき）」「既存のテストが通る」「仕様からの逸脱・判明した差分が作業ログに書かれている（設計反映の入力）」の型で書かなければならない。
- When 実装チケット群を作り終えたとき、Shall スキルは全体計画書のフェーズ列で実装・テストの次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: ワークの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと（書き込んでよい範囲・実行してよい操作の分類。許可範囲案を反映する）、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When 実装計画チケットを完了するとき、Shall 実装計画書（md + HTML）・実装チケット群・次の計画チケットが存在し、DoD（計画書に変更対象・許可範囲案・テスト方針・実装ステップ・検証方法がある / 実装チケットの DoD にテスト ID と実行方法がある / 次の計画チケットがある）がすべて満たされ、作業ログが機構のチケットテンプレートの項目に沿って書かれ、必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 実装計画チケットを完了したとき、Shall スキルは結果報告（計画書の場所、実装チケットの枚数と並列にできる組、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「変更対象が仕様書のインターフェースと対応し、漏れや余計な変更がないか」「テスト方針がテストシナリオを網羅し、失敗ケース・境界値を含むか」「ステップの順序（テスト先行）と 1 チケットの大きさ」「許可範囲案が最小か」「設計反映で書き戻しが要りそうな点の洗い出し」を挙げなければならない。

### 代替フロー

- If 受け入れ条件がコードの変更を必要としないと分かった場合、Then スキルは実装計画書に「対象なし」とその根拠を書き、実装チケットを起こさず次の計画チケットだけを作って実装計画チケットを即座に完了しなければならない（フェーズを省かない）。
- If 設計フェーズが「対象なし」で終わっていて設計書の変更が無い場合、Then スキルは既存の設計書・調査結果レポート・受け入れ条件から計画を書き、よりどころにしたインターフェースを計画書に明記しなければならない。
- If 再開時に実装計画チケットが作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、計画書・チケットを二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのワークに戻った場合、Then スキルは実装計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、指摘への対応を作業ログの「判断と根拠」に残さなければならない。

### 例外フロー

- If 設計書のテストシナリオにテスト ID が無い、またはインターフェースが実装を計画できる粒度に達していない場合、Then スキルは推測で補わず、不足を結果報告に書いて設計フェーズへの差し戻し（設計の追加チケット）を提案しなければならない。
- If コードやテストへの書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、その内容を実装チケットに回さなければならない（計画ワークではコードを書かない）。
- If ビルド・テストの実行が機構に拒否された場合、Then スキルは実行せず、設定ファイルとテストコードを読んで仕組みを把握しなければならない（実行は実装チケットで行う）。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

### 実装計画書の内容

- When 実装計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、変更対象（パスと変更内容。仕様書のインターフェースとの対応）、許可範囲案（実装チケットが書き込んでよい範囲。最小にする）、テスト方針（テストシナリオのテスト ID をどの種類のテストで実装するか・失敗ケースと境界値・実行方法）、実装ステップ（テストを先に書く順序を含む）、検証方法（全体としての確認手順）、リスクと未解決事項（実装中に判断が要りそうな点・設計反映で書き戻しが要りそうな点）、判断を保留した点。
- When テスト方針を書くとき、Shall テスト駆動を基本とし、テストを先に書いて失敗を確認してから実装するステップを組み込まなければならない。
- When 実装計画書を書くとき、Shall 「これから何をするか」だけを書き、コードの断片を書き始めてはならない。
- When 実装計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### 実装計画チケットの扱い

- When 実装計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、ソースコード・テスト・設計文書・`.claude/` 配下を書けてはならない。
- When 実装計画チケット・実装チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければどちらも「要」を既定としなければならない（実装は振る舞いを変えるリスクが高い）。

### 他のスキル・機構との整合

- When 設計書・調査結果レポート・全体計画書を参照するとき、Shall スキルはそれらを書き換えず、疑義があれば結果報告の「見てほしい点」に書かなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When コードの品質基準に言及するとき、Shall not スキルは基準を再掲せず、プロジェクトの規約（`CLAUDE.md` の基本原則・コード規約のルール）を参照しなければならない。

## 前提条件

- 設計フェーズのワークの切れ目の処理（レビュー要ならレビュー完了）が済み、実装計画チケットが未着手にあること
- 実装計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと提供コマンドが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずに「判断を保留した点」と「見てほしい点」に書く。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 変更範囲・テストの網羅・許可範囲は人間レビューで確定する。スキルは案を出し、レビュー前にコードを書き始めない
- **外部的制約**: 許可範囲案は機構が定める上限の中で提案し、保護された範囲（`.claude/` 配下など）を含めない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 受け入れ条件 → テストシナリオ（テスト ID）→ テスト方針 → 実装チケットの DoD と辿れる |
| 一貫性 | チケットの記載事項・DoD の型・作業ログは他の work スキルと同じ。フェーズの名前は `00-workflow-issue-mr-driven.md`「ワークの構成」と一致する |
| 簡潔性 | 実装計画書はステップと対応表に集中し、コードの先取りを書かない |
| 冪等性 | 再開時に計画書とチケットを二重に作らない |
