## 実施した内容と結果

### 1. 章の骨格とフロー節の順序は全件守られている ◎良

根拠: 45 件の全数集計。

- `## 概要` の下位項目（`**背景**` / `**目的**` / `**スコープ**` / `含む:` / `含まない:`）は 45 件すべてに存在する
- `制約条件` の `**技術的制約**` ラベルも 45 件すべてに存在する
- 受け入れ基準の 1〜3 番目の節は メインフロー → 代替フロー → 例外フロー の順で、45 件すべてが規定文言で始まっている

結論: テンプレートが固定している部分は機能している。改訂はテンプレートの章立てではなく、受け入れ基準の
内側に限定してよい。

### 2. メイン / 代替 / 例外の振り分けに判定基準が無く、同じ性質の記述が別の節に入っている ✕問題

根拠: 節の中身を読み合わせた具体例。

同じ「呼び出し元に返して止まる」振る舞いが、書によって代替にも例外にも入る。

| 記述 | 置かれている節 | 書 |
|---|---|---|
| 同名のブランチが既に存在する → 上書きせず別案を返す | 代替フロー | `skills/20-common-step-feature-mr.md` |
| 未コミットの変更がある状態で呼ばれた → ブランチを作らず返す | 例外フロー | `skills/20-common-step-feature-mr.md` |
| push 前チェックを意図的に飛ばす → 理由を差分に残してから飛ばす | 代替フロー | `skills/20-common-step-commit-push.md` |
| 直前のコミットに誤りが見つかった → 訂正の新規コミットで直す | 例外フロー | `skills/20-common-step-commit-push.md` |

前の 2 行はどちらも「前提が満たされず、処理を進めずに呼び出し元へ返す」で性質が同じなのに節が違う。
後ろの 2 行はどちらも「失敗ではないが通常と違う道を通る」で性質が同じなのに節が違う。

さらに、同じ「代替フロー」の中に性質の違うものが同居している。`20-common-step-feature-mr` の代替フローは
2 項目あり、片方（ブランチ名の衝突）は**停止して呼び出し元の判断を仰ぐ**、もう片方（open な MR が既にある）は
**別の道で目的を達成して完了する**。読み手は節名からどちらか判別できない。

結論: 「誰が起点か（利用者の選択 / 環境の状態 / 外部の失敗）」と「その道の終わり方（目的を達成する /
達成せず返す）」の 2 軸で判定基準を作れば、上の 4 例はいずれも一意に決まる。設計で軸を確定する。

### 3. メインフローの規模に上限が無く、最大 52 項目の書がある △注意

根拠: 45 件の EARS 項目数の全数集計。

| 指標 | メインフロー項目数 |
|---|---|
| 合計 | 494 |
| 平均 | 11.0 |
| 中央値 | 10 |
| 最大 | 52（`自己改善ワークフロー機構.md`） |
| 最小 | 2 |

上位 5 件は 52 / 28 / 24 / 18 / 18。中央値の 10 に対して最大が 5 倍で、上側に長い裾がある。
文字数で見ると、メインフローだけで `自己改善ワークフロー機構.md` が 6,972 字、`workflow-guard.md` が
3,329 字あり、レビュアーが 1 画面で追える量を超えている。

分布（項目数: 件数）: 2:2, 3:1, 4:2, 5:5, 6:5, 7:2, 8:2, 9:1, 10:5, 11:4, 12:2, 13:4, 14:3, 15:1, 18:3, 24:1, 28:1, 52:1

結論: 中央値 10 の実態と、上位 4 件（18 以上）だけが外れる形を踏まえると、上限の候補は 12〜15 の範囲。
12 なら 45 件中 14 件が分割対象、15 なら 6 件が対象になる。設計で数値を確定する。

### 4. 分割の前例が既に書の中にある ◎良

根拠: `skills/10-task-overall-plan.md` の見出し。

```
### メインフロー: issue の確定
### メインフロー: ブランチと draft MR の作成
### メインフロー: 全体計画の作成と合意
```

メインフロー 24 項目を 3 つに分け、規定文言「メインフロー」の後ろに補足を後置している。これは
`20-common-step-requirement` の手順 3 が既に認めている書き方（「見出しは規定文言で始める。補足の後置は可」）
に沿っている。

結論: 分割ルールはゼロから作らなくてよい。この前例を「何を単位に分けるか」の規定として明文化し、
分けた図どうしの参照方法だけを新しく決める。

### 5. 自由記述のばらつきは章の中ではなく、受け入れ基準の 4 番目以降の節に出ている △注意

根拠: 4 番目以降の節見出しの全数集計と、自由記述章の文字数の分布。

自由記述章の粒度は揃っている。`## 概要` は中央値 714 字、最小 517 字、最大 1,716 字で、最大の 1 件
（`自己改善ワークフロー機構.md`、唯一の横断文書）を除けば 517〜1,078 字に収まる。`非機能要件` の表も
中央値 4 行、最小 2 行、最大 7 行で安定している。

揺れているのは受け入れ基準の 4 番目以降の節で、45 件に合計 83 個の節があり、見出しは 55 種類ある。

| 見出し | 件数 |
|---|---|
| 他のスキル・機構との整合 | 24 |
| 承認ポイント | 3 |
| 用語辞書 / 正史のみの記述 / DDR の運用 | 各 2 |
| その他（`調査結果レポートの内容`、`要件書の形`、`判定基準`、`タスクの構成` など 50 種類） | 各 1 |

規定文言は「他のスキル・機構との整合」だけで、それ以外の 54 種類は各書が独自に切った節。中身を見ると
「他のアセットとの関係」ではなく「その書が定める成果物の中身の規定」（例: `調査結果レポートの内容`、
`全体計画書の内容`）で、整合とは別の役割を持っている。

結論: 「自由記述を減らす」よりも「4 番目以降の節に何を置けるか」を規定するほうが効く。設計では、
名前付きの規約節を正式な型として認めるか、整合の節に寄せるかを決める。

### 6. mermaid の GitHub 上のレンダリング範囲を一次情報で確認できなかった △注意

根拠: `docs.github.com` へのアクセスが egress 制限で拒否された。

```
{"error_type":"EGRESS_BLOCKED","domain":"docs.github.com",
 "message":"Access to docs.github.com is blocked by the network egress proxy."}
```

Web 検索の二次情報では、mermaid は issue・PR・Discussions・wiki・リポジトリ内の Markdown で描画され、
複雑なファイルはタイムアウトして平文にフォールバックすることがある、とされる。PR の差分表示で
描画されるかは、二次情報の中でも記述が分かれた。

リポジトリ内に mermaid の既存利用は 1 件も無い（`.claude/` 配下・`docs/` 配下ともに 0 件。ヒットしたのは
本 issue で作った wip 配下のチケットと計画書だけ）。既存の図は SKILL.md の ASCII アート
（`00-workflow-issue-mr-driven` の冒頭）で、要件書には図が無い。

結論: 描画される場所に依存しない設計にする。PR の差分は行単位なので、**mermaid のソースが平文のまま
読めること**を型の要件にする（1 行 1 ノード、ノード名を意味のある日本語にする、など）。描画の有無は
人間のレビュアーが GitHub 上で実地に確認できるため、残課題として渡す。

### 7. 見本候補を 2 件選定した ◎良

根拠: 節ごとの項目数の集計から、検証したい規約ごとに対象を選んだ。

| 候補 | メイン / 代替 / 例外 / 他 | 何を検証できるか |
|---|---|---|
| `hooks/20-PreToolUse/workflow-guard.md` | 28 / 2 / 4 / 0 | 上限超過時の分割ルール。判定の連なりが本体で、4 番目以降の節を持たない純粋なフロー |
| `skills/00-workflow-issue-mr-driven.md` | 14 / 7 / 4 / 11 | 代替・例外への離脱点の表記（代替 7・例外 4 は全 45 件で最多クラス）と、4 番目以降の節の扱い（11 項目） |

補欠として `自己改善ワークフロー機構.md`（52 項目）がある。分割ルールの限界を試せるが、唯一の横断文書で
性質が他と違い、差分も大きくなるため見本には向かない。

結論: 上の 2 件で、決めた規約 5 つ（判定基準・mermaid 記法・ノード数上限・分割ルール・離脱点の表記）を
すべて 1 回は通せる。

## 設計への反映

1. フローの判定基準を「起点（利用者の選択 / 環境の状態 / 外部の失敗）」×「終わり方（目的を達成する / 達成せず返す）」の 2 軸で定める。f2 の 4 例が一意に決まることを確認する（反映先: `10_spec/skills/20-common-step-requirement.md`）
2. メインフローのノード数上限を 12〜15 の範囲で確定する。f3 の分布を根拠として書に残す（反映先: 同上）
3. 分割ルールは `10-task-overall-plan.md` の前例（`メインフロー: <名前>`）を明文化し、分けた図どうしの参照方法を足す（反映先: 同上）
4. mermaid 記法は「ソースが平文で読める」ことを要件に置く。描画されない場所があっても成立する形にする（反映先: 同上 + `assets/requirements.template.md`）
5. 受け入れ基準の 4 番目以降の節を型として規定する。83 個・55 種類の実態を踏まえ、名前付きの規約節を認めるか整合に寄せるかを決める（反映先: `00_requirement/skills/20-common-step-requirement.md` と `.claude/rules/ai-asset-design-docs.md`）
6. 自由記述章（概要・背景・目的・スコープ）は現状で揃っているため、分量の目安を追認する形で書く（中央値 714 字を根拠に上限の目安を置く）

## 想定と異なった点

| 計画時の見込み | 実際 | どう扱ったか |
|---|---|---|
| 自由記述章の粒度がばらついている | 概要 517〜1,078 字（横断文書 1 件を除く）、非機能要件 2〜7 行で揃っていた | ばらつきの本体は受け入れ基準の 4 番目以降の節だった。設計への反映 5 に置き換えた |
| フロー節の順序違反が残っている（issue #8 が 3 件と記録） | 45 件すべてで メイン → 代替 → 例外 の順が守られている | 順序は既に直っている。改訂は振り分けの基準に絞る |
| mermaid のレンダリング条件を調べれば制約が分かる | 一次情報にアクセスできず、二次情報も PR 差分について記述が分かれた | 描画に依存しない設計（ソースの可読性を要件に置く）に方針を変えた |
| 45 件の要件書は EARS を `- **When**` の太字で書いている | 太字は使わず `- When ` の平文だった | 集計スクリプトの抽出条件を直して数え直した |

## 残課題

- GitHub の PR 差分表示で mermaid が描画されるかを、人間のレビュアーが実地で確認する（本 PR に mermaid を含む差分が乗った時点で分かる）
- レビューでの指摘の再発を測る仕組みが無い。改訂の効果は次の要件書を書くときの体感でしか分からない
- `.claude/rules/` に `markdown-docs` が存在しない（`ai-asset-design-docs` が frontmatter の規約の正として参照しているが未作成）。issue #11 の範囲
- 見本 2 件を除く 43 件は改訂後の型に揃っていない状態が残る（issue #8 の範囲）
