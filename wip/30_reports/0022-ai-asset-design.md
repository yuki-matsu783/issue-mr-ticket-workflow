## 実施した内容と結果

### 1. `push.sh` の 1 枚目依存を #10 へ申し送る（S2） △注意

`i0009-18` は G8 を「提供コマンドの実体は直さない / #10 への申し送りは出さない」で閉じ、その根拠に「残るリスクは `run-tests.sh` に閉じており、**作業領域外への書き込みやリモート操作には及ばない**」と書いていた。実体を読むとこれが偽だった。

```
push.sh:98   ticket="${doing[0]}"                                # 名前順の 1 枚目
push.sh:99   ops="$(fm_list "$ticket" allow.ops 2>/dev/null || true)"
push.sh:100  if grep -qx -- "remote-write:push" <<<"$ops"; then  # → 項目 2 を通す
```

作業中が 2 枚のとき、**push を宣言していない側で作業していても 1 枚目の宣言で push が通る**。影響はリモートに及ぶ。

**決定**: 決定（実体を直さない）は保ち、根拠を訂正して **#10（3/3）への申し送り**に切り替えた。`run-tests.sh` と `ticket.sh next` は影響がローカルに閉じるので「修正不要」のまま。申し送りが届く経路として、全体計画に「#10（3/3）への申し送り」の表を新設し、全体まとめの承認⑥の issue コメントに含めることを段取りに書いた。DDR `i0009-40`。

**結論**: 決定を保ったまま根拠を正す形に直せた。ただし**申し送りが届く保証は手順だけ**で、機構の強制は無い。

### 2. `web` は `curl` / `wget` を実行分類として強制する（S3） ✕問題

`i0009-12` は「`WebFetch` だけを止めても**抜け道が残る**（`Bash` の `curl` まで止めるのは過剰）」を理由の 1 つに挙げていた。実体はその逆だった。

- `scope.sh` の `_SC_READ_ONLY_CMDS` に `curl` / `wget` は**無い**（`.claude/hooks/lib/scope.sh:29`）
- `workflow-guard` 制御方式 6 に `web` の分岐は無く、最後は「上記のいずれにも該当しない → **deny WF204**（既定拒否）」

つまり `curl` は既に塞がれている。しかも `curl` は `decisions.jsonl` にコマンド列が残り、`WebFetch` は matcher 外で記録すら残らない。**記録が残る側だけが塞がれ、記録が残らない側が素通りする**。共通仕様 §8 の「`web` を宣言したときだけ通る」も要件の制約条件（自制の列挙）も、この事実と食い違っていた。

**決定**: `curl` / `wget` を `scope_classify` の **`web`** に分類し、`allow.ops` と `types[t].ops` の両方にあれば許可・無ければ WF204。ただし**出力先を持つ形**（`curl -o` / `-O` / `--output` / `--remote-name`、`wget` の既定と `-O <file>`）は**先に**書き込みとして判定し、出力先パスが `wip/tmp/**` / `logs/**` 以外なら WF205。`WebFetch` / `WebSearch` は `i0009-12` のとおり強制しない（§13 の緩和はツール側 2 つに限定）。DDR `i0009-41`。

**結論**: 宣言が初めて効くようになり、受け入れ条件 5 の「`web` の強制」に実体で答えられる。**`i0009-12` の決定をコマンド側だけ覆す判断**なので、線引きの妥当性は見てほしい。

### 3. 打ち切りの fail-open に権限設定と事後ゲートを採らない（S4） ◎良

`i0009-11` は打ち切りを「塞げない唯一の穴」として速さで守ると決めたが、**却下した案が機構の外側の手段を検討していなかった**。公式には 2 つある。

- `hooks.md:1744`「[Deny and ask rules] are still evaluated regardless of what the hook returns」→ 権限設定の拒否規則は打ち切りの影響を受けない
- `hooks.md:867`「`PostToolBatch` … Stops the agentic loop before the next model call」→ 事後に loop を止められる

しかも要件の制約条件は既に「権限設定は多重防御として併用してよい」と書いており、例外フローの「この経路は**塞げない**ため」と整合していなかった。

**決定**: どちらも**機構の決定には含めない**。`permissions.deny` は (1) `.claude/settings.json` がユーザーの持ち物で機構が書き換える対象でない、(2) 複合コマンドを止められないので「止まったつもりで止まっていない」を作る、が理由。`PostToolBatch` は**取り返しがつかない操作は既に実行された後**で「実行前に止める」を満たさない。あわせて例外フローを「**機構の中に**この経路を塞ぐ手段は無い」に直し、外側の多重防御は併用してよいと書いた。DDR `i0009-42`。

**結論**: 「検討したうえで採らない」が残り、要件の内側と外側の書き分けができた。

### 4. 公式で閉じられる TBD は閉じ、実測が要るものは残す（S5・S6・S7） ◎良

§12 の TBD に 3 つの扱いのずれがあった。

| # | ずれ | 直し方 |

| T1 | 取得済みの原本（`hooks.md:2346`「To inject context into the parent session after a subagent returns, use a `PostToolUse` hook on the `Agent` tool instead.」）が既に答えているのに実測待ち | **閉じた**。現行の登録が公式の推奨形そのもの。4c 表からも外した |

### 5. 非機能要件の是正と自制統制の明記（S8・S9・S11） ◎良

DDR `i0009-44`。**結論**: 要件が自分で課した規約に従い、同じ事実が矛盾する場所すべてで揃った。
