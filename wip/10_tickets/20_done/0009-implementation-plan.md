### うまくいったこと

- 仕様書がテスト ID（TB-T01〜TB-T14）を持っていたので、設計差し戻しの判定がすぐ済み、ステップとテスト ID の対応表がそのまま作れた

### うまくいかなかったこと

- ステップ 6（拡張ホスト層）だけ対応するテスト ID が無い。`vscode` が拡張ホストの外で解決できないためで、計画の型（1 ステップ = テスト ID で合否）から外れる。合否を「npm test の全通過と tsc の無警告」で代え、README の手動確認手順に逃がした

### 仕様からの逸脱

- 処理フローの順序（計画書 → 実施チケット群 → 次の計画チケット）に対し、チケットを先に作ってから計画書を書いた。0002・0006 と同じ理由
- 実行者と人間レビュー要否は全体計画書の方針の差分 1・4 に従う。ただし 0012（feedback-plan）だけは人間レビュー「要」のままにした。後続フェーズの要否は人間の判断であり、差分 4 が置き換える対象（ワーク境界のレビュー）とは別の承認だからである

### 判断と根拠

- 実装チケットを 2 枚にした。中核層 5 モジュールは 1 本の依存の鎖で途中で切るとレビューできる単位にならず、拡張ホスト層はテストの性質が違う（単体テスト対象外）ため境界として自然
- 開発依存を 3 つに固定し「増やしたくなったら足さずに計画へ戻す」とリスク表に書いた。依存が増えると受け入れ条件 10（ローカルで通る）の確実性が下がるため
- 検証方法に「core/ に from "vscode" が無いことを grep で確認」を入れた。層の分離は仕様の禁止事項だが、機械的に確かめられる形にしないと守られたか分からないため
- 検証方法に機構のテスト（run-tests.sh）の実行を入れた。拡張の追加が機構を壊していないことを確かめるため
