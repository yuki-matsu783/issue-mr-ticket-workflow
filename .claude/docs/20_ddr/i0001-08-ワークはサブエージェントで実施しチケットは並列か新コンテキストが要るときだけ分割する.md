# i0001-08. ワークはサブエージェントで実施し、チケットは並列か新コンテキストが要るときだけ分割する

## 背景

参考実装はどちらもメインセッションが全ワークを直列に実施する。1 issue の作業が長くなるとコンテキストが compact され、現在地や手順の理解が失われる問題に対し、両実装とも SessionStart フックでの再注入で対処していた。一方、Claude Code のサブエージェントは独立したコンテキストで動き、モデルを指定でき、並列に起動できる。

## 決定

- **全体計画とフィードバック計画以外のワークは原則としてサブエージェントで実施する。** メインセッション（`00-workflow-issue-mr-driven`）はワークの起動・結果報告の受け取り・ワークの切れ目の処理（push・MR 本文更新・レビュー依頼・完了確認）に徹する。ワークを担当するサブエージェントのモデルは全体計画で合意する
- **全体計画まで（issue の確定・ブランチと MR の作成・全体計画）とフィードバック計画はメインエージェントが行う。** 人間との細かい対話（承認・合意）が要り、サブエージェントはユーザーと対話できないため。同じ理由で、全体まとめの中の人間の承認が要る操作（衝突解消・issue へのコメント投稿）もメインエージェントが行う
- **チケットは既定ではワークのサブエージェントの中で順に実施する。** チケット単位でさらにサブエージェントに分割するのは、(1) 互いに依存しないチケット群を並列に進めたいとき、(2) 新しいコンテキストで実施したいとき（チケットの実行者がワークのモデルと異なるときを含む）に限る
- サブエージェントは入れ子で起動できない前提とし、チケット単位のサブエージェントはワークからの要求に応じてメインセッションが起動する
- 宣言した範囲の強制（フック）はサブエージェントの中でも同じように働く

## 理由

- ワークごとにコンテキストが切れるため、1 つのワークの中で compact が起きにくく、ワークの手順とチケットの内容だけを持った状態で作業できる
- メインセッションのコンテキストにはワークの結果報告だけが積まれるので、長い issue でもオーケストレータの現在地が失われにくい
- チケットを常にサブエージェントにすると、1 枚ごとに文脈の受け渡しコストがかかり、直前のチケットの学びが次に引き継がれない。既定はワーク内で順に実施し、分割は利点がある場合に限る
- 実行モデルの指定（i0001-07）は、サブエージェントのモデル指定で自然に実現できる

## 却下した案

- **メインセッションがすべて直列に実施する（参考実装方式）**: 実装が単純で文脈の受け渡しが不要だが、長い issue で compact に依存し、モデルの使い分けができない
- **チケットを常にサブエージェントで実施する**: 並列性と隔離が最大になるが、チケット間の文脈が毎回失われ、小さなチケットほどオーバーヘッドが支配的になる
- **ワークのサブエージェントがチケットのサブエージェントを入れ子で起動する**: 構造が素直だが、Claude Code のサブエージェントは入れ子起動できない前提のため採れない

## 影響

- 要件定義書 B 節・前提条件、`00-workflow-issue-mr-driven.md` の整合節
- work スキルは「サブエージェントとして起動される」前提で、入力（チケット・計画・issue の受け入れ条件）と出力（結果報告）を明確に持つ必要がある
- ワークからメインセッションへ「このチケット群は並列で」「このチケットは別モデルで」と要求する形式を仕様で定める

## 未決定事項

- ワークのサブエージェントの中で提供コマンド（チケットの着手・完了）を実行するのか、メインセッションが代行するのかは仕様で決める
