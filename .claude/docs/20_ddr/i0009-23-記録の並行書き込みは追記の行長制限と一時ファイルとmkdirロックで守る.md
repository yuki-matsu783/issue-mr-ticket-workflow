# i0009-23. 記録の並行書き込みは追記の行長制限と一時ファイルと `mkdir` ロックで守る

## 背景

§5 は `logs/` の 8 種類の置き場を定めているが、**同時書き込みについて何も書いていなかった**。境界レビュー（付録 A の R22）で、次の 2 つの公式の記述が突き合わされた。

- 「All matching hooks run in parallel.」（`i0009-21`）
- 「`PostToolUse` … **fires concurrently when Claude makes parallel tool calls**」

競合し得るのは 3 種類。

| ファイル | 書く側 | 競合の形 |
|---|---|---|
| `logs/hooks/decisions.jsonl` | **全フック**（PreToolUse で 7 本、PostToolUse で 4 本） | 追記の割れ |
| `logs/sessions/<session_id>/approvals.json` | workflow-diff-check（書く）/ workflow-guard（読む） | 書きかけを読む |
| `logs/usage/<branch>.json` | post-push-usage-report（Stop / SubagentStop / push 時） | read-modify-write で片方の加算が消える |

特に `usage/<branch>.json` は、並行するサブエージェントの SubagentStop が同時に加算し得るため、集計値と `last_offset` の両方が壊れる（`last_offset` が巻き戻ると二重計上にもなる）。

## 決定

§5 に「並行書き込みの規則」を 3 段階で置く。

1. **追記だけのファイル（`*.jsonl` / `*.log`）**: 1 行を `>>` で追記し、**1 行を 4 KB（`PIPE_BUF`）未満に保つ**。`decisions.jsonl` の `note` と `target` は合わせて 1 KB を超えないよう切り詰め、切り詰めた旨を末尾に `…` で示す
2. **読んで書き換えるファイル（`approvals.json` / `push-state.json` / `usage/<branch>.json`）**: 同じディレクトリ内の一時ファイル（`<name>.tmp.<pid>`）へ書いてから `mv` で置き換える（同一ファイルシステム内の rename は原子的）
3. **read-modify-write が競合し得るもの（`usage/<branch>.json`）**: `mkdir <name>.lock` によるロックで直列化する。取得できなければ**最大 2 秒待って諦め、加算せずに `parse_errors` を +1 して終了 0**（案内側なので通す）。ロックは処理の最後に `rmdir` し、`trap` でも消す

テストは新規 `HK-T17` で固定する。

## 理由

- **3 段階に分けたのは、必要な強度が違うから**。追記は行長を守れば OS が原子性を保証するので、ロックは要らない。読み書きは `mv` で読み手を守れる。加算だけがロックを要する
- `PIPE_BUF` の 4 KB は POSIX が `O_APPEND` の追記に対して原子性を保証する上限。`decisions.jsonl` の 1 行は通常 200〜500 バイトだが、`note` に「一致したパターンと出どころ」を書く仕様があるので、上限を明示しないと超え得る
- **`mkdir` を選んだのは移植性**。`flock` は Git Bash に無いことがある。`mkdir` は存在すれば失敗するので原子的で、bash 組み込みではないが外部コマンドは 1 回で済む（案内側なのでホットパスの fork 上限 — `i0009-22` — の対象外）
- **2 秒で諦めるのは、案内側フックが本体を止めないため**。使用量の集計が 1 回抜けるのは、セッションが止まるより軽い。抜けたことは `parse_errors` に残る

## 却下した案

- **`flock` を使う**: Git Bash に無いことがあり、前提条件（`jq` と bash 4.3 以上）に外部依存を増やす
- **ロックを全ファイルに掛ける**: `decisions.jsonl` は全フックが毎回書くので、ロックがホットパスの直列化点になる。行長制限で足りるところにロックを掛けない
- **競合を諦めて「壊れたら作り直す」**: `usage/<branch>.json` は `since_sha` からの累積なので、作り直すと集計期間が失われる（`post-push-usage-report` の WF913 は既にこの縮退を持つが、常用する縮退にはしない）
- **`decisions.jsonl` をフックごとに分ける**: 振り返りで時系列に読む用途（§5「振り返りの材料」）が壊れる。マージする手間を増やすだけ
