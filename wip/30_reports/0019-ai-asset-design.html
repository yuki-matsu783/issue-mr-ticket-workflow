実施した内容と結果

  1. 1

    順序に頼る記述をすべて外した ◎良 根拠: 公式 hooks.md:414、境界レビュー R1・R19

    公式は「All matching hooks run in parallel. If you define the same handler in more than one settings file, it runs once.」と明記している。これまでの設計は 3 か所でこれに反していた。§1 の 順 列を 位置（settings.json の配列上の位置であって実行順ではない）に改め、「先に拒否したフックが理由を返す」を「複数が同時に deny を返し得る。どの理由が AI に見えるかは不定として扱い、各フックの拒否理由は単独で読んで成立する文面にする」に変えた。「安価で範囲の広い判定 → 高価で狭い判定」という順序による絞り込みを削り、「各フックが単独で軽いことだけが性能を決める」にした。各フック仕様の「〜の後、〜の前」を 5 本で「共通仕様 §1 の N 行目。位置であって実行順ではない」に書き換えた（R19 の workflow-guard の「最後に実行」も含む）。HK-T01 の照合対象を「イベント・matcher・フック・配列上の位置」に書き直した。

    実測への依存: 無し（公式の記述で確定）

    根拠を見る（読んだ箇所と出力）

  §11 HK-T01 の照合対象

  workflow-guard:27（「最後に実行」= R19）/ post-push-usage-report:26

    事実と食い違う前提が消えた。実装者が「先に走るフックが弾くから省ける」という最適化を入れる余地が無くなった。

  2. 2

    ホットパスの目安を「jq 1 回」という検査できる上限に置き換えた ✕問題 根拠: 境界レビュー R11、20-common-step-shell-script.md:107（95 ms/回）

    i0009-11 が置いた「ホットパスで 1 秒以内」は結果であって守り方ではない（実装者が守れているか判断できず、テストにも落ちない）。しかも §2 が「作業ツリーの位置は git rev-parse --show-toplevel を基準にする」と書いており、素直に読むと各フックが毎回 git を起動する — 20-common-step-shell-script 仕様が「Git Bash で約 95 ms/回」を理由に否定した方式を、共通仕様が要求していた。決定: ホットパスのフックが起動してよい外部プロセスは、stdin を解析する jq の 1 回だけ（git / date / sed / find を呼ばない）。make_counting_path で呼び出し回数として検査する。§2 の記述も「読み込み行が解決したリポジトリルート（LOGGER_ROOT / HOOK_ROOT）を基準にする」に変えた。並列実行なのでホットパス 5 本は同時に起動し、1 本あたりの fork がそのまま 5 倍のプロセスになることも §1 に書いた。

    実測への依存: あり（上限で全フックが書けるかは実装フェーズ。実行時間の実測は 4c）

    根拠を見る（読んだ箇所と出力） 
    既存の同方式: HK-T05（cmdpos の fork なし）・HK-T13（push-detect の fork ゼロ）
              いずれも make_counting_path で回数を数えている

  ツールの成否が確定した後に走るのでホットパスではなく、上限の対象外

  → 純 bash で読むか、hook_read_input の 1 回に相乗りさせるか（0021 と実装フェーズ）
DDR: i0009-22

    結論

    「速さで守る」という i0009-11 の決定が検査できる形になった。ただし実装可能性は未確認で、守れない場合は上限か設計のどちらかを直すことになる。

  3. 3

    登録を ${CLAUDE_PROJECT_DIR} 基準の絶対パスにした ◎良 根拠: 公式 hooks.md:3713・:416、境界レビュー R10

    登録の雛形は bash .claude/hooks/<NN-Event>/<name>.sh というリポジトリルート相対パスだった。公式は「Handlers run in the current directory with Claude Code's environment.」（cwd が消えていた場合だけフォールバックする）と「Use absolute paths … In shell form, wrap it in double quotes」の 2 つを言っている。cwd はリポジトリルートとは限らない（Claude が cd した後・worktree・サブディレクトリ）。決定: command を bash "${CLAUDE_PROJECT_DIR}/.claude/hooks/<NN-Event>/<name>.sh" にする。ラッパー付きの拒否側 5 登録も同じ形。なぜ重大か: 相対パスが解決できないと bash は終了 127。ラッパーの || はまさにこれを拾うので、拒否側 5 本すべてが同時に deny を返し、書き込み・実行・プランモード・起動のすべてが止まる。この状態から AI 側でできることは無い。案内側 6 本は同じ状況で静かに動作停止する。

    実測への依存: 一部あり（${CLAUDE_PROJECT_DIR} が worktree で何を指すかは 4c）

    根拠を見る（読んだ箇所と出力） 
    hooks.md:3713 Use absolute paths: specify full paths for scripts.
              In shell form, wrap it in double quotes
hooks.md:416  Handlers run in the current directory with Claude Code's environment.
              （cwd が消えていた場合のみ 起動ディレクトリ→プロジェクトルート→ホーム→temp）
帰結: 相対パス解決失敗 → exit 127 → ラッパーの || が発火 → 拒否側 5 本が同時に deny
更新: §1 の登録の雛形・fail-closed ラッパー・HK-T01
DDR: i0009-20

    結論

    実装計画が一番避けたい形のロックアウトの経路が 1 つ塞がった。フェーズ 4b の登録は必ずこの形で行う。

  4. 4

    push_detect から状態を外し、進捗の起点を呼び手が持つ形にした △注意 根拠: 境界レビュー R2、post-push-compact-prompt.md:60

    push-detect.sh の検知条件 3 は「push-state.json[b].sha が HEAD と異なる」で、この関数を post-push-compact-prompt（正）と post-push-usage-report（共有）の 2 本が使う。ところが compact-prompt は本体の最後で push-state.json[b] を {sha: head, count+1} に更新する。compact-prompt が先に走ると usage-report の検知は偽になり集計しない。並列実行なのでどちらが先かは不定 = レース。レポート名の <count> も番号がずれる。決定: push_detect <起点 sha> は状態ファイルを読まず書かない。起点は呼び手が渡す（compact-prompt = push-state.json[b].sha / usage-report = usage/<branch>.json の last_push_sha（新設））。push_count も新設し、usage-report は push-state.json を一切参照しない。

    実測への依存: 無し（設計の分離）

    根拠を見る（読んだ箇所と出力） 
    問題の構造:
  push_detect の条件3 = push-state.json[b].sha != HEAD
  compact-prompt 本体5 = push-state.json[b] を {sha: head, count+1} に更新
  → 並列なのでどちらが先か不定（レース）
分離後:
  compact-prompt : 起点 = push-state.json[b].sha       （このフック専用）
  usage-report   : 起点 = usage/.json.last_push_sha（新設）
更新: push 検知 1〜3・本体 5 / 呼出条件・入出力スキーマ・既定 1・既定 4・UR-T07
      §5 の 2 行 / §11 HK-T13
DDR: i0009-24

    結論

    共有ライブラリが特定の状態ファイルを持つ設計（i0009-17 と同じ形の誤り）が解消した。代償はレポートの通し番号が 2 系統になること。

  5. 5

    logs/ の並行書き込みを 3 段階で規定した △注意 根拠: 公式 hooks.md:414・:2088、境界レビュー R22

    §5 は同時書き込みについて何も書いていなかった。公式は「All matching hooks run in parallel」に加えて「PostToolUse … fires concurrently when Claude makes parallel tool calls」と明記している。競合し得るのは 3 種類で、必要な強度が違う。追記だけのファイル（decisions.jsonl）は 1 行を 4 KB（PIPE_BUF）未満に保つ（note と target は合わせて 1 KB まで）。読んで書き換えるファイル（approvals.json / push-state.json / usage/<branch>.json）は一時ファイル + mv で置き換える。read-modify-write が競合し得るもの（usage/<branch>.json）は mkdir ロックで直列化し、取れなければ最大 2 秒で諦め、加算せず parse_errors を +1 して終了 0（案内側なので通す）。新規テスト HK-T17 で固定した。要件の非機能（可用性）にも外部から見える性質として 1 文足した。

    実測への依存: あり（mkdir の原子性と 4 KB の追記保証は POSIX の記述に依拠。Git Bash での実測は HK-T17 まで）

    根拠を見る（読んだ箇所と出力） 
    競合する 3 種類:
  decisions.jsonl      全フック（PreToolUse で 7 本）    追記の割れ
  approvals.json       diff-check が書き guard が読む    書きかけを読む
  usage/.json  並行サブエージェントの SubagentStop  加算が消える
mkdir を選んだ理由: flock は Git Bash に無いことがある。mkdir は存在すれば失敗＝原子的
2 秒で諦める理由: 案内側フックが本体を止めない。抜けたことは parse_errors に残る
更新: §5（並行書き込みの規則）・§11（HK-T17）
      要件 非機能・可用性（外部から見える性質として 1 文）
DDR: i0009-23

    結論

    並列実行から出る 3 つ目の帰結を塞いだ。保証の根拠が POSIX の記述なので、HK-T17 を通すまでは仮定。

  6. 6
