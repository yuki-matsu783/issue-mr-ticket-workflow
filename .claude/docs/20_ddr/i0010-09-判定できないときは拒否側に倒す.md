# 判定できないときは拒否側に倒す

## 背景

提供コマンドの実装で「判定できない」場面が 3 か所出た。どれも、判定できないことを「判定できた」側のどちらかに畳んだ結果、静かに間違った結論を出していた。

- `finalize.sh` の `is_draft`: CLI が無い・API が失敗した場合を「draft でない」と同じ扱いにすると、記録を失った環境で `ready` に倒れ、何も解除していないのに「解除した」と報告する
- `finalize.sh` の `state` の再導出: `logs/merge-state.json` の値が既知の段階名でないときに引数の誤り（終了 2）で止めると、記録は直接編集できないので人間にも直す手段が残らない
- `boundary.sh` の `complete`: `requested_at` かホストの時刻を読めなかった指摘を「依頼より前」として落とすと、人間が書いた指摘が黙って消える

3 つとも別々の場面だが、必要な判断は同じ「どちらに倒すか」である。

## 決定

**判定できないときは「進んだことにする」側ではなく「もう一度やる」側に倒す**ことを原則とし、次のように適用する。

- `is_draft` は 3 値（`draft` / `draft でない` / `判定できない`）を返し、呼び手は「判定できない」を拒否側（`pushed`）として扱い、draft 解除の段階を実際に実行する
- `merge-state.json` の `state` が既知の段階名でないときは終了 2 で止めず、実態から再導出して続ける
- 指摘の時刻を読めないときはその指摘を落とさず、取得した指摘に含める

## 理由

- **段階の再実行は冪等だが、実行していない段階を済んだことにすると取り返せない**。draft の解除も、完了検査の書き出しも、もう一度実行して困ることは無い
- **指摘を落とす側の損害が非対称**。取りこぼすと人間のレビューが無かったことになるが、余分に 1 件出しても人間が読んで捨てるだけである
- **止めることが常に安全側とは限らない**。進行状態は直接編集できない（フックが拒否する）ので、記録の値が壊れているときに終了 2 で止めると、機構の外からも中からも直せない詰みになる。ここでの「拒否側」は「止める」ではなく「もう一度やる」である
- **`.draft // empty` のような書き方が事故の入口だった**。`//` は `false` も右辺に倒すので、draft でない MR が「判定できない」になる。値の有無と値そのものを分けて読む形に統一する

## 却下した案

- **判定できないときは常に終了 1 で止めて人間に委ねる**: `state` の破損では人間にも直す手段が無く、詰む。また、CLI が無い環境では毎回止まることになり、外部委任モードの意味が薄れる
- **判定できないときは楽観側（進んだ側）に倒して速く終わらせる**: 「解除した」と報告しながら実際は draft のまま、という最も見つけにくい失敗を作る
- **場面ごとに個別に決める**: 実際に 3 か所で同じ判断が必要になった。原則を 1 つ置いて適用例を並べるほうが、4 か所目で迷わない

## 影響

- `10_spec/skills/10-task-overall-summary.md` の再導出の節に、3 値の判定・未知の `state` の扱い・原則の 1 段落を追加し、`00_requirement/skills/10-task-overall-summary.md` の例外フローに対応する受け入れ基準を先に追加する
- `10_spec/skills/00-workflow-issue-mr-driven.md` の `complete` に時刻の比較の但し書きを追加し、要件の例外フローに `[E6]` を追加する
- テスト `FN-T11`（未知の `state`）・`FN-T14`（判定できない draft）・`BD-T14` / `BD-T15`（時刻の比較）で固定する
