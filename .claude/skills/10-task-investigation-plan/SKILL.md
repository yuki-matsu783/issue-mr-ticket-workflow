# 10-task-investigation-plan — 調査の観点を決めて調査チケットを起こす

計画書・チケット・`wip/tmp/` 以外に書き込まない。ソースコードも設計文書も `.claude/` 配下も触らない（調べたい・直したい箇所は計画書の対象に書いて実施チケットへ回す）。全体計画書と issue の受け入れ条件を書き換えない（疑義は結果報告の「見てほしい点」へ）。次の計画チケットを推測で作らず、次の次のチケットを先回りして作らない。計画書に調査結果や経過を書かない（「これから何をするか」だけ）。目視で次のチケットを選ばず `ticket.sh next` に従う。

## 目的

調査フェーズの入口。何を調べれば次の計画が判断できるかを観点に落とし、1 観点 = 1 チケットで起票する。

- 要件: `.claude/docs/00_requirement/skills/10-task-investigation-plan.md`
- 仕様（正。計画タスク共通の処理フロー・調査計画の固有手順・eval ID IVP-E01〜04）: `.claude/docs/10_spec/skills/10-task-investigation-plan.md`

## 手順

### 計画タスクの共通手順（正。他の `10-task-*-plan` はここを参照する）

1. **着手**: `bash .claude/skills/20-common-step-ticket/scripts/ticket.sh start <番号>`（作業中が他にあれば TK002 で止まる）。以後、作業ログはその都度追記する
2. **入力の確認**: 全体計画書（対象 issue・フェーズ列・方針）と前フェーズの成果物を読む。全体計画書が無い・フェーズ列が読めない・前フェーズの成果物とチケットが対応しないときは計画書を書かず、状態の不整合として結果報告に書いて呼び出し元に戻す
3. **計画書**: `wip/20_plans/<自チケット連番>-<種類>.md` を `assets/` のテンプレートから作り、`20-common-step-report-view` の手順で同名 HTML を作って `check-html.sh` に通す。内容は下の「OUT ひな形」
4. **実施チケット群**: `ticket.sh create` で 1 枚以上作る。DoD は下の「チケットの DoD の型」、依存は `--predecessors` で示す。実行者・人間レビュー要否・やってよいことは全体計画の方針と `.claude/rules/work-defaults.md` に従い、外すときは理由をチケットに書く
   - **DoD にコマンドを書くときは、書く前に `--help` かそのコマンドの仕様でオプションの形を確かめる**。実行者は DoD の文字列をそのまま打つので、存在しないオプションや形の違うグロブを書くと実施チケットの側で必ず躓く（`--filter` のようにパス全体に掛かるのか名前だけに掛かるのかで書き方が変わるものは特に確かめる）
5. **次の計画チケット**: 全体計画書（フィードバック計画以降はフィードバック計画書）のフェーズ列で次に来る計画チケットを **1 枚だけ**作る（次が無ければ全体まとめ）。`predecessors` には 4 で作った実施チケットの全番号を入れる。フェーズ列に書かれていなければ作らず、不整合として報告する。「対象なし」のときは 4 を飛ばし、計画書に対象なしの根拠を書いてこの 1 枚だけを作る
6. **完了**: `ticket.sh complete <番号>`（計画書がある / 実施チケットの DoD が計画書と対応 / 次の計画チケットがある。作業ログの必須項目と成果物のコミット済みも検査される）
7. **結果報告**: 計画書の場所・実施チケットの枚数・次の計画チケット・見てほしい点を呼び出し元に返す。push・MR 本文の更新・レビュー依頼は呼び出し元が行う

- **保留の書き方**（計画書の「保留した点」節。すべての計画タスクに共通）: 保留は「決めなかった」ではなく「決められない根拠がある」ものだけを立てる。1 件ごとに **(1) 何が未決か・(2) 現行の文書にどう書かれているか（引用または節の名前）・(3) 誰がいつ決めるか** を書く。(2) を省くと、後のフェーズが現行を読み直すところからやり直すことになる
- **保留を立てるとき・決着させるときは、先に「既に満たされていないか」を確かめる**（現行の文書・実装を読んで、その保留が既に解決済みでないかを見る）。済んでいるものを保留として持ち回ると、後のフェーズが解決済みの論点に時間を使う
- **再開**: 作業ログ「現在地」から続け、計画書とチケットを二重に作らない
- **差し戻し**（同種の追加チケットで戻ってきたとき）: 計画書と起票済みの未着手チケットを直す。完了済みは作業中に戻さない。対応を作業ログ「判断と根拠」に残す
- **書き込みを拒否されたら**: 範囲を広げる確認を求めず、その内容を計画書の対象に書いて実施チケットへ回す
- 次の計画チケットが無いまま完了しようとしても DoD で拒否される（作ってから完了する）

### 調査計画の固有手順

- 3 の計画書で、**調査観点**は全体計画書の「判断が必要になりそうな点」と issue の受け入れ条件から導く。答えが次の計画に効かない問いは含めない。1 観点のまとまり = 1 チケット
- リポジトリ外の情報が要る観点は**外部技術調査**として計画書に明示し、そのチケットの `allow.ops` に `web` を含める（明示の無いチケットはリポジトリ内の読み取りに限る）。この宣言は `curl` / `wget` に対して機構が強制する
- 既存のテスト・ビルドを動かして確かめる観点は、実行するコマンドと範囲を計画書の「対象と方法」に書き、そのチケットの `allow.ops` に `build-test` を含める（明示の無いチケットは実行しない）
- `.claude/**` への一時的な変更（`settings.json` へのフックの一時登録など）は計画しない。機構の上限が拒否する経路で、確かめたいことは既存の記録（transcript・`logs/`）で代えるか、AI アセット実装フェーズの検証に回す
- issue の種別が AI アセットなら、読む対象は `.claude/` 配下のアセットとその要件・仕様・DDR（問いの立て方は同じ）
- **調査チケットの DoD の型**: 「観点『{{問い}}』への答えが調査結果レポートに書かれている」「根拠（ファイル・行・コマンドの出力）が添えられている」「答えが出なかった問いは理由付きで残課題に残っている」
- 人間レビュー要否の既定（方針が無い場合）: 調査計画チケット・調査チケットとも「要」
- **見てほしい点の固定項目**: 観点が判断点と受け入れ条件を網羅しているか / チケットの粒度と枚数 / 調査の範囲が実装に踏み込んでいないか / 次の計画チケットの種類がフェーズ列と一致しているか

## OUT ひな形

`assets/investigation-plan.template.md`（共通の型は `20-common-step-report-view` の `assets/plan.template.md`）。

| 節 | 内容 |
|----|------|
| 対象 | issue・MR |
| 調査観点 | 問いの一覧と、それぞれがどの判断点・受け入れ条件に効くか |
| 対象と方法 | 問いごとの読む場所・確かめ方（書き込みなし）。外部技術調査は明示 |
| 調査チケット | どの問いをどのチケットが担うか・依存 |
| 成果物の形 | 調査結果レポートに何が書かれていれば次の計画が判断できるか |
| 保留した点 | 判断を保留した項目 |
| 対象なし | 該当時のみ: 根拠 |

## エラー時の対処

| 状況 | 対処 |
|------|------|
| `ticket.sh start` が TK002 | 作業中のチケットが他にある。そちらを完了・取り消ししてから着手する |
| 全体計画書が無い / フェーズ列が読めない | 計画書を書かず、状態の不整合として結果報告に書いて呼び出し元に戻す |
| フェーズ列に次の計画タスクが無い | 次の計画チケットを推測で作らない。不整合として報告する |
| 書き込みがフックに拒否された | 迂回せず、その内容を計画書の対象に書いて実施チケットへ回す |
| `check-html.sh` が `RV00x` | 指摘された項目を直してから完了する。縮退させない |
| `ticket.sh complete` が TK005 | DoD・作業ログ・未コミットのどれかが未充足。列挙された項目を埋めてから再実行する |
