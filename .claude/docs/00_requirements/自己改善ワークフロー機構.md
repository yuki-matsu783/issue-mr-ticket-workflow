# 自己改善ワークフロー機構

## 概要

Claude Code 上での開発作業を、issue を起点に MR（GitHub では PR。本書では MR と呼ぶ）上で人間がレビューしながら、チケット単位で進めるワークフロー機構の要件を定義する。機構は自分自身（`.claude/` 配下の AI アセット）を改善対象に含み、作業のたびに得た知見をスキル・フック・ルール・設計文書へ還流させる。

- **背景**: 参考実装が 2 系統ある。`参考ディレクトリ/agent-workflow` は 3 層スキル（workflow / work / task）とチケット駆動、フックによる権限統制とワーク境界の統制を持つ。`参考ディレクトリ/MR-driven-workflow` は commit / push のスクリプト経由強制、レポートの HTML ビュー、DDR、敵対的レビュー、frontmatter 規約と bash 規約を持つ。本機構は両者の長所を 1 つに統合し、このリポジトリを clone すればそのまま使える形で提供する。
- **目的**:
  1. すべての開発作業が 1 issue = 1 ブランチ = 1 MR に紐づき、ワークの切れ目ごとに人間のレビューを経て進む
  2. AI が「やってよいこと」をチケットに宣言し、逸脱をフックが機械的に拒否する
  3. commit / push を含む状態遷移をスクリプトに一本化し、AI の自己申告で状態が進まないようにする
  4. レビュー用の成果物（レポート）を人間が読みやすい HTML ビューで提供する
  5. 決定の経緯を DDR に、現在有効な要件・仕様を requirements / spec に分けて残し、作業の知見を AI アセットへ還流する
- **スコープ**:
  - 含む: 作業の振り分け、ワークの種類とワーク境界、チケット駆動の運用、権限統制フック、commit / push スクリプトとそれを使うスキル、レポートと HTML ビューのテンプレート、ドキュメント体系（requirements / spec / DDR / 用語辞書 / ルール）、全体まとめでの振り返りと AI アセットへの反映、セッションをまたぐ再開
  - 含まない: MR のマージ（人間が行う）、他リポジトリへの配布と配布先からの収穫、Gemini CLI 等の他エージェント向け複製、対応工数レポート、スライド生成、GitLab 対応（設計上は差し替え可能にするが初版は GitHub のみ）

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼を issue と MR に紐づけ、ワークごとに MR 上でレビューしながら、AI に細かいチケットを 1 枚ずつ進めてほしい。

**[So that]** AI が何をしているかを常に把握でき、逸脱を機械的に止められ、レビューの負担を段階的に分けられるため。

**[As a]** レビュアーとして、

**[I want]** 各ワークの成果を、結論・確度・見てほしい点が前半にまとまった HTML ビューで読みたい。

**[So that]** 差分の細部に入る前に全体像と確度をつかみ、レビューの重点を決められるため。

**[As a]** 機構の保守者として、

**[I want]** 作業中に見つかったアセットの不備や欠落を、振り返りで型どおりに洗い出し、issue や設計文書へ確実に残したい。

**[So that]** 同じ罠を繰り返さず、機構が使うたびに良くなるため。

## 受け入れ基準（Acceptance Criteria）

### A. 作業の振り分けと issue / MR の確定

- When ユーザーから依頼を受けたとき、Shall AI は依頼の内容を問わず、開発作業向け（`workflow-issue-mr-driven`）か軽作業向け（`workflow-quick-request`）のどちらかの振り分けスキルを読み込んでから着手しなければならない。
- When 振り分けスキルを読み込まずに書き込み系・実行系ツールが呼ばれたとき、Shall フックはその呼び出しを exit 2 で拒否し、どちらのスキルを読み込むべきかを AI に通知しなければならない（読み取り系ツールは対象外）。
- When 開発作業と判定されたとき、Shall AI はコードに触る前に既存 issue を検索して類似候補を提示し、どの issue で対応するかの承認を得なければならない。
- When issue が確定したとき、Shall AI は issue 番号を含む feature ブランチと、issue に紐づく（`Closes #N`）draft MR を作成し、その番号と URL を控えなければならない。
- When 軽作業と判定されたとき、Shall AI は作業範囲を宣言してから進め、終了時に使った AI アセットの改善要否を確認しなければならない。

### B. ワークの種類とワーク境界

- When 全体計画を立てるとき、Shall AI は次の 14 種のワークから、その issue で使うフェーズ列を決め、省略するフェーズには理由を書かなければならない。

| # | ワーク名 | type（識別子案） | 種別 | 主な成果物 |
|---|---|---|---|---|
| 1 | 全体計画 | `overall-plan` | 計画 | 全体計画書（フェーズ列・受け入れ条件との対応）と最初の計画チケット |
| 2 | 調査計画 | `investigation-plan` | 計画 | 調査計画書、調査チケット群、次の計画チケット |
| 3 | 調査実施 | `investigation` | 実施 | 調査結果レポート（md + HTML） |
| 4 | 設計計画 | `design-plan` | 計画 | 設計計画書（書く設計文書の一覧と骨子）、設計チケット群 |
| 5 | 設計実施 | `design` | 実施 | 要件定義書・仕様書（アプリ本体向け `docs/`）、設計結果レポート |
| 6 | 実装・テスト計画 | `implementation-plan` | 計画 | 実装計画書（変更対象・許可パス案・テスト方針）、実装チケット群 |
| 7 | 実装・テスト実施 | `implementation` | 実施 | コードとテスト、実装結果レポート |
| 8 | 設計フィードバック計画 | `design-feedback-plan` | 計画 | 実装と設計文書の差分一覧と書き戻し計画 |
| 9 | 設計フィードバック実施 | `design-feedback` | 実施 | 実装に合わせて更新した設計文書、DDR |
| 10 | AI アセット設計計画 | `ai-asset-design-plan` | 計画 | `.claude/docs/` に書く要件・仕様の一覧と骨子 |
| 11 | AI アセット設計実施 | `ai-asset-design` | 実施 | `.claude/docs/` の要件定義書・仕様書・用語辞書・DDR |
| 12 | AI アセット化計画 | `ai-asset-implementation-plan` | 計画 | 変更するフック・スキル・ルール・エージェント・settings の一覧とテスト方針 |
| 13 | AI アセット化実施 | `ai-asset-implementation` | 実施 | フック・スキル・ルール・エージェント・settings とそのテスト |
| 14 | 全体まとめ | `wrap-up` | まとめ | 統括レポート（md + HTML）、振り返り、AI アセット改善候補、MR 本文の最終化 |

- When フェーズ列を決めるとき、Shall 全体計画は先頭を全体計画、末尾を全体まとめとし、その間の各フェーズは「計画 → 実施」の対で並べなければならない（片方だけの採用は不可）。
- When ソフトウェア変更を扱うとき、Shall 標準のフェーズ列は 調査 → 設計 → 実装・テスト → 設計フィードバック → 全体まとめ とし、AI アセットの変更を扱うときは 調査 → AI アセット設計 → AI アセット化 → 全体まとめ としなければならない。両方を含む issue では両系列を全体計画で並べてよい。
- When 1 つのワーク（同じ type のチケット群）が完了したとき、Shall AI はそのワークの成果を push し、MR 本文にワークの要約を追記し、レビュー観点を添えて MR 上でレビューを依頼し、レビュー完了の連絡を受けるまで次のワークに着手してはならない。
- When レビュー依頼の後、Shall AI は `AskUserQuestion` で待たずに応答を終え、次のユーザー発言（レビュー完了の連絡）で再開しなければならない。
- When レビュー完了の連絡を受けたとき、Shall スクリプトが MR のレビュー状態とコメントを取得し、`CHANGES_REQUESTED` または未返信のインラインスレッドが残っていれば完了扱いにせず、その旨を AI に返さなければならない。
- When レビューで指摘があったとき、Shall AI は完了済みチケットを差し戻さず、同じ type の追加チケットとして対応しなければならない。
- When 次のワークのチケットに着手しようとしたとき、Shall フックは直前のワークのレビューが完了していなければ exit 2 で拒否しなければならない（同じ type の追加チケットは例外として許可する）。
- When 計画ワークが完了するとき、Shall その計画ワークは同じフェーズの実施チケット群と、次のフェーズの計画チケット 1 枚を todo に起こしていなければならない（チケットを最初に全件作らない）。

### C. チケット駆動の運用

- When チケットを作るとき、Shall チケットは `wip/10_tickets/00_todo/` に `NNN-<type>-<slug>.md` の名前で置かれ、frontmatter に少なくとも `type` / `status` / `depends_on` と「このチケットでやってよいこと」（後述 D）を持たなければならない。
- When チケットに着手・完了するとき、Shall AI はスクリプト経由で `00_todo/` → `10_doing/` → `20_done/` へ移動し、移動はコミットを伴わなければならない（着手コミットがそのチケットの差分の基準点になる）。
- When `10_doing/` に 2 枚目のチケットを置こうとしたとき、Shall フックは exit 2 で拒否しなければならない（WIP リミット 1）。
- When チケットを完了するとき、Shall チケットの DoD（完了条件）がすべて満たされ、作業ログ（うまくいったこと・うまくいかなかったこと・仕様からの逸脱）が書かれていなければならない。
- When 次に着手するチケットを選ぶとき、Shall AI は目視で判断せず、境界判定スクリプトが返す `todo_head_type` から次に読み込む work スキルを機械的に決めなければならない。
- When `wip/` 配下の成果物（全体計画・チケット・計画書・レポート・レビュー状態）が MR のマージ前に片付けられるとき、Shall 片付けはスクリプトが行い、main に残したい要約は MR 本文・issue コメント・`.claude/docs/` に書き写されていなければならない。

### D. 権限統制フック（チケットに宣言した範囲の強制）

- When チケットが `10_doing/` にあるとき、Shall AI が呼ぶ書き込み系ツール（Edit / Write / NotebookEdit）と Bash は、そのチケットの frontmatter に宣言された「やってよいこと」（書き込み可能なパスの glob、実行可能なコマンドの分類）の範囲でのみ許可されなければならない。
- When 宣言の範囲外の書き込み・コマンドが呼ばれたとき、Shall フックは exit 2 で拒否し、stderr に「エラーコード（`[WFxxx]`）・違反した対象・現在のチケットと type・AI が次に取るべき対処」を含むメッセージを出力しなければならない。メッセージには「迂回せず、必要ならユーザーに提案する」旨を含める。
- When チケットの frontmatter が宣言できる範囲を決めるとき、Shall 各 type の上限（許可パス・禁止パス・コマンド分類）はユーザーが管理する設定ファイル（`workflow-types.json` 相当）が定め、チケットの宣言はその上限を超えて権限を広げてはならない（deny は宣言で覆せない）。
- When doing 中のチケット自身の `type` や許可範囲を書き換えようとしたとき、Shall フックは exit 2 で拒否しなければならない。
- When 設定にも宣言にも記載のないパスへ書き込もうとしたとき、Shall フックは拒否ではなく確認（ask）として扱い、承認された範囲をセッション内で記憶してよい。ただしヘッドレス実行では ask が拒否になることを仕様に明記する。
- When 型定義に `.claude/**` の保護が含まれるとき、Shall AI アセット設計（`ai-asset-design`）は `.claude/docs/**` のみ、AI アセット化（`ai-asset-implementation`）は `.claude/hooks/**`・`.claude/skills/**`・`.claude/rules/**`・`.claude/agents/**`・`.claude/settings.json` のみを書けるよう分離し、通常の実装チケットからは `.claude/**` を書けてはならない。
- When フックが判定を行ったとき、Shall 許可・確認・拒否の結果を Git 管理外のログに記録し、振り返りの一次資料として参照できなければならない。
- When 状態ファイル（レビュー状態・マージ前作業の状態など、スクリプトが書く JSON）を AI が直接編集しようとしたとき、Shall フックは doing の有無にかかわらず exit 2 で拒否しなければならない。

### E. commit / push のスクリプト経由強制

- When AI がコミットまたは push を行うとき、Shall それぞれ専用のスクリプト経由でのみ行え、`git` のコミット・push コマンドの直接実行は PreToolUse フックが exit 2 で拒否しなければならない。拒否メッセージには使うべきスクリプトとスキルのパスを含める。
- When 直接実行を検知するとき、Shall フックはコマンド文字列の「コマンド位置」で判定し、コミットメッセージ本文・ヒアドキュメント・コメント・日本語の地の文に語が含まれるだけでは拒否してはならない。判定できない場合は部分一致へ縮退してよく、縮退時の挙動を仕様に明記する。
- When コミットスクリプトを呼ぶとき、Shall スクリプトはメッセージとステージ対象のパスを明示的に受け取り、`--amend`・`--no-verify`・全件ステージに相当する機能を持ってはならない。クレデンシャル類と開発副産物は除外リストで弾き、除外した事実を出力する。
- When コミットメッセージを作るとき、Shall 件名は `<prefix>: <日本語の説明>` の 1 行で「何を」「どう」変えたかを含み、AI 生成物であることを示すフッター（`Co-Authored-By` 等）や生成モデル名を含めてはならない。prefix は Conventional Commits に `ai-asset`（`.claude/` 配下の AI が読むアセットの変更）を加えたものとする。
- When push スクリプトを呼ぶとき、Shall スクリプトは push 前チェック（未コミットの変更が無い・doing チケットが無い・レポートの md と HTML が同期している・チケット遷移が正しい、など仕様で定める項目）を行い、未充足なら push せずに理由を返さなければならない。
- When push 前チェックを意図的に飛ばすとき、Shall 飛ばした項目と理由が Git 管理下のファイルに記録され、MR の差分としてレビュアーに見えなければならない。環境変数などレビュアーに見えない無効化手段を用意しない。
- When これらのスクリプトを AI が使うとき、Shall コミット用・push 用の task スキル（`task-git-commit` / `task-git-push` 相当）が手順を標準化し、他のスキルはそのスキルを参照して呼ばなければならない（各スキルが独自にコマンドを書かない）。
- When スクリプトによる状態遷移（チケット移動・レビュー依頼・レビュー完了・マージ前作業）がコミットを伴うとき、Shall それらのスクリプトも同じコミットスクリプトの規約に従わなければならない。

### F. レポートと HTML ビュー

- When 実施ワーク（調査・設計・実装・設計フィードバック・AI アセット設計・AI アセット化）と全体まとめが完了するとき、Shall 結果を `wip/30_reports/` に Markdown で書き、同じベース名の HTML ビューを併存させなければならない。Markdown が正文で、HTML はその視覚化である。
- When HTML ビューを作るとき、Shall AI はスキルの `assets/` にあるテンプレートを同じベース名でコピーし、Edit で節を埋め、使わない任意節を `<section>` ごと削除し、プレースホルダを 1 つも残してはならない。生成スクリプトで HTML を組み立てない。
- When HTML ビューを提供するとき、Shall 外部リソース（CDN のスクリプト・スタイル・フォント・画像）に依存しない自己完結 HTML で、ライト / ダークの両テーマで読めなければならない。
- When レポート用テンプレートを設計するとき、Shall 節構成は「サマリ（総括・件数・重点レビュー依頼）→ 確かめられなかったこと → 実施した内容と結果 → 設計への反映 → 想定と異なった点 → 残課題」の順で、結論の性質（良 / 注意 / 問題）とレビューの重み（◆ / ◇ / ・）を別の軸で表し、色だけに意味を持たせてはならない。
- When レポートのテンプレートを複数のデザインで提供するとき、Shall `<style>` 以外の DOM は全テンプレートで同一とし、その同一性をテストで確認しなければならない。
- When HTML ビューを出力したあと、Shall AI は機械的検査（プレースホルダ残存 0 件・リンク破断 0 件・重複 ID 無し・外部依存 0 件・`<style>` が 1 つ）を実行し、結果をチケットの作業ログに残さなければならない。
- When 計画書（全体計画・各計画ワークの計画書）を書くとき、Shall 計画には「これから何をするか」のみを書き、実施結果はレポートへ分離しなければならない。計画書の HTML ビューは任意とする。
- When 全体まとめを行うとき、Shall 統括レポートが issue の受け入れ条件との対応、各ワークのレビュー結果、うまくいかなかったこと、改善提案、残課題を 1 つにまとめ、その要約が MR 本文と issue コメントに書き写されなければならない。

### G. ドキュメント体系

- When 機構自身の設計を書くとき、Shall 要件定義書を `.claude/docs/00_requirements/`、仕様書を `.claude/docs/10_spec/`、DDR を `.claude/docs/20_ddr/`、用語辞書を `.claude/docs/90_glossary/` に置かなければならない。アプリ本体の設計文書は `docs/` 配下に同じ運用で置く。
- When requirements / spec を更新するとき、Shall それらは「その時点で有効な正史」だけを記述し、検討の経緯・却下した案・過去の版の内容を本文に残してはならない（変更履歴はレビュー記録の表と DDR で追う）。
- When 設計上の決定（複数案から選んだ・方針を変えた）が行われたとき、Shall その背景・決定・理由・却下案・影響を DDR に記録しなければならない。DDR は issue 番号ベースの識別子 `i<issue番号4桁>-<枝番2桁>-<タイトル>.md` で命名し、issue を持たない DDR は作らない。
- When DDR がマージされたあと、Shall 本文を変更してはならず、後続の決定で無効になった場合は frontmatter の `status`（`superseded` / `deprecated`）と `superseded_by` だけを更新しなければならない。
- When DDR の一覧を提供するとき、Shall 一覧は frontmatter から生成される生成物とし、手書きで保守してはならない。
- When リポジトリ内に Markdown を作るとき、Shall OKF 準拠の frontmatter（`type` 必須、`title` / `description` / `tags` / `keywords` 推奨）を付けなければならない。ただし issue / MR テンプレートや投稿本文になる断片、フックが解釈する専用 frontmatter を持つチケットは対象外とし、SKILL.md とエージェント定義の既存 `description` は上書きしない。
- When テンプレートファイルを置くとき、Shall 名前を `<名前>.template.md` / `.template.html` / `.template.sh` に統一し、テンプレートは完成形として正しい `type` を埋め込んでいなければならない。
- When 用語を定義するとき、Shall 用語辞書は正典（requirements / spec）への案内役に徹し、辞書自身が用語を再定義してはならない。

### H. ルール（`.claude/rules/`）の反映

- When `.claude/rules/` を整備するとき、Shall 参考実装の次のルールを本機構向けに調整して取り込み、`paths:` で適用範囲を絞れるものは絞らなければならない。

| ルール | 取り込む内容 |
|---|---|
| AI エージェント共通ルール | 応答は日本語。ごく小さな変更を除き全作業を issue 起点で進める。**issue を起票したこと自体は着手の指示ではない**（着手は人間の明示的な指示による。AI から着手を持ちかけない）。実作業の前に計画を提示し、承認されるまで書き換え・コマンド実行をしない。計画は全体計画と個別計画の 2 階層。GitHub の情報取得は WebFetch / curl ではなく `gh` CLI を使い、`gh` 不在時は公式 MCP ツールへ代替する（WebFetch / curl へは落とさない）。ドキュメント探索は frontmatter 索引を第一手段にし、`grep` は本文中の文字列を探すときに限る（索引機構の導入後に有効化） |
| Markdown frontmatter 規約 | OKF 準拠キー、`type` の値一覧（`requirements` / `spec` / `ddr` / `rule` / `skill` / `skill-reference` / `agent` / `plan` / `report` / `guide` / `review-points` 等）、DDR の識別子・`status`・`note`、対象外ファイル、テンプレート命名、値に `: ` を含めない |

| AI が渡すコマンド文字列の規約 | `description` は日本語 1 行で簡潔に、複数行コマンドは各ブロックに日本語コメント、1 行目にコメントを置かない、フック誤検知語を避ける、複雑なものは `.sh` に切り出す |
| ヘッドレス実行考慮 | `ask` を返す設計はヘッドレスで拒否になることを検討・明記する。フック・スクリプトは可能な限り `ask` を使わず exit 2 と代替経路で設計する |
| Git 運用 | ブランチ命名（`feature-<issue番号>-<slug>` / `fix-...`）、ベースブランチの取り込みは `git merge`（`git rebase` 禁止）、コミット運用（スクリプト経由・`git status` 確認・副産物の扱い） |
| ドキュメント運用 | 情報の寿命と置き場所の対応表（永続: `.claude/docs/` `docs/` / ブランチ限り: `wip/`）、コード内コメントから `wip/` を参照しない |
| ディレクトリ構成 | 各ディレクトリの役割と配置指針 |

### I. 自己改善（振り返りと AI アセットへの反映）

- When 全体まとめを行うとき、Shall AI はその issue で使った AI アセット（スキル・フック・ルール・エージェント・CLAUDE.md）と、フックの判定ログ・レポートの「想定と異なった点」「重点レビュー依頼」・MR のレビュー指摘を入力として、改善候補を洗い出さなければならない。
- When 改善候補を分類するとき、Shall 「足りなかった」「邪魔だった」「無かった」「問題なし」の観点と、「(a) アセットが無かった」「(b) あったが誤っていた」「(c) あったが罠が書かれていなかった」「(d) あったのに辿り着けなかった」の類型で整理し、候補が 0 件のときも 0 件である根拠をレポートに残さなければならない。
- When 改善候補の反映先を決めるとき、Shall 「いつ効くか（常時読込 / スキル呼び出し時 / レビュー時 / ツール呼び出し時）」と「守らせ方（読ませる / 手順化する / フックで落とす）」の 2 軸で選び、常時読込のアセットを増やすコストを考慮しなければならない。
- When 改善候補が `.claude/` 配下のアセット（スキル・フック・ルール・エージェント・settings）の変更を伴うとき、Shall AI はその MR 内で直接修正せず、issue として起票する案を提示し、承認後に起票しなければならない（振る舞いが変わらない文言修正も同じ。複数の軽微な候補は 1 つの issue にまとめてよい）。全体まとめのチケットは `.claude/**` を書けない。
- When 実施ワークの成果をレビューに出す前に、Shall AI は敵対的レビュー（経緯を渡さない読み取り専用サブエージェントが、ディレクトリ階層の `REVIEW-POINTS.md` を観点として欠陥を探す）を実施でき、指摘は MR のインラインコメントとして投稿し、人間の指摘と同列に返信しなければならない。実施回数はフェーズごとに上限を持ち、上限を緩める手段を用意しない。
- When 軽作業（`workflow-quick-request`）が終わるとき、Shall 全体まとめと同じ観点・類型で使った AI アセットの改善要否を確認し、「issue として記録だけする」を選べなければならない。

### J. セッションをまたぐ継続

- When セッションが開始・再開・compact されたとき、Shall フックが現在のブランチ・issue・MR・チケットの状態（todo / doing / done の先頭）・レビュー状態・次に読み込むべきスキルを `wip/` 配下のファイルと MR から導出して注入し、AI が手書きの引き継ぎメモに依存せずに再開できなければならない。
- When 振り分けスキルの再宣言を求めるとき、Shall `wip/10_tickets/` の todo / doing / done のいずれかにチケットがある間（マージ前の片付けで消えるまで）は継続とみなし、再宣言を要求してはならない。
- When issue を起票しただけのとき、Shall AI はそれを着手の指示とみなさず、着手はユーザーの明示的な指示（「#N をやって」等）を待たなければならない。
- When レビュー依頼・完了・マージ前作業の状態を持つとき、Shall 状態は Git 管理下の JSON に記録され、スクリプトだけが書き換え、`request` / `complete` は MR への実操作（コメント投稿・レビュー取得）を自ら行ってその証跡（コメント ID・URL・SHA）を残さなければならない。

### アルタナティブフロー（代替経路）

- When issue と MR を作らずにチケット駆動だけを試したいとき、Shall ワーク境界の承認を `AskUserQuestion` で取る単独実行モードを提供し、その経路は証跡が会話上の承認に依存することを仕様に明記しなければならない。
- When `gh` CLI が使えない環境のとき、Shall スクリプトは MR 操作を外部（MCP ツール等）に委ね結果を引数で受け取るモードを提供し、証跡の強度が `gh` 実行時より劣ることを状態ファイルに記録しなければならない。
- When 小さな依頼でワーク境界の往復が過剰なとき、Shall 全体計画でフェーズを省略（理由付き）でき、レビュー依頼に「approve のみで可」と添えられなければならない。type をまとめることでは対処しない。
- When レビュアーがチャットでレビュー判断を伝えたとき、Shall AI はその判断を MR の通常コメントとして記録してから `complete` を実行しなければならない。

### 例外フロー（エラーケース）

- When フックが exit 2 で拒否したとき、Shall AI は状態ファイルの直接編集・別コマンドでの迂回・フックの無効化を行わず、メッセージの「対処」に従うか、ユーザーに提案しなければならない。
- When `complete` が `CHANGES_REQUESTED` または未返信スレッドで止まったとき、Shall AI は同じ type の追加チケットで対応し、返信スクリプトでスレッドに返信してから再実行しなければならない。
- When マージ前の衝突判定で default ブランチとの衝突が検知されたとき、Shall AI は衝突ファイルを示して承認を得てから `git merge` で取り込み、`git rebase` や片側丸ごと採用（`--ours` / `--theirs`）で解消してはならない。
- When フックの依存（jq・ライブラリ・設定ファイル）が壊れていて判定できないとき、Shall 拒否側のフック（権限統制・commit / push 強制）は拒否へ倒し、注入側のフック（SessionStart）は何も注入せずに通す（fail-open）。どちらへ倒すかは仕様に明記する。
- When ヘッドレス実行で承認（`AskUserQuestion`）が必要になったとき、Shall AI は承認が必要な内容を報告してセッションを終え、次回セッションの再開判定から続けなければならない。
- When 承認が得られずに却下されたとき、Shall AI はその段階に留まり、先の段階（issue 作成・ブランチ作成・マージ前作業・issue への投稿）へ進んではならない。

## 前提条件

- リポジトリは GitHub でホストされ、`gh` CLI が導入・認証済みである（未導入時は導入を案内して停止する）
- 実行環境は Windows の git bash（MSYS bash 4.3 以上）と `jq` を前提とし、WSL / Linux での動作は未検証として扱う
- MR は squash merge され、ブランチ上の `wip/` の履歴は main に残らない
- ユーザーは MR 上でレビュー（approve / comment / changes requested / インラインコメント）を行える
- 1 issue = 1 ブランチ = 1 MR。1 セッションは 1 つの MR だけを扱う

---

## 制約条件

- **技術的制約**:
  - フック・スクリプトは bash で書き、bash 規約（H 節）に従う。PowerShell は Bash ツールと並んで検知対象に含めるが、実処理は bash に統一する
  - フックは PreToolUse の全 Bash / PowerShell 呼び出しで起動しうるため、前置フィルタで足切りし、外部プロセス起動を最小化する
  - Claude Code の `permissions.deny` は複合コマンドをすり抜けるため、強制はフック側が担う（`deny` は多重防御として併用してよい）
  - HTML ビューは自己完結とし、Claude Code の Artifact 機能に依存しない（ローカルでブラウザを開けば読める）
- **ビジネス的制約**:
  - MR のマージ・issue の内容・レビュー完了の判断は人間が行う。AI は draft 解除までで止まる
  - 他人の issue への投稿など取り消せない外部への副作用は、本文そのものの承認を得てから行う
- **外部的制約**:
  - GitHub のレビュー API はインラインコメントの投稿がアトミックであり、差分に存在しない行を指定すると全件失敗する
  - `gh` は人間のアカウントで認証されるため、AI の投稿は本文先頭の署名で識別する

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | フックの空振り（対象外の呼び出し）は外部プロセスを起動せず数十 ms 以内で抜ける。SessionStart の注入は 8 KB を目安とし、超過時は警告を添える |
| セキュリティ | AI が書く frontmatter を信頼せず、権限の上限はユーザー管理の設定が決める。クレデンシャル類はコミット除外リストで弾く。フックのログに機密情報を出力しない。悪意ある迂回への対抗は目的としない（既定動作を安全側へ倒す仕組みであり、安全境界ではない） |
| 可用性 | 拒否側のフックは依存が壊れたとき拒否へ、注入側のフックは通す側へ倒す。状態ファイルはスクリプトが原子的に更新し、中断で壊れない |
| 保守性 | ワーク（type）の追加は設定ファイルの type 定義 2 件（計画・実施）とスキル 2 件と対応表 1 行で済む。正は 1 箇所に決め、複製する場合はテストで同一性を固定する。エラーコードは `[WFxxx]` で機械判定できる |
| テスト容易性 | フック・スクリプトは `main` ガードを持ち、テストから `source` して純粋関数を単体テストできる。テストは `passed=N failures=N` を出力し失敗時 exit 1 |
| 可読性 | ドキュメント・コミットメッセージ・コマンドの `description` は日本語。SKILL.md は読むタイミング単位で `references/` に分割し、1 ファイルが Read の上限を超えない |
| 一貫性 | 振り返りの観点・類型の文言を全体まとめと軽作業の両方で揃える。レポートのテンプレートは DOM を共有する |
