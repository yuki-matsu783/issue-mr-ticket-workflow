# 10-work-ai-asset-design-plan スキル

## 概要

AI アセット設計フェーズの計画ワークの要件を定義する。AI アセット（スキル・フック・ルール・エージェント・設定）の変更に先立ち、機構自身の設計文書の置き場（`.claude/docs/`）に**どの要件定義書・仕様書・用語辞書を、どんな骨子で書くか**と判断点の結論方針を決めて AI アセット設計計画書にまとめ、AI アセット設計チケット群と次のフェーズの計画チケットを起こして計画チケットを完了する。設計文書もアセット本体も書かない。

- **背景**: AI アセットは機構自身の振る舞いを変えるため、文書なしに直すと「なぜこの拒否があるのか」「このスキルの正はどこか」が失われる。要件・仕様・スキルの 1:1:1 を保ちながら、何を書くか・何を決めるかを先に 1 枚にし、人間が設計に入る前に方向を正せるようにしたい。
- **目的**: 文書の一覧（新規 / 更新・置き場・骨子）と判断点の結論方針を、受け入れ条件との対応・横断文書との整合・ヘッドレス実行の帰結の検討付きで、レビュー可能な計画書として残す。
- **スコープ**:
  - 含む: AI アセット設計計画書の作成、判断点の結論方針、文書の一覧と骨子、横断文書・用語辞書との整合の洗い出し、ヘッドレス実行の扱いの検討、設計チケット群と次の計画チケットの作成、計画チケットの着手から完了まで、「対象なし」の扱い、再開時の扱い
  - 含まない: 設計文書の作成（`10-work-ai-asset-design-exec`）、アセット本体の変更（AI アセット実装・テストフェーズ）、アプリ本体の設計文書（設計フェーズ）、フェーズ列の決定（`10-work-overall-plan` / `10-work-feedback-plan`）、ワークの切れ目の処理（`00-workflow-issue-mr-driven`）

---

## ユーザーストーリー

**[As a]** 自己改善する機構を運用する開発者として、

**[I want]** AI アセットが変更される前に、どの要件・仕様がどんな骨子で書かれ、何を根拠にどの案を採るつもりかを 1 枚の計画で確認したい。

**[So that]** 機構自身の変更が文書の裏付けなしに進むのを防ぎ、1:1:1 の対応を保ったままアセットを育てられるため。

---

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When このワークに入ったとき、Shall スキルは全体計画で合意した実行者（サブエージェントのモデル）で、調査結果レポート（またはフィードバック計画の決定）・issue の受け入れ条件・既存の機構の設計文書（要件・仕様・用語辞書・DDR）・機構のドキュメント規約を入力に進めなければならない。
- When AI アセット設計計画チケットに着手するとき、Shall スキルは提供コマンドで未着手 → 作業中に進め、手作業でチケットを動かしてはならない。
- When 作業を進めるとき、Shall スキルは作業ログをその都度追記し（現在地・判断と根拠・拒否や迂回・使った AI アセット・スコープ外の気づき）、完了時にまとめて書いてはならない。
- When 文書の一覧を決めるとき、Shall 対象アセットごとに 1:1:1 の原則（要件定義書と仕様書はアセット名と同名で、アセットの種類ごとのサブディレクトリに置く）に従い、既存文書があれば更新・無ければ新規として一覧に載せ、判断の経緯は DDR の追加として計画しなければならない。
- When 人間の確認・承認を増やす設計を含むとき、Shall スキルはヘッドレス実行（ユーザーが応答できない実行形態）での帰結と代替経路を仕様書に書くことを骨子に含めなければならない。
- When AI アセット設計計画書の案ができたとき、Shall スキルは関連するアセット・文書のまとまりを単位に設計チケット群（1 枚以上）を未着手に作らなければならない。互いに依存しないチケットは並列に進めてよいことを記す。
- When 設計チケットを作るとき、Shall その DoD は「文書が機構のテンプレートに沿って作成（更新）されている」「受け入れ条件 <X> が受け入れ基準 / テストシナリオ（テスト ID）に落ちている」「横断文書・用語辞書の該当箇所が整合している」「決定の経緯が DDR に残っている」「確認を伴う設計はヘッドレス時の挙動が仕様書にある」の型で書かなければならない。
- When 設計チケット群を作り終えたとき、Shall スキルはフェーズ列で AI アセット設計の次に来るフェーズの計画チケットを 1 枚だけ未着手に作らなければならない（通常は AI アセット実装・テスト計画）。それより先のチケットは作らない。
- When チケットを作るとき、Shall チケットに次を明記しなければならない: ワークの種類、状態、先行チケット、実行者（LLM モデル）、人間レビューの要否とその理由、このチケットでやってよいこと、目的、完了条件（DoD）。実行者・レビュー要否・やってよいことは全体計画で合意した方針に従い、方針から外す場合は理由をチケットに書く。
- When AI アセット設計計画チケットを完了するとき、Shall 計画書（md + HTML）・設計チケット群・次の計画チケットが存在し、DoD（計画書に結論方針・文書の一覧と骨子・横断文書との整合・受け入れ条件との対応がある / 設計チケットの DoD が文書と対応している / 次の計画チケットがある）がすべて満たされ、作業ログの必須項目が埋まっていなければならない。完了は提供コマンドで行い、欠けていれば拒否される。
- When 完了したとき、Shall スキルは結果報告（計画書の場所、設計チケットの枚数と並列にできる組、次の計画チケット、レビューで見てほしい点）を返して呼び出し元に制御を戻さなければならない。
- When レビューで見てほしい点を書くとき、Shall 少なくとも「文書の一覧が 1:1:1 の原則と置き場の規約に沿っているか」「結論方針が調査結果（またはフィードバック計画の決定）と整合し、機構の中核（フック等）の変更の要否が明示されているか」「ヘッドレス実行の帰結が検討されているか」「設計チケットの粒度と次の計画チケットの種類」を挙げなければならない。

### 代替フロー

- If 受け入れ条件が機構の設計文書の変更を必要としないと分かった場合、Then スキルは計画書に「対象なし」とその根拠を書き、設計チケットを起こさず次の計画チケットだけを作って即座に完了しなければならない（フェーズを省かない）。
- If このフェーズがフィードバック計画から来ており改善候補の一覧が入力にある場合、Then スキルは候補ごとの反映先（いつ効くか × 守らせ方の 2 軸の選択）を文書の骨子に引き継ぎ、候補との対応を計画書に残さなければならない。
- If 対象アセットに既存の要件・仕様が無い場合、Then スキルは新規作成として一覧に載せ、横断的な文書に既に書かれている内容はそちらを正として参照する方針を計画書に書かなければならない。
- If 再開時に計画チケットが作業中で計画書やチケットの一部がある場合、Then スキルは作業ログの「現在地」から続きを進め、二重に作ってはならない。
- If レビューの差し戻しで同じ種類の追加チケットとしてこのワークに戻った場合、Then スキルは計画書と起票済みの未着手チケットを直し（完了済みチケットは戻さない）、対応を作業ログの「判断と根拠」に残さなければならない。

### 例外フロー

- If 機構の設計文書やアセット本体への書き込みが機構に拒否された場合、Then スキルは範囲を広げる確認を求めず、文書は設計チケットに、アセット本体は実装・テストフェーズに回さなければならない（計画ワークは計画書とチケットだけを書く）。
- If 調査結果（またはフィードバック計画の決定）だけでは結論方針を立てられない場合、Then スキルは推測で決めず、「設計チケットで結論を書く」または「調査の追加が要る」として結果報告に書き、判断を人間レビューに委ねなければならない。
- If 次の計画チケットを作らずに完了しようとした場合、Then DoD が満たされないため完了できず、作ってから完了しなければならない。

### AI アセット設計計画書の内容

- When 計画書を書くとき、Shall 次を含めなければならない: 対象 issue と MR、判断点の結論方針（採る案と根拠。機構の中核の変更が要るか、設定・定義の追加で済むかの別）、文書の一覧（新規 / 更新・置き場・各文書の骨子）、横断文書・用語辞書との整合、ヘッドレス実行の扱い、受け入れ条件との対応、設計チケットの一覧、判断を保留した点。
- When 計画書を書くとき、Shall 「これから何をするか」だけを書き、設計の本文を書き始めてはならない（骨子まで）。
- When 計画書を置くとき、Shall 作業領域の計画書の置き場に、提供されたテンプレートに沿って 1 つ置き、同じ名前の HTML ビューを併存させなければならない（Markdown が正文。作り方と検査はレポートの HTML ビューと同じ）。

### AI アセット設計計画チケットの扱い

- When 計画チケットが作業中のとき、Shall そのチケットの「やってよいこと」は計画書の置き場・チケットの置き場・`wip/tmp/` への書き込みに限り、機構の設計文書・アセット本体・アプリのコードと文書を書けてはならない。
- When 計画チケット・設計チケットの人間レビュー要否を決めるとき、Shall 全体計画で合意した方針に従い、方針が無ければどちらも「要」を既定としなければならない（機構自身の振る舞いに影響する）。

### 他のスキル・機構との整合

- When 調査結果レポート・フィードバック計画書・全体計画書を参照するとき、Shall スキルはそれらを書き換えず、疑義があれば結果報告の「見てほしい点」に書かなければならない。
- When 次に着手するチケットを選ぶとき、Shall スキルは提供コマンドが示す結果に従い、目視で判断してはならない。
- When 設計文書の書式に言及するとき、Shall not スキルは要件定義書・仕様書の書き方を再掲せず、設計書作成の task スキルと機構のドキュメント規約を参照しなければならない。

## 前提条件

- フェーズ列で AI アセット設計が含まれており、直前のワークの切れ目の処理が済み、計画チケットが未着手にあること
- 計画チケットの実行者として全体計画で合意したモデルのサブエージェントで起動されること
- 計画書・チケットのテンプレートと提供コマンド、設計書作成の task スキルが用意されていること

---

## 制約条件

- **技術的制約**: サブエージェントで実施するためユーザーに質問できない。判断に迷う点は決めずに「判断を保留した点」と「見てほしい点」に書く。計画書は 1 フェーズに 1 つ
- **ビジネス的制約**: 結論方針と文書の構成は人間レビューで確定する。スキルは案を出し、レビュー前に設計文書を書き始めない
- **外部的制約**: 対象は機構の設計文書に限る。アプリ本体の設計文書は設計フェーズで扱う

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 計画書に issue 番号・MR 番号が残り、受け入れ条件（または改善候補）→ 文書 → チケットの対応を辿れる |
| 一貫性 | チケットの記載事項・DoD の型・作業ログは他の work スキルと同じ。フェーズの名前は `00-workflow-issue-mr-driven.md`「ワークの構成」と一致する |
| 簡潔性 | 計画書は骨子までに留め、設計の本文を先取りしない |
| 冪等性 | 再開時に計画書とチケットを二重に作らない |
