## 実施した内容と結果

### 1. 置き場の削除はディレクトリ自身と祖先も拒否する（A8） △注意

`i0009-30` は「作業中が 0 枚の切れ目では `workflow-guard` も判定しないので `rm wip/10_tickets/20_done/*.md` が誰にも止められない」という穴を塞いだ。ところが追加した判定は `wip/10_tickets/20_done/**` の glob で、**`**` はパターンの位置より下**を指す。

| コマンド | 一致するか |
|---|---|
| `rm wip/10_tickets/20_done/0003.md` | する → WF303 |
| `rm -rf wip/10_tickets/20_done`（ディレクトリ自身） | **しない** |
| `rm -rf wip/10_tickets` | **しない** |
| `rm -rf wip` | **しない** |

作業中 0 枚の窓では `workflow-guard` も判定しないので、**塞いだはずの穴が 1 段上のパスにそのまま残っていた**。`rm -rf wip` は進行状態・チケット・計画書・結果報告をまとめて消す。

**決定**: 元が置き場のディレクトリ自身（`wip/10_tickets/10_doing`・`20_done`）**またはその祖先（`wip/10_tickets`・`wip`）**のときも WF302 / WF303 とする。祖先はどちらの置き場も消すので **WF302**（作業中の置き場が消える方。回復しにくい）に倒す。`SG-T11` を新設し、**`rm -rf wip/tmp` と `rm -rf logs` は通る**負のコントロールを添えた。DDR `i0009-59`。

**却下した案**: glob の規則を変えてパターン自身の親に一致させる（`.claude/**` がリポジトリルートに一致するなど他のすべてが壊れる）／`wip/**` を丸ごと保護（`wip/tmp/**` への書き込みが止まる）／`-rf` の有無で拾う（書き方を数えることになり、`rm wip/.../20_done` を取りこぼす）。

**結論**: glob の意味を変えずに、この 1 か所で明示した。ただし**書き方の網羅**（`./wip`・`wip/`・`cd wip && rm -rf .`）は残課題。

### 2. `hc_lock` は陳腐化したロックを強制解放する（A7） ◎良

`i0009-23` は「**ロックの解放漏れが一番怖い**」と書き、対策を `trap` にした。ところが同じ共通仕様の §3 が自ら書いている。

> §1 のラッパーの `||` も §3 の `trap ERR` も、**打ち切られた場合には効かない**（プロセスごと終了させられ、出力が捨てられるため）

`post-push-usage-report` は transcript を解析する重い処理で、**ロックを保持したまま打ち切られる可能性がいちばん高い**。そうなるとロックディレクトリが残り続け、以後の Stop / SubagentStop は毎回 2 秒待って諦め、**使用量の集計が恒久的に止まる**（しかも 2 秒の遅延が常時乗る）。

**決定**: `hc_lock` は取得を試みる前に、**ロックの作成時刻が 60 秒より古ければ陳腐化とみなして `rmdir` してから取り直す**。強制解放は実行ログに 1 行残す。60 秒以内のロックは従来どおり 2 秒で諦める。`HK-T20` で固定（60 秒超は回復する / 60 秒以内は諦める / 強制解放が記録される）。DDR `i0009-60`。

**60 秒の根拠**: `hc_lock` が守るのは JSON を 1 つ読んで加算して書く処理で、正常なら数十 ms。`command` 型フックの既定タイムアウトは 600 秒、`UserPromptSubmit` は 30 秒（`i0009-11`）なので、60 秒は「打ち切られたフックのロック」を確実に拾い、「生きているフックのロック」を誤って奪わない範囲にある。

**却下した案**: PID で生死を判定（Windows の Git Bash で移植性が無く、PID は再利用される）／`flock`（Git Bash に無いことがある。`mkdir` を選んだ理由がそれ）／諦めたら記録だけ（人間が手で消すまで直らない）／タイムアウトを伸ばす（残置ロックには効かない）。

### 3. `usage` の加算に `hc_lock` を使うと個別仕様に書く（B6） ◎良

`i0009-23` は影響に「`post-push-usage-report.md`（`usage/<branch>.json` の加算をロックで直列化）」と挙げていたが、**当該仕様に「ロック」の語が 1 つも無かった**。実際に競合する `--accumulate` の加算が無防備で、一時ファイル + `mv` は「既定」側にだけ入っていた。**R22 は §5 と `HK-T17` では閉じたが、実装される側の仕様では閉じていなかった**（`i0009-58` が規約にした型そのもの）。

**決定**: `--accumulate` と既定の加算に「`hc_lock usage-<branch>` を取ってから加算し、取れなければ 2 秒で諦めて実行ログに 1 行残して終了 0」を書いた。陳腐化（60 秒）は `hc_lock` が持つので個別仕様には書かない（**数値を 2 か所に置かない**）。DDR `i0009-61`。

**なお `i0009-50`（サブエージェントは既定で background）により、複数のサブエージェントが同時に走っている状態が既定**になった。競合の確率は `i0009-23` の想定より高い。

### 4. 制御方式の番号を変えたら参照する表も直す（B9・A6・B10） ◎良

- **B9**: 0020 が MCP の分岐を制御方式 4 として新設し、旧 4（入力不正）を 5 に繰り下げたが、「要件との対応」表は「判定不能 | **制御方式 4**、WF309」のままだった → 5 に直し、MCP の分岐を指す行を追加。**規約として**「制御方式に途中挿入して番号を繰り下げたら、同じ変更でその文書内と他文書からの参照を直す」「**末尾に足せるものは末尾に足す**（繰り下げを起こさない）」を定めた。DDR `i0009-62`
- **A6**: 呼出条件が「`mcp__.*` は draft 解除と**置き場宛の書き込み**を捕まえるために要る」のままで、制御方式 4（それ以外の MCP は許可）と食い違っていた → 「draft 解除を捕まえるために要る」に揃えた。制御方式 4 の理由「MCP は `file_path` も `command` も持たない」も、MCP サーバがスキーマを自由に決められる以上は断定できないので、「**このフックが読む `file_path` / `command` のキーを持たない**」に緩め、**パス様のキーを持つ MCP ツールが現れたら制御方式 4 に置き場の判定を足す**と再点検の条件を書いた
- **B10**: 制御方式 0 が `notify` を記録すると書くのに記録節に `notify` が無かった → 追加。また番号順に読むと 0 が「停止中 → 許可」の 1 より先に走り、停止中でも記録が出て §3 に反する → 「**1 の後に評価する**（番号は判定の材料としての前後関係を表す）」と明記

1. **0016 へ**: `hc_lock` の実装に**陳腐化の判定**（作成時刻 60 秒）を含める。作成時刻の取得は `find <dir> -maxdepth 0 -mmin +1` の 1 プロセスで足りる（`hc_lock` はホットパスではない）

5. **今後の設計チケットへ**: `i0009-62` の規約（制御方式に途中挿入したら参照を直す・末尾に足せるものは末尾に足す）と `i0009-58` の規約（横断→個別に降ろす先を 4 種類列挙し切る）
