# 00-workflow-issue-mr-driven スキル

## 概要

ユーザーの依頼を GitLab の issue と draft MR に紐づけてから実作業に入り、人間レビューが必要なワークの切れ目で MR 上のレビューを挟んで進める、開発作業向けの振り分けスキルの要件を定義する。このスキルは順序と承認ポイントを司るオーケストレータであり、issue / ブランチの操作は task スキルに、各ワークの実施は work スキルに委ねる。機構全体の要件は `自己改善ワークフロー機構.md` が持つ。本書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

- **背景**: チケット駆動の実作業だけでは「その作業がどの issue に対するもので、どの MR に載るのか」「どこで人間が確認するのか」が決まらない。作業の起点を issue に固定し、issue の確定・全体計画・レビューが必要なワークの切れ目・外部への副作用に人間の判断を挟みたい。
- **目的**: 「依頼 → 全体計画チケットの着手 → 既存 issue の照合 → 承認 → issue の確定 → feature ブランチと draft MR → 全体計画（フェーズ列・実行者・レビュー要否の合意）→ ワークの繰り返し（レビュー要のチケットを含むワークの後は人間レビュー）→ 全体まとめ（統括・振り返り・マージ前作業・draft 解除）→ 停止」の順序を固定し、すべての作業が 1 issue = 1 ブランチ = 1 MR に紐づき、レビューが必要な箇所を飛ばして進めない状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md と参照資料）、issue 追記・issue 通知のテンプレート、類似 issue の判定基準、承認ポイントの定義、全体計画までのメインエージェントによる実施、ワークの繰り返しの制御（サブエージェントへの委任・次のワークの選択・push・MR 本文更新・レビュー依頼と完了・指摘への追加チケット・未着手チケットの見直し）、全体まとめの中のマージ前作業と draft 解除、再開
  - 含まない: MR のマージ（人間が行う）、issue / ブランチ / MR の具体的な操作手順（task スキル）、各ワークの内容（`10-work-*`）、宣言範囲の強制やワーク境界の判定の仕組み（仕様書）、レビューの自動化

---

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼した作業を、issue と MR に紐づけ、全体計画までは対話で合意し、以降はレビューが必要なワークの切れ目で MR 上のレビューを挟みながら進めたい。

**[So that]** 重複した対応や issue に紐づかない変更を防ぎ、AI の作業を必要な箇所で確認でき、依頼・合意・作業・成果の経緯を GitLab / GitHub 上で追えるため。

## 受け入れ基準（Acceptance Criteria）

### ワークの構成

このスキルが組み合わせるワークは次の 15 種で、issue ごとにこの中からフェーズ列を組む。各ワークの中身（成果物の書き方・チケットの起こし方）は対応する work スキルの要件定義書が正とし、ここでは種類・順序・担当・切れ目の規則だけを定める。

| # | ワーク名 | 種別 | 担当 | 主な成果物 |
|---|---|---|---|---|
| 1 | 全体計画 | 計画 | メインエージェント | 全体計画書（issue の種別・フェーズ列・受け入れ条件との対応・各チケットの実行者とレビュー要否の方針）と最初の計画チケット |
| 2 | 調査計画 | 計画 | サブエージェント | 調査計画書、調査チケット群、次の計画チケット |
| 3 | 調査実施 | 実施 | サブエージェント | 調査結果レポート（md + HTML） |
| 4 | 設計計画 | 計画 | サブエージェント | 設計計画書（書く設計文書の一覧と骨子）、設計チケット群 |
| 5 | 設計実施 | 実施 | サブエージェント | 要件定義書・仕様書（アプリ本体向け `docs/`）、設計結果レポート |
| 6 | 実装・テスト計画 | 計画 | サブエージェント | 実装計画書（変更対象・許可範囲案・テスト方針）、実装チケット群 |
| 7 | 実装・テスト実施 | 実施 | サブエージェント | コードとテスト、実装結果レポート |
| 8 | フィードバック計画 | 計画 | メインエージェント | ここまでの振り返り（チケットの作業ログ・レビュー指摘・拒否の記録から洗い出した反映すべき内容）と、候補ごとの「この MR で対応 / 別 issue」の決定、後続フェーズ（設計フィードバック・AI アセット設計・AI アセット化）のチケットの作成・修正、別 issue の起票 |
| 9 | 設計フィードバック計画 | 計画 | サブエージェント | 実装と設計文書の差分一覧と書き戻し計画 |
| 10 | 設計フィードバック実施 | 実施 | サブエージェント | 実装に合わせて更新した設計文書、DDR |
| 11 | AI アセット設計計画 | 計画 | サブエージェント | `.claude/docs/` に書く要件・仕様の一覧と骨子 |
| 12 | AI アセット設計実施 | 実施 | サブエージェント | `.claude/docs/` の要件定義書・仕様書・用語辞書・DDR |
| 13 | AI アセット化計画 | 計画 | サブエージェント | 変更するフック・スキル・ルール・エージェント・設定の一覧とテスト方針 |
| 14 | AI アセット化実施 | 実施 | サブエージェント | フック・スキル・ルール・エージェント・設定とそのテスト |
| 15 | 全体まとめ | まとめ | サブエージェント（承認が要る操作はメインエージェント） | 残った反映すべき内容の別 issue 起票、default ブランチとの衝突解消、統括レポート（md + HTML）、MR 本文の最終化、関連 issue へのコメント、作業領域の片付け、push、draft 解除 |

- When フェーズ列を決めるとき、Shall スキルは issue の種別（アプリ / AI アセット。両方を含む issue は両方）を判定してユーザーと合意し、種別ごとの次のテンプレートを土台にしなければならない。先頭は全体計画、末尾は全体まとめとし、調査とフィードバック計画は必ず含める。

| issue の種別 | フェーズ列のテンプレート |
|---|---|
| アプリ（`docs/`・ソースコードの変更が主目的。AI アセットへは副産物として反映） | 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計フィードバック / AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |
| AI アセット（`.claude/` 配下の変更が主目的） | 調査 → AI アセット設計 → AI アセット化 → フィードバック計画 → 追加の AI アセット設計 / AI アセット化（フィードバック計画で決める）→ 全体まとめ |

- When テンプレートを当てるとき、Shall 主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット化）は依頼の性質に応じて全体計画で含め、フィードバック計画より後のフェーズは全体計画では決めずフィードバック計画で決めなければならない。フィードバック計画以外のフェーズは「計画 → 実施」の対で並べる（片方だけの採用は不可）。
- When フェーズを並べるとき、Shall 調査 → 設計 → 実装・テスト → フィードバック計画 → 設計フィードバック → AI アセット設計 → AI アセット化 → 全体まとめ の順とし、含めないフェーズだけを飛ばさなければならない。
- When 含めたフェーズでやることが無いと計画ワークで分かったとき、Shall そのフェーズを省くのではなく、計画チケットを「対象なし」として即座に完了し、次のフェーズの計画チケットを起こさなければならない（まだ行っていない全体計画の段階で「やらない」と判断しない）。
- When 計画ワークが完了するとき、Shall その計画ワークは同じフェーズの実施チケット群と、次のフェーズの計画チケット 1 枚を作成済みでなければならない（チケットを最初に全件作らない）。
- When ワークの中のチケットを実施するとき、Shall チケットは既定ではそのワークのサブエージェントの中で順に実施され、互いに依存しないチケット群を並列に進めたいとき、または新しいコンテキストで実施したいとき（チケットの実行者がワークのモデルと異なるときを含む）に限り、チケット単位でさらにサブエージェントに分割しなければならない。分割したチケットにも宣言した範囲の強制が同じように働く。
- When 1 つのワーク（同じ種類のチケット群）が完了したとき、Shall そこをワークの切れ目とし、そのワークのチケットに 1 枚でも「人間レビュー要」のものがあれば、MR 上の人間レビューが完了するまで次のワークに進めてはならない。

### メインフロー

- When このスキルで進めると決まったとき、Shall スキルは最初に全体計画チケットを作成して作業中に置き、以降のプロンプトで振り分けの再宣言を求められない状態にしてから、依頼の整理に入らなければならない。全体計画チケットの作業中に限り、issue・ブランチ・MR の作成と push を行える。
- When 依頼の整理に入ったとき、Shall スキルは依頼を要約（何を・種別・受け入れ条件・やらないこと）し、既存の issue（open を優先、0 件なら closed も）を検索して類似候補を提示しなければならない。
- When 類似する open な issue が見つかったとき、Shall スキルはその issue で対応するかをユーザーに確認し、承認を得るまで issue の変更・ブランチ作成・実作業を行ってはならない。
- When 既存 issue で対応することが承認され、その issue の既存の記述で依頼の内容と受け入れ条件が十分に表せているとき、Shall スキルは追記の提案や確認をせず、そのまま次に進んでよい。
- When 既存 issue の記述では依頼の内容や受け入れ条件が不足しているとき、Shall スキルは不足分を issue の末尾に追記する案を提示し、承認後に追記しなければならない（既存の記述は消さない）。
- When 類似する issue が見つからなかったとき、Shall スキルは新しい issue の案（タイトル・種別・概要・詳細・受け入れ条件・スコープ外・優先度）とブランチ名・MR タイトルを提示し、承認後に作成しなければならない。
- When issue が確定したとき、Shall スキルは issue 番号を含む feature ブランチ（`feature-<N>-<slug>` / `fix-<N>-<slug>`）と、issue に紐づく draft MR を作成し、番号と URL をユーザーに報告しなければならない。
- When ブランチと MR が作成されたとき、Shall スキルはメインエージェント自身で全体計画を作り、フェーズ列・各チケットの実行者（LLM モデル）・人間レビュー要否の方針についてユーザーと合意し、合意後に全体計画チケットを完了しなければならない。全体計画までのやり取りはサブエージェントに委ねない。
- When フェーズ列を決めるとき、Shall スキルは issue の種別（アプリ / AI アセット。両方なら両方）を判定して種別ごとのテンプレート（上記「ワークの構成」）を土台にし、調査とフィードバック計画は必ず含め、主作業のフェーズ（アプリなら設計と実装・テスト、AI アセットなら AI アセット設計と AI アセット化）は依頼の性質に応じて含めなければならない。フィードバック計画より後のフェーズは全体計画では決めず、フィードバック計画で決める。含めたフェーズでやることが無いと計画時に分かった場合は、そのフェーズを省くのではなく、計画ワークで「対象なし」としてチケットを即座に完了する。
- When 全体計画とフィードバック計画以外のワークを実施するとき、Shall スキルは各ワークをサブエージェント（全体計画で合意したモデル）に委ね、自身はワークの起動・結果報告の受け取り・ワークの切れ目の処理に徹しなければならない。
- When 1 つのワークが完了し、そのワークに人間レビュー要のチケットが 1 枚でも含まれるとき、Shall スキルは push し、MR 本文にそのワークの要約を追記し、レビュー観点（差分範囲・見てほしい点・次のワーク）を添えて MR 上でレビューを依頼し、応答を終えなければならない。
- When 1 つのワークが完了し、そのワークのチケットがすべて人間レビュー不要のとき、Shall スキルは push し、MR 本文に要約を追記し、人間レビューを省略して次のワークに進むことをユーザーに報告した上で続けてよい。
- When レビュー完了の連絡を受けたとき、Shall スキルは MR 上のレビュー結果と指摘を取得して提示し、対応要否をユーザーに確認せず、指摘のすべてを同じ種類の追加チケットとして起こしてから再度ワークに入らなければならない（完了済みチケットを未完了に戻さない）。
- When ワークが承認され次のワークに進むとき、Shall スキルは未着手のチケット（範囲・実行者・レビュー要否・DoD）をレビュー結果や新しい知見に合わせて見直してよく、変更した場合はその内容をユーザーに伝えなければならない。
- When 指摘が 0 件、または追加チケットのワークも承認されたとき、Shall スキルは機構が示す次のワークのスキルを読み込み、全体まとめまで繰り返さなければならない。
- When フィードバック計画のワークに入ったとき、Shall スキルはメインエージェント自身でユーザーと対話しながら、ここまでのワークのチケットに残された「うまくいかなかったこと」「AI アセットに反映すべき内容」・レビュー指摘・拒否と確認の記録を振り返り、候補ごとに「この MR で対応する」（既定）か「別 issue として起票する」（変更が大きくなりすぎる場合）かを決め、設計フィードバック・AI アセット設計・AI アセット化のチケットを作成・修正し、別 issue は承認を得て起票しなければならない。振り返りの機会はこの 1 回だけとし、以後のワークで見つかったものは全体まとめで別 issue にする。
- When 全体まとめのワークに入ったとき、Shall そのワークはフィードバック計画より後のワークで新たに見つかった反映すべき内容の別 issue 起票（承認を得て。この MR では対応しない）→ default ブランチとの衝突解消 → 統括レポートの作成（人間レビュー要であればここでレビュー）→ MR 本文の最終化 → 関連 issue へのコメント → 作業領域の片付け → push → draft 解除 の順に行い、マージは行わず停止しなければならない。振り返りと改善候補の起票はフィードバック計画で済んでいるため行わない。
- When 全体まとめの中で作業領域を片付けて push し draft を解除するとき、Shall チケットが無くなった状態でもこれらの操作が機構に拒否されず、振り分けの再宣言も求められてはならない。

### 承認ポイント

- When どの issue で対応するか（既存 / 新規 / 別候補 / 分割 / 対応なし）を決めるとき、Shall スキルは選択肢を提示し、明示的な承認を得なければならない。
- When 新規 issue の本文、または既存 issue への追記が必要なとき、Shall スキルはブランチ名・MR タイトルも同時に提示し、明示的な承認を得なければならない。既存 issue の記述で足りるときはこの承認は不要とし、ブランチ名・MR タイトルは issue の選択の承認と同時に提示する。
- When 全体計画でフェーズ列・各チケットの実行者・人間レビュー要否を決めるとき、Shall スキルはユーザーと合意しなければならない。
- When フィードバック計画で改善候補ごとの対応先（この MR / 別 issue）と後続フェーズのチケットを決めるとき、Shall スキルはユーザーと合意しなければならない。
- When 人間レビュー要のチケットを含むワークの完了後にレビューを依頼したとき、Shall スキルは応答を終えて人間のレビューを待ち、チャット上の質問でセッションを塞いではならない。
- When default ブランチとの衝突を解消するとき、Shall スキルは衝突ファイルと解消方針を提示して承認を得てから `git merge` で取り込み、`git rebase` や片側丸ごと採用を使ってはならない。
- When 関連 issue にコメントを投稿するとき、Shall スキルは投稿先の issue 番号と本文そのものを提示して承認を得なければならない。
- When 全体まとめの中で人間の承認が必要な操作（衝突解消・issue へのコメント投稿）があるとき、Shall 承認の取得と操作はサブエージェントではなくメインエージェントが行わなければならない。

### 他のスキル・機構との整合

- When issue を検索・作成・追記するとき、Shall スキルは自前で `glab issue` / `gh issue` を組み立てず issue 操作の task スキルの手順に従わなければならない。
- When ブランチと MR を作成・更新するとき、Shall スキルはブランチ・MR 操作の task スキルの手順に従わなければならない。
- When コミット・push・チケットの状態変更・レビュー依頼と完了・マージ前作業を行うとき、Shall スキルは機構の提供コマンド（とそれを使う task スキル）経由でのみ行い、`git` のコミット・push の直接実行、進行状態の直接編集、draft 解除の直接実行を行ってはならない。
- When 全体計画チケット以外のチケットが作業中のとき、Shall not スキルは `glab` / `gh` コマンドや push を実行してはならない（リモートへの操作はワークの切れ目と全体まとめで行う）。
- When 次に読み込むワークのスキルを選ぶとき、Shall スキルは目視で判断せず機構の示す結果に従い、対応するスキルが無ければ不整合として報告して停止しなければならない。
- When ワークから並列に進めたいチケット群や新しいコンテキストで実施したいチケット（実行者がワークのモデルと異なるものを含む）の要求を受けたとき、Shall スキルがチケット単位のサブエージェントを起動しなければならない。
- When ワークの実施中であるとき、Shall not スキルはチケット運用の手順（着手・完了・作業ログ・DoD）を再掲せず、`10-work-ticket-driven` の手順を参照しなければならない。

### アルタナティブフロー（代替経路）

- If 現在のブランチに open な MR があり、作業領域にチケット（未着手 / 作業中 / 完了）がある場合、Then スキルは issue の照合からやり直さず、現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み）を機構から得て再開しなければならない。レビュー待ちのときはレビュー完了の連絡がない限り応答を終える。
- If 類似候補が closed な issue のみである場合、Then スキルは過去の類似事例（issue 番号・当時の結論）を示したうえで、新規に作るか対応なしとするかをユーザーに確認しなければならない。対応なしが選ばれたら全体計画チケットを取り消して停止する。
- If 依頼が複数の独立した問題を含む場合、Then スキルは issue を分割する案を提示し、ユーザーが選んだ 1 つから着手しなければならない（1 issue = 1 MR）。
- If ユーザーが issue 番号や URL を指定した場合、Then スキルは検索を省略し「既存 issue で対応」として扱ってよい。
- If 依頼が `00-workflow-quick-request` の振り返り、またはフィードバック計画の改善候補から「issue を作って進める」と合意して切り替えて来た場合、Then スキルは引き継がれた要約・受け入れ条件・種別・フェーズ列をそのまま用い、依頼の要約に関する質問を省略してよい。ただし未コミットの変更の確認と承認は省略しない。
- If issue を起票しただけで着手の指示が無い場合、Then スキルはブランチ作成に進まず、着手はユーザーの明示的な指示を待たなければならない。
- If 小さな依頼でレビューの往復が過剰な場合、Then スキルはチケットの人間レビュー要否を「不要」に倒し、やることの無いフェーズは計画ワークで即座に完了することで対処し、必須フェーズの省略やワークの種類の統合で対処してはならない。
- If `glab` / `gh` CLI が使えない環境の場合、Then スキルは機構の外部委任モード（MCP ツールでリモート操作を代行）を使い、WebFetch / curl へ落としてはならない。
- If レビュアーがチャットでレビュー判断を伝えた場合、Then スキルはその判断を MR の通常コメントとして記録してからレビュー完了の手続きに進まなければならない。

### 例外フロー（エラーケース）

- If `glab`（GitHub では `gh`）が未インストール・未認証である場合、Then スキルは導入・認証を案内し、作業を開始してはならない。
- If `origin` が GitLab でも GitHub でもない場合、Then スキルは対象外として報告して停止しなければならない。
- If 作業ツリーに未コミットの変更がある場合、Then スキルはブランチ作成前に変更内容を示し、扱い（コミット / stash / 破棄 / 中断）をユーザーに確認しなければならない（自分で判断しない）。
- If MR 作成が「差分なし」で失敗した場合、Then スキルは空コミットを作成して再試行しなければならない。
- If issue の作成・追記や MR の作成に失敗した場合、Then スキルは失敗したコマンドと出力を報告し、別の手段で代替してはならない。
- If レビュー依頼が前提未充足（未コミット / 未 push / MR なし / ワークの切れ目でない / 既に依頼済み）で拒否された場合、Then スキルは未充足を解消して再実行し、切れ目でなければ次のチケットに着手しなければならない。
- If レビュー完了の手続きが「変更要求あり」または「未返信のスレッドあり」で止まった場合、Then スキルは同じ種類の追加チケットで対応し、スレッドに返信してから再実行しなければならない。進行状態を直して通そうとしない。
- If マージ前作業の前提（未着手・作業中のチケットが無い・最後のワークが承認済み・未コミット無し・衝突無し・通知先あり）が満たせない場合、Then スキルは機構が返す未充足を報告し、該当する手順（ワーク / レビュー / 衝突解消 / 通知先の指定）へ戻らなければならない。
- If 承認で却下された場合、Then スキルはその段階に留まり、先の段階へ進んではならない。

## 前提条件

- 対象プロジェクトが GitLab または GitHub 上の Git リポジトリで、`origin` がそれを指していること
- `glab`（GitHub では `gh`）CLI がインストール・認証済みで、issue と MR の作成権限があること
- チケット駆動の仕組み（`10-work-*` スキル、提供コマンド、宣言範囲の強制、テンプレート）が導入済みであること
- `00-workflow-quick-request` と対になる振り分けとして、`CLAUDE.md`「作業の振り分け」から呼ばれること

---

## 制約条件

- **技術的制約**: GitLab（`glab` CLI）を基準に記述し、GitHub では MR → PR、`glab` → `gh` に読み替える。1 セッションは 1 つの MR だけを扱う。サブエージェントはユーザーと対話できないため、人間との合意・承認が要る処理はメインエージェントが行う
- **ビジネス的制約**: MR のマージ・issue の内容・レビュー完了の判断・チケットのレビュー要否の方針は人間が決める。AI は draft 解除で止まる
- **外部的制約**: 機構の統制に従い、スキル側に迂回経路を書かない。機構側にリモート操作の許可を追加しない

|------|------|
| パフォーマンス | issue 検索は件数を絞り、候補提示は上位 10 件程度に絞る |
