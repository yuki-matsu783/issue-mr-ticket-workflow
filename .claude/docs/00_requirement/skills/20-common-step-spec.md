# 20-common-step-spec スキル

## 概要

仕様書の作成・更新の共通ステップの要件を定義する。要件定義書と対になる仕様書の置き場所と命名、種別ごとの節構成、要件との対応の付け方、内部構造の書き方、エラー識別子の採番、正史と経緯の分離を標準化する。置き場は AI アセット（`.claude/docs/`）とアプリ（アプリルートの `docs/`）の双方を扱う。設計・AI アセット設計の実施タスクから使われる。

- **背景**: 要件定義書が外部から観察できる振る舞いだけを持つ方針のため、実装が従うべき内部構造（提供コマンドの名前と引数・判定の順序・状態やログのスキーマ・エラーコード・ファイルの実パス）を書く場所が別に要る。ここがぶれると、実装が要件から直接内部を推測して書き手ごとに違う実装になる。
- **目的**: 実装・テストが仕様書だけを見れば作れる粒度の内部構造が、要件と対応づけて 1 か所に書かれ、要件 : 仕様 : 実装が 1:1:1 で辿れる状態を作る。
- **スコープ**:
  - 含む: 配置と命名、frontmatter、要件の受け入れ基準との対応の付け方、内部構造の記述（コマンド・判定順・スキーマ・エラーコード・パス・テンプレートの構成）、更新の仕方（正史の書き換え）
  - 含まない: 仕様の中身の合意（呼び出し元のタスクと人間レビュー）、要件定義書の書き方（`20-common-step-requirement`）、実装そのもの（AI アセット実装・テストのタスク）

---

## ユーザーストーリー

**[As a]** 仕様に沿って実装・テストする開発者（と実装タスクの AI）として、

**[I want]** 仕様書だけを読めば内部構造が一意に決まり、それがどの要件を満たすためかが対応で辿れてほしい。

**[So that]** 実装のたびに要件から内部を推測せずに済み、要件が変わったとき直すべき仕様が特定できるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 仕様書を作るとき、Shall スキルは対応する要件定義書と同名のファイルを、同じ設計文書ルートの `10_spec/` 配下の同じ相対パスに置かなければならない（要件 1 つに仕様 1 つ）。設計文書ルートは、対象が AI アセットなら `.claude/docs/`、対象がアプリなら[アプリルート](../../90_glossary/ドキュメント体系用語.md#アプリルート)の `docs/` である。
- When 節構成を決めるとき、Shall 対象の種別（スキル / エージェント / フック / アプリ）ごとに定められた節構成に従わなければならない。アプリの節構成は、アプリ種別に依らない 9 節と、画面や出力を持つアプリだけが置く任意節 1 つで構成されなければならない。
- When 書き始めるとき、Shall frontmatter（type / title / description / tags / keywords）を付け、どの要件定義書と対か・要件のどの受け入れ基準をどの節が実現するかが読み取れる構成にしなければならない。
- When 内部構造を書くとき、Shall 実装・テストが追加の推測なしに作れる粒度（提供コマンドの名前と引数・入出力・判定の順序と条件・状態やログのスキーマ・エラーコードと文言・ファイルとテンプレートの配置）で書かなければならない。
- When 同じ内部構造を複数のスキル・フックが使うとき、Shall 定義を 1 つの仕様書に置き、他からは参照しなければならない（重複定義しない）。
- When 既存の仕様書を更新するとき、Shall 正史を直接書き換え、本文に変更履歴を残してはならない（経緯は DDR と git 履歴が持つ）。

### 代替フロー

- If 要件定義書に書かれた振る舞いに対応する仕様がまだ決められない場合、Then スキルは未決の論点として明示し（TBD の理由と決めるために要る情報を書く）、黙って省略してはならない。
- If 仕様を書く過程で要件側の記述の誤り・不足に気づいた場合、Then スキルは仕様側で辻褄を合わせず、要件定義書の修正を呼び出し元に返さなければならない。

### 例外フロー

- If 対応する要件定義書が存在しない場合、Then スキルは仕様書を先に作らず、要件が先であることを呼び出し元に返さなければならない。
- If 仕様がまだ人間と合意されていない決定を含む場合、Then スキルは合意が先であることを呼び出し元に返さなければならない。

### 規約: エラー識別子の台帳

- When AI アセットのエラー識別子の接頭辞を新たに使うとき、Shall 機構の採番台帳に接頭辞と範囲を追加してから使わなければならない。
- When アプリの不備・エラーの識別子を決めるとき、Shall そのアプリの仕様書自身が台帳を兼ね、接頭辞は 2 文字とし、使う前に既存のアプリの仕様書を検索して衝突しないことを確かめなければならない。
- Shall not アプリの識別子の接頭辞を機構の採番台帳に登録しない（台帳は AI アセットの接頭辞だけを集約する）。

### 他のスキルとの整合

- When 要件定義書に内部構造が書かれているのを見つけたとき、Shall スキルはその記述を仕様書へ移し、要件側は外部から観察できる表現に直す提案を呼び出し元に返さなければならない。
- Shall not 「関連するドキュメント」「レビュー記録」の節を置かない。

## 前提条件

- 対応する要件定義書が存在し、書く仕様の元になる決定が呼び出し元のタスクで合意済みであること

---

## 制約条件

- **技術的制約**: Markdown + frontmatter。1 ファイル 1 対象（要件と同名）
- **ビジネス的制約**: 仕様書は人間レビューの対象であり、実装タスクの入力。読み手は人間と AI の両方
- **外部的制約**: 外部から観察できる振る舞いの正は要件定義書。仕様はそれを実現する内部の正であり、要件と矛盾してはならない

## 非機能要件

| 項目 | 説明 |
|------|------|
| 追跡性 | 要件の受け入れ基準 → 仕様の節 → 実装が 1:1:1 で辿れる |
| 完全性 | 実装・テストが仕様書以外の推測を必要としない |
| 一貫性 | 共有される内部構造の定義が 1 か所にだけある |
