この計画で何をするか

チケット 0040〜0052 の作業ログとレポートから改善候補 19 件を洗い出し、観点・類型・反映先の 2 軸で分類して対応先を決めた。issue #15 の 2026-09-03 追記分の受け入れ条件 6 件はすべて充足している。後続フェーズは全体まとめ 1 枚だけになる。

決めたこと

  • 新規に別 issue を 3 件起票する（cmdpos.sh の既知の制約 / HTML ビューの複製経路 / ticket.sh のフラグとテスト分類 3 件）
  • 既存 issue に 8 件を合流させる（#30 / #32 / #23 / #34 / #10）。本 PR では追記しない
  • 2 件は #15 に残す（scope.sh / hook-common.sh の移行判断、uv の導入）
  • 2 件は対応しない（実測値の保守の仕組み、cmdpos_parse の速度）
  • 後続フェーズは設計反映・追加設計・追加実装のいずれも不要。全体まとめ 0053 を 1 枚起こす

「対応しない」の理由

  • #18: 本 PR で仕様書 §1 に比率の形で実測の目安を置いたことで当面の受け皿はできた。比率は環境で変わらないので古びにくく、更新の契機を機構化するほどの頻度が無い。次に実測が要る場面が来たときに #15 の中で改めて扱う
  • #19: ホットパスの上限（DDR i0009-22）に収まっており実害が無い。最適化はボトルネックを特定してから行う原則に反する
