# 0037 AI アセット実装結果 — ヒアドキュメント本文を実行位置として数えない

## サマリ

0028 で踏んだ過剰拒否（登録から 3 回目の Bash 呼び出しが止まった）を直した。**原因は 0036 で入れた判定軸そのものではなく、`cmdpos` の `_` が 3 つの別物を指していたこと**だった。

`cmdpos` は仕様どおり「クォート・コメント・ヒアドキュメント本文」をすべてプレースホルダ `_` に潰す。0036 の `_bc_exe_unknown` は「実行体がすべて `_` = 潰れたクォート由来 = 難読化」と読むので、**実行位置ですらない本文（bash は決して実行しない）を難読化と誤読していた**。呼び手には区別する手段が無かった。

`CP_DATA[i]`（1 = その段はデータだけで実行位置ではない）を足し、`block-chmod` がその段を実行体の判定から外す。**0036 で得た「未知の表記も同じ経路で捕まる」性質はそのまま残る**。追加は純粋に足すだけで、`CP_EXE` / `CP_ARGS` など既存の出力から見える値は 1 つも変わらない。

実装中に**別のバグを 1 件見つけて直した**。`# コメント` が**行頭のときだけコメントとして畳まれていなかった**（語の切れ目の一覧に改行が無い）。そのため `ls\n# do not use chmod\necho b` は実行体 `#` の段になり、コメントの中の語が引数として残っていた。

全件テストは **2 ロケールで 15 本 / 71 件・FAIL 0**、変異テスト **6 か所**すべてで落ちることを確かめた。

## レビューしてほしい観点

**◆特に見てほしい（判断に困っている）**

- **r1（△注意）`CP_DATA` の意味の切り方**。「段のトークンがすべてプレースホルダなら data=1」という定義にした。`ls # コメント` は実行位置 `ls` を持つので data=0、コメントだけの行とヒアドキュメント本文は data=1。**この切り方で見落とす形が無いか**を見てほしい
- **r2（△注意）入力から生のプレースホルダを落とす補強を残すか**。現実に踏む経路は思いつかなかった（変異 M16 は最初 0 件で、テストを直して 2 件になった）。「出力に現れるプレースホルダは正規化が置いたものだけ」という性質を後続のフック 10 本が前提にしてよい、という理由で残した

**◇承認が欲しい（方針は決めた）**

- **r3**: `CP_DATA` を新しい配列にしたこと（`CP_OPAQUE` に相乗りしない。あちらは「中身が実行され得る」で意味が正反対）
- **r4**: 行頭の `#` をコメントとして畳むようにしたこと。仕様 §7 に語の切れ目の定義が無く、実装が改行を含めていなかった
- **r5**: 拒否理由を 2 通りに分けたこと（実行体を特定できて拒否 / 特定できないために倒した）

**・細かいレビューは不要（ほぼ確実）**

- プレースホルダを `\x03` にしたこと（`\x01` は `_CP_DUP`、`\x02` は `_CP_AMPRED` が使用中）
- `test_cmdpos.sh` の `dump` に `data=%s` を足したこと

## 確かめられなかったこと（この結果が言っていないこと）

- **`_` を作る経路を網羅していない**。塞いだのはヒアドキュメント本文とコメントの 2 経路。ほかに「データなのに実行位置に見える」形が無いかは調べていない
- **`CP_DATA` の呼び手は `block-chmod` 1 本だけ**。残り 10 本（0029 / 0030）でどう使うかは決めていない
- **`shellcheck` は 5 巡連続で未導入**。静的検査は実施できていない
- **PowerShell 側は測っていない**。ヒアストリング（`@'…'@`）は `_cp_ps_preprocess_to_reply` が別経路で潰しており、そちらに `CP_DATA` は付かない
- **bash 4.2 以下での実行は試していない**（0036 からの持ち越し）
- **過剰拒否が「これで無くなった」とは言えない**。0028 で踏んだ 1 経路と、0028 の切り分けで作った対照の範囲でしか確かめていない

## 実施した内容と結果

### 1. `CP_DATA[i]` で `_` の多義性を解いた ✕問題

`cmdpos` の `_` は 3 つの別物を指していた。

| `_` の出どころ | 実行位置か | 例 |
|---|---|---|
| 潰れたクォート | **はい**（bash はその語を実行する） | `"chmod" +x a` → `_ +x a` |
| コメント | いいえ | `# do not use chmod` |
| ヒアドキュメント本文 | いいえ | `cat <<PY` の後ろの行 |

呼び手はどちらか一方に倒すしかなく、0036 は「実行位置」に倒したので、データを難読化と誤読した。

`CP_DATA[i]` を足した。正規化はデータだけの内容を内部プレースホルダ `\x03` で出し、段を組み立てる時点で `_` に戻しつつ「全トークンがプレースホルダなら `CP_DATA=1`」を記録する。**呼び手から見える値（`CP_EXE` / `CP_ARGS` …）は 1 つも変わらない**。

`block-chmod` は制御方式 5 のループ先頭で `CP_DATA=1` の段を飛ばす。

### 2. 行頭の `#` がコメントとして畳まれていなかった ✕問題

`_cp_normalize_to_reply` の `'#'` の分岐は直前の文字が語の切れ目かを見るが、その一覧に改行（`$_CP_NL`）が入っていなかった。

```
（直す前）
ls\n# do not use chmod\necho b   →  [0]exe=ls [1]exe=#  [2]exe=echo
                                              ^^^^^^^ コメントの中の語が引数として残る
（直した後）
ls\n# do not use chmod\necho b   →  [0]exe=ls [1]exe=_  [2]exe=echo   （seg1 は data=1）
```

bash はコメント行を丸ごと無視するので、データとして畳むのが正しい。`block-chmod` では実害が出ていなかった（実行体 `#` は禁止語に一致しない）が、`workflow-guard` など「引数を見る」フックはコメントの中の語を引数として拾っていた。

### 3. 拒否理由を 2 通りに分けた △注意

0028 で過剰拒否を踏んだとき、出た文面は「実行権限の変更は不要で、スクリプトは 'bash <パス>' で実行する」だけで、**文書に `chmod` と書いただけの読み手には何の案内にもならなかった**。

実行体を特定できないために倒したときは、何が妨げたかと、実行するつもりが無い場合の道を書くようにした（実測）。

```
$ bash -c "chmod --version"
WF501: コマンドの中に禁止コマンド 'chmod' の語があり、実行体を特定できない箇所（変数展開・
コード文字列など）があるため拒否側に倒した。実際に 'chmod' を実行するつもりなら、実行権限の
変更は不要で、スクリプトは 'bash <パス>' で実行する。実行するつもりが無い（文書・コメント・
検索語として書いただけ）なら、その語を含む部分を Write / Edit で書くか、シェルに渡さない形に
変える。迂回（環境変数での無効化・語の分割・言い換え）はしないこと
```

### 4. プレースホルダが既存の内部プレースホルダと衝突した ✕問題

`\x02` を選んだが、`cmdpos` は既に `_CP_AMPRED=$'\x02'`（`&>` の保護）で使っていた。入力から生のプレースホルダを落とす補強を入れた瞬間、`&>` のリダイレクトが壊れた。

```
FAIL HK-T05: 出力に 'redir=[all.log]' が無い
  : count=1 degraded=0\nseg0: exe=cmd sub=_> args=[_> all.log] redir=[] ...
```

**既存テストの 1 件が拾った**ので `\x03` に変えた。`_CP_DUP=\x01` / `_CP_AMPRED=\x02` / `_CP_DATA_PH=\x03` が別々の行にあり、割り当て表が 1 か所にまとまっていないのが原因（0032 へ送る）。

### 5. 補強のテストに最初は検出力が無かった △注意

`\x03 +x a` のように他のトークンを伴う形は、補強が無くても `data=0` になる（段の全トークンがプレースホルダでないため）。変異 M16 が 0 件だった。

**段がプレースホルダ 1 個だけになる形**（`ls\n\x03\necho b` と `\x03` 単独）に直して 2 件になった。0036 の申し送り「変異が 0 件だったら『その行は要らない』と即断せず、重ならない条件を探す」がそのまま効いた。

## 設計への反映（後続へ）

1. **0029 / 0030 へ**: 10 本を書くとき、`CP_DATA[i]` が 1 の段は実行位置として扱わない（`block-chmod` と同じ）。**過剰拒否が塞がったので、拒否側 4 本を足しても作業が止まる恐れは下がった**
2. **0031 へ**: ① ② の段階登録は計画どおり。手順から「新しいセッションを開く」を外す（0028 の実測）
3. **0032 へ**: 仕様 §7 に `CP_DATA[i]` を足す／正規化の記述を「3 つを `_` に潰すが、データだけの段は `CP_DATA` で区別できる」に直す／語の切れ目に改行を含めることを明示／**内部プレースホルダの割り当て表（`\x01` `\x02` `\x03`）を仕様に置く**

## 想定と異なった点

| 見込み | 実際 | どう扱ったか |
|---|---|---|
| 0028 の過剰拒否は判定軸そのものの問題 | `_` が 3 つの別物を指していたことが原因で、判定軸は戻さずに直せた | `CP_DATA` を足して呼び手が区別できるようにした |
| コメントは既にコメントとして畳まれている | **行頭のときだけ畳まれていなかった**（語の切れ目に改行が無い） | 一覧に改行を足した。`block-chmod` では実害なし、`workflow-guard` では実害あり |
| プレースホルダに `\x02` を使える | `_CP_AMPRED` が既に使用中で、`&>` のリダイレクトが壊れた | 既存テスト 1 件が拾った。`\x03` に変え、割り当て表を 0032 へ送った |
| 補強のテストは検出力がある | 変異 M16 が 0 件。他のトークンを伴う形では補強の有無を区別できない | 段がプレースホルダ 1 個だけになる形に直して 2 件になった |
| 変異テストは前景で一括に回せる | 5 件 ×（テスト 2 回 + 基準確認 2 回）が 10 分の上限を超えた | 件数 × 所要時間を先に見積もり、1 回の呼び出しを 2〜3 件に割る |

## 残課題

- **`_` を作る経路の網羅**は確かめていない（塞いだのは 2 経路）
- **PowerShell のヒアストリング**には `CP_DATA` が付かない（別経路で潰している）
- **内部プレースホルダの割り当て表**が 1 か所に無い（0032 で仕様に置く）
- **`_bc_seg_unknown` はバッククォートを見ていない**（0036 から持ち越し）
- **`shellcheck` の未導入**（環境の制約。5 巡連続）
- **`check-html.sh` は md と HTML の内容一致を検査しない**（16 回連続の申し送り）
- **仕様からの逸脱**が 0027 / 0033 / 0035 / 0036 からの持ち越し 14 件 + 今回 2 件（`CP_DATA` の追加・語の切れ目に改行）
