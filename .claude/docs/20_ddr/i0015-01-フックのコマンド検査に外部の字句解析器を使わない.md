# i0015-01. フックのコマンド検査に外部の字句解析器（Python の `shlex`）を使わない

## 背景

`.claude/hooks/lib/cmdpos.sh` は、コマンド文字列から「実行位置に何があるか」を取り出す純 bash の字句解析器（429 行）で、ホットパス 5 本（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）が共有している。クォート・ヒアドキュメント・`$( )`・リダイレクトを状態機械で処理しており、機構の中で最も複雑な部分にあたる。

`i0009-22` は「ホットパスのフックが起動してよい外部プロセスは `jq` だけ」「コマンド分割は純 bash で行う」と定めた。issue #15 はこの自縛が複雑さの原因になっていると指摘し、`shlex` で一部を置き換えられないかを検討対象に挙げた（受け入れ条件「フック層（`cmdpos.sh` / `scope.sh` / `hook-common.sh`）を移行するか据え置くかの判断が記録されている」）。

置き場の候補は 3 つあった。(a) 本番の `cmdpos.sh` を `shlex` に置き換える、(b) `shlex` をテストの照合役（差分テスト）として常設する、(c) 採用しない。

## 決定

- **フックのコマンド検査に外部の字句解析器を使わない。`cmdpos.sh` は純 bash のまま据え置く**（上の (c)）
- **`i0009-22` は上書きせず維持する**。「ホットパスが起動してよい外部プロセスは `jq` だけ」はそのまま
- この判断は `shlex` に限らず、**外部プロセスとして起動する字句解析器一般**に及ぶ。理由の 2 と 3 は言語を問わないため
- 判断の材料になった実測は、桁と比率の形でフック共通仕様 §1 に残す（絶対値は環境で変わるので基準にしない）

## 理由

3 つあり、**どれか 1 つでも単独で却下理由になる**。

### 1. 判定を誤る（見落とし 6 件・誤検知 1 件）

`test_cmdpos.sh` のテスト入力を土台にしたコーパス 50 件で、現行実装と `shlex` 版の試作を突き合わせた（一致 27 件 / 差分 23 件）。差分のうち 7 件が判定を誤る方向だった。

| 種別 | 件数 | 例 |
|---|---|---|
| 見落とし（実在するコマンドが見えない） | 6 | `echo "$(git commit -m x)"` / ``echo `git commit` `` / `echo $((1<<2)); git commit` / `foo#bar git status` / `cat <<EOF⏎EOF⏎git push` |
| 誤検知（実行されない語をコマンドとみなす） | 1 | `cat <<EOF⏎foo; git push⏎EOF` |

原因は `shlex` に次の 4 機能が無いことに帰着する。

- **ヒアドキュメントの追跡が無い**。本文を普通の語として出すため、本文中の `;` で段が増え（誤検知）、区切り語の後に続く本物のコマンドを吸い込む（見落とし）。同じ欠落が両方向の誤りを生む
- **コマンド置換を展開しない**。`$( )` は 1 語のまま、バッククォートはただの文字になる
- **算術展開を読み飛ばさない**。`punctuation_chars=True` は `echo $((1<<2)); ls` を `['echo', '$', '((', '1', '<<', '2', '));', 'ls']` に割り、`));` が 1 語になるため**その中の `;` が区切りとして働かない**。後続の段が丸ごと消える
- **コメント判定が語頭を見ない**。`commenters` は文字単位なので `foo#bar git status` を `['foo']` に切り詰める。`cmdpos.sh` は直前の文字が語の切れ目かを見ている

見落としは**検査をすり抜ける方向**の誤りで、拒否側 5 本のフックが素通しすることになる。同等の正しさを保つには上の 4 機能を Python 側で書き直すことになり、`shlex` を使う利点が消える。

### 2. ホットパスが遅くなる（1 本 +20.7 ms、5 本で +103 ms）

各 50 回の中央値（Linux コンテナ）。

| 対象 | 中央値 |
|---|---:|
| python 内の `shlex` 解析（プロセス起動なし） | 0.048 ms |
| bash 内の `cmdpos_parse`（プロセス起動なし） | 2.40 ms |
| `jq -n` 起動 | 3.85 ms |
| bash 起動 + `cmdpos.sh` 読込 + 解析（ホットパス 1 本の実態） | 6.62 ms |
| `python3 -S -c pass`（site なしの空起動） | 10.89 ms |
| `python3 -S -c 'import shlex'` | 21.45 ms |
| `python3` 起動 + 解析 | 27.33 ms |

**解析そのものは `shlex` が 50 倍速い**（0.048 ms 対 2.40 ms）。しかし Python の起動が解析の 570 倍かかる。ホットパスのフックは毎ツール呼び出しで起動し直す使い捨てプロセスなので、速い解析は活きない。

`i0009-22` が認めている外部プロセスは `jq`（3.85 ms）で、Python の追加はその **7.1 倍**を 1 本ごとに使う。`import shlex` だけで 10.6 ms 増える（`re` を引き込むため）ので、起動オプションで削っても届かない。

### 3. Python が全実行環境で保証されない（fail-open を塞げない）

`i0001-14` は判定材料を「想定する全実行環境で確実にアクセスできるもの」に限っている。Python は Git Bash に同梱されない。同 DDR は「全環境で確実にアクセスできる対象が増えた場合はその対象を使ってよい」という逃げ道を用意しているが、そのためには `uv` 等の配布と SessionStart でのブートストラップが要り、その SessionStart 自身は Python 不在でも動く必要がある（入れ子の依存）。

より重いのは失敗時の振る舞いである。`i0009-11` のとおり**打ち切り（timeout）は fail-open で塞げない**。Python 不在の環境ではコマンド検査が丸ごと落ちる。bash 版のフォールバックを残すなら、**同じ判定を 2 言語で二重に実装**することになり、両者の食い違いが新しいバグの種になる。

## 却下した案

### (a) 本番の `cmdpos.sh` を `shlex` に置き換える

置き換わるのは 429 行のうち正規化部（`_cp_normalize_to_reply` とその補助、おおよそ 120 行）に留まる。出力 10 項目のうち `shlex` が供給するのは `CP_ARGS`（全面）と `CP_EXE`・`CP_REDIRECTS`（部分）の 3 項目だけで、残る 7 項目（`CP_SUBCMD` / `CP_WRITE_TARGETS` / `CP_OPAQUE` / `CP_PROVIDED` / `CP_DATA` / `CP_GITLIKE` / `CP_DEGRADED`）は外側に自前で書く。

得られる縮小が 120 行なのに対し、上の理由 1・2・3 がすべて乗る。割に合わない。

### (b) `shlex` をテストの照合役（差分テスト）として常設する

起動コスト（理由 2）はテストなら問題にならない。実際 `shlex` は現行実装の弱点を 6 件で正しく解いており、とくに `git 'commit'`（クォートで割った語）は `test_cmdpos.sh` が「判定できない既知の制約」とコメント付きで固定している入力である。この案には筋があった。

却下したのは次の 3 点による。

- **照合役が信頼できない**。比較の相手は `shlex` 単体ではなく「`shlex` + 自前の再実装」であり、その再実装が理由 1 の 4 つの盲点を持つ。盲点のあるものを正解とみなす仕組みは、誤った警告と誤った安心の両方を生む
- **雑音比が高い**。差分 23 件のうち 10 件は判定に影響しない表現差だった。継続運用するには比較する項目を絞る設計が要り、その設計自体が第 2 の仕様になる
- **費用が効果に見合わない**。第 2 のパーサを保守する費用に対し、今回見つかったのは既知の制約 1 件だけで、新規の不具合はゼロだった。`i0006-04`（テストは素の bash に共通ヘルパを足す形にし bats は導入しない）が避けた「テストのための依存」を、より重い形で持ち込むことになる

なお、今回の突き合わせで分かった「現行実装が `git 'commit'` を判定できない」は実在の制約であり、`shlex` に頼らずに直せる見込みがある。それは本 DDR の対象外で、別の issue として扱う。

### (c) `i0009-22` を上書きして Python を認める

上書きの必要が無い。理由 2 と 3 は `i0009-22` を緩めても消えない。
