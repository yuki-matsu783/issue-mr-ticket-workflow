# workflow-issue-mr-driven スキル

## 概要

ユーザーの依頼を GitLab の issue と draft MR に紐づけてから実作業に入り、人間レビューが必要なワークの切れ目で MR 上のレビューを挟んで進める、開発作業向けの振り分けスキルの要件を定義する。このスキルは順序と承認ポイントを司るオーケストレータであり、issue / ブランチの操作は task スキルに、各ワークの実施は work スキルに委ねる。機構全体の要件は `自己改善ワークフロー機構.md` が持つ。本書は GitLab の用語で書き、GitHub では MR → PR、`glab` → `gh` と読み替える。

- **背景**: チケット駆動の実作業だけでは「その作業がどの issue に対するもので、どの MR に載るのか」「どこで人間が確認するのか」が決まらない。作業の起点を issue に固定し、issue の確定・レビューが必要なワークの切れ目・マージ前作業に人間の判断を挟みたい。
- **目的**: 「依頼 → 既存 issue の照合 → 承認 → issue の確定 → feature ブランチと draft MR → 全体計画（フェーズ列・実行者・レビュー要否の合意）→ ワークの繰り返し（レビュー要のチケットを含むワークの後は人間レビュー）→ 全体まとめ → マージ前作業 → draft 解除 → 停止」の順序を固定し、すべての作業が 1 issue = 1 ブランチ = 1 MR に紐づき、レビューが必要な箇所を飛ばして進めない状態を実現する。
- **スコープ**:
  - 含む: スキル本体（SKILL.md と参照資料）、issue 追記・issue 通知のテンプレート、類似 issue の判定基準、承認ポイントの定義、ワークの繰り返しの制御（次のワークの選択・push・MR 本文更新・レビュー依頼と完了・指摘への追加チケット・未着手チケットの見直し）、完了処理の順序、再開
  - 含まない: MR のマージ（人間が行う）、issue / ブランチ / MR の具体的な操作手順（`task-gh-issue` / `task-gh-feature`）、各ワークの内容（`work-*`）、宣言範囲の強制やワーク境界の判定の仕組み（仕様書）、レビューの自動化

---

## ユーザーストーリー

**[As a]** Claude Code で開発する開発者として、

**[I want]** 依頼した作業を、既存 issue との照合と自分の承認を経て issue と MR に紐づけ、レビューが必要なワークの切れ目で MR 上のレビューを挟みながら進めてほしい。

**[So that]** 重複した対応や issue に紐づかない変更を防ぎ、AI の作業を必要な箇所で確認でき、依頼・合意・作業・成果の経緯を GitLab / GitHub 上で追えるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When ユーザーから開発作業の依頼を受けたとき、Shall スキルは実作業を始める前に依頼を要約（何を・種別・受け入れ条件・やらないこと）し、既存の issue（open を優先、0 件なら closed も）を検索して類似候補を提示しなければならない。
- When 類似する issue が見つかったとき、Shall スキルはその issue で対応するかをユーザーに確認し、承認を得るまで issue の変更・ブランチ作成・実作業を行ってはならない。
- When 既存 issue で対応することが承認され、その issue の既存の記述で依頼の内容と受け入れ条件が十分に表せているとき、Shall スキルは追記の提案や確認をせず、そのまま次に進んでよい。
- When 既存 issue の記述では依頼の内容や受け入れ条件が不足しているとき、Shall スキルは不足分を issue の末尾に追記する案を提示し、承認後に追記しなければならない（既存の記述は消さない）。
- When 類似する issue が見つからなかったとき、Shall スキルは新しい issue の案（タイトル・種別・概要・詳細・受け入れ条件・スコープ外・優先度）とブランチ名・MR タイトルを提示し、承認後に作成しなければならない。
- When issue が確定したとき、Shall スキルは issue 番号を含む feature ブランチ（`feature-<N>-<slug>` / `fix-<N>-<slug>`）と、issue に紐づく draft MR を作成し、番号と URL をユーザーに報告しなければならない。
- When ブランチと MR が作成されたとき、Shall スキルは issue 番号・MR の URL・受け入れ条件を引き継いで全体計画のワークに進み、フェーズ列・各チケットの実行者（LLM モデル）・人間レビュー要否の方針についてユーザーと合意しなければならない。
- When 1 つのワークが完了し、そのワークに人間レビュー要のチケットが 1 枚でも含まれるとき、Shall スキルは push し、MR 本文にそのワークの要約を追記し、レビュー観点（差分範囲・見てほしい点・次のワーク）を添えて MR 上でレビューを依頼し、応答を終えなければならない。
- When 1 つのワークが完了し、そのワークのチケットがすべて人間レビュー不要のとき、Shall スキルは push し、MR 本文に要約を追記し、人間レビューを省略して次のワークに進むことをユーザーに報告した上で続けてよい。
- When レビュー完了の連絡を受けたとき、Shall スキルは MR 上のレビュー結果と指摘を取得して提示し、対応要否をユーザーに確認し、対応が必要なものは同じ種類の追加チケットとして起こしてから再度ワークに入らなければならない（完了済みチケットを未完了に戻さない）。
- When ワークが承認され次のワークに進むとき、Shall スキルは未着手のチケット（範囲・実行者・レビュー要否・DoD）をレビュー結果や新しい知見に合わせて見直してよく、変更した場合はその内容をユーザーに伝えなければならない。
- When 指摘が 0 件、または追加チケットのワークも承認されたとき、Shall スキルは機構が示す次のワークのスキルを読み込み、未着手・作業中のチケットが無くなるまで繰り返さなければならない。
- When 全体まとめのワークが承認されたとき、Shall スキルは MR 本文を統括レポートの要約（変更内容・受け入れ条件との対応・動作確認・残課題）で最終更新し、マージ前作業に進む承認を得なければならない。
- When マージ前作業が承認されたとき、Shall スキルは「作業領域の片付け → default ブランチとの衝突確認 → 関連 issue へのコメント → draft 解除」を順に行い、各ステップが実施済みであると機構が確認できたときだけ draft を解除し、マージは行わず停止しなければならない。

### 承認ポイント

- When どの issue で対応するか（既存 / 新規 / 別候補 / 分割）を決めるとき、Shall スキルは選択肢を提示し、明示的な承認を得なければならない。
- When 新規 issue の本文、または既存 issue への追記が必要なとき、Shall スキルはブランチ名・MR タイトルも同時に提示し、明示的な承認を得なければならない。既存 issue の記述で足りるときはこの承認は不要とし、ブランチ名・MR タイトルは issue の選択の承認と同時に提示する。
- When 全体計画でフェーズ列・各チケットの実行者・人間レビュー要否を決めるとき、Shall スキルはユーザーと合意しなければならない。
- When 人間レビュー要のチケットを含むワークの完了後にレビューを依頼したとき、Shall スキルは応答を終えて人間のレビューを待ち、チャット上の質問でセッションを塞いではならない。取得した指摘への対応要否の確認にはチャット上の質問を使ってよい。
- When 全体まとめ完了後にマージ前作業へ進むとき、Shall スキルは明示的な承認を得なければならない。承認後は draft 解除まで改めて確認しない。
- When default ブランチとの衝突を解消するとき、Shall スキルは衝突ファイルと解消方針を提示して承認を得てから `git merge` で取り込み、`git rebase` や片側丸ごと採用を使ってはならない。
- When 関連 issue にコメントを投稿するとき、Shall スキルは投稿先の issue 番号と本文そのものを提示して承認を得なければならない。
- When ユーザーが応答できない実行形態で承認が必要になったとき、Shall スキルは承認が必要な内容（衝突・通知本文など）を報告してセッションを終え、次回セッションの再開から続けなければならない。

### 他のスキル・機構との整合

- When issue を検索・作成・追記するとき、Shall スキルは自前で `glab issue` / `gh issue` を組み立てず `task-gh-issue` の手順に従わなければならない。
- When ブランチと MR を作成・更新するとき、Shall スキルは `task-gh-feature` の手順に従わなければならない。
- When コミット・push・チケットの状態変更・レビュー依頼と完了・マージ前作業を行うとき、Shall スキルは機構の提供コマンド（とそれを使う task スキル）経由でのみ行い、`git` のコミット・push の直接実行、進行状態の直接編集、draft 解除の直接実行を行ってはならない。
- When チケットが作業中のとき、Shall not スキルは `glab` / `gh` コマンドや push を実行してはならない（リモートへの操作はワークの切れ目で行う）。
- When 次に読み込むワークのスキルを選ぶとき、Shall スキルは目視で判断せず機構の示す結果に従い、対応するスキルが無ければ不整合として報告して停止しなければならない。
- When ワークを実施するとき、Shall スキルは各ワークをサブエージェント（全体計画で合意したモデル）に委ね、自身はワークの起動・結果報告の受け取り・ワークの切れ目の処理に徹しなければならない。並列に進めたいチケット群や新しいコンテキストで実施したいチケット（実行者がワークのモデルと異なるものを含む）は、ワークからの要求に応じてスキルがチケット単位のサブエージェントを起動する。
- When ワークの実施中であるとき、Shall not スキルはチケット運用の手順（着手・完了・作業ログ・DoD）を再掲せず、`work-ticket-driven` の手順を参照しなければならない。

### アルタナティブフロー（代替経路）

- If 現在のブランチに open な MR があり、作業領域にチケット（未着手 / 作業中 / 完了）がある場合、Then スキルは issue の照合からやり直さず、現在地（ワークの途中 / レビュー依頼前 / レビュー待ち / レビュー済み）を機構から得て再開しなければならない。レビュー待ちのときはレビュー完了の連絡がない限り応答を終える。
- If 類似候補が closed な issue のみである場合、Then スキルは再オープンして対応するか新規に作るかをユーザーに確認しなければならない。
- If 依頼が複数の独立した問題を含む場合、Then スキルは issue を分割する案を提示し、ユーザーが選んだ 1 つから着手しなければならない（1 issue = 1 MR）。
- If ユーザーが issue 番号や URL を指定した場合、Then スキルは検索を省略し「既存 issue で対応」として扱ってよい。
- If 依頼が `workflow-quick-request` の振り返り、または全体まとめの改善候補から「issue を作って進める」と合意して切り替えて来た場合、Then スキルは引き継がれた要約・受け入れ条件・種別・フェーズ列をそのまま用い、依頼の要約に関する質問を省略してよい。ただし未コミットの変更の確認と承認は省略しない。
- If issue を起票しただけで着手の指示が無い場合、Then スキルはブランチ作成に進まず、着手はユーザーの明示的な指示を待たなければならない。
- If 小さな依頼でレビューの往復が過剰な場合、Then スキルは全体計画でのフェーズ省略（理由付き）と、チケットの人間レビュー要否を「不要」に倒すことで対処し、ワークの種類をまとめてはならない。
- If `glab` / `gh` CLI が使えない環境の場合、Then スキルは機構の外部委任モード（MCP ツールでリモート操作を代行）を使い、WebFetch / curl へ落としてはならない。
- If レビュアーがチャットでレビュー判断を伝えた場合、Then スキルはその判断を MR の通常コメントとして記録してからレビュー完了の手続きに進まなければならない。

### 例外フロー（エラーケース）

- If `glab`（GitHub では `gh`）が未インストール・未認証である場合、Then スキルは導入・認証を案内し、作業を開始してはならない。
- If `origin` が GitLab でも GitHub でもない場合、Then スキルは対象外として報告して停止しなければならない。
- If 作業ツリーに未コミットの変更がある場合、Then スキルはブランチ作成前に変更内容を示し、扱い（コミット / stash / 破棄 / 中断）をユーザーに確認しなければならない（自分で判断しない）。
- If MR 作成が「差分なし」で失敗した場合、Then スキルは空コミットを作成して再試行しなければならない。
- If issue の作成・追記や MR の作成に失敗した場合、Then スキルは失敗したコマンドと出力を報告し、別の手段で代替してはならない。
- If レビュー依頼が前提未充足（未コミット / 未 push / MR なし / ワークの切れ目でない / 既に依頼済み）で拒否された場合、Then スキルは未充足を解消して再実行し、切れ目でなければ次のチケットに着手しなければならない。
- If レビュー完了の手続きが「変更要求あり」または「未返信のスレッドあり」で止まった場合、Then スキルは同じ種類の追加チケットで対応し、スレッドに返信してから再実行しなければならない。進行状態を直して通そうとしない。
- If マージ前作業の前提（未着手・作業中のチケットが無い・最後のワークが承認済み・未コミット無し・衝突無し・通知先あり）が満たせない場合、Then スキルは機構が返す未充足を報告し、該当する手順（ワーク / レビュー / 衝突解消 / 通知先の指定）へ戻らなければならない。
- If 承認で却下された場合、Then スキルはその段階に留まり、先の段階へ進んではならない。

## 前提条件

- 対象プロジェクトが GitLab または GitHub 上の Git リポジトリで、`origin` がそれを指していること
- `glab`（GitHub では `gh`）CLI がインストール・認証済みで、issue と MR の作成権限があること
- チケット駆動の仕組み（`work-*` スキル、提供コマンド、宣言範囲の強制、テンプレート）が導入済みであること
- `workflow-quick-request` と対になる振り分けとして、`CLAUDE.md`「作業の振り分け」から呼ばれること

---

## 制約条件

- **技術的制約**: GitLab（`glab` CLI）を基準に記述し、GitHub では MR → PR、`glab` → `gh` に読み替える。1 セッションは 1 つの MR だけを扱う
- **ビジネス的制約**: MR のマージ・issue の内容・レビュー完了の判断・チケットのレビュー要否の方針は人間が決める。AI は draft 解除で止まる
- **外部的制約**: 機構の統制に従い、スキル側に迂回経路を書かない。機構側にリモート操作の許可を追加しない

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | issue 検索は件数を絞り、候補提示は上位 10 件程度に絞る |
| セキュリティ | issue / MR の本文に環境変数の値・トークン・個人情報を書かない。投稿本文の一時ファイルはリポジトリ外に置く |
| 可用性 | GitLab / GitHub に接続できない場合でも、依頼の要約と issue 案の作成（ローカル）までは進められる |
| 追跡性 | ブランチ名・MR 本文・全体計画・統括レポート・issue コメントのすべてに issue 番号を残す。人間レビューを省略したワークは MR 本文とチャットの両方でそれと分かる |
| 冪等性 | 再開時に issue 照合・ブランチ作成をやり直さず、現在地から続けられる |
| 可読性 | SKILL.md は順序と承認ポイントに集中し、委譲先の手順を再掲しない。読むタイミングごとの詳細は参照資料に分割する |
