### 判断と根拠

- **保留 P1（並列の採否）**: 呼び出し元の確定を入口の前提として受け、覆さなかった。根拠は起動プロンプトが示した 2 点（issue #50 の依頼そのものが並列の実現であること / 調査 e32 が原則との衝突を「成り立たない」と判定したこと）。利得側の数値を持たないまま採ることは隠さず、DDR に明記する DoD にした
- **並列の実行単位を「作業ツリー」にした**: `isolation: worktree` の実効性（R34）と `worktree.baseRef` の効き（R35）は `.claude/` への書き込みが要り、設計フェーズの許可範囲（`wip/**` / `.claude/docs/**`）では閉じられない。単位を作業ツリーに置けば、作り方（サブエージェント隔離 / 人間の別セッション）が実装フェーズでどちらに転んでも設計が崩れない
- **進行状態・ロック・集計を本流に一本化した**: 進行状態は issue と MR に属する情報で、どちらも 1 つしか無い以上、作業ツリーごとに分ける意味が無い。これは DDR `i0009-55` の部分上書きになるので新しい DDR を立てる。判定記録と実行ログは作業ツリー側に残し、`cwd` と `agent_id` を足す（合流後にどの作業ツリーの判定かを追えるようにするため）
- **合流を提供コマンド経由（案 D 系）にした**: `scope.sh` の `merge` 分類を広げる案（J2）は DDR `i0004-07` が利点として挙げた「取り込み以外の merge を拒否できる」を手放すことになる。提供コマンドなら既定拒否の原則を緩めずに口だけ開けられ、解けない衝突を人へ返す判定と合流の記録をコマンドが持てる
- **チケットの採番を「本流でのみ作成」に置き換えた**: 調査は採番の重複（衝突せずに合流する）を束 1 の 1 番に挙げ、複合キー / ULID / 合流時の検査の 3 系統を候補にしていた。計画タスクが常に直列で本流を走る以上、実施チケットの番号は分岐前に全部決まっている。作成を本流に限れば重複が構造的に起きず、番号体系にも `find_ticket` にも `boundary.sh` にも触らずに済む
- **`cd` を通さないと決めた**: 調査 e43 の評価軸 3 が「`cd` を検査せずに `read` に足すのは作業ツリー外への書き込みを開けることと同じ」と指摘していた。作業ツリーの中では cwd が最初から worktree なので `cd` は要らない
- **逆向きの穴 5 件（L4）を本 issue で閉じると決めた**: 起動プロンプトが行き先の判断を求めていた項目。同じ `scope_classify` の git 分岐を本 issue が作り替えるので同じ改修で閉じるほうが安全で、別 issue に送ると「分類を広げた記録だけが残り統制の穴は残る」（e43 の評価軸 2 が名指しした状態）になる。とくに `-c diff.external` は任意コマンドの実行まで開いている

- **R44（完了済みチケットの作業ログを直す口が無い）は別 issue に送った**: 判断そのもの（`ticket.sh` に訂正の口を足すか）は提供コマンドの振る舞いの追加で、worktree とも並列とも無関係、受け入れ条件 A1〜A6 のどれにも当たらない。設計文書の単位を受け入れ条件と対応させるために混ぜなかった。ただし 0011 が実際に詰まっているので、**当座の逃げ道（訂正はレポート側に集約する）を実施タスク共通手順に 1 行足す**ことだけは本 issue（0015）で行う
