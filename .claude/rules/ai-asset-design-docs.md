# ai-asset-design-docs — AI アセット設計文書（.claude/docs/）の正典規約

AI アセット（スキル・フック・ルール・エージェント）の設計文書は、アセットと要件書・仕様書が 1:1:1 で対応し、要件書は外から見える振る舞いだけを、仕様書は実装が推測なしに作れる内部構造を書く。正史だけを残し、経緯は DDR、用語の定義は用語辞書に置く。この置き場の規定は本ルール 1 本で揃う（`design-docs` の参照を要しない。共通する規定は両方に書き、内容を食い違わせない）。frontmatter のキーと `type` の値一覧は `markdown-docs` ルール、SKILL.md など**アセット本体**の書き方は `ai-asset-authoring` ルールが持つ。

## 適用範囲

- `.claude/docs/**` の文書を作成・変更するとき（要件定義書 `00_requirement/`、仕様書 `10_spec/`、DDR `20_ddr/`、用語辞書 `90_glossary/`）
- 文書の内容の妥当性は MR 上の人間レビューが判断する。このルールは形（対応関係・視点・節構成・書いてはいけないもの）を定める

## 構造・配置

- 置き場は `.claude/docs/00_requirement/` / `10_spec/` / `20_ddr/` / `90_glossary/` の 4 つ
- 1:1:1: アセットごとに `00_requirement/<種類>/<アセット名>.md` と `10_spec/<種類>/<アセット名>.md` を持つ（種類はスキル `skills/`、フック `hooks/<イベント番号ディレクトリ>/`、エージェント `agents/`）。要件と仕様は同じ相対パス・同じファイル名。2 アセットを 1 文書にまとめない。ルール（`00_requirement/rules/`）は要件書のみで仕様書を作らない（機械が読む表の形式は、読む側のフックの仕様書へ）
- 横断文書（特定のアセットに紐づかない規定）は `00_requirement/` / `10_spec/` の直下に置く。サブディレクトリにはアセットに紐づく文書だけを置く。複数のアセットにまたがる規定は、横断文書にする前に「正を 1 つのアセットの文書に決めて他から参照する」形を先に検討する
- DDR は設計上の決定ごとに 1 ファイル。命名は `i<issue番号4桁>-<枝番2桁>-<タイトル>.md`。issue を持たない DDR を作らない。一覧は frontmatter から生成し、手書きで保守しない
- 用語辞書は「用語の定義（意味・目的・他の用語との関係）」の正。振る舞いの正（When / Shall）は要件書・仕様書が持ち、役割を重複させない
- 仕様書の種別ごとの節構成の正は `10_spec/skills/20-common-step-spec.md`、要件書のテンプレートは `20-common-step-requirement` スキルの `assets/requirements.template.md`

## 書式・可読性

- 要件書・仕様書は正史のみ。検討の経緯・却下した案・過去の版の内容・変更履歴の表・「以前は〜」を本文に残さない（履歴は git のコミット履歴と DDR で追う）
- 外部視点の徹底: アセットの要件書は利用者（開発者・レビュアー・AI エージェント）から見た振る舞い（何ができ、何が拒否され、何が出力されるか）だけで書く。内部構造（スクリプト名・コマンド・判定の順序・データのスキーマ・実パス）は仕様書へ。迷ったら「外部の観察者に見えるか」で線を引く
- 要件書の形: 章順は 概要（背景・目的・スコープ。「含まない」には担い先）→ ユーザーストーリー → 受け入れ基準 → 前提条件 → 制約条件 → 依存関係 → 非機能要件。受け入れ基準は EARS（When 〜 Shall / If 〜 Then / Shall not）で書き、節は **メインフロー → 代替フロー → 例外フロー** の見出しを先頭に置き、この順・この文言で統一する（規約・整合の節はその後ろ）
- 要件書に「関連するドキュメント」節・「レビュー記録」節を置かない（関連は依存関係の節で足り、レビューの経緯は MR と DDR で追う）
- DDR は 背景 / 決定 / 理由 / 却下した案 / 影響 を持つ
- 辞書のエントリは 用語名 + 定義（2〜4 行）+ 別名・禁止表記（あれば）。定義は辞書の中だけで完結させ、設計書へのリンクに頼らない。辞書に振る舞いの要件（When / Shall、判定基準・数値・手順）を書かない
- 収録済みの用語は辞書の表記に従い、初出箇所で辞書へリンクし、定義を再掲しない。禁止表記を使わない。載せる語は、複数の文書で使われ指し先や表記が揺れうる機構固有語（スキル名、ワークの種類、チケットの状態、機構が導入した概念、MR → PR のような読み替え規則）に限る
- frontmatter の規約は `markdown-docs` ルールに従う（再掲しない）

## セキュリティ

- 該当なし — 設計文書は共有前提の記述で秘密情報を含めない一般則は文書全般の規約（`markdown-docs`）が担い、設計文書に固有の規定は無い

## 堅牢性

- マージ済みの DDR は本文を変更しない。無効になったときは frontmatter の状態（置き換え済み / 廃止）と置き換え先だけを更新する。訂正が要るときは新しい DDR で置き換える
- 新しい機構固有語は、まず辞書に定義してから設計書で使う。収録語をリネームしたときは同じチケットの中で辞書を更新し、旧称は別名・禁止表記に残す
- 仕様書は対応する要件書より先に変えない（要件の変更が先）。要件側の誤り・不足を仕様側の辻褄合わせで吸収しない
- 他の文書と矛盾する記述を見つけたら、片方だけ直さず、矛盾する文書を特定して同じ変更の中で揃える

## パフォーマンス

- 該当なし — 設計文書は読み物で実行時の性能観点が無い。探索は frontmatter 索引で足りる粒度（1 対象 1 文書）を保つことは「構造・配置」が担う

## テスト・機械的検査

- 1:1:1 の対応（要件と仕様の相対パス一致）・要件書の章順と受け入れ基準の節順・禁止節の不在・DDR の命名・一覧の生成状態の機械的検査は、設計文書検査（仕様書が定める）に統合する。整備されるまでは `20-common-step-requirement` 処理フロー 7 / `20-common-step-spec` 処理フロー 5 のセルフレビューと MR 上のレビューで見る
- 仕様書の「要件との対応」表は要件の受け入れ基準を全件カバーする（行数が一致する）。実現箇所の無い要件（実装漏れ）と要件の無い節（過剰仕様）を仕様書の書き終わりに確かめる
- レビューで見る観点は本ルールの各章。別のチェックリスト文書を作らない
