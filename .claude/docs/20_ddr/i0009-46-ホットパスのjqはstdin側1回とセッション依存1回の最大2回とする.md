# i0009-46. ホットパスの `jq` は stdin 側 1 回とセッション依存 1 回の最大 2 回とする

## 背景

`i0009-22` はホットパス 5 本（`workflow-entry` / `workflow-state-guard` / `block-chmod` / `block-direct-git` / `workflow-guard`）が起動してよい外部プロセスを「**stdin を解析する `jq` の 1 回だけ**」と決め、`i0009-37` が `jq` の副入力オプションで `scope-limits.json` を相乗りさせて「1 回で足りる」と結論した。

ワーク境界の 2 巡目レビューで、この結論が成立しないことが分かった。

| フックが読む JSON | パス | 1 回目に混ぜられるか |
|---|---|---|
| フック入力 | stdin | — |
| `scope-limits.json` | 固定 | できる |
| `logs/review-state.json` / `logs/merge-state.json` | 固定 | できる |
| **`logs/sessions/<session_id>/approvals.json`**（`workflow-guard` 判定順 (6)） | **`session_id` 依存** | **できない** |
| **`logs/sessions/<session_id>/entry.json`**（`workflow-entry` 手順 3） | **`session_id` 依存** | **できない** |

`session_id` は stdin を解析して初めて分かる。公式に `session_id` を渡す環境変数は無い（`grep -c CLAUDE_SESSION wip/tmp/hooks.md` → 0。`session_id` は共通入力フィールドとしてのみ与えられる）。したがって**パスが stdin に依存する副入力を 1 回目の `jq` に渡すことは原理的にできない**。`i0009-37` の「残るのは上限設定だけ」は偽で、0019 の f2（✕問題）は解消していなかった。

## 決定

ホットパスの上限を「**`jq` だけを起動してよく、呼び出しは最大 2 回**」に改める。2 回の内訳は固定する。

| 段 | 関数 | 読むもの |
|---|---|---|
| 1 回目 | `hook_read_input [固定パス...]` | stdin と、**パスが stdin に依存しない副入力**（`scope-limits.json` / `review-state.json` / `merge-state.json`） |
| 2 回目 | `hook_read_state <パス>...` | **`session_id` に依存する副入力**（`approvals.json` / `entry.json`）。要るフックだけが呼ぶ |

- 実際の回数: `block-chmod` / `block-direct-git` / `workflow-state-guard` は **1 回**、`workflow-guard` / `workflow-entry` は **2 回**
- `git` / `date` / `sed` / `find` を呼ばないこと、回数を `make_counting_path` で数えることは `i0009-22` のまま
- 検査は `HK-T19`（回数）で固定する

## 理由

- **2 回目は構造が強いている**。「要求が増えたから緩める」のではなく、`session_id` が stdin にしか無いという実行基盤の性質から出る最小の回数である。だから「次に別の設定が要ったら 3 回」にはならない — 固定パスの副入力はいくつ増えても 1 回目に相乗りできる
- **内訳を決めれば上限は制約として機能し続ける**。`i0009-22` が心配したのは「要求のたびに緩む」ことで、回数ではなく**緩め方**が問題だった。段の意味（固定パス / セッション依存）を書けば、増やす余地が無い
- **1 本あたりの増加は最大 1 fork**。ホットパス 5 本のうち 2 本だけが 2 回になるので、同時起動時の合計は 5 → 7。`i0009-22` が挙げた「1 本の fork が 5 倍になる」の懸念は残るが、避ける手段が無い
- **純 bash の JSON パーサを書く案より安全**。`frontmatter.sh` が汎用 YAML パーサではないと断っているのと同じ理由で、入れ子とエスケープを持つ JSON を純 bash で読むのは壊れやすい

## 却下した案

- **`approvals.json` / `entry.json` を純 bash で読む**: JSON の入れ子とエスケープを純 bash で正しく扱うのは壊れやすい。`approvals.json` は承認済みパスの配列で、パスに `"` や `\` が入り得る
- **`approvals.json` / `entry.json` の書式を JSONL や `key=value` に変える**: 読み側は楽になるが、書き手（`workflow-diff-check` / `workflow-entry`）が独自形式を書くことになり、`hc_json_write`（原子的置換）の対象からも外れる。`approvals.json` は `workflow-diff-check` が read-modify-write するので、形式を変えても競合の扱いは変わらない
- **`session_id` を使わず 1 つのファイルに全セッションを混ぜる**: `i0009-07` 系の「セッション状態は `session_id` で分離し、並行する別セッションと混ざらない」（§5）に反する。並行セッションの承認が互いに見えてしまう
- **`workflow-guard` から `approvals.json` の参照をやめる**（承認の記憶を捨てる）: 承認済み範囲を毎回聞き直すことになり、要件（承認された範囲は同じセッション内では再確認しない）に反する
- **上限を「`jq` は何回でもよい」に緩める**: `i0009-22` の趣旨（fork をこれ以上増やさない圧力）が消える。内訳を固定すれば上限は保てる
