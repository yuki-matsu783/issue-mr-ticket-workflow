# フィードバック計画はヘッドレスでも止まらず既定で進む

## 背景

`10-task-feedback-plan` の要件と仕様は、ユーザーが応答できない実行形態（`claude -p` 等）で対応先の合意が取れないとき「候補の一覧と提案を報告してセッションを終える」と定めていた。合意なしに後続チケットを作らない、という慎重側の設計である。

issue #6 のチケット 0022 の申し送り B7 はこれと**正反対**のことを求めている: 「自律運用・ヘッドレスでは対応先を決めて起票まで行い、`note` で報告する」。issue #10 の調査（結果報告 0006 の d3）がこの矛盾を検出し、どちらを採るかを決めないと仕様が書けない状態になった。

## 決定

- **ヘッドレス実行でも止まらない**。既定の提案（候補ごとの対応先は「この MR で対応する」）どおりに決め、後続フェーズの計画チケットの作成（処理フロー 6）まで行い、フィードバック計画チケットを完了する
- 決めた内容（候補・分類・対応先・理由）は `boundary.sh note` で MR の通常コメントとして記録する
- **別 issue の起票（処理フロー 5）だけはヘッドレスでも行わない**。「別 issue」と判断した候補は起票せず、内容と理由を計画書と `note` に残す
- この扱いは `10-task-overall-summary` の別 issue 起票と同じ形にする（承認が取れなければ起票せず、候補を残して次の手順へ進む）

## 理由

- **止めると issue が宙に浮く**。フィードバック計画は後続フェーズの要否を確定させるタスクで、ここで止まると後続の計画チケットが 1 枚も起票されない。次のセッションが再開しても、`ticket.sh next` が返すのは作業中のフィードバック計画チケットだけで、何をすべきかが決まっていない
- **既定の提案だけで目的を達成できる**。「この MR で対応する」が既定なので、合意が取れないときにその既定を採ることは、ユーザーが提示されたら選んだであろう選択肢を選ぶことに等しい。判断を勝手に変えているわけではない
- **記録が残るので後から差し戻せる**。`note` で MR に残せば、人間はコメントを読んで「この候補は別 issue に回す」と指示できる。同じ type の追加チケットで戻る経路が既にある
- **止まる価値があるのは取り消せない副作用だけ**。別 issue の起票は他人が見る場所への書き込みで、後から取り消しても通知は残る。ここだけは既定で進めない

## 却下した案

- **現行のまま止める**: 慎重ではあるが、ヘッドレス運用でフィードバック計画に到達した時点で必ず止まる。自律運用を想定する以上、必ず止まる地点を残すのは設計として成立しない
- **別 issue の起票も既定で行う**: 申し送り B7 の文言だけを読めばこう読めるが、外部への副作用を承認なしに起こす扱いは他のタスク（全体まとめ）と食い違う。機構全体で「取り消せない外部への副作用は承認を要する」を守るほうを優先した
- **ヘッドレスでは候補の洗い出しだけ行い、対応先の決定を次のセッションに送る**: チケットを作業中のまま残すことになり、`ticket.sh next` が `current` を返し続ける。結局止まるのと同じ
- **既定を「対応しない」にして進む**: 止まらずに済むが、振り返りの成果が何も後続に渡らない。フィードバック計画を実施した意味が無くなる

## 影響

- `00_requirement/skills/10-task-feedback-plan.md` の例外フロー 1 件を書き換える（報告して終える → 既定で決めて起票まで行い記録する。別 issue は例外）
- `10_spec/skills/10-task-feedback-plan.md` の処理フロー 4 を書き換える。手順 5（別 issue の起票）はヘッドレスでは飛ばす
- ヘッドレス実行の帰結の一覧（AI アセット設計計画書が持つ表）で、`10-task-feedback-plan` は「進む」に分類される
- 対話が前提のタスクという位置づけは変えない（メインエージェント専任・振り返りは 1 issue に 1 回）。変えたのは「応答が無いときの倒し方」だけである
