# design-docs の eval 定義

## 目的

`.claude/rules/design-docs.md`（`apl/**` の設計文書の規約）が `paths` の一致で読み込まれているときに、要件定義書・仕様書を現在の正史だけで書き、経緯は DDR に分け、要件は外部視点で書き、1 アプリ 1 対象（要件定義書と仕様書を同名 1:1）の配置を守る振る舞いが安定するかを確かめる。

## 評価シナリオ

各行は仕様書「テスト観点（eval）」の行と 1:1 に対応する（eval ID が対応の鍵）。

| eval ID | 入力プロンプトと状況 | 期待する振る舞い | 判定方法 | 添付ファイル |
|---------|--------------------|-----------------|---------|-------------|
| DD-E01 | 設計反映タスクで「実装で仕様と違った点（判定順を変えた）を仕様書に反映して」 | 仕様書は現在の振る舞いだけに書き換え、「以前は〜だったが」「〜に変更した」という履歴を仕様書に書かず、判断の経緯と却下案を DDR に 1 件起こす | 仕様書の差分に履歴語（以前 / 変更前 / 旧）が無く、DDR が追加されていること | `.claude/rules/design-docs.md`、対象の仕様書、DDR の既存例 |
| DD-E02 | 「この要件定義書に、実装で使うスクリプト名と判定の順序を書いておいて」 | 要件定義書には外部から見える振る舞い（何ができるか・何が拒否されるか）だけを書き、スクリプト名・判定順・スキーマは仕様書に書くと切り分けて提案する | 要件定義書の差分にスクリプト名・関数名・判定順が無く、仕様書側への追記（または提案）があること | `.claude/rules/design-docs.md`、対象の要件定義書と仕様書 |
| DD-E03 | 「新しいアプリ X の設計文書を作って」（要件・仕様のどちらも無い） | 1 アプリにつき要件定義書 1・仕様書 1 を対で作り、`apl/X/docs/00_requirement/X.md` と `apl/X/docs/10_spec/X.md` に同名で置き、frontmatter をテンプレートに合わせる。関連ドキュメント節・レビュー記録節を置かない | 2 つのファイルがその置き場に同名で存在し、frontmatter の `type` が正しく、規約が禁じる節が無いこと | `.claude/rules/design-docs.md`、`20-common-step-requirement/assets/requirements.template.md` |

## 比較条件

- with: `.claude/rules/design-docs.md` が `paths`（`apl/**`）の一致で読み込まれている状態で各シナリオのプロンプトを与える
- without: `design-docs.md` を読み込まない状態で、CLAUDE.md と requirement / spec の共通ステップ仕様だけを文脈に置いて同じプロンプトを与える
- 実施回数: シナリオごとに with / without を各 3 回

## 効果ありの判定基準

- DD-E01: with の 3 回すべてで仕様書に履歴が入らず DDR が起きる。without で 1 回以上仕様書に履歴を書く、または DDR を起こさない
- DD-E02: with の 3 回すべてで要件と仕様の切り分けが提案され、without で 1 回以上要件定義書に内部構造を書く
- DD-E03: with の 3 回すべてでアプリルート配下に同名 1:1 の対ができ正しい節構成になり、without で 1 回以上片方だけ、置き場違い、または禁じられた節を置く
- 3 シナリオのうち 2 つ以上で上記を満たせば効果あり。差が出ないシナリオはルールの該当章の文言を見直す対象として記録する
