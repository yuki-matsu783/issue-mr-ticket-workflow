# adversarial-reviewer エージェント

## 概要

敵対的レビュー（経緯を知らされない読み取り専用のレビュアーが、成果物ルールの観点章に沿って欠陥を探すレビュー）を実施するサブエージェントの要件を定義する。人間レビューの前段として使う。

- **背景**: 成果物を作った本人は「なぜそう作ったか」の文脈を持つため、同じコンテキストでのセルフレビューは追認に流れやすい。経緯を渡さない独立したコンテキストのレビュアーに「この変更が壊れるとしたら、どこで、どういう入力・状況のときか」を探させることで、人間レビューの前に欠陥を減らし、人間の負担を設計判断の確認に絞れる。指摘は MR のインラインコメントとして投稿され人間の指摘と同列に返信されるため、位置と確度が機械的に扱える形で返る必要がある。
- **目的**: 実施タスクの成果に対して、実装の文脈に引きずられない指摘が確度付きで得られ、呼び出し元が投稿する指摘を選別できる状態を実現する。
- **スコープ**:
  - 含む: エージェント定義、入力（レビュー対象と観点）、レビューの進め方と姿勢、指摘の内容（位置・重大度・確度）、0 件の扱い
  - 含まない: 指摘の選別と MR への投稿（呼び出し元）、指摘への対応要否の判断（人間と呼び出し元の AI）、実施回数の上限の管理（機構がフェーズごとに持ち、緩める手段を用意しない）、レビュー観点の内容（成果物ルールの観点章が正）、人間レビューそのもの

---

## ユーザーストーリー

**[As a]** MR をレビューする人間のレビュアーとして、

**[I want]** 自分が読む前に、明らかな欠陥は敵対的レビューで拾われていてほしい。

**[So that]** 自分は設計判断と受け入れ条件の確認に集中できるため。

**[As a]** レビューを依頼する呼び出し元（メインエージェント）として、

**[I want]** 指摘が位置・重大度・確度付きの機械的に扱える形で返ってきてほしい。

**[So that]** 投稿する指摘を確度で選別し、MR のインラインコメントとして人間の指摘と同列に扱えるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When 呼び出し元がレビューを依頼するとき、Shall エージェントはレビュー対象（差分または対象ファイルの一覧）と、成果物ルールの観点章から集められたレビュー観点を渡されて起動され、それだけを手がかりにレビューを始めなければならない（観点を自分で集めに行かない）。
- When レビューするとき、Shall エージェントは渡された観点を対象へ順に突き合わせ、観点に無い欠陥（境界値・エラー経路・変更の波及先の追随漏れ・書かれた説明と実体の食い違い）も探さなければならない。該当の無い観点について「問題なし」を並べない。
- When 指摘の裏取りが要るとき、Shall エージェントは対象とその周辺を読み取り専用で確認してよく、実装の経緯（コミットの履歴・作業ログ・過去の議論）を読んではならない（実装者の意図の混入を防ぐ。書かれているものだけで判断し、書かれていないことは「欠けている」として扱う）。
- When 指摘を返す前に、Shall エージェントは各指摘への反証を 1 回試み、覆った指摘は落とすか確度を下げ、裏取りしていない指摘に高い確度を付けてはならない。
- When 指摘を返すとき、Shall 各指摘は対象の位置・重大度・確度と、「何が問題か」「どういう入力・状況で壊れるか」「どう直すか」を含み、呼び出し元が MR のインラインコメントとして投稿できる機械的に扱える形で返されなければならない。
- When 指摘になりうると考えて中身を確かめ、その結果として否定できたとき、Shall エージェントはそれを「確かめて問題なしと判断した点」として、確かめた事柄と確かめ方を添えて返さなければならない（呼び出し元が「見ていない範囲」と「見たうえで問題が無かった範囲」を区別できるようにする。該当の無い観点を並べることとは別である）。
- When レビュー対象が件数や網羅を主張しているとき、Shall エージェントはそのうち何件かを抜き取って実体と突き合わせ、突き合わせた主張・実体・結果の一覧を返さなければならない（まとめの主張を数えずに信じない）。突き合わせて食い違ったものは指摘としても返す。
- When 欠陥が見つからなかったとき、Shall エージェントは指摘 0 件として返し、水増しの軽微な指摘で埋めてはならない。
- When レビューを実施するとき、Shall not エージェントはファイルの作成・変更・git 操作・リモートへの投稿（MR コメントを含む）を行ってはならない（投稿は呼び出し元の責務）。
- When 指摘を落とすか迷うとき、Shall not エージェントは実装の意図を推測して指摘を取り下げてはならない（推測ではなく反証と裏取りで判断する）。

### 代替フロー

- If レビュー観点が渡されなかった場合、Then エージェントは一般的な観点（正しさ・境界値・エラー処理・テストの有無）でレビューし、観点が渡されなかった旨を結果に添えなければならない。
- If 対象がコードではなく文書（計画書・レポート・設計文書）の場合、Then エージェントは同じ姿勢（観点の突き合わせ・反証・確度の申告）でレビューしなければならない（指摘の形も変えない）。

### 例外フロー

- If レビュー対象が読めない・渡された指し先が存在しない場合、Then エージェントはレビューできなかった対象とその理由を返し、対象を自分で差し替えたり、読めた分だけで全体をレビューしたと装ったりしてはならない。

## 前提条件

- 成果物ルール（`.claude/rules/`）が観点章を持ち、対象に適用する観点の収集と引き渡しは呼び出し元が済ませていること
- 呼び出し元（メインセッション）が起動・指摘の選別と投稿・実施回数の管理を担うこと（サブエージェントは入れ子で起動できないため、実施タスクのサブエージェントからは起動の要求だけが返る）
- 読み取り専用の道具だけで動作できること（書き込み・投稿の手段を持たされない）

---

## 制約条件

- **技術的制約**: 読み取り専用で動作し、ユーザーと対話できない。レビューの実施ごとに新しいコンテキストで起動され、過去の実施結果を持ち越さない。**レビュー対象を作った実行者とは別のモデルで動く**（同じモデルは同じ癖で同じ見落としをするため）
- **ビジネス的制約**: 指摘への対応要否は人間と呼び出し元の AI が決める。実施回数の上限はフェーズごとに機構が持ち、エージェント側に上限を緩める手段を持たせない
- **外部的制約**: 投稿された指摘は人間の指摘と同列に MR 上で返信される（投稿と返信は呼び出し元が行う）

## 依存関係

- 成果物ルール群の観点章（`rules/ルール体系.md` の章スキーマ。レビュー観点の正）
- `00-workflow-issue-mr-driven` と各実施 task スキル（実施の判断と起動の要求元）
- レビュー指摘を MR へ投稿する提供コマンド（未作成）

## 非機能要件

| 項目 | 説明 |
|------|------|
| 独立性 | 実施のたびに新しいコンテキストで動き、実装の経緯・過去の実施結果に影響されない |
| 信頼性 | 確度の自己申告が投稿の選別に使える水準で正直である（裏取りの無い高確度を付けない） |
| 一貫性 | 対象の種類（コード・文書）やフェーズによらず、指摘の形と姿勢が同じ |
| 簡潔性 | 出力は指摘だけに絞り、講評・要約の散文を添えない |
