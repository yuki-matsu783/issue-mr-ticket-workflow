# i0001-01. 要件と仕様は正史のみを残し経緯は DDR に分離する

## 背景

参考実装の agent-workflow は、要件定義書の「レビュー記録」表に方針転換の経緯まで書き、仕様書の本文にも「以前は〜だったが issue #N で〜に変えた」という記述が混ざる。MR-driven-workflow は spec を「現在の正史」として上書きし、経緯は DDR に分離しているが、spec の「影響範囲」節が issue ごとの changelog として積み上がり 4,600 行に達している。

## 決定

- `.claude/docs/00_requirements/` と `.claude/docs/10_spec/` には**その時点で有効な内容だけ**を書く。過去の版の内容・検討した案・却下理由を本文に残さない
- 決定の経緯（背景・決定・理由・却下案・影響）は `.claude/docs/20_ddr/` の DDR に書く。識別子は `i<issue番号4桁>-<枝番2桁>` とし、issue を持たない DDR は作らない
- DDR の本文はマージ後に変更しない。無効化は frontmatter の `status` / `superseded_by` だけで表す
- requirements / spec は「レビュー記録」「変更履歴」の表を持たない。いつ何が変わったかは git のコミット履歴と MR、なぜ変わったかは DDR で追う

## 理由

- 読み手が「今どうなっているか」を知るのに過去の経緯を読み飛ばす必要が無くなる
- 経緯を DDR に閉じ込めることで、spec が changelog として肥大化する構造を避ける
- issue 番号ベースの識別子は GitLab / GitHub が中央採番するため、並行ブランチで同じ番号を採る事故が原理的に起きない

## 却下した案

- **レビュー記録表に経緯も書く（agent-workflow 方式）**: 1 ファイルで完結し導線が単純だが、表が長くなるほど本文の正史と経緯の境界が曖昧になる
- **spec に「影響範囲」節を持ち issue ごとに追記する（MR-driven-workflow 方式）**: 何がいつ変わったかを spec だけで追えるが、追記のみで縮まないため Read の上限を超える
- **DDR を連番で採番する**: 単純だが、2 ブランチが同時に DDR を足すと同じ番号になり git が無言でマージする

## 影響

- 要件定義書 `.claude/docs/00_requirements/自己改善ワークフロー機構.md` の G 節
- 今後の spec テンプレートは「未決定事項」を持ってよいが、「変更履歴」節を持たない
- DDR の一覧は frontmatter から生成する（生成スクリプトは AI アセット化フェーズで作る）
