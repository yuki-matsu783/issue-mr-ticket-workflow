# i0001-14. フックはリモートに問い合わせず、想定する全実行環境でアクセスできるものだけを判定材料にする

## 背景

参考実装 MR-driven-workflow の SessionStart フックは `gh` / `glab` で現在のブランチに紐づく issue / MR の状態を取得し、CLI 不在時は MCP フォールバックの案内を注入し、未認証時は失敗メッセージだけを返す作りだった。本機構の `session-start` フックの要件書の初版も、MR 番号・URL・draft 状態・未返信スレッド数をリモートから取得する前提で書かれていた。

本機構が想定する実行環境は Windows の git bash・WSL・CI・Claude Code on the web・サブエージェントと幅があり、CLI の有無・認証の状態・ネットワークの到達性が環境ごとに異なる。フックはセッションの開始やツール呼び出しのたびに自動で走り、AI が明示的に実行するものではないため、環境制約で動かなかったときに AI が自力で復旧する経路が無く、フロー全体が止まる。

## 決定

- フックの判定・導出の材料は、**想定する全実行環境で確実にアクセスできるもの**（リポジトリ内のファイル、git のローカル操作、フックへの入力）に限る。`glab` / `gh` や API などリモートへの問い合わせはフックから行わない
- MR に関する情報（番号・URL・レビュー依頼と完了の証跡・draft 解除の記録）は、リモートを操作した提供コマンド（ブランチ・MR 作成、レビュー依頼・完了、マージ前作業）がその時点でローカルの進行状態に記録し、フックはそれを読む
- リモートの現在値が要る情報（未返信スレッド数・レビュー判定・MR の open / closed）はフックでは扱わず、AI が明示的に実行する提供コマンドが取得する
- 基準は「想定する全実行環境でアクセスできるか」であり「リモートかどうか」ではない。全環境で確実にアクセスできる対象が増えた場合（例: 全環境で認証済みの CLI が保証される）は、その対象への問い合わせをフックから行ってよい
- この原則は要件定義書には書かず、本 DDR にだけ残す。各フックの要件書には「何をどこから導出するか」という振る舞いだけを書く

## 理由

- 環境制約でフックが失敗し、フローが停止するのを避ける。フックは自動で走るため、失敗したときの復旧手段が AI に無い
- 提供コマンドは AI が明示的に実行するため、リモートに到達できず失敗しても AI がその場で対処（ユーザーへの報告・外部委任モードへの切り替え）できる。リモートへの依存をそちらに寄せるほうが安全側に倒れる
- 状態遷移はすべて提供コマンド経由（i0001-03）なので、リモートを操作した結果はその時点でローカルに記録でき、フックが改めて問い合わせる必要が無い
- セッション開始やツール呼び出しのたびに API の往復が走らず、フックが速い。単体テストでリモートを差し替える必要も無い

## 却下した案

- **参考実装方式（フックが `gh` / `glab` で取得し、不在時は MCP フォールバックを案内する）**: 情報は常に新鮮だが、認証・ネットワークに依存し、環境ごとの分岐とフォールバックの保守が要る。フックが止まるとフローも止まる
- **リモートに到達できたときだけ問い合わせ、失敗したら黙って省略する**: 実装は簡単だが、環境によって注入内容が変わり、再開の手順が環境依存になる。到達確認のタイムアウト待ちでセッション開始が遅れる
- **フックから MCP ツールで取得する**: フックは MCP ツールを呼べない

## 影響

- 要件定義書 `00_requirements/hooks/00-SessionStart/session-start.md`: 導出の元をリポジトリ内のファイルに限定し、未返信スレッド数と `glab` / `gh` 不在時の案内を削除。機構の外で作られた MR は「記録なし」として扱い、提供コマンドで紐づけ直す代替経路を追加
- `workflow-entry` / `workflow-guard` / `workflow-diff-check` / `workflow-state-guard` / `block-direct-git` / `block-chmod` / `subagent-start-check` / `subagent-stop-check` は元からリモートを使わない
- `post-push-compact-prompt` は参照リンクを origin の設定・機構の進行状態・ローカルの git から組み立て、リモートに問い合わせない。`post-push-usage-report` は集計とレポート本文の組み立てまでを担い、MR への投稿はワークの切れ目の処理で AI が実行する提供コマンドが行う（参考実装ではフック自身が投稿していた）
- 提供コマンド（ブランチ・MR 作成、レビュー依頼・完了、マージ前作業）は、リモート操作の結果（MR 番号・URL・証跡）をローカルの進行状態に記録する要件を持つ。記録の形式は仕様で定める
- 既存の MR を進行状態に紐づけ直す手段をブランチ・MR 作成の task スキル（提供コマンド）が持つ
