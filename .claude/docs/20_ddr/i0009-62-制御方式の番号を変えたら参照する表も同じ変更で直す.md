# i0009-62. 制御方式の番号を変えたら、参照する表も同じ変更で直す

## 背景

0020 は `workflow-state-guard` に MCP の分岐を**制御方式 4** として新設し、それまでの 4（入力不正）を **5** に繰り下げた。ところが同じ文書の「要件との対応」表の最終行は「例外: 判定不能は関係しうる操作だけ拒否側 | **制御方式 4**、WF309」のまま残っていた。現在の 4 は MCP の分岐で、判定不能は 5 である。

0024 でも同じことが起きかけた（`subagent-stop-check` に WF801 の縮退判定を制御方式 2 として新設し、以降を繰り下げた）。

制御方式の番号は**文書内の複数箇所から参照される**。

- 「要件との対応」表の実現箇所
- テスト観点の説明
- 他のフックの仕様からの参照（「`workflow-guard` の制御方式 6」など）
- DDR の「影響」

番号だけを見ても、それがどの判定を指すかは分からない。ずれても機械では検出できない。

## 決定

- `workflow-state-guard` の「要件との対応」表を実体に合わせる（判定不能を制御方式 5 に。MCP の分岐を指す行を追加）
- **規約として**: 制御方式に分岐を挿入して番号を繰り下げたら、**同じ変更の中で**その文書内の参照（要件との対応表・テスト観点・記録節）と、他文書からの参照を直す
- 参照の探し方は「`制御方式 <番号>`」で `grep` する（表記を揺らさない）
- 番号を持つ節を新設するときは、**末尾に足せるなら末尾に足す**（繰り下げを起こさない）。判定順に意味があって途中に入れるしかないときだけ繰り下げる

## 理由

- **番号は名前ではない**。「制御方式 4」は位置を指すだけで、何を判定するかを含まない。名前（「MCP の分岐」）で参照すればずれないが、判定順そのものが仕様なので番号を捨てられない
- **`i0009-58` の一般規約では拾えない**。あれは「横断→個別」の方向を扱うもので、これは**同じ文書の中**の整合。別の型として書く
- **末尾に足せば繰り下げが起きない**という予防が有効。`workflow-state-guard` の MCP の分岐は判定順の意味（制御方式 2・3 に当たらないものを拾う）から途中に入れる必要があったが、テスト観点のような並びは末尾に足せる（`i0009-45`・0024 の `SA-T07` の並べ直しと同じ話）
- **`grep` で確かめられる**。表記を「制御方式 <番号>」に揃えておけば、変更のたびに検索して照合できる

## 却下した案

- **制御方式に番号ではなく名前を付ける（「制御方式: MCP」）**: 判定**順**が仕様の一部なので、順序を表す番号は必要。名前を併記する案もあるが、既存の 11 本すべてを書き換えることになり、この issue の範囲を超える
- **機械的な検査を作る**: 「制御方式 5」という文字列がその文書の制御方式の数を超えていないか、程度なら書けるが、**中身が合っているか**は検査できない（4 と 5 を取り違えても両方存在する）
- **要件との対応表から番号を外し、識別子（WF309）だけにする**: 識別子は複数の制御方式から出ることがあり（WF302 は制御方式 2 と 3 の両方から出る）、実現箇所を一意に指せない

## 影響

- `10_spec/hooks/20-PreToolUse/workflow-state-guard.md`「要件との対応」表（判定不能を制御方式 5 に・MCP の行を追加）
- **今後の設計チケットへ**: 制御方式に途中挿入したら、同じ変更で `grep '制御方式 '` して参照を直す。末尾に足せるものは末尾に足す
- 関連: `i0009-58`（横断→個別に降ろす規約）・`i0009-45`（テスト ID の通番）
