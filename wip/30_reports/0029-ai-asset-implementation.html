登録段階 ① に載る案内側フック 6 本を書いた。案内側は「判定できないときは黙って通す」ので、fail-closed ラッパーを付けていない。本体に判定規則は 1 つも無く、許可範囲は scope.sh、push の検知は push-detect.sh、transcript の解析は transcript.sh、コマンド位置は cmdpos.sh に閉じている。新規テストは 237 件、全件テストは 2 ロケールで 21 本 / 112 件・FAIL 0。実装中に仕様との差を 7 件見つけ、うち 2 件は仕様の側を直す必要がある（0032 へ）。

  • 2◎良
  • 2△注意
  • 2✕問題

◆特に見てほしい

判断に困っている

  • r1（△注意）subagent-stop-check の縮退判定を agentId で引けない。PreToolUse Agent の時点では agentId がまだ発行されていないので、subagent-start-check は記録に載せようがない。実装はセッション単位で引いたが、「同じセッションで 1 回でも Agent を起動していれば以後は縮退でないと判定する」副作用がある
  • r2（△注意）git status に -uall を足したこと。既定では未追跡がディレクトリ単位に畳まれ、中身の許可範囲を判定できない（実測で wip/ が WF601 に化けた）。代償は未追跡が大量にあるリポジトリで走査が重くなること
  • r3（△注意）workflow-diff-check が approvals.json にロックを取らないこと。ホットパスから hc_lock を呼ぶと find が毎回 fork する。競合時に失われるのは承認 1 件に留まる、という判断

◇承認が欲しい

方針は決めた

  • r4: workflow-diff-check が「今回承認された範囲」をその場の差分判定にも反映すること
  • r5: subagent-start-check の 2 経路出力を hook-common の private ヘルパで組み立てたこと（公開 API 化は 0032 へ）
  • r6: WF911 / WF913 の識別子を本文の先頭に自分で置いたこと（hook_inject は識別子を付けない）
  • r7: --accumulate は停止中に decisions.jsonl へ何も書かないこと

・細かいレビューは不要

ほぼ確実

  • post-push-compact-prompt の 2 件のバグ修正
  • SP-T08 のテストで executor を sub-opus ではなく opus にしたこと
  • session-start のテストを SE-T05 後半・SE-T06 後半に絞ったこと（DDR i0009-09 と同じ理由）

確かめられなかったこと（この結果が言っていないこと）

  • 本番のフックとして動かしていない。6 本とも settings.json に未登録（登録は ① で人間の操作・0031）。T1〜T4 / T9 はまだ 1 つも測れていない
  • boundary.sh が無いので session-start の注入の整形は空。SE-T01〜T04・T07〜T09 は 3/3（issue #10）へ送った

実施した内容と結果

  1. 1

    workflow-diff-check — 承認の記憶と差分の検知 ◎良 根拠: DC-T01〜T07 = 43 件 FAIL 0

    2 つの仕事を 1 本に持つ。承認の記憶は「書き込み操作が PostToolUse に届いた = 人間が承認して実行された」と読み、WF202（未記載）だった対象の承認単位（親ディレクトリ。file_granular とルート直下はファイル単位）を approvals.json に追記する。WF203（毎回確認）は記憶しない。対象パスは Edit / Write なら tool_input.file_path、Bash なら cmdpos + scope_classify の SC_TARGETS から取る。差分の検知は git status --porcelain=v2 -z -uall と git diff --name-status -z <base_sha> を合わせ、パスごとに scope_resolve する。

    根拠を見る（実行コマンドと出力） 
    $ bash .claude/hooks/22-PostToolUse/tests/test_workflow_diff_check.sh
passes=43 failures=0

    結論

    許可範囲の判定は scope.sh の scope_resolve だけを使い、独自の範囲を持たない。今回承認された範囲はその場の差分判定にも反映する（足さないと、承認されて実行された直後の Write が WF601 に列挙される）。

  2. 2

    post-push-usage-report — 1 本を 2 つの契機で使う ◎良 根拠: UR-T01〜T07 = 36 件 FAIL 0

    --accumulate（Stop / SubagentStop）で logs/usage/<branch>.json に加算し、既定（PostToolUse）で合算してレポート本文を作る。二重計上の防止は last_offset（transcript の処理済み行数）。SubagentStop は agent_transcript_path を読む（transcript_path はメインのものなので、読むとメイン分が subagents[] に二重計上される）。起点は自分の状態から渡すので、並列に走る post-push-compact-prompt が先に状態を進めても検知が壊れない（DDR i0009-24）。

    根拠を見る（実行コマンドと出力） 
    $ bash .claude/hooks/22-PostToolUse/tests/test_post_push_usage_report.sh
passes=36 failures=0

    結論

    実作業時間は transcript.sh が返す timestamps を呼び手側で足す（ユーザー入力の直前と 10 分超の間隔を除く）。transcript.sh の契約は「タイムスタンプ列を返す」までなので、計算は本体に置いた。

  3. 3

    subagent-start-check — 2 つのイベント、2 つの経路 △注意 根拠: SA-T01〜T09 = 56 件 FAIL 0

    同じスクリプトを SubagentStart と PreToolUse Agent に登録し、hook_event_name で分ける。SubagentStart には model が来ないので比較できるのは PreToolUse だけ（DDR i0009-06）。WF801 / WF803 は systemMessage と additionalContext の両方に出す。前者はユーザーにその場で表示され、サブエージェントが動き出す前に人間が気づける唯一の経路。

    根拠を見る（実行コマンドと出力） 
    $ bash .claude/hooks/12-SubagentStart/tests/test_subagent_start_check.sh
passes=56 failures=0

    結論

    通知しなかったときも skip を理由つきで記録する（DDR i0009-52）。理由は 6 通り（一致 / 対象チケット無し / executor の記載無し / 実行者がメイン / model が特定できない / subagent_type が対象外）。2 経路の出力は hook-common に公開 API が無く、private ヘルパを直に使った（0032 で公開 API 化を提案）。

  4. 4

    subagent-stop-check — status で分け、縮退はセッション単位で引く △注意 根拠: SP-T01〜T08 = 51 件 FAIL 0

    tool_response.status が async_launched（background へ移った = まだ作業していない）なら作業後の検査をしない。行うと作業前の作業領域を見ることになる。代わりに WF814 を出す。completed なら SubagentStop が残した記録をtool_response.agentId（camelCase）で引き、無ければその場で検査する。

    根拠を見る（実行コマンドと出力） 
    $ bash .claude/hooks/13-SubagentStop/tests/test_subagent_stop_check.sh
passes=51 failures=0

    結論

    仕様は WF801 の縮退判定を「同じ agentId の記録があるか」と書くが、PreToolUse Agent の時点では agentId がまだ発行されていないので記録に載せられない。実装は「このセッションの subagent-start-check の記録が 1 件でもあるか」で引く。縮退は登録行が外れているというセッション横断の条件なので、単位としてはこちらのほうが実態に合う。0032 で仕様側に書き戻す。

  5. 5

    4c プローブ — 仕様から 2 件逸脱して値を落とす ✕問題 根拠: 既定で副作用ゼロを 4 本のテストが固定

    decisions.jsonl は §5 で 10 キー固定なので permission_mode / model / tool_response / agent_type を入れる場所が無い。systemMessage を出す WF801 / WF803 は subagent_type が task-executor で executor が main 以外のときにしか発火しないので、そのままでは T9（systemMessage が届くか）が測れない。lib/probe-4c.sh を足し、6 本すべてが入力の読み込み直後・早期 return より前で probe_4c を呼ぶ。

    根拠を見る（実行コマンドと出力） 
    # 既定（環境変数なし）では 1 行目で戻る
probe_4c() {
  [[ "${WORKFLOW_PROBE_4C:-0}" == "1" ]] || return 0

    結論

    逸脱 2 件: (1) rules/logger.md の「値ではなく有無・長さ」から外れて 7 フィールドの値を落とす、(2) フック共通仕様 §5 の logs/ の表に無いパス（logs/hooks/probe-4c.jsonl）を増やす。0031 の実測が終わったら、このファイルと呼び出し 1 行を削除する。

  6. 6

    実装中に見つけた自分のバグ 2 件（post-push-compact-prompt） ✕問題 根拠: PP-T01 / PP-T04 が拾った

    どちらも 0029 で書いたコードで、テストが拾った。push-state.json が 1 度も書けていなかったこと（jq --slurpfile にプロセス置換 /dev/fd/63 を渡していて Windows の jq が開けない）と、logs/mr.json の MR 番号を .number // .iid で読んでいたこと（正のキーは .mr）。

    根拠を見る（実行コマンドと出力） 
    FAIL PP-T01: expected 'd8be06c...' actual ''
FAIL PP-T01: expected '1' actual ''

    結論

    どちらもファイルを直に読む形・正のキーを先に見る形へ直した。--slurpfile + プロセス置換が他に無いかは 0032 で見る。

設計への反映

  1. 仕様 workflow-diff-check.md 制御方式 4 に -uall を書く（未追跡はファイル単位で判定する）
  2. 仕様 subagent-stop-check.md 制御方式 2 の縮退判定を「セッション単位」に直す（agentId では引けない理由つき）
  3. hook-common に 2 経路出力（systemMessage + additionalContext）の公開 API を置く
  4. フック共通仕様 §3 に hook_notify と hook_inject の識別子の扱いの差を書く
  5. 仕様 subagent-stop-check.md SP-T08 の sub-opus を opus（model-aliases.txt にある族名）へ直す
  6. logs/mr.json の MR 番号のキーが .mr であることを明記する
