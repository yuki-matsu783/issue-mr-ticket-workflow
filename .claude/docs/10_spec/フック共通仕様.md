# フック共通仕様

各フックの要件定義書が「フック横断の仕様書が正として定める」と委ねた事項をここに置く。個々のフックの仕様（`10_spec/hooks/<NN-Event>/<name>.md`）はこの文書を前提に差分だけを書く。

## 1. 置き場と登録

- 実体: `.claude/hooks/<NN-Event>/<name>.sh`（bash。`bash <パス>` で呼ぶため実行権限は不要）。テストは同じディレクトリの `tests/test_<name>.sh`（雛形は `20-common-step-shell-script`）
- 共有ライブラリ: `.claude/hooks/lib/`
  - `hook-common.sh`: 入力 JSON の読み取り（`jq`）、緊急停止の判定、記録（`logs/`）、deny / ask / additionalContext の出力ヘルパ、セッション状態の読み書き
  - `cmdpos.sh`: コマンド位置の判定（§7）。`block-direct-git` が正で、`block-chmod` / `workflow-guard` / `workflow-state-guard` / `post-push-*` が共有する
  - `scope.sh`: 許可範囲の判定（§8）。`workflow-guard` が正で、`workflow-diff-check` / `subagent-stop-check` が共有する
- 登録: `.claude/settings.json` の `hooks` に、イベントごとに `{"matcher": ..., "hooks": [{"type": "command", "command": "bash .claude/hooks/<NN-Event>/<name>.sh"}]}` で登録する。登録の正は次の表（各フックの仕様「呼出条件」と一致させる。テスト HK-T01 で照合）

| イベント | matcher | フック（実行順） |
|---|---|---|
| SessionStart | （全 source: startup / resume / clear / compact） | session-start |
| UserPromptSubmit | — | workflow-entry（プロンプト境界の処理） |
| PreToolUse | `Skill` | workflow-entry（宣言の記録） |
| PreToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell\|EnterPlanMode\|Agent\|Workflow` | workflow-entry（未宣言の拒否）→ workflow-state-guard → block-chmod → block-direct-git → workflow-guard |
| PostToolUse | `Edit\|Write\|MultiEdit\|NotebookEdit\|Bash\|PowerShell` | workflow-diff-check |
| PostToolUse | `Bash\|PowerShell` | post-push-compact-prompt → post-push-usage-report |
| SubagentStart | — | subagent-start-check |
| SubagentStop | — | subagent-stop-check |
| Stop | — | post-push-usage-report（`--accumulate`: 応答完了時の使用量の蓄積） |
| PostToolUse | `Agent` | subagent-stop-check（メインエージェント側への通知経路。§3） |

- 同じイベントに複数のフックがあるとき、1 つでも deny を返せば操作は拒否される。拒否側のフック（entry / state-guard / block-* / guard）は互いに独立に判定し、先に拒否したフックが理由を返す。順序は「安価で範囲の広い判定 → 高価で狭い判定」

## 2. 入力

- stdin に JSON。共通フィールド: `session_id`、`transcript_path`、`cwd`、`hook_event_name`。イベント別: `tool_name` / `tool_input`（PreToolUse・PostToolUse）、`tool_response`（PostToolUse）、`prompt`（UserPromptSubmit）、`source`（SessionStart）、`agent_id` / `agent_type` / `model`（SubagentStart。`model` が無い版では実行者の比較を行わない）、`agent_transcript_path`（SubagentStop）
- ツールの分類（`hook-common.sh` の関数 `tool_class`）:

| 分類 | ツール |
|---|---|
| 書き込み | `Edit` `Write` `MultiEdit` `NotebookEdit` |
| 実行 | `Bash` `PowerShell` |
| 読み取り | `Read` `Glob` `Grep` `LS` `WebFetch` `WebSearch` など上記以外 |
| プランモード | `EnterPlanMode` |
| 起動 | `Agent` `Workflow` |
| 宣言 | `Skill`（`tool_input.skill` が振り分けスキル名のとき） |

- 判定の材料はこの入力・作業領域（`wip/`）・`logs/`・設定ファイルに限る。フックはリモートに問い合わせない（DDR i0001-14）。CLI の有無・認証・ネットワークに左右されない
- 作業ツリーの位置: `cwd` ではなく `git rev-parse --show-toplevel` を基準にする（サブディレクトリからの実行に備える）

## 3. 制御方式

| 目的 | イベント | 出力 |
|---|---|---|
| 拒否 | PreToolUse | stdout に `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<識別子>: <理由と対処>"}}`、終了 0 |
| 確認 | PreToolUse | 同上で `permissionDecision: "ask"`（理由に確認の根拠とチケットを含める）。ヘッドレス（§10）では `deny` に置き換える |
| 許可 | PreToolUse | 何も出力せず終了 0 |
| プロンプトの補足 | UserPromptSubmit | `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","additionalContext":"..."}}` |
| 操作後の通知 | PostToolUse | `{"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"<識別子>: ..."}}`（AI のコンテキストに入る。操作は取り消せない） |
| セッション開始の注入 | SessionStart | stdout のテキスト（そのままコンテキストに入る） |
| サブエージェントへの注入 | SubagentStart | `{"hookSpecificOutput":{"hookEventName":"SubagentStart","additionalContext":"..."}}` |
| メインへの通知（サブエージェント終了） | PostToolUse（`Agent`） | additionalContext。SubagentStop 側は記録だけ行う（SubagentStop の出力はサブエージェント側にしか届かないため。実装時に届き方を検証し、届くなら PostToolUse 登録を外す — TBD） |

- 拒否・確認・通知の文面は日本語で、先頭に識別子（§6）、続けて「何が起きたか」「対処」。ファイルの中身・差分の内容・環境変数の値・トークン・個人情報を含めない。コマンドの引用は先頭 80 文字まで
- 案内側のフック（session-start / diff-check / subagent-* / post-push-*）は依存が壊れたら**何も出さずに通す**。拒否側のフック（entry / guard / state-guard / block-*）は判定できなければ**拒否側に倒し**、理由に「機構の不調」を含める（`WFx09` 系の識別子）。無関係と確定できる操作は止めない
- フック自身の実行エラー（bash の異常終了）は Claude Code に非ブロッキングエラーとして扱われ操作が通ってしまうため、拒否側のフックは `trap` で捕捉して deny を出してから終了する

## 4. 緊急停止

- 機構全体: `WORKFLOW_ENFORCE=0`。フック単位: `WORKFLOW_<NAME>_ENFORCE=0`（`<NAME>` はフック名を大文字スネークにしたもの。例: `WORKFLOW_ENTRY_ENFORCE=0`、`WORKFLOW_GUARD_ENFORCE=0`、`BLOCK_DIRECT_GIT` → `WORKFLOW_BLOCK_DIRECT_GIT_ENFORCE=0`）
- 環境変数はセッション開始時に読み込まれるため同じセッション内では変えられない。AI は設定できず、ユーザーに「どちらを止めるか」と新しいセッションでの実行を伝える（`CLAUDE.md`「作業の振り分け」）
- 停止中のフックは判定・注入を行わず、`decisions.jsonl` に `{"decision":"disabled"}` を 1 行残す（session-start は停止中である旨を注入内容の先頭 1 行に出す）
- push 前チェックを飛ばす目的での停止は不可（`wip/push-check-skip.md` が正規の手段 — commit-push 仕様）

## 5. 記録と状態（`logs/`）

`logs/` はリポジトリ直下、`.gitignore` 済み、片付けの対象外（DDR i0001-28）。

| パス | 内容 | 書く側 | 寿命 |
|---|---|---|---|
| `logs/sh/<name>.log` | 実行ログ（共通 logger。`LOGGER_NAME=hook-<name>`） | 全フック | 手動削除まで |
| `logs/hooks/decisions.jsonl` | 判定の記録 1 行 1 件: `{"ts","session_id","hook","event","decision":"allow\|ask\|deny\|notify\|inject\|disabled\|skip","id":"WFxxx","tool","target","ticket","note"}` | 全フック | 振り返りの材料。全体まとめの後も残す |
| `logs/sessions/<session_id>/entry.json` | 振り分けの宣言状態: `{"prompt_seq","declared_skill","declared_at","continuation":"tickets\|review\|merge_prep\|null"}` | workflow-entry | セッション限り |
| `logs/sessions/<session_id>/approvals.json` | 未記載パスの承認の記憶: `[{"scope":"<親ディレクトリ or ファイル>","ticket","at"}]` | workflow-diff-check（書く）/ workflow-guard（読む） | セッション限り |
| `logs/sessions/<session_id>/usage.json` | 使用量の蓄積（post-push-usage-report） | Stop / push 時 | 投稿完了でリセット |
| `logs/push-state.json` | ブランチごとの前回 push 時点: `{"<branch>":{"sha","at","count"}}` | post-push-compact-prompt | 手動削除まで |
| `logs/mr.json` / `logs/review-state.json` / `logs/review-history.jsonl` / `logs/merge-state.json` | 提供コマンドの進行状態（`00-workflow-issue-mr-driven` / `10-task-overall-summary` 仕様） | boundary.sh / finalize.sh | フックは読むだけ |

- セッション状態は `session_id` で分離し、同じ作業ツリーで並行する別セッションと混ざらない。サブエージェント内のツール呼び出しは親と同じ `session_id` を持つため、宣言・承認の記憶はそのまま適用される（違えば実装時に `agent_id` から親を引く — TBD）
- `logs/sessions/` の 7 日より古いディレクトリは session-start が非侵襲的に削除する（失敗しても通す）
- `logs/` への書き込みは `workflow-guard` の許可範囲の判定対象外（機構自身の記録）。ただし進行状態ファイルへの AI の直接書き込みは `workflow-state-guard` が拒否する

## 7. コマンド位置の判定（`cmdpos.sh`）

入力: コマンド文字列（Bash / PowerShell）。出力: 実行位置にあるコマンドの列（各要素 = 実行体の basename と引数）、または `opaque`（判定不能）。純 bash（外部プロセス無し）。

1. 前処理: ヒアドキュメント本文（`<<TAG`〜`TAG`、`<<'TAG'`、`<<-`）、`#` コメント（行頭または空白の後）、シングルクォート文字列を除去。ダブルクォート文字列は本文を除去するが、その中の `$(...)` と `` ` ` `` は展開して実行位置として扱う
2. 分割: `;` `&&` `||` `|` `|&` 改行 `(` `)` `{` `}` `&`（バックグラウンド）で分割
3. 各セグメントの先頭から透過ラッパーを剥がす: `sudo` `env`（`VAR=val` の並び含む）`command` `exec` `time` `nice` `nohup` `builtin` `if` `then` `else` `elif` `while` `until` `do` `!`
4. 実行体を正規化: ディレクトリ部と `.exe` を除いた basename（`/usr/bin/git`、`./git`、`git.exe` → `git`）
5. 不透明な実行系（`eval` `bash -c` `sh -c` `zsh -c` `xargs` `find ... -exec` `powershell -Command` `pwsh` `node -e` `python -c` `perl -e` `ruby -e`）が実行位置にあれば、そのセグメントを `opaque` とする。呼び出し側は「opaque かつ対象語（`commit` / `push` / `chmod` / 状態ファイル名等）を含む」なら拒否側に倒す
6. PowerShell: `;` と改行で分割、呼び出し演算子 `&` と `.` を剥がす、ヒアストリング `@'`〜`'@` / `@"`〜`"@` を除去、バッククォート行継続を結合。バックスラッシュ区切りのパスは basename 化で吸収できない形（`.\git.exe` は吸収できる）があり得るため、`git` を含むトークンが実行位置にあれば拒否側に倒す
7. 縮退: bash 4.3 未満、または 1 コマンドが 4096 文字を超えるときは判定を行わず `degraded` を返し、呼び出し側は部分一致（対象語の有無）で判定して「縮退した判定」をメッセージに含める（`ai-command-style` ルールの言い換えを案内）
8. **提供コマンドの識別**: 実行体が `bash`（または `sh`）で第 1 引数が `.claude/skills/*/scripts/*.sh` または `.claude/hooks/**/*.sh` に一致するセグメントは「提供コマンド」。フックが見るのはツールへ渡された文字列だけなので、提供コマンド内部の `git` 実行や `logs/` 書き込みはそもそも判定の対象に現れない（DDR i0004-05）。提供コマンドの引数に現れるパス（`commit.sh -m .. <files>`）は `workflow-guard` が書き込みと同じ判定を適用する

## 8. 許可範囲の判定（`scope.sh`）と上限設定

- 上限設定: `.claude/hooks/config/scope-limits.json`（ユーザー管理。`workflow-guard` の仕様が形式の正）。構造:

```json
{
  "common": {
    "allow": ["wip/10_tickets/00_todo/**", "wip/20_plans/**", "wip/30_reports/**", "wip/tmp/**", "wip/00_overall_plan/**"],
    "protected": [".claude/**", ".gitignore", ".gitattributes"],
    "file_granular": [".claude/settings.json", "CLAUDE.md"],
    "state_files": ["logs/mr.json", "logs/review-state.json", "logs/review-history.jsonl", "logs/merge-state.json"]
  },
  "types": {
    "investigation": {"allow": [], "deny": ["src/**", "docs/**"], "confirm": [], "ops": ["read", "remote-read"], "plan_mode": false},
    "implementation": {"allow": ["src/**", "tests/**"], "deny": [".claude/**"], "confirm": ["package.json"], "ops": ["read", "build-test", "remote-read"], "plan_mode": false},
    "ai-asset-design": {"allow": [".claude/docs/**"], "deny": [".claude/skills/**", ".claude/hooks/**", ".claude/rules/**", ".claude/agents/**", ".claude/settings.json"], "ops": ["read", "remote-read"]},
    "ai-asset-implementation": {"allow": [".claude/skills/**", ".claude/hooks/**", ".claude/rules/**", ".claude/agents/**", ".claude/settings.json", ".claude/evals/**"], "deny": [".claude/docs/**"], "ops": ["read", "build-test", "hook-test", "remote-read"]},
    "overall-plan": {"allow": [], "ops": ["read", "remote-read", "remote-write:issue-create", "remote-write:issue-append", "remote-write:mr-create", "remote-write:push"], "plan_mode": true},
    "feedback-plan": {"ops": ["read", "remote-read", "remote-write:issue-create"]},
    "overall-summary": {"ops": ["read", "remote-read", "remote-write:issue-create", "remote-write:mr-edit", "remote-write:mr-comment", "remote-write:attach", "remote-write:push", "remote-write:draft-ready", "merge-base"]}
  }
}
```

  15 種すべてに `types` のエントリを持つ（テスト HK-T02 で `.claude/hooks/config/task-types.tsv`・`rules/work-defaults.md` の行とキー集合を照合）。パターンは glob（`**` 対応）、リポジトリルート相対
- 判定順（書き込み対象パス `p`、作業中チケットの type `t`、宣言 `d`）: (1) `p` が `logs/**`（state_files を除く）→ 対象外 / (2) `common.protected` に一致し、かつ `types[t].allow` に明示されていない → **deny WF201** / (3) `types[t].deny` に一致 → **deny WF201** / (4) `types[t].confirm` に一致 → **ask WF203**（毎回） / (5) `common.allow` または `types[t].allow` に一致、または `d.write` に一致（ただし `d.write` は `types[t].allow ∪ common.allow` の内側に限る。外側は無視） → **allow** / (6) `approvals.json` の承認済み範囲に一致 → **allow** / (7) それ以外 → **ask WF202**（承認単位は親ディレクトリ。`file_granular` に載るファイルはファイル単位）
- 操作の分類 `ops`: `read`（状態を変えない読み取り系コマンドの一覧は `scope.sh` の `READ_ONLY_CMDS`: `ls cat head tail grep rg find git-status/log/diff/show/branch/rev-parse/fetch jq wc sort diff test echo pwd which command -v bash -n shellcheck` など）/ `build-test`（`npm test` 等。プロジェクトが `scope-limits.json` の `commands.build-test` に列挙）/ `hook-test`（`.claude/hooks/**/tests/*.sh`・`.claude/skills/*/scripts/tests/*.sh`）/ `remote-read`（`gh` / `glab` の `view` `list` `api` の GET・`status`）/ `remote-write:<種別>`（`push` は push.sh、`issue-create` `issue-append` `mr-create` `mr-edit` `mr-comment` `attach` `draft-ready` は対応する `gh` / `glab` サブコマンド）/ `merge-base`（`git merge origin/<default>`）。提供コマンドは分類を問わず許可（前提検査はコマンド側）
- チケットの宣言 `d` は frontmatter の `allow`（§9）。宣言に無い `ops` は使えない（上限の内側で絞る役）

## 9. チケットの機械可読項目

チケットの記載事項は frontmatter（YAML）に置き、フックと提供コマンドはこれを読む（人間もここを読む。表への転記はしない）:

```yaml
---
type: ticket
ticket_type: implementation        # タスクの種類（.claude/hooks/config/task-types.tsv の type）
predecessors: ["0006"]             # 先行チケット
executor: "sonnet"                 # 実行者（サブエージェントのモデル）または main
human_review: {required: true, reason: "..."}
allow:
  write: ["src/auth/**", "tests/auth/**"]   # 書き込んでよい範囲（上限の内側）
  ops: ["read", "build-test", "remote-read"] # 実行してよい操作の分類
started_at: ...                    # ticket.sh が記録
completed_at: ...
base_sha: ...                      # 差分基準点
---
```

`workflow-guard` は作業中チケットの frontmatter のうち `ticket_type` `allow` `executor` `human_review` `predecessors` への書き込み（Edit / Write）を改変として拒否し（WF208）、本文（DoD のチェック・作業ログ）は許可する。`workflow-diff-check` は `ticket_type` が着手時のコミット値から変わっていれば警告する（WF603）。

## 10. ヘッドレスの判定

`WORKFLOW_HEADLESS=1` または `CI` が真値のとき、フックは「ユーザーが応答できない」とみなし、`ask` を `deny` に置き換える（理由に「計画タスクで宣言を十分に列挙する必要がある」を含める）。スキル側（`00-workflow-quick-request` 等）も同じ変数で判定する。`claude -p` の自動検知は入力に判別材料が無いため行わない（実装時に `permission_mode` 等で判別できると分かれば追加する — TBD）。
