# i0001-25. ベースブランチへの追従は開始・再開時の検知と draft 解除直前の最終ゲートで行い、常時監視は持たない

## 背景

敵対的レビューで、参考実装 MR-driven-workflow が持っていたベースブランチ追従の 3 機構（①開始・再開時の behind 検知、②MR 作成〜マージ間の追従監視、③draft 解除直前の最終ゲート）のうち、本機構には③相当が全体まとめの序盤（8 手順中 2 番目の衝突解消）にしか無いと指摘された。この機構はレビュー往復で MR が長寿命になる設計のため、古い base の上で設計・実装が進むと「衝突しないが遅れている」（ベース側にルール・仕様だけが追記された）ケースを取りこぼす。参考実装はまさにこのケースで事故している（10 コミット遅れのまま作業し、未取得分にルール追記が含まれていた）。

## 決定

- **開始・再開時の検知**: `00-workflow-issue-mr-driven` は作業の開始・再開の時点で default ブランチに取り込んでいないコミットがあればユーザーに知らせ、取り込み（merge）を提案する。衝突が無くても、ベース側に追記されたルール・仕様を知らないまま作業を進めない
- **draft 解除直前の最終ゲート**: 全体まとめは draft を解除する直前に最新の default ブランチとの衝突・遅れを再確認し、default が進んでいれば衝突解消の手順に戻る。序盤の衝突解消だけに頼らない
- 検知はリモート取得を伴うためスキル（開始・再開の手順）が行い、フックは行わない（フックはリモートに問い合わせない — `i0001-14`）。`session-start` フックには追従状態を注入しない
- **MR 作成〜マージ間の常時監視（参考実装の②）は採らない**

## 理由

- 「衝突しないが遅れている」を検知できるのは作業に入る前の確認だけで、これが最も安い（fetch と比較のみ）。長寿命 MR での取りこぼしはここで防ぐ
- draft 解除は人間のマージ判断への引き渡し点であり、その時点のベースとの関係が最後に確かめられていないと、レビュー待ちや片付けの間の default の前進を見逃す
- 常時監視はフックのリモート問い合わせ禁止（`i0001-14`）と衝突し、開始・再開時 + タスクの切れ目ごとの push（衝突すれば push が失敗して気づける）+ 最終ゲートで実用上の穴は小さい

## 却下した案

- **MR 作成〜マージ間の追従監視（参考実装の②）**: フックがリモートへ問い合わせない原則と両立せず、スキル側での定期確認は実施タイミングの定義が曖昧になる。開始・再開と最終ゲートの 2 点で足りる
- **session-start フックでの behind 注入**: フックのリモート問い合わせ禁止に反する。ローカルに fetch 済みの情報だけでは「遅れていない」ことを保証できず、誤った安心を与える
- **全体まとめ序盤の衝突解消だけ（従来）**: その後の統括レポート作成・レビュー待ち・片付けの間に default が進むと、draft 解除時点の状態を誰も確かめない

## 影響

- `00-workflow-issue-mr-driven.md`（開始・再開時の検知の代替フロー）
- `10-task-overall-summary.md`（draft 解除直前の再確認）
- `hooks/00-SessionStart/session-start.md`（追従状態を注入しないことの明記）
- draft 解除の提供コマンドの仕様（解除前の再検証に衝突・遅れの確認を含める）
