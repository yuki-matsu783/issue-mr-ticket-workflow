# 旧ワークフロースキルの残存資産の処遇と扱わない申し送り

## 背景

issue #10 は旧 `00-workflow-issue-mr-driven` / `00-workflow-quick-request` の 2 本を新設計へ改訂する。調査（結果報告 0003 の a8）で、旧スキルの配下に**新仕様の OUT ひな形に無い資産が 5 件**残っていることが分かった。改訂の対象に入れないと、新しい SKILL.md の隣に参照されない古いファイルが残り続ける。

あわせて、#6 / #9 の申し送り 24 項目のうちこの issue で扱わないものの線引き（全体計画の保留 P5）をここで決める。

## 決定

### 旧資産 5 件の処遇

| 資産 | 処遇 | 理由 |
|---|---|---|
| `00-workflow-issue-mr-driven/assets/issue-addendum.template.md` | **削除** | 同じものが `20-common-step-issue/assets/` にある。issue の起票・追記は共通ステップに委譲されており、テンプレートの正もそちらにある |
| `00-workflow-issue-mr-driven/assets/issue-notify.template.md` | **削除** | 新しい全体まとめは作業中の issue にコメントを投稿しない（成果物の所在は MR 本文のリンク一覧が担う。DDR `i0010-02`）。用途そのものが無くなった。本文に含まれる旧名も同時に消える |
| `00-workflow-issue-mr-driven/references/issue-triage.md` | **`20-common-step-issue` へ移設** | issue の検索・類似判定は `20-common-step-issue` に委譲された。中身（類似 / 関連 / 無関係の判定基準と `gh` コマンド集）は今も使うので、持ち主だけを移す |
| `00-workflow-issue-mr-driven/evals/evals.json` | **`.claude/evals/00-workflow-issue-mr-driven.md` へ移行** | eval の置き場は `.claude/evals/<アセット名>.md`（`20-common-step-ai-asset-creator` 手順 5）。旧形式の JSON はこの 2 本だけで、`20-common-step-*` は既に統一されている |
| `00-workflow-quick-request/evals/evals.json` | **`.claude/evals/00-workflow-quick-request.md` へ移行** | 同上 |

- 移行の際、`evals.json` に含まれる旧名（`10-work-*` / `20-task-*` / `workflow-lib.sh` / `retrospective`）は移行先で新しい名前に書き換える。移行は「形式の変換」と「参照更新」を同じチケットで行う
- 削除する 2 件は、削除の前に中身が新しい置き場に存在することを確かめる（`issue-addendum` は `20-common-step-issue/assets/` にあること、`issue-notify` は用途が消えたこと）

### この issue で扱わない申し送り

24 項目のうち **24 項目すべてをこの issue で扱う**（扱わないものは無い）。内訳は次のとおりで、保留 P5 は「該当なし」で閉じる。

| 状況 | 件数 | 反映先 |
|---|---|---|
| 設計フェーズで仕様に反映した | 23 | 0011〜0016（`10-task-*` 6 本・`20-common-step-*` 3 本・`agents/*` 2 本） |
| 既に反映済みだった | 1 | #19 の一部（確度と出力スキーマ）。残りは 0014 で反映 |

**「反映済み」と申し送りに書かれていた 1 項目（#20 相当の要件書の小節）が実は反映済みだった**ことも確かめた（`20-common-step-requirement` 仕様 処理フロー 4 とテンプレート）。0006 の d6 が見つけられなかったのは、申し送りの文言が見出しの階層を 1 つ深く書いていたためである。

## 理由

- **旧資産を残すと、新しい SKILL.md の隣に参照されないファイルが並ぶ**。読み手はどちらが正か分からず、AI は両方を読む。改訂のたびに「これは使うのか」を判断する手間が増える
- **削除 / 移設 / 移行を分けたのは、中身の要否が違うから**。中身が要らない（重複・用途消滅）なら削除、中身は要るが持ち主が変わったなら移設、中身も持ち主も要るが形式が古いなら移行になる
- **申し送りを 1 項目も落とさなかったのは、分量が想定より小さかったから**。0006 の d2 は「8 本の仕様書に 23 項目で作業量が見込みより大きい」と警告したが、実際には反映先が仕様書ごとにまとまっており、4 枚のチケット（0012〜0015）に収まった。落とす理由が無い

## 却下した案

- **旧資産をすべて削除する**: `issue-triage.md` の中身（類似判定の基準と `gh` コマンド集）は今も使う。削除すると `20-common-step-issue` が同じものを書き直すことになる
- **旧資産をすべて残す**: 参照されないファイルが残り、旧名 111 件のうち `evals.json` の 26 件が消えない。受け入れ条件 A3（旧名 0 件）を満たせない
- **`evals.json` を JSON のまま置き場だけ移す**: 形式が `20-common-step-*` の 9 本と揃わない。eval は人間が読んで判断するものなので、Markdown のほうが読みやすい
- **申し送りのうち大きいもの（#2〜#9 の実装計画の 8 項目）を別 issue に回す**: 実装フェーズがこの issue の中にあるので、次のフェーズが古い仕様で動くことになる。この issue の中で反映しないと意味が無い

## 影響

- 実装フェーズで 5 件の処遇（削除 2・移設 1・移行 2）を行う。移行は旧名の書き換えを伴うので、参照更新のステップと同じチケットに置く
- 受け入れ条件 A3 の「旧名 0 件」は、`evals.json` 2 本の移行（26 件）と SKILL.md 2 本の改訂（83 件）と仕様書 1 行の書き換え（1 件）、`issue-notify.template.md` の削除（1 件）で満たされる（合計 111 件）
- 全体計画の保留 P5（扱わない申し送りの線引き）は「該当なし」で閉じる
