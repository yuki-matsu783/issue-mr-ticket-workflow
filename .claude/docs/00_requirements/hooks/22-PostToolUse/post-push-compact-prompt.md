# post-push-compact-prompt フック

## 概要

push はタスクの切れ目と全体まとめで行われ、その直後に MR 本文の更新とレビュー依頼が続く。このフックは push の成功を検知し、レビュー依頼メッセージに載せる参照リンクを AI に渡し、切れ目の処理を終えたらユーザーに `/compact` を促すよう伝える。本書は GitLab の用語で書き、GitHub では MR → PR と読み替える。

- **背景**: レビュー依頼に MR や差分へのリンクが無いと、レビュアーが見に行くまでに一段の手間があり、どのファイルを重点的に見ればよいかも自力で探すことになる。また push 直後はコンテキストを整理する（`/compact`）のに適したタイミングだが、AI から促さないと忘れる。compact 後の現在地は `session-start` が再注入するため、compact しても作業は続けられる。
- **目的**: push 直後に、レビュー依頼に必要な参照リンクが AI の手元に揃い、ユーザーが `/compact` を打つ機会を得られる状態を実現する。
- **スコープ**:
  - 含む: push の成功の検知、参照リンクの組み立てと供給、前回 push 時点の記録、`/compact` の促し、記録
  - 含まない: レビュー依頼メッセージの作成と投稿（`00-workflow-issue-mr-driven` とレビュー依頼の提供コマンド）、push 前チェック（push の提供コマンド）、対応工数の集計（`post-push-usage-report`）

---

## ユーザーストーリー

**[As a]** レビュアーとして、

**[I want]** レビュー依頼に MR・差分・重点ファイルへのリンクが具体的な URL で付いていてほしい。

**[So that]** 依頼を読んだその場から差分に入れ、どこを重点的に見るかを迷わないため。

**[As a]** Claude Code で作業する開発者として、

**[I want]** push の直後に `/compact` のタイミングを AI から知らせてほしい。

**[So that]** タスクの切れ目でコンテキストを整理でき、長い issue でも AI の認識が崩れにくくなるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When AI が push の提供コマンドを実行し、それが成功したとき（HEAD がリモートに反映されたことをローカルの git の状態から確認できるとき）、Shall フックは働かなければならない。
- When push が失敗したとき、または push 以外のコマンドが実行されたとき、Shall not フックは何もせず、前回 push 時点の記録も更新してはならない。
- When push の提供コマンドの実行を検知するとき、Shall コマンドとして実際に実行される位置にある場合だけを対象にし、地の文・引用・コメントに語が現れるだけで働いてはならない（判定は `block-direct-git` と共有する）。
- When 緊急停止などにより `git` の push が直接実行され成功したとき、Shall フックは同じように働かなければならない。
- When push が成功したとき、Shall フックは次を AI に伝えなければならない: MR へのリンク、default ブランチとの差分へのリンク、今回の push で変わったファイルごとの「本体」と「差分ページ内の位置」へのリンク候補、このブランチで 2 回目以降の push なら前回 push 時点から今回までの差分へのリンクと MR のコメント一覧へのリンク。
- When リンクを組み立てるとき、Shall リポジトリの URL は origin の設定から、MR の番号と URL は機構が記録した進行状態から、変更ファイルと前回 push 時点はローカルの git とフック自身の記録から得なければならない。
- When GitLab と GitHub でリンクの形が異なるとき、Shall フックは origin から判定したホストに合わせた既知の形式で組み立て、URL 文字列を推測で書き換えてはならない。
- When 変更ファイルのリンク候補を伝えるとき、Shall 件数に上限を設け、超過分は件数だけを伝え、どのファイルを載せるか・本体と差分位置のどちらを載せるかは AI が判断しなければならない（フックは候補の供給に徹する）。
- When リンクが伝えられたとき、Shall AI はレビュー依頼メッセージ（レビュー依頼の提供コマンドに渡す本文）にそれらを含めなければならない。
- When 機構が MR を記録していないとき、Shall フックは MR に依存しないリンク（default ブランチとの差分・変更ファイル）だけを伝え、MR が未記録である旨を添えなければならない。
- When push が成功したとき、Shall フックは AI に「タスクの切れ目の処理（MR 本文の更新・レビュー依頼）を終えたら、ユーザーに `/compact` の実行を促すこと」を伝えなければならない。
- When AI がそのターンでユーザーに `/compact` を促すとき、Shall AI はユーザーへの確認の質問（`AskUserQuestion`）でセッションを塞いではならない（ユーザーがその場で `/compact` を打てるようにする）。
- When compact のあとにセッションが続くとき、Shall 現在地は `session-start` が再注入し、AI は続きから進められなければならない。
- When push が成功したとき、Shall フックはそのブランチの今回 push 時点（HEAD）を自身の記録として保持し、次回の push で前回時点として使えなければならない。記録はコミットの対象にしない。
- When ブランチが異なるとき、Shall 記録はブランチごとに独立していなければならない。
- When 全体まとめの片付けが行われるとき、Shall 前回 push 時点の記録は `logs/`（コミットの対象外・片付けの対象外）に置かれ、片付けのあとの最終 push でも前回 push からの差分を示せなければならない。
- When フックが AI に伝えたとき、Shall その記録（push の時点・伝えたリンクの要約）が残らなければならない。記録と伝える内容に環境変数の値・トークン・個人情報を含めない。
- When 伝えるとき、Shall 人間が読んでも分かる日本語で、リンクは具体的な URL として渡さなければならない。

### 代替フロー

- If issue と MR を作らずにチケット駆動だけを試す単独実行モードで動いている場合、Then フックは MR が未記録のときと同じ扱いで、MR に依存しないリンクだけを伝えなければならない。
- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは何も伝えず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If origin の取得・差分の取得・進行状態の読み取りに失敗した場合、Then フックは取得できた分だけを伝えるか、何も伝えずに通さなければならない（案内側の仕組み。push の結果や AI の操作を止めない）。
- If 前回 push 時点の記録が無い場合（初回の push、記録の消失）、Then フックは初回として扱い、前回 push からの差分とコメント一覧へのリンクを省いてその旨を添えなければならない。

## 前提条件

- push が提供コマンド経由で行われること
- ブランチ・MR 作成の task スキル（提供コマンド）が、作成した MR の番号と URL を進行状態に記録すること
- `origin` が GitLab または GitHub のリポジトリを指していること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。リンクの組み立てに使う情報はリポジトリ内のファイル・git のローカル操作・フックへの入力に限る。`post-push-usage-report` と同じ契機で働くため、両者の出力が互いを妨げない。判定の記録とセッションに紐づく状態はコミットの対象にせず、同じ作業ツリーで並行する別のセッションと分離する。記録・状態の置き場と寿命、拒否メッセージの識別子と緊急停止の環境変数の体系は、フック横断の仕様書が正として定める
- **ビジネス的制約**: どのリンクをレビュー依頼に載せるかは AI が判断し、フックは候補を供給するだけ
- **外部的制約**: `/compact` を実行するのはユーザーであり、AI もフックも代行しない

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | push 以外のコマンドでは外部プロセスを起動せずに体感できない時間で通す。push 後の組み立ても git のローカル操作だけで終える |
| セキュリティ | 記録と伝える内容に環境変数の値・トークン・個人情報を含めない |
| 可用性 | 取得に失敗しても push の結果や AI の操作を止めず、取得できた分だけを伝える |
| 一貫性 | リンクの形式は GitLab / GitHub それぞれの既知の形式に従い、`post-push-usage-report` と同じ push 検知を使う |
| テスト容易性 | origin の URL・進行状態・変更ファイル・前回 push の記録を与えて、伝える内容を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
