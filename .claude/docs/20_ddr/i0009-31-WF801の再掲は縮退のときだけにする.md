# i0009-31. WF801 の再掲は縮退のときだけにする

## 背景

`subagent-stop-check` は「PostToolUse `Agent` で、`subagent-start-check` の WF801 の記録も再掲する」ことになっていた。概要には「WF801 の再掲は**事後の保険**であり本線ではない。**PreToolUse の経路が使えない縮退のときだけ**、この再掲が唯一の通知経路になる」と書かれていたが、**制御方式にもテストにも条件が無く**、`SP-T05` は「WF801 の記録があれば再掲される」と**無条件**を固定していた。

境界レビュー（付録 A の R20）の指摘: 通常経路では PreToolUse で 1 回、PostToolUse で 1 回、**同じ不一致が 2 回**メインエージェントのコンテキストに入る。しかも 2 回目はサブエージェントが仕事を終えた後なので、回復手順（「止めて正しいモデルで起動し直す」）が既に無意味。「もう一度不一致が起きた」と読まれる危険もある。

## 決定

再掲に条件を付ける。

- 同じ `agent_id`（取れなければ同じセッションの直近）について、`decisions.jsonl` に `subagent-start-check` の WF801 の `notify` 記録が**無い**とき（= PreToolUse の経路が使えず縮退しているとき）**だけ**再掲する
- 概要の「事後の保険」という表現を「**縮退時の唯一の通知経路**であり、通常経路では出さない」に改める
- `SP-T05` を「記録が**ある**とき（通常経路）は再掲**しない**、**無い**とき（縮退）だけ再掲する」に書き直す

## 理由

- **説明と実装が食い違ったまま残るのが問題**。概要は既に「縮退のときだけ」と言っていたので、制御方式とテストを説明に合わせる（説明の方を「無条件に再掲する」に変える選択肢もあるが、2 回通知する設計を選ぶ理由が無い）
- **`decisions.jsonl` は既に全フックが書いている**ので、判定材料が増えない。`agent_id` は SubagentStop の入力にあり、PostToolUse `Agent` でも辿れなければセッションの直近で代替できる
- 2 回目の通知は回復の案内としても無意味（既に走り終わっている）。コンテキストを消費するだけ

## 却下した案

- **無条件の再掲を維持し、2 回目を「再掲・事後」と明示する**: 文面で区別できても、コンテキストは 2 回消費される。しかも通常経路では 1 回目（PreToolUse の `additionalContext`）も結果と同時に届く（`i0009-26`）ので、**ほぼ同時に 2 つ**入ることになり紛らわしい
- **PreToolUse 側の `additionalContext` をやめて PostToolUse に一本化する**: `i0009-26` で決めた `systemMessage`（ユーザーへの起動前の警告）と `additionalContext` は同じフックの同じ出力なので、片方だけ落とすと実装が不自然になる
- **記録ではなく環境変数やファイルでフラグを立てる**: `decisions.jsonl` に既にある情報を別の場所に複製することになる
