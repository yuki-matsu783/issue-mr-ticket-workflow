# 10-task-implementation-plan スキル 仕様

## 概要・禁止事項

実装・テスト計画タスクの内部仕様。対応する要件は [00_requirement/skills/10-task-implementation-plan.md](../../00_requirement/skills/10-task-implementation-plan.md)。処理フローの共通手順は `10_spec/skills/10-task-investigation-plan.md`「計画タスクの共通手順（正）」に従い、ここでは固有部分だけを書く。

禁止事項（共通手順の禁止事項に加えて）:

- ソースコード・テストコードを書き始めること（実装は実装チケット）
- 設計文書の書き換え（不備は設計差し戻しの提案として結果報告へ）
- 設計に無い機能・仕様に無い振る舞いをステップに入れること（別 issue 候補として結果報告へ）
- 検証手段（テスト ID）の無いステップを起こすこと

## 呼出条件

- `next` が実装計画チケットを示したとき、全体計画で合意した実行者（サブエージェント）で読み込まれる

## IN / OUT

| IN | OUT |
|----|----|
| 設計書（要件定義書・仕様書。テストシナリオとテスト ID）、全体計画書、issue の受け入れ条件、既存コードとテストの構成（読むだけ） | 実装計画書（`wip/20_plans/`、md + HTML）、実装チケット群、次の計画チケット 1 枚、結果報告 |

## IN / OUT サンプル

- 実装チケット: `0009-implementation.md`「ステップ 1: 空パスワードの検証（`auth/validate.ts`）。DoD: AUTH-T01・T02 が失敗ケース含め通る（`npm test -- auth`）」
- 結果報告の見てほしい点: 「ステップ分割の妥当性（検証可能単位か・依存順か）/ テスト ID とステップの対応の網羅 / 許可範囲案の広さ / 設計不備の指摘の妥当性」

## 処理フロー

共通手順に加えて:

- 設計書のテストシナリオに**テスト ID が無い**（または受け入れ条件に対応するシナリオが無い）場合、実装チケットは起こさず、不足を根拠付きで結果報告に書き、設計（`design`）の追加チケットを起こす提案を返す。計画書は「設計差し戻し待ち」として残す
- ステップは**検証可能な単位**（1 ステップ = 対応するテスト ID で合否が決まる）に分け、依存順に並べる。1 チケット = 1〜2 ステップ
- 実装チケットの DoD の型: 「{{対象}} が仕様書 {{節}} のとおりに動く」「テスト {{ID}} が失敗ケース（境界値・異常系）を含めて通る（実行方法: {{コマンド}}）」「既存のテストが通る」「仕様からの逸脱があれば作業ログに記録されている」
- **許可範囲案**（やってよいこと）はステップごとに書く場所（ディレクトリ・ファイル）を挙げ、必要最小限にする。テスト・ビルドの実行コマンドも含める
- テスト方針は TDD（テスト先行 → 失敗確認 → 実装）を既定とし、既存のテスト構成・コマンドに合わせる。CLAUDE.md の規約（可読性・単一責任・マジックナンバー禁止等）は参照して再掲しない
- 人間レビュー要否の既定（方針が無い場合）: 実装計画チケット「要」、実装チケットは `rules/work-defaults.md` に従う
- 見てほしい点の固定項目: ステップ分割の妥当性 / テスト ID とステップの対応の網羅 / 許可範囲案の広さ / 設計不備の指摘の妥当性（該当時）

## OUT ひな形

`assets/implementation-plan.template.md`:

| 節 | 内容 |
|----|------|
| 対象 | issue・MR・根拠とする設計書 |
| 変更対象 | 追加・変更するファイルとその理由（仕様書の節） |
| 許可範囲案 | ステップごとの書き込み先・実行コマンド |
| テスト方針 | TDD の進め方、テスト ID × ステップの対応表、実行方法 |
| ステップ | 順序・依存・チケット |
| 検証方法 | 全ステップ完了時の確認（既存テスト含む） |
| リスク | 影響範囲・巻き戻し方 |
| 保留した点 / 対象なし / 設計差し戻し | 該当時 |

## テスト観点（eval）

| eval ID | 入力（プロンプトと状況） | 期待する振る舞い | 判定方法 |
|---------|------------------------|-----------------|---------|
| IMP-E01 | アプリの仕様書を入力に実装計画を書く場面 | 実装ステップをテストが通る単位で区切り、計画書の記述順とチケットの実行順を一致させる | ステップの並びと `predecessors` の一致 |
| IMP-E02 | テスト方針を書く場面 | 仕様書からテスト ID を機械的に抜き出し、抜き出しの件数と割付表の行数が一致することを書く | 抜き出しのコマンドと件数の記載 |
| IMP-E03 | 仕様書にテスト ID が無い | 推測で補わず、不足を結果報告に書いて設計フェーズへの差し戻しを提案する | 結果報告の記載と、実装チケットの有無 |
| IMP-E04 | 名前やパスを変える修正を計画する場面 | それを入力・期待値に持つテストを検索で洗い出し、同じチケットの書き込み範囲に含める | チケットの `allow.write` と検索の根拠 |
