# アプリの成果物の置き場を apl/<アプリ名>/ 配下にする

## 背景

DDR `i0013-01` の決定により、チケットボード拡張のソースは `src/vscode-ticket-board/`、設計文書は `docs/00_requirement/` と `docs/10_spec/`、決定の記録は `docs/20_ddr/` に置かれている。当時の判断は「機構の許可範囲 `scope-limits.json` が実装に `src/**`、設計に `docs/**` を割り当てているため、その中に収める」というものだった。

この形は 1 つのアプリの成果物がリポジトリ直下の 2 つのディレクトリに分かれる。2 本目のアプリが来ると、`src/` と `docs/` のどのサブツリーがどのアプリのものかは名前の一致だけが頼りになり、境界が消える。実際 issue #20 でアプリ向けの設計文書の型を機構側に置こうとしたとき、「アプリの設計文書の置き場」を `docs/` と書くか `docs/<アプリ名>/` と書くかがその場で決まらなかった。

## 決定

- アプリの成果物は、アプリごとに `apl/<アプリ名>/` を[アプリルート](../90_glossary/ドキュメント体系用語.md#アプリルート)としてまとめる
- アプリルートの直下に、ソースを `src/`、テストを `test/`、設計文書を `docs/`、ビルド設定（`package.json` / `tsconfig.json` / 入れ子の `.gitignore`）を置く
- 設計文書は `docs/00_requirement/` / `docs/10_spec/` / `docs/20_ddr/` / `docs/90_glossary/` の 4 ディレクトリ構成とし、要件定義書と仕様書は 1 アプリ 1 対象で `<アプリ名>.md` の同名 1:1 とする（AI アセット側のような種類ディレクトリを持たない）
- `design-docs` ルールの適用範囲を `docs/**` から `apl/**` に変える
- `scope-limits.json` の許可範囲を、`design` / `design-feedback` は `apl/*/docs/**`、`implementation` は `apl/*/src/**` `apl/*/test/**` に変える
- 既存の `src/vscode-ticket-board/` は中身をそのまま `apl/vscode-ticket-board/` へ移し、`docs/` は `apl/vscode-ticket-board/docs/` へ移す

## 理由

- **境界がアプリ単位で閉じる**: アプリが増えても、1 つのアプリに関わるものは 1 つのディレクトリを見れば揃う。設計文書とソースが離れないので、仕様と実装の対応も追いやすい
- **ビルド設定を変えずに済む**: 拡張の `package.json`（`"main": "./out/src/extension.js"`、`"compile": "tsc -p ."`）と `tsconfig.json`（`"outDir": "out"` / `"rootDir": "."` / `"include": ["src/**/*.ts", "test/**/*.ts"]`）はすべてアプリルート相対で、ディレクトリごと持ち上げれば無変更で通る
- **許可範囲を設計と実装で分けられる**: `apl/*/docs/**` と `apl/*/src/**` に分ければ、設計タスクがソースを、実装タスクが設計文書を書き換えることを防げる。`apl/**` 一括にするとこの分離が失われる。照合器 `scope.sh` の `scope_match` に両パターンを与え、期待どおりに一致・不一致することを確かめた
- **拡張の動作に影響しない**: 拡張のチケット走査は `vscode.workspace.workspaceFolders?.[0]` を基点にしており、拡張ファイル自身の位置を参照していない

## 却下した案

- **`apl/` 直下に集約する（`apl/<アプリ名>/` にソース、`apl/00_requirement/` などに設計文書）**: 設計文書がアプリをまたいで 1 つのツリーに集まるため、アプリが増えたときに `apl/00_requirement/` の中でアプリ名のファイルが並ぶことになる。1 アプリ 1 ディレクトリの利点が消える
- **ソースだけ `apl/` に移し、設計文書は `docs/` のまま**: `design-docs` ルールを変えずに済み差分は最小だが、成果物が 2 か所に分かれる問題がそのまま残る。今回の変更の動機を満たさない
- **`src/<アプリ名>/` と `docs/<アプリ名>/` に揃える**: 許可範囲の書き換えだけで済むが、1 つのアプリを見るのに 2 か所を開く形は変わらない
- **`i0013-01` のまま据え置く**: アプリが 1 本のうちは実害が出ない。ただし issue #20 でアプリ向けの型を機構に固定する以上、型が前提とする置き場を先に決めないと、型のほうが後から動くことになる

## 影響

- `i0013-01`（成果物の置き場を src 配下にする）はこの決定に置き換えられる。同 DDR は本文を変更せず、frontmatter の状態を「置き換え済み」にして置き換え先をこの DDR に向ける（アプリ側の文書のため、設計反映フェーズで行う）
- `.claude/rules/design-docs.md` の `paths` と本文、`.claude/hooks/config/scope-limits.json` の許可範囲、`.claude/docs/10_spec/フック共通仕様.md` の許可範囲の表、`.claude/evals/design-docs.md` の前提が変わる
- 拡張のソース 5 ファイルのヘッダコメント（`仕様: docs/10_spec/vscode-ticket-board.md`）と `README.md` の参照は、アプリルート相対に更新する
- `docs/20_ddr/i0013-02`（アプリ向け仕様書の節構成）は決定内容が置き場に依存しないため、移動のみで本文は変えない
