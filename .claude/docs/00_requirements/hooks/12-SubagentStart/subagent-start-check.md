# subagent-start-check フック

## 概要

ワークとチケットの実施はサブエージェントに委ねられ、実行者（LLM モデル）は全体計画で合意されてチケットに書かれる。このフックはサブエージェントの起動時点で、起動したモデルとチケットの実行者の不一致を検知して伝え、作業中のチケットの要点をサブエージェントに注入する。

- **背景**: 誤ったモデルで起動しても、サブエージェントの完了後に気づいたのではワークが丸ごと誤ったモデルで実施された後になる（サブエージェント起動の操作の完了は、サブエージェントの終了と同時のため、操作のあとの検知では遅い）。また `session-start` はサブエージェントには何も注入しない設計のため、サブエージェントが自分のチケットの範囲・DoD を知る手段は起動時のプロンプトに依存する。
- **目的**: 起動の瞬間に実行者の不一致が分かって起動し直しの判断が早くでき、サブエージェントが自分のチケットの宣言を知った状態で作業を始められる状態を実現する。
- **スコープ**:
  - 含む: 起動したモデルとチケットの実行者の比較と通知、作業中のチケットの要点の注入、記録、緊急停止
  - 含まない: 不一致の拒否（行わない。続けるか起動し直すかは AI が判断する）、宣言した範囲の強制（`workflow-guard`。サブエージェントの中でも同じように働く）、サブエージェント終了時の整合チェック（`subagent-stop-check`）、起動するモデルの決定（全体計画とチケット）

## ユーザーストーリー

**[As a]** 全体計画で実行者を合意した開発者として、

**[I want]** 合意と違うモデルでサブエージェントが起動されたら、その場で知らせてほしい。

**[So that]** ワークが誤ったモデルで丸ごと実施される前に、起動し直せるため。

**[As a]** チケットを実施するサブエージェントとして、

**[I want]** 自分のチケットのやってよいことと DoD を作業の最初から知っていたい。

**[So that]** 範囲外に踏み出して拒否されてから気づくのではなく、最初から範囲の中で進められるため。

## 受け入れ基準（Acceptance Criteria）

### メインフロー

- When サブエージェントが起動され、作業中のチケットに実行者（LLM モデル）が書かれているとき、Shall フックは起動したモデルと比較し、異なる場合はその不一致（チケットの実行者・起動したモデル・対象のチケット）をメインエージェントに伝え、記録に残さなければならない。
- When 不一致を伝えるとき、Shall not フックは起動を妨げてはならず、続けるか起動し直すかは AI がチケットの実行者に従って判断しなければならない。
- When 起動したモデルとチケットの実行者が一致するとき、作業中のチケットが無いとき、または実行者の記載が無いとき、Shall not フックは不一致の通知をしてはならない。
- When 起動したモデルをフックの入力から特定できないとき、Shall not フックは通知をしてはならない（誤った警告を出さない）。
- When サブエージェントが起動され、作業中のチケットがあるとき、Shall フックはそのチケットの要点（チケット名・ワークの種類・やってよいこと・DoD）をサブエージェントのコンテキストに注入しなければならない。チケット本文の全文や、その他のファイルの中身は注入しない。
- When 作業中のチケットが無いとき（ワーク単位のサブエージェントで、チケットへの着手をこれから行う場合）、Shall not フックは何も注入してはならない（着手すべきチケットは起動時のプロンプトと提供コマンドが示す）。
- When フックが通知・注入を行ったとき、Shall その記録（対象のチケット・起動したモデル・注入の要約）が残らなければならない。記録と注入内容に機密情報を含めない。
- When 通知するとき、Shall メッセージは他のフックと機械的に区別できる識別子を持たなければならない。

### 代替フロー

- If 緊急停止が必要になった場合、Then AI は同じセッションの中で停止を設定できない（停止は環境変数の設定だけで行え、セッションの開始時にしか反映されない）ため、ユーザーに設定してほしい内容（機構全体の停止か、このフックだけの停止か）を伝え、新しいセッションでの実行を促さなければならない。停止が設定されたセッションでは、フックは通知も注入も行わず、停止していることが記録から分かるようにしなければならない。

### 例外フロー

- If 作業中のチケットが読めない・実行者の記載が解釈できない場合、Then フックは何も伝えずに通さなければならない（案内側の仕組み。チケットの記載の不正は `workflow-guard` が拒否する）。
- If フックの入力が解釈できない場合、Then フックは何もせずに通し、サブエージェントの起動を止めてはならない。

---

## 前提条件

- チケットが実行者（LLM モデル）・やってよいこと・DoD を機構が解釈できる形で持っていること（チケットテンプレート）
- Claude Code のフック機構がサブエージェントの起動時にフックを動かし、起動したモデルを入力から特定できること（特定できない場合は通知しない）
- 実行者として指定できるモデルはサブエージェントで選択できるモデルに限ること

---

## 制約条件

- **技術的制約**: 実体は bash で書き、Windows の git bash で動く。判定の材料はフックへの入力と作業領域のファイルに限る
- **ビジネス的制約**: 実行者の決定と変更は全体計画・未着手チケットの見直しで行い、フックは検知と通知だけを担う
- **外部的制約**: 起動は妨げない（拒否ではなく通知。起動し直しの判断は AI が行う）

## 非機能要件

| 項目 | 説明 |
|------|------|
| パフォーマンス | 起動のたびに働くため、判定と注入は体感できない時間で終える |
| セキュリティ | 記録と注入内容に環境変数の値・トークン・個人情報を含めない |
| 可用性 | 判定できないときは何もせずに通し、サブエージェントの起動を止めない |
| 簡潔性 | 注入はチケットの要点だけに絞り、全文や他のファイルを含めない |
| テスト容易性 | 起動の入力と作業領域の状態を与えて、通知と注入の内容を単体テストできる。テストは合否件数を出力し失敗時に非 0 で終わる |
